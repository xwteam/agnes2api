# デプロイガイド

**Language:** [English](../en/DEPLOY.md) | [简体中文](../zh-CN/DEPLOY.md) | [繁體中文](../zh-TW/DEPLOY.md) | 日本語 | [한국어](../ko/DEPLOY.md)

agnes2api は同一のコードベースとリクエスト処理ロジックから構築された 2 つの
デプロイ先を提供します。あなたのインフラに合わせてどちらかを選んでください。
両者の違いはストレージバックエンドのみです。Worker は Cloudflare KV
ネームスペースを、Docker はマウントされたボリューム上の JSON ファイルを使います。

## 環境変数

| 変数 | 必須 | デフォルト | 説明 |
|---|---|---|---|
| `GATEWAY_TOKEN` | **はい** | – | クライアントが本ゲートウェイを呼び出す際に提示しなければならないトークン。 |
| `RESET_CONFIG` | いいえ | – | 緊急脱出口: `1` にすると起動時にストレージ上の `config` キーを**完全に無視**し（無視するだけで削除はしません）、環境変数と組み込みのデフォルト値だけを使います。保存された設定が壊れてゲートウェイが起動しなくなったときの復旧用です。復旧したらこの行を消してください。消さないとパネルで保存した設定が永久に反映されません。 |
| `AGNES_BASE_URL` | いいえ | `https://apihub.agnes-ai.com/v1` | 上流 Agnes API のベース URL。 |
| `UPSTREAM_TIMEOUT_MS` | いいえ | `8000` | **ストリーミング**応答と動画ポーリングの最初のバイトのタイムアウト。この時間（ミリ秒）以内に上流の最初のバイトが届かない場合、呼び出しを中断する。 |
| `UPSTREAM_SYNC_TIMEOUT_MS` | いいえ | `120000` | **同期**エンドポイントの全体タイムアウト予算。「最初のバイトが、上流が結果全体を計算し終えてから届く」種類のリクエストにのみ適用される: 画像生成、動画ジョブ作成、そしてすべての**非ストリーミング**対話。詳細は下記。 |
| `MAX_STRIKES` | いいえ | `3` | 連続する一時的な失敗（タイムアウト、ネットワークエラー、上流 `5xx`）がこの閾値に達すると key を長いクールダウンに入れる。 |
| `COOLDOWN_RATE_LIMIT_MS` | いいえ | `60000` | 上流が `429` を返した後、その key に適用されるクールダウン時間。 |
| `COOLDOWN_PAYMENT_MS` | いいえ | `3600000` | 上流が `402` を返した後、その key に適用されるクールダウン時間。 |
| `COOLDOWN_STRIKE_MS` | いいえ | `1800000` | key の一時的な失敗が `MAX_STRIKES` に達した後のクールダウン時間。満了時に自動で復帰する。 |
| `POOL_CACHE_TTL_MS` | いいえ | `60000` | 各 isolate／プロセスが key プールのスナップショットをメモリ上に保持する時間。`0` でキャッシュ無効。**KV の読み取り回数はリクエスト数とは無関係**で、更新頻度だけで決まる。算出式は下記「クォータの見積もり」を参照。代償: 他の isolate が判定したクールダウン／除外が、この isolate に見えるまで最大で**この値 + 約 60 秒**かかる（60 秒分は KV のエッジキャッシュのデフォルト `cacheTtl`）。デフォルトの 60000 では上限は約 **120 秒**。しかも「見えるのが遅れる」だけではない: 古いスナップショット上で行われたスケジューリング系の書き込みはレコード全体を上書きしてしまい、他の isolate がその時間内に書いた `evicted` / `cooldownUntil` を**消してしまう**——その判定はもう一度やり直しになる。 **インスタンス構築時に一度だけ**読まれます（`src/http/wire.ts`）。変更はコンテナの再起動、または isolate の再生成後に反映され、**パネルで変更しても即座には反映されません**。 |
| `POOL_TOUCH_INTERVAL_MS` | いいえ | `21600000` | key の「最終使用時刻」を書き込む最大間隔。`0` で成功リクエストごとに書き込む。これは表示専用のフィールドでスケジューリングは一切読まず、リクエストごとに書くと無料枠の 1,000 回/日の書き込み枠を使い切り、クールダウンや除外すら書けなくなる。代償: 「最終使用」の精度はこの間隔まで粗くなる。同じ間隔はパネルの利用回数カウンター（リクエスト数／成功率）にも効く。**ストレージ上の `stats` を手作業で小さくすると（ゼロにするなど）、パネルは一旦その値を表示したあと、古い値に戻ることがある**: スナップショットは TTL ぶん後にゼロ化されたレコードを読むが、稼働中のインスタンスは自分が書き込んだ基準値を覚えていて、次に実際に書き込むときそれを書き戻すため。遅くともそのインスタンスが回収された時点で完全に一致する。**カウンターを消すには repo を経由する正式な経路を使うこと**: `PATCH /admin/api/keys/:id` に `clearStats` を付ける。これは**このリクエストを処理したインスタンス**が抱えている書き込み基準値と未書き込みの増分をまとめて破棄するので、**このリセットより後に始まったリクエスト**が古い値を書き戻すことはない。ただし**リセットの時点ですでに実行中だったリクエスト**はリセット前のレコードを持っており、完了時にその古い値から基準値を作り直す。同時に動いている**別の**インスタンス（別の isolate、または同じボリュームを使う別のコンテナ）もそれぞれ自分の基準値を持っており、古い値を一度だけ書き戻すことがある。**今日これは API だけで、パネルにこのボタンはない。** **インスタンス構築時に一度だけ**読まれます（`src/http/wire.ts`）。変更はコンテナの再起動、または isolate の再生成後に反映され、**パネルで変更しても即座には反映されません**。 |
| `USAGE_STATS_ENABLED` | いいえ | `false` | パネルの「使用量」セクションの Tier-2 時系列（日／時間／モデル／プロトコル別）。**判定は文字どおりの `true`** で、`1` や `yes` はオフ扱いです。**既定はオフで、その「オフ」はゼロコスト**です: メモリ上のアキュムレータを作らず、ストレージ書き込みも 1 回も発生しません。オンにすると 1 インスタンスあたり 1 日最大 13 回の put（書き込み枠の約 10.4%、isolate 8 個で合計 104 回/日）。使い切るとその日はもう書かず、次の UTC 日に回復します。未書き出しの尻尾は最長 2 時間です。詳細は下の「クォータ試算」の Tier-2 の項を参照。app のビルド時に 1 回読むため、変更はコンテナ再起動／isolate 回収後に効きます。 |
| `PORT` | いいえ（Node/Docker のみ） | `8080` | Node ランタイムのリッスンポート。Worker では使用されません。 |
| `DATA_DIR` | いいえ（Node/Docker のみ） | `/app/data` | ファイルストレージが `store.json` を書き込むディレクトリ。Worker では使用されません。 |

上表の変数はすべて `.env.example` に 1 行ずつ記載されています。`cp .env.example .env` の
後、必要な項目だけ書き換えてください。あのファイルのコメントは詳しさがまちまちで、
ほとんどの変数は 1 行、いくつかは十数行に及びます。取り得る値と代償は本表を参照して
ください。
上記の数値型の変数はすべて整数である必要があります。
`POOL_CACHE_TTL_MS` と `POOL_TOUCH_INTERVAL_MS` は下限が `0`（`0` は「無効」の意）で、
それ以外はすべて `0` より大きい必要があり、そうでない場合ゲートウェイは起動を拒否します。

`POOL_CACHE_TTL_MS` と `POOL_TOUCH_INTERVAL_MS` は **app の構築時に一度だけ**読まれます。
変更を反映するにはコンテナの再起動、または isolate の再生成を待つ必要があり、
他の設定項目のようにリクエストごとには反映されません。

### クォータの見積もり: Worker + 無料枠 KV で 1 日に何リクエストさばけるか

無料枠の KV は 1 日 100,000 回の読み取りと 1,000 回の書き込みです。ゲートウェイの読み書きは
どちらも**リクエスト数に比例しません**。したがって「1 リクエストあたり何回」ではなく
「1 日あたり何回」で見積もります。

- **デフォルト設定では KV はもうボトルネックではありません**。上限は Cloudflare Workers
  無料枠自体の **1 日 100,000 リクエスト**になります。ただしこの結論には**前提があり、
  無条件ではありません**: KV の読み取りクォータは代わりに「同時にアクティブな isolate 数」を
  制約します。それはトラフィックの地理的分布によって変わる量で、こちらから直接指定できません。
  アクティブな isolate 1 つあたり 1 日に

      (86400 ÷ POOL_CACHE_TTL_MS の秒数) × (1 + プール内の key 数)  +  2880

  回読み取ります。末尾の 2880 は設定ホルダーが 30 秒ごとに更新する分で、同じ枠を消費します。
  デフォルト値かつ key 20 本なら isolate あたり **33,120 回**。1 日 48〜96 回のインデックス
  照合を加えると、**アクティブな isolate が 3 つで約 99.4% を使い切ります**。つまり推奨設定の
  時点で既にぎりぎりです。isolate がそれ以上になる見込みなら `POOL_CACHE_TTL_MS` を大きく
  してください（key 20 本・isolate 5 つならおよそ `120000`）。
- **キャッシュを無効化**した場合（`POOL_CACHE_TTL_MS=0`、緊急脱出口）は読み取りがリクエスト数に
  比例して増え、下限はおよそ `100,000 ÷ (1 + key 数)` ⇒ key 20 本で **1 日約 4,700 リクエスト**。
- **書き込み側**: 定常状態では 1 日およそ `key 数 × 4` 回（`lastUsedAt` は 6 時間ごとに 1 回）。
  key 20 本なら 80 回で書き込み枠の 8%、残りはクールダウンと除外の記録用です。加えて各 key が
  初めて使われるときに一度だけ書き込みが発生します。
- **イベントボード（Task 6）の書き込み側**: 各 isolate は 1 日あたり最大 `EVENT_WRITES_PER_DAY`
  （**12**）回まで書き込みます。超えると `budgetExhausted` が正直に報告され、黙って捨てたり
  再試行したりはしません。**この閘門は単一の isolate 内でのみ有効**であり、全体として安全か
  どうかは「同時実行 isolate 数 × この値」が予算内に収まるかどうかに依存します——1 つの
  isolate は他の isolate がどれだけ予算を使ったか知る術がありません（CAS も isolate 間の
  調整もありません）。**8 並行 isolate**で見積もると（この節の他の箇所で使っている 3 より
  保守的です。トラフィックが少ない個人利用のゲートウェイでも、Cloudflare のエッジは世界中に
  あり、実際に何個の isolate が並行するかを完全には制御できないため）: `12 × 8 = 96` 回/日、
  書き込み枠の **9.6%**。上記の key プールの書き込み側（80 回/日、8%）と合わせると、合計
  約 176 回/日（**17.6%**）で、約 82% の余裕が残ります。**この試算はレビューで実際の問題が
  見つかったために存在します**：初期版は 1 時間単位で予算を数え、各 isolate が独立して
  1 時間あたり最大 12 回まで数えていたため、isolate が 4 つあるだけで書き込み枠を突破できて
  しまいました（`4 × 12 × 24 = 1,152`、1,000 を超過）。修正として予算のウィンドウを「1 時間
  ごと」から「1 日ごと」に変え、この試算をここに書き残しました。同じ修正で、コールドスタート
  した isolate の最初のフラッシュがスロットリングを回避してしまう抜け道も塞ぎました——
  以前は isolate がコールドスタートするたびに無条件の書き込みが 1 回発生していましたが、
  現在はコールドスタート後の最初のフラッシュも他のフラッシュと同じ最小間隔の閘門を通ります。
- **レジストラの書き込み側（P3c Task 1 で追加）——この節全体は `registrar.enabled` が
  true のときにだけ存在します。** 既定のデプロイ（レジストラはオフ）では、この節が追加する
  書き込みは **0 回/日**であり、「少し減る」ではありません。オンのとき、補充の 1 巡ごとに
  3 つの項目を払い、**すべてが「補充頻度」という 1 本の軸にぶら下がっています**
  （Worker では `wrangler.toml` の Cron、既定 `*/30 * * * *` = 1 日 48 巡。Node では
  `TEND_INTERVAL_MS`）:
    - **補充ロック**: 1 巡あたり put 1 回 + delete 1 回。この項目は今回より前から存在して
      いましたが、この試算に書かれたことが一度もありませんでした。
    - **補充イベントの保存**: 1 巡あたり最大 put 1 回。**書くかどうかを決めるのは
      「この巡のイベントバッファが空かどうか」**であって、イベントの名前ではありません。
      健全で、**かつ設定も健全**な 1 巡はイベントを一切出さないので 0 回です。
      ⚠️ **「健全なら 0」には前提があり、それを明記します**: `loadConfig` は
      `TEND_INTERVAL_MS` が `MINT_BATCH × CODE_TIMEOUT_MS × チャネル数`
      （既定で `5 × 120000 × 1 = 600000`、つまり 10 分）を下回るとき、
      **毎巡かならず**設定警告を 1 件出します。その設定では**何も鋳造しない巡でも
      毎回 1 回書き込みます**。
    - **補充履歴（`tend:history`）**: 1 巡あたり get 1 回 + put 1 回、**無条件**。
      単一キー、ファンアウトなし。
  ⚠️ **この 3 つを `EVENT_WRITES_PER_DAY`（isolate ごとに 1 日 12 回）で理解しないでください。**
  あの閘門は `fetch` 経路のためのもので、「1 つの isolate が多数のリクエストを処理し、予算が
  長命なインスタンス上で繰り返し消費される」という前提に立っています。補充経路では 1 巡ごとに
  **まったく新しい isolate**（Worker の `scheduled()`）である可能性が高く、生涯に 1 回だけ
  保存し、毎回まっさらな予算を持ちます ⇒ **この軸ではあの閘門は何も止めず、上界にもなりません**。
  本当の上界は補充頻度そのものです: **Cron を詰める、あるいは `TEND_INTERVAL_MS` を小さくすると、
  この 3 項目は同じだけ増えます。**
- **パネルの書き込み操作の書き込み側（P3c で追加）——「人がクリックしたときだけ起きる」ので、
  上の定常状態の勘定には入りません。** 頻度の上界は語れません（上界は運用者の手です）。
  そこでここでは**操作ごとの単価**を示します。以下の数値はすべて実測の読み取り値で、
  **1 マスずつ数えたもの**です: key の書き込み操作は `tests/contract/admin-keys-write.test.ts`、
  「今すぐ補充」は `tests/contract/manual-tend.test.ts`、設定ページの 2 本は
  `tests/contract/admin-config.test.ts`。
  （この一文は以前 1 つ目のファイルしか挙げていませんでしたが、「今すぐ補充」の行はそれとは
  無関係で、当時どのマスもそれを数えていませんでした——全ブランチレビュー I4。
  直し方はその 1 マスを足すことであって、この一文を弱めることではありません。）
    - **新しい key を M 本インポート**: put `M + 1` 回（記録 M 本 + 索引 1 回）、get `M + 1` 回、
      **list 0 回**。1 回のインポートは最大 200 本（超えると 400、**黙って切り捨てません**）
      ⇒ 1 クリックの上界は **put 201 回**、つまり 1 日の書き込み配分の 2 割です。
      何回かに分けても安くはなりません（索引の 1 回は毎バッチ払います）。
    - **重複インポート**（同じ key をもう一度貼り、「既存 key の状態をリセット」に
      チェックを入れない）: **put 0 回**。重複はデフォルトでスキップ、上書きしません。
      リスト全体をもう一度貼るのは安全かつ安価です。
    - 「既存 key の状態をリセット」にチェックを入れた場合: **すでにプールにある** key 1 本ごとに put 1 回。
    - **key を 1 本変更**（停止 / 再開 / メモ / クールダウン解除 / strikes クリア / 除外解除 /
      利用回数のリセット）: get 1 回 + put 1 回。**上のどの操作も同じ単価**——同じ handler、
      同じ 1 回の書き込みを通り、利用回数のリセットは余分な読み書きを一切しない
      （消しているのはメモリ上の書き込み基準値）。
    - **key を 1 本削除**: get 2 回 + put 1 回（索引）+ delete 1 回。
    - **N 本の一括停止 / 一括クールダウン解除**: get N 回 + put N 回。
    - **N 本の一括削除**: get `N + 1` 回 + put **1** 回（索引は 1 回だけ）+ delete N 回。
    - **「今すぐ補充」を 1 回押す**: 固定で put **3 回**（ガードキー + ロック取得 + 補充履歴）
      + delete 1 回（ロック解放。別バケット）。さらに**実際に発行できた key 1 本につき
      put 2 回**（レコード + 索引）。これは**1 日あたりの上限を持つ唯一のパネル操作**で、
      1 日最大 **24** 回（4 つ目のガードレール、[REGISTRAR.md](REGISTRAR.md) 参照）⇒
      持続可能な値は `24 × 3 = 72` 回/日、下の 3 行目の 320 に足すと **392 回/日（39.2%）**。
      毎回デフォルトの `MINT_BATCH = 5` を満たす場合の上限は `24 × 13 = 312` ⇒
      **632 回/日（63.2%）** ですが、その行は一時メールボックスの枠と `TARGET_KEYS` が先に
      限界に達するため持続しません。**このゲートを足す理由は「突き抜けるから」ではなく
      「余裕がないから」です**：10 分のクールダウンだけなら上限は `24 × 6 = 144` 回/日
      = put 432 回、320 に足すとすでに 75%。しかもその 320 のうち 96 は
      `12 × 同時 isolate 数` であり、**自分では調整できません**。
    - **設定を 1 回保存**（`PUT /admin/api/config`）: **put 1 回** + get 3〜4 回
      （書き込み前に `readAll` 1 回 + 生の読み取り 1 回、書き込み後に `readAll` で 1 回読み戻し。
      続けてもう一度保存するときは直前の `invalidate()` により設定リフレッシュのミドルウェアが
      もう 1 回読み、診断状態の分岐でも同様に 1 回増えます）。
      **検証に落ちた回は put 0 回 + get 2〜3 回** —— 1 バイトも書きません
      （保存の直後は同様に 1 回多く読みます。上と同じ理由です）。
    - **資格情報を 1 本クリア**（`POST /admin/api/config/secrets/clear`）: **put 1 回** + get 2 回。
      `gatewayToken` をクリアする分岐（クリア後はこの設定が読み込めなくなる）は get 3 回。
    - **ドライラン検証**（`POST /admin/api/config/validate`）: **put 0 回** + get 1 回。
    - **設定のリセット**（`/admin/api/config/reset`、設定ページの危険ゾーン 1 つ目のボタン）:
      **put 1 回** + get 2 回（書き込み前に 1 回、書き込み後にもう 1 回読み戻す）。
      ストレージ上の設定 1 件をまるごと空に書き戻します。**消費するのは put のバケットで、
      delete のバケットではありません**——キーを削除せず空の値を書くのは、KV の削除
      トゥームストーン系の問題を避けるためです。
    - **Key プールの全削除**（`/admin/api/keys/purge`、危険ゾーン 2 つ目のボタン）:
      **delete N 回（N = プールサイズ）+ put 1 回**（索引の書き込みは 1 回だけ。
      一括削除と同じ判断です）。
      ⚠️ **無料枠の delete バケットは 1 日 1,000 回**（読み取り・書き込み・list とは別枠）⇒
      **N が 1,000 に近づくと、このボタン 1 つでその日の削除枠を使い切ります**。
      プールが大きいほど高くつきます。読み取り側はプールスナップショット 1 回
      （isolate キャッシュに当たれば get 0 回）と読み戻し 1 回。空のプールでもう一度押すと
      delete 0 回・put 0 回です。
  ⚠️⚠️ **上の「設定を 1 回保存」と「資格情報を 1 本クリア」には 1 日あたりの上限がありません。
  これは意図的であって、抜けているのではありません。** どちらも管理者トークンを要し、人が
  クリックしたときにだけ起きます——自動経路からは触れません。ストレージのガードレールを
  付けること自体が read-modify-write（ガードキー）を 1 回増やす、つまり書き込みを 1 回節約する
  ために先に 1 回払うことになります。**沈黙で「何かの予算が見ている」と思わせないよう、
  代償をここに明記します**: 1 回のチューニング作業で数十回保存するのはまったく普通の運用で、
  数十回の put は 1 日の書き込み配分の数パーセントです。そして「今すぐ補充」の 1 日 24 回の
  ゲートは**この 2 本には効きません**。余裕を見積もるときはこの点を踏まえてください。
  ⚠️ これらは下の 3 列と**足し合わせません**: 3 列は「誰も操作しないときに 1 日何回」、
  この節は「1 クリックあたりいくら」です。気にすべき形は 1 つだけ——
  **一度に数百本の key をインポートすること**。パネルで最も高価な 1 クリックです。

- **書き込み側の合計、`registrar.enabled` を軸に 3 列**（key 20 本、並行 isolate 8 個の口径）:

  | シナリオ | put/日 | 書き込み枠に占める割合 |
  |---|---|---|
  | **レジストラがオフ（既定）**、誰も操作していない | **176** | **17.6%** |
  | レジストラがオン、**毎巡が健全**、誰も操作していない | **272** | **27.2%** |
  | レジストラがオン、**毎巡が失敗イベントを出す**、誰も操作していない | **320** | **32.0%** |

  ⚠️ **この 3 つはいずれも上界ではなく「現在の値」です。** 96 回/日の項目は
  `12 × 並行 isolate 数` に等しく、その数はトラフィックの地理的分布によって変わり、
  **あなた自身にも設定できません**。余裕を見積もるときはこの点に従い、272 や 320 を
  天井と考えないでください。
  **`delete` 枠**は別勘定です: 補充ロックが 1 日 48 回解放しますが、この枠は今日ほぼ空いています。

  ⚠️ **この 3 項目はすべて 1 巡あたりで課金されます。そして「1 日に何巡か」には
  互いに独立した 2 本の軸があります。混ぜて読まないでください:**
    - **頻度軸**: 補充頻度を詰めると 3 項目は**比例して増えます**（上の一文がそれです）。
      **Worker 形態でのつまみは `wrangler.toml` の Cron**、Node 形態では
      `TEND_INTERVAL_MS` です。`TEND_INTERVAL_MS` は **Node のスケジューラだけが
      消費します**——Worker 側でこれを変えても**1 巡も増えません**。逆に
      `registrar_tend_lock` の put/delete は**両方のランタイムに存在します**
      （P3c Task 5 以降、Node 側も同じロックを取ります——複数のコンテナが 1 つの
      ボリュームを共有する構成では、プロセス内の真偽値は役に立ちません）。
    - **閾値軸**: `TEND_INTERVAL_MS` が `MINT_BATCH × CODE_TIMEOUT_MS × チャネル数`
      を下回ると、イベントの項目が**「健全な巡は 0 回」から「毎巡 1 回」へ跳ねます**。
      この跳ねは頻度とは無関係で、上記の毎巡出る設定警告が原因です。
  **最悪なのは 2 本の軸が重なったときです。** 本節は Worker + 無料枠 KV の話なので、
  **その形態で完全に合法な**例を挙げます: Cron を `*/5 * * * *` に変更 ⇒ 1 日 288 巡、
  かつ毎巡イベントが出る ⇒ `80 + 96 + 288 + 288 + 288 = 1,040` 回/日で、
  **すでに書き込み枠を超えています**。
  上の 3 行はいずれも既定の Cron（30 分に 1 巡）を前提にしています。**頻度に依存しない
  定数として読まないでください。**

- **Tier-2 使用量統計の書き込み側（P3d で新規、`USAGE_STATS_ENABLED`、**既定はオフ**）
  —— 今期で唯一の新しい書き込み元です。**

  **オフの間、この項目の書き込みは常に 0** です。メモリ上のアキュムレータも作らず、
  `storage.put` は 1 回も発生しません。これは「ついでの節約」ではありません。上の
  key プールの 80 回/日と**同じ** 1 日 1,000 回の書き込み枠を奪い合っており、統計が
  書き込み枠を食い潰すと key プールのクールダウンと除外の記帳まで道連れになります。

  オンにした場合: **1 インスタンスあたり 1 日最大 13 回の put**。並行 isolate 8 個で
  見積もると `13 × 8` = **104** 回/日、書き込み枠の約 10.4% です。4 つのシナリオの合計:

  | シナリオ | put/日 | 書き込み枠に占める割合 |
  |---|---|---|
  | **Tier-2 オフ（既定）**、レジストラもオフ | **176** | 17.6% |
  | Tier-2 オン、レジストラはオフ | **280** | 28.0% |
  | Tier-2 オン、レジストラもオンで毎巡が失敗イベントを出す | **424** | 42.4% |
  | 上の行 + 10 分ごとに「今すぐ補充」を 1 回押す | **856** | 85.6% |

  ⚠️ **最悪の行に余裕はなく、上の 3 列と同じくこの表も上界ではありません。** 正しい読み方は
  次のとおりです: **Tier-2 の 104 はこの表で唯一ハードゲートを持つ項目**（下の ③）であり、
  他のどの項目にもゲートはありません。

  この 13 回の内訳は以下の 4 点で、すべて読む必要があります。

  ① **12 回の書き出し + 1**。書き出しの最小間隔は **2 時間**なので 1 日に入るのは最大 12 回。
     この `+1` は余裕ではなく、**UTC 0 時をまたぐ書き出しがキーを 2 つ書く**という事実です
     （前日分が 1 つ、当日分が 1 つ）。12 にすると 24 時間ごとにちょうど 1 回、書き込みが
     予算に拒否されます —— データは失われません（その日は未書き出しのまま残り、次の巡で
     拾われます）が、②の「最長 2 時間」という約束が 4 時間になります。

  ② **未書き出しの尻尾は最長 2 時間で、その 2 つの症状は 1 つの事実であって 2 つではありません**:
     パネルの「今日」の数字は最大 2 時間古くなり得ること、そして**2 時間に満たない寿命の
     インスタンス**（短命な Worker isolate、素早い Docker 再起動）が**貯めたカウントごと
     消えること**です。計時はインスタンスの起動時点から始まるので、10 分しか生きなかった
     isolate は 1 文字も保存できません。これは使用量の数字に終始「≈」が付く理由の 1 つであり、
     欠陥ではありません。

  ③ **1 インスタンスあたり 1 日 13 回の put はハードゲートです**: 使い切るとその日はもう
     書かず、**次の UTC 日に自動的に回復**し、溜まっていた日の分は回復後に書き出されます
     （メモリ上のアキュムレータは消されません）——**ただしそのインスタンスが生きている
     ことが前提です**。
     ⚠️ **この半文は Worker 形態では構造的に到達しません**: アキュムレータはメモリ上にしか
     なく、Worker の isolate は通常、次の UTC 日まで生き残りません（上の ② と同じ話です:
     10 分しか生きなかった isolate は 1 文字も保存できません）。つまり Worker で
     「回復後に書き出される」が成立するには**同じ isolate が UTC 0 時をまたいでいる**必要が
     あり、それは常態ではなく例外です。またげなかった場合、その数日分のカウントは
     **インスタンスとともに消えます —— 遅れて計上されるのではありません**。
     ⚠️⚠️ **Docker 形態ではこの閘門そのものが存在しません**。したがってこの約束はそちら側
     には当てはまりません: 1 日の書き込み予算があるかどうかは**ストレージに書き込み
     クォータがあるかどうか**だけで決まり（判定基準は下の ④）、ファイルストレージには
     ありません ⇒ 予算は空（`budgetPerDay = null`）で、使い切ることもなく、したがって
     「回復」も「書き出し直し」もありません。**「Docker なら 13 回の閘門に当たっても
     データが消えない」と読まないでください —— Docker にその閘門はありません**。
     そちら側で失われるのは上の ② の尻尾（プロセス停止時、未書き出しの最長 2 時間）です。
     ⚠️ このゲートは**単一インスタンスの内部でのみ有効**です —— isolate が 8 個なら
     13 回の枠が 8 つ独立に存在します。上のイベント枠とまったく同源で、
     インスタンス間の協調はありません。

  ④ **2 つのランタイムの挙動は完全に同一で、ランタイム判別は行いません。** 書き出し間隔の
     **既定値**は両側で同じ値・同じコードパスです（リクエストの締めくくりで
     **書き込み完了を同期的に待ちます**。バックグラウンド処理ではありません —— Workers では
     応答を返した後に isolate が止まり、バックグラウンド処理は黙って打ち切られます）。
     `USAGE_FLUSH_INTERVAL_MS` で上書きできますが、**判定基準は「あなたのストレージに
     書き込み枠があるか」であって「どのランタイムで動いているか」ではありません**:
     · **ファイルストレージ（Docker）には書き込み枠がない** ⇒ 任意の正の整数を受け付け、
       **1 日あたりの書き込み予算もなくなります**。上界は間隔そのものです。
       300000（5 分）に戻すのは十分妥当です。
     · **KV（Workers）には書き込み枠がある** ⇒ 予算は 1 インスタンス 1 日 13 回のままで、
       間隔は `間隔 × (13 − 1) >= 1 日` を満たす必要があります。破ると**起動時にエラー**になり、
       使用可能な最小値（7200000）を知らせます。黙って受け入れないのは意図的です:
       そういう値でも書き込み量は基準内に見えますが、**データは昼過ぎから嘘になります**。
       起動しないより気づきにくいのです。

  ⑤ **同じ日について残るのは最大 2 インスタンス分で、それを超えると互いに上書きします。**
     使用量シャードは `usage:<UTC 日>:<スロット>` で保存され、**スロットは 2 つしかありません**。
     各インスタンスは自分のシャード id で安定して振り分けられます。⇒ 上で isolate 8 個として
     算出した 104 回/日は**書き込み量**であって「8 個分のデータが全部残った」ではありません。
     同一スロットでは後勝ちです。**これも使用量の数字に「≈」が付く理由の 1 つです**
     （もう 1 つは ② の尻尾）。書き込み枠には影響せず、数字の完全性にだけ影響します。
     「≈」が意味しているのはこれです。

  ⑥ **メディアの 3 つのエンドポイント（画像生成・動画作成・動画取得）は集計に入りません。**
     4 つの対話プロトコルと**同じ上流 key を消費します**が記帳しないため、パネルの
     「総リクエスト数」は実際の転送量より系統的に小さくなります。今期の既知の境界であり
     欠陥ではありません。key の消費量は key プール側の数字で判断してください。

- **Tier-2 用量の読み取り側 —— 消費するのは 1 日の読み取り配額ではなく、「1 回の呼び出しで
  何本のサブリクエストを出せるか」です。** `/admin/api/usage` の `30d` の枠は、
  **1 回のリクエストで `USAGE_DAY_RETAIN × USAGE_SLOTS` = `30 × 2` = 60 回の KV get** を
  発行します（`src/core/admin/usage-stats.ts`）。1 日 100,000 回の読み取り配額に対して
  この 60 回は無視できます。**プラットフォームの保証がないのは 1 回の呼び出しあたりの
  サブリクエスト本数のほうです**: Cloudflare の Workers limits ページはこれを 2 行に
  分けています——「Subrequests per invocation」は無料プラン **50**、
  「Subrequests to internal services」は無料プラン **1,000**。ところがそのページは
  internal services の定義を一切書いておらず、KV バインディングの呼び出しがどちらの行に
  当たるかも書いていません。一方 KV 自身の limits ページには
  「Operations/Worker invocation」**1,000**（無料プランと有料プランで同一）とあります。
  **2 つのページが食い違っており、実機で決着させてもいません** ⇒ KV のページで読めば
  60 回は 6%、50 の行で読めば **60 は超過** です。したがって `30d` の枠は Worker 上で
  Node と挙動が異なる可能性があり、本ゲートウェイが保証するのは**正直に失敗すること**
  だけです: 読み取りのファンアウトが途中で失敗すると**`days` 全体が `null` になり**
  （パネルは `—` を表示）、`note` は `read_failed` になります。500 を返すことも、
  読めた分の分片を全体として扱うこともしません。
  ⚠️ **下のイベントボードの 48 回のコールドリードを根拠にしないでください** ——
  48 は上記のどちらの読み方でも合法であり、「60 が大丈夫かどうか」については一言も
  語っていません。無料プランでこの枠を安心して使うには、まず実機で測る必要があります。
- **Playground の動画: 1 タスクあたり最大 `1 + 60` 回の上流リクエスト**（作成 1 回 +
  最大 60 拍のポーリング、`VIDEO_POLL_MAX_ATTEMPTS`）。⚠️ **この 61 倍が拡大するのは
  上流側の配額と key の使用回数だけで、KV の 1 日の書き込み配額は拡大しません**:
  `lastUsedAt` と用量カウンターは `POOL_TOUCH_INTERVAL_MS`（既定 6 時間）の書き込み
  抑止ゲートに守られており、1 回のポーリングでは書き出し間隔を満たせません。

- **イベントボードの読み取り側（評価 C4/C4b 修正後の実データ。以前の草稿より保守的）**:
  ポーリングはもう索引に依存せず、候補キー数は**厳密に有界**です——`after` がどれだけ古くても、
  デプロイがどれだけ長く動いていても、1 回のリクエストが走査するのは最大でも 24 個の時間
  ウィンドウ × 2 個のスロット = **48** 回の get です（評価 C4 の修正前は、古い、あるいは
  悪意ある `after` によって 1 回のリクエストが約 100 万回の get に達することがありました。
  `tests/contract/quota-panel.test.ts` の回帰テストを参照）。`after` が直近の時間ウィンドウ
  内にあるときは「ウォームリード」で、通常は 2 回の get だけで済みます（ポーリングが時間
  ウィンドウの境界をまたぐ瞬間だけ 4 回）。
  **「有界」は「アクティブさと無関係」を意味しません**——評価 C4b が指摘した直感に反する
  結論は次のとおりです：
    - **新しいイベントが継続的に発生する「アクティブ」なデプロイ**: 新しいイベントが
      ポーリング間隔を常に最短の 15 秒に押し戻し、ほとんどのポーリングがウォームリードに
      なります。最悪ケース（毎回 4 回/ポーリング）で見積もると：`(86400 ÷ 15) × 4 = 23,040`
      回/日（読み取り枠の約 23%。実際にはウィンドウ境界をまたぐポーリングはごく一部なので、
      通常はこれよりずっと低くなります）。
    - **長期間新しいイベントが発生しない「静かな」デプロイ**（デプロイ直後でまだ診断
      イベントが一度も発生していない場合を含む）: `after` カーソルはいつまでも新しい値を
      得られず、凍結したカーソルが 24 時間の保持ウィンドウから外れた時点で、**それ以降の
      すべてのポーリングが満額の 48 回の get になります**。同時に新しいコンテンツがない
      ため、指数バックオフによってポーリング間隔は上限の 60 秒まで押し上げられます。
      定常状態は `(86400 ÷ 60) × (48 + 1) = 70,560` 回/日（読み取り枠の約 **71%**）です。
      ⚠️ **この数値は「定常状態のアイドル包絡」であって上界ではありません。** ボードを開いた
      まま誰も触らない状態を前提にしています。対話的な経路は含まれません: レベル絞り込み
      ボタンを 1 回押すごとに満額のコールドリードが 1 回発生し、このボードに戻る、タブが再び
      可視になる場合も即座に 1 巡します——**いずれも今日はスロットリングされていません**。
      式の `+1` は**ポーリング 1 巡ごとにそれ自身が引き起こす設定読み取り**です。設定更新
      ミドルウェアは全ルートより前に走り、設定キャッシュの TTL は 30 秒——60 秒のポーリング
      間隔より短いので、1 巡ごとにちょうど 1 回余分に読みます。これは下の key プールの計算に
      ある `86400 ÷ 設定 TTL 秒数` の項と**同じバケット**を消費します（あの項は上限の
      2,880 回/日という値で、パネルだけが動いている isolate が実際に使うのは 1,440 回）。
      二つの計算を合算するときに**二重に数えないでください**。
      **診断イベントをほとんど発生させないほど健全なデプロイの方が、1 つのパネルタブを
      開くだけで「アクティブ」なデプロイよりも多くの読み取り枠を消費してしまう**、という
      直感に反するが事実の結論です。読み取り枠の余裕を計画する際は、この大きい方の数値を
      基準にしてください（小さい「アクティブ」側の数値ではなく）。特に上記の key プールの
      読み取り側と合算する場合（上記の「アクティブな isolate が 3 つで約 99.4% を使い切る」
      というシナリオを参照）は注意が必要です。
    - **ダウンロードエンドポイント**（`GET /admin/api/events/download`）はクリックのたびに
      固定で 48 回の get を消費します（`readEvents(null)` は常にコールドリードで、カーソルを
      使いません）——これは手動クリック時にのみ発生し、規模としては無視できますが、
      正確を期すためここに記録しておきます。
  どちらのシナリオも、上限は**デプロイの稼働日数が増えても増加し続けることはありません**
  ——この部分は C4 の修正後も引き続き成り立ちます。

  枠とは独立しています。定常状態の転送では `list` は一度も発生しません——`pool:index` という
  インデックスキーはまさにそのために存在します。消費するのは**4 か所**です: 1 日 48〜96 回の
  インデックス照合（補充スケジュールの各ラウンド冒頭で 1 回ずつ）、**パネルの「今すぐ補充」**
  （P3c 以降、そのラウンドで実際に key を発行できた場合は締めくくりにもう一度照合します
  ⇒ 1 日あたり最大 24 回追加、上界はそのガードレール自身です——この 1 か所はこの一覧から
  漏れており、さらにこの文は照合を「独立してスケジュールされるジョブ」と限定していましたが、
  P3c 以降は**運用者が手動で起動する**消費者も持ちます。全ブランチレビュー I2）、
  **プールが空のときのフォールバック
  走査**（インデックスは正常なのに生きたレコードが 1 件も読めない場合、手動でインポートされた
  レコードがインデックスに入っていないかを確認するため `list` を 1 回だけ実行します）、そして
  **インデックス欠損時のフォールバック**（`pool:index` 自体が読めない、または壊れている場合に
  同じく `list` を 1 回実行してインデックスの再構築を試みます。多くは書き込み枠を使い切って
  インデックスがいつまでも作れなかったケースです）。後者 2 つは組み込みの **10 分**のバック
  オフを**共有します**（環境変数ではなく固定の定数）——どちらも同じ `list` 枠に向かうので、
  別々に窓を開いても意味がありません——したがってプールが空、またはインデックスが壊れている
  間でも isolate あたり 1 日最大 144 回で、インデックス照合の 48〜96 回とパネルの最大 24 回を
  足してもまだ余裕があります。
- **`list` の枠を使い切ると、劣化ではなく機能停止になります。** プールが空で `list` が失敗した
  場合、ゲートウェイは `500` を返し、本当の原因をログに書きます。**`503 pool_empty` には
  偽装しません**——このとき照合も同じ枠を使っていて同様に失敗しており、本ドキュメントが示す
  2 つの自己修復経路がどちらも失われているからです。UTC の日付が変わってクォータが
  リセットされるまで回復しません。

**上記の読み取り式には「isolate が TTL より長く生きる」という前提があります。** トラフィック
が少ない、あるいは十分に多くの Cloudflare エッジロケーションに分散している場合、isolate は
1 つの TTL が経過する前に回収されることが多く、その場合は各 isolate が生涯に少なくとも 1 回は
プールを読み込むため、読み取り回数は TTL ではなく**コールドスタート回数**で決まります。上限は
おおよそ `100000 ÷ (プール内の key 数 + 2)` 回のコールドスタート/日です（`+2` はインデックスと
設定それぞれ 1 回分）。**この領域では `POOL_CACHE_TTL_MS` を大きくしても読み取りは 1 回も
節約できません**——節約できるのは「同じ isolate 内での重複読み込み」だけです。

同じ理由で、プールが空のとき／インデックス欠損時の `list` のバックオフも**インスタンスごと**
です。冷えた isolate はそれぞれ自分のコストを払うので、合計は isolate の数に比例して増えます。

### 管理パネル関連の変数（P3、デフォルトで無効）

| 変数 | 必須 | 既定値 | 説明 |
|---|---|---|---|
| `ADMIN_TOKEN` | いいえ | なし（パネル無効） | 管理エンドポイントのトークン。**`GATEWAY_TOKEN` と異なる値**であること、かつ 24 文字以上であることが必須。さらに**先頭・末尾に空白があってはいけません**: HTTP はヘッダー値の前後の空白を除去しますが環境変数は保持するため、空白付きのトークンはどのクライアントからも送信できません。さらにトークンは**印字可能な ASCII（0x20–0x7E）のみ**で構成する必要があります。この制限には性質の異なる 3 つの理由があります: ① U+00FF を超える文字（漢字・emoji・ゼロ幅スペース）と改行・NUL は、ヘッダー値の設定時に `fetch` が**例外を投げます**——リクエストがそもそも送信されないため、200 を返すのに決して入れないパネルができあがり、サーバー側には `admin.login_failed` の 1 行すら残りません; ② **TAB を除く**その他の制御文字（`0x01–0x08`、`0x0B`、`0x0C`、`0x0E–0x1F`、`0x7F` の計 29 個）はブラウザーからは送信できますが、HTTP パーサーが `400` として拒否します; ③ **TAB（`0x09`）**および `é` / `£` / ノーブレークスペースのような `0x80–0xFF` のバイトは**実際には送信でき、動作もします**——これを拒否しているのは物理的な制約ではなく**当方の堅牢性のためのトレードオフ**であり、**両者で理由が異なります**。TAB は**目に見えない文字**で、`.env` やシークレットに貼り付けられても誰も気づけません（前後の空白と同種の診断しやすさの問題ですが、あちらは物理的、こちらはトレードオフです）。`0x80–0xFF` の方はエンコーディングの問題です: 環境変数は UTF-8、ヘッダー値は Latin-1 として復号され、その範囲で両者が一致することは仕様上保証されていません（検証したのは Node のみで、Cloudflare Workers 側は未検証です）。また RFC 9110 はこの範囲を非推奨としています。ASCII のみのトークンをご利用ください。**途中のスペースは許可されます**——`correct horse battery staple` のようなパスフレーズは問題なく送信・到達しますし、24 文字という下限のもとではランダム文字列より扱いを誤りにくいことも多いためです。先頭・末尾の空白は上のルールが担当します。未設定または規則違反の場合、`/admin` ツリー全体が登録されず、理由は `admin.token_rejected` に記録されます。 |
| `TRUST_PROXY` | いいえ | 未設定（転送ヘッダーを**一切**信頼しない） | ゲートウェイが実際にプロキシの背後にある場合**のみ** `1` にしてください。**Cloudflare Worker 形態もこれに該当するので設定すべきです。** 設定すると、ログイン失敗イベントに記録されるクライアント IP は `CF-Connecting-IP` から取られ、無い場合にのみ `X-Forwarded-For` の先頭要素へフォールバックします。 |

**未設定なら管理パネルが使えないだけで、ゲートウェイの転送は通常どおり動きます。** このとき
`/admin/...` へのリクエストは **`401` ではなく `404`** になります。ツリーそのものが登録されない
ため、「ここに管理画面がある」という事実自体が漏れません。これはレジストラーがデフォルトで
無効なのと同じ方針です。`ADMIN_TOKEN` の欠落や設定ミスでゲートウェイの転送を止めてはいけません。

**24 文字という下限の理由。** Worker 形態には**分散ログインレート制限がありません**。実装する
には KV をカウント窓として使う必要があり、それは攻撃者に書き込みクォータを消費させるレバーを
渡すことになります（攻撃面が「パスワードを当てる」から「キープールの状態書き込みを潰す」まで
広がる）。したがってトークンのエントロピーが唯一の防御であり、この下限は推奨値ではありません。
下回る場合パネルは有効化されず、コンテナログに `admin.token_rejected` が出力されます。

**`GATEWAY_TOKEN` と異なる必要がある理由。** `GATEWAY_TOKEN` は**すべての下流ユーザー**に配る
中継トークンです。これをパネルのトークンとして使い回すと、中継トークンを持つ誰もがキープール
全体を読み、レジストラーを停止し、登録バックエンドを自分のサーバーに向け替えられます——以降に
作られる全アカウントのメールアドレス・パスワード・認証コードが奪われます。

このルールは**管理リクエストごとに再検査されるだけで、起動時には遮断しません**。両者が同一の
場合——例えば `wrangler kv key put` や `store.json` の直接編集で `gatewayToken` を手作業で
書き換えた場合——管理エンドポイントは **`503` を返し**、error レベルで `admin.token_conflict`
が記録されます（起動時点で既に衝突しているなら、起動ログにも同じ行が出るのですぐ原因が
分かります）。**ゲートウェイの転送は影響を受けません。**

**衝突が起きた時点で `ADMIN_TOKEN` は漏洩したものとして扱ってください。回復方法は一つだけ、
まったく新しい値にローテーションすることです。** Worker では `npx wrangler secret put ADMIN_TOKEN`
を実行して再デプロイ、Docker では `.env` を編集してコンテナを作り直します。
**ストレージ上の `gatewayToken` を戻すだけで済ませないでください。** それでも管理エンドポイントは
すぐ回復します（設定キャッシュが次に更新された時点で有効になり、**再起動は不要**）が、
それが回復させるのは可用性であって安全性ではありません。衝突していた間、管理トークンと
ゲートウェイトークンは同じ値であり、ゲートウェイトークンは**すべての下流ユーザー**に配るもの
です——既に持っている人（あるいはこれから渡される人）は、そのまま管理画面を開けてしまいます。
可用性を先に戻すために `gatewayToken` を戻すのは構いませんが、その後で**必ず `ADMIN_TOKEN` を
ローテーション**してください。両方を終えて初めて対処完了です。

**なぜこのルールだけ起動時に遮断しないのか。** `gatewayToken` は稼働中に変わり得るのに、起動時の
判定には二度目の評価の機会がありません。そこで `/admin` ツリー全体を登録しない扱いにすると、
衝突中にコールドスタートした isolate（および衝突中に起動した Docker コンテナ）は**恒久的に
`404`** になり、設定を戻しても直らず再起動しか手がなくなります。一方で衝突前に構築されたものは
`503` にとどまり、値を戻せばすぐ回復します。同じ設定・同じ瞬間に二つの答えが存在することになり、
上の「再起動は不要」という一文が半分嘘になります。`ADMIN_TOKEN` 自身に関する 3 つのルール
（前後の空白、送信できない文字、最小長）は入力が環境変数だけで稼働中に変わらないため、引き続き起動時に遮断し、
失敗の形は `404` のままです。

`ADMIN_TOKEN` は**環境変数からのみ読み取られ、ストレージからは読みません**。パネルが自分の鍵を
ローテーションすることはできません。ローテーション方法は、Worker なら
`npx wrangler secret put ADMIN_TOKEN` の後に再デプロイ、Docker なら `.env` を編集してコンテナを
作り直します。

**管理トークンの漏洩は `ADMIN_TOKEN` そのものの漏洩です。** パネルはこれをブラウザーの
localStorage にそのまま保存します。派生トークンはなく、製品内に失効経路もありません。失効させる
唯一の方法は、シークレットを変更して再デプロイ（Worker）またはコンテナを作り直す（Docker）ことです。
パネルは 12 時間後にトークンの再入力を求めますが、それはその localStorage の値が使える期間を
短くするだけで、**失効ではありません**。パネルは TLS の背後に置き、信頼できる端末でのみ開いてください。

**この上限にできないことも明記します。** パネルの CSP は `connect-src 'self'` でトークンを外部
ドメインへ `fetch` することを、`form-action 'none'` でフォーム経由の持ち出しを防ぎます。しかし
`location.href = "https://…?k=" + token` のような**ナビゲーションによる持ち出し**は防げません
— CSP にはもうそれを止めるディレクティブがありません（`navigate-to` は仕様から削除されました）。
本当の解決策はサーバーが発行する**失効可能な派生トークン**ですが、それはサーバー側でセッションを
保存することを要求し、「`ADMIN_TOKEN` は環境変数からのみ読む」という設計上の制約と衝突するため、
後続のリリースに回します。

**`TRUST_PROXY` はセキュリティスイッチなので既定で無効です。** これが決めるクライアント IP は
`admin.login_failed` イベントに記録されるため、クライアントが送ってくるヘッダーを無条件に信頼すると、
誰でも総当たりの痕跡を任意の IP になすりつけられます。

**無効時はどの転送ヘッダーも信頼せず、このフィールドは一律 `null` になります——`CF-Connecting-IP`
も例外ではありません。** このヘッダーは「プラットフォームが注入するので偽装できない」と説明されがち
ですが、その性質は**リクエストが実際に Cloudflare を通る場合にのみ**成り立ちます。Node/Docker を直接
公開している構成では上書きするものが何もないため、クライアントが自分で
`CF-Connecting-IP: 1.2.3.4` を送れば信じられてしまいます——そして直接公開は Docker 配備の既定の形です。

**有効時は `CF-Connecting-IP` が優先され、`X-Forwarded-For` はフォールバックにすぎません。**
2 つのヘッダーは偽装のしやすさが根本的に異なります。

- `CF-Connecting-IP` は Cloudflare のエッジが書き込み、クライアントが送ってきた同名ヘッダーを
  **上書きします**——リクエストが実際に Cloudflare を通る限り偽装できません。
- `X-Forwarded-For` はどのミドルボックスでも追記できる連鎖で、クライアントが偽物を送ることもできる
  ため、どこまで信じられるかはプロキシ構成次第です。

**Worker 形態では `TRUST_PROXY=1` を設定してください。** そこでは Cloudflare が定義上前段にいるため
`CF-Connecting-IP` が権威ある値です。この形態で `X-Forwarded-For` を優先するのは誤りで、その連鎖には
クライアントが詰め込んだものが入っている可能性があります。スイッチを設定しない場合、このフィールドは
単に `null` として記録されます。

**汎用リバースプロキシ（nginx / Caddy / Traefik）の背後で `TRUST_PROXY=1` を有効にする場合は、
プロキシ側で `CF-Connecting-IP` を除去してください。** その構成では誰もこのヘッダーを上書きしませんが、
ゲートウェイは「Cloudflare が前段にいる」前提でこれを優先するため、攻撃者が自分で付けたヘッダーが
プロキシの書いた `X-Forwarded-For` を**上回って**しまいます。nginx なら 1 行です:

```nginx
proxy_set_header CF-Connecting-IP "";
```

Caddy は `header_up CF-Connecting-IP ""`、Traefik はミドルウェアの `customRequestHeaders` を使います。

**どちらのヘッダーも先に形式チェックを通ります**: ドット区切りの IPv4 と IPv6 の形（16 進数、
コロン、`::ffff:` マッピング内のドット）だけがイベントに入り、それ以外は一律 `null` として
記録されます。これは認証の防御線ではなく（この値の消費箇所はリポジトリ全体でログイン失敗
イベント 1 か所だけです）、未認証の呼び出し元が監査フィールドに任意のテキストを書き込めない
ようにするためのものです。管理パネルのイベント欄はこのフィールドで絞り込みと表示を行います。

利用できる値が何も無い場合、このフィールドは正直に `null` として記録されます——**`"unknown"` という
偽の値は決して作りません**。実在の送信元と誤解されるためです。

### 設定ページで変更できるもの（P3c）

パネルの**設定**ページはカード 3 枚です：**認証キー**／**上流とクールダウン**／
**レジストラー**（完全に対等な 2 つのメールボックスチャネルのサブカードと「詳細設定」の
折りたたみを含む）。書き込み先は**ストレージ内の `config` キー**であり、環境変数ではありません。

**各項目には 1 つではなく 3 つの値が表示されます。**「保存値 X · 環境変数 Y · 実効値 Z」の行が、
「あなたが保存したもの」「デプロイ側が与えているもの」「ゲートウェイが実際に使っているもの」を
分けて示します。優先順位は常に **環境変数 > ストレージ > 組み込み値** です。

**環境変数でロックされた項目はパネルから変更しても反映されないため、パネルはそもそも編集させません。**
入力欄はグレーアウトされ、どの環境変数によるものか、変更はデプロイ側で行う必要があることが併記されます。
`PUT /admin/api/config` はそうした項目に対して `400 locked_by_env` を返し、**ストレージには一切書きません**。
書いてしまうと「保存成功・実効値は不変」となり、運用者はキャッシュのせいだと思って何周期も無駄に待つことになります。

⚠️ **P3c からはレジストラー系（`REGISTRAR_ENABLED`／`REGISTRAR_PRIMARY`／`REGISTRAR_FALLBACK`／
`TARGET_KEYS`／`MINT_BATCH`／`TEND_INTERVAL_MS`／`CODE_TIMEOUT_MS`／`MINT_DELAY_MIN_MS`／
`MINT_DELAY_MAX_MS`／`MAX_DOMAIN_ATTEMPTS`／`REGISTRAR_TOKEN_NAME`／`AGNES_PLATFORM_URL`／
`YYDS_BASE_URL`／`YYDS_API_KEY`／`MOEMAIL_BASE_URL`／`MOEMAIL_API_KEY`）もこのロック表に入りました。**
それ以前は入っていませんでした：`docker-compose.yml` に `TARGET_KEYS=30` があるとき、
パネルで 20 に変えても保存は成功し、実効値はずっと 30 のまま——**再起動しても直らず**、
パネルには何の表示もありませんでした。

**資格情報は書き込み専用です。** ゲートウェイトークンと 2 つのチャネルの API キーは
**平文では決して返しません**。返すのは「設定済みかどうか」と**末尾 4 文字**だけです
（5 文字未満なら末尾 4 文字すら返しません——それは全部を見せることになるからです）。したがって：

- 入力欄は常に空で、プレースホルダーには**空欄のままにすると変更されません**と表示されます；
- 保存時、これらの欄が**未入力または空 = 変更しない**（クリアではありません）。空をクリアとして
  実装すると、運用者が設定ページを一度保存しただけでゲートウェイトークンが消え、しかも
  **現在のプロセスは直前の有効なスナップショットで動き続ける**ため、次の再起動まで異常に見えません；
- クリアは専用の「クリア」ボタン（確認ダイアログ付き）からのみ可能です。

⚠️ **パネルから書き込んだ資格情報は KV／`store.json` に平文で保存されます**。P1 の
「キーは平文で保存」と同じ水準です。ここに入力するものが暗号化された secret だとは考えないでください。
データディレクトリ／KV ネームスペースは資格情報として扱ってください。

⚠️ **環境変数にも `GATEWAY_TOKEN` が無い状態でゲートウェイトークンをクリアした場合**、
現在のプロセスは動き続けますが、**次の再起動や isolate の再生成で起動できなくなります**。
パネルはその場で赤い注意書きで明示します。同じページですぐに新しいゲートウェイトークンを設定して復旧してください。**環境変数がこの値を与えている場合、クリアは安全です**：消えるのはストレージ上の一部だけで、実効値は環境変数にフォールバックし変わりません。パネルはこの 2 つの状態で別々の文言を出し、判断を利用者に押し付けません。

⚠️ **「詳細設定」の中にある登録バックエンドの URL（`AGNES_PLATFORM_URL`）は普通の設定項目ではありません。**
これは**すべての自動登録の送信先**です。別のサーバーに変えると、そのサーバーが各登録に使う
メールアドレス・パスワード・認証コードを受け取ります。だからこそ折りたたみの中に置き、赤い警告を付け、
メインの「保存」とは別に専用の確認ボタンを設けています。

**保存後、パネルは「保存して反映しました」とは言いません。** 実効値を**読み戻し**、
実際に変わった項目をハイライトし、**他のレプリカ／isolate が変更を見るまで最大どれくらいかかるか**を
明示します：設定ホルダーの TTL は 30 秒、KV エッジキャッシュの既定は 60 秒なので、上限は約 **90 秒**です。
このインスタンスは即時です（保存時にローカルキャッシュを無効化します）が、他のインスタンスは違います。
**パネルの文言に「即時反映」と書いてはいけません。**

### レジストラー関連の変数（オプション、デフォルトで無効）

レジストラーはオプションの自動プール補充コンポーネントで、デフォルトでは無効になって
おり、ゲートウェイの中核である転送機能には影響しません。ここでは変数の早見表のみを
示します。動作原理、2 つのメールボックスチャネルの選び方、Cloudflare Cron の壁時計
上限などの詳細は [REGISTRAR.md](REGISTRAR.md) を参照してください。

| 変数 | 必須 | デフォルト | 説明 |
|---|---|---|---|
| `REGISTRAR_ENABLED` | いいえ | `false` | マスタースイッチ。`true` にしないとレジストラーは有効になりません。 |
| `REGISTRAR_PRIMARY` | 有効化時は必須 | なし | 主チャネル、`yyds` または `moemail`。両者は対等でデフォルト値なし。 |
| `REGISTRAR_FALLBACK` | いいえ | 空（フォールバックなし） | 副チャネル、`yyds` または `moemail`。 |
| `TARGET_KEYS` | いいえ | `20` | 目標とする利用可能 key 数。 |
| `MINT_BATCH` | いいえ | `5` | 1 ラウンドで発行する key の最大数。 |
| `TEND_INTERVAL_MS` | いいえ（Node/Docker のみ） | `1800000` | Node 側の補充間隔。Worker 側は `wrangler.toml` の Cron が代わりに決める。 |
| `CODE_TIMEOUT_MS` | いいえ | `120000` | 認証コードを待つタイムアウト。 |
| `MINT_DELAY_MIN_MS` / `MINT_DELAY_MAX_MS` | いいえ | `2000` / `5000` | 発行試行の間に入れるランダム待機時間。 |
| `MAX_DOMAIN_ATTEMPTS` | いいえ | `8` | 1 回の発行試行で試すドメインの最大数。 |
| `REGISTRAR_TOKEN_NAME` | いいえ | `auto` | 発行された key が Agnes 管理画面に表示される名前。 |
| `AGNES_PLATFORM_URL` | いいえ | `https://platform-backend.agnes-ai.com` | 登録に使う Agnes プラットフォームのバックエンド。 |
| `YYDS_BASE_URL` / `YYDS_API_KEY` | いいえ / チャネルが yyds の場合は必須 | `https://maliapi.215.im` / 空 | YYDS Mail チャネルの認証情報。 |
| `MOEMAIL_BASE_URL` / `MOEMAIL_API_KEY` | チャネルが moemail の場合は必須 | 空 / 空 | MoeMail チャネルの認証情報（自己ホスト、デフォルトアドレスなし）。 |

### 2 つのタイムアウト予算の使い分け

判断基準は「上流の最初のバイトがいつ届き得るか」であり、エンドポイントの名前では
ありません:

| 予算 | 対象エンドポイント | 変数 |
|---|---|---|
| 最初のバイト | **ストリーミング**対話（`stream: true`）、動画ポーリング `GET /v1/videos/{id}` | `UPSTREAM_TIMEOUT_MS` |
| 同期 | 画像生成、動画ジョブ作成、**すべての非ストリーミング対話**（4 プロトコルとも） | `UPSTREAM_SYNC_TIMEOUT_MS` |

非ストリーミングのリクエストは、上流が回答全体を生成し終えてからでないと応答ヘッダを
返しません。画像生成とまったく同じ遅延の性質であり、8 秒の最初のバイト予算で切ると
正常なリクエストが大量に失敗し、key プールまで巻き添えになります。

`UPSTREAM_SYNC_TIMEOUT_MS` は**1 リクエストの総予算**、つまりクライアントの最悪待ち時間
です——「プールの大きさ × 予算」ではありません。ゲートウェイはこの予算のうち単一の key に
最大でも半分しか使わず、残りは別の key での再試行に取っておきます。こうすることで、
プール内にハングした key（接続はできるが決して応答しない）があってもリクエストを丸ごと
食い潰されません。したがって**単一呼び出しの最悪所要時間の 2 倍以上**に設定してください。

同期予算でのタイムアウトは、その場では key を罰しません。同一リクエスト内で切り替えた
別の key が実際に成功した場合にのみ、先にタイムアウトした key に計上します
（`MAX_STRIKES` に達するとクールダウン）。そのリクエストで全部の key がタイムアウトした
場合は 1 つも罰しません——予算が小さすぎるか上流全体が遅い可能性の方が高いためです。

「排除」と「クールダウン」は別物です。上記の設定にかかわらず、上流の `401`/`403`
はその key を**永久に**排除します——これらは「この key はもう有効ではない」状態
であり、再試行に意味がないためです。一時的な失敗が排除につながることはありません。
`MAX_STRIKES` に達しても `COOLDOWN_STRIKE_MS` のクールダウンに入るだけで自動的に
復帰するので、上流の一時的な不調がプールを恒久的に破壊することはありません。

どの key もリクエストを処理できない場合、ゲートウェイは `503` を返し、`error.reason`
に判別可能な理由を示します：`pool_empty`（key が未登録）、`all_cooling`（全 key が
クールダウン中。自動的に回復し、`Retry-After` ヘッダーが復帰時刻を示す）、
`all_evicted`（全 key が認証情報の失効により永久排除。**自動回復しない**ため key の
入れ替えが必要）、`upstream_error`（key 自体は有効だが、上流が毎回失敗した）。

### 非常に長い非ストリーミングリクエストは途中で切断されるか（2 つの形態で異なりうる）

**結論: Worker 側に頼れるプラットフォームの保証はありません。したがって本書も管理画面も
一切保証しません。**

Cloudflare Workers の limits ページで確認できた公式の記述は 2 つあります。HTTP でトリガー
される Worker には**実時間の上限がない**（"There is no hard limit on duration for
HTTP-triggered Workers"）、個々の送信サブリクエストにも**時間制限がない**
（"There is no set time limit on individual subrequests"）。いずれも「クライアントが接続を
維持している限り」という条件付きです。

**この 2 つですべてを覆えるわけではありません。** 個別に明記します。

- 公式文書にある **125 秒のプロキシ読み取りタイムアウト（エラー 524）** は「Cloudflare を
  リバースプロキシとして経由するゾーンのトラフィック」という文脈でのみ書かれており、
  **Worker 自身が発行するサブリクエストに適用されるかどうかは一切述べられていません**。
  見つからない以上「プラットフォームの保証なし」として扱い、推測はしません。
- 同じページには、ランタイムが週に数回更新され、更新時に実行中のリクエストには **30 秒**の
  猶予が与えられ、それを超えると中止されるとあります。低確率ですが、存在はします。
- `wrangler.toml` にある **15 分（900 秒）**は **Cron Trigger（`scheduled()`）**の実時間上限で
  あり、**`fetch()` のものではありません**。根拠として流用しないでください。

⇒ **実際の影響は 2 点:**
① `UPSTREAM_SYNC_TIMEOUT_MS`（既定 120000）規模の非ストリーミングリクエストは、
   Worker と Docker で**挙動が同じとは限りません**。Node/Docker 側にプラットフォームの
   実時間上限はなく、設定した予算だけが効きます。
② **管理画面（プレイグラウンド）の文言は「2 つの形態が同じ」とは言いません。**
   「何秒までは必ず切れない」という数字も示しません。長いリクエストが必要な場合は、
   実測できた範囲で `UPSTREAM_SYNC_TIMEOUT_MS` を設定するか、ストリーミングの
   エンドポイント（初回バイトの予算）に切り替えてください。

### 方法 B —— 手動デプロイ

1. リポジトリをクローンして依存関係をインストールします。

   ```bash
   git clone https://github.com/xwteam/agnes2api.git
   cd agnes2api
   pnpm install
   ```

2. key プール用の KV ネームスペースを作成し、`wrangler.toml` に書き戻します。

   ```bash
   node scripts/setup-worker.mjs
   ```

   リポジトリの `wrangler.toml` に入っている `id` は常にプレースホルダーです
   （公開リポジトリには実際のデプロイ情報を一切含めません）ので、この手順は
   必須です。このスクリプトは手動で `npx wrangler kv namespace create POOL` を
   実行し、返ってきた `id` を `[[kv_namespaces]]` ブロックの
   `REPLACE_WITH_YOUR_KV_NAMESPACE_ID` に貼り付けるのと同じことをします。
   **実行後、この `wrangler.toml` への変更はコミットしないでください**——
   `check-wrangler-placeholder.mjs` の CI ゲートが誤ってコミットされた実際の
   id を検出して止めます。

3. ゲートウェイトークンを Worker の secret として設定します（絶対に
   `wrangler.toml` にコミットしないでください）。

   ```bash
   npx wrangler secret put GATEWAY_TOKEN
   ```

4. デプロイします。

   ```bash
   npx wrangler deploy
   ```

### タグ push による自動デプロイ

Worker をデプロイします。ただし、リポジトリの

### ローカル開発

`GATEWAY_TOKEN` は `wrangler.toml` と同じディレクトリにあるローカルの

## Docker

1. リポジトリをクローンし、環境変数ファイルを準備します。

   ```bash
   git clone https://github.com/xwteam/agnes2api.git
   cd agnes2api
   cp .env.example .env
   ```

2. `.env` を編集し、少なくとも `GATEWAY_TOKEN` を設定します。それ以外の
   変数は上記の [環境変数](#環境変数) 表を参照してください。

3. コンテナを起動します。

   ```bash
   docker compose up -d
   ```

   `docker-compose.yml` は既定でポート `8080` を公開し（`.env` の `PORT` で
   上書き可能）、`./data` をコンテナ内の `/app/data` にマウントします——
   `store.json`（key プールと永続化された設定）はここに保存されます。
   再起動やアップグレードをまたいでこのディレクトリを必ず保持してください。
   インポート済みの key プールの唯一のコピーです。

4. コンテナが健全に起動しているか確認します。

   ```bash
   curl http://localhost:8080/health
   ```

   イメージには `HEALTHCHECK` が組み込まれており、Docker はこれをもとに
   コンテナの健全性を報告します。データディレクトリが書き込めない場合、`/health` は
   `status` が `degraded` の `503` を返し、コンテナは unhealthy と表示されます。
   具体的な原因はコンテナログを参照してください。

### コンテナは `./data` の所有者を書き換えます（事前にご確認ください）

コンテナは **root で entrypoint に入り**、次の 2 つを行ってから権限を落とします:

- `DATA_DIR`（既定 `/app/data`）の所有者がコンテナ内の実行ユーザー `app`
  （**uid 100 / gid 101**）と異なる場合のみ、そのディレクトリを再帰的に `chown` します。
  所有者が既に一致していれば何も書き換えません。
- その後 `su-exec` で権限を落とすため、**メインプロセス（PID 1）は root ではなく app**
  として動きます。

実行時に行う必要がある理由は、バインドマウントではホスト側ディレクトリの所有者が
イメージのビルド時 `chown` を上書きしてしまい、コンテナ内の app が `store.json` に
書き込めなくなるからです。しかもこの失敗は静か（すべての API が `pool_empty` を返す）です。

**副作用**: バインドマウントで書き換わるのは**ホスト**上のファイルです。
`docker compose up -d` の後、あなたの `./data` とその中のファイルの所有者は自分の uid から
`100:101` に変わり、以後ホスト側で読み書きやバックアップをするには `sudo` が必要に
なります。それを避けたい場合は `--user`（または compose の `user:`）で非 root 実行を
指定してください。その場合 entrypoint は chown を一切行わず、データディレクトリの所有者と
書き込み可否はあなたが用意します。

同じ理由でイメージには **`USER app` を入れていません**。既定ユーザーは root です
（`docker inspect --format '{{.Config.User}}' <image>` は空を出力）。これは Kubernetes に
影響します: `runAsNonRoot: true` を設定しつつ `runAsUser` を明示しない場合、kubelet は
コンテナの起動を拒否します。そうしたデプロイでは `runAsUser: 100`、`runAsGroup: 101`
（または任意の uid）を明示し、ボリュームの所有者は自分で用意してください——非 root 起動時、
entrypoint は「chown せずそのまま実行する」分岐を通ります。

安全境界: `DATA_DIR` が `/` やトップレベルのシステムディレクトリ（`/etc`、`/usr` など）に
設定された場合、entrypoint はその上での再帰的 chown を拒否します（警告を出すだけで起動は
継続）。コンテナのファイルシステム全体が app から書き込み可能になるのを防ぐためです。

## 上流 Agnes key のインポート

現バージョンのゲートウェイには key をプールへ追加するための HTTP
エンドポイントはありません。ストレージバックエンドへ直接書き込む必要が
あります。各エントリは `key:<id>` というキーを持つ JSON オブジェクトで、
`<id>` はプール内で一意な任意の文字列で構いません（ゲートウェイ自身が
レコードを作成する際は key のハッシュ値から導出しますが、読み込み時には
その値は検証されないため、手動インポートでは任意の一意な識別子で問題
ありません）。

```json
{
  "id": "1a2b3c4d5e6f7a8b",
  "key": "実際の-agnes-api-key",
  "addedAt": 1735689600000,
  "lastUsedAt": null,
  "cooldownUntil": 0,
  "strikes": 0,
  "evicted": false,
  "evictedReason": null
}
```

### Docker

実行中のプロセスとの書き込み競合を避けるため、まずコンテナを停止し、
ホスト上で `./data/store.json` を編集して、キー
`"key:1a2b3c4d5e6f7a8b"` の下に上記のようなレコードを追加してから、
コンテナを再度起動します。

```bash
docker compose stop
# ./data/store.json を編集
docker compose start
```

`./data/store.json` がまだ存在しない場合は、`key:<id>` という形式の
キーを持つ単一の JSON オブジェクトとして新規作成してください。

### Cloudflare Worker

wrangler を使ってレコードを `POOL` KV ネームスペースへ直接書き込みます。

```bash
npx wrangler kv key put --binding=POOL "key:1a2b3c4d5e6f7a8b" \
  '{"id":"1a2b3c4d5e6f7a8b","key":"実際の-agnes-api-key","addedAt":1735689600000,"lastUsedAt":null,"cooldownUntil":0,"strikes":0,"evicted":false,"evictedReason":null}' \
  --remote
```

`--remote` を省略すると、本番ではなく `wrangler dev` が使用するローカルの
ネームスペースに書き込まれます。

ゲートウェイはプール内の id 一覧を `pool:index` というキーに保持しており、転送のたびに KV の
`list` を消費せずに済みます（無料枠の `list` は 1 日 1,000 回しかなく、読み取り・書き込みとは
別枠です）。**レコードを手作業で書いてもこの索引は変わりません**。したがって新しい key が
いつ使われ始めるかは、そのときのプールの状態によります:

- **プールが空のとき**: 索引が「空」と言い、実際にレコードが 1 件も読めない場合、ゲートウェイは
  `list` 走査に 1 回だけフォールバックし、手動インポートされたレコードを検出して索引に
  追加します。この走査には組み込みの 10 分バックオフがあるため（上の「クォータの見積もり」参照）、
  可視化までの上界は **10 分以内 + `POOL_CACHE_TTL_MS` 1 回分**です。
- **プールが空でないとき**: 転送経路は索引が知っているレコードしか取得しないため、索引が
  知らないレコードは**完全に見えません**（エラーも一切出ません）。次の cron 照合が索引を
  修復するまで（既定 30 分、しかも**トリガー時刻に公式な保証はありません**。下記参照）、
  さらにその後最大 `POOL_CACHE_TTL_MS` 1 回分待つ必要があります。

**手動インポートを即座に反映させたい場合は、レコードを書くのと同時に id を `pool:index` へ
追加してください:**

```bash
npx wrangler kv key get --binding=POOL "pool:index" --remote
# ids 配列に新しい id を追加し、値全体を書き戻す（v は常に 1）
npx wrangler kv key put --binding=POOL "pool:index" \
  '{"v":1,"ids":["既存のid","1a2b3c4d5e6f7a8b"]}' --remote
```

索引を書き込めば、各 isolate は最大でも `POOL_CACHE_TTL_MS` 1 回分でこの key を使い始めます。

レジストラを使わない場合でも `wrangler.toml` の `[triggers]` を削除しないでください。
この cron は `pool:index` と実際の `key:` レコードを突き合わせて修復する唯一の経路であり、
`REGISTRAR_ENABLED` の値とは無関係に実行されます。

**この cron の発火タイミングは公式に保証されていません。** Cloudflare は Cron
Trigger が `crons` の式どおりに発火する信頼性について文書化していません（スキップ
されない保証も、遅延の上限も明記されていません）。これは配額計算にとっては安全
な方向です——対帳の発火回数が減れば KV の読み書き消費も予測より減るだけで、
増えることはありません。ただし**孤立レコードやゴースト索引項目が索引に回収され
るまでの時間には保証がありません**。最悪の場合、想定していた「最長 30 分」より
長くかかることがあります。その待機中は対象の key が一時的に使えないだけで、
データが失われたり壊れたりすることはありません。

## key を失効させる

**レコードを削除し、その id を `pool:index` からも外す——両方を行ってください。** レコードだけ
削除してもエラーにはなりません（読めないレコードは単に除外されます）が、id が索引に残るため、
次の照合で刈り取られるまで更新のたびに読み取りを 1 回無駄にします。

```bash
npx wrangler kv key delete --binding=POOL "key:1a2b3c4d5e6f7a8b" --remote
# ids 配列からその id を取り除き、値全体を書き戻す
npx wrangler kv key put --binding=POOL "pool:index" '{"v":1,"ids":["残りのid"]}' --remote
```

Docker の場合は `./data/store.json` から `"key:<id>"` のエントリを削除し、`"pool:index"` の
`ids` 配列を直します。先に `docker compose stop` しておくことを推奨します。

古いスナップショットを読み込み済みの isolate / プロセスは、最大 `POOL_CACHE_TTL_MS` 1 回分で
その key を選ばなくなります。Worker ではさらに KV の伝播ウィンドウ（およそ 60 秒）が加わります。
削除がすべての colo に見えるまでにそれだけかかるためです。

**そのウィンドウの間も書き戻されることはありません**: ゲートウェイは状態変更を永続化する前に
レコードがまだ存在するかを確認し、読めなければその書き込みを破棄して自分のスナップショットを
直ちに更新します。唯一の例外がその伝播ウィンドウで、確認のための読み取りが KV のエッジ
キャッシュから返された場合、その colo はレコードがまだあると判断します。Docker（ファイル
ストレージ）にはこのキャッシュがないため、そちらでは厳密です。
