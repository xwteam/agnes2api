# デプロイガイド

agnes2api のデプロイ先は 1 つだけで、本リポジトリのコードから作った Docker イメージを `docker compose` で動かします。

> [!NOTE]
> 状態はすべて 1 か所にしかありません——マウントされたボリューム上の JSON ファイル
>（`store.json`）です。そのディレクトリを取っておけば、状態は全部取ってあることになります。

## 環境要件

道は 1 本なので、列も 1 つです。

| 項目 | 要件 |
|------|------|
| コマンドライン | Docker Engine 24+ と `docker compose` |
| プラットフォーム | コンテナを動かせるマシン 1 台 |
| 上流 | Agnes API key が最低 1 本。次節を参照 |

> [!TIP]
> これ以外に入れるものはありません——ローカルの Node.js もビルドツールチェーンも不要です。
> `cp .env.example .env` のあと `docker compose up -d` 一発で立ち上がります。
## Agnes 認証情報の取得

ゲートウェイ自身は key を発行しません。あなたが持っている 1 本ないし数本の Agnes API key に
リクエストを振り分けるだけです。入手経路は 2 つあり、**2 つは対等**で、主・副は決めていません。

### 手動で取得する

Agnes プラットフォームでアカウントを作り、コンソールで API key を 1 本発行してコピーします。
この経路では一度に 1 本しか手に入りませんが、まずゲートウェイを動かして 4 つのプロトコルが
通ることを確かめる段階にはそれで十分です。

### レジストラーに自動補充させる

本リポジトリにはオプションのレジストラーが同梱されており、`TARGET_KEYS` を目標にプールを
自動で補充します。**既定はオフ**です（`REGISTRAR_ENABLED` を設定しなければオフのまま）。
仕組み、2 つのメールボックスチャネルの選び方、1 ラウンドがどれくらいかかりうるかは
[REGISTRAR.md](REGISTRAR.md) に全部書いてあります。

> [!IMPORTANT]
> どちらの経路でも key は `store.json` に**平文**で保存されます。
> データディレクトリは認証情報として扱ってください。

## Docker デプロイ

### 前提条件

> [!NOTE]
> 同じディレクトリの [README](README.md) の `## ⚡ クイックデプロイ` の節には、同じ 3 つの
> コマンドが短い形で載っています。本節はその長い形です: それぞれのコマンドがあなたに
> 委ねている判断を書き開きます。最初の 1 つは、初回起動の前に必ず決めておくトークンです。

リポジトリをクローンし、環境変数ファイルを準備します。

```bash
git clone https://github.com/xwteam/agnes2api.git
cd agnes2api
cp .env.example .env
```

**イメージを使わずソースから動かす場合**: `pnpm dev:node` は `node scripts/build-ui.mjs`
で始まり、そのあとビルドして `dist/entry/node.js` を起動します。素の
`node dist/entry/node.js` でも起動しますが、パネルは前回生成されたものに留まります ——
`admin-ui/` を変えたのに何も変わらないときは、たいていこれが理由です。

### 設定

`.env` を編集し、少なくとも `GATEWAY_TOKEN` を設定します。それ以外の
変数は後述の [環境変数](#環境変数) 表を参照してください。

`.env` の最小構成は 2 行です。残りはすべて既定値があるので、必要になってから足せば十分です:

```env
# 必須: クライアントが本ゲートウェイを呼び出す際に提示するトークン。下流に配るのはこれです。
GATEWAY_TOKEN=自分で用意した長いランダム文字列に置き換える

# 任意: コンテナ内のリッスンポート。
# docker-compose.yml はこれをホスト側に公開するポートとしても使います。
PORT=8080
```

> [!CAUTION]
> **`DATA_DIR` は docker-compose.yml のボリュームマウントと固く結び付いています。Docker
> 形態ではこれだけを単独で変更しないでください。** あの行 `./data:/app/data` はハード
> コードで、`.env` の `DATA_DIR` はその補間に一切関与しません。あの行を直さずに
> `DATA_DIR` を別のパスへ向けても何も止めません: コンテナは起動し、`/health` は `ok` を
> 返し、パネルも key プールも正常で、レジストラーも補充を続けます —— その間 store.json は
> **コンテナの書き込み可能レイヤー**に落ちます。次に「更新」でアップグレードするとコンテナ
> が再作成され、key プール全体、発行済みの対外 API キー、パネル設定がまとめて消え、
> あなたがずっとバックアップしてきた `./data` は最初から空です。
> データをホストのどこに置くかを変えるなら、あのマウント行の**左半分**を変えます。右半分を
> 変えるなら `DATA_DIR` も同じパスに揃え、両方を一緒に変えます。起動時に entrypoint が
> これを検査し、どのマウントポイントにも乗っていないときはコンテナログに
> 「どのマウントポイントにも乗っていない」警告を出します —— この連鎖で唯一の信号がその 1 行で、
> `/health` はデータがどこに落ちたかを報告しません。

#### データディレクトリと所有者: コンテナは `./data` を書き換えます（事前にご確認ください）

コンテナは **root で entrypoint に入り**、次の 2 つを行ってから権限を落とします:

- `DATA_DIR`（既定 `/app/data`）の所有者がコンテナ内の実行ユーザー `app`
  （**uid 100 / gid 101**）と異なる場合のみ、そのディレクトリを再帰的に `chown` します。
  所有者が既に一致していれば何も書き換えません。
- その後 `su-exec` で権限を落とすため、**メインプロセス（PID 1）は root ではなく app**
  として動きます。

実行時に行う必要がある理由は、バインドマウントではホスト側ディレクトリの所有者が
イメージのビルド時 `chown` を上書きしてしまい、コンテナ内の app が `store.json` に
書き込めなくなるからです。しかもこの失敗は静か（すべての API が `pool_empty` を返す）です。

**副作用**: バインドマウントで書き換わるのは**ホスト**上のファイルです。
`docker compose up -d` の後、あなたの `./data` とその中のファイルの所有者は自分の uid から
`100:101` に変わり、以後ホスト側で読み書きやバックアップをするには `sudo` が必要に
なります。それを避けたい場合は `--user`（または compose の `user:`）で非 root 実行を
指定してください。その場合 entrypoint は chown を一切行わず、データディレクトリの所有者と
書き込み可否はあなたが用意します。

同じ理由でイメージには **`USER app` を入れていません**。既定ユーザーは root です
（`docker inspect --format '{{.Config.User}}' <image>` は空を出力）。これは Kubernetes に
影響します: `runAsNonRoot: true` を設定しつつ `runAsUser` を明示しない場合、kubelet は
コンテナの起動を拒否します。そうしたデプロイでは `runAsUser: 100`、`runAsGroup: 101`
（または任意の uid）を明示し、ボリュームの所有者は自分で用意してください——非 root 起動時、
entrypoint は「chown せずそのまま実行する」分岐を通ります。

安全境界: `DATA_DIR` が `/` やトップレベルのシステムディレクトリ（`/etc`、`/usr` など）に
設定された場合、entrypoint はその上での再帰的 chown を拒否します（警告を出すだけで起動は
継続）。コンテナのファイルシステム全体が app から書き込み可能になるのを防ぐためです。

### デプロイ

コンテナを起動します。

```bash
docker compose up -d
```

**最初のイメージが公開される前**（または fork 後）は、このコマンドはローカルビルドに
フォールバックします —— `docker-compose.yml` の `build:` ブロックがそのためのものです。

`docker-compose.yml` は既定でポート `8080` を公開し（`.env` の `PORT` で
上書き可能）、`./data` をコンテナ内の `/app/data` にマウントします——
`store.json`（key プールと永続化された設定）はここに保存されます。
再起動やアップグレードをまたいでこのディレクトリを必ず保持してください。
インポート済みの key プールの唯一のコピーです。

### 検証

コンテナが健全に起動しているか確認します。

```bash
curl http://localhost:8080/health
```

イメージには `HEALTHCHECK` が組み込まれており、Docker はこれをもとに
コンテナの健全性を報告します。データディレクトリが書き込めない場合、`/health` は
`status` が `degraded` の `503` を返し、コンテナは unhealthy と表示されます。
具体的な原因はコンテナログを参照してください。

トラブルシューティングで繰り返し使う 2 本を先にここで出しておきます。本書で以降に出てくる
「コンテナログ」はすべて 2 本目のことです:

```bash
docker compose ps                     # 立っているか、健全か
docker compose logs -f --tail=100     # コンテナログ: entrypoint の警告も admin.token_rejected もここ
```

### 更新

```bash
docker compose pull
docker compose up -d
```

`docker compose pull` が取りに行くのは `.env` の `IMAGE_TAG` が指す tag です（未設定なら
`latest`）。イメージのフルネームは `ghcr.io/xwteam/agnes2api`、利用できる tag は
[GHCR の packages ページ](https://github.com/xwteam/agnes2api/pkgs/container/agnes2api)にあります。
**アップグレード = `IMAGE_TAG` を上げたいバージョンにして `docker compose up -d`、
ロールバック = 元に戻す。** tag を固定して初めて、この `.env` が「今どのバージョンが動いて
いるか」に答えられます。`:latest` は答えられません。

> [!IMPORTANT]
> **`.env` を編集したら `docker compose restart` ではなく `docker compose up -d` を実行します。**
> 前者は同じコンテナを再起動するだけで、コンテナの環境は**作成**時に固定されるため、`.env` を
> 変えても 1 バイトも変わりません。`up -d` は設定の変化を検知して初めてコンテナを再作成します。
> `ADMIN_TOKEN` の追加もトークンのローテーションも同じ落とし穴で、後者はより厄介です:
> ローテーションできたつもりで、古いトークンがまだ有効なままになります。

`./data` はそのままで、key プールと設定はそこにあります。**アップデート前にそのディレクトリを
バックアップしてください**（後述の「バックアップと復元」）。インポート済み key プールの唯一の
コピーであり、二つ目はありません。

## 環境変数

| 変数 | 必須 | デフォルト | 説明 |
|----|----|----------|----|
| `GATEWAY_TOKEN` | **はい** | – | クライアントが本ゲートウェイを呼び出す際に提示しなければならないトークン。 |
| `RESET_CONFIG` | いいえ | – | 緊急脱出口: `1` にすると起動時にストレージ上の `config` キーを**完全に無視**し（無視するだけで削除はしません）、環境変数と組み込みのデフォルト値だけを使います。いつ使うか、使ったあと何をするかは下記。 |
| `AGNES_BASE_URL` | いいえ | `https://apihub.agnes-ai.com/v1` | 上流 Agnes API のベース URL。 |
| `UPSTREAM_TIMEOUT_MS` | いいえ | `8000` | **ストリーミング**応答と動画ポーリングの最初のバイトのタイムアウト。この時間（ミリ秒）以内に上流の最初のバイトが届かない場合、呼び出しを中断する。 |
| `UPSTREAM_SYNC_TIMEOUT_MS` | いいえ | `120000` | **同期**エンドポイントの全体タイムアウト予算。「最初のバイトが、上流が結果全体を計算し終えてから届く」種類のリクエストにのみ適用される: 画像生成、動画ジョブ作成、そしてすべての**非ストリーミング**対話。詳細は下記。 |
| `MAX_STRIKES` | いいえ | `3` | 連続する一時的な失敗（タイムアウト、ネットワークエラー、上流 `5xx`）がこの閾値に達すると key を長いクールダウンに入れる。 |
| `COOLDOWN_RATE_LIMIT_MS` | いいえ | `60000` | 上流が `429` を返した後、その key に適用されるクールダウン時間。 |
| `COOLDOWN_PAYMENT_MS` | いいえ | `3600000` | 上流が `402` を返した後、その key に適用されるクールダウン時間。 |
| `COOLDOWN_STRIKE_MS` | いいえ | `1800000` | key の一時的な失敗が `MAX_STRIKES` に達した後のクールダウン時間。満了時に自動で復帰する。 |
| `POOL_CACHE_TTL_MS` | いいえ | `60000` | 各プロセスが key プールのスナップショットをメモリ上に保持する時間。`0` でキャッシュ無効。**ストレージの読み取り回数はリクエスト数とは無関係**で、更新頻度だけで決まる。代償は下記を参照。 **インスタンス構築時に一度だけ**読まれます（`src/http/wire.ts`）。変更はコンテナを作り直したあとに反映され、**パネルで変更しても即座には反映されません**。 |
| `POOL_TOUCH_INTERVAL_MS` | いいえ | `21600000` | key の「最終使用時刻」を書き込む最大間隔。`0` で成功リクエストごとに書き込む。これは表示専用のフィールドでスケジューリングは一切読まず、同じ間隔はパネルの利用回数カウンターにも効く。代償と「カウンターの消し方」は下記。 **インスタンス構築時に一度だけ**読まれます（`src/http/wire.ts`）。変更はコンテナを作り直したあとに反映され、**パネルで変更しても即座には反映されません**。 |
| `USAGE_STATS_ENABLED` | いいえ | `false` | パネルの「使用量」セクションの Tier-2 時系列（日／時間／モデル／プロトコル別）。**判定は文字どおりの `true`** で、`1` や `yes` はオフ扱いです。**既定はオフで、その「オフ」はゼロコスト**です。オンにしたときの代償と、**短命なインスタンスではカウントが遅れるのではなく消える**ことは下記。app のビルド時に 1 回読むため、変更はコンテナを作り直したあとに効きます。 |
| `PORT` | いいえ | `8080` | コンテナ内のリッスンポート。`docker-compose.yml` が同じ番号をホスト側にも公開します。 |
| `DATA_DIR` | いいえ | `/app/data` | ファイルストレージが `store.json` を書き込むディレクトリ。**単独で変更しないでください**: compose のボリュームマウントと固く結び付いています。前述の「Docker デプロイ → 設定」を参照。 |
| `APIKEY_CACHE_TTL_MS` | いいえ | `300000` | 対外 API キー表の各インスタンスでのキャッシュ時間。`0` で無効。停止したキーが、同じボリュームを共有する他のコンテナで失効するまでの時間も決めます。後述を参照。 |

### 取りうる範囲と「インスタンス生成時に 1 回だけ読む」2 つの例外

上表の変数はすべて `.env.example` に 1 行ずつ記載されています。`cp .env.example .env` の
後、必要な項目だけ書き換えてください。あのファイルのコメントは詳しさがまちまちで、
ほとんどの変数は 1 行、いくつかは十数行に及びます。取り得る値と代償は本表を参照して
ください。
上記の数値型の変数はすべて整数である必要があります。
`POOL_CACHE_TTL_MS` と `POOL_TOUCH_INTERVAL_MS` は下限が `0`（`0` は「無効」の意）で、
それ以外はすべて `0` より大きい必要があり、そうでない場合ゲートウェイは起動を拒否します。

`POOL_CACHE_TTL_MS` と `POOL_TOUCH_INTERVAL_MS` は **app の構築時に一度だけ**読まれます。
変更を反映するにはコンテナを作り直す必要があり、
他の設定項目のようにリクエストごとには反映されません。

### `RESET_CONFIG`: この緊急脱出口をいつ使うか

> 本来の用途は**パネルに保存された設定をまるごとバイパスすること**です。環境変数と組み込みの
> デフォルト値だけで 1 回起動し、既知のクリーンな状態に戻します。使い終わったらこの行を消してください。
> 消さないとパネルで保存した設定が永久に反映されません。

> [!WARNING]
> **「設定が壊れたらこれで復旧する」ものだと思わないでください。** 保存された値が原因で
> ゲートウェイが起動しなくなることは今やほとんどありません。数値が不正なら**デフォルト値へフォールバック**し
> （パネルに劣化として表示されます）、レジストラー関連の問題は**レジストラーが今回起動しない**だけで、
> ゲートウェイの転送は通常どおりです。今も起動を妨げ得る唯一の条件は**ゲートウェイのトークンが両側とも無い**ことで、
> `RESET_CONFIG=1` はまさに保存されたトークンごと無視します。**そのまま実行すると事態は悪化します。**

### `POOL_CACHE_TTL_MS` の代償

**ストレージの読み取り回数はリクエスト数とは無関係**です——スナップショットが温かいあいだ
転送経路は 1 回も読みません。このつまみで買えるのは「1 プロセスあたり `store.json` を読む
回数が減ること」、払うのは「そのスナップショットがどれだけ古くてよいか」です。

> **これが意味を持つのは複数のプロセスが 1 つのボリュームを共有するときだけ**です:
> ロードバランサーの後ろに複数コンテナ、あるいはローリング再起動で新旧が同時に動く場合。
> 他のプロセスが判定したクールダウン／除外は最大で**この値**ぶん遅れて見えます。
> デフォルトの 60000 なら上限は **60** 秒。単一コンテナならこの窓はありません:
> クールダウンを判定したのは、そのスナップショットを持っているプロセス自身だからです。

しかも「見えるのが遅れる」だけではない: 古いスナップショット上で行われたスケジューリング系の
書き込みはレコード全体を上書きしてしまい、他のプロセスがその時間内に書いた `evicted` /
`cooldownUntil` を**消してしまう**——その判定はもう一度やり直しになる。

### `POOL_TOUCH_INTERVAL_MS` の代償と「カウンターの消し方」

成功リクエストごとに書くというのは、誰もスケジューリングに使わないタイムスタンプのために
`store.json` を毎回まるごと書き直すということ。そうしない代償: 「最終使用」の精度はこの
間隔まで粗くなる。同じ間隔はパネルの利用回数カウンター（リクエスト数／成功率）にも効く。

> [!WARNING]
> **ストレージ上の `stats` を手作業で小さくすると（ゼロにするなど）、パネルは一旦その値を
> 表示したあと、古い値に戻ることがある**: スナップショットは TTL ぶん後にゼロ化された
> レコードを読むが、稼働中のインスタンスは自分が書き込んだ基準値を覚えていて、次に実際に
> 書き込むときそれを書き戻すため。遅くともそのインスタンスが回収された時点で完全に一致する。

**カウンターを消すには repo を経由する正式な経路を使うこと**: `PATCH /admin/api/keys/:id` に
`clearStats` を付ける。これは**このリクエストを処理したインスタンス**が抱えている書き込み
基準値と未書き込みの増分をまとめて破棄するので、**このリセットより後に始まったリクエスト**が
古い値を書き戻すことはない。ただし**リセットの時点ですでに実行中だったリクエスト**は
リセット前のレコードを持っており、完了時にその古い値から基準値を作り直す。同時に動いている
同じボリュームを使う**別の**コンテナもそれぞれ自分の
基準値を持っており、古い値を一度だけ書き戻すことがある。
**今日これは API だけで、パネルにこのボタンはない。**

### `USAGE_STATS_ENABLED`: オンにすると何を払うか

「オフ」はゼロコストです: メモリ上のアキュムレータを作らず、ストレージ書き込みも 1 回も
発生しません。オンにすると 1 インスタンスあたり 1 書き出し間隔につき `store.json` の
シャードを 1 つ書き直します——**既定の 2 時間間隔なら 1 日最大 13 回**で、トラフィックの
ない間隔では 1 回も書きません。未書き出しの尻尾は最長 2 時間です。このスイッチはコンテナを
作り直したあとに効きます。

> [!WARNING]
> **「尻尾」は「遅れ」とは違います**: カウントはまずインスタンスのメモリに貯まるため、
> **1 回の書き出し間隔を生き延びられないインスタンスは、貯めたカウントごと消えます**。
> **遅れて反映されるのではありません**。
> **コンテナの作り直しこそこれが最も起きやすい場面です**: 環境変数を 1 つ変えるために
> 作り直すだけで、最大 2 時間ぶんのカウントが古いプロセスと一緒に去り、パネル上その期間は
> 「誰も使っていない」と見分けがつきません。気になるなら
> `USAGE_FLUSH_INTERVAL_MS` を小さくしてください。その代償は次節に書いてあります。

### `USAGE_FLUSH_INTERVAL_MS`: 何を買い戻せて、何は買い戻せないか

「尻尾は最長 2 時間」を見たとき、最初に思いつくのは書き出し間隔を小さくすることでしょう。
この形態ではその道は通っています: `USAGE_FLUSH_INTERVAL_MS` は**任意の正の整数**を受け付け、
300000（5 分）はまったく妥当です。払うのは 1 インスタンスあたり 1 間隔につきシャードを
1 回書き直すこと、買えるのは「プロセスが止まったときに一緒に消えるカウント」が短くなること。

> [!WARNING]
> **この値を書き間違えると、最初のリクエストではなく app の組み立て時点で拒否されます**
>（`src/http/usage-sink.ts`）: 整数でない、または 1 未満なら、プロセスは理由を出して終了します。
> **このチェックは `USAGE_STATS_ENABLED` がオンかどうかとは無関係です**（`src/http/wire.ts`
> が無条件に解決します）ので、統計をオフにしても**消えません**——
> 値を直すか、その行ごと消してください。コンテナが立ち上がらないという症状は意図的です:
> 「統計データが静かに歪む」よりずっと気づきやすいからです。

<details>
<summary><b>クリックで展開: 「尻尾は最長 2 時間」が約束していること・していないこと（4 点）</b></summary>

① **尻尾は「遅れ」ではなく、2 つの症状は同じ 1 つの事実です**: パネルの「今日」は書き出し
   間隔 1 つぶん古いことがあり、**次の書き出しより前に止まったインスタンスは、貯めたカウント
   ごと持っていきます**。計時はインスタンスが起動した時点から始まるので、10 分だけ動いて
   作り直されたコンテナは 1 件も保存していません。使用量の数字が全体に「≈」を付けている
   理由の 1 つで、欠陥ではありません。

② **この形態には「1 日の書き込み予算」というゲートがありません。** そのゲート自体はコードに
   ありますが（`budgetPerDay`）、ファイルストレージには守るべき書き込みクォータがないので、
   ゲートウェイはそこを空のままにします: 「使い切る」が起きず、「回復」も「後追い書き出し」も
   ありません。**「Docker ならカウントを失わない」と読まないでください**——失うのは ① の尻尾です。

③ **同じ日について残るのは最大 2 インスタンス分で、それ以上は互いに上書きします。** 使用量の
   シャードは `usage:<UTC 日>:<スロット>` として保存され、**スロットは 2 つだけ**です。各
   インスタンスは自分のシャード id で安定してどちらかに割り振られます。3 つ以上のコンテナが
   1 つのボリュームを共有すると、同じスロット内では後勝ちです。**これが「≈」のもう 1 つの
   理由**で、影響するのは数字の網羅性だけ、転送には一切関係しません。

④ **3 つのメディアエンドポイント（画像生成、動画ジョブ作成、動画ポーリング）は数えません。**
   4 つの対話プロトコルと**同じ**上流 key を消費しますが何も記録しない ⇒ パネルの「総
   リクエスト数」は実際の転送量より構造的に小さく出ます。既知の境界であって欠陥ではありません。
   key の消費量は key プール側で判断してください。

</details>

### ストレージ上の各キーを同期させる代償

ファイルストレージには読み取り・書き込み・`list`・delete のいずれにもクォータがありません
——書き直し 1 回の代償は自分のディスクへの書き込み 1 回です。知っておく価値があるのは
**1 つの変更が他から見えるまでどれくらいかかるか**で、これは 2 つのキーにとっては
セキュリティ上の性質、残りにとってはトラブルシューティングの落とし穴です。

#### key プールとそのインデックス

ゲートウェイはプール内の id を並べた `pool:index` を持っており、転送経路が全件走査を
しなくて済むようにしています。**2 つの自己修復経路だけは全件走査を避けられず**、どちらも
同じ組み込みの **10 分**バックオフを共有します（環境変数ではなく固定の定数です）:

- **空プールの再走査**——インデックスは読めるのに生きたレコードが 1 件も読めないとき、
  ゲートウェイは 1 回走査して「手で書いたがインデックスに入っていない」レコードを拾います。
- **インデックス欠損のフォールバック**——`pool:index` 自体が読めない／壊れているとき、
  ゲートウェイは同じく 1 回走査してインデックスの再構築を試みます。

プールが空で**なおかつ**その走査も失敗したとき、ゲートウェイは `500` を返し、本当の理由は
ログに残ります。**`503 pool_empty` に見せかけることはしません**——その時点で本ドキュメントが
説明した 2 つの自己修復経路は両方とも切れており、「プールが空です」と言うのは人を間違った
場所へ案内するだけだからです。

#### 対外 API キー: 失効は即座ではありません

パネルが発行したキーの検証は 1 つの表を読みます。各インスタンスはそれを
`APIKEY_CACHE_TTL_MS`（既定 5 分）だけキャッシュします。

- **クライアントが全員 `GATEWAY_TOKEN` を使うデプロイは、この表を 1 度も読みません。** この
  ゼロはスイッチではなく**構造的**なものです: マスタートークンは認証の第 1 段で比較され、
  その経路にはこの表を読む呼び出し箇所がありません。認証情報を一切持たないリクエストも
  同様に 0 回で、スキャナーにはてこがありません。
- **発行・改名・停止・削除・全消去はいずれも表全体を 1 回書き直します**。しかも人がクリック
  したときだけです。表に何本キーが入っていても回数は変わりません。

> [!IMPORTANT]
> **停止と削除は即座ではありません。これはセキュリティに関わるので「すぐ効きます」と
> 読まないでください。** そのリクエストを処理したインスタンスは即座に反映しますが、同じ
> ボリュームを共有する他のコンテナは最大で `APIKEY_CACHE_TTL_MS` ⇒ 既定で約 **5 分**
> かかります。速くする方法はその値を小さくすることだけで、代償は 1 インスタンスあたり
> 1 間隔につき表を 1 回多く読むことだけです。

#### パネルのクリックが何を書くか

いずれも計量はされませんが、クリックする前に知っておく価値のある形が 2 つあります:

- **新しい key を M 本インポートする**と M 件のレコードとインデックス 1 回を書きます。
  **1 回あたり最大 200 本**——超えるとそのまま `400` で、**黙って切り捨てることはありません**。
  大きなインポートを分割しても安くはなりません。インデックスはバッチごとに書き直すからです。
- **同じ key をもう一度インポートしても**（「既存 key の状態をリセット」を付けない場合）
  **何も書きません**: 重複は既定でスキップされ上書きされないので、一覧をまるごと貼り直しても
  安全です。
- **N 本の一括削除**はインデックスを**1 回**しか書き直しません（N 回ではありません）。
  **key プールの全消去**も同じ規則です。
- **key を 1 本変更**（停止 / 有効化 / メモ / クールダウン解除 / strikes クリア /
  除外解除 / 利用回数のリセット）は、**どれを変えても読み 1 回・書き 1 回**です:
  すべて同じハンドラの同じ 1 回の永続化を通り、利用回数のリセットは余計な読み書きを
  一切しません（消すのはメモリ上の永続化基準値です）。

  > [!IMPORTANT]
  > **括弧の最後の項目は、ここで唯一「パネルからは押せない」ものです**: 利用回数の
  > リセットは**今日は API だけで、パネルにこのボタンはありません**（上の
  > `POOL_TOUCH_INTERVAL_MS` の行と同じ）。この列挙はハンドラが理解する全動作であって、
  > パネルのボタン一覧ではありません。別の経路のほうが高いと思われないよう書いています。
- **「今すぐ補充」はパネル唯一の 1 日上限付きの操作**です——1 日最大 **24** 回（4 番目の
  ガードレール、[REGISTRAR.md](REGISTRAR.md) 参照）。このゲートが守るのは使い捨てメール
  ボックスの枠と上流プラットフォームであって、ストレージの予算ではありません。
- **設定の保存**は `config` の 1 件を書き直し、**検証に落ちた保存は 1 バイトも書きません**。
- **危険ゾーンの 2 つのボタン**: 設定のリセット（`/admin/api/config/reset`）は同じ 1 件を
  書き直し、key プールの全消去（`/admin/api/keys/purge`）は全レコードを削除してインデックスを
  **1 回だけ**書き直します。

同じ理由で、読み取りのファンアウトも 2 つ知っておく価値があります:

- **パネル「使用量」の `30d` の段**は 1 リクエストで `30 × 2` 個のシャード
  （`USAGE_DAY_RETAIN × USAGE_SLOTS`）を読みます。**このファンアウトを本リポジトリは実機で
  計測したことがありません**。ですからここで約束するのは**正直に失敗すること**だけです:
  途中で失敗したときは `days` の系列まるごとが `null` になり `note` は `read_failed` に
  なります —— 読めた分だけを完全な絵として渡すことはしません。
- **プレイグラウンドの動画 1 タスクは上流リクエスト最大 `1 + 60` 回**（作成 1 回 + 最大
  `VIDEO_POLL_MAX_ATTEMPTS` 回のポーリング）。これが倍にするのは**上流**のクォータと key の
  使用カウントであって、自分のディスク上の何かではありません。

### 管理パネル関連の変数（デフォルトで無効）

| 変数 | 必須 | 既定値 | 説明 |
|----|----|------|----|
| `ADMIN_TOKEN` | いいえ | なし（パネル無効） | 管理エンドポイントのトークン。**`GATEWAY_TOKEN` と異なる値**であること、24 文字以上であること、**先頭・末尾に空白がない**こと、そして**印字可能な ASCII（0x20–0x7E）のみ**で構成されていることが必須。文字集合・長さの下限・ゲートウェイ口令と異なることという 3 つの理由と、規則違反の種類ごとに何が起きるかは下記。 |
| `TRUST_PROXY` | いいえ | 未設定（転送ヘッダーを**一切**信頼しない） | ゲートウェイが実際にプロキシ（CDN、またはコンテナの前段の nginx / Caddy / Traefik）の背後にある場合**のみ** `1` にしてください。ログイン失敗イベントのクライアント IP をどこから取るかを決めます。詳細は下記。 |

**未設定なら管理パネルが使えないだけで、ゲートウェイの転送は通常どおり動きます。** このとき
`/admin/...` へのリクエストは **`401` ではなく `404`** になります。ツリーそのものが登録されない
ため、「ここに管理画面がある」という事実自体が漏れません。これはレジストラーがデフォルトで
無効なのと同じ方針です。`ADMIN_TOKEN` の欠落や設定ミスでゲートウェイの転送を止めてはいけません。

どちらの行も、他の設定と同じ `.env` に書きます:

```env
# 任意: 管理パネルのトークン。未設定なら /admin ツリーは一切登録されません。
# GATEWAY_TOKEN とは別の値で、24 文字以上、印字可能な ASCII のみ。
ADMIN_TOKEN=別の長いランダム文字列に置き換えてください

# 任意: クライアントアドレスを書き換えるプロキシの背後にコンテナがある場合のみ 1 に。
# 直接公開しているデプロイでは設定しないでください。
TRUST_PROXY=1
```

#### `ADMIN_TOKEN` の 3 つのハードルール

**「規則違反」には結果のまったく異なる 2 種類があります。ひとつの文にまとめないでください。**
未設定、またはトークン自体が規則違反（前後の空白 / 印字不可の ASCII / 24 文字未満）の場合は
`/admin` ツリー全体が登録されず、ログには `admin.token_rejected` が出ます。規則には合っていても
実効の `GATEWAY_TOKEN` と同一の場合は、ツリーは**通常どおり登録**されパネル自体も開きますが、
管理エンドポイントだけが毎回 `503` を返し、ログには `admin.token_conflict` が出ます（この規則は
起動時ではなく管理リクエストごとに再判定されます）。

**先頭・末尾に空白があってはいけません**: HTTP はヘッダー値の前後の空白を除去しますが環境変数は
保持するため、空白付きのトークンはどのクライアントからも送信できません。

##### なぜ印字可能 ASCII だけなのか

さらにトークンは**印字可能な ASCII（0x20–0x7E）のみ**で構成する必要があります。この制限には
性質の異なる 3 つの理由があります:

1. U+00FF を超える文字（漢字・emoji・ゼロ幅スペース）と改行・NUL は、ヘッダー値の設定時に
   `fetch` が**例外を投げます**——リクエストがそもそも送信されないため、200 を返すのに決して
   入れないパネルができあがり、サーバー側には `admin.login_failed` の 1 行すら残りません。
2. **TAB を除く**その他の制御文字（`0x01–0x08`、`0x0B`、`0x0C`、`0x0E–0x1F`、`0x7F` の計 29 個）
   はブラウザーからは送信できますが、HTTP パーサーが `400` として拒否します。
3. **TAB（`0x09`）**および `é` / `£` / ノーブレークスペースのような `0x80–0xFF` のバイトは
   **実際には送信でき、動作もします**——これを拒否しているのは物理的な制約ではなく**当方の
   堅牢性のためのトレードオフ**であり、**両者で理由が異なります**。TAB は**目に見えない文字**で、
   `.env` やシークレットに貼り付けられても誰も気づけません（前後の空白と同種の診断しやすさの
   問題ですが、あちらは物理的、こちらはトレードオフです）。`0x80–0xFF` の方はエンコーディングの
   問題です: 環境変数は UTF-8、ヘッダー値は Latin-1 として復号され、その範囲で両者が一致する
   ことは仕様上保証されていません。
   また RFC 9110 はこの範囲を非推奨としています。

ASCII のみのトークンをご利用ください。**途中のスペースは許可されます**——
`correct horse battery staple` のようなパスフレーズは問題なく送信・到達しますし、24 文字という
下限のもとではランダム文字列より扱いを誤りにくいことも多いためです。先頭・末尾の空白は上の
ルールが担当します。

##### 24 文字という下限の理由

**24 文字という下限の理由。** このゲートウェイには**ログインレート制限が一切ありません**
——IP 単位でも、トークン単位でも、インスタンス単位でもです。実装する
にはストレージ上にカウント窓を作る必要があり、それは未認証の呼び出し元に書き込みを起こさせるレバーを
渡すことになります（攻撃面が「パスワードを当てる」から「キープールの状態書き込みを潰す」まで
広がる）。したがってトークンのエントロピーが唯一の防御であり、この下限は推奨値ではありません。
下回る場合パネルは有効化されず、コンテナログに `admin.token_rejected` が出力されます。

##### `GATEWAY_TOKEN` と異なる必要がある理由

**`GATEWAY_TOKEN` と異なる必要がある理由。** `GATEWAY_TOKEN` は**すべての下流ユーザー**に配る
中継トークンです。これをパネルのトークンとして使い回すと、中継トークンを持つ誰もがキープール
全体を読み、レジストラーを停止し、登録バックエンドを自分のサーバーに向け替えられます——以降に
作られる全アカウントのメールアドレス・パスワード・認証コードが奪われます。

##### 衝突はどう表面化し、どう対処するのか

このルールは**管理リクエストごとに再検査されるだけで、起動時には遮断しません**。両者が同一の
場合——例えば `store.json` の直接編集で `gatewayToken` を手作業で
書き換えた場合——管理エンドポイントは **`503` を返し**、error レベルで `admin.token_conflict`
が記録されます（起動時点で既に衝突しているなら、起動ログにも同じ行が出るのですぐ原因が
分かります）。**ゲートウェイの転送は影響を受けません。**

**衝突が起きた時点で `ADMIN_TOKEN` は漏洩したものとして扱ってください。回復方法は一つだけ、
まったく新しい値にローテーションすることです。** `.env` を編集して
`docker compose up -d` を実行し、新しい値でコンテナを作り直してください。
**ストレージ上の `gatewayToken` を戻すだけで済ませないでください。** それでも管理エンドポイントは
すぐ回復します（設定キャッシュが次に更新された時点で有効になり、**再起動は不要**）が、
それが回復させるのは可用性であって安全性ではありません。衝突していた間、管理トークンと
ゲートウェイトークンは同じ値であり、ゲートウェイトークンは**すべての下流ユーザー**に配るもの
です——既に持っている人（あるいはこれから渡される人）は、そのまま管理画面を開けてしまいます。
可用性を先に戻すために `gatewayToken` を戻すのは構いませんが、その後で**必ず `ADMIN_TOKEN` を
ローテーション**してください。両方を終えて初めて対処完了です。

##### なぜこの 1 条だけ起動時に止めないのか

**なぜこのルールだけ起動時に遮断しないのか。** `gatewayToken` は稼働中に変わり得るのに、起動時の
判定には二度目の評価の機会がありません。そこで `/admin` ツリー全体を登録しない扱いにすると、
衝突中に起動したコンテナはすべて**恒久的に
`404`** になり、設定を戻しても直らずもう一度再起動するしか手がなくなります。一方で衝突前に起動したものは
`503` にとどまり、値を戻せばすぐ回復します。同じ設定・同じ瞬間に二つの答えが存在することになり、
上の「再起動は不要」という一文が半分嘘になります。`ADMIN_TOKEN` 自身に関する 3 つのルール
（前後の空白、送信できない文字、最小長）は入力が環境変数だけで稼働中に変わらないため、引き続き起動時に遮断し、
失敗の形は `404` のままです。

##### ローテーションの方法と、漏れたときの対処

`ADMIN_TOKEN` は**環境変数からのみ読み取られ、ストレージからは読みません**。パネルが自分の鍵を
ローテーションすることはできません。ローテーション方法は `.env` を編集してから
`docker compose up -d` です——コンテナの環境は作成時に凍結されるので、
`docker compose restart` では駄目です。

**管理トークンの漏洩は `ADMIN_TOKEN` そのものの漏洩です。** パネルはこれをブラウザーの
localStorage にそのまま保存します。派生トークンはなく、製品内に失効経路もありません。失効させる
唯一の方法は、`.env` の値を変更してコンテナを作り直すことです。
パネルは 12 時間後にトークンの再入力を求めますが、それはその localStorage の値が使える期間を
短くするだけで、**失効ではありません**。パネルは TLS の背後に置き、信頼できる端末でのみ開いてください。

**この上限にできないことも明記します。** パネルの CSP は `connect-src 'self'` でトークンを外部
ドメインへ `fetch` することを、`form-action 'none'` でフォーム経由の持ち出しを防ぎます。しかし
`location.href = "https://…?k=" + token` のような**ナビゲーションによる持ち出し**は防げません
— CSP にはもうそれを止めるディレクティブがありません（`navigate-to` は仕様から削除されました）。
本当の解決策はサーバーが発行する**失効可能な派生トークン**ですが、それはサーバー側でセッションを
保存することを要求し、「`ADMIN_TOKEN` は環境変数からのみ読む」という設計上の制約と衝突するため、
後続のリリースに回します。

#### `TRUST_PROXY` はクライアント IP の取得元を決める

設定すると、ログイン失敗イベントに記録されるクライアント IP は `CF-Connecting-IP` から取られ、
無い場合にのみ `X-Forwarded-For` の先頭要素へフォールバックします。

**`TRUST_PROXY` はセキュリティスイッチなので既定で無効です。** これが決めるクライアント IP は
`admin.login_failed` イベントに記録されるため、クライアントが送ってくるヘッダーを無条件に信頼すると、
誰でも総当たりの痕跡を任意の IP になすりつけられます。

**無効時はどの転送ヘッダーも信頼せず、このフィールドは一律 `null` になります——`CF-Connecting-IP`
も例外ではありません。** このヘッダーは「プラットフォームが注入するので偽装できない」と説明されがち
ですが、その性質は**リクエストが実際に Cloudflare を通る場合にのみ**成り立ちます。Node/Docker を直接
公開している構成では上書きするものが何もないため、クライアントが自分で
`CF-Connecting-IP: 1.2.3.4` を送れば信じられてしまいます——そして直接公開は Docker 配備の既定の形です。

**有効時は `CF-Connecting-IP` が優先され、`X-Forwarded-For` はフォールバックにすぎません。**
2 つのヘッダーは偽装のしやすさが根本的に異なります。

- `CF-Connecting-IP` は Cloudflare のエッジが書き込み、クライアントが送ってきた同名ヘッダーを
  **上書きします**——リクエストが実際に Cloudflare を通る限り偽装できません。
- `X-Forwarded-For` はどのミドルボックスでも追記できる連鎖で、クライアントが偽物を送ることもできる
  ため、どこまで信じられるかはプロキシ構成次第です。

##### 2 つのトポロジーそれぞれの設定方法

**オリジンの前段に Cloudflare がいる場合は `TRUST_PROXY=1` を設定してください。** Cloudflare は
リクエストごとに `CF-Connecting-IP` を書き換えるため、それが権威ある値です。この形態で
`X-Forwarded-For` を優先するのは誤りで、その連鎖にはクライアントが詰め込んだものが入っている
可能性があります。スイッチを設定しない場合、このフィールドは単に `null` として記録されます。
**オリジンに直接到達できなくなってから有効にしてください**——さもないと CDN を迂回した
クライアントが自分でヘッダーを付けてきます。

**汎用リバースプロキシ（nginx / Caddy / Traefik）の背後で `TRUST_PROXY=1` を有効にする場合は、
プロキシ側で `CF-Connecting-IP` を除去してください。** その構成では誰もこのヘッダーを上書きしませんが、
ゲートウェイは「Cloudflare が前段にいる」前提でこれを優先するため、攻撃者が自分で付けたヘッダーが
プロキシの書いた `X-Forwarded-For` を**上回って**しまいます。nginx なら 1 行です:

```nginx
proxy_set_header CF-Connecting-IP "";
```

Caddy は `header_up CF-Connecting-IP ""`、Traefik はミドルウェアの `customRequestHeaders` を使います。

##### 形式チェックと、取得できないときは正直に `null`

**どちらのヘッダーも先に形式チェックを通ります**: ドット区切りの IPv4 と IPv6 の形（16 進数、
コロン、`::ffff:` マッピング内のドット）だけがイベントに入り、それ以外は一律 `null` として
記録されます。これは認証の防御線ではなく（この値の消費箇所はリポジトリ全体でログイン失敗
イベント 1 か所だけです）、未認証の呼び出し元が監査フィールドに任意のテキストを書き込めない
ようにするためのものです。管理パネルのイベント欄はこのフィールドで絞り込みと表示を行います。

利用できる値が何も無い場合、このフィールドは正直に `null` として記録されます——**`"unknown"` という
偽の値は決して作りません**。実在の送信元と誤解されるためです。

### 設定ページで変更できるもの

これらの項目はカード 3 枚に分かれます：**認証キー**と**上流とクールダウン**は**設定**
ページに、**レジストラー**（完全に対等な 2 つのメールボックスチャネルのサブカードと
「詳細設定」の折りたたみを含む）は**レジストラ**ボードの「設定」タブにあります。
3 枚とも書き込み先は**ストレージ内の `config` キー**であり、環境変数ではありません。

**各項目には 1 つではなく 3 つの値が表示されます。**「保存値 X · 環境変数 Y · 実効値 Z」の行が、
「あなたが保存したもの」「デプロイ側が与えているもの」「ゲートウェイが実際に使っているもの」を
分けて示します。優先順位は常に **環境変数 > ストレージ > 組み込み値** です。

#### 環境変数でロックされた項目はそもそも編集できません

**環境変数でロックされた項目はパネルから変更しても反映されないため、パネルはそもそも編集させません。**
入力欄はグレーアウトされ、どの環境変数によるものか、変更はデプロイ側で行う必要があることが併記されます。
`PUT /admin/api/config` はそうした項目に対して `400 locked_by_env` を返し、**ストレージには一切書きません**。
書いてしまうと「保存成功・実効値は不変」となり、運用者はキャッシュのせいだと思って何周期も無駄に待つことになります。

> [!IMPORTANT]
> **レジストラー系（`REGISTRAR_ENABLED`／`REGISTRAR_CHANNEL`（互換エイリアスを含む）／
> `TARGET_KEYS`／`MINT_BATCH`／`TEND_INTERVAL_MS`／`CODE_TIMEOUT_MS`／`MINT_DELAY_MIN_MS`／
> `MINT_DELAY_MAX_MS`／`MAX_DOMAIN_ATTEMPTS`／`REGISTRAR_TOKEN_NAME`／`AGNES_PLATFORM_URL`／
> `YYDS_BASE_URL`／`YYDS_API_KEY`／`MOEMAIL_BASE_URL`／`MOEMAIL_API_KEY`）もこのロック表に入りました。**
> それ以前は入っていませんでした：`docker-compose.yml` に `TARGET_KEYS=30` があるとき、
> パネルで 20 に変えても保存は成功し、実効値はずっと 30 のまま——**再起動しても直らず**、
> パネルには何の表示もありませんでした。

#### 資格情報は書き込み専用

**資格情報は書き込み専用です。** ゲートウェイトークンと 2 つのチャネルの API キーは
**平文では決して返しません**。返すのは「設定済みかどうか」と**末尾 4 文字**だけです
（5 文字未満なら末尾 4 文字すら返しません——それは全部を見せることになるからです）。したがって：

- 入力欄は常に空で、プレースホルダーには**空欄のままにすると変更されません**と表示されます；
- 保存時、これらの欄が**未入力または空 = 変更しない**（クリアではありません）。空をクリアとして
  実装すると、運用者が設定ページを一度保存しただけでゲートウェイトークンが消え、しかも
  **現在のプロセスは直前の有効なスナップショットで動き続ける**ため、次の再起動まで異常に見えません；
- クリアは専用の「クリア」ボタン（確認ダイアログ付き）からのみ可能です。

##### パネルから書き込んだ資格情報はどう保存されるか

> [!WARNING]
> **パネルから書き込んだ資格情報は `store.json` に平文で保存されます**。
> 「キーは平文で保存」と同じ水準です。ここに入力するものが暗号化された secret だとは考えないでください。
> データディレクトリは資格情報として扱ってください。

> [!WARNING]
> **環境変数にも `GATEWAY_TOKEN` が無い状態でゲートウェイトークンをクリアした場合**、
> 現在のプロセスは動き続けますが、**次の再起動で起動できなくなります**。
> パネルはその場で赤い注意書きで明示します。同じページですぐに新しいゲートウェイトークンを設定して復旧してください。**環境変数がこの値を与えている場合、クリアは安全です**：消えるのはストレージ上の一部だけで、実効値は環境変数にフォールバックし変わりません。パネルはこの 2 つの状態で別々の文言を出し、判断を利用者に押し付けません。

#### 「詳細設定」内のレジストラーのバックエンド URL

> [!WARNING]
> **「詳細設定」の中にある登録バックエンドの URL（`AGNES_PLATFORM_URL`）は普通の設定項目ではありません。**
> これは**すべての自動登録の送信先**です。別のサーバーに変えると、そのサーバーが各登録に使う
> メールアドレス・パスワード・認証コードを受け取ります。だからこそ折りたたみの中に置き、赤い警告を付け、
> メインの「保存」とは別に専用の確認ボタンを設けています。

#### 保存レシートと伝播にかかる時間

**保存後、パネルは「保存して反映しました」とは言いません。** 実効値を**読み戻し**、
実際に変わった項目をハイライトし、**他のレプリカが変更を見るまで最大どれくらいかかるか**を
明示します：設定ホルダーの更新は最短でも **30** 秒に 1 回なので、それが上限です。
このインスタンスは即時です（保存時にローカルキャッシュを無効化します）が、他のインスタンスは違います。
**パネルの文言に「即時反映」と書いてはいけません。**

### レジストラー関連の変数（オプション、デフォルトで無効）

レジストラーはオプションの自動プール補充コンポーネントで、デフォルトでは無効になって
おり、ゲートウェイの中核である転送機能には影響しません。ここでは変数の早見表のみを
示します。動作原理、2 つのメールボックスチャネルの選び方、Cloudflare Cron の壁時計
上限などの詳細は [REGISTRAR.md](REGISTRAR.md) を参照してください。

| 変数 | 必須 | デフォルト | 説明 |
|----|----|----------|----|
| `REGISTRAR_ENABLED` | いいえ | `false` | マスタースイッチ。`true` にしないとレジストラーは有効になりません。 |
| `REGISTRAR_CHANNEL` | 有効化時は必須 | なし | レジストラーが使うチャネル、`yyds` または `moemail`。2 つのうち 1 つを選びます。デフォルト値なし。 |
| `TARGET_KEYS` | いいえ | `20` | 目標とする利用可能 key 数。 |
| `MINT_BATCH` | いいえ | `5` | 1 ラウンドで発行する key の最大数。 |
| `TEND_INTERVAL_MS` | いいえ | `1800000` | 補充ラウンドを回す間隔。同じタイマーが `pool:index` の照合も行うため、レジストラーがオフでも動き続ける。 |
| `CODE_TIMEOUT_MS` | いいえ | `120000` | 認証コードを待つタイムアウト。 |
| `MINT_DELAY_MIN_MS` / `MINT_DELAY_MAX_MS` | いいえ | `60000` / `90000` | 発行試行の間に入れるランダム待機時間。下限は実測値（これを下回ると上流手前のレート制限が入ります）。上限はジッタの余裕です。 |
| `MAX_DOMAIN_ATTEMPTS` | いいえ | `1` | 1 回の発行試行で試すドメインの最大数。レジストラーはドメインの判定を記憶して再利用するため定常状態では 1 で足ります。**大きくするとラウンドごとのレート制限枠の消費が同じだけ増えます**。 |
| `REGISTRAR_TOKEN_NAME` | いいえ | `auto` | 発行された key が Agnes 管理画面に表示される名前。 |
| `AGNES_PLATFORM_URL` | いいえ | `https://platform-backend.agnes-ai.com` | 登録に使う Agnes プラットフォームのバックエンド。 |
| `YYDS_BASE_URL` / `YYDS_API_KEY` | いいえ / チャネルが yyds の場合は必須 | `https://maliapi.215.im` / 空 | YYDS Mail チャネルの認証情報。 |
| `MOEMAIL_BASE_URL` / `MOEMAIL_API_KEY` | チャネルが moemail の場合は必須 | 空 / 空 | MoeMail チャネルの認証情報（自己ホスト、デフォルトアドレスなし）。 |

> [!NOTE]
> **非推奨になった 2 つの旧名称は、意図的に上の表に入れていません。**
> `REGISTRAR_PRIMARY` は `REGISTRAR_CHANNEL` の**互換エイリアス**です（優先度は低く、
> 使われている場合はパネル上部に通知が出ます。項目のグレーアウトは同じです）。
> `REGISTRAR_FALLBACK` は**経路選択に関与しなくなり**、パネルで「このチャネルは破棄された」
> と名指しで伝えるためだけに一度読まれます。どちらの旧名称もアップグレード中のデプロイを
> 止めませんが、`.env.example` にはもう記載していません——新規デプロイは新しい名前を使います。

#### これら 15 個の変数に誤った値を書いたとき

> [!WARNING]
> **これら 15 個の変数に誤った値を書いても、もうコンテナは起動しなくなりません。**
> 数値系（`TARGET_KEYS=abc`、`MINT_BATCH=0` など）は**上の表のデフォルト値へフォールバック**し、
> パネルに劣化を 1 回報告し、イベントセクションに `config.invalid` を 1 件残します。
> チャネル系・認証情報系の誤り（チャネル名の綴り間違い、レジストラーが有効なのにチャネル未選択、
> 選んだチャネルの API キー欠落）は**レジストラーが今回起動しない**だけで、
> ゲートウェイの転送は通常どおりです。
>
> **これは能力の低下です。明記します**：以前はデプロイのタイプミスでコンテナが落ちたので即座に分かりましたが、
> 今は静かに動き続けるため、パネルのバナーかイベントセクションを自分で見に行く必要があります。
> 手順は下のトラブルシューティングの「レジストラーは有効なのに key を発行しない」を参照してください。

### 2 つのタイムアウト予算の使い分け

判断基準は「上流の最初のバイトがいつ届き得るか」であり、エンドポイントの名前では
ありません:

| 予算 | 対象エンドポイント | 変数 |
|----|------------------|----|
| 最初のバイト | **ストリーミング**対話（`stream: true`）、動画ポーリング `GET /v1/videos/{id}` | `UPSTREAM_TIMEOUT_MS` |
| 同期 | 画像生成、動画ジョブ作成、**すべての非ストリーミング対話**（4 プロトコルとも） | `UPSTREAM_SYNC_TIMEOUT_MS` |

非ストリーミングのリクエストは、上流が回答全体を生成し終えてからでないと応答ヘッダを
返しません。画像生成とまったく同じ遅延の性質であり、8 秒の最初のバイト予算で切ると
正常なリクエストが大量に失敗し、key プールまで巻き添えになります。

`UPSTREAM_SYNC_TIMEOUT_MS` は**1 リクエストの総予算**、つまりクライアントの最悪待ち時間
です——「プールの大きさ × 予算」ではありません。ゲートウェイはこの予算のうち単一の key に
最大でも半分しか使わず、残りは別の key での再試行に取っておきます。こうすることで、
プール内にハングした key（接続はできるが決して応答しない）があってもリクエストを丸ごと
食い潰されません。したがって**単一呼び出しの最悪所要時間の 2 倍以上**に設定してください。

同期予算でのタイムアウトは、その場では key を罰しません。同一リクエスト内で切り替えた
別の key が実際に成功した場合にのみ、先にタイムアウトした key に計上します
（`MAX_STRIKES` に達するとクールダウン）。そのリクエストで全部の key がタイムアウトした
場合は 1 つも罰しません——予算が小さすぎるか上流全体が遅い可能性の方が高いためです。

「排除」と「クールダウン」は別物です。上記の設定にかかわらず、上流の `401`/`403`
はその key を**永久に**排除します——これらは「この key はもう有効ではない」状態
であり、再試行に意味がないためです。一時的な失敗が排除につながることはありません。
`MAX_STRIKES` に達しても `COOLDOWN_STRIKE_MS` のクールダウンに入るだけで自動的に
復帰するので、上流の一時的な不調がプールを恒久的に破壊することはありません。

どの key もリクエストを処理できない場合、ゲートウェイは `503` を返し、`error.reason`
に判別可能な理由を示します：`pool_empty`（key が未登録）、`all_cooling`（全 key が
クールダウン中。自動的に回復し、`Retry-After` ヘッダーが復帰時刻を示す）、
`all_evicted`（全 key が認証情報の失効により永久排除。**自動回復しない**ため key の
入れ替えが必要）、`upstream_error`（key 自体は有効だが、上流が毎回失敗した）。

### 非常に長い非ストリーミングリクエストは途中で切断されるか（前段にいるものが決めます）

**結論: ゲートウェイ自身は `UPSTREAM_SYNC_TIMEOUT_MS` 以外に実時間の上限を課さないので、
健全な長いリクエストを途中で切れるのは、その前段にいるものだけです。**

コンテナの中で動く Node プロセスには**プラットフォームの時間上限が一切ありません**。
非ストリーミングリクエストを縛るのは設定した予算だけで、他には何もありません。
本書が約束するのはそれだけで、管理画面もそれ以上のことは言いません。

**前段にいるものは自分で確認してください。** 個別に明記します。

- リバースプロキシには自前の読み取りタイムアウトがあり、既定値はどれも短めです:
  nginx の `proxy_read_timeout` は 60 秒、Caddy 自体は無制限でもその上流はそうとは限りません。
  上げるなら `UPSTREAM_SYNC_TIMEOUT_MS` と同じ軸で上げてください。さもないと先に切るのは
  プロキシです。
- オリジンの前段に CDN を置くとさらに 1 つ増えます: Cloudflare が文書化している
  **プロキシ読み取りタイムアウトは 100 秒（エラー 524）** で、ゲートウェイのどの設定でも
  延ばせません。
- ロードバランサーのアイドルタイムアウトも同じで、クライアント側から見た症状は同一です:
  接続がただ終わり、見るべき `error.reason` もありません。

⇒ **実際の影響は 2 点:**
① `UPSTREAM_SYNC_TIMEOUT_MS`（既定 120000）は、**前段の連鎖で最も厳しいタイムアウトより
   小さく**設定してください。さもないとゲートウェイなら完走できたリクエストが他人に切られ、
   その理由はログに残りません。
② **本当に長いリクエストが必要ならストリーミングのエンドポイントを使ってください。**
   初回バイトの予算は最初の 1 バイトしか縛らず、その後の生成時間は数えません。しかも
   バイトを出し続けるストリームは、連鎖のどこから見てもアイドルには見えません。

## マルチアカウント設定

key をインポートする通常の経路は管理パネル、または `POST /admin/api/keys`
を直接呼ぶことです（1 回あたり最大 200 本。[API.md](API.md) と
[ADMIN.md](ADMIN.md) を参照）。以下の**ストレージバックエンドへ直接書き込む**
手順は 2 つの場面専用です：`ADMIN_TOKEN` をまだ設定していない（パネルの
ツリー自体が登録されない）場合と、パネルが使えないときの緊急復旧です。
この手順は **`pool:index` を更新しません**。新しいレコードがすぐ見えるとは
限らず、その代償は下の「索引と反映までの時間」にあります。
各エントリは `key:<id>` というキーを持つ JSON オブジェクトで、
`<id>` はプール内で一意な任意の文字列で構いません（ゲートウェイ自身が
レコードを作成する際は key のハッシュ値から導出しますが、読み込み時には
その値は検証されないため、手動インポートでは任意の一意な識別子で問題
ありません）。

```json
{
  "id": "1a2b3c4d5e6f7a8b",
  "key": "実際の-agnes-api-key",
  "addedAt": 1735689600000,
  "lastUsedAt": null,
  "cooldownUntil": 0,
  "strikes": 0,
  "evicted": false,
  "evictedReason": null
}
```

### Docker へのインポート

実行中のプロセスとの書き込み競合を避けるため、まずコンテナを停止し、
ホスト上で `./data/store.json` を編集して、キー
`"key:1a2b3c4d5e6f7a8b"` の下に上記のようなレコードを追加してから、
コンテナを再度起動します。

```bash
docker compose stop
# ./data/store.json を編集
docker compose start
```

`./data/store.json` がまだ存在しない場合は、`key:<id>` という形式の
キーを持つ単一の JSON オブジェクトとして新規作成してください。

### 索引と反映までの時間

ゲートウェイはプール内の id 一覧を `pool:index` というキーに保持しており、転送のたびに全件を
走査せずに済みます。**レコードを手作業で書いてもこの索引は変わりません**。したがって新しい
key がいつ使われ始めるかは、そのときのプールの状態によります:

- **プールが空のとき**: 索引が「空」と言い、実際にレコードが 1 件も読めない場合、ゲートウェイは
  走査に 1 回だけフォールバックし、手動インポートされたレコードを検出して索引に
  追加します。この走査には組み込みの 10 分バックオフがあるため（上の「key プールとその
  インデックス」参照）、可視化までの上界は **10 分以内 + `POOL_CACHE_TTL_MS` 1 回分**です。
- **プールが空でないとき**: 転送経路は索引が知っているレコードしか取得しないため、索引が
  知らないレコードは**完全に見えません**（エラーも一切出ません）。次の照合が索引を
  修復するまで（`TEND_INTERVAL_MS`、既定 30 分）、
  さらにその後最大 `POOL_CACHE_TTL_MS` 1 回分待つ必要があります。

**手動インポートを即座に反映させたい場合は、同じ編集の中で id を `pool:index` へ
追加してください:**

```json
{"v":1,"ids":["既存のid","1a2b3c4d5e6f7a8b"]}
```

索引を書き込めば、プールは最大でも `POOL_CACHE_TTL_MS` 1 回分でこの key を使い始めます。

**照合はレジストラーがオンかどうかに関係なく走ります**。同じ `TEND_INTERVAL_MS` のタイマー
です: これが `pool:index` と実際の `key:` レコードを突き合わせて修復する唯一の経路なので、
孤立レコードやゴースト索引項目は 1 間隔以内に回収されます。この間隔をとんでもなく大きく
すれば、その待ち時間も同じだけ伸びます。待機中は対象の key が一時的に使えないだけで、
失われたり壊れたりすることはありません。

### key を失効させる

**レコードを削除し、その id を `pool:index` からも外す——両方を行ってください。** レコードだけ
削除してもエラーにはなりません（読めないレコードは単に除外されます）が、id が索引に残るため、
次の照合で刈り取られるまで更新のたびに読み取りを 1 回無駄にします。

`./data/store.json` から `"key:<id>"` のエントリを削除し、`"pool:index"` の `ids` 配列を
直します。動いているプロセスに編集を上書きされないよう、先に `docker compose stop` して
ください:

```json
{"v":1,"ids":["残りのid"]}
```

古いスナップショットを読み込み済みのプロセスは、最大 `POOL_CACHE_TTL_MS` 1 回分で
その key を選ばなくなります。

**そのウィンドウの間も書き戻されることはありません**: ゲートウェイは状態変更を永続化する前に
レコードがまだ存在するかを確認し、読めなければその書き込みを破棄して自分のスナップショットを
直ちに更新します。ファイルストレージではこの確認読み取りがファイルそのものに当たり、間に
キャッシュがないため、この保証は厳密です。

## 検証

3 本のコマンドを、安いものから順に。`$BASE` は自分のアドレス（`PORT` を変えず前段に
ドメインも置いていないなら `http://localhost:8080`）に、`$TOKEN` は自分で
設定した `GATEWAY_TOKEN` に置き換えてください。

### ヘルスチェック

```bash
curl -s "$BASE/health"
```

`status` が `ok` ならストレージは読み書きできています。`degraded` はストレージ側に問題がある
という意味で、原因はログにあります。**これだけはトークン不要**なので、トークンを間違えていても
返ってくる唯一のエンドポイントでもあります。

### モデルリストの取得

```bash
curl -s "$BASE/v1/models" -H "Authorization: Bearer $TOKEN"
```

本ゲートウェイが扱うモデルの一覧が返ります。これが通ればトークンは合っています。`401` なら
合っていません。

### 実際の対話を 1 回

```bash
curl -s "$BASE/v1/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"agnes-2.0-flash","messages":[{"role":"user","content":"ping"}]}'
```

実際に上流まで届くのはこれです。`503` が返り `error.reason` が `pool_empty` なら、プールに
まだ key がありません。上の節に戻って 1 本インポートしてください。

## トラブルシューティング

遭遇しやすい順に 7 件。どれも「症状 → 対処」の形で、対処は上から順に試してください。

### ゲートウェイが起動せず、ログにトークン不足の 1 行だけが出る

**症状**：コンテナが**起動直後に終了**し、`docker compose ps` では restarting か exited、
ログには `缺少 GATEWAY_TOKEN，网关无法启动` の 1 行しかありません。**中途半端な状態はここには
ありません**: ゲートウェイはすべてのリクエストに `503` を返すのではなく組み立て自体を拒むので、
誰かがエンドポイントを叩かなくても `docker compose ps` で見えます。

**対処**：

1. `.env` に `GATEWAY_TOKEN=` の行があり、**イコールの後ろが空でない**ことを確認します。
2. 直したら `docker compose up -d` を実行します。**`docker compose restart` では駄目です**
   ——コンテナの環境は作成時に凍結されるので、restart では何も読み直されません。

> [!WARNING]
> **この症状に `RESET_CONFIG=1` を使ってはいけません。** その意味は「**保存された `config` キーを完全に無視する**」
> であり、ゲートウェイのトークンがまさにそこにある（パネルで保存したもの）場合、唯一のトークンごと消えてしまいます。
> この障害は上の 2 手順でしか直せません。

### すべてのリクエストが 503 を返し、理由はプールが空

**症状**：どの転送エンドポイントも `503` を返し、`error.reason` は `pool_empty`。

**対処**：

1. 管理パネルの key プール画面から、または `POST /admin/api/keys`（[API.md](API.md) 参照）で key を最低 1 本インポートします。`ADMIN_TOKEN` 未設定なら「マルチアカウント設定」の節に従ってストレージへ直接書き込みます。
2. インポート済みなのに空のまま: 手書きのレコードは **`pool:index` を変更しません**。突き合わせ（`TEND_INTERVAL_MS`、既定 30 分）を待つか、id を手で索引に足してください。
3. レジストラーはオンなのにプールが増えない: パネルのイベントボードを見るか、[REGISTRAR.md](REGISTRAR.md) に従って 2 つのメールボックスチャネルを切り分けてください。

### レジストラーは有効なのに key を発行しない（パネルは有効と言うのにプールが増えない）

**症状**：レジストラーのスイッチは入っているのに補充ラウンドが 1 度も走らない。プールの key は減る一方で、
最終的に上の「すべてのリクエストが 503 を返し、理由はプールが空」という形で表面化します——そのときには
真の原因から何層も離れています。

これは**静かな機能欠落**です。レジストラーは任意のサブシステムなので、その設定が読み込めなくても
**ゲートウェイの転送は通常どおり**動き、補充だけが止まります。何もクラッシュしないので、自分で見に行く必要があります。

**どこを見るか**（4 か所すべてが同じことを指しています）：

1. 管理パネルの**設定**ページ上部にバナー：「レジストラーは有効ですが、この設定を読み込めなかったため今回は起動していません。転送には影響しません」
   と、不足している項目の一覧。
2. **レジストラー**セクションの状態行が「有効」ではなく「有効 · 今回は起動せず」になっています。
3. **概要**ページの設定サマリーでも、レジストラーの行が同じ表示になります。
4. イベントセクションに毎ラウンド `error` レベルの `registrar.blocked` が出て、不足項目が並びます。

**対処**：バナーに並んだ項目を設定ページで埋めてください（選んだメールボックスチャネルの
API キーが無い、あるいはチャネルをまだ選んでいない、が最も多いケースです）。
**保存すれば復旧します。コンテナの再起動も再デプロイも不要です。**

### パネルが開かず、`/admin` が 404 を返す

**症状**：ブラウザーで `/admin` を開くと `404`。ログイン画面でも `401` でもない。

**対処**：

1. **`ADMIN_TOKEN` を設定していない**ときの正常な形です。ツリーごと登録されないので、「ここに管理画面がある」ことすら漏れません。
2. 設定しても 404 のときは、**まずコンテナが本当に再作成されたかを確認**します: Docker 形態では `.env` を編集したあとに `docker compose up -d` が必要で、`docker compose restart` は読み直しません。これを飛ばすと、下の 3 番が間違った方向へ誘導します。
3. 再作成しても 404: トークンが規則違反です（24 文字未満 / 前後に空白 / 印字不可の ASCII）。コンテナログに `admin.token_rejected` が出ます。
4. パネルは開くのにエンドポイントが `503`: `ADMIN_TOKEN` がストレージの `gatewayToken` と衝突しています。ログは `admin.token_conflict` で、対処は上の節にあります。

### パネルで保存した設定が他のインスタンスになかなか反映されない

**症状**：パネルで設定を保存し、このインスタンスはすぐ変わったが、同じボリュームを共有する別のコンテナは古い値のまま。

**対処**：

1. **正常です**。設定ホルダーの更新は最短でも **30** 秒に 1 回なので、それが上限です。少し待ってから見てください。
2. 2 分たっても変わらない: そのフィールドが環境変数でロックされていないか確認します。ロックされたフィールドはパネルで淡色表示になり、エンドポイントは `400 locked_by_env` を返します。
3. 変更したのが `POOL_CACHE_TTL_MS` / `POOL_TOUCH_INTERVAL_MS` の場合: この 2 つは**インスタンス構築時に一度だけ**読まれるので、コンテナを作り直すしかありません。

### 非ストリーミング要求が大量にタイムアウトし、key プールが赤くなる

**症状**：画像生成・動画ジョブ作成・非ストリーミング対話がまとめてタイムアウトし、パネル上で一群の key がクールダウンに入る。

**対処**：

1. `UPSTREAM_SYNC_TIMEOUT_MS` を**単発呼び出しの最悪所要時間の 2 倍以上**に上げます。既定の `120000` は遅いモデルには厳しめです。
2. `UPSTREAM_TIMEOUT_MS`（最初のバイトの枠、既定 `8000`）で非ストリーミング要求を縛らないでください。あの枠はストリーミングと動画ポーリング用です。
3. 上流全体の速度低下でないことを確認します。1 回のリクエストで全部の key がタイムアウトしたとき、ゲートウェイは**どれも罰しません**。クールダウンは同じリクエスト内で別の key が実際に成功したときだけ記録されます。

### Docker コンテナは起動したのに `/health` が degraded

**症状**：`docker compose ps` が unhealthy を示し、`/health` は `503`、`status` は `degraded`。

**対処**：

1. 9 割はデータディレクトリに書けていません。コンテナログの entrypoint 行を読み、`./data` の所有者が `100:101` かどうか確認してください。
2. `--user` や compose の `user:` で非 root を指定した場合、entrypoint は chown を**行いません**。所有者と書き込み可否は自分で用意する必要があります。
3. `DATA_DIR` が `/` やトップレベルのシステムディレクトリを指しているとき、entrypoint は再帰 chown を拒否して警告を出すだけです——まともなディレクトリに変えてください。
4. **所有者を三度確認しても正しいのに degraded のまま**: たいてい `store.json` が解析できません。上の 3 つはすべて権限の話ですが、これは違います —— ストレージ層が正しい JSON を読めないと読み書きのたびに例外が飛び、起動プローブは「書き込み可」を false として記録し、`/health` は同じ `503` degraded を返します。コンテナを止めて `python3 -m json.tool ./data/store.json` で検証してください: 上の「マルチアカウント設定」が教える手編集が最も多い壊し方です（カンマ 1 つ多いだけで十分）。壊れていればバックアップから復元します。本当の原因はコンテナログの 1 行目に出ています。

## パフォーマンス最適化

まず 1 点はっきりさせておきます。**このゲートウェイ自身はほとんど時間を使いません。**
コストは 2 か所——上流の応答時間と、ストレージの読み書きクォータです。したがってこの節で
触る価値があるつまみは 3 つだけです。

```env
# 任意: 各プロセスが key プールのスナップショットを保持する時間（ミリ秒）。0 で無効。
# 大きくするとファイル読み取りを節約できる。代償は他コンテナの判定が見えるのが遅れること。
POOL_CACHE_TTL_MS=120000

# 任意: 「最終使用時刻」を書き込む最大間隔（ミリ秒）。0 で成功リクエストごとに書き込む。
# 表示専用のフィールドなので、小さくしても書き込み回数が増えるだけで得はない。
POOL_TOUCH_INTERVAL_MS=21600000

# 任意: 同期エンドポイント（画像・動画ジョブ・すべての非ストリーミング対話）の全体予算（ミリ秒）。
# 単発呼び出しの最悪所要時間の 2 倍以上にしないと、正常なリクエストまで落ちて key プールに響く。
UPSTREAM_SYNC_TIMEOUT_MS=180000
```

効果の大きい順に 3 つ:

1. **1 つのボリュームを複数コンテナで共有していないなら `POOL_CACHE_TTL_MS` は触らないでください。**
   単一コンテナならそのスナップショットが権威なので、大きくしても何も買えず、`store.json` を
   手で書き換えたことに気づくのが遅くなるだけです。実際にレプリカを走らせ、同じ key が
   二度判定されるのを見てから大きくしてください。
   算式は上の「クォータの見積もり」にあります。
2. **パネルの「最終使用」を細かくしたいという理由で `POOL_TOUCH_INTERVAL_MS` を下げないでください。**
   表示専用のフィールドである一方、書き込み枠は 1 日 1,000 回しかなく、クールダウンと除外の
   記録が同じ枠を奪い合っています。
3. **長いリクエストはストリーミングのエンドポイントに寄せます。** 最初のバイトの枠は最初の
   1 バイトまでしか縛らず、その後の生成時間は数えません。非ストリーミングの枠は上流が答えを
   全部作り終えるまでを含みますし、2 つの形態でプラットフォーム側の挙動が同じとも限りません。

## 監視とメンテナンス

### ヘルスエンドポイント

`/health` はトークン不要な唯一のエンドポイントで、両形態にあります:

```bash
curl -s "$BASE/health"
```

`status` が `ok` ならストレージは読み書き可能、`degraded` ならストレージ側に問題があります
（Docker ではたいていデータディレクトリに書けていません）。Docker 形態ではイメージ内蔵の
`HEALTHCHECK` がこれを叩いており、`docker compose ps` の healthy/unhealthy はそこから来ます。

### パネルのイベントボード

`ADMIN_TOKEN` を設定すると、パネルのイベントボードがゲートウェイ自身の診断イベントを
レベル別に並べます（ログイン失敗、トークン衝突、補充失敗、予算切れなど）。
**ログの代わりにはなりません**: 保持は 24 時間、1 回のポーリングで遡れるのは最大 48 キーです。
長期保存が要るならコンテナログを転送してください。

### 使用量統計（既定はオフ）

日／時間／モデル／プロトコル別の時系列は**既定でオフ**で、その「オフ」はゼロコストです——
アキュムレータを作らず、ストレージ書き込みも 1 回も起きません。オンにするには:

```env
# 任意: パネル「使用量」セクションの Tier-2 時系列。判定は文字どおりの true で、1 や yes はオフ扱い。
# オンにすると 1 インスタンスあたり 1 間隔につきシャードを 1 つ書き直す。未書き出しの
# 尻尾は最長 2 時間。この窓の中で止まったプロセスはそのカウントごと消える（遅れて計上されるのではない）。
USAGE_STATS_ENABLED=true
```

**オンにする前に上の 2 つの警告を読んでください。** 失われるのはプロセスが止まった瞬間に
まだ抱えていたカウントで、環境変数を 1 つ変えるためにコンテナを作り直すだけでそれは起きます。
この形態では `USAGE_FLUSH_INTERVAL_MS` をいくらでも小さくできます——このトレードオフは
あなたのもので、外から課された制限ではありません。

## アップデート

2 つのアップデートコマンドは [Docker デプロイ](#docker-デプロイ) の「更新」にあります。
この節では、その 2 つのコマンドの外側の話をします。

### アップデートの前に

1. **先にストレージをバックアップします。** key プールと設定はこの 1 部しかありません。
   後述の「バックアップと復元」を参照。
2. **基準値を控えます: 現在の `version` と key プールの件数。** 前者は
   `curl -s "$BASE/health"` が返すあのフィールド、後者はパネルの概要ページにあります。基準値が
   ないと、下の 3 つの確認では「上がった」と「そもそも上がっていない」を区別できません。
3. **CHANGELOG に目を通します。** 破壊的変更はそこに書かれます。6 つの README のバッジが
   そこを指しています。
4. **アップデートにストレージの初期化は不要です。** 保存レコードは後方互換で、`pool:index` の
   `v` フィールドは今日のところ常に `1` です。

### アップデート後に確認すること

1. `/health` が `200`、`status` が `ok` を返し、**さらに `version` が今回上げたバージョン番号と
   一致すること**。3 つのうちこの後半だけが「上がった」と「そもそも上がっていない」を区別
   できます: `version` はコンパイル時定数でイメージに焼き込まれ、残り 2 つは旧バージョンでも
   一字一句そのまま通ります。イメージが公開されなかったとき（Release だけ出てビルドが中断された
   —— 本リポジトリで実際に起きました）、`docker compose pull` は静かに成功する空振りです。
2. パネル（動かしているなら）にログインでき、key プールの件数がアップデート前と同じであること。
   概要ページのランタイム欄にもバージョン番号が出ており、1 番と裏取りできます。
3. 上の「検証」の 3 本目を 1 回流し、実際に上流まで届くことを確認すること。

ロールバック: Docker は `.env` の `IMAGE_TAG` を前のバージョンに戻して `docker compose up -d`
をやり直します（イメージのフルネームと tag 一覧の場所は上の「Docker デプロイ → 更新」）。
**その tag が registry に本当に存在するかを先に確認してください**: 取得できないとき compose は
失敗せず、**いまの作業ツリー**からそのバージョン番号のイメージをビルドします。ロールバックは
「成功」し、障害はそのまま残ります。

## バックアップと復元

key プールと設定はこの 1 部だけで、控えはありません。**バックアップとはストレージそのものを
取ることです。**

### 取り方

```bash
docker compose stop
cp -a ./data ./data.bak
docker compose start
```

一度止めるのは書き込み競合を避けるためです。復元はディレクトリを戻して
`docker compose up -d` するだけです。

### 中身と、拾い書きが罠になる理由

`./data/store.json` に全部入っています —— key のレコードと `pool:index` だけでなく、
`apikeys`（発行済みの対外 API キー表）、`config`（パネルが保存した設定）、
`registrar:domains` と `registrar:backoff`（レジストラーのドメイン可用性と
バックオフ台帳）、`tend:history`（補充履歴）、そしてイベントリングも。

> [!CAUTION]
> **そのファイルから `key:<id>` と `pool:index` だけを拾い出すと 4 系統のキーを取りこぼし、
> しかもその取りこぼしは復元の現場ではまったく見えません。** その拾い方で復元すると: 上流の key プールは
> 戻り、`/health` は `ok` を返し、自分で `GATEWAY_TOKEN` を使った疎通も通ります —— なのに
> 下流ユーザーの手元にあるサブキーは全部 `401` になります。取りこぼすのはこの 4 系統:
> `apikeys`（発行済みの対外 API キー表。復元しないことは全サブキーの一斉失効に等しく、平文は
> 発行時の 1 回しか出ないため取り戻せず、全部を再発行するしかありません）、`config`（パネルが
> 保存した設定。ゲートウェイのトークンと 2 つのメールボックスチャネルの認証情報を含む）、
> `registrar:domains` と `registrar:backoff`（失うとレジストラーは「有効 · 今回は起動せず」に
> なります）、`tend:history`（補充履歴）。
> **上の `cp -a ./data` にはこの問題が一切ありません**——それが推奨のレシピである理由です。

> [!WARNING]
> バックアップファイルには **平文の key と平文の認証情報**が入っています（ゲートウェイの
> トークンも、2 つのメールボックスチャネルの API Key も、ストレージ側の設定にあります）。
> 認証情報として扱ってください: リポジトリに入れない、公開のオブジェクトストレージに置かない。

## セキュリティ推奨事項

- **`GATEWAY_TOKEN` と `ADMIN_TOKEN` は別々の 2 本にしてください。** 前者は**すべての下流
  ユーザー**に配る中継トークンです。それをパネルのトークンに流用すると、key プール全体、
  レジストラーのスイッチ、登録バックエンドの URL まで一緒に渡すことになります。
- **パネルは TLS の後ろに置き、信頼できるマシンでだけ開いてください。** パネルは
  `ADMIN_TOKEN` をブラウザーの localStorage にそのまま保存します。派生トークンも、製品内の
  失効手段もありません。12 時間後に再入力を求めるのは窓を短くするだけで、**失効ではありません**。
- **`TRUST_PROXY` はゲートウェイが本当にプロキシの背後にあるときだけオンにしてください。**
  汎用リバースプロキシの背後でオンにするなら、そのプロキシ側で `CF-Connecting-IP` を落として
  ください。落とさないと、攻撃者が自分で付けた値がプロキシの書いた `X-Forwarded-For` を
  上書きしてしまいます。
- **データディレクトリとバックアップはすべて認証情報として扱ってください。**
  key もパネル経由で書いた認証情報もすべて平文で保存され、key の平文保存と同じ水準です。
### 対外 API キーは上流 key プールと正反対です

- **対外 API キーの平文は一度しか現れません。** 発行したリクエストのレスポンスにだけ含まれ、
  以後どのインターフェースからも取得できません——ゲートウェイが保存するのは SHA-256 ダイジェスト
  だけです。紛失したら復元できないので、削除して発行し直してください。**上流 key プールとは
  正反対**です（あちらは実際に使うので平文で保存する必要があります）。
- **`GATEWAY_TOKEN` を配らず、下流ごとにサブキーを 1 本ずつ渡してください。** サブキーは
  個別に停止・有効期限設定・失効ができますが、マスタートークンは一度配ってしまうと、
  ローテーションして全員を同時に止める以外に取り消す方法がありません。

最小限のセキュリティ基準となる設定:

```env
# 必須: クライアントが本ゲートウェイを呼び出す際に提示するトークン。下流に配るのはこれです。
GATEWAY_TOKEN=自分で用意した長いランダム文字列に置き換える

# 任意: 管理パネルのトークン。未設定なら /admin ツリーごと登録されず、401 ではなく 404 になる。
# GATEWAY_TOKEN と異なる値で、24 文字以上、印字可能な ASCII のみ。
ADMIN_TOKEN=もう一本の長いランダム文字列に置き換える

# 任意: クライアントアドレスを書き換えるプロキシや CDN の背後にコンテナがあるときだけ 1 に。
# 直接公開しているデプロイでは設定しない。
TRUST_PROXY=1
```
