# デプロイガイド

**Language:** [English](../en/DEPLOY.md) | [简体中文](../zh-CN/DEPLOY.md) | [繁體中文](../zh-TW/DEPLOY.md) | 日本語 | [한국어](../ko/DEPLOY.md)

agnes2api は同一のコードベースとリクエスト処理ロジックから構築された 2 つの
デプロイ先を提供します。あなたのインフラに合わせてどちらかを選んでください。
両者の違いはストレージバックエンドのみです。Worker は Cloudflare KV
ネームスペースを、Docker はマウントされたボリューム上の JSON ファイルを使います。

## 環境変数

| 変数 | 必須 | デフォルト | 説明 |
|---|---|---|---|
| `GATEWAY_TOKEN` | **はい** | – | クライアントが本ゲートウェイを呼び出す際に提示しなければならないトークン。 |
| `AGNES_BASE_URL` | いいえ | `https://apihub.agnes-ai.com/v1` | 上流 Agnes API のベース URL。 |
| `UPSTREAM_TIMEOUT_MS` | いいえ | `8000` | **ストリーミング**応答と動画ポーリングの最初のバイトのタイムアウト。この時間（ミリ秒）以内に上流の最初のバイトが届かない場合、呼び出しを中断する。 |
| `UPSTREAM_SYNC_TIMEOUT_MS` | いいえ | `120000` | **同期**エンドポイントの全体タイムアウト予算。「最初のバイトが、上流が結果全体を計算し終えてから届く」種類のリクエストにのみ適用される: 画像生成、動画ジョブ作成、そしてすべての**非ストリーミング**対話。詳細は下記。 |
| `MAX_STRIKES` | いいえ | `3` | 連続する一時的な失敗（タイムアウト、ネットワークエラー、上流 `5xx`）がこの閾値に達すると key を長いクールダウンに入れる。 |
| `COOLDOWN_RATE_LIMIT_MS` | いいえ | `60000` | 上流が `429` を返した後、その key に適用されるクールダウン時間。 |
| `COOLDOWN_PAYMENT_MS` | いいえ | `3600000` | 上流が `402` を返した後、その key に適用されるクールダウン時間。 |
| `COOLDOWN_STRIKE_MS` | いいえ | `1800000` | key の一時的な失敗が `MAX_STRIKES` に達した後のクールダウン時間。満了時に自動で復帰する。 |
| `POOL_CACHE_TTL_MS` | いいえ | `60000` | 各 isolate／プロセスが key プールのスナップショットをメモリ上に保持する時間。`0` でキャッシュ無効。**KV の読み取り回数はリクエスト数とは無関係**で、更新頻度だけで決まる。算出式は下記「クォータの見積もり」を参照。代償: 他の isolate が判定したクールダウン／除外が、この isolate に見えるまで最大で**この値 + 約 60 秒**かかる（60 秒分は KV のエッジキャッシュのデフォルト `cacheTtl`）。デフォルトの 60000 では上限は約 **120 秒**。しかも「見えるのが遅れる」だけではない: 古いスナップショット上で行われたスケジューリング系の書き込みはレコード全体を上書きしてしまい、他の isolate がその時間内に書いた `evicted` / `cooldownUntil` を**消してしまう**——その判定はもう一度やり直しになる。 |
| `POOL_TOUCH_INTERVAL_MS` | いいえ | `21600000` | key の「最終使用時刻」を書き込む最大間隔。`0` で成功リクエストごとに書き込む。これは表示専用のフィールドでスケジューリングは一切読まず、リクエストごとに書くと無料枠の 1,000 回/日の書き込み枠を使い切り、クールダウンや除外すら書けなくなる。代償: 「最終使用」の精度はこの間隔まで粗くなる。同じ間隔はパネルの利用回数カウンター（リクエスト数／成功率）にも効く。**ストレージ上の `stats` を手作業で小さくすると（ゼロにするなど）、パネルは一旦その値を表示したあと、古い値に戻ることがある**: スナップショットは TTL ぶん後にゼロ化されたレコードを読むが、稼働中のインスタンスは自分が書き込んだ基準値を覚えていて、次に実際に書き込むときそれを書き戻すため。遅くともそのインスタンスが回収された時点で完全に一致する。P3c で repo を経由する正式なリセット経路を用意する。 |
| `PORT` | いいえ（Node/Docker のみ） | `8080` | Node ランタイムのリッスンポート。Worker では使用されません。 |
| `DATA_DIR` | いいえ（Node/Docker のみ） | `/app/data` | ファイルストレージが `store.json` を書き込むディレクトリ。Worker では使用されません。 |

`COOLDOWN_RATE_LIMIT_MS` と `COOLDOWN_PAYMENT_MS` は `.env.example` に既定では
記載されていませんが、どちらのデプロイ先でも環境変数として読み込まれ、必要に
応じて設定できます。上記の数値型の変数はすべて整数である必要があります。
`POOL_CACHE_TTL_MS` と `POOL_TOUCH_INTERVAL_MS` は下限が `0`（`0` は「無効」の意）で、
それ以外はすべて `0` より大きい必要があり、そうでない場合ゲートウェイは起動を拒否します。

`POOL_CACHE_TTL_MS` と `POOL_TOUCH_INTERVAL_MS` は **app の構築時に一度だけ**読まれます。
変更を反映するにはコンテナの再起動、または isolate の再生成を待つ必要があり、
他の設定項目のようにリクエストごとには反映されません。

### クォータの見積もり: Worker + 無料枠 KV で 1 日に何リクエストさばけるか

無料枠の KV は 1 日 100,000 回の読み取りと 1,000 回の書き込みです。ゲートウェイの読み書きは
どちらも**リクエスト数に比例しません**。したがって「1 リクエストあたり何回」ではなく
「1 日あたり何回」で見積もります。

- **デフォルト設定では KV はもうボトルネックではありません**。上限は Cloudflare Workers
  無料枠自体の **1 日 100,000 リクエスト**になります。ただしこの結論には**前提があり、
  無条件ではありません**: KV の読み取りクォータは代わりに「同時にアクティブな isolate 数」を
  制約します。それはトラフィックの地理的分布によって変わる量で、こちらから直接指定できません。
  アクティブな isolate 1 つあたり 1 日に

      (86400 ÷ POOL_CACHE_TTL_MS の秒数) × (1 + プール内の key 数)  +  2880

  回読み取ります。末尾の 2880 は設定ホルダーが 30 秒ごとに更新する分で、同じ枠を消費します。
  デフォルト値かつ key 20 本なら isolate あたり **33,120 回**。1 日 48〜96 回のインデックス
  照合を加えると、**アクティブな isolate が 3 つで約 99.5% を使い切ります**。つまり推奨設定の
  時点で既にぎりぎりです。isolate がそれ以上になる見込みなら `POOL_CACHE_TTL_MS` を大きく
  してください（key 20 本・isolate 5 つならおよそ `120000`）。
- **キャッシュを無効化**した場合（`POOL_CACHE_TTL_MS=0`、緊急脱出口）は読み取りがリクエスト数に
  比例して増え、下限はおよそ `100,000 ÷ (1 + key 数)` ⇒ key 20 本で **1 日約 4,700 リクエスト**。
- **書き込み側**: 定常状態では 1 日およそ `key 数 × 4` 回（`lastUsedAt` は 6 時間ごとに 1 回）。
  key 20 本なら 80 回で書き込み枠の 8%、残りはクールダウンと除外の記録用です。加えて各 key が
  初めて使われるときに一度だけ書き込みが発生します。
- **イベントボード（Task 6）の書き込み側**: 各 isolate は 1 日あたり最大 `EVENT_WRITES_PER_DAY`
  （**12**）回まで書き込みます。超えると `budgetExhausted` が正直に報告され、黙って捨てたり
  再試行したりはしません。**この閘門は単一の isolate 内でのみ有効**であり、全体として安全か
  どうかは「同時実行 isolate 数 × この値」が予算内に収まるかどうかに依存します——1 つの
  isolate は他の isolate がどれだけ予算を使ったか知る術がありません（CAS も isolate 間の
  調整もありません）。**8 並行 isolate**で見積もると（この節の他の箇所で使っている 3 より
  保守的です。トラフィックが少ない個人利用のゲートウェイでも、Cloudflare のエッジは世界中に
  あり、実際に何個の isolate が並行するかを完全には制御できないため）: `12 × 8 = 96` 回/日、
  書き込み枠の **9.6%**。上記の key プールの書き込み側（80 回/日、8%）と合わせると、合計
  約 176 回/日（**17.6%**）で、約 82% の余裕が残ります。**この試算はレビューで実際の問題が
  見つかったために存在します**：初期版は 1 時間単位で予算を数え、各 isolate が独立して
  1 時間あたり最大 12 回まで数えていたため、isolate が 4 つあるだけで書き込み枠を突破できて
  しまいました（`4 × 12 × 24 = 1,152`、1,000 を超過）。修正として予算のウィンドウを「1 時間
  ごと」から「1 日ごと」に変え、この試算をここに書き残しました。同じ修正で、コールドスタート
  した isolate の最初のフラッシュがスロットリングを回避してしまう抜け道も塞ぎました——
  以前は isolate がコールドスタートするたびに無条件の書き込みが 1 回発生していましたが、
  現在はコールドスタート後の最初のフラッシュも他のフラッシュと同じ最小間隔の閘門を通ります。
- **イベントボードの読み取り側（評価 C4/C4b 修正後の実データ。以前の草稿より保守的）**:
  ポーリングはもう索引に依存せず、候補キー数は**厳密に有界**です——`after` がどれだけ古くても、
  デプロイがどれだけ長く動いていても、1 回のリクエストが走査するのは最大でも 24 個の時間
  ウィンドウ × 2 個のスロット = **48** 回の get です（評価 C4 の修正前は、古い、あるいは
  悪意ある `after` によって 1 回のリクエストが約 100 万回の get に達することがありました。
  `tests/contract/quota-panel.test.ts` の回帰テストを参照）。`after` が直近の時間ウィンドウ
  内にあるときは「ウォームリード」で、通常は 2 回の get だけで済みます（ポーリングが時間
  ウィンドウの境界をまたぐ瞬間だけ 4 回）。
  **「有界」は「アクティブさと無関係」を意味しません**——評価 C4b が指摘した直感に反する
  結論は次のとおりです：
    - **新しいイベントが継続的に発生する「アクティブ」なデプロイ**: 新しいイベントが
      ポーリング間隔を常に最短の 15 秒に押し戻し、ほとんどのポーリングがウォームリードに
      なります。最悪ケース（毎回 4 回/ポーリング）で見積もると：`(86400 ÷ 15) × 4 = 23,040`
      回/日（読み取り枠の約 23%。実際にはウィンドウ境界をまたぐポーリングはごく一部なので、
      通常はこれよりずっと低くなります）。
    - **長期間新しいイベントが発生しない「静かな」デプロイ**（デプロイ直後でまだ診断
      イベントが一度も発生していない場合を含む）: `after` カーソルはいつまでも新しい値を
      得られず、凍結したカーソルが 24 時間の保持ウィンドウから外れた時点で、**それ以降の
      すべてのポーリングが満額の 48 回の get になります**。同時に新しいコンテンツがない
      ため、指数バックオフによってポーリング間隔は上限の 60 秒まで押し上げられます。
      定常状態は `(86400 ÷ 60) × 48 = 69,120` 回/日（読み取り枠の約 **69%**）——
      **診断イベントをほとんど発生させないほど健全なデプロイの方が、1 つのパネルタブを
      開くだけで「アクティブ」なデプロイよりも多くの読み取り枠を消費してしまう**、という
      直感に反するが事実の結論です。読み取り枠の余裕を計画する際は、この大きい方の数値を
      基準にしてください（小さい「アクティブ」側の数値ではなく）。特に上記の key プールの
      読み取り側と合算する場合（上記の「アクティブな isolate が 3 つで約 99.5% を使い切る」
      というシナリオを参照）は注意が必要です。
    - **ダウンロードエンドポイント**（`GET /admin/api/events/download`）はクリックのたびに
      固定で 48 回の get を消費します（`readEvents(null)` は常にコールドリードで、カーソルを
      使いません）——これは手動クリック時にのみ発生し、規模としては無視できますが、
      正確を期すためここに記録しておきます。
  どちらのシナリオも、上限は**デプロイの稼働日数が増えても増加し続けることはありません**
  ——この部分は C4 の修正後も引き続き成り立ちます。
- **`list` と `delete` はさらに別々の枠で、それぞれ 1 日 1,000 回**です。読み取り・書き込みの
  枠とは独立しています。定常状態の転送では `list` は一度も発生しません——`pool:index` という
  インデックスキーはまさにそのために存在します。消費するのは**3 か所**です: 1 日 48〜96 回の
  インデックス照合（独立してスケジュールされるジョブ）、**プールが空のときのフォールバック
  走査**（インデックスは正常なのに生きたレコードが 1 件も読めない場合、手動でインポートされた
  レコードがインデックスに入っていないかを確認するため `list` を 1 回だけ実行します）、そして
  **インデックス欠損時のフォールバック**（`pool:index` 自体が読めない、または壊れている場合に
  同じく `list` を 1 回実行してインデックスの再構築を試みます。多くは書き込み枠を使い切って
  インデックスがいつまでも作れなかったケースです）。後者 2 つは組み込みの **10 分**のバック
  オフを**共有します**（環境変数ではなく固定の定数）——どちらも同じ `list` 枠に向かうので、
  別々に窓を開いても意味がありません——したがってプールが空、またはインデックスが壊れている
  間でも isolate あたり 1 日最大 144 回で、インデックス照合の 48〜96 回を足してもまだ余裕が
  あります。
- **`list` の枠を使い切ると、劣化ではなく機能停止になります。** プールが空で `list` が失敗した
  場合、ゲートウェイは `500` を返し、本当の原因をログに書きます。**`503 pool_empty` には
  偽装しません**——このとき照合も同じ枠を使っていて同様に失敗しており、本ドキュメントが示す
  2 つの自己修復経路がどちらも失われているからです。UTC の日付が変わってクォータが
  リセットされるまで回復しません。

**上記の読み取り式には「isolate が TTL より長く生きる」という前提があります。** トラフィック
が少ない、あるいは十分に多くの Cloudflare エッジロケーションに分散している場合、isolate は
1 つの TTL が経過する前に回収されることが多く、その場合は各 isolate が生涯に少なくとも 1 回は
プールを読み込むため、読み取り回数は TTL ではなく**コールドスタート回数**で決まります。上限は
おおよそ `100000 ÷ (プール内の key 数 + 2)` 回のコールドスタート/日です（`+2` はインデックスと
設定それぞれ 1 回分）。**この領域では `POOL_CACHE_TTL_MS` を大きくしても読み取りは 1 回も
節約できません**——節約できるのは「同じ isolate 内での重複読み込み」だけです。

同じ理由で、プールが空のとき／インデックス欠損時の `list` のバックオフも**インスタンスごと**
です。冷えた isolate はそれぞれ自分のコストを払うので、合計は isolate の数に比例して増えます。

### 管理パネル関連の変数（P3、デフォルトで無効）

| 変数 | 必須 | 既定値 | 説明 |
|---|---|---|---|
| `ADMIN_TOKEN` | いいえ | なし（パネル無効） | 管理エンドポイントのトークン。**`GATEWAY_TOKEN` と異なる値**であること、かつ 24 文字以上であることが必須。さらに**先頭・末尾に空白があってはいけません**: HTTP はヘッダー値の前後の空白を除去しますが環境変数は保持するため、空白付きのトークンはどのクライアントからも送信できません。さらにトークンは**印字可能な ASCII（0x20–0x7E）のみ**で構成する必要があります。この制限には性質の異なる 3 つの理由があります: ① U+00FF を超える文字（漢字・emoji・ゼロ幅スペース）と改行・NUL は、ヘッダー値の設定時に `fetch` が**例外を投げます**——リクエストがそもそも送信されないため、200 を返すのに決して入れないパネルができあがり、サーバー側には `admin.login_failed` の 1 行すら残りません; ② **TAB を除く**その他の制御文字（`0x01–0x08`、`0x0B`、`0x0C`、`0x0E–0x1F`、`0x7F` の計 29 個）はブラウザーからは送信できますが、HTTP パーサーが `400` として拒否します; ③ **TAB（`0x09`）**および `é` / `£` / ノーブレークスペースのような `0x80–0xFF` のバイトは**実際には送信でき、動作もします**——これを拒否しているのは物理的な制約ではなく**当方の堅牢性のためのトレードオフ**です: 環境変数は UTF-8、ヘッダー値は Latin-1 として復号され、その範囲で両者が一致することは仕様上保証されていません（検証したのは Node のみで、Cloudflare Workers 側は未検証です）。また RFC 9110 はこの範囲を非推奨としています。ASCII のみのトークンをご利用ください。**途中のスペースは許可されます**——`correct horse battery staple` のようなパスフレーズは問題なく送信・到達しますし、24 文字という下限のもとではランダム文字列より扱いを誤りにくいことも多いためです。先頭・末尾の空白は上のルールが担当します。未設定または規則違反の場合、`/admin` ツリー全体が登録されず、理由は `admin.token_rejected` に記録されます。 |
| `TRUST_PROXY` | いいえ | 未設定（転送ヘッダーを**一切**信頼しない） | ゲートウェイが実際にプロキシの背後にある場合**のみ** `1` にしてください。**Cloudflare Worker 形態もこれに該当するので設定すべきです。** 設定すると、ログイン失敗イベントに記録されるクライアント IP は `CF-Connecting-IP` から取られ、無い場合にのみ `X-Forwarded-For` の先頭要素へフォールバックします。 |

**未設定なら管理パネルが使えないだけで、ゲートウェイの転送は通常どおり動きます。** このとき
`/admin/...` へのリクエストは **`401` ではなく `404`** になります。ツリーそのものが登録されない
ため、「ここに管理画面がある」という事実自体が漏れません。これはレジストラーがデフォルトで
無効なのと同じ方針です。`ADMIN_TOKEN` の欠落や設定ミスでゲートウェイの転送を止めてはいけません。

**24 文字という下限の理由。** Worker 形態には**分散ログインレート制限がありません**。実装する
には KV をカウント窓として使う必要があり、それは攻撃者に書き込みクォータを消費させるレバーを
渡すことになります（攻撃面が「パスワードを当てる」から「キープールの状態書き込みを潰す」まで
広がる）。したがってトークンのエントロピーが唯一の防御であり、この下限は推奨値ではありません。
下回る場合パネルは有効化されず、コンテナログに `admin.token_rejected` が出力されます。

**`GATEWAY_TOKEN` と異なる必要がある理由。** `GATEWAY_TOKEN` は**すべての下流ユーザー**に配る
中継トークンです。これをパネルのトークンとして使い回すと、中継トークンを持つ誰もがキープール
全体を読み、レジストラーを停止し、登録バックエンドを自分のサーバーに向け替えられます——以降に
作られる全アカウントのメールアドレス・パスワード・認証コードが奪われます。

このルールは**管理リクエストごとに再検査されるだけで、起動時には遮断しません**。両者が同一の
場合——例えば `wrangler kv key put` や `store.json` の直接編集で `gatewayToken` を手作業で
書き換えた場合——管理エンドポイントは **`503` を返し**、error レベルで `admin.token_conflict`
が記録されます（起動時点で既に衝突しているなら、起動ログにも同じ行が出るのですぐ原因が
分かります）。**ゲートウェイの転送は影響を受けません。** どちらかのトークンを戻せば管理
エンドポイントは自動的に回復します。ストレージ上の `gatewayToken` を戻した場合は設定キャッシュが
次に更新された時点で有効になり、**再起動は不要です**。`ADMIN_TOKEN` の方を変更する場合は環境
変数なので、再デプロイ（Worker）またはコンテナの作り直し（Docker）が必要です。

**なぜこのルールだけ起動時に遮断しないのか。** `gatewayToken` は稼働中に変わり得るのに、起動時の
判定には二度目の評価の機会がありません。そこで `/admin` ツリー全体を登録しない扱いにすると、
衝突中にコールドスタートした isolate（および衝突中に起動した Docker コンテナ）は**恒久的に
`404`** になり、設定を戻しても直らず再起動しか手がなくなります。一方で衝突前に構築されたものは
`503` にとどまり、値を戻せばすぐ回復します。同じ設定・同じ瞬間に二つの答えが存在することになり、
上の「再起動は不要」という一文が半分嘘になります。`ADMIN_TOKEN` 自身に関する 3 つのルール
（前後の空白、送信できない文字、最小長）は入力が環境変数だけで稼働中に変わらないため、引き続き起動時に遮断し、
失敗の形は `404` のままです。

`ADMIN_TOKEN` は**環境変数からのみ読み取られ、ストレージからは読みません**。パネルが自分の鍵を
ローテーションすることはできません。ローテーション方法は、Worker なら
`npx wrangler secret put ADMIN_TOKEN` の後に再デプロイ、Docker なら `.env` を編集してコンテナを
作り直します。

**管理トークンの漏洩は `ADMIN_TOKEN` そのものの漏洩です。** パネルはこれをブラウザーの
localStorage にそのまま保存します。派生トークンはなく、製品内に失効経路もありません。失効させる
唯一の方法は、シークレットを変更して再デプロイ（Worker）またはコンテナを作り直す（Docker）ことです。
パネルは 12 時間後にトークンの再入力を求めますが、それはその localStorage の値が使える期間を
短くするだけで、**失効ではありません**。パネルは TLS の背後に置き、信頼できる端末でのみ開いてください。

**この上限にできないことも明記します。** パネルの CSP は `connect-src 'self'` でトークンを外部
ドメインへ `fetch` することを、`form-action 'none'` でフォーム経由の持ち出しを防ぎます。しかし
`location.href = "https://…?k=" + token` のような**ナビゲーションによる持ち出し**は防げません
— CSP にはもうそれを止めるディレクティブがありません（`navigate-to` は仕様から削除されました）。
本当の解決策はサーバーが発行する**失効可能な派生トークン**ですが、それはサーバー側でセッションを
保存することを要求し、「`ADMIN_TOKEN` は環境変数からのみ読む」という設計上の制約と衝突するため、
後続のリリースに回します。

**`TRUST_PROXY` はセキュリティスイッチなので既定で無効です。** これが決めるクライアント IP は
`admin.login_failed` イベントに記録されるため、クライアントが送ってくるヘッダーを無条件に信頼すると、
誰でも総当たりの痕跡を任意の IP になすりつけられます。

**無効時はどの転送ヘッダーも信頼せず、このフィールドは一律 `null` になります——`CF-Connecting-IP`
も例外ではありません。** このヘッダーは「プラットフォームが注入するので偽装できない」と説明されがち
ですが、その性質は**リクエストが実際に Cloudflare を通る場合にのみ**成り立ちます。Node/Docker を直接
公開している構成では上書きするものが何もないため、クライアントが自分で
`CF-Connecting-IP: 1.2.3.4` を送れば信じられてしまいます——そして直接公開は Docker 配備の既定の形です。

**有効時は `CF-Connecting-IP` が優先され、`X-Forwarded-For` はフォールバックにすぎません。**
2 つのヘッダーは偽装のしやすさが根本的に異なります。

- `CF-Connecting-IP` は Cloudflare のエッジが書き込み、クライアントが送ってきた同名ヘッダーを
  **上書きします**——リクエストが実際に Cloudflare を通る限り偽装できません。
- `X-Forwarded-For` はどのミドルボックスでも追記できる連鎖で、クライアントが偽物を送ることもできる
  ため、どこまで信じられるかはプロキシ構成次第です。

**Worker 形態では `TRUST_PROXY=1` を設定してください。** そこでは Cloudflare が定義上前段にいるため
`CF-Connecting-IP` が権威ある値です。この形態で `X-Forwarded-For` を優先するのは誤りで、その連鎖には
クライアントが詰め込んだものが入っている可能性があります。スイッチを設定しない場合、このフィールドは
単に `null` として記録されます。

**汎用リバースプロキシ（nginx / Caddy / Traefik）の背後で `TRUST_PROXY=1` を有効にする場合は、
プロキシ側で `CF-Connecting-IP` を除去してください。** その構成では誰もこのヘッダーを上書きしませんが、
ゲートウェイは「Cloudflare が前段にいる」前提でこれを優先するため、攻撃者が自分で付けたヘッダーが
プロキシの書いた `X-Forwarded-For` を**上回って**しまいます。nginx なら 1 行です:

```nginx
proxy_set_header CF-Connecting-IP "";
```

Caddy は `header_up CF-Connecting-IP ""`、Traefik はミドルウェアの `customRequestHeaders` を使います。

**どちらのヘッダーも先に形式チェックを通ります**: ドット区切りの IPv4 と IPv6 の形（16 進数、
コロン、`::ffff:` マッピング内のドット）だけがイベントに入り、それ以外は一律 `null` として
記録されます。これは認証の防御線ではなく（この値の消費箇所はリポジトリ全体でログイン失敗
イベント 1 か所だけです）、未認証の呼び出し元が監査フィールドに任意のテキストを書き込めない
ようにするためのものです。管理パネルのイベント欄はこのフィールドで絞り込みと表示を行います。

利用できる値が何も無い場合、このフィールドは正直に `null` として記録されます——**`"unknown"` という
偽の値は決して作りません**。実在の送信元と誤解されるためです。

上限などの詳細は [REGISTRAR.md](REGISTRAR.md) を参照してください。

| `REGISTRAR_PRIMARY` | 有効化時は必須 | なし | 主チャネル、`yyds` または `moemail`。両者は対等でデフォルト値なし。 |

| `TEND_INTERVAL_MS` | いいえ（Node/Docker のみ） | `1800000` | Node 側の補充間隔。Worker 側は `wrangler.toml` の Cron が代わりに決める。 |

### 2 つのタイムアウト予算の使い分け

判断基準は「上流の最初のバイトがいつ届き得るか」であり、エンドポイントの名前では
ありません:

| 予算 | 対象エンドポイント | 変数 |
|---|---|---|
| 最初のバイト | **ストリーミング**対話（`stream: true`）、動画ポーリング `GET /v1/videos/{id}` | `UPSTREAM_TIMEOUT_MS` |
| 同期 | 画像生成、動画ジョブ作成、**すべての非ストリーミング対話**（4 プロトコルとも） | `UPSTREAM_SYNC_TIMEOUT_MS` |

非ストリーミングのリクエストは、上流が回答全体を生成し終えてからでないと応答ヘッダを
返しません。画像生成とまったく同じ遅延の性質であり、8 秒の最初のバイト予算で切ると
正常なリクエストが大量に失敗し、key プールまで巻き添えになります。

`UPSTREAM_SYNC_TIMEOUT_MS` は**1 リクエストの総予算**、つまりクライアントの最悪待ち時間
です——「プールの大きさ × 予算」ではありません。ゲートウェイはこの予算のうち単一の key に
最大でも半分しか使わず、残りは別の key での再試行に取っておきます。こうすることで、
プール内にハングした key（接続はできるが決して応答しない）があってもリクエストを丸ごと
食い潰されません。したがって**単一呼び出しの最悪所要時間の 2 倍以上**に設定してください。

同期予算でのタイムアウトは、その場では key を罰しません。同一リクエスト内で切り替えた
別の key が実際に成功した場合にのみ、先にタイムアウトした key に計上します
（`MAX_STRIKES` に達するとクールダウン）。そのリクエストで全部の key がタイムアウトした
場合は 1 つも罰しません——予算が小さすぎるか上流全体が遅い可能性の方が高いためです。

「排除」と「クールダウン」は別物です。上記の設定にかかわらず、上流の `401`/`403`
はその key を**永久に**排除します——これらは「この key はもう有効ではない」状態
であり、再試行に意味がないためです。一時的な失敗が排除につながることはありません。
`MAX_STRIKES` に達しても `COOLDOWN_STRIKE_MS` のクールダウンに入るだけで自動的に
復帰するので、上流の一時的な不調がプールを恒久的に破壊することはありません。

どの key もリクエストを処理できない場合、ゲートウェイは `503` を返し、`error.reason`
に判別可能な理由を示します：`pool_empty`（key が未登録）、`all_cooling`（全 key が
クールダウン中。自動的に回復し、`Retry-After` ヘッダーが復帰時刻を示す）、
`all_evicted`（全 key が認証情報の失効により永久排除。**自動回復しない**ため key の
入れ替えが必要）、`upstream_error`（key 自体は有効だが、上流が毎回失敗した）。

## Cloudflare Worker

### 方法 A —— Deploy to Cloudflare ボタン

ルートの [README](../../README.md) にあるボタンをクリックし、Cloudflare を
認可すると、リポジトリを fork/clone してデプロイまで自動的に行われます。
その後も、下記の **secret** と **KV ネームスペース** の手順は自分で完了させる
必要があります——ボタンだけではこの 2 つは設定されません。

### 方法 B —— 手動デプロイ

1. リポジトリをクローンして依存関係をインストールします。

   ```bash
   git clone https://github.com/xwteam/agnes2api.git
   cd agnes2api
   pnpm install
   ```

2. key プール用の KV ネームスペースを作成し、`wrangler.toml` に書き戻します。

   ```bash
   node scripts/setup-worker.mjs
   ```

   リポジトリの `wrangler.toml` に入っている `id` は常にプレースホルダーです
   （公開リポジトリには実際のデプロイ情報を一切含めません）ので、この手順は
   必須です。このスクリプトは手動で `npx wrangler kv namespace create POOL` を
   実行し、返ってきた `id` を `[[kv_namespaces]]` ブロックの
   `REPLACE_WITH_YOUR_KV_NAMESPACE_ID` に貼り付けるのと同じことをします。
   **実行後、この `wrangler.toml` への変更はコミットしないでください**——
   `check-wrangler-placeholder.mjs` の CI ゲートが誤ってコミットされた実際の
   id を検出して止めます。

3. ゲートウェイトークンを Worker の secret として設定します（絶対に
   `wrangler.toml` にコミットしないでください）。

   ```bash
   npx wrangler secret put GATEWAY_TOKEN
   ```

4. デプロイします。

   ```bash
   npx wrangler deploy
   ```

### タグ push による自動デプロイ

`.github/workflows/deploy-worker.yml` は `v*` タグが push されると自動的に
Worker をデプロイします。ただし、リポジトリの
**Settings → Secrets and variables → Actions** に `CLOUDFLARE_API_TOKEN`
が設定されている必要があります。設定されていない場合、ワークフローは警告を
出力してデプロイ手順をスキップし、実行自体は失敗しません。

### ローカル開発

```bash
npx wrangler dev
```

`GATEWAY_TOKEN` は `wrangler.toml` と同じディレクトリにあるローカルの
`.dev.vars` ファイル（すでに `.gitignore` 済み）に書いてください——
`wrangler.toml` に直接秘密情報を書かないでください。

## Docker

1. リポジトリをクローンし、環境変数ファイルを準備します。

   ```bash
   git clone https://github.com/xwteam/agnes2api.git
   cd agnes2api
   cp .env.example .env
   ```

2. `.env` を編集し、少なくとも `GATEWAY_TOKEN` を設定します。それ以外の
   変数は上記の [環境変数](#環境変数) 表を参照してください。

3. コンテナを起動します。

   ```bash
   docker compose up -d
   ```

   `docker-compose.yml` は既定でポート `8080` を公開し（`.env` の `PORT` で
   上書き可能）、`./data` をコンテナ内の `/app/data` にマウントします——
   `store.json`（key プールと永続化された設定）はここに保存されます。
   再起動やアップグレードをまたいでこのディレクトリを必ず保持してください。
   インポート済みの key プールの唯一のコピーです。

4. コンテナが健全に起動しているか確認します。

   ```bash
   curl http://localhost:8080/health
   ```

   イメージには `HEALTHCHECK` が組み込まれており、Docker はこれをもとに
   コンテナの健全性を報告します。データディレクトリが書き込めない場合、`/health` は
   `status` が `degraded` の `503` を返し、コンテナは unhealthy と表示されます。
   具体的な原因はコンテナログを参照してください。

### コンテナは `./data` の所有者を書き換えます（事前にご確認ください）

コンテナは **root で entrypoint に入り**、次の 2 つを行ってから権限を落とします:

- `DATA_DIR`（既定 `/app/data`）の所有者がコンテナ内の実行ユーザー `app`
  （**uid 100 / gid 101**）と異なる場合のみ、そのディレクトリを再帰的に `chown` します。
  所有者が既に一致していれば何も書き換えません。
- その後 `su-exec` で権限を落とすため、**メインプロセス（PID 1）は root ではなく app**
  として動きます。

実行時に行う必要がある理由は、バインドマウントではホスト側ディレクトリの所有者が
イメージのビルド時 `chown` を上書きしてしまい、コンテナ内の app が `store.json` に
書き込めなくなるからです。しかもこの失敗は静か（すべての API が `pool_empty` を返す）です。

**副作用**: バインドマウントで書き換わるのは**ホスト**上のファイルです。
`docker compose up -d` の後、あなたの `./data` とその中のファイルの所有者は自分の uid から
`100:101` に変わり、以後ホスト側で読み書きやバックアップをするには `sudo` が必要に
なります。それを避けたい場合は `--user`（または compose の `user:`）で非 root 実行を
指定してください。その場合 entrypoint は chown を一切行わず、データディレクトリの所有者と
書き込み可否はあなたが用意します。

同じ理由でイメージには **`USER app` を入れていません**。既定ユーザーは root です
（`docker inspect --format '{{.Config.User}}' <image>` は空を出力）。これは Kubernetes に
影響します: `runAsNonRoot: true` を設定しつつ `runAsUser` を明示しない場合、kubelet は
コンテナの起動を拒否します。そうしたデプロイでは `runAsUser: 100`、`runAsGroup: 101`
（または任意の uid）を明示し、ボリュームの所有者は自分で用意してください——非 root 起動時、
entrypoint は「chown せずそのまま実行する」分岐を通ります。

安全境界: `DATA_DIR` が `/` やトップレベルのシステムディレクトリ（`/etc`、`/usr` など）に
設定された場合、entrypoint はその上での再帰的 chown を拒否します（警告を出すだけで起動は
継続）。コンテナのファイルシステム全体が app から書き込み可能になるのを防ぐためです。

## 上流 Agnes key のインポート

現バージョンのゲートウェイには key をプールへ追加するための HTTP
エンドポイントはありません。ストレージバックエンドへ直接書き込む必要が
あります。各エントリは `key:<id>` というキーを持つ JSON オブジェクトで、
`<id>` はプール内で一意な任意の文字列で構いません（ゲートウェイ自身が
レコードを作成する際は key のハッシュ値から導出しますが、読み込み時には
その値は検証されないため、手動インポートでは任意の一意な識別子で問題
ありません）。

```json
{
  "id": "1a2b3c4d5e6f7a8b",
  "key": "実際の-agnes-api-key",
  "addedAt": 1735689600000,
  "lastUsedAt": null,
  "cooldownUntil": 0,
  "strikes": 0,
  "evicted": false,
  "evictedReason": null
}
```

### Docker

実行中のプロセスとの書き込み競合を避けるため、まずコンテナを停止し、
ホスト上で `./data/store.json` を編集して、キー
`"key:1a2b3c4d5e6f7a8b"` の下に上記のようなレコードを追加してから、
コンテナを再度起動します。

```bash
docker compose stop
# ./data/store.json を編集
docker compose start
```

`./data/store.json` がまだ存在しない場合は、`key:<id>` という形式の
キーを持つ単一の JSON オブジェクトとして新規作成してください。

### Cloudflare Worker

wrangler を使ってレコードを `POOL` KV ネームスペースへ直接書き込みます。

```bash
npx wrangler kv key put --binding=POOL "key:1a2b3c4d5e6f7a8b" \
  '{"id":"1a2b3c4d5e6f7a8b","key":"実際の-agnes-api-key","addedAt":1735689600000,"lastUsedAt":null,"cooldownUntil":0,"strikes":0,"evicted":false,"evictedReason":null}' \
  --remote
```

`--remote` を省略すると、本番ではなく `wrangler dev` が使用するローカルの
ネームスペースに書き込まれます。

ゲートウェイはプール内の id 一覧を `pool:index` というキーに保持しており、転送のたびに KV の
`list` を消費せずに済みます（無料枠の `list` は 1 日 1,000 回しかなく、読み取り・書き込みとは
別枠です）。**レコードを手作業で書いてもこの索引は変わりません**。したがって新しい key が
いつ使われ始めるかは、そのときのプールの状態によります:

- **プールが空のとき**: 索引が「空」と言い、実際にレコードが 1 件も読めない場合、ゲートウェイは
  `list` 走査に 1 回だけフォールバックし、手動インポートされたレコードを検出して索引に
  追加します。この走査には組み込みの 10 分バックオフがあるため（上の「クォータの見積もり」参照）、
  可視化までの上界は **10 分以内 + `POOL_CACHE_TTL_MS` 1 回分**です。
- **プールが空でないとき**: 転送経路は索引が知っているレコードしか取得しないため、索引が
  知らないレコードは**完全に見えません**（エラーも一切出ません）。次の cron 照合が索引を
  修復するまで（既定 30 分、しかも**トリガー時刻に公式な保証はありません**。下記参照）、
  さらにその後最大 `POOL_CACHE_TTL_MS` 1 回分待つ必要があります。

**手動インポートを即座に反映させたい場合は、レコードを書くのと同時に id を `pool:index` へ
追加してください:**

```bash
npx wrangler kv key get --binding=POOL "pool:index" --remote
# ids 配列に新しい id を追加し、値全体を書き戻す（v は常に 1）
npx wrangler kv key put --binding=POOL "pool:index" \
  '{"v":1,"ids":["既存のid","1a2b3c4d5e6f7a8b"]}' --remote
```

索引を書き込めば、各 isolate は最大でも `POOL_CACHE_TTL_MS` 1 回分でこの key を使い始めます。

レジストラを使わない場合でも `wrangler.toml` の `[triggers]` を削除しないでください。
この cron は `pool:index` と実際の `key:` レコードを突き合わせて修復する唯一の経路であり、
`REGISTRAR_ENABLED` の値とは無関係に実行されます。

**この cron の発火タイミングは公式に保証されていません。** Cloudflare は Cron
Trigger が `crons` の式どおりに発火する信頼性について文書化していません（スキップ
されない保証も、遅延の上限も明記されていません）。これは配額計算にとっては安全
な方向です——対帳の発火回数が減れば KV の読み書き消費も予測より減るだけで、
増えることはありません。ただし**孤立レコードやゴースト索引項目が索引に回収され
るまでの時間には保証がありません**。最悪の場合、想定していた「最長 30 分」より
長くかかることがあります。その待機中は対象の key が一時的に使えないだけで、
データが失われたり壊れたりすることはありません。

## key を失効させる

**レコードを削除し、その id を `pool:index` からも外す——両方を行ってください。** レコードだけ
削除してもエラーにはなりません（読めないレコードは単に除外されます）が、id が索引に残るため、
次の照合で刈り取られるまで更新のたびに読み取りを 1 回無駄にします。

```bash
npx wrangler kv key delete --binding=POOL "key:1a2b3c4d5e6f7a8b" --remote
# ids 配列からその id を取り除き、値全体を書き戻す
npx wrangler kv key put --binding=POOL "pool:index" '{"v":1,"ids":["残りのid"]}' --remote
```

Docker の場合は `./data/store.json` から `"key:<id>"` のエントリを削除し、`"pool:index"` の
`ids` 配列を直します。先に `docker compose stop` しておくことを推奨します。

古いスナップショットを読み込み済みの isolate / プロセスは、最大 `POOL_CACHE_TTL_MS` 1 回分で
その key を選ばなくなります。Worker ではさらに KV の伝播ウィンドウ（およそ 60 秒）が加わります。
削除がすべての colo に見えるまでにそれだけかかるためです。

**そのウィンドウの間も書き戻されることはありません**: ゲートウェイは状態変更を永続化する前に
レコードがまだ存在するかを確認し、読めなければその書き込みを破棄して自分のスナップショットを
直ちに更新します。唯一の例外がその伝播ウィンドウで、確認のための読み取りが KV のエッジ
キャッシュから返された場合、その colo はレコードがまだあると判断します。Docker（ファイル
ストレージ）にはこのキャッシュがないため、そちらでは厳密です。
