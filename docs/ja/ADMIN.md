# 管理パネル

この文書が扱うのは画面に見えている側だけ——各ボードがどんな問いに答えるのか、表示されている数値がどういう口径なのか、どの操作が書き込みになるのか、です。

> [!NOTE]
> 管理パネルは**任意**です。`ADMIN_TOKEN` を設定していなければ `/admin` のツリーはそもそも
> 登録されず、ゲートウェイは普段どおり転送を続けます。
> この文書が扱う範囲: パネルへの入り方、各ボードを順に一巡し、最後にパネルが
> しないことと障害対応です。

> [!IMPORTANT]
> **変数そのもの（既定値・取りうる範囲・代償）の完全版は
> [DEPLOY.md](DEPLOY.md) の環境変数表にあります。**
> ここでは案内するだけで、二つ目の写しは置きません。
> （README にはよく使う 12 行の早見表がありますが、あれは表紙用の抜粋であり
> 二つ目の真の出所ではありません。）

## パネルへの入り方

### パネルのアドレス

パネルはゲートウェイ自身のドメインの下にあります。別のポートも別のサービスも要りません。

```text
https://<your-gateway>/admin
```

`<your-gateway>` はご自分のゲートウェイのアドレスに置き換えてください。末尾スラッシュ
付きの `/admin/` は `/admin` へ自動的に転送されるので、手入力しがちな二通りの書き方は
どちらでも入れます。

### 前提条件

- **前提条件はひとつだけ**: デプロイ時に `ADMIN_TOKEN` を設定することです。24 文字以上で、
  印字可能な ASCII だけで構成され、`GATEWAY_TOKEN` とは異なる値でなければなりません。
  この三条それぞれの理由と境界、そして不適合のときにどのイベントが記録されるかは、
  [DEPLOY.md](DEPLOY.md) の「管理パネル関連の変数」の節にあります。
- **未設定あるいは不適合のとき、`/admin` が返すのは `404` であって `401` ではありません**。
  ツリーが登録されていないだけなので、「ここに管理画面がある」と外に知らせることも
  ありません。パネルが開けなくても**ゲートウェイの転送には影響しません**。

### トークンの保管と失効

- **トークンはブラウザの localStorage にそのまま保存され**、パネルは 12 時間後に再入力を
  求めます。
- この上限が縮めるのは localStorage に置かれた値の利用可能な窓だけで、**失効させるもの
  ではありません**。取り消す道はひとつ、`ADMIN_TOKEN` を差し替えて再デプロイ / コンテナを
  作り直すことです。パネルは TLS の内側に置き、信頼できる端末でのみ開いてください。
  詳しい論証は [DEPLOY.md](DEPLOY.md) の「管理トークンの漏洩」の段にあります。

### 上部バー

上部バーはパネル全体を横切ります。左から順に、ブランド、サービス状態バッジ、リポジトリ
リンク、言語、テーマ、ログアウト。サイドバーには 8 項目のナビゲーションだけが残ります。

- **上部バーに「再起動」ボタンはありません**: Worker 形態には再起動できるプロセスが
  そもそも無く（概要ボードのそのセルは「常駐プロセスなし」と表示します）、Node / Docker
  形態にも自己再起動の口はありません。
- **テーマ切り替えはログインゲートにもあります**: ダークテーマはトークンを入力している
  時点で既に効いているので、その段階で切り替えられる必要があります。
- **左上のマークは README 冒頭のあの画像そのもの**で、ブラウザのタブに出るファビコンも
  同じものです。ログインゲートに置いてあるのもこの一枚です。どちらもその画像を縮小して
  パネルにインライン化したもので、ピクセル単位で突き合わせる門番が付いています
  ——パネルとプロジェクトの顔が別々になることはありません。

#### 状態バッジ

- **状態バッジは 3 段階**: 稼働中 / 機能低下 / 状態不明。データ源はゲートウェイの
  `/health` ——認証を必要とせず、ストレージにも触れないエンドポイントです。データ
  ディレクトリが書き込み可能なら `ok`、書き込めないなら `degraded` を返し、その応答の
  ステータスコードは `503` です。イメージ内蔵のヘルスチェックが見ているのも同じ一本です。
- **判定できないときは「稼働中」ではなく「状態不明」と言います**: ネットワーク失敗、
  JSON ではない応答、見たことのない `status` の値、この 3 つはすべて third の段階に入ります。
  ずっと点いたままの緑ランプは、ランプが無いのと同じ情報量です。
- **示しているのは「直近の確認」であって「今この瞬間」ではありません**: パネルに入った
  ときに一度確認し、そのあとはバッジをクリックすると再度確認します。

## 8 つのボード早見表

| ボード | 答える問い | 読み取り専用か書き込みか | 必要なスイッチ |
|------|----------|------------------------|--------------|
| 概要 | このデプロイは今どんな形態か、使える key はあと何本か | 読み取り専用 | – |
| Key プール | 各 key は今どの状態か、なぜ使えないのか | 書き込み | – |
| レジストラ | 自動補充は動いているか、直近の数回で何を発行したか | 書き込み | `REGISTRAR_ENABLED` |
| イベント | 最近どんな運用レベルの出来事があったか | 読み取り専用 | – |
| 使用量 | リクエスト量・成功率・レイテンシは時間とともにどう動いたか | 読み取り専用 | `USAGE_STATS_ENABLED`（第二層のみ） |
| モデル | ゲートウェイが対外的に認めるモデルと、そのモダリティ・プロトコル | 読み取り専用 | – |
| プレイグラウンド | 本物のリクエストで、あるプロトコルが通るか一度確かめる | 上流を叩く | – |
| 設定 | 実行時設定の現在値と、環境変数に固定されている項目 | 書き込み | – |

「書き込み」は**そのページで押した操作がストレージに書き込むこと**を指し、「上流を叩く」は
上流へ実際にリクエストを一度送ることを指します。

> [!IMPORTANT]
> **「上流を叩く」は「ストレージに書かない」
> という意味ではありません**: プレイグラウンドが投げるのは本ゲートウェイ自身の転送口への本物の
> リクエストで、通常の転送とまったく同じ経路を通ります——今回使われた key も同じように記帳され、
> 永続化の条件は転送経路とまったく同じ（同様にまとめ書き）で、第二層の使用量が有効ならさらに
> 一件記録します。

## 概要

概要が答えるのはひとつの問いです。**このデプロイは今どんな形態で、プールに使える key が
あと何本残っているか。**

### プールのバケットとランタイムの自己申告

- **プールの 5 つのバケット**: 総数 / 使用可 / クールダウン中 / 排除済み / 無効化済み。
  5 つとも常に表示します。本物の `0` はそれ自体が真実だからです。**読み取れなかった枠は
  `—` を表示し、`0` を捏造することはありません**——この二つは画面上で同じ見た目に
  なってはいけません。
- **ランタイムとストレージの自己申告**: ランタイム名、バージョン、サーバ時刻、
  ストレージバックエンド、書き込み可否、そして Node 形態にしかないメモリ / 稼働時間 /
  PID。いずれも API が返した内容だけを使い、パネルが自分のランタイムを嗅ぎ分けることは
  しません。Worker 形態には常駐プロセスがないので、その 3 枠は「常駐プロセスなし」と
  表示されます。`0` でも空白でもありません。

### 2 本の鮮度と第一層の使用量

- **2 本の鮮度**: プールのスナップショットと設定は、それぞれ別に「何秒前に読んだか」を
  持ちます。同じ時間軸ではないので分けて表示します。プール側の遅れは
  `POOL_CACHE_TTL_MS` に加えてエッジキャッシュの一層で決まり、その上界と代償は
  [DEPLOY.md](DEPLOY.md) の該当セルに書いてあります。
- **第一層の累計使用量**: リクエスト数 / 成功 / 失敗 / クライアントエラー / 成功率。
  プール内の全 key を集計した値なので `≈` が付きます。key ごとのカウンターは並行時に
  少なく数えられ（KV に CAS がないため）、永続化は最大で `POOL_TOUCH_INTERVAL_MS` ぶん
  遅れます。

### 設定の要約

- **設定の要約**: レジストラのスイッチ、主チャネルとフォールバックチャネル、`TARGET_KEYS` の現在の実効値。
  環境変数に固定されているフィールドにはロック印が付きます——それらを設定ページで
  変更しても反映されません。環境変数のほうが優先されるからです。

## Key プール

### バケットのバッジは優先順位の射影

- **バケットのバッジは優先順位を一度だけ射影したもの**で、独立した 4 つの旗ではありません。
  ひとつの key が複数の条件を同時に満たすときは、無効化済み > 排除済み > クールダウン中 >
  使用可 の順で最初のひとつを取ります。ですから「無効化されていて、なおクールダウン中」の
  key のバッジは「無効化済み」になります。クールダウンが消えたわけではなく、バッジからは
  見えないだけです。

### ボード上の操作

#### 単体の操作

- **単体の操作は 8 つ**: 無効化、有効化、クールダウン解除、失敗カウントの消去、排除の取り消し、
  メモの編集、疎通確認、削除。

#### 一括操作

- **一括操作は 3 つ**: 一括無効化、一括クールダウン解除、一括削除。

### インポートと状態のリセット

- **一度のインポートは最大 200 件の key**。これを超えたら即座に `400` で、**黙って切り詰める
  ことはありません**——切り詰めは「入れたつもりで実は入っていない」を生みます。
- **「既存 key の状態をリセットする」チェックボックスが実際にリセットするもの**:
  **システムが判定した失敗状態**——失敗カウント、クールダウン期限、クールダウン理由、
  排除フラグ、排除理由です。次の 4 つは**意図的に触りません**: 無効化フラグ（自分で倒した
  スイッチであり、一度の貼り付けで黙って戻してよいものではありません）、追加日時（由来は
  失敗状態ではありません）、使用量の統計（履歴は失敗状態ではありません）、メモ（自分のために
  書いた言葉です）。

### 削除の前提条件と単体の疎通確認

- **key を削除するには、無効化済みか排除済みであることが必要**: どちらか一方を満たしていればよく、
  システムに排除された key をわざわざ手で無効化し直す必要はありません。まだ現役の key を
  そのまま削除しようとすると拒否されます。一括経路ではこの制約はバッチ全体の失敗にはならず、
  項目ごとに理由が返ります。
- **単体の疎通確認**は、その key で実際に上流へ一度リクエストを送ります。一覧の「最終使用」と
  使用量カウンターはまとめてから永続化されるため、分解能は `POOL_TOUCH_INTERVAL_MS` の
  間隔より細かくはなりません。

### key を 1 本変更するリクエストと応答

ボード上の単体操作はどれも同じ `PATCH /admin/api/keys/{id}` を通り、1 回のリクエストで
複数をまとめて指定できます——ここでは有効化とクールダウン解除の 2 つです。ヘッダーに載せる
のは**管理トークン**であって、ゲートウェイトークンではありません。

```bash
curl -X PATCH http://localhost:8080/admin/api/keys/9f2c \
  -H "x-admin-key: your-admin-token" \
  -H "Content-Type: application/json" \
  -d '{ "disabled": false, "clearCooldown": true }'
```

応答が伝えるのは書き込みが通ったかどうかだけで、レコード全体を読み戻すことはしません。
変更後の状態は一覧に戻って確認してください。

```json
{ "ok": true }
```

このリクエストボディの各フィールドの型と意味は [API.md](API.md) にあり、この文書は
二つ目の写しを持ちません。

## レジストラ

パネルのレジストラボードは**索引であって説明書ではありません**。補充の規則、チャネルの
選び方、自分で用意すべき資格情報、障害時の追い方はすべて [REGISTRAR.md](REGISTRAR.md) に
あり、この文書は二つ目の写しを持ちません。ボードから見えるのは次のとおりです。

### 2 本のメールチャネル

- **2 本のメールチャネルは対等**で既定値がありません。主チャネルは明示指定が必須、
  フォールバックチャネルは未設定でも構いません。ボードにはそれぞれの役割（主 / フォールバック）と資格情報の設定有無が
  表示されます。

### 補充の履歴とチャネルテスト

- **補充の履歴**: 各回がいつ走ったか、どのチャネルを通ったか、タイマー起動か人の操作か、
  どれだけ時間がかかったか。
- **チャネルテストはそのチャネルの利用可能ドメイン一覧を読むだけ**です。メールボックスの
  作成もアカウント登録も行わず、枠も消費しません。

### 「今すぐ補充」の 4 本のガードレール

- **「今すぐ補充」には 4 本のガードレール**があり、どれかひとつでも満たさなければ起動しません。
  同一レプリカ内の実行中ガード、レプリカ間のストレージ短期ロック、手動補充どうしの最小間隔、
  そして手動実行の一日あたりの上限です。それぞれのエラーコード・算式・残存リスクは
  [REGISTRAR.md](REGISTRAR.md) の「今すぐ補充」の節にあります。
- レジストラが無効（`REGISTRAR_ENABLED` が `true` でない）のときもボードは見えますが、
  状態は無効と表示され、「今すぐ補充」はバックエンドに拒否されます。

## イベント

### ここに載るもの

- ここに載るのは**低頻度の構造化イベント**だけです。設定の読み取り失敗、プール索引の再構築、
  管理 API のログイン失敗といった運用診断に加えて、レジストラの補充イベントとパネル自身の
  書き込み操作。**転送経路が key を自動でクールダウンや排除にしたときは、今のところ
  イベントを出しません**——そこは Key プールのボードでその key 自身の状態を見てください。

### ツールバーと保持ウィンドウ

- **ツールバー**: レベルで絞り込み、テキストで検索、自動更新の一時停止、クリア、ダウンロード。
  「クリア」は画面上のこの一覧を消すだけで、**サーバ側に永続化済みのイベントには触れません**。
  もう一度見るには「ダウンロード」を押すか、ページを再読み込みしてください。
- **イベントは時間単位のウィンドウに入り、24 個のウィンドウが保持されます**——ちょうど一日ぶんで、
  それより古いものは自然に失効し、パネルからはもう辿れません。

### 5 本の警告バー

- 警告バーはそれぞれ別のことを言っており、**互いに独立したバーで、同時に点灯しえます**。

| 警告バー | 何を言っているか | どうすればよいか |
|--------|----------------|----------------|
| 破棄 | このレプリカのイベントバッファが、永続化前に最も古い数件を押し出した | イベントの発生が永続化より速い。コンテナログ / Workers Logs でその区間を探す |
| 予算 | このレプリカの今日のイベント書き込み予算を使い切った | 同上。永続化されなかったぶんはログに残っている |
| 打ち切り | このページは条件に一致するすべてのイベントを表示していない | 絞り込みを狭めるか、見る期間を短くする |
| カーソル先行 | 取得位置がサーバ時刻より先行している。時刻の巻き戻し、あるいはレプリカ間の時刻ずれ | パネルは新しい位置から再取得済み。これは自然に収まる |
| カーソル契約違反 | API が返したカーソルが数値でも null でもなく、パネルは直前のものを保持した——**以後、新しいイベントが表示されなくなる可能性がある** | イベントストアがこのゲートウェイ以外から書かれていないか確認する |

### イベント 1 件の形

パネルが key を 1 本無効化したあと、イベントボードと「ダウンロード」が返すのは同じ構造化
レコードです。イベント名は安定した機械可読の文字列で、絞り込みも分類もこれだけを見ます。
`msg` を解析することはありません。

```json
{
  "ts": 1735689600000,
  "level": "warn",
  "event": "key.disabled",
  "msg": "面板停用了一把 key（它仍然占着 targetKeys 的名额，不会触发补池）",
  "fields": { "id": "9f2c" }
}
```

## 使用量

### 二つの層

- **使用量は二層で、第一層は常にあります。** 第一層はプール全体の累計値（概要ページ上部の
  カードが使っているのがまさにこれ）で、スイッチは要りません。第二層は日 / 時間 / モデル /
  プロトコル別に分解した時系列で、`USAGE_STATS_ENABLED` が制御し、**既定では無効**です。
- **無効のあいだ、このページは空のグラフを描きません**。`0` ばかりのグラフは「この期間は
  誰も使っていない」と読まれますが、実際は「このデプロイはそもそも記帳していない」です。
  この二つが同じ見た目になってはいけません。

### 期間と保持

- **期間は 4 段階**: `24h`、`3d`、`7d`、`30d`。
- **保持は最長 30 日**で、それより古いデータは失効しています。いちばん長い段は区間全体の
  シャードを一度に読み出しますが、それが Cloudflare Worker 上で常に完了するかどうかを、
  本リポジトリは実機で計測したことがありません——失敗したときは、完全に見える数字を出さず
  読み取り失敗としてそのまま表示します。

### なぜ概算なのか

- **ここの数値には `≈` が付き、その出所は三つとも別物です**: ① 未永続化の尾——カウンターは
  まずインスタンスのメモリに溜まり、あとからまとめて書き込まれます。この窓の長さは
  パネル自身が教えてくれます。② 短命なインスタンス——書き込み前に回収されれば、その区間は
  失われます。③ 一日のシャードは 2 つのスロットしかないため、それより多いレプリカが同時に
  書くと、同じスロットは後勝ちになります。
- **読み取れなかったセルは `—` を表示し、`0` にはしません**。「今日は本当に 0 件だった」
  「第二層が無効」「今回の読み取りが失敗した」は別々の三つで、パネルがそれらを同じ見た目に
  描くことは許されません。

## モデル

### このページが答えること

- **このページが答えるのはひとつの問いです**: このゲートウェイが対外的に認めるモデルは
  どれか、各モデルはどの種類か、実際にどのプロトコルで使えるのか、そしてどのエンドポイントを
  叩けばよいのか。

### 3 つの種類とプロトコル対応

- **種類は 3 つ**: チャット、画像、動画。チャットのモデルは 4 つのチャットプロトコルに
  ぶら下がります。画像と動画のモデルはプロトコル欄が空です——どのチャットプロトコルにも
  属さず、それぞれのメディアエンドポイントを通ります。
- **プロトコル対応は 1 マスずつのバッジ**であって、「対応」「非対応」の一言ではありません。
  この欄はモデルごとに埋めます。

  > [!WARNING]
  > **今日のカタログには「あるプロトコルでは使えて別の
  > プロトコルでは使えない」モデルは 1 つもありません**: チャットのモデルは 4 つすべてで
  > 使え、メディアのモデル 3 つはこの欄が空です。プロトコルで絞り込めますが、絞った結果が
  > ゼロ件のときは空の表を描かず「このプロトコルで利用できるモデルはありません」と
  > そのまま言います。

### エンドポイント欄と読めなかったとき

- **エンドポイント欄が示すのは「クライアントがどのパスを叩くか」**で、
  [API.md](API.md) と同じ真源から来ています。この文書は二つ目の写しを持ちません。
- **カタログを読めなかったときはダッシュを表示し**、同じ画面に読み取り失敗のバナーと
  再試行ボタンが出ます。

  > [!IMPORTANT]
  > **「読めなかった」と「モデルが 1 つもない」は別のことですが、
  > 今日それを言い切っている文はダッシュのホバー説明にしかありません**（`title=`）:
  > マウスなら見えますが、タッチ画面では出てきません。

> [!WARNING]
> **対外契約に既知の食い違いが一箇所あり、そのまま登記します**: Gemini のモデル一覧
> エンドポイントは**すべて**のモデルについて `generateContent` を宣言しており、
> **あの動画モデルも含まれます**。一方で動画の実際の経路は「タスク作成 + ポーリング」の
> 二段式です。このページは実際の利用可否で埋めており、両者が食い違うときはこのページを
> 信じてください。

## プレイグラウンド

### 2 つの鍵は厳密に分離

- **2 つの鍵は厳密に分離されており、これがこのページで最も重要なことです。**
  管理トークンは `x-admin-key` を通り、`/admin/api` のツリーだけを叩きます。
  プレイグラウンドが使うのは**ゲートウェイトークン**（`GATEWAY_TOKEN`）で、各プロトコル
  慣用の認証ヘッダーを通って対外側のツリーを叩きます。2 つはブラウザー内で別々に保存され、
  **ログアウト時にまとめて消えます**——共有端末や画面共有の場では、消し残した方が
  そのまま次の人に渡ってしまいます。
- **ゲートウェイトークンはご自分で一度貼り付けます。「自動入力」はありません**:
  パネルは平文を読み取れない（資格情報は書き込み専用）ため、できるのは設定ページに
  保存されている末尾 4 桁と貼り付けた値を照らし合わせ、「一致」「不一致」
  「読み取れないので今回は照合できない」のいずれかを伝えることだけです。

### 3 つのモード

- **モードは 3 つで、設定できる項目がそれぞれ違います**:

| モード | 叩くエンドポイント | このモードで設定できること |
|------|------------------|--------------------------|
| チャット | 4 つのチャットプロトコルそれぞれの対外パス | プロトコルとモデルを選ぶ。ストリーミングも有効にできる |
| 画像 | 画像生成のエンドポイント 1 本 | モデルのみ。プロトコル選択もストリーミング切り替えもなし |
| 動画 | タスク作成と結果取得の 2 本 | モデルのみ。タスク作成後は結果を自動でポーリング |

**プロトコル選択とストリーミング切り替えはチャットのときだけ現れます。** 単に隠している
のではありません: プロトコルカタログ上、メディアの 2 本はどのチャットプロトコルにも
属していません。押せないボタンを並べれば、画像でもプロトコルを選べる / ストリーミング
できると誤解させるだけです。

### ストリーミングと動画モード

- **ストリーミングでは token 数を表示しません**: パネルはストリーミング中に使用量を
  読まないので、そこに `0` と書けば嘘になります。だからその枠には数値を出しません。
- **動画は二段式です**: まずタスクを作成してタスク ID を受け取り、その ID で結果を
  ポーリングします。ポーリングは**5 秒ごと、上限は 60 回 / 5 分**で、先に達した方が
  効きます——今日この二つはちょうど等価です（60 回 × 5 秒がちょうど 5 分）。
  ページが隠れていた間は打点が止まっても壁時計は進むので、そのときは時間側が先に達します。

> [!WARNING]
> **本物の上流が動画を 1 本生成するのにどれだけかかるかを、本リポジトリは一度も
> 計測していません。** この 2 つの上限は「閉じ忘れたタブが永久ポーリング機になる」ことを
> 塞ぐためのもので、実際の生成時間から導いたものではありませんし、この文書は両者の関係に
> ついて何の結論も述べません。上限に達するとパネルは「ポーリングが上限に達したため停止した」
> と明言し、タスク ID を画面に残します——タスク自体はまだ動いている可能性があり、
> 後ほどご自身でその ID を使って確認できます。

### 「送信」は毎回本当に上流を叩く

- **タスク作成の応答に使えるタスク ID がないとき、パネルは推測しません**: 決まった項目
  だけを ID として読み、どれも使えなければポーリングを行わず、応答の原文をそのまま出します。
- **「送信」を押すたびに本当に上流を叩きます**: そのリクエストは通常の転送とまったく同じ
  経路を通り、使われた key も同じように記帳されます（ボード早見表の下の一文を参照）。
  動画は 1 回のタスク作成に加えて、最大 60 回のポーリングです。
- **画面に残るやり取りは最大 20 往復**で、古い方はこのページから削除され、
  何往復ぶん削除したかをパネルが伝えます。「やり取りを消去」で自分で消すこともできます。
  消えるのは画面上のこの控えだけで、サーバ側には何も起こりません。

## 設定

### 5 枚のカード

設定ページには今日 5 枚のカードがあります。

| カード | 何を扱うか | 注意点 |
|------|----------|------|
| 認証キー | ゲートウェイトークンのみ。管理トークンはこのカード上では読み取り専用の表示で、パネルは自分の鍵を変えられません | 資格情報は書き込み専用。入力欄が空 = その項目は変更しない |
| 上流とクールダウン | 上流アドレス、タイムアウト、クールダウンと排除のつまみ | うち 2 つは実例作成時に一度読む項目。本節末を参照 |
| レジストラー | 補充のつまみ一式、**各メールチャネル自身の資格情報**（左右対称の子カード 2 枚）、そして「詳細設定」の折りたたみ | 折りたたみの中の項目は、毎回の自動登録の宛先を変えます |
| 統合サンプル | そのまま実行できる呼び出し例 | アドレスは今このパネルを開いているオリジンから取り、トークンはプレースホルダーです |
| 危険ゾーン | 取り消せない結果を持つボタンが 2 つ: 設定のリセットと Key プールの全削除 | どちらも二段階の確認あり。全削除では現在のプールサイズの手入力も求められます |

### 4 つ組と優先順位

- **どの項目も 4 つ組を並べて表示します**: ストレージには何があるか、環境変数には何があるか、
  いま効いているのはどれか、そして誰がそれを固定しているか。優先順位は
  **環境変数 > ストレージの値 > 組み込みの既定値**です。環境変数に固定された項目は
  このページで変更しても反映されず、パネルはデプロイ側のどの変数を変えるべきかを直接示します。

### 資格情報は書き込み専用

- **資格情報は書き込み専用**: パネルは平文を受け取らず、画面に出るのは「設定済み / 未設定」と
  末尾 4 桁だけです。空欄は「変更しない」。本当に消すには「クリア」を押しますが、その一歩は
  先に何が起きるかを伝えます——環境変数の値に戻るのか、次回の再起動で起動できなくなるのか、
  いまは何にも影響しないのか。

### 保存したときの応答

- **保存したあと、パネルが返すのは「保存しました」の一言だけではありません**: 実効値を
  読み直し、本当に変わった項目を強調し、そのうえで今回どの種類の項目を触ったかで伝播の
  言い方が分かれます。普通の項目なら、画面に出る文は**逐語で
  「このインスタンスには既に反映されています」から始まり**、続けて他のレプリカ / isolate に
  最大どれだけかかるかを述べます——つまりこのインスタンスでは既に反映済みだと言っており、
  「どこにもまだ反映されていない」ではありません。
  この上界は設定キャッシュと KV エッジキャッシュの二層を足したものです。

  > [!IMPORTANT]
  > **どちらの数値も環境変数表にはありません**: いずれも `src/http/config-holder.ts` に
  > ベタ書きされた定数で、誰にも調整できません。値は [DEPLOY.md](DEPLOY.md) の設定ページの
  > 保存応答について述べた**本文**に書いてあります。

### 例外の 2 フィールド

> [!IMPORTANT]
> **例外のフィールドが 2 つあります**: プールのスナップショットキャッシュと書き込み
> まとめの間隔（`POOL_CACHE_TTL_MS` と `POOL_TOUCH_INTERVAL_MS`）は**実例を作るときに
> 一度だけ読む**項目です ⇒ 保存しても**このインスタンスすら反映していません**。
> コンテナの再起動か isolate の回収が要ります。今回の保存が**この 2 つだけ**を触った
> ときは、上の「既に反映済み + 上界」の一文は**まるごと出ず**、代わりに「保存はされた
> が、このインスタンスにもまだ反映されていない」が出ます。両方の種類を一緒に変えた
> ときは、二つの文が同時に出ます。

### パネルは自分の鍵を変えられない

- **パネルは自分の鍵を変えられません**: `ADMIN_TOKEN` は環境変数からのみ読みます。
  差し替えるにはデプロイ側の環境変数を変えて再起動してください。
- **ストレージの設定が読み込めないとき、このページは診断ビューになります**: 何が足りないかを
  1 件ずつ並べ、しかも**フォームは編集可能なまま**です——それが唯一の出口だからです。

## 危険ゾーン

設定ページの最後のカードです。ここにある 2 つのボタンはどちらも取り消せず、元に戻す手段も
ありません。

| ボタン | 触るもの | 触らないもの | 二段階の確認 |
|------|--------|------------|------------|
| 設定をリセット | ストレージ上の設定 1 件を、書き込み 1 回でまるごと空にします（ゲートウェイトークンと 2 つのメールチャネルの資格情報を含む） | キープール、キーごとの使用量、イベント記録、補充履歴 | ダイアログがリセット後に何が欠けるかを示し、それから確認を求めます |
| Key プールを空にする | プール内のすべての key のレコードと、その id 索引 | 設定、イベント記録、補充履歴 | 確認に加えて、現在のプールサイズを手で入力する必要があります |

### リセットは工場出荷状態への復元ではない

- **設定のリセットは工場出荷状態への復元ではありません。** 実効値は「環境変数 > ストレージ >
  組み込みの値」の 3 層から決まり、このボタンが消すのは真ん中の層だけです。環境変数で
  ロックされた項目は 1 ビットも動きません。したがって一部の項目に対しては何もせず、画面は
  実際に変わった項目だけをハイライトします。

### 全削除は使用量履歴も持っていく

- **Key プールの全削除は使用量履歴も一緒に持っていきます。** キーごとのリクエスト数・成功数・
  直近のエラーはそのレコードの値の中にあり、レコードを消すことは履歴を消すことです。
  取り戻せる控えはありません。key の平文も同じくストレージにしか存在しません。

### 画面上で終わってもレプリカは追いついていない

- **画面上で終わったことは、すべてのレプリカが追いついたことを意味しません。** リセット後、
  他のレプリカや isolate がそれを見るのは設定キャッシュとエッジキャッシュが切れてからです。
  全削除後も、転送経路はプールスナップショットの TTL とエッジキャッシュの合計だけ、それらの
  key を選び続けることがあります。プールスナップショット側の上限のつまみ
  （`POOL_CACHE_TTL_MS`）は [DEPLOY.md](DEPLOY.md) の環境変数表にあります。

  > [!IMPORTANT]
  > **設定側の上限はその表にはありません**——`src/http/config-holder.ts` にベタ書きされた
  > 2 つの定数の和で、誰にも調整できず、値は同じ文書の本文に書いてあります。
  > このページでは、設定のほうは上の設定カードの説明でも触れており、
  > プールスナップショットのほうは概要ページの 2 本の鮮度についての項目にあります。

### 割り当てと資格情報

- **それぞれのボタンがどれだけの割り当てを使うかは [DEPLOY.md](DEPLOY.md) の割り当て計算に
  書いてあります**: リセットは書き込み 1 回、全削除は key 1 件につき削除 1 回に索引の
  書き込み 1 回を足したものです。プールが大きいほど、このボタンは高くつきます。
- **どちらのボタンも資格情報を表示し返しません。** リセットの応答に入るのは読み戻した 4 つ組、
  「設定されているか」、そして末尾 4 文字のヒント（`hint`、設定ページの資格情報欄に出るものと
  同じ）です——**このページの他の場所と逐語で同じ基準です: 末尾 4 文字はあり、平文は
  1 文字もありません。**

## パネルがしないこと

### 自分の鍵を交換しない

`ADMIN_TOKEN` は環境変数からのみ読むため、パネルはそれを変更できませんし、「すでに配った
利用を今すぐ失効させる」という取り消し口もありません。交換するとは、デプロイ側の変数を
変えて再デプロイするかコンテナを作り直すことです。

### 資格情報の平文を表示し返さない

バックエンドが返すのは「設定されているか」と末尾 4 桁だけなので、「自分のトークンを入れて」
というボタンは作れません——それにはバックエンドに平文の読み出し口が要り、その口がひとたび
開けば書き込み専用という原則が丸ごと消えます。

### wrangler secret や .env の代わりにはならない

このページが変えるのはストレージ側の設定であり、環境変数のほうが優先されます。食い違う
ときは画面にロック印が出ますが、環境変数そのものを変えられるのはデプロイ側だけです。

### リモートのメディアを取りに行かない

プレイグラウンドの結果アドレスはそのまま並び、いつでもコピーできます。**「開く」リンクが
付くのは `http` / `https` で始まるものだけ**で、`javascript:` / `blob:` / `file:` は上流が
本当に返してきても付きません（たどった先は上流の内容が決めるトップレベル文書になるから
です）。埋め込まれるのは `data:` 形式の画像だけで、その経路は第三者へのリクエストを一切
発生させません。

## 障害対応

### 開かない、返るのは `404`

**原因**：このデプロイに `ADMIN_TOKEN` がない、あるいは設定したが不適合だった、ということ
です。ツリーが登録されていないので、外からは管理画面の有無すら分かりません。

**対処**：デプロイ側で適合する `ADMIN_TOKEN` を設定し直し（三条の規則はこの文書の冒頭に
あります）、再デプロイするかコンテナを作り直してください。

### 開かない、返るのは `401`

**原因**：トークン自体が違います。多くは差し替え済みの値です。

**対処**：現在の `ADMIN_TOKEN` をもう一度入力してください。

> [!IMPORTANT]
> **これをパネルがログイン画面へ
> 戻す動きと一緒くたにしないでください**: 12 時間という窓はパネル自身の判定で、そこに達した
> ときはリクエストが 1 件も出ていかず、サーバ側には何の記録も残りません。どちらももう一度
> 入力すれば済みます。

### 開かない、返るのは `503`

**原因**：`ADMIN_TOKEN` がストレージ側のゲートウェイトークンと同じ値になっています。この
規則は管理リクエストごとに再判定され、イベントボードとログに `admin.token_conflict` が
1 件残ります。

**対処**：ストレージ側のゲートウェイトークンを `ADMIN_TOKEN` と異なる値に変えてください。

> [!WARNING]
> **この一歩で回復するのは可用性だけです**: その管理トークンは漏洩したものとして扱う必要が
> あり、完全な手順は [DEPLOY.md](DEPLOY.md) にあります。両方を終えて初めて対処完了です。

### トークンを貼るとログイン欄が文字を拒む

**原因**：パネルは送信する前に文字種を判定し、印字可能な ASCII（`0x20–0x7E`）しか受け取り
ません。`U+00FF` を超える符号位置——CJK、絵文字、ゼロ幅スペース——および NUL / LF / CR は
ブラウザーがそもそも送れず、`é` / `£` は送れはしますが、ランタイム間のエンコーディングの
判断としてこのゲートウェイも受け取りません。この経路では**リクエストが 1 件も出ていかない**
ので、サーバ側にはログイン失敗の 1 件すら残りません。

**対処**：印字可能な ASCII だけで作ったトークンを貼り直してください。

> [!IMPORTANT]
> **デプロイ側がその
> 種のトークンを持っているときは、この文言は出ません**: そのときはツリーがそもそも登録されて
> おらず、返ってくるのは上の `404` です。

### 画面が古い値のまま

**原因**：設定とプールのスナップショットはそれぞれ別のキャッシュ窓を持ち、その外側にさらに
KV のエッジキャッシュが一層あります。プールスナップショット側の上界と代償は
[DEPLOY.md](DEPLOY.md) の環境変数表にあります。設定側の上界はベタ書きの定数で、**その表には
ありません**——値は同じ文書の本文に書いてあります。どちらもここには写しません。

**対処**：二層のキャッシュがそれぞれ切れるのを待つか、コンテナを再起動する / isolate の回収
を待ってください。概要ページの「何秒前に読んだか」の 2 行はまさにこのためにあります。

### エラー文がバックエンドの原文

**原因**：パネルは**認識できる**エラーコードには自前の各言語文を出し、認識できないコードには
バックエンドの一文をそのまま出して「これはバックエンドの原文です。このパネルにはそのエラー
コードの訳文がまだありません」と印を付けます。

**対処**：その原文を手がかりにログとイベントボードを当たってください。

> [!IMPORTANT]
> **これを「すべての
> エラーが自分の言語で出る」と読まないでください**——認識できないものはそうなりませんし、
> パネルはその事実に印を付けるほうを選び、訳文であるかのように見せることはしません。
