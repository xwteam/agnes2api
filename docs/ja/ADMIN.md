# 管理パネル

**Language:** [English](../en/ADMIN.md) | [简体中文](../zh-CN/ADMIN.md) | [繁體中文](../zh-TW/ADMIN.md) | 日本語 | [한국어](../ko/ADMIN.md)

管理パネルは**任意**です。`ADMIN_TOKEN` を設定していなければ `/admin` のツリーはそもそも
登録されず、ゲートウェイは普段どおり転送を続けます。この文書が扱うのは画面に見えている
側だけ——各ボードがどんな問いに答えるのか、表示されている数値がどういう口径なのか、
どの操作が書き込みになるのか、です。**変数そのもの（既定値・取りうる範囲・代償）は
リポジトリ全体で一箇所、[DEPLOY.md](DEPLOY.md) の環境変数表にだけあります。**
ここでは案内するだけで、二つ目の写しは置きません。

この文書が扱う範囲: パネルへの入り方と、概要 / Key プール / レジストラ / イベント /
使用量の各ボードです。

## パネルへの入り方

- **アドレス**: `https://<your-gateway>/admin`。`<your-gateway>` はご自分のゲートウェイの
  アドレスに置き換えてください。末尾スラッシュ付きの `/admin/` は `/admin` へ自動的に
  転送されるので、手入力しがちな二通りの書き方はどちらでも入れます。
- **前提条件はひとつだけ**: デプロイ時に `ADMIN_TOKEN` を設定することです。24 文字以上で、
  印字可能な ASCII だけで構成され、`GATEWAY_TOKEN` とは異なる値でなければなりません。
  この三条それぞれの理由と境界、そして不適合のときにどのイベントが記録されるかは、
  [DEPLOY.md](DEPLOY.md) の「管理パネル関連の変数」の節にあります。
- **未設定あるいは不適合のとき、`/admin` が返すのは `404` であって `401` ではありません**。
  ツリーが登録されていないだけなので、「ここに管理画面がある」と外に知らせることも
  ありません。パネルが開けなくても**ゲートウェイの転送には影響しません**。
- **トークンはブラウザの localStorage にそのまま保存され**、パネルは 12 時間後に再入力を
  求めます。
- この上限が縮めるのは localStorage に置かれた値の利用可能な窓だけで、**失効させるもの
  ではありません**。取り消す道はひとつ、`ADMIN_TOKEN` を差し替えて再デプロイ / コンテナを
  作り直すことです。パネルは TLS の内側に置き、信頼できる端末でのみ開いてください。
  詳しい論証は [DEPLOY.md](DEPLOY.md) の「管理トークンの漏洩」の段にあります。

## 8 つのボード早見表

| ボード | 答える問い | 読み取り専用か書き込みか | 必要なスイッチ |
|---|---|---|---|
| 概要 | このデプロイは今どんな形態か、使える key はあと何本か | 読み取り専用 | – |
| Key プール | 各 key は今どの状態か、なぜ使えないのか | 書き込み | – |
| レジストラ | 自動補充は動いているか、直近の数回で何を発行したか | 書き込み | `REGISTRAR_ENABLED` |
| イベント | 最近どんな運用レベルの出来事があったか | 読み取り専用 | – |
| 使用量 | リクエスト量・成功率・レイテンシは時間とともにどう動いたか | 読み取り専用 | `USAGE_STATS_ENABLED`（第二層のみ） |
| モデル | ゲートウェイが対外的に認めるモデルと、そのモダリティ・プロトコル | 読み取り専用 | – |
| プレイグラウンド | 本物のリクエストで、あるプロトコルが通るか一度確かめる | 上流を叩く | – |
| 設定 | 実行時設定の現在値と、環境変数に固定されている項目 | 書き込み | – |

「書き込み」は**ストレージへの書き込み**を指し、「上流を叩く」はストレージには書かないが
上流へ実際にリクエストを一度送ることを指します。

## 概要

概要が答えるのはひとつの問いです。**このデプロイは今どんな形態で、プールに使える key が
あと何本残っているか。**

- **プールの 5 つのバケット**: 総数 / 使用可 / クールダウン中 / 排除済み / 無効化済み。
  5 つとも常に表示します。本物の `0` はそれ自体が真実だからです。**読み取れなかった枠は
  `—` を表示し、`0` を捏造することはありません**——この二つは画面上で同じ見た目に
  なってはいけません。
- **ランタイムとストレージの自己申告**: ランタイム名、バージョン、サーバ時刻、
  ストレージバックエンド、書き込み可否、そして Node 形態にしかないメモリ / 稼働時間 /
  PID。いずれも API が返した内容だけを使い、パネルが自分のランタイムを嗅ぎ分けることは
  しません。Worker 形態には常駐プロセスがないので、その 3 枠は「常駐プロセスなし」と
  表示されます。`0` でも空白でもありません。
- **2 本の鮮度**: プールのスナップショットと設定は、それぞれ別に「何秒前に読んだか」を
  持ちます。同じ時間軸ではないので分けて表示します。プール側の遅れは
  `POOL_CACHE_TTL_MS` に加えてエッジキャッシュの一層で決まり、その上界と代償は
  [DEPLOY.md](DEPLOY.md) の該当セルに書いてあります。
- **第一層の累計使用量**: リクエスト数 / 成功 / 失敗 / クライアントエラー / 成功率。
  プール内の全 key を集計した値なので `≈` が付きます。key ごとのカウンターは並行時に
  少なく数えられ（KV に CAS がないため）、永続化は最大で `POOL_TOUCH_INTERVAL_MS` ぶん
  遅れます。
- **設定の要約**: レジストラのスイッチ、主・予備チャネル、`TARGET_KEYS` の現在の実効値。
  環境変数に固定されているフィールドにはロック印が付きます——それらを設定ページで
  変更しても反映されません。環境変数のほうが優先されるからです。

## Key プール

- **バケットのバッジは優先順位を一度だけ射影したもの**で、独立した 4 つの旗ではありません。
  ひとつの key が複数の条件を同時に満たすときは、無効化済み > 排除済み > クールダウン中 >
  使用可 の順で最初のひとつを取ります。ですから「無効化されていて、なおクールダウン中」の
  key のバッジは「無効化済み」になります。クールダウンが消えたわけではなく、バッジからは
  見えないだけです。
- **単体の操作は 8 つ**: 無効化、有効化、クールダウン解除、失敗カウントの消去、排除の取り消し、
  メモの編集、疎通確認、削除。
- **一括操作は 3 つ**: 一括無効化、一括クールダウン解除、一括削除。
- **一度のインポートは最大 200 件の key**。これを超えたら即座に `400` で、**黙って切り詰める
  ことはありません**——切り詰めは「入れたつもりで実は入っていない」を生みます。
- **「既存 key の状態をリセットする」チェックボックスが実際にリセットするもの**:
  **システムが判定した失敗状態**——失敗カウント、クールダウン期限、クールダウン理由、
  排除フラグ、排除理由です。次の 4 つは**意図的に触りません**: 無効化フラグ（自分で倒した
  スイッチであり、一度の貼り付けで黙って戻してよいものではありません）、追加日時（由来は
  失敗状態ではありません）、使用量の統計（履歴は失敗状態ではありません）、メモ（自分のために
  書いた言葉です）。
- **削除の前に無効化が必要**: まだ使われている key をそのまま削除しようとすると拒否されます。
  一括経路ではこの制約はバッチ全体の失敗にはならず、項目ごとに理由が返ります。
- **単体の疎通確認**は、その key で実際に上流へ一度リクエストを送ります。一覧の「最終使用」と
  使用量カウンターはまとめてから永続化されるため、分解能は `POOL_TOUCH_INTERVAL_MS` の
  間隔より細かくはなりません。

## レジストラ

パネルのレジストラボードは**索引であって説明書ではありません**。補充の規則、チャネルの
選び方、自分で用意すべき資格情報、障害時の追い方はすべて [REGISTRAR.md](REGISTRAR.md) に
あり、この文書は二つ目の写しを持ちません。ボードから見えるのは次のとおりです。

- **2 本のメールチャネルは対等**で既定値がありません。主チャネルは明示指定が必須、予備は
  未設定でも構いません。ボードにはそれぞれの役割（主 / 予備）と資格情報の設定有無が
  表示されます。
- **補充の履歴**: 各回がいつ走ったか、どのチャネルを通ったか、タイマー起動か人の操作か、
  どれだけ時間がかかったか。
- **チャネルテストはそのチャネルの利用可能ドメイン一覧を読むだけ**です。メールボックスの
  作成もアカウント登録も行わず、枠も消費しません。
- **「今すぐ補充」には 4 本のガードレール**があり、どれかひとつでも満たさなければ起動しません。
  同一レプリカ内の実行中ガード、レプリカ間のストレージ短期ロック、手動補充どうしの最小間隔、
  そして手動実行の一日あたりの上限です。それぞれのエラーコード・算式・残存リスクは
  [REGISTRAR.md](REGISTRAR.md) の「管理パネルの「今すぐ補充」」の節にあります。
- レジストラが無効（`REGISTRAR_ENABLED` が `true` でない）のときもボードは見えますが、
  状態は無効と表示され、「今すぐ補充」はバックエンドに拒否されます。

## イベント

- ここに載るのは**低頻度の構造化イベント**だけです。設定の読み取り失敗、プール索引の再構築、
  管理 API のログイン失敗といった運用診断に加えて、レジストラの補充イベントとパネル自身の
  書き込み操作。**転送経路が key を自動でクールダウンや排除にしたときは、今のところ
  イベントを出しません**——そこは Key プールのボードでその key 自身の状態を見てください。
- **ツールバー**: レベルで絞り込み、テキストで検索、自動更新の一時停止、クリア、ダウンロード。
  「クリア」は画面上のこの一覧を消すだけで、**サーバ側に永続化済みのイベントには触れません**。
  もう一度見るには「ダウンロード」を押すか、ページを再読み込みしてください。
- **イベントは時間単位のウィンドウに入り、24 個のウィンドウが保持されます**——ちょうど一日ぶんで、
  それより古いものは自然に失効し、パネルからはもう辿れません。
- 4 種類の警告バーは、それぞれ別のことを言っています。

| 警告バー | 何を言っているか | どうすればよいか |
|---|---|---|
| 破棄 | このレプリカのイベントバッファが、永続化前に最も古い数件を押し出した | イベントの発生が永続化より速い。コンテナログ / Workers Logs でその区間を探す |
| 予算 | このレプリカの今日のイベント書き込み予算を使い切った | 同上。永続化されなかったぶんはログに残っている |
| 打ち切り | このページは条件に一致するすべてのイベントを表示していない | 絞り込みを狭めるか、見る期間を短くする |
| カーソル | 取得位置が契約に反している、あるいはサーバ時刻より先行している | パネルは再取得済み。繰り返すならイベントストアがこのゲートウェイ以外から書かれている |

## 使用量

- **使用量は二層で、第一層は常にあります。** 第一層はプール全体の累計値（概要ページ上部の
  カードが使っているのがまさにこれ）で、スイッチは要りません。第二層は日 / 時間 / モデル /
  プロトコル別に分解した時系列で、`USAGE_STATS_ENABLED` が制御し、**既定では無効**です。
- **無効のあいだ、このページは空のグラフを描きません**。`0` ばかりのグラフは「この期間は
  誰も使っていない」と読まれますが、実際は「このデプロイはそもそも記帳していない」です。
  この二つが同じ見た目になってはいけません。
- **期間は 4 段階**: `24h`、`3d`、`7d`、`30d`。
- **保持は最長 30 日**で、それより古いデータは失効しています。いちばん長い段は区間全体の
  シャードを一度に読み出しますが、それが Cloudflare Worker 上で常に完了するかどうかを、
  本リポジトリは実機で計測したことがありません——失敗したときは、完全に見える数字を出さず
  読み取り失敗としてそのまま表示します。
- **ここの数値には `≈` が付き、その出所は三つとも別物です**: ① 未永続化の尾——カウンターは
  まずインスタンスのメモリに溜まり、あとからまとめて書き込まれます。この窓の長さは
  パネル自身が教えてくれます。② 短命なインスタンス——書き込み前に回収されれば、その区間は
  失われます。③ 一日のシャードは 2 つのスロットしかないため、それより多いレプリカが同時に
  書くと、同じスロットは後勝ちになります。
- **読み取れなかったセルは `—` を表示し、`0` にはしません**。「今日は本当に 0 件だった」
  「第二層が無効」「今回の読み取りが失敗した」は別々の三つで、パネルがそれらを同じ見た目に
  描くことは許されません。
