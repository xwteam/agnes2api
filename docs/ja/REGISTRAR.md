# レジストラー（自動プール補充）

> **デフォルトで無効です。** `REGISTRAR_ENABLED` のデフォルトは `false` で、導入しただけ
> では一切アカウント登録を開始しません。明示的に `true` に設定した場合のみ有効になり
> ます。

## これは何か

レジストラーはオプション機能です。key プール内の利用可能な key 数が `TARGET_KEYS` を
下回ると、新しい Agnes アカウントを自動登録し、ログインし、API key を発行してプールに
書き込みます。登録には Agnes から届く認証コードの受信が必要なため、下記のメールボック
スチャネルのいずれかに依存します。

> **コンプライアンスに関する注意**
>
> 大量アカウント登録は Agnes の利用規約と緊張関係にあります。レジストラーを有効にする
> かどうか、どの程度の頻度で使うかは、運用者自身が判断し、責任を負うべき事項です——
> 本プロジェクトはこの判断を代行しません。

## 2 つのメールボックスチャネル：選び方

レジストラーは認証コードを受信するために 2 つのメールボックスチャネルをサポートしま
す。

### 2 つのチャネルの比較

| | YYDS Mail | MoeMail |
|----|---------|-------|
| 性質 | サードパーティの一時メールボックスサービス | 自分でホストする一時メールボックスサービス |
| API ベース URL | デフォルトあり（`YYDS_BASE_URL`、公開 API エンドポイント） | デフォルトなし（`MOEMAIL_BASE_URL`）、自分で立てたインスタンスのアドレスを入力 |
| 認証情報の取得 | サービスに API Key を申請（`YYDS_API_KEY`） | 自分のインスタンス内で API Key を発行（`MOEMAIL_API_KEY`） |

### 主チャネルとフォールバックチャネルの設定

**2 つのチャネルは完全に対等であり、本プロジェクトはどちらも主要チャネルに指定せず、
どちらも推奨しません。**

`REGISTRAR_PRIMARY` にデフォルト値はなく、レジストラーを有効にする際は `yyds` か
`moemail` を明示的に指定する必要があります。`REGISTRAR_FALLBACK` は任意です。主チャネル
が**チャネルレベルの失敗**（ドメイン一覧取得の失敗、メールボックス作成の連続失敗、認証
情報の無効化、認証コードが届かない、など）に遭遇した場合、その回だけ自動的にフォール
バックします。空欄のままならフォールバックは行われません。

> 「認証コードが届かない」もチャネルレベルの失敗です。認証コードはまさにこのメールボッ
> クスチャネル経由で配送されるため、ドメインの MX レコード失効やメール転送ルールの削除
> ——API はすべて 2xx を返すのにメールだけが永遠に届かない——も同様に「このチャネルは今
> key を生み出せない」を意味します。

### 主チャネルの選び方

判断基準：レジストラーは「ドメインを切り替える」ことで Agnes による使い捨てメールボッ
クスドメインのブロックを回避しています。利用可能なドメインが多いほど、レジストラーは
長く動作し続けられます。両サービスでそれぞれ何個の利用可能ドメインを持っているか確認
し、多い方を主チャネルにするとよいでしょう——これはどちらのサービスかとは無関係で、
あなた自身のアカウントや自己ホスト環境の設定次第です。

## 組み込みの認証情報はゼロ——自分で用意してください

このリポジトリには実際の鍵、アカウント、プライベートドメインは一切含まれていません。
レジストラーを有効にする前に、以下を自分で用意する必要があります。

### チャネルごとに用意するもの

- **YYDS Mail を使う場合**：サービスに API Key を申請し、`YYDS_API_KEY` に設定します
  （`YYDS_BASE_URL` にはすでにデフォルト値があり、通常変更不要です）。
- **MoeMail を使う場合**：MoeMail インスタンスを自分でホストし、そのアクセスアドレス
  を `MOEMAIL_BASE_URL` に、インスタンス内で発行した API Key を `MOEMAIL_API_KEY` に
  設定します（どちらもデフォルト値がないため、必ず明示的に設定してください）。

### 最低限どこまで用意すればよいか

少なくとも `REGISTRAR_PRIMARY` が指すチャネルの認証情報を用意してください。
`REGISTRAR_FALLBACK` を設定する場合は、そのチャネルの認証情報も併せて用意します。

## 設定項目

| 変数 | 必須 | デフォルト | 説明 |
|----|----|----------|----|
| `REGISTRAR_ENABLED` | いいえ | `false` | マスタースイッチ。`true` にしないとレジストラーは有効になりません。 |
| `REGISTRAR_PRIMARY` | 有効化時は必須 | なし | 主チャネル、`yyds` または `moemail`。両者は対等でデフォルト値なし。 |
| `REGISTRAR_FALLBACK` | いいえ | 空（フォールバックなし） | フォールバックチャネル、`yyds` または `moemail`。主チャネルがチャネルレベルで失敗した際に使われる。 |
| `TARGET_KEYS` | いいえ | `20` | 目標とする利用可能 key 数。これを下回ったときのみ補充が発生。 |
| `MINT_BATCH` | いいえ | `5` | 1 ラウンドで発行する key の最大数。 |
| `TEND_INTERVAL_MS` | いいえ（Node/Docker のみ） | `1800000`（30 分） | Node 側の補充スケジュール間隔。Worker 側は `wrangler.toml` の Cron が決める（下記参照）。 |
| `CODE_TIMEOUT_MS` | いいえ | `120000`（120 秒） | 1 回の発行試行で認証コードを待つタイムアウト。 |
| `MINT_DELAY_MIN_MS` | いいえ | `2000` | 1 ラウンド内で発行試行の間に入れるランダム待機時間の下限（ミリ秒）。 |
| `MINT_DELAY_MAX_MS` | いいえ | `5000` | 1 ラウンド内で発行試行の間に入れるランダム待機時間の上限（ミリ秒）。 |
| `MAX_DOMAIN_ATTEMPTS` | いいえ | `8` | 1 回の発行試行で試す一時メールドメインの最大数。 |
| `REGISTRAR_TOKEN_NAME` | いいえ | `auto` | 発行された Agnes API key が Agnes 管理画面に表示される名前。 |
| `AGNES_PLATFORM_URL` | いいえ | `https://platform-backend.agnes-ai.com` | 登録・ログイン・key 発行に使う Agnes プラットフォームのバックエンド（ベンダーの公開エンドポイント）。 |
| `YYDS_BASE_URL` | いいえ | `https://maliapi.215.im` | YYDS Mail の API ベース URL（ベンダーの公開エンドポイント）。 |
| `YYDS_API_KEY` | チャネルが yyds の場合は必須 | 空 | YYDS Mail の API Key。 |
| `MOEMAIL_BASE_URL` | チャネルが moemail の場合は必須 | 空 | 自分でホストした MoeMail インスタンスのアドレス。デフォルトなし。 |
| `MOEMAIL_API_KEY` | チャネルが moemail の場合は必須 | 空 | その MoeMail インスタンスの API Key。 |

上表の変数はすべて `.env.example` に 1 行ずつ記載されており（多くの場合デフォルトで
十分なため、変更しなくて構いません）、どちらのデプロイ先でも読み込まれます。上記の
数値型変数はすべて正の整数である必要があり、そうでない場合ゲートウェイは起動を拒否します。

## 2 つのランタイムのスケジューリングの違い

### 誰がトリガーし、間隔はどこから来るか

| デプロイ先 | トリガー方式 | 間隔を決めるもの |
|----------|------------|----------------|
| Cloudflare Worker | `wrangler.toml` の `[triggers]` に設定した Cron（デフォルト `*/30 * * * *`、30 分ごと） | `wrangler.toml` の cron 式を編集 |
| Node / Docker | プロセス内タイマー | `TEND_INTERVAL_MS`（デフォルト `1800000` ミリ秒） |

どちらのランタイムも最終的には**同じ補充関数**を呼び出します。違うのは**誰が定刻に呼び出す
責任を持つか**、そして**トリガー間隔がどこから来るか**です:

| | トリガー | 間隔の出どころ | 変更した場合 |
|----|--------|--------------|------------|
| Node / Docker | プロセス内の自己再スケジュールタイマー | `TEND_INTERVAL_MS`（環境変数 > 保存された設定 > デフォルト `1800000`） | **次のラウンドから有効**（現在のラウンドは古い間隔のまま走り切る。デフォルトで最長 30 分）。**再起動は不要** |
| Cloudflare Worker | プラットフォームの Cron Trigger | `wrangler.toml` の `[triggers].crons` | **設定を変更しても反映されない**。`wrangler.toml` を編集して再デプロイする必要がある |

トリガー間隔以外の補充関連の設定項目（`TARGET_KEYS` / `MINT_BATCH` / チャネルの認証情報など）
は、両方のランタイムで本当にまったく同じです。

### Cloudflare Cron トリガーの壁時計時間の上限（パラメータ調整前に必読）

Worker にデプロイする場合、補充は Cron トリガーによって起動されます。パラメータを触る
前に本節を最後まで読んでください。

#### プラットフォームが課す 4 つの上限

| 制限項目 | 値 | 説明 |
|--------|----|----|
| 1 回の呼び出しの壁時計時間（wall-clock） | **15 分（900 秒）** | Cron トリガーの上限。達するとプラットフォームに中断されます。 |
| `ctx.waitUntil()` | **この上限を延長しません** | その猶予機構は HTTP リクエストにのみ適用され、Cron トリガーの呼び出しには適用されません。 |
| CPU 時間 | 30 秒 | 補充処理中の `await` によるネットワーク呼び出し（認証コードの送信・ポーリングなど）は CPU 時間に計上されないため、実質的なボトルネックにはなりません。 |
| リクエスト単位のタイムアウト | 15 秒 | レジストラーの通信経路上の**すべての** HTTP リクエストに付く固定値で、設定できません。 |

**リクエスト単位のタイムアウトは、以下 2 つの見積もりが成立する前提です**——これが無いと、
1 本のハングした接続だけで 1 ラウンドが無限に伸びます。

#### 1 ラウンドの所要時間、2 つの見積もり

| 見積もり | 式 | デフォルト値での結果 |
|--------|----|--------------------|
| **通常時の所要時間** | `MINT_BATCH × CODE_TIMEOUT_MS` ＋ 1 ラウンド内のランダム待機 | 600 ＋ 20 ≈ **約 600〜620 秒**。900 秒の壁時計上限に対して約 **30% の余裕** |
| **理論上の最悪ケース**（発行 1 回） | `CODE_TIMEOUT_MS + (1 + 3 × MAX_DOMAIN_ATTEMPTS + 3) × 15 秒` | 120 ＋ 420 = **540 秒**。`MINT_BATCH` を掛けると 900 秒を大きく超えます |
| `REGISTRAR_FALLBACK` を設定した場合 | 「最悪所要時間」× チャネル数（＝2） | 通常時の所要時間は変わりません |

- **通常時**とは、各リクエストが速やかに返り、最初のドメインもブロックされない場合です。
  認証コード待ちが支配的で、おおよそ `MINT_BATCH × CODE_TIMEOUT_MS` = 5 × 120 秒 =
  600 秒。ランダム待機は最大 4 回・1 回あたり最大 5 秒で約 20 秒です。
- **最悪ケースのリクエスト本数**の内訳はこうです。1 回の発行はコードのポーリングに加え、
  「ドメイン一覧 1 回＋試行するドメインごとに 3 回（メールボックス作成・コード送信・
  メールボックス削除）＋3 回（登録・ログイン・key 作成）」を発行します。つまり
  **デフォルト設定でも極端なケースでは壁時計上限に達し得ます**——これは意図的な割り切り
  です。key は発行され次第すぐ保存されるため、中断されてもそのラウンドが不完全になるだけ
  です。極端なケースまで壁時計内に収めたい場合は `MINT_BATCH` を 1〜2 にするか、
  `CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS` を小さくしてください。
- **フォールバックチャネルは最悪値だけを押し上げ、通常時の値は変えません。** 通常時は
  認証コードが届くのでフォールバックは起動しません。「認証コードが届かない」のような
  チャネルレベルの失敗のときだけ、同じ補充枠がもう一度 `CODE_TIMEOUT_MS` 待つことに
  なります。起動時の `TEND_INTERVAL_MS が 1 ラウンドの最悪所要時間を下回っています` と
  いう警告も、このモデル（`MINT_BATCH × CODE_TIMEOUT_MS × チャネル数`）に基づいています。

#### Worker は壁時計を使い切る前に自発的に切り上げます

**これは上の「最悪所要時間」の行はカバーしますが、「理論上の最悪」の行はカバーしません。**
1 回の発行を始める前に毎回「残りの壁時計でこの 1 回を最後まで走らせられるか」を判定し
（判定式は `CODE_TIMEOUT_MS × チャネル数` ＋ 試行間隔）、足りなければ**そもそも開始しま
せん**。ラウンドを早めに終了し、`registrar.round_budget_exhausted` という警告イベントを
記録します（「今回の壁時計予算では発行をもう 1 回完走できないため、早めに切り上げます」と
いう内容）。すでに発行済みの key はそのまま保存され、残りの枠は次のスケジュールに回されます。
1 回目の発行すら収まらない場合は別のイベント `registrar.round_budget_impossible`（レベルは
エラー）が記録されます。詳細は次の小節を参照してください。

重要なのは「途中で切られる」のではなく「開始しない」ことです。プラットフォームに中断され
ると、その時点で使用中だった一時メールボックスは削除されずに残ります（YYDS は約 24 時間後
に `expiresAt` で、MoeMail は 1 時間の TTL で失効）。したがって Worker では
**`MINT_BATCH` は 1 ラウンドの上限であって保証値ではありません**。そのラウンドが埋まらない
ことがあります。Node / Docker にはプラットフォームの壁時計上限がないため、**定期ラウンド**
ではこの機構は働かず、`MINT_BATCH` は全数使われます。

> ⚠️ **ただしパネルの「今すぐ補充」は例外で、両方のランタイムが同じラウンド予算を持ちます**。
> 1 回のクリックが最大どれだけ走るかはこのボタン自身の性質であってランタイムの性質ではない
> ため、Node / Docker でも手動補充は発行数が少なくなることがあります。残りは次の定期ラウンド
> が補います。

**⚠️ この予算は万能ではなく、残るケースがあります。** 判定式には支配的な項
`CODE_TIMEOUT_MS × チャネル数` しか入っておらず、15 秒のリクエスト単位タイムアウトや
403 バックオフは**意図的に含めていません**。含めると、上の「理論上の最悪」が元々 900 秒を
超えているため、1 回も開始できなくなります。予算は壁時計の 87% で、残る約 120 秒がその尾を
吸収する余裕です。

| どの層が遅いか | 予算でカバーできるか | 結果 |
|--------------|--------------------|----|
| **上流が認証コードを届けてこないだけ**（本節で最も一般的な遅さ） | **完全にカバーされます** | ラウンドを早めに終了し、残りの枠は次のスケジュールへ |
| **ほぼすべての HTTP リクエストが 15 秒フルにハングする**（病的なケース） | 1 回の試行が余裕を超えることがあります | プラットフォームに中断され、その一時メールボックスが残ります |

2 行目が心配なら、上の「理論上の最悪」の式で計算し、`MINT_BATCH` を 1〜2 にするか
`CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS` を小さくしてください。

#### 2 つのログ：上限超過はイベント名で grep

**`CODE_TIMEOUT_MS` を大きくしすぎないでください。** `CODE_TIMEOUT_MS × チャネル数` が
1 ラウンドの予算（壁時計の 87%）を超えると、Worker では**試行を 1 回も開始できず**、補充は
毎ラウンド何も生み出しません。ログは 2 か所に出ます。**イベント名**で grep するのが確実です
（下の「トラブルシューティング」参照。文言は表現の調整で変わり得ますし、読んでいる言語に
翻訳されているとも限りませんが、イベント名は変わりません）。

- **起動時**は**警告**（`console.warn`）で、イベント名は
  `registrar.attempt_exceeds_worker_budget`（`grep 'registrar.attempt_exceeds_worker_budget'`）。
  出力はおおよそ次の形です:
  `[registrar] registrar.attempt_exceeds_worker_budget CODE_TIMEOUT_MS×チャネル数が
  Worker の 1 ラウンド壁時計予算を超えています codeTimeoutMs=... chainLength=...
  worstAttemptMs=... workerRoundBudgetMs=...`。
  これは**ゲートウェイの起動を止めません**——「認証情報が不足すると起動時にエラーとなり
  起動しない」ケースとは異なります。Node / Docker にはプラットフォームの壁時計上限がなく
  同じ設定でも完全に正当なので、両方のランタイムでこの警告は出ますが、実際に影響を受ける
  のは Worker だけです。
- **Worker の補充ラウンドごと**（1 回目の発行すら開始できない場合）に**エラー**
  （`console.error`）が出ます。イベント名は `registrar.round_budget_impossible`
  （`grep 'registrar.round_budget_impossible'`）。出力はおおよそ次の形です:
  `[registrar] registrar.round_budget_impossible 1 回の発行の最悪所要時間がすでに
  このラウンドの壁時計予算を超えており、1 回も開始できません
  worstAttemptMs=... roundBudgetMs=...`。
  毎ラウンド出るので、一時的な事象ではなく継続状態だと判断できます。

**`MINT_BATCH`・`CODE_TIMEOUT_MS`・`MAX_DOMAIN_ATTEMPTS` を大きくする前に、上記 2 つの式で
必ず計算してください。** 上限に達すると、その回の Cron 呼び出しはプラットフォームによって
中断されます。中断されても、すでに発行された key が失われることはありません——key は発行
され次第即座にストレージへ書き込まれるため、中断されたラウンドは単に不完全なだけであり、
次のスケジュールで続きから補充が試みられます。

## 不足数の数え方（どの key が `TARGET_KEYS` の枠を占めるか）

### 4 つの key の状態と枠の占有

不足数 = `TARGET_KEYS` − **除外されていない key の数**。判定基準はただ 1 つ、
**`evicted` が偽なら枠を占める**です。

| key の状態 | `TARGET_KEYS` の枠を占めるか | 上流に使えるか |
|----------|----------------------------|--------------|
| 新規 / 利用可能 | はい | はい |
| **クールダウン中**（レート制限、連続失敗） | **はい** | いいえ |
| **管理者が無効化** | **はい** | いいえ |
| 除外済み（401/403、認証情報が失効） | いいえ | いいえ |

### なぜクールダウン中の key も枠を占めるのか

**「クールダウン中も枠を占める」のは意図的です。** クールダウンは**自分で戻ってくる**状態
であり、それを不足として新規発行すると、発行されたアカウントのほうは**自分では消えません**
——一度の一時障害が恒久的なコストに変わります。実測（`TARGET_KEYS=3`）：クールダウンを枠に
数えない場合、プール全体がレート制限された 1 ラウンドで 3 個追加され ⇒ プールは 6；
クールダウンが明けると不足数は負になり回収もされないため ⇒ **6 のまま固定**。次の嵐で 9、
その次で 12 と線形に増え、そのすべてが実際の Agnes 登録 1 回と実際に消費された一時メール
ボックス 1 個です。

**コストは明記します**：プール全体がクールダウン中のとき、レジストラーは代替を**発行しません**。
クールダウンの間ゲートウェイは `503` を返し続けます（最長で `COOLDOWN_PAYMENT_MS` /
`COOLDOWN_STRIKE_MS` の 1 回分）。すぐ復旧したい場合は、補充に期待するのではなく、管理画面で
該当 key に「クールダウン解除」を実行してください。

## 管理画面の「今すぐ補充」

管理画面のあのボタン（`POST /admin/api/registrar/tend`）です。`202` は**開始した**という意味で、
補充はレスポンスのあとも走り続けます。結果は「補充履歴」欄で確認してください（`trigger` は
`manual` と表示されます）。

### 4 つのガードレール

**4 つのガードレール**があり、どれか 1 つでも満たさなければ起動しません：

| ガードレール | 満たさないとき | 何を防ぐか |
|------------|--------------|----------|
| 同一プロセス / 同一 isolate の実行中ガード | `409 tend_in_flight` | 定期ラウンドとボタンの衝突、同一レプリカ上の同時 2 クリック |
| ストレージレベルの短いロック（`registrar_tend_lock`） | `409 locked` | **レプリカをまたぐ**重複（ボリューム共有の複数コンテナ、Worker の 2 つの isolate） |
| 手動補充どうしは最低 10 分あける | `429 manual_cooldown` | 連打による一時メールボックス枠の浪費 |
| 1 日あたり最大 **24** 回 | `429 write_budget_exhausted` | 連打による**ストレージ書き込みクォータ**の浪費（計算は [DEPLOY.md](DEPLOY.md) の「クォータ計算」） |

`429` のボディには `remaining`（今日の残り回数）、`resetAt`（UTC 0 時に回復）、`retryAfterMs`
が入ります。**`202` のボディにも `remaining` が入ります**——ボタンが押せなくなってから伝える
のではなく、残り回数を最初から正直に表示するためです。レジストラーが無効なときは
`409 registrar_disabled` を返します。

### 正直な限定と残存リスク

⚠️ **正直な限定。「並行性は解決済み」と読まないでください。** KV は結果整合であり、この
ストレージロックは**ベストエフォートであって排他プリミティブではありません**。防げるのは
「前のラウンドが明らかにまだ走っている」という最も一般的な重複であり、同じミリ秒に発行された
2 つのクリックは両方ともロックを取り得ます。ガードキーと補充履歴も read-modify-write なので、
並行ウィンドウでは更新が失われ得ます——上限は「ゲートが最大（並行数 − 1）回多く通す、
補充履歴が最大（並行数 − 1）行欠ける」です。

⚠️ **残存リスク**：手動補充は Worker の Cron と**同じラウンド単位のウォールクロック予算
（780 秒）**を持ちます。その役割は「明らかに完走できない試行を開始しない」ことであり、
**漏れをなくすものではなく、確率を下げるだけ**です——プラットフォームは予算ウィンドウ内でも
呼び出しを中断し得て、その瞬間に発行中だった一時メールボックスは削除されません。
定期ラウンドとは異なる点に注意してください：**Node/Docker の定期ラウンドはこの予算を持たず、
手動補充は持ちます**。そのため同じ設定でも手動のラウンドは定期ラウンドより発行数が少なくなる
ことがあり、残った枠は次の定期ラウンドに回ります。

### この 3 つのキーは自然には消えません

`registrar_tend_lock`、`registrar_manual_guard`、`tend:history` の 3 つは**いずれも TTL を
持ちません**。名前は固定リテラルで個数は常に 1、古い値はすべて**値の比較**で判定されるため
（期限切れのロックは誰も止めず、昨日のカウントは数えられません）、残っていても無害です。

**コストは明記します**：レジストラーを恒久的に無効化する場合や、デプロイを削除して KV 名前
空間だけ残す場合、これらは自動では消えません。掃除するには手動でキーを削除してください：

- Worker：`wrangler kv key delete --binding=POOL registrar_manual_guard`（3 つそれぞれ 1 回）
- Node / Docker：`DATA_DIR/store.json` を編集し、その 3 つのトップレベルフィールドを削除

**`tend:history` は通常は残すべきです**：事後分析で最も見たいものであり、「レジストラーを
止めた N 日後に補充履歴がまるごと消える」のは最悪のタイミングです——運用者は多くの場合、
何か起きた**からこそ**レジストラーを止めているのです。

## 発行された key が転送経路で使えるようになるまで

**最大で `POOL_CACHE_TTL_MS` 1 回分（既定 60 秒）であり、「次のリクエストから」ではありません。**

補充と転送は互いに独立した 2 つの key プールリポジトリインスタンスを使います。補充側は毎ラウンド
実際にストレージを読みます（現在の本当の利用可能数を見る必要があり、さもないと重複して発行し
メールボックスのクォータを無駄に消費します）。転送側は isolate / プロセス単位のスナップショットを
保持します。それぞれが自分のキャッシュを持つため、補充が key を書き込んだあと、転送経路は
**自分のスナップショット**が期限切れになって初めてそれを見ます。Worker ではアクティブな isolate
ごとにそれぞれの TTL がかかります。

**プールが空になったときに最も誤解されやすい点です**: ログには既に `[registrar] … minted=1` と
出ているのに、ゲートウェイは TTL 1 回分のあいだ `503 pool_empty` を返し続けます。補充が効いて
いないわけではないので、`POOL_CACHE_TTL_MS` を 1 回分待ってください。短くしたい場合はこの値を
小さくします（コストは [DEPLOY.md](DEPLOY.md) の「クォータの見積もり」を参照）。

## なぜ key を順番に発行し、並行実行しないのか

補充は 1 ラウンド内で key を**順番に**発行し、試行ごとにランダムな待機時間を挟みます。
複数の発行リクエストを並行して発火させることはありません。これはパフォーマンス上の
トレードオフではなく、機能上の制約です。並行実行すると、YYDS Mail のメールボックス作
成レート制限（短時間に約 10 回を超えて作成すると `403` を返す）と、Agnes 自身の登録リ
スク制御の両方に同時に抵触してしまいます。順番実行とランダムな待機時間は、レジストラー
が動作し続けるための前提条件であり、並行化で「最適化」すべきものではありません。

## プライバシーについて

登録処理中に生成されるメールアドレス、アカウント、パスワードはメモリ上に一時的に存在
するだけで、**使い終わったら破棄され、永続化されることはありません**。ストレージに残
るのは発行された API key のレコードのみです。一時メールボックスは、発行の成否にかかわ
らず、試行終了後に削除されます。

## トラブルシューティング

### 起動とログの約束

- **有効化時に認証情報が不足していると、起動時にエラーとなり、不足している項目が明示
  されます。** レジストラーはフェイルクローズ方針を採用しており、認証情報の不足を静
  かに見過ごすことはなく、ゲートウェイを明確に失敗させることで問題を発見しやすくして
  います。
- 補充処理中のログには一貫して `[registrar]` というプレフィックスが付くため、これで
  フィルタリングして状況を確認できます。各ログ行の 2 番目のフィールドは安定した
  機械可読の**イベント名**（例: `registrar.round_budget_impossible`）です。イベント名で
  grep する方が、人間向けの文言で grep するより確実です——文言は表現の調整で変わり得ま
  すが、イベント名はこのログの唯一の安定した対外契約であり、変わりません。
### `reasons=` の失敗理由を読む

- **1 ラウンドで発行しきれなかった枠があると、終了ログに `reasons=` 付きの警告が 1 行
  追加されます**（例：`reasons=yyds:register_failed×3 moemail:code_timeout×1`）。まずは
  この行でどの層の障害かを判断してください。`code_timeout` = このチャネルが Agnes から
  のメールを受け取れていない（ドメインの MX／転送ルール）。
  `register_failed` / `login_failed` / `key_failed` = Agnes 側の登録経路が変わった。
  `provider_error` = メールボックスサービス自体（認証情報、アクティブメールボックスの
  上限、サービス障害）。`provider_missing` = 内部の結線エラー。通常の設定では発生しません
  （認証情報の不足は起動時にエラーになるため、ここまで到達しません）。
- **`reasons=` に `key_suspicious` が出た場合**：上流から返ってきた key の中身に印字不可能な
  文字か空白が含まれています。**そのラウンドは実際に発行しています**（Agnes 側のアカウントは
  本当に作られ、一時メールボックスも本当に消費されました）。したがってその key は
  **そのままプールに保存されます**——ここで拒否することは、二度と取り戻せない資格情報を
  破棄することだからです。ただし選択されるたびに転送が失敗する可能性が高いので、管理画面で
  無効化するか削除してください。同時に `registrar.minted_key_suspicious` の error イベントが
  出ます（記録するのはチャネルと長さだけで、**平文は記録しません**）。
### あるチャネルが失敗し続けるとき

- 特定のチャネルで登録が失敗し続ける場合（たとえば Agnes が認証コードや CAPTCHA のポ
  リシーを強化した場合など）、これはコードレベルでは回避できない上流側の変化です。
  レジストラーを無効化し、代わりに key を手動でインポートすることもできます
  （[DEPLOY.md](DEPLOY.md) を参照）。
