# レジストラー（自動プール補充）

本ページではレジストラーを扱います。何をするのか、2 つのメールボックスチャネルをどう選ぶのか、どんな設定項目があるのか、動かしたあとログをどう読みトラブルシューティングするのか、です。

> **デフォルトで無効です。** `REGISTRAR_ENABLED` のデフォルトは `false` で、導入しただけ
> では一切アカウント登録を開始しません。明示的に `true` に設定した場合のみ有効になり
> ます。

## これは何か

レジストラーはオプション機能です。key プール内の利用可能な key 数が `TARGET_KEYS` を
下回ると、新しい Agnes アカウントを自動登録し、ログインし、API key を発行してプールに
書き込みます。登録には Agnes から届く認証コードの受信が必要なため、下記のメールボック
スチャネルのいずれかに依存します。

> [!WARNING]
> **コンプライアンスに関する注意**
>
> 大量アカウント登録は Agnes の利用規約と緊張関係にあります。レジストラーを有効にする
> かどうか、どの程度の頻度で使うかは、運用者自身が判断し、責任を負うべき事項です——
> 本プロジェクトはこの判断を代行しません。

## 2 つのメールボックスチャネル：選び方

レジストラーは認証コードを受信するために 2 つのメールボックスチャネルをサポートしま
す。

### 2 つのチャネルの比較

| | YYDS Mail | MoeMail |
|----|---------|-------|
| 性質 | サードパーティの一時メールボックスサービス | 自分でホストする一時メールボックスサービス |
| API ベース URL | デフォルトあり（`YYDS_BASE_URL`、公開 API エンドポイント） | デフォルトなし（`MOEMAIL_BASE_URL`）、自分で立てたインスタンスのアドレスを入力 |
| 認証情報の取得 | サービスに API Key を申請（`YYDS_API_KEY`） | 自分のインスタンス内で API Key を発行（`MOEMAIL_API_KEY`） |
| アドレスの書き方 | サービスのルートアドレス（`/v1` のような API パスのプレフィックスは付けない） | インスタンスのルートアドレス（同様にプレフィックスは付けない） |

最後の行は単独で触れておきます。ゲートウェイ自身が公開する `AGNES_BASE_URL` には `/v1` が
**付き**ますが、この 2 つは別物であり、片方をそのまま写すのが最も多い間違いです。`…/v1` を
指定するとレジストラーは `…/v1/v1/domains` を組み立て、上流は 404 を返します。この種の失敗は
**実際にリクエストしたアドレス**をイベントに残すようになりました（アドレス内のユーザー名／
パスワード、クエリ文字列、フラグメントはプレースホルダーに置き換えられます）。イベントを
一目見れば、この落とし穴だと分かります。

### どちらのチャネルを使うか

> [!IMPORTANT]
> **2 つのチャネルはいずれか一方を選びます。主／予備という関係はなく、自動切り替えも
> ありません。** 2 つのチャネルは完全に対等であり、本プロジェクトはどちらも選ばず、
> どちらも推奨しません。

`REGISTRAR_CHANNEL` にデフォルト値はなく、レジストラーを有効にする際は `yyds` か
`moemail` を明示的に指定する必要があります。選んだほうが認証コードを受け取り、
もう一方は**入力しても使われません**。ただし先に設定しておけば、いつでも切り替えられます。

> [!WARNING]
> **選んだチャネルが失敗しても、レジストラーがもう一方に切り替えることはありません。**
> 認証コードが届かない（ドメインの MX レコード失効、メール転送ルールの削除——API はすべて
> 2xx を返すのにメールだけが永遠に届かない）状態は「このチャネルは今 key を生み出せない」
> であり、あなた自身が切り替えるまでそのラウンド、場合によってはその日ずっと発行数が
> ゼロになります。詳しい挙動は下の「チャネルが失敗したあと何が起きるか」を参照してください。

#### 旧名称はどうなるか

> この項目はかつて `REGISTRAR_PRIMARY` と呼ばれ、隣に `REGISTRAR_FALLBACK` が
> ありました。旧名称は**互換エイリアスとして今後も残ります**（新しい名前より優先度は低く、
> 使われている場合はパネル上部に通知が出ます）。旧の予備側の変数は**経路選択に関与しなく
> なりました**が、パネルで「このチャネルは破棄された」と名指しで伝えるためだけに一度だけ
> 読まれます。どちらの旧名称もアップグレード中のデプロイを止めることはありません。

### そのチャネルの選び方

判断基準：レジストラーは「ドメインを切り替える」ことで Agnes による使い捨てメールボッ
クスドメインのブロックを回避しています。利用可能なドメインが多いほど、レジストラーは
長く動作し続けられます。両サービスでそれぞれ何個の利用可能ドメインを持っているか確認
し、多い方のほうが長く使えます——これはどちらのサービスかとは無関係で、
あなた自身のアカウントや自己ホスト環境の設定次第です。

## 組み込みの認証情報はゼロ——自分で用意してください

このリポジトリには実際の鍵、アカウント、プライベートドメインは一切含まれていません。
レジストラーを有効にする前に、以下を自分で用意する必要があります。

### チャネルごとに用意するもの

- **YYDS Mail を使う場合**：サービスに API Key を申請し、`YYDS_API_KEY` に設定します
  （`YYDS_BASE_URL` にはすでにデフォルト値があり、通常変更不要です）。
- **MoeMail を使う場合**：MoeMail インスタンスを自分でホストし、そのアクセスアドレス
  を `MOEMAIL_BASE_URL` に、インスタンス内で発行した API Key を `MOEMAIL_API_KEY` に
  設定します（どちらもデフォルト値がないため、必ず明示的に設定してください）。

### 最低限どこまで用意すればよいか

少なくとも `REGISTRAR_CHANNEL` が指すチャネルの認証情報を用意してください。
もう一方のチャネルの認証情報は、入力しても空のままでも構いません。レジストラーが起動
するかどうかには影響しません。入力しておくと、そのチャネルの「設定済み」表示と「接続
テスト」ボタンがパネルで使えるようになり、切り替える前に比較できます。

## 設定項目

```env
# ── スイッチとチャネル ────────────────────────────────────────────
# 全体スイッチ。true のときだけレジストラーが有効になります。（任意、既定 false）
REGISTRAR_ENABLED=false
# レジストラーが使うチャネル。yyds か moemail。2 つのうち 1 つを選びます。既定値なし。
#（有効化時は必須）旧名称 REGISTRAR_CHANNEL の前身 REGISTRAR_PRIMARY は互換エイリアス
# として今後も残り、旧の予備側の変数は経路選択に関与しません。
REGISTRAR_CHANNEL=

# ── 補充のペース ──────────────────────────────────────────────────
# 目標とする利用可能 key 数。これを下回ると補充が走ります。（任意、既定 20）
TARGET_KEYS=20
# 1 ラウンドで発行する key の上限。（任意、既定 5）
MINT_BATCH=5
# Node 側の補充スケジュール間隔（ミリ秒）。Worker 側は wrangler.toml の Cron が
# 決めます（後述）。（任意、既定 1800000＝30 分、Node / Docker のみ参照）
TEND_INTERVAL_MS=1800000
# 発行 1 回あたりの認証コード待ちタイムアウト（ミリ秒）。（任意、既定 120000＝120 秒）
CODE_TIMEOUT_MS=120000
# 1 ラウンド内の発行間ランダム待機の下限 / 上限（ミリ秒）。（任意、既定 60000 / 90000）
# 下限は実測値です: 同じ送信元から 60 秒以上あけると連続で成功しましたが、間隔なしで
# 連射すると 3 回目で上流手前のレート制限に当たり、罰則期間は十数分ありました。
# 上限はジッタの余裕であって実測値ではありません。
MINT_DELAY_MIN_MS=60000
MINT_DELAY_MAX_MS=90000
# 発行 1 回で試す一時メールボックスドメインの最大数。（任意、既定 1）
# レジストラーは「上流がこのドメインを受け入れるか」を記憶して再利用するため、
# 定常状態では 1 回の発行成功につきコード送信リクエストは 1 回だけです。
# 大きくするとラウンドごとのレート制限枠の消費が同じだけ増えます（実測枠は 1 期間あたり 4~6 回程度）。
MAX_DOMAIN_ATTEMPTS=1
# 発行した Agnes API key が Agnes 管理画面に表示される名前。（任意、既定 auto）
REGISTRAR_TOKEN_NAME=auto

# ── 上流とチャネルの認証情報 ──────────────────────────────────────
# 登録・ログイン・key 発行に使う Agnes プラットフォームのバックエンド
# （ベンダーの公開エンドポイント）。（任意）
AGNES_PLATFORM_URL=https://platform-backend.agnes-ai.com
# YYDS Mail の API ベース URL（ベンダーの公開エンドポイント）と API Key。
# （ベース URL は任意。Key はチャネルが yyds のとき必須。本リポジトリは
#   実際の認証情報を一切同梱しません）
YYDS_BASE_URL=https://maliapi.215.im
YYDS_API_KEY=
# 自分でホストした MoeMail インスタンスのアドレスとその API Key。どちらも既定値なし。
# （チャネルが moemail のとき必須）
MOEMAIL_BASE_URL=
MOEMAIL_API_KEY=
```

上のブロックの変数はすべて `.env.example` に 1 行ずつ記載されており（多くの場合デフォルトで
十分なため、変更しなくて構いません）、どちらのデプロイ先でも読み込まれます。上記の
数値型変数はすべて正の整数である必要があり、そうでない場合ゲートウェイは起動を拒否します。

## 2 つのランタイムのスケジューリングの違い

### 誰がトリガーし、間隔はどこから来るか

| デプロイ先 | トリガー方式 | 間隔を決めるもの |
|----------|------------|----------------|
| Cloudflare Worker | `wrangler.toml` の `[triggers]` に設定した Cron（デフォルト `*/30 * * * *`、30 分ごと） | `wrangler.toml` の cron 式を編集 |
| Node / Docker | プロセス内タイマー | `TEND_INTERVAL_MS`（デフォルト `1800000` ミリ秒） |

2 つの設定はそれぞれ次のような形です:

```toml
# wrangler.toml —— Worker 形態のトリガー間隔はここだけで決まります
[triggers]
crons = ["*/30 * * * *"]
```

```env
# .env —— Node / Docker 形態のトリガー間隔（ミリ秒）
TEND_INTERVAL_MS=1800000
```

どちらのランタイムも最終的には**同じ補充関数**を呼び出します。違うのは**誰が定刻に呼び出す
責任を持つか**、そして**トリガー間隔がどこから来るか**です:

| | トリガー | 間隔の出どころ | 変更した場合 |
|----|--------|--------------|------------|
| Node / Docker | プロセス内の自己再スケジュールタイマー | `TEND_INTERVAL_MS`（環境変数 > 保存された設定 > デフォルト `1800000`） | **次のラウンドから有効**（現在のラウンドは古い間隔のまま走り切る。デフォルトで最長 30 分）。**再起動は不要** |
| Cloudflare Worker | プラットフォームの Cron Trigger | `wrangler.toml` の `[triggers].crons` | **設定を変更しても反映されない**。`wrangler.toml` を編集して再デプロイする必要がある |

トリガー間隔以外の補充関連の設定項目（`TARGET_KEYS` / `MINT_BATCH` / チャネルの認証情報など）
は、両方のランタイムで本当にまったく同じです。

### Cloudflare Cron トリガーの壁時計時間の上限（パラメータ調整前に必読）

Worker にデプロイする場合、補充は Cron トリガーによって起動されます。パラメータを触る
前に本節を最後まで読んでください。

#### プラットフォームが課す 4 つの上限

| 制限項目 | 値 | 説明 |
|--------|----|----|
| 1 回の呼び出しの壁時計時間（wall-clock） | **15 分（900 秒）** | Cron トリガーの上限。達するとプラットフォームに中断されます。 |
| `ctx.waitUntil()` | **この上限を延長しません** | その猶予機構は HTTP リクエストにのみ適用され、Cron トリガーの呼び出しには適用されません。 |
| CPU 時間 | 30 秒 | 補充処理中の `await` によるネットワーク呼び出し（認証コードの送信・ポーリングなど）は CPU 時間に計上されないため、実質的なボトルネックにはなりません。 |
| リクエスト単位のタイムアウト | 15 秒 | レジストラーの通信経路上の**すべての** HTTP リクエストに付く固定値で、設定できません。 |

**リクエスト単位のタイムアウトは、以下 2 つの見積もりが成立する前提です**——これが無いと、
1 本のハングした接続だけで 1 ラウンドが無限に伸びます。

#### 1 ラウンドの所要時間、2 つの見積もり

| 見積もり | 式 | デフォルト値での結果 |
|--------|----|--------------------|
| **通常時の所要時間** | `MINT_BATCH × CODE_TIMEOUT_MS` ＋ `(MINT_BATCH − 1) × MINT_DELAY_MAX_MS` | 600 ＋ 360 = **960 秒**。**すでに 900 秒の壁時計上限を超えています**（下の「Worker は壁時計を使い切る前に自発的に切り上げます」を参照） |
| **理論上の最悪ケース**（発行 1 回） | `CODE_TIMEOUT_MS + (3 × MAX_DOMAIN_ATTEMPTS + 3) × 15 秒 + (MAX_DOMAIN_ATTEMPTS − 1) × MINT_DELAY_MAX_MS` | 120 ＋ 90 = **210 秒**（既定値 1） |

- **通常時**とは各リクエストが速やかに返る場合です。`MINT_BATCH × CODE_TIMEOUT_MS` =
  5 × 120 秒 = 600 秒に、最大 90 秒の待機 4 回分 = 360 秒が加わります。
- **この待機の項は今は無視できません。** `MINT_DELAY_MAX_MS` が 5 秒から 90 秒に
  なり、20 秒から 360 秒に増え、ラウンド最悪は 960 秒 > 900 秒です。
  **新しい欠陥ではありません**——下のラウンド予算がこのために存在します。
- **最悪ケースのリクエスト本数**の内訳はこうです。コードのポーリングに加え、
  「試行するドメインごとに 3 回＋3 回（登録・ログイン・key 作成）」。ドメイン一覧は
  **ラウンド単位**に移りました（1 ラウンド 1 回）。壁時計内に収めたい場合は
  `MINT_BATCH` を 1〜2 にするか、`CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS` を小さくしてください。
- **ここにはかつて「チャネル数」という係数がありました。** 2 つのチャネルは以前は主と
  予備の関係で、「認証コードが届かない」ときは切り替えて再試行するため、同じ補充枠が
  両方のチャネルで `CODE_TIMEOUT_MS` を待ち切る必要がありました。いずれか一方を選ぶ
  方式になった今、2 回目の待機はなく、この係数はまるごと消えました。起動時の
  `TEND_INTERVAL_MS が 1 ラウンドの最悪所要時間を下回っています` という警告も、
  このモデル（`MINT_BATCH × CODE_TIMEOUT_MS + (MINT_BATCH − 1) × MINT_DELAY_MAX_MS`）に基づいています。

#### Worker は壁時計を使い切る前に自発的に切り上げます

**これは上の「最悪所要時間」の行はカバーしますが、「理論上の最悪」の行はカバーしません。**
1 回の発行を始める前に毎回「残りの壁時計でこの 1 回を最後まで走らせられるか」を判定し
（判定式は `CODE_TIMEOUT_MS` ＋ 試行間隔）、足りなければ**そもそも開始しま
せん**。ラウンドを早めに終了し、`registrar.round_budget_exhausted` という警告イベントを
記録します（「今回の壁時計予算では発行をもう 1 回完走できないため、早めに切り上げます」と
いう内容）。すでに発行済みの key はそのまま保存され、残りの枠は次のスケジュールに回されます。
1 回目の発行すら収まらない場合は別のイベント `registrar.round_budget_impossible`（レベルは
エラー）が記録されます。詳細は次の小節を参照してください。

重要なのは「途中で切られる」のではなく「開始しない」ことです。プラットフォームに中断され
ると、その時点で使用中だった一時メールボックスは削除されずに残ります（YYDS は約 24 時間後
に `expiresAt` で、MoeMail は 1 時間の TTL で失効）。したがって Worker では
**`MINT_BATCH` は 1 ラウンドの上限であって保証値ではありません**。そのラウンドが埋まらない
ことがあります。Node / Docker にはプラットフォームの壁時計上限がないため、**定期ラウンド**
ではこの機構は働かず、`MINT_BATCH` は全数使われます。

> [!IMPORTANT]
> **ただしパネルの「今すぐ補充」は例外で、両方のランタイムが同じラウンド予算を持ちます**。
> 1 回のクリックが最大どれだけ走るかはこのボタン自身の性質であってランタイムの性質ではない
> からです。持つのは**手動用の一族**——予算 70 秒、発行は最大 1 本——で、定期ラウンドの
> 780 秒とは別勘定です。残りの枠は次の定期ラウンドが補います。

> [!WARNING]
> **この予算は万能ではなく、残るケースがあります。** 判定式は
> `CODE_TIMEOUT_MS + (MAX_DOMAIN_ATTEMPTS − 1) × MINT_DELAY_MAX_MS` で、15 秒のリクエスト
> 単位タイムアウトは**意図的に含めていません**。含めると 1 回も開始できなくなります。
> 予算は壁時計の 87% で、残る約 120 秒がその尾を吸収する余裕です。
>
> **この段落はかつて「403 バックオフ」に触れていましたが、それは死んだ分岐を指していました。**
> レート制限に当たった場合は**その場でラウンド全体を終了し、ラウンドをまたぐバックオフ期間を
> 記録します**。「少し待ってから叩き続ける」という動作はもうありません（下の
> 「上流にレート制限されたときに起きること」を参照）。

| どの層が遅いか | 予算でカバーできるか | 結果 |
|--------------|--------------------|----|
| **上流が認証コードを届けてこないだけ**（本節で最も一般的な遅さ） | **完全にカバーされます** | ラウンドを早めに終了し、残りの枠は次のスケジュールへ |
| **ほぼすべての HTTP リクエストが 15 秒フルにハングする**（病的なケース） | 1 回の試行が余裕を超えることがあります | プラットフォームに中断され、その一時メールボックスが残ります |

2 行目が心配なら、上の「理論上の最悪」の式で計算し、`MINT_BATCH` を 1〜2 にするか
`CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS` を小さくしてください。

#### 2 つのログ：上限超過はイベント名で grep

**`CODE_TIMEOUT_MS` を大きくしすぎないでください。** `CODE_TIMEOUT_MS` が
1 ラウンドの予算（壁時計の 87%）を超えると、Worker では**試行を 1 回も開始できず**、補充は
毎ラウンド何も生み出しません。ログは 2 か所に出ます。**イベント名**で grep するのが確実です
（下の「トラブルシューティング」参照。文言は表現の調整で変わり得ますし、読んでいる言語に
翻訳されているとも限りませんが、イベント名は変わりません）。

下の 2 つのフェンスはゲートウェイが**そのまま**出力する原文です。`msg` はソースに簡体字中国語で
ハードコードされており、**このページの言語には翻訳されません**。1 件のログは常に**1 行**です
——`src/adapters/logger-console.ts` が改行を空白に潰しているためで、続き行には `[registrar]`
接頭辞が付かず失われてしまうからです。したがって grep はイベント名で行い、このページの訳文では
行わないでください。

**① 起動時**は**警告**（`console.warn`）で、イベント名は
`registrar.attempt_exceeds_worker_budget`（`grep 'registrar.attempt_exceeds_worker_budget'`）。
出力はおおよそ次の形です:

```text
[registrar] registrar.attempt_exceeds_worker_budget CODE_TIMEOUT_MS 超过 Worker 单轮墙钟预算：Cloudflare Worker 形态下补池会一把 key 都铸不出来（每轮 attempted=0），请调小 CODE_TIMEOUT_MS。Node/Docker 的定时轮没有平台墙钟上限、不受此限制，但面板的「立即补池」在两种运行时上都带同一份轮级预算，Node/Docker 上同样铸不出来。 codeTimeoutMs=... worstAttemptMs=... workerRoundBudgetMs=...
```

これは**ゲートウェイの起動を止めません**——「認証情報が不足すると起動時にエラーとなり
起動しない」ケースとは異なります。Node / Docker にはプラットフォームの壁時計上限がなく
同じ設定でも完全に正当なので、両方のランタイムでこの警告は出ますが、実際に影響を受けるのは
Worker だけです。

**② Worker の補充ラウンドごと**（1 回目の発行すら開始できない場合）に**エラー**
（`console.error`）が出ます。イベント名は `registrar.round_budget_impossible`
（`grep 'registrar.round_budget_impossible'`）。出力はおおよそ次の形です:

```text
[registrar] registrar.round_budget_impossible 单次铸 key 的最坏耗时已超过本轮墙钟预算，一次尝试都无法开始，补池将持续零产出——这是配置问题不是瞬时状况，请调小 CODE_TIMEOUT_MS worstAttemptMs=... roundBudgetMs=...
```

毎ラウンド出るので、一時的な事象ではなく継続状態だと判断できます。

**`MINT_BATCH`・`CODE_TIMEOUT_MS`・`MAX_DOMAIN_ATTEMPTS` を大きくする前に、上記 2 つの式で
必ず計算してください。** 上限に達すると、その回の Cron 呼び出しはプラットフォームによって
中断されます。中断されても、すでに発行された key が失われることはありません——key は発行
され次第即座にストレージへ書き込まれるため、中断されたラウンドは単に不完全なだけであり、
次のスケジュールで続きから補充が試みられます。

## 不足数の数え方（どの key が `TARGET_KEYS` の枠を占めるか）

### 4 つの key の状態と枠の占有

不足数 = `TARGET_KEYS` − **除外されていない key の数**。判定基準はただ 1 つ、
**`evicted` が偽なら枠を占める**です。

| key の状態 | `TARGET_KEYS` の枠を占めるか | 上流に使えるか |
|----------|----------------------------|--------------|
| 新規 / 利用可能 | はい | はい |
| **クールダウン中**（レート制限、連続失敗） | **はい** | いいえ |
| **管理者が無効化** | **はい** | いいえ |
| 除外済み（401/403、認証情報が失効） | いいえ | いいえ |

### なぜクールダウン中の key も枠を占めるのか

**「クールダウン中も枠を占める」のは意図的です。** クールダウンは**自分で戻ってくる**状態
であり、それを不足として新規発行すると、発行されたアカウントのほうは**自分では消えません**
——一度の一時障害が恒久的なコストに変わります。実測（`TARGET_KEYS=3`）：クールダウンを枠に
数えない場合、プール全体がレート制限された 1 ラウンドで 3 個追加され ⇒ プールは 6；
クールダウンが明けると不足数は負になり回収もされないため ⇒ **6 のまま固定**。次の嵐で 9、
その次で 12 と線形に増え、そのすべてが実際の Agnes 登録 1 回と実際に消費された一時メール
ボックス 1 個です。

**コストは明記します**：プール全体がクールダウン中のとき、レジストラーは代替を**発行しません**。
クールダウンの間ゲートウェイは `503` を返し続けます（最長で `COOLDOWN_PAYMENT_MS` /
`COOLDOWN_STRIKE_MS` の 1 回分）。すぐ復旧したい場合は、補充に期待するのではなく、管理画面で
該当 key に「クールダウン解除」を実行してください。

## 管理画面の「今すぐ補充」

管理画面のあのボタン（`POST /admin/api/registrar/tend`）です。**このボタンは 1 巡が走り
終わるのを待ってから `200` を返します**（最長で約 2 分）。レスポンスの `outcome` がその
ラウンドの結末で、「補充履歴」欄にも残ります（`trigger` は `manual` と表示されます）。

`outcome` は三つに分かれ、**同じ「失敗」として読んではいけません**——対処がまったく
違います。`done` は走り切ったもので、そのラウンドの `minted` / `attempted` / `failures`
を伴います。`skipped` は上流へのリクエストを 1 本も送らなかったもの（クリックのあとに
レジストラーが無効化された、あるいはこの設定を読み込めなくなった）。`crashed` は 1 巡が
例外で中断したもので、上流側では**一時メールボックスが既に作られている場合があります**
——原因はイベント欄で確認してください。

> [!NOTE]
> **成功が `202` から `200` に変わったのは破壊的変更です**（`started: true` は旧パネルの
> ために残し、`done: true` を足しました）。以前はクリックを受け取った時点で `202` を返し、
> 1 巡まるごとを `ctx.waitUntil` に預けてレスポンスのあとで走らせていました。ところが
> Cloudflare は応答終了から約 30 秒でそれを取り消し、**取り消しは例外を投げません** ⇒
> 補充履歴は書かれず、イベントも出ず、ロックも解放されません。パネル上のそのラウンドは
> 「そもそも押していない」と 1 バイトも区別が付かず、漏れたロックは定期ラウンドまで
> 塞ぎます。`ctx.waitUntil` は消しておらず、「クライアントが途中で切れたときの受け皿」に
> 降格しました。

### 4 つのガードレール

**4 つのガードレール**があり、どれか 1 つでも満たさなければ起動しません：

| ガードレール | 満たさないとき | 何を防ぐか |
|------------|--------------|----------|
| 同一プロセス / 同一 isolate の実行中ガード | `409 tend_in_flight` | 定期ラウンドとボタンの衝突、同一レプリカ上の同時 2 クリック |
| ストレージレベルの短いロック（`registrar_tend_lock`） | `409 locked` | **レプリカをまたぐ**重複（ボリューム共有の複数コンテナ、Worker の 2 つの isolate） |
| 手動補充どうしは最低 10 分あける | `429 manual_cooldown` | 連打による一時メールボックス枠の浪費 |
| 1 日あたり最大 **24** 回 | `429 write_budget_exhausted` | 連打による**ストレージ書き込みクォータ**の浪費（計算は [DEPLOY.md](DEPLOY.md) の「クォータ計算」） |

`429` のボディには `remaining`（今日の残り回数）、`resetAt`（UTC 0 時に回復）、`retryAfterMs`
が入ります。**`200` のボディにも `remaining` が入ります**——ボタンが押せなくなってから伝える
のではなく、残り回数を最初から正直に表示するためです。レジストラーが無効なときは
`409 registrar_disabled` を返します。手前で弾かれる分岐のステータスコードは、この変更で
一つも変わっていません。

**あの短いロックの TTL は経路で分かれます**：定期ラウンドは 15 分（＝ Worker の Cron の
壁時計上限）、手動ラウンドは **3 分**です。手動ラウンドがプラットフォームに中断されると
ロックは自然に期限が切れるのを待つしかなく、15 分にしておくと 1 回のクリックが定期補充を
必ず 1 巡以上は塞ぎます（本番で 2 回起きました）。3 分は手動どうしの 10 分のクールダウン
より短いので、漏れたロックが次に押せるようになる時刻まで生き残ることはありません。

### 正直な限定と残存リスク

> [!WARNING]
> **正直な限定。「並行性は解決済み」と読まないでください。** KV は結果整合であり、この
> ストレージロックは**ベストエフォートであって排他プリミティブではありません**。防げるのは
> 「前のラウンドが明らかにまだ走っている」という最も一般的な重複であり、同じミリ秒に発行された
> 2 つのクリックは両方ともロックを取り得ます。ガードキーと補充履歴も read-modify-write なので、
> 並行ウィンドウでは更新が失われ得ます——上限は「ゲートが最大（並行数 − 1）回多く通す、
> 補充履歴が最大（並行数 − 1）行欠ける」です。

> [!WARNING]
> **残存リスク**：手動補充が持つのは**自分専用の一族**です——ラウンド予算 70 秒、1 巡で
> 発行するのは最大 1 本、認証コード待ちは最長 60 秒、試すドメインは 1 つだけ。Worker の
> Cron のあの 780 秒とは別勘定です。後ろの三つはいずれも `Math.min` で頭を押さえるだけで
> 代入ではありません：設定でもっと小さくした値が引き上げられることはなく、実際に切り詰め
> られたときはレスポンスの `outcome.capped` が切り詰め前後の値をそのまま報告します
> （イベントではなくレスポンスで返すのは、イベントにすると 1 クリックごとにストレージ書き込みが
> 1 回増え、「健康なラウンドは書き込みゼロ」というクォータ上の性質が壊れるからです）。
> 予算の役割は今も「明らかに完走できない試行を開始しない」ことであり、**漏れをなくすものでは
> なく、確率を下げるだけ**です——プラットフォームは予算ウィンドウ内でも呼び出しを中断し得て、
> その瞬間に発行中だった一時メールボックスは削除されません。定期ラウンドとは異なる点に注意
> してください：**Node/Docker の定期ラウンドはこの予算を持たず、手動補充は持ちます**。
> そのため同じ設定でも手動のラウンドは定期ラウンドより発行数が少なく、残った枠は次の定期
> ラウンドに回ります。

### これらのキーは自然には消えません

`registrar_tend_lock`、`registrar_manual_guard`、`tend:history`、`registrar:domains`、
`registrar:backoff` の 5 つは**いずれも TTL を持ちません**。名前は固定リテラルで個数は常に 1、
古い値はすべて**値の比較**で判定されるため（期限切れのロックは誰も止めず、昨日のカウントは
数えられず、期限切れのバックオフはどのラウンドも止めません）、残っていても無害です。

**コストは明記します**：レジストラーを恒久的に無効化する場合や、デプロイを削除して KV 名前
空間だけ残す場合、これらは自動では消えません。掃除するには手動でキーを削除してください：

- Worker：`wrangler kv key delete --binding=POOL registrar_manual_guard`（5 つそれぞれ 1 回）
- Node / Docker：`DATA_DIR/store.json` を編集し、その 5 つのトップレベルフィールドを削除

**`registrar:domains` は「ドメイン台帳が誤って記憶した」と判断したときの唯一の手動の出口
でもあります**：削除するとレジストラーはコールドスタートに戻り、すでに支払ったコード送信
リクエストを払い直します。本当に誤っていると判断したときだけにしてください。

**`tend:history` は通常は残すべきです**：事後分析で最も見たいものであり、「レジストラーを
止めた N 日後に補充履歴がまるごと消える」のは最悪のタイミングです——運用者は多くの場合、
何か起きた**からこそ**レジストラーを止めているのです。

## 発行された key が転送経路で使えるようになるまで

**最大で `POOL_CACHE_TTL_MS` 1 回分（既定 60 秒）であり、「次のリクエストから」ではありません。**

補充と転送は互いに独立した 2 つの key プールリポジトリインスタンスを使います。補充側は毎ラウンド
実際にストレージを読みます（現在の本当の利用可能数を見る必要があり、さもないと重複して発行し
メールボックスのクォータを無駄に消費します）。転送側は isolate / プロセス単位のスナップショットを
保持します。それぞれが自分のキャッシュを持つため、補充が key を書き込んだあと、転送経路は
**自分のスナップショット**が期限切れになって初めてそれを見ます。Worker ではアクティブな isolate
ごとにそれぞれの TTL がかかります。

**プールが空になったときに最も誤解されやすい点です**: ログには既に `[registrar] … minted=1` と
出ているのに、ゲートウェイは TTL 1 回分のあいだ `503 pool_empty` を返し続けます。補充が効いて
いないわけではないので、`POOL_CACHE_TTL_MS` を 1 回分待ってください。短くしたい場合はこの値を
小さくします（コストは [DEPLOY.md](DEPLOY.md) の「クォータの見積もり」を参照）。

## なぜ key を順番に発行し、並行実行しないのか

補充は 1 ラウンド内で key を**順番に**発行し、試行ごとにランダムな待機時間を挟みます。
複数の発行リクエストを並行して発火させることはありません。これはパフォーマンス上の
トレードオフではなく、機能上の制約です。並行実行すると、YYDS Mail のメールボックス作
成レート制限（短時間に約 10 回を超えて作成すると `403` を返す）と、Agnes 自身の登録リ
スク制御の両方に同時に抵触してしまいます。順番実行とランダムな待機時間は、レジストラー
が動作し続けるための前提条件であり、並行化で「最適化」すべきものではありません。

## プライバシーについて

登録処理中に生成されるメールアドレス、アカウント、パスワードはメモリ上に一時的に存在
するだけで、**使い終わったら破棄され、永続化されることはありません**。ストレージに残
るのは発行された API key のレコードのみです。一時メールボックスは、発行の成否にかかわ
らず、試行終了後に削除されます。

## トラブルシューティング

### レジストラーの 3 つの状態

レジストラーは「オン / オフ」の 2 状態ではなく、**3 状態**です。3 つめが最も誤読されやすいため、
パネルの 4 か所で同じことを書いています。

- **無効**：`REGISTRAR_ENABLED` が未設定、またはパネルのスイッチがオフ。補充ラウンドは 1 度も
  走らず、外部リクエストも送りません。パネルには「無効」と出ます。これが既定で、復旧は不要です。
  使うなら設定ページで有効にし、メールボックスチャネルを少なくとも 1 つ構成してください。
- **有効**：オンで、この設定が読み込めています。`TEND_INTERVAL_MS`（または Worker の Cron）に
  従って補充します。パネルには「有効」と出て、2 枚のチャネルカードが認証情報の有無と、
  今回使われているチャネルかどうかを示します。
- **有効 · 今回は起動せず**：スイッチはオンだが、この設定を読み込めなかった（チャネル未選択、
  選んだチャネルの認証情報欠落 など）ため起動していません。
  **ゲートウェイの転送はまったく影響を受けず**、補充だけが止まります。

3 つめの状態はパネルの 4 か所に出て、いずれも同じことを指しています：設定ページ上部のバナー
（不足項目の一覧）、レジストラーの状態行、概要ページの設定サマリー、そしてイベントセクションの
毎ラウンドの `error` レベル `registrar.blocked`。
**復旧方法**：バナーに並んだ項目を設定ページで埋めて保存するだけです。コンテナの再起動も
再デプロイも不要です。

> [!WARNING]
> **その代償**：障害が「うるさいもの」から「静かなもの」に変わります。補充が止まるとプールは
> 徐々に枯れ、数時間から数日後に `pool_empty` という形で表面化しますが、そのときの症状は真の
> 原因から何層も離れています。上の 4 つの手掛かりはそのために存在します——**自分で見に行く必要が
> あります**。

### 起動とログの約束

- **有効化時に認証情報が不足している場合、レジストラーは今回起動しませんが、ゲート
  ウェイの転送は通常どおり続きます。**
  ここは**変更されました**。以前はゲートウェイ全体をフェイルクローズさせていました
  が、レジストラーは任意のサブシステムであり、メールボックスの key が 1 つ足りないだけ
  で転送・`/health`・管理パネルまで巻き添えにすべきではありません。不足している項目は
  パネルに 1 件ずつ並び、毎ラウンド `error` レベルの `registrar.blocked` が記録されます。
  3 つの状態については下の「レジストラーの 3 つの状態」を参照してください。
- 補充処理中のログには一貫して `[registrar]` というプレフィックスが付くため、これで
  フィルタリングして状況を確認できます。各ログ行の 2 番目のフィールドは安定した
  機械可読の**イベント名**（例: `registrar.round_budget_impossible`）です。イベント名で
  grep する方が、人間向けの文言で grep するより確実です——文言は表現の調整で変わり得ま
  すが、イベント名はこのログの唯一の安定した対外契約であり、変わりません。
### `reasons=` の失敗理由を読む

- **1 ラウンドで発行しきれなかった枠があると、終了ログに `reasons=` 付きの警告が 1 行
  追加されます**（例：`reasons=yyds:register_failed×3 moemail:code_timeout×1`）。まずは
  この行でどの層の障害かを判断してください。`code_timeout` = このチャネルが Agnes から
  のメールを受け取れていない（ドメインの MX／転送ルール）。
  `register_failed` / `login_failed` / `key_failed` = Agnes 側の登録経路が変わった。
  `provider_error` = メールボックスサービス自体（認証情報、アクティブメールボックスの
  上限、サービス障害）。`provider_missing` = 内部の結線エラー。通常の設定では発生しません
  （認証情報の不足は起動時にエラーになるため、ここまで到達しません）。
- **`reasons=` に `key_suspicious` が出た場合**：上流から返ってきた key の中身に印字不可能な
  文字か空白が含まれています。**そのラウンドは実際に発行しています**（Agnes 側のアカウントは
  本当に作られ、一時メールボックスも本当に消費されました）。したがってその key は
  **そのままプールに保存されます**——ここで拒否することは、二度と取り戻せない資格情報を
  破棄することだからです。ただし選択されるたびに転送が失敗する可能性が高いので、管理画面で
  無効化するか削除してください。同時に `registrar.minted_key_suspicious` の error イベントが
  出ます（記録するのはチャネルと長さだけで、**平文は記録しません**）。
### レジストラーは「使えるメールドメイン」を記憶します

上流は一部の使い捨てメールドメインしか受け付けず、残りは拒否します。**この判定を保存して
再利用するようになりました**。

- 定常状態では**1 回の発行成功につき `/api/verification` は 1 回だけ**です。上流の全ドメイン
  から無作為に何個か取り出して順に試すのではなく、すでに使えると分かっているドメインを選び
  ます。`MAX_DOMAIN_ATTEMPTS` の既定値を 1 まで下げられるのはこのためです。
- パネルのレジストラー欄に「ドメイン台帳: 利用可 N · 除外 N · 再確認待ち N · 未確認 N
  （更新 …）」という行が出ます。
- **2 ラウンド続けて**拒否されて初めて候補の最後尾に回されます（**同じラウンド内で何回
  拒否されても 1 回と数えます**）。1 ラウンドだけの場合は「再確認待ち」
  として引き続き選ばれ、優先度が下がるだけです。1 回成功すれば無条件で「利用可」に戻ります。

#### この判定が誤り得る理由

> [!WARNING]
> **「除外」は上流の宣言ではなく、こちらの判定です。** 上流は同じ `400` で「このドメインは
> ブロック済み」と「その送信元は送りすぎ」の両方を表現し、区別できる手掛かりは本文だけです。
> こちらはそれを**語句リスト**で判定しているため、上流が文言を変えれば誤判定します。
> それを押さえているのは 3 層です。判定は 2 回必要、1 ラウンドで学ぶのは最大 1 件、
> そして**並べ替えはどのドメインも完全には除外しません**（除外扱いは最後尾に回るだけ）。
> ただしこの 3 層が押さえているのは「良いドメインが除外される」という一方向だけです。
> 逆方向——台帳の「利用可」が古く、実際には上流に締め出されている——を押さえているのは
> 別の決まりです：**分類器が下した判定はそのまま記録し、結論を握り潰さない**。
> この決まりは以前、ある保険（「利用可と分かっているドメインが拒否されたらレート制限と
> 読み替える」）に壊されており、代償は遅くなることではなく最長 7 日間の**補充ゼロ**でした。
> この保険は撤去済みです。
> つまりこの締めの一文は**方向ごとに分けて**読む必要があります。3 つの方向で代償は同じでは
> ありません。
> ① 良いドメインが除外される方向——確かに遅くなるだけで、**ゼロにはなりません**
> （3 層の防御に加え、並べ替えはどのドメインも除外しません）。
> ② 台帳は「利用可」なのに上流はすでに締め出している方向——「分類器が下した判定はそのまま
> 記録する」という決まりが支えており、その決まりは修復済みです。
> ③ 分類器が**本物のレート制限**を「ドメインがブロックされた」と読む場合——上流のレート制限
> の文言に**当方の語句リストが 1 つも一致しなかった**ため（「上流が何も言っていない」ではありま
> せん。上流は言っており、当方が認識できなかっただけです）、上の 2 層のバックオフは一度も発生
> せず、そのラウンドも早めに止まらなくなり、1 ラウンドで最大 `MINT_BATCH` 回の必ず失敗する
> 認証コード要求が出ます。これを受け止めるのは下の表の 3 行目で、根拠は上流の文言ではなく
> **そのラウンドの形**（同じラウンドで複数のドメインがまとめてブロック判定される、**または
> 上流が列挙するドメインが 1 つ残らずブロック判定される**、しかも key が 1 本も出ない）です。

#### ドメイン台帳が誤って記憶したと判断した場合

パネルにドメインを 1 件ずつ並べる画面はありません（上流の
数百件を載せると、数秒ごとにポーリングされるエンドポイントの応答が一桁大きくなります）。
取れる手は 3 つ: 判定の期限切れを待つ（除外は 24 時間、利用可は 7 日）、2 回ルールの自己訂正を
待つ、またはストレージキーを手で削除する（下の「これらのキーは自然には消えません」参照）。

### 上流にレート制限されたときに起きること

上流の手前にエッジのレート制限（`429`）があり、さらに上流自身の登録レート制限（`400` と
「リクエストが多すぎます」といった文言）があります。**どちらの罰則期間も 1 ラウンドの補充
より長く、しかも期間中にリクエストを 1 回投げるたびに期間が延びます。**

そのため、いずれかに当たった場合は次のようになります。

- **そのラウンドはその場で終了**します。ドメインの切り替えも、次の枠への続行もしません。
- **バックオフ期間**を記録し、次のラウンドを始める前に必ず確認します。**期間中は上流への
  リクエストを 1 回も送らず、一時メールボックスも 1 つも作りません。** 補充履歴のその行の
  失敗理由は「バックオフ期間中のため、このラウンドは 1 回も開始していません」です。
- 続けて当たるとバックオフは**指数的に**伸びます（上限 4 時間）。ここでの「続けて」が数えるのは
  **key が 1 本も出なかったラウンドの連続数**です。そのラウンドで 1 本でも発行できていれば指数は
  数え直しになり——同じラウンドの最後にレート制限へ当たった場合でも、バックオフは倍になるのではなく
  最初の段に戻ります。そのラウンドで一度もレート制限へ当たらなかったときは、そのキー自体を消します。
- 直前のバックオフ期間が終わってから 4 時間以上当たらなければ、指数はやはり数え直しになります
  （プールが満杯のままで、登録機が何ラウンドも実際には走っていない、といった場合です）。

#### 3 つ目の段: 当方の語句リストは 1 つも一致しなかったが、そのラウンドのドメインがまとめて落ちた

上流が文言を一度変えるだけで、本物の
レート制限が 1 件ずつ「ドメインがブロックされた」と読まれます——上の 2 段は一度も発火せず、
そのラウンドも早めには止まりません。そこで唯一残る根拠が**そのラウンドの形**で、判定は
2 通りあり、どちらか一方に当たれば成立します。

- 同じラウンドで 2 件以上のドメインがブロック判定される；
- **または上流が列挙するドメインが、そのラウンドで 1 つ残らずブロック判定される**
  （メールボックスドメインを 1 つしか設定していない構成はこちらで受け止めます —— その構成は
  上の「2 件以上」に永遠に届きません）。

どちらも**そのラウンドで key が 1 本も出ていない**ことが条件です。レジストラーはこれを根拠に
バックオフ期間を記録します（起点 30 分、指数も上限 4 時間も同じ）。
**ただしそのラウンドを中止せず、ドメインの判定も一切握り潰しません**——そのラウンドで試す
はずだったドメインは試され、出るはずの key も出ます。そのラウンドで key が 1 本でも出ていれば、
この段は一切記録しません。

#### この段が点灯したとき、可能性は 2 つとも残っています

> [!WARNING]
> **可能性は 2 つとも残っており、バナーが代わりに選んではくれません**：
> 上流がレート制限の文言を変えて当方の語句リストが取りこぼした場合と、上流が本当にそれらの
> ドメインをブロックリストに入れ替えた場合です。**「上流はレート制限について何も言っていない」
> と読まないでください** —— この段が存在する筆頭の場面は、まさに上流が言ったのに当方が認識
> できなかった場面です。

#### 上流の原文をどこで探すか：2 つの分岐で手に入る証拠が違います

**「`registrar.domain_blocked` を見ればよい」を鵜呑みにしないでください —— 2 つの分岐の
一方では、そのイベントはそもそも 1 件も発行されません。その代償をここに正直に記録します：**

- **同じラウンドで複数のドメインが「ブロック」と判定された分岐**：クランプが効いた時点で
  そのラウンドの**すべての**「ブロック」判定が一括で破棄されます ⇒ 台帳は `blocked` を
  学習しません ⇒ **そのラウンドでは `registrar.domain_blocked` が 1 件も発行されません**。
  この分岐で手に入る上流の原文は `registrar.known_good_domain_rejected` の分だけで、しかも
  それは**台帳が既に「使える」と知っていたドメインしか対象にしません** —— コールドスタートや、
  上流がそのラウンドで初めて列挙したドメインには、原文が 1 件も残りません。同じラウンドで
  発行される `registrar.domain_verdicts_discarded` が持つのは破棄された判定の件数、その
  ラウンドの産出、バックオフの期限だけで、**上流の原文は含みません**。
- **上流が列挙するドメインが 1 つ残らず「ブロック」と判定された分岐**（メールドメインを
  1 つだけ設定したデプロイが通るのはこちらです）：クランプは閾値に届かず効かない ⇒ 台帳は
  通常どおり結論を学習し、2 回目で判定が確定したときに `registrar.domain_blocked` が上流の
  原文を載せて発行されます。

#### 3 つ目の段が受け止めたあとに残るリクエスト量

数で書きます（内蔵値、テストダブルで計測）：
指数の上限に達したあとは**8 ラウンドに 1 回、1 回あたり `MINT_BATCH` = 5 件の認証コード要求**
です。Cron が 30 分に 1 回なので 48 ラウンド/日 ÷ 8 × 5 = **1 日あたり約 30 件**。
比較用の 2 つの数字：**この段が受け止める前は毎ラウンド打ち切りなしで出ていた ⇒ 1 日あたり約
240 件**。そして「上流の文言が語句リストに載った」2 つ目の段は当たった時点でラウンド全体を
止めます（1 ラウンド 1 件）⇒ **1 日あたり約 6 件**。
⇒ **30 は 6 ではありません**：この段はラウンドを中止しないぶん 2 つ目の段より高くつきます ——
そのラウンドで出るはずの key は出て、代償としてそのラウンドの残りの試行も出ていきます。

#### バックオフのバナー: 3 つの段で対処は異なります

パネルのレジストラー欄にはバックオフのバナーが出ます。

| どの段か | パネルの表示 | できること |
|----------|------------|----------|
| エッジのレート制限 | 「補充の間隔が詰まりすぎている」 | `MINT_DELAY_MIN_MS` を大きくするか `MINT_BATCH` を小さく |
| 上流自身の登録レート制限 | 「返答に『リクエストが多すぎます』といった文言があった——これは当方の語句リストによる判定で、上流が下した結論ではありません」 | まず `MINT_DELAY_MIN_MS` を大きく、`MINT_BATCH` を小さく。送信元の変更は登録枠を本当に使い切ったと確認してから |
| そのラウンドのドメインがまとめてブロック判定され、発行数が 0 | 「当方の語句リストに一致なし。可能性は 2 つとも残っています」 | 分岐ごとに残る証拠が違います（前節参照）。`registrar.domain_blocked` に必ずあるとは限りません |

> [!IMPORTANT]
> **メールボックスチャネルを切り替えてもこれは回避できません。** 制限はあなたの送信元
> アドレスと上流のあいだに掛かっており、どのメールボックスチャネルを使うかとは無関係です。
> バックオフのバナーが出ているときにチャネルを切り替えても無駄です。

**空のプールを満たすのは目に見えて遅くなります**: 目標 20 個の key は「数分」から
おおよそ 4〜5 ラウンドになります。Cron が 30 分に 1 回なら **約 2〜2.5 時間**です。
これは「枠を使い切ってもなお空打ちする」状態を「遅いが本当に key が出る」状態に
置き換えたことの直接の代償です。

### チャネルが失敗したあと何が起きるか

**2 つのうち 1 つを選ぶ方式なので、「もう一方に切り替える」のはあなたにしかできません。**
選んだチャネルが失敗したときの挙動は次のとおりです。

- **その枠は無効になり、そのラウンドの次の枠は通常どおり開始します**（先に
  `MINT_DELAY_MIN_MS`〜`MINT_DELAY_MAX_MS` のランダムな待機が入ります）。ドメイン一覧の
  取得失敗、認証情報の無効化、候補ドメインすべてでメールボックスを作れない、認証コードが
  届かない、ネットワークの揺らぎ、全ドメインがブロック、登録／ログイン／
  key 作成の失敗——これらはすべてこの区分です。
- **例外は 2 つあり、どちらもそのラウンドを即座に終了します**：
  - Agnes バックエンド全体の障害（`upstream_error`）——続けても障害中に失敗確定の
    リクエストを増やすだけだからです。
  - **上流のレート制限に当たった場合（`rate_limited`）**——下の
    「上流にレート制限されたときに起きること」を参照してください。
- **レート制限以外にはラウンドをまたぐバックオフも指数リトライもありません。** 通常の失敗は
  次のラウンドの時刻を変えません（Node / Docker は固定の `TEND_INTERVAL_MS` タイマー、
  Worker は `wrangler.toml` の Cron）。ラウンド内の抑制はすでに 2 層あります（試行間の
  ランダムな待機と、Worker 側のラウンド単位の壁時計予算）。

#### 代償と、その気づき方

> [!WARNING]
> **これは機能の後退です。はっきり書いておきます。** 以前は認証コードを受け取れないチャネル
> でも一度は自動で切り替わり、補充は遅くなっても key は出続けました。今は同じ失敗が
> そのラウンド、場合によってはその日ずっと発行数ゼロを意味し、あなたが切り替えるまで
> 変わりません。障害の形は「補充が遅くなる」から「補充がまったく出ない → プールが枯れる →
> 数時間から数日後に `pool_empty` 503 として表面化する」へ変わります——**自己回復する障害を
> 人手が要る障害と引き換えにした**わけです。これはいずれか一方を選ぶ方式の本質的な代償で
> あり、欠陥ではありません。

**気づき方**：補充履歴の各ラウンドの失敗理由には 1 件ずつチャネル名が付いています
（`reasons=` の行）。ほかにレジストラーセクションのプール 4 数値、そしてチャネルのリクエスト
が失敗したときに**実際にリクエストしたアドレス**を含むイベントがあります。発行数がゼロなら、
パネルでもう一方のチャネルの「接続テスト」を押します。これはドメインを列挙したうえで
**そちらの認証情報を実際に検証します**（方法はチャネル次第で、一時メールボックスを作って
削除する方式もあります）。切り替えたら次の補充ラウンドの失敗理由を見てください。
key が発行されて初めて確かめられます。

### あるチャネルが失敗し続けるとき

- 特定のチャネルで登録が失敗し続ける場合（たとえば Agnes が認証コードや CAPTCHA のポ
  リシーを強化した場合など）、これはコードレベルでは回避できない上流側の変化です。
  レジストラーを無効化し、代わりに key を手動でインポートすることもできます
  （[DEPLOY.md](DEPLOY.md) を参照）。
