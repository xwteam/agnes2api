# レジストラー（自動プール補充）

**Language:** [English](../en/REGISTRAR.md) | [简体中文](../zh-CN/REGISTRAR.md) | [繁體中文](../zh-TW/REGISTRAR.md) | 日本語 | [한국어](../ko/REGISTRAR.md)

> **デフォルトで無効です。** `REGISTRAR_ENABLED` のデフォルトは `false` で、導入しただけ
> では一切アカウント登録を開始しません。明示的に `true` に設定した場合のみ有効になり
> ます。

## これは何か

レジストラーはオプション機能です。key プール内の利用可能な key 数が `TARGET_KEYS` を
下回ると、新しい Agnes アカウントを自動登録し、ログインし、API key を発行してプールに
書き込みます。登録には Agnes から届く認証コードの受信が必要なため、下記のメールボック
スチャネルのいずれかに依存します。

> **コンプライアンスに関する注意**
>
> 大量アカウント登録は Agnes の利用規約と緊張関係にあります。レジストラーを有効にする
> かどうか、どの程度の頻度で使うかは、運用者自身が判断し、責任を負うべき事項です——
> 本プロジェクトはこの判断を代行しません。

## 2 つのメールボックスチャネル：選び方

レジストラーは認証コードを受信するために 2 つのメールボックスチャネルをサポートしま
す。

| | YYDS Mail | MoeMail |
|---|---|---|
| 性質 | サードパーティの一時メールボックスサービス | 自分でホストする一時メールボックスサービス |
| API ベース URL | デフォルトあり（`YYDS_BASE_URL`、公開 API エンドポイント） | デフォルトなし（`MOEMAIL_BASE_URL`）、自分で立てたインスタンスのアドレスを入力 |
| 認証情報の取得 | サービスに API Key を申請（`YYDS_API_KEY`） | 自分のインスタンス内で API Key を発行（`MOEMAIL_API_KEY`） |

**2 つのチャネルは完全に対等であり、本プロジェクトはどちらも主要チャネルに指定せず、
どちらも推奨しません。** `REGISTRAR_PRIMARY` にデフォルト値はなく、レジストラーを有効
にする際は `yyds` か `moemail` を明示的に指定する必要があります。`REGISTRAR_FALLBACK`
は任意です。主チャネルが**チャネルレベルの失敗**（ドメイン一覧取得の失敗、メールボック
ス作成の連続失敗、認証情報の無効化など）に遭遇した場合、その回だけ自動的にフォール
バックします。空欄のままならフォールバックは行われません。

判断基準：レジストラーは「ドメインを切り替える」ことで Agnes による使い捨てメールボッ
クスドメインのブロックを回避しています。利用可能なドメインが多いほど、レジストラーは
長く動作し続けられます。両サービスでそれぞれ何個の利用可能ドメインを持っているか確認
し、多い方を主チャネルにするとよいでしょう——これはどちらのサービスかとは無関係で、
あなた自身のアカウントや自己ホスト環境の設定次第です。

## 組み込みの認証情報はゼロ——自分で用意してください

このリポジトリには実際の鍵、アカウント、プライベートドメインは一切含まれていません。
レジストラーを有効にする前に、以下を自分で用意する必要があります。

- **YYDS Mail を使う場合**：サービスに API Key を申請し、`YYDS_API_KEY` に設定します
  （`YYDS_BASE_URL` にはすでにデフォルト値があり、通常変更不要です）。
- **MoeMail を使う場合**：MoeMail インスタンスを自分でホストし、そのアクセスアドレス
  を `MOEMAIL_BASE_URL` に、インスタンス内で発行した API Key を `MOEMAIL_API_KEY` に
  設定します（どちらもデフォルト値がないため、必ず明示的に設定してください）。

少なくとも `REGISTRAR_PRIMARY` が指すチャネルの認証情報を用意してください。
`REGISTRAR_FALLBACK` を設定する場合は、そのチャネルの認証情報も併せて用意します。

## 設定項目

| 変数 | 必須 | デフォルト | 説明 |
|---|---|---|---|
| `REGISTRAR_ENABLED` | いいえ | `false` | マスタースイッチ。`true` にしないとレジストラーは有効になりません。 |
| `REGISTRAR_PRIMARY` | 有効化時は必須 | なし | 主チャネル、`yyds` または `moemail`。両者は対等でデフォルト値なし。 |
| `REGISTRAR_FALLBACK` | いいえ | 空（フォールバックなし） | 副チャネル、`yyds` または `moemail`。主チャネルがチャネルレベルで失敗した際に使われる。 |
| `TARGET_KEYS` | いいえ | `20` | 目標とする利用可能 key 数。これを下回ったときのみ補充が発生。 |
| `MINT_BATCH` | いいえ | `5` | 1 ラウンドで発行する key の最大数。 |
| `TEND_INTERVAL_MS` | いいえ（Node/Docker のみ） | `1800000`（30 分） | Node 側の補充スケジュール間隔。Worker 側は `wrangler.toml` の Cron が決める（下記参照）。 |
| `CODE_TIMEOUT_MS` | いいえ | `120000`（120 秒） | 1 回の発行試行で認証コードを待つタイムアウト。 |
| `MINT_DELAY_MIN_MS` | いいえ | `2000` | 1 ラウンド内で発行試行の間に入れるランダム待機時間の下限（ミリ秒）。 |
| `MINT_DELAY_MAX_MS` | いいえ | `5000` | 1 ラウンド内で発行試行の間に入れるランダム待機時間の上限（ミリ秒）。 |
| `MAX_DOMAIN_ATTEMPTS` | いいえ | `8` | 1 回の発行試行で試す一時メールドメインの最大数。 |
| `TOKEN_NAME` | いいえ | `auto` | 発行された Agnes API key が Agnes 管理画面に表示される名前。 |
| `AGNES_PLATFORM_URL` | いいえ | `https://platform-backend.agnes-ai.com` | 登録・ログイン・key 発行に使う Agnes プラットフォームのバックエンド（ベンダーの公開エンドポイント）。 |
| `YYDS_BASE_URL` | いいえ | `https://maliapi.215.im` | YYDS Mail の API ベース URL（ベンダーの公開エンドポイント）。 |
| `YYDS_API_KEY` | チャネルが yyds の場合は必須 | 空 | YYDS Mail の API Key。 |
| `MOEMAIL_BASE_URL` | チャネルが moemail の場合は必須 | 空 | 自分でホストした MoeMail インスタンスのアドレス。デフォルトなし。 |
| `MOEMAIL_API_KEY` | チャネルが moemail の場合は必須 | 空 | その MoeMail インスタンスの API Key。 |

`MINT_DELAY_MIN_MS`、`MINT_DELAY_MAX_MS`、`TOKEN_NAME`、`AGNES_PLATFORM_URL` は既定では
`.env.example` に記載されていません（多くの場合デフォルトで十分なため）が、どちらの
デプロイ先でも読み込まれるので必要に応じて設定できます。上記の数値型変数はすべて正の
整数である必要があり、そうでない場合ゲートウェイは起動を拒否します。

## 2 つのランタイムのスケジューリングの違い

| デプロイ先 | トリガー方式 | 間隔を決めるもの |
|---|---|---|
| Cloudflare Worker | `wrangler.toml` の `[triggers]` に設定した Cron（デフォルト `*/30 * * * *`、30 分ごと） | `wrangler.toml` の cron 式を編集 |
| Node / Docker | プロセス内タイマー | `TEND_INTERVAL_MS`（デフォルト `1800000` ミリ秒） |

どちらのランタイムも最終的には同じ補充関数を、まったく同じ設定で呼び出します。違うのは
「誰が定刻に呼び出す責任を持つか」だけです。

### Cloudflare Cron トリガーの壁時計時間の上限（パラメータ調整前に必読）

Worker にデプロイする場合、補充は Cron トリガーによって起動されます。以下を必ず理解し
てください。

- Cron トリガー 1 回の呼び出しには、**15 分（900 秒）の壁時計時間（wall-clock）上限**
  があります。
- **`ctx.waitUntil()` はこの上限を延長しません**——その猶予機構は HTTP リクエストにの
  み適用され、Cron トリガーの呼び出しには適用されません。
- CPU 時間の上限は 30 秒ですが、補充処理中の `await` によるネットワーク呼び出し（認証
  コードの送信・ポーリングなど）は CPU 時間に計上されないため、CPU 上限は実質的なボト
  ルネックにはなりません。
- 登録機の通信経路上の **すべての HTTP リクエストには 15 秒のリクエスト単位のタイム
  アウト**（固定値、設定不可）が付いています。これは以下 2 つの見積もりが成立する前提
  です——これが無いと、1 本のハングした接続だけで 1 ラウンドが無限に伸びます。
- **通常時の所要時間**（各リクエストが速やかに返り、最初のドメインもブロックされない
  場合）は認証コード待ちが支配的で、おおよそ `MINT_BATCH × CODE_TIMEOUT_MS` =
  5 × 120 秒 = 600 秒に、1 ラウンド内の発行試行間のランダム待機時間（最大 4 回、1 回
  あたり最大 5 秒）約 20 秒を加えた **約 600〜620 秒**となり、900 秒の壁時計上限に対し
  て約 **30% の余裕**があります。
- **理論上の最悪ケース**にはリクエスト単位のタイムアウトも算入する必要があります。1 回
  の発行はコードのポーリングに加え、「ドメイン一覧 1 回＋試行するドメインごとに 3 回
  （メールボックス作成・コード送信・メールボックス削除）＋3 回（登録・ログイン・key
  作成）」を発行するため、`CODE_TIMEOUT_MS + (1 + 3 × MAX_DOMAIN_ATTEMPTS + 3) × 15 秒`
  ＝デフォルトでは約 120 + 420 = **540 秒**、これに `MINT_BATCH` を掛けると 900 秒を
  大きく超えます。つまり**デフォルト設定でも極端なケースでは壁時計上限に達し得ます**
  ——これは意図的な割り切りです。key は発行され次第すぐ保存されるため、中断されても
  そのラウンドが不完全になるだけです（次項参照）。極端なケースまで壁時計内に収めたい
  場合は `MINT_BATCH` を 1〜2 にするか、`CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS` を
  小さくしてください。
- **`MINT_BATCH`・`CODE_TIMEOUT_MS`・`MAX_DOMAIN_ATTEMPTS` を大きくする前に、上記 2 つの
  式で必ず計算してください。** 上限に達すると、その回の Cron 呼び出しはプラットフォーム
  によって中断されます。
- 中断されても、すでに発行された key が失われることはありません——key は発行され次第
  即座にストレージへ書き込まれるため、中断されたラウンドは単に不完全なだけであり、次
  のスケジュールで続きから補充が試みられます。

## なぜ key を順番に発行し、並行実行しないのか

補充は 1 ラウンド内で key を**順番に**発行し、試行ごとにランダムな待機時間を挟みます。
複数の発行リクエストを並行して発火させることはありません。これはパフォーマンス上の
トレードオフではなく、機能上の制約です。並行実行すると、YYDS Mail のメールボックス作
成レート制限（短時間に約 10 回を超えて作成すると `403` を返す）と、Agnes 自身の登録リ
スク制御の両方に同時に抵触してしまいます。順番実行とランダムな待機時間は、レジストラー
が動作し続けるための前提条件であり、並行化で「最適化」すべきものではありません。

## プライバシーについて

登録処理中に生成されるメールアドレス、アカウント、パスワードはメモリ上に一時的に存在
するだけで、**使い終わったら破棄され、永続化されることはありません**。ストレージに残
るのは発行された API key のレコードのみです。一時メールボックスは、発行の成否にかかわ
らず、試行終了後に削除されます。

## トラブルシューティング

- **有効化時に認証情報が不足していると、起動時にエラーとなり、不足している項目が明示
  されます。** レジストラーはフェイルクローズ方針を採用しており、認証情報の不足を静
  かに見過ごすことはなく、ゲートウェイを明確に失敗させることで問題を発見しやすくして
  います。
- 補充処理中のログには一貫して `[registrar]` というプレフィックスが付くため、これで
  フィルタリングして状況を確認できます。
- 特定のチャネルで登録が失敗し続ける場合（たとえば Agnes が認証コードや CAPTCHA のポ
  リシーを強化した場合など）、これはコードレベルでは回避できない上流側の変化です。
  レジストラーを無効化し、代わりに key を手動でインポートすることもできます
  （[DEPLOY.md](DEPLOY.md) を参照）。
