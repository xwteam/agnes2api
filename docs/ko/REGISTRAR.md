# 레지스트라(자동 키 풀 보충)

> **기본값은 비활성화입니다.** `REGISTRAR_ENABLED`의 기본값은 `false`이며, 설치만으로는
> 어떠한 계정 등록도 자동으로 시작되지 않습니다. 명시적으로 `true`로 설정해야만 레지스
> 트라가 작동합니다.

## 이것은 무엇인가

레지스트라는 선택적 구성 요소입니다. key 풀 안의 사용 가능한 key 수가 `TARGET_KEYS`
아래로 떨어지면, 새로운 Agnes 계정을 자동으로 등록하고 로그인한 뒤 API key를 발급해
풀에 채워 넣습니다. 등록 과정에서 Agnes가 보내는 인증 코드를 수신해야 하므로, 아래의
메일함 채널 중 하나에 의존합니다.

> **컴플라이언스 안내**
>
> 대량 계정 등록은 Agnes 서비스 약관과 긴장 관계에 있습니다. 레지스트라를 활성화할지,
> 어떤 빈도로 사용할지는 운영자 스스로 판단하고 그에 따른 책임을 져야 하는 사안입니다
> ——본 프로젝트는 이 결정을 대신 내리지 않습니다.

## 두 메일함 채널: 어떻게 선택할까

레지스트라는 인증 코드를 수신하기 위해 두 가지 메일함 채널을 지원합니다.

### 두 채널 비교

| | YYDS Mail | MoeMail |
|----|---------|-------|
| 성격 | 제3자 임시 메일함 서비스 | 직접 호스팅하는 임시 메일함 서비스 |
| API base URL | 기본값 있음(`YYDS_BASE_URL`, 공개 API 엔드포인트) | 기본값 없음(`MOEMAIL_BASE_URL`), 직접 배포한 인스턴스 주소를 입력 |
| 자격 증명 발급 방법 | 해당 서비스에 API Key 신청(`YYDS_API_KEY`) | 직접 배포한 인스턴스에서 API Key 생성(`MOEMAIL_API_KEY`) |

### 주 채널과 폴백 채널 설정하기

> [!IMPORTANT]
> **두 채널은 완전히 대등하며, 본 프로젝트는 어느 쪽도 주 채널로 지정하지 않고 어느
> 쪽도 추천하지 않습니다.**

`REGISTRAR_PRIMARY`는 기본값이 없으며, 레지스트라를 활성화할 때 `yyds` 또는 `moemail`
중 하나를 명시적으로 지정해야 합니다. `REGISTRAR_FALLBACK`은 선택 사항으로, 주 채널이
**채널 수준 실패**(도메인 목록 조회 실패, 메일함 생성이 연속으로 실패, 자격 증명 무효,
인증 코드가 오지 않음 등)를 겪으면 해당 시도에 한해 자동으로 폴백 채널로 전환됩니다.
비워 두면 폴백을 사용하지 않습니다.

> "인증 코드가 오지 않음"도 채널 수준 실패입니다. 인증 코드는 바로 이 메일함 채널을 통해
> 전달되므로, 도메인 MX 레코드 만료나 메일 전달 규칙 삭제처럼 API는 모두 2xx를 반환하는데
> 메일만 영영 오지 않는 상황 역시 "이 채널은 지금 key를 만들어 낼 수 없다"를 뜻합니다.

### 주 채널은 어떻게 고르나

판단 기준: 레지스트라는 "도메인을 바꿔가며" Agnes가 일회용 메일함 도메인을 차단하는
것을 우회합니다. 사용 가능한 도메인이 많을수록 레지스트라가 더 오래 작동합니다. 양쪽
서비스에서 각각 사용 가능한 도메인이 몇 개인지 확인한 뒤, 더 많은 쪽을 주 채널로 삼는
것이 좋습니다——이는 어느 서비스인지와는 무관하며, 오직 당신 자신의 계정이나 자체 호스
팅 환경의 설정에 달려 있습니다.

## 내장된 자격 증명은 없습니다 — 직접 준비하세요

이 저장소에는 실제 키, 계정, 프라이빗 도메인이 전혀 포함되어 있지 않습니다. 레지스트
라를 활성화하기 전에 다음을 직접 준비해야 합니다.

### 채널별로 준비할 것

- **YYDS Mail을 사용하는 경우**: 해당 서비스에 API Key를 신청해 `YYDS_API_KEY`에 설정
  합니다(`YYDS_BASE_URL`은 이미 기본값이 있어 보통 변경할 필요가 없습니다).
- **MoeMail을 사용하는 경우**: MoeMail 인스턴스를 직접 호스팅하고, 접속 주소를
  `MOEMAIL_BASE_URL`에, 해당 인스턴스에서 생성한 API Key를 `MOEMAIL_API_KEY`에 설정합
  니다(둘 다 기본값이 없으므로 반드시 명시적으로 설정해야 합니다).

### 최소한 어디까지 준비해야 하나

최소한 `REGISTRAR_PRIMARY`가 가리키는 채널의 자격 증명은 준비해야 합니다.
`REGISTRAR_FALLBACK`을 설정했다면 해당 채널의 자격 증명도 함께 준비하세요.

## 설정 항목

| 변수 | 필수 여부 | 기본값 | 설명 |
|----|---------|------|----|
| `REGISTRAR_ENABLED` | 아니오 | `false` | 마스터 스위치. `true`여야 레지스트라가 활성화됨. |
| `REGISTRAR_PRIMARY` | 활성화 시 필수 | 없음 | 주 채널, `yyds` 또는 `moemail`. 둘은 대등하며 기본값 없음. |
| `REGISTRAR_FALLBACK` | 아니오 | 공백(폴백 없음) | 보조 채널, `yyds` 또는 `moemail`. 주 채널이 채널 수준으로 실패할 때 사용됨. |
| `TARGET_KEYS` | 아니오 | `20` | 목표로 하는 사용 가능 key 수. 이 값 아래로 떨어져야 보충이 발생. |
| `MINT_BATCH` | 아니오 | `5` | 한 라운드에서 발급할 key의 최대 개수. |
| `TEND_INTERVAL_MS` | 아니오(Node/Docker 전용) | `1800000`(30분) | Node 측 보충 스케줄 간격. Worker 측은 `wrangler.toml`의 Cron이 대신 결정함(아래 참조). |
| `CODE_TIMEOUT_MS` | 아니오 | `120000`(120초) | 한 번의 발급 시도에서 인증 코드를 기다리는 타임아웃. |
| `MINT_DELAY_MIN_MS` | 아니오 | `2000` | 한 라운드 내 발급 시도 사이에 두는 무작위 대기 시간의 하한(밀리초). |
| `MINT_DELAY_MAX_MS` | 아니오 | `5000` | 한 라운드 내 발급 시도 사이에 두는 무작위 대기 시간의 상한(밀리초). |
| `MAX_DOMAIN_ATTEMPTS` | 아니오 | `8` | 한 번의 발급 시도에서 시도할 임시 메일함 도메인의 최대 개수. |
| `REGISTRAR_TOKEN_NAME` | 아니오 | `auto` | 발급된 Agnes API key가 Agnes 대시보드에 표시되는 이름. |
| `AGNES_PLATFORM_URL` | 아니오 | `https://platform-backend.agnes-ai.com` | 등록·로그인·key 발급에 사용하는 Agnes 플랫폼 백엔드(벤더의 공개 엔드포인트). |
| `YYDS_BASE_URL` | 아니오 | `https://maliapi.215.im` | YYDS Mail의 API base URL(벤더의 공개 엔드포인트). |
| `YYDS_API_KEY` | 채널이 yyds일 때 필수 | 공백 | YYDS Mail의 API Key. |
| `MOEMAIL_BASE_URL` | 채널이 moemail일 때 필수 | 공백 | 직접 배포한 MoeMail 인스턴스 주소. 기본값 없음. |
| `MOEMAIL_API_KEY` | 채널이 moemail일 때 필수 | 공백 | 해당 MoeMail 인스턴스의 API Key. |

위 표의 모든 변수는 `.env.example`에 한 줄씩 들어 있으며(대개 기본값으로 충분하므로
따로 고칠 일은 드뭅니다), 두 배포 대상 모두 이 값을 읽어 들입니다. 위의 수치형 변수는
모두 양의 정수여야 하며, 그렇지 않으면 게이트웨이가 기동을 거부합니다.

## 두 런타임 간 스케줄링 차이

### 누가 트리거하고 간격은 어디서 오는가

| 배포 대상 | 트리거 방식 | 간격을 결정하는 요소 |
|---------|-----------|--------------------|
| Cloudflare Worker | `wrangler.toml`의 `[triggers]`에 설정한 Cron(기본값 `*/30 * * * *`, 30분마다) | `wrangler.toml`의 cron 표현식을 수정 |
| Node / Docker | 프로세스 내 타이머 | `TEND_INTERVAL_MS`(기본값 `1800000`ms) |

두 런타임 모두 결국 **동일한 보충 함수**를 호출합니다. 차이는 **누가 제때 호출할 책임을
지는가**, 그리고 **트리거 간격이 어디서 오는가**입니다:

| | 트리거 | 간격의 출처 | 바꾸면 |
|----|------|-----------|------|
| Node / Docker | 프로세스 내 자체 재스케줄 타이머 | `TEND_INTERVAL_MS`(환경 변수 > 저장된 설정 > 기본값 `1800000`) | **다음 라운드부터 적용**(현재 라운드는 기존 간격으로 끝까지 진행. 기본값 기준 최대 30분). **재시작 불필요** |
| Cloudflare Worker | 플랫폼의 Cron Trigger | `wrangler.toml`의 `[triggers].crons` | **설정을 바꿔도 반영되지 않음**. `wrangler.toml`을 수정하고 재배포해야 함 |

트리거 간격을 제외한 나머지 보충 설정 항목(`TARGET_KEYS` / `MINT_BATCH` / 채널 자격 증명 등)은
두 런타임에서 실제로 완전히 동일합니다.

### Cloudflare Cron 트리거의 월클록(wall-clock) 상한(파라미터 조정 전 필독)

Worker에 배포하는 경우, 보충은 Cron 트리거에 의해 시작됩니다. 파라미터를 건드리기 전에
이 절을 끝까지 읽어 두세요.

#### 플랫폼이 거는 네 가지 상한

| 제한 항목 | 값 | 설명 |
|---------|----|----|
| 호출 1회의 월클록(wall-clock) | **15분(900초)** | Cron 트리거의 상한이며, 닿으면 플랫폼이 호출을 중단합니다. |
| `ctx.waitUntil()` | **이 상한을 연장하지 않습니다** | 그 유예 메커니즘은 HTTP 요청에만 적용되며, Cron으로 트리거된 호출에는 적용되지 않습니다. |
| CPU 시간 | 30초 | 보충 과정에서의 `await` 네트워크 요청(인증 코드 발송, 폴링 등)은 CPU 시간에 포함되지 않으므로 실제 병목이 되지는 않습니다. |
| 요청 단위 타임아웃 | 15초 | 레지스트라 경로의 **모든** HTTP 요청에 걸리는 고정값이며 설정할 수 없습니다. |

**요청 단위 타임아웃은 아래 두 가지 추정이 성립하기 위한 전제입니다**——이것이 없으면 멈춰
버린 연결 하나만으로도 한 라운드가 무한정 길어질 수 있습니다.

#### 한 라운드 소요 시간의 두 가지 추정

| 추정 | 공식 | 기본값에서의 결과 |
|----|----|-----------------|
| **일반적인 소요 시간** | `MINT_BATCH × CODE_TIMEOUT_MS` + 라운드 내 무작위 대기 | 600 + 20 ≈ **약 600~620초**, 900초의 월클록 상한까지 약 **30%의 여유** |
| **이론상 최악의 소요 시간**(발급 1회) | `CODE_TIMEOUT_MS + (1 + 3 × MAX_DOMAIN_ATTEMPTS + 3) × 15초` | 120 + 420 = **540초**, 여기에 `MINT_BATCH`를 곱하면 900초를 크게 넘습니다 |
| `REGISTRAR_FALLBACK`을 설정한 경우 | "최악 소요 시간" × 채널 수(즉 ×2) | 평상시 소요 시간은 그대로입니다 |

- **일반적인 경우**란 모든 요청이 빠르게 응답하고 첫 도메인이 차단되지 않은 상황으로,
  인증 코드 대기가 지배적입니다. 대략 `MINT_BATCH × CODE_TIMEOUT_MS` = 5 × 120초 = 600초,
  무작위 대기는 최대 4회·회당 최대 5초로 약 20초입니다.
- **최악의 경우 요청 수**는 이렇게 나옵니다. 한 번의 발급은 코드 폴링 외에 "도메인 목록
  1회 + 시도하는 도메인마다 3회(메일박스 생성·코드 발송·메일박스 삭제) + 3회(가입·로그인·
  key 생성)"를 보냅니다. 즉 **기본 설정도 극단적인 상황에서는 월클록 상한에 닿을 수
  있습니다**——의도적으로 받아들인 절충입니다. key는 발급 즉시 저장되므로 중단되어도 해당
  라운드가 미완성으로 끝날 뿐입니다. 극단적인 상황까지 월클록 안에 두고 싶다면
  `MINT_BATCH`를 1~2로 낮추거나 `CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS`를 줄이세요.
- **폴백 채널은 최악값만 끌어올리고 평상시 값은 바꾸지 않습니다.** 평상시에는 인증 코드가
  정상 도착하므로 폴백은 아예 사용되지 않습니다. "인증 코드가 오지 않음" 같은 채널 수준
  실패일 때만 같은 보충 슬롯이 폴백 채널에서 `CODE_TIMEOUT_MS`만큼 한 번 더 기다리게
  됩니다. 시작 시 뜨는 `TEND_INTERVAL_MS가 라운드 최악 소요 시간보다 작습니다` 경고도 이
  모델(`MINT_BATCH × CODE_TIMEOUT_MS × 채널 수`)을 사용합니다.

#### Worker는 월클록이 소진되기 전에 스스로 멈춥니다

**이것은 위의 "최악 소요 시간" 행은 커버하지만 "이론상 최악" 행은 커버하지 않습니다.**
발급을 한 번 시작하기 전마다 "남은 월클록으로 이번 한 번을 끝까지 돌릴 수 있는가"를 먼저
계산하고(판정식은 `CODE_TIMEOUT_MS × 채널 수` + 시도 간격), 부족하면 **아예 시작하지
않습니다**. 라운드를 일찍 끝내고 `registrar.round_budget_exhausted` 경고 이벤트를
기록합니다("이번 라운드 월클록 예산으로는 발급을 한 번 더 완주할 수 없어 조기 종료합니다"
라는 내용). 이미 발급된 key는 그대로 저장되고 남은 슬롯은 다음 스케줄로 넘어갑니다.
첫 번째 시도조차 들어가지 않는다면 다른 이벤트 `registrar.round_budget_impossible`
(레벨은 error)이 기록됩니다. 자세한 내용은 다음 소절을 참고하세요.

핵심은 "중간에 잘리는" 것이 아니라 "시작하지 않는" 것입니다. 플랫폼에 중단되면 그 순간
사용 중이던 임시 메일함이 삭제되지 못한 채 남습니다(YYDS는 약 24시간 후 `expiresAt`로,
MoeMail은 1시간 TTL로 만료). 따라서 Worker에서 **`MINT_BATCH`는 라운드당 상한이지
보장값이 아닙니다.** 그 라운드가 다 채워지지 않을 수 있습니다. Node/Docker에는 플랫폼
월클록 상한이 없어 **예약 라운드**에서는 이 메커니즘이 동작하지 않으며 `MINT_BATCH`를
그대로 모두 사용합니다.

> ⚠️ **다만 패널의 「지금 보충」은 예외로, 두 런타임 모두 동일한 라운드 예산을 사용합니다.**
> 한 번의 클릭이 최대 얼마나 오래 실행되는지는 그 버튼 자체의 성질이지 런타임의 성질이
> 아니므로, Node/Docker에서도 수동 보충은 발급 수가 줄어들 수 있습니다. 나머지는 다음 예약
> 라운드가 채웁니다.

**⚠️ 이 예산은 만능이 아니며 남는 시나리오가 있습니다.** 판정식에는 지배적인 항인
`CODE_TIMEOUT_MS × 채널 수`만 들어 있고, 15초 요청 단위 타임아웃과 403 백오프는 **의도적으로
넣지 않았습니다**. 넣으면 위의 "이론상 최악"이 애초에 900초를 넘기 때문에 단 한 번도 시작하지
못하게 됩니다. 예산은 월클록의 87%이며, 남은 약 120초가 그 꼬리를 흡수하는 여유입니다.

| 어느 층이 느린가 | 예산이 커버하는가 | 결과 |
|----------------|-----------------|----|
| **업스트림이 인증 코드를 못 보내주는 것뿐**(이 절에서 가장 흔한 느린 경우) | **완전히 커버됩니다** | 라운드를 조기 종료하고 남은 슬롯은 다음 스케줄로 |
| **거의 모든 HTTP 요청이 15초를 꽉 채워 멈춘다**(병적인 경우) | 한 번의 시도가 남겨둔 여유를 넘길 수 있습니다 | 그래도 플랫폼에 중단되어 그때의 임시 메일함이 남습니다 |

두 번째 행이 걱정된다면 위의 "이론상 최악" 공식으로 계산해 `MINT_BATCH`를 1~2로 낮추거나
`CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS`를 줄이세요.

#### 두 개의 로그: 상한 초과는 이벤트 이름으로 grep

**`CODE_TIMEOUT_MS`를 너무 크게 잡지 마세요.** `CODE_TIMEOUT_MS × 채널 수`가 라운드 예산
(월클록의 87%)을 넘으면 Worker에서는 **시도를 한 번도 시작할 수 없어** 보충이 매 라운드
아무것도 만들어내지 못합니다. 로그는 두 군데에 남습니다. **이벤트 이름**으로 grep하는 편이
더 확실합니다(아래 "문제 해결" 참고 — 문구는 표현 조정으로 바뀔 수 있고 읽고 있는 언어로
번역되어 있으리라는 보장도 없지만, 이벤트 이름은 바뀌지 않습니다).

- **시작 시**에는 **경고**(`console.warn`)가 남습니다. 이벤트 이름은
  `registrar.attempt_exceeds_worker_budget`(`grep 'registrar.attempt_exceeds_worker_budget'`)이며,
  대략 다음과 같은 형태입니다:
  `[registrar] registrar.attempt_exceeds_worker_budget CODE_TIMEOUT_MS×채널 수가 Worker
  라운드 월클록 예산을 초과했습니다 codeTimeoutMs=... chainLength=... worstAttemptMs=...
  workerRoundBudgetMs=...`.
  이 경고는 **게이트웨이 시작을 막지 않습니다** — "자격 증명이 없으면 시작 시점에 오류가
  나서 뜨지 않는다"와는 다릅니다. Node/Docker에는 플랫폼 월클록 상한이 없어 같은 설정도
  완전히 정상이므로, 두 런타임 모두 이 경고를 남기지만 실제로 영향을 받는 것은 Worker
  뿐입니다.
- **Worker의 보충 라운드마다**(첫 번째 시도조차 시작할 수 없을 때) **오류**
  (`console.error`)가 남습니다. 이벤트 이름은 `registrar.round_budget_impossible`
  (`grep 'registrar.round_budget_impossible'`)이며, 대략 다음과 같은 형태입니다:
  `[registrar] registrar.round_budget_impossible 한 번의 발급에 걸리는 최악 소요 시간이
  이미 이번 라운드 월클록 예산을 넘어, 단 한 번도 시작할 수 없습니다
  worstAttemptMs=... roundBudgetMs=...`.
  매 라운드 반복되므로 일시적인 상황이 아니라 지속 상태임을 확인할 수 있습니다.

**`MINT_BATCH`, `CODE_TIMEOUT_MS`, `MAX_DOMAIN_ATTEMPTS`를 늘리기 전에 위 두 공식으로 직접
계산해 보세요.** 상한에 닿으면 해당 Cron 호출은 플랫폼에 의해 중단됩니다. 중단되더라도 이미
발급된 key는 손실되지 않습니다——key는 발급되는 즉시 스토리지에 기록되므로, 중단된 라운드는
그저 미완성으로 끝날 뿐이며 다음 스케줄 주기에서 이어서 보충을 시도합니다.

## 부족분을 계산하는 방식(어떤 key가 `TARGET_KEYS` 자리를 차지하는가)

### 네 가지 key 상태와 자리 차지 여부

부족분 = `TARGET_KEYS` − **제외되지 않은 key의 수**. 판단 기준은 단 하나,
**`evicted`가 거짓이면 자리를 차지합니다.**

| key 상태 | `TARGET_KEYS` 자리를 차지하는가 | 업스트림에 쓸 수 있는가 |
|--------|-------------------------------|-----------------------|
| 신규 / 사용 가능 | 예 | 예 |
| **쿨다운 중**(속도 제한, 연속 실패) | **예** | 아니오 |
| **관리자가 비활성화** | **예** | 아니오 |
| 제외됨(401/403, 자격 증명 만료) | 아니오 | 아니오 |

### 왜 쿨다운 중인 key도 자리를 차지하는가

**"쿨다운도 자리를 차지한다"는 의도적입니다.** 쿨다운은 **스스로 돌아오는** 상태인데,
그것을 부족분으로 보고 새 계정을 발급하면 발급된 계정은 **스스로 사라지지 않습니다**
——한 번의 일시적 장애가 영구적인 비용으로 바뀝니다. 실측(`TARGET_KEYS=3`): 쿨다운을 자리로
세지 않으면 풀 전체가 속도 제한된 한 라운드에서 3개가 더 발급되어 ⇒ 풀이 6이 되고,
쿨다운이 끝나면 부족분이 음수가 되어 회수되지 않으므로 ⇒ **영구히 6에 머무릅니다**.
다음 폭풍에는 9, 그다음에는 12로 선형으로 늘어나며, 그 하나하나가 실제 Agnes 가입 1회와
실제로 소비된 임시 메일함 1개입니다.

**비용을 명시합니다**: 풀 전체가 쿨다운 중일 때 레지스트라는 대체분을 **발급하지 않습니다**.
쿨다운 동안 게이트웨이는 계속 `503`을 반환합니다(최대 `COOLDOWN_PAYMENT_MS` /
`COOLDOWN_STRIKE_MS` 한 번). 즉시 복구하려면 보충에 기대지 말고 관리 패널에서 해당 key에
"쿨다운 해제"를 사용하세요.

## 관리 패널의 "지금 보충"

관리 패널의 그 버튼입니다(`POST /admin/api/registrar/tend`). `202`는 **시작되었다**는 뜻이며,
보충은 응답 이후에도 계속 실행됩니다. 결과는 "보충 이력" 항목에서 확인하세요(`trigger`가
`manual`로 표시됩니다).

### 네 개의 가드레일

**네 개의 가드레일**이 있으며, 하나라도 만족하지 못하면 시작되지 않습니다:

| 가드레일 | 만족하지 못할 때 | 무엇을 막는가 |
|--------|----------------|-------------|
| 같은 프로세스 / 같은 isolate 내 진행 중 가드 | `409 tend_in_flight` | 정기 라운드와 버튼의 충돌, 한 복제본에서의 동시 두 번 클릭 |
| 스토리지 수준의 짧은 잠금(`registrar_tend_lock`) | `409 locked` | **복제본 간** 중첩(볼륨을 공유하는 여러 컨테이너, Worker의 두 isolate) |
| 수동 보충 사이 최소 10분 간격 | `429 manual_cooldown` | 연타로 임시 메일함 한도를 태우는 것 |
| 하루 최대 **24**회 | `429 write_budget_exhausted` | 연타로 **스토리지 쓰기 쿼터**를 태우는 것(계산식은 [DEPLOY.md](DEPLOY.md)의 "쿼터 계산") |

`429` 본문에는 `remaining`(오늘 남은 횟수), `resetAt`(UTC 자정에 회복), `retryAfterMs`가
들어갑니다. **`202` 본문에도 `remaining`이 들어갑니다** — 버튼이 눌리지 않게 된 뒤에야
알리는 대신, 남은 횟수를 처음부터 정직하게 보여주기 위해서입니다. 레지스트라가 꺼져 있으면
`409 registrar_disabled`를 반환합니다.

### 정직한 한정과 잔여 위험

⚠️ **정직한 한정 — "동시성 문제는 해결되었다"로 읽지 마세요.** KV는 최종 일관성이며, 이
스토리지 잠금은 **최선 노력일 뿐 상호 배제 프리미티브가 아닙니다**. 막을 수 있는 것은
"이전 라운드가 분명히 아직 돌고 있다"는 가장 흔한 중첩이며, 같은 밀리초에 발생한 두 번의
클릭은 여전히 둘 다 잠금을 얻을 수 있습니다. 가드 키와 보충 이력도 read-modify-write이므로
동시성 구간에서 갱신이 유실될 수 있습니다 — 상한은 "게이트가 최대 (동시 수 − 1)회를 더
통과시키고, 보충 이력이 최대 (동시 수 − 1)행을 놓친다"입니다.

⚠️ **잔여 위험**: 수동 보충은 Worker의 Cron과 **동일한 라운드 단위 월클록 예산(780초)**을
가집니다. 그 역할은 "완주할 수 없음이 뻔한 시도를 시작하지 않는 것"이며,
**유출을 없애지 않고 확률만 낮춥니다** — 플랫폼은 예산 구간 안에서도 호출을 중단할 수 있고,
그 순간 발급 중이던 임시 메일함은 삭제되지 않습니다. 정기 라운드와 다른 점에 유의하세요:
**Node/Docker의 정기 라운드에는 이 예산이 없고, 수동 보충에는 있습니다**. 그래서 같은 설정에서도
수동 라운드가 정기 라운드보다 적게 발급할 수 있으며, 남은 자리는 다음 정기 라운드로 넘어갑니다.

### 이 세 개의 키는 저절로 사라지지 않습니다

`registrar_tend_lock`, `registrar_manual_guard`, `tend:history` 세 키는 **모두 TTL이 없습니다**.
이름이 고정 리터럴이고 개수는 항상 1이며, 오래된 값은 언제나 **값 비교**로 판정되므로
(만료된 잠금은 아무도 막지 않고, 어제의 카운트는 세지 않습니다) 남아 있어도 무해합니다.

**비용을 명시합니다**: 레지스트라를 영구히 끄거나, 배포를 삭제하면서 KV 네임스페이스만 남기면
이 키들은 스스로 사라지지 않습니다. 정리하려면 직접 키를 삭제하세요:

- Worker: `wrangler kv key delete --binding=POOL registrar_manual_guard`(세 키 각각 한 번)
- Node / Docker: `DATA_DIR/store.json`을 편집해 해당 세 개의 최상위 필드를 삭제

**`tend:history`는 보통 남겨 두는 편이 좋습니다**: 사후 분석에서 가장 보고 싶은 것이며,
"레지스트라를 끈 지 N일 뒤에 보충 이력이 통째로 사라진다"는 최악의 타이밍입니다 — 운영자는
대개 무언가 문제가 생겼기 **때문에** 레지스트라를 끕니다.

## 발급된 key가 전달 경로에서 쓰이기까지

**최대 `POOL_CACHE_TTL_MS` 한 번(기본 60초)이며, "다음 요청부터"가 아닙니다.**

보충과 전달은 서로 독립적인 두 개의 key 풀 저장소 인스턴스를 씁니다. 보충 쪽은 매 라운드
저장소를 실제로 읽습니다(지금 진짜 사용 가능한 개수를 봐야 하며, 그렇지 않으면 중복 발급으로
메일함 할당량을 헛되이 씁니다). 전달 쪽은 isolate / 프로세스 단위 스냅숏을 들고 있습니다.
각자 자기 캐시를 유지하므로, 보충이 key를 쓴 뒤에도 전달 경로는 **자기 스냅숏**이 만료되어야
그것을 봅니다. Worker에서는 활성 isolate마다 각자의 TTL이 걸립니다.

**풀이 비었을 때 가장 오해하기 쉽습니다**: 로그에는 이미 `[registrar] … minted=1`이 찍혔는데
게이트웨이는 TTL 한 번 동안 계속 `503 pool_empty`를 반환합니다. 보충이 안 된 것이 아니므로
`POOL_CACHE_TTL_MS` 한 번을 기다리세요. 줄이고 싶으면 이 값을 작게 하면 됩니다(비용은
[DEPLOY.md](DEPLOY.md)의 "할당량 계산" 참조).

## key를 순차적으로 발급하고 동시에 발급하지 않는 이유

보충은 한 라운드 내에서 key를 **순차적으로** 발급하며, 시도 사이마다 무작위 대기 시간
을 둡니다. 여러 발급 요청을 동시에 실행하지 않습니다. 이는 성능상의 트레이드오프가
아니라 기능적 제약입니다. 동시 실행은 YYDS Mail의 메일함 생성 속도 제한(짧은 시간 안
에 약 10회를 초과해 생성하면 `403`을 반환)과 Agnes 자체의 등록 위험 관리 정책을 동시
에 건드리게 됩니다. 순차 실행과 무작위 대기는 레지스트라가 계속 작동하기 위한 전제
조건이며, 동시성으로 "최적화"해야 할 대상이 아닙니다.

## 개인정보 보호

등록 과정에서 생성되는 이메일 주소, 계정, 비밀번호는 메모리에만 잠시 존재하며, **사용
이 끝나면 즉시 폐기되고 영구 저장되지 않습니다.** 스토리지에는 오직 발급된 API key
기록만 남습니다. 임시 메일함은 발급 성공 여부와 관계없이 시도가 끝나면 삭제됩니다.

## 문제 해결

### 시작과 로그의 약속

- **활성화했는데 자격 증명이 없으면, 시작 시점에 오류가 발생하며 어떤 항목이 빠졌는지
  알려줍니다.** 레지스트라는 페일클로즈(fail-closed) 정책을 따르므로, 자격 증명 누락
  이 조용히 무시되지 않고 게이트웨이가 명확하게 실패해 문제를 쉽게 찾을 수 있습니다.
- 보충 과정의 로그에는 일관되게 `[registrar]` 접두사가 붙으므로, 이를 기준으로 필터
  링해 볼 수 있습니다. 각 로그 줄의 두 번째 필드는 안정적인 기계 판독용 **이벤트
  이름**(예: `registrar.round_budget_impossible`)입니다. 이벤트 이름으로 grep하는 편이
  사람이 읽는 문구로 grep하는 것보다 확실합니다 — 문구는 표현 조정으로 바뀔 수 있지만,
  이벤트 이름은 이 로그의 유일하게 안정적인 대외 계약이며 바뀌지 않습니다.
### `reasons=`의 실패 원인 읽기

- **한 라운드에서 발급되지 않은 슬롯이 있으면 마무리 로그에 `reasons=`가 붙은 경고가 한
  줄 더 남습니다**(예: `reasons=yyds:register_failed×3 moemail:code_timeout×1`). 먼저 이
  줄로 어느 계층의 장애인지 판단하세요. `code_timeout` = 이 채널이 Agnes의 메일을 받지
  못함(도메인 MX / 전달 규칙); `register_failed` / `login_failed` / `key_failed` = Agnes
  쪽 가입 경로가 바뀜; `provider_error` = 메일함 서비스 자체(자격 증명, 활성 메일함 한도,
  서비스 장애); `provider_missing` = 내부 배선 오류이며 정상적인 설정에서는 나타나지 않습니다
  (자격 증명 누락은 시작 시점에 바로 오류가 나므로 여기까지 오지 않습니다).
- **`reasons=`에 `key_suspicious`가 나오는 경우**: 업스트림이 돌려준 key 내용에 출력 불가
  문자나 공백이 들어 있습니다. **그 라운드는 실제로 발급에 성공했습니다**(Agnes 쪽 계정이
  실제로 생성되었고 임시 메일함도 실제로 소비되었습니다). 그래서 그 key는 **그대로 풀에
  저장됩니다** — 여기서 거부하는 것은 두 번 다시 되찾을 수 없는 자격 증명을 파기하는 일이기
  때문입니다. 다만 선택될 때마다 전달이 실패할 가능성이 높으니 관리 패널에서 비활성화하거나
  삭제하세요. 동시에 `registrar.minted_key_suspicious` error 이벤트가 남습니다(채널과 길이만
  기록하며 **평문은 기록하지 않습니다**).
### 어떤 채널이 계속 실패할 때

- 특정 채널에서 등록이 계속 실패한다면(예: Agnes가 인증 코드나 CAPTCHA 정책을 강화한
  경우), 이는 코드 수준에서는 우회할 수 없는 업스트림 측 변화입니다. 레지스트라를 비
  활성화하고 대신 key를 수동으로 임포트할 수 있습니다([DEPLOY.md](DEPLOY.md) 참고).
