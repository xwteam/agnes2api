# 레지스트라(자동 키 풀 보충)

이 문서는 레지스트라를 다룹니다. 무엇을 하는지, 두 메일함 채널 중 무엇을 고를지, 어떤 설정 항목이 있는지, 돌린 뒤 로그를 어떻게 읽고 문제 해결은 어떻게 하는지를 설명합니다.

> **기본값은 비활성화입니다.** `REGISTRAR_ENABLED`의 기본값은 `false`이며, 설치만으로는
> 어떠한 계정 등록도 자동으로 시작되지 않습니다. 명시적으로 `true`로 설정해야만 레지스
> 트라가 작동합니다.

## 이것은 무엇인가

레지스트라는 선택적 구성 요소입니다. key 풀 안의 사용 가능한 key 수가 `TARGET_KEYS`
아래로 떨어지면, 새로운 Agnes 계정을 자동으로 등록하고 로그인한 뒤 API key를 발급해
풀에 채워 넣습니다. 등록 과정에서 Agnes가 보내는 인증 코드를 수신해야 하므로, 아래의
메일함 채널 중 하나에 의존합니다.

> [!WARNING]
> **컴플라이언스 안내**
>
> 대량 계정 등록은 Agnes 서비스 약관과 긴장 관계에 있습니다. 레지스트라를 활성화할지,
> 어떤 빈도로 사용할지는 운영자 스스로 판단하고 그에 따른 책임을 져야 하는 사안입니다
> ——본 프로젝트는 이 결정을 대신 내리지 않습니다.

## 두 메일함 채널: 어떻게 선택할까

레지스트라는 인증 코드를 수신하기 위해 두 가지 메일함 채널을 지원합니다.

### 두 채널 비교

| | YYDS Mail | MoeMail |
|----|---------|-------|
| 성격 | 제3자 임시 메일함 서비스 | 직접 호스팅하는 임시 메일함 서비스 |
| API base URL | 기본값 있음(`YYDS_BASE_URL`, 공개 API 엔드포인트) | 기본값 없음(`MOEMAIL_BASE_URL`), 직접 배포한 인스턴스 주소를 입력 |
| 자격 증명 발급 방법 | 해당 서비스에 API Key 신청(`YYDS_API_KEY`) | 직접 배포한 인스턴스에서 API Key 생성(`MOEMAIL_API_KEY`) |
| 주소를 쓰는 방법 | 서비스의 루트 주소, `/v1` 같은 API 경로 접두사는 붙이지 않음 | 인스턴스의 루트 주소, 마찬가지로 접두사는 붙이지 않음 |

마지막 행은 따로 짚어 둘 만합니다. 게이트웨이가 외부에 제공하는 `AGNES_BASE_URL`에는 `/v1`이
**붙지만** 이 둘은 서로 다른 것이며, 한쪽을 그대로 옮겨 적는 것이 가장 흔한 실수입니다.
`…/v1`로 적으면 레지스트라는 `…/v1/v1/domains`를 조립하고 업스트림은 404를 돌려줍니다.
이런 실패는 이제 **실제로 요청한 주소**를 이벤트에 남깁니다(주소 안의 사용자 이름/비밀번호,
쿼리 문자열, 프래그먼트는 자리표시자로 바뀝니다). 이벤트를 한 번만 보면 이 함정을 알아볼 수
있습니다.

### 어떤 채널을 쓸지 고르기

> [!IMPORTANT]
> **두 채널 중 하나만 고릅니다. 주/보조라는 관계가 없고 자동 전환도 없습니다.**
> 두 채널은 완전히 대등하며, 본 프로젝트는 어느 쪽도 미리 고르지 않고 어느 쪽도
> 추천하지 않습니다.

`REGISTRAR_CHANNEL`은 기본값이 없으며, 레지스트라를 활성화할 때 `yyds` 또는 `moemail`
중 하나를 명시적으로 지정해야 합니다. 선택한 쪽이 인증 코드를 받고, 다른 쪽은
**입력해도 사용되지 않습니다**. 다만 미리 설정해 두면 언제든 전환할 수 있습니다.

> [!WARNING]
> **선택한 채널이 실패해도 레지스트라가 다른 채널로 바꿔 쓰지 않습니다.**
> 인증 코드가 오지 않는 상황(도메인 MX 레코드 만료, 메일 전달 규칙 삭제 — API는 모두
> 2xx를 반환하는데 메일만 영영 오지 않음)은 곧 "이 채널은 지금 key를 만들어 낼 수 없다"이며,
> 직접 채널을 바꿀 때까지 그 라운드, 경우에 따라서는 그날 내내 하나도 발급되지 않습니다.
> 구체적인 동작은 아래 "채널이 실패한 뒤에는 어떻게 되나"를 보세요.

#### 옛 이름은 어떻게 되나

> 이 항목은 예전에 `REGISTRAR_PRIMARY`였고 옆에 `REGISTRAR_FALLBACK`이 있었습니다.
> 옛 주 채널 이름은 **호환 별칭으로 계속 남습니다**(새 이름보다 우선순위가 낮고, 사용 중이면
> 패널 상단에 알림이 뜹니다). 옛 보조 채널 변수는 **더 이상 경로 선택에 관여하지 않지만**,
> 패널에서 "이 채널은 폐기되었다"고 이름을 짚어 알려 주기 위해 한 번만 읽힙니다.
> 두 옛 이름 모두 업그레이드 중인 배포를 멈추게 하지 않습니다.

### 그 한 채널은 어떻게 고르나

판단 기준: 레지스트라는 "도메인을 바꿔가며" Agnes가 일회용 메일함 도메인을 차단하는
것을 우회합니다. 사용 가능한 도메인이 많을수록 레지스트라가 더 오래 작동합니다. 양쪽
서비스에서 각각 사용 가능한 도메인이 몇 개인지 확인해 보면, 더 많은 쪽이 더 오래 갑니다
——이는 어느 서비스인지와는 무관하며, 오직 당신 자신의 계정이나 자체 호스
팅 환경의 설정에 달려 있습니다.

## 내장된 자격 증명은 없습니다 — 직접 준비하세요

이 저장소에는 실제 키, 계정, 프라이빗 도메인이 전혀 포함되어 있지 않습니다. 레지스트
라를 활성화하기 전에 다음을 직접 준비해야 합니다.

### 채널별로 준비할 것

- **YYDS Mail을 사용하는 경우**: 해당 서비스에 API Key를 신청해 `YYDS_API_KEY`에 설정
  합니다(`YYDS_BASE_URL`은 이미 기본값이 있어 보통 변경할 필요가 없습니다).
- **MoeMail을 사용하는 경우**: MoeMail 인스턴스를 직접 호스팅하고, 접속 주소를
  `MOEMAIL_BASE_URL`에, 해당 인스턴스에서 생성한 API Key를 `MOEMAIL_API_KEY`에 설정합
  니다(둘 다 기본값이 없으므로 반드시 명시적으로 설정해야 합니다).

### 최소한 어디까지 준비해야 하나

최소한 `REGISTRAR_CHANNEL`이 가리키는 채널의 자격 증명은 준비해야 합니다. 다른 채널의
자격 증명은 미리 채워도 되고 비워 두어도 됩니다. 레지스트라가 시작되는지 여부에는 영향을
주지 않습니다. 채워 두면 패널에서 그 채널의 "설정됨" 표시와 "연결 테스트" 버튼을 쓸 수
있어, 전환하기 전에 둘을 비교해 볼 수 있습니다.

## 설정 항목

```env
# ── 스위치와 채널 ─────────────────────────────────────────────────
# 마스터 스위치. true일 때만 레지스트라가 활성화됩니다. (선택, 기본값 false)
REGISTRAR_ENABLED=false
# 레지스트라가 사용할 채널. yyds 또는 moemail. 둘 중 하나만 고릅니다. 기본값 없음.
# (활성화 시 필수) 옛 이름 REGISTRAR_PRIMARY는 호환 별칭으로 계속 남고,
# 옛 보조 채널 변수는 경로 선택에 관여하지 않습니다.
REGISTRAR_CHANNEL=

# ── 보충 속도 ─────────────────────────────────────────────────────
# 목표 사용 가능 key 수. 이보다 적을 때만 보충이 시작됩니다. (선택, 기본값 20)
TARGET_KEYS=20
# 한 라운드에서 발급할 key의 최대 개수. (선택, 기본값 5)
MINT_BATCH=5
# Node 쪽 보충 스케줄 간격(ms). Worker 쪽은 wrangler.toml의 Cron이 결정합니다(아래 참고).
# (선택, 기본값 1800000 = 30분, Node/Docker만 읽음)
TEND_INTERVAL_MS=1800000
# 발급 1회당 인증 코드 대기 타임아웃(ms). (선택, 기본값 120000 = 120초)
CODE_TIMEOUT_MS=120000
# 한 라운드 안에서 발급 사이 무작위 대기의 하한 / 상한(ms). (선택, 기본값 60000 / 90000)
# 하한은 실측값입니다: 같은 발신 주소에서 60초 이상 간격을 두면 연속으로 성공했지만,
# 간격 없이 연달아 보내면 세 번째에 업스트림 앞단 속도 제한에 걸렸고 처벌 구간은 십수 분이었습니다.
# 상한은 지터 여유일 뿐 실측값이 아닙니다.
MINT_DELAY_MIN_MS=60000
MINT_DELAY_MAX_MS=90000
# 발급 1회에서 시도할 임시 메일함 도메인의 최대 개수. (선택, 기본값 1)
# 등록기는 이제 «업스트림이 이 도메인을 받아주는가»를 기억해 재사용하므로,
# 정상 상태에서는 발급 1회 성공당 코드 전송 요청이 정확히 1회입니다.
# 이 값을 키우면 라운드마다 소모하는 속도 제한 여유가 그만큼 늘어납니다(실측 여유는 구간당 약 4~6회).
MAX_DOMAIN_ATTEMPTS=1
# 발급된 Agnes API key가 Agnes 대시보드에 표시될 이름. (선택, 기본값 auto)
REGISTRAR_TOKEN_NAME=auto

# ── 업스트림과 채널 자격 증명 ─────────────────────────────────────
# 가입·로그인·key 생성에 사용하는 Agnes 플랫폼 백엔드 주소(벤더의 공개 엔드포인트).
# (선택)
AGNES_PLATFORM_URL=https://platform-backend.agnes-ai.com
# YYDS Mail의 API base URL(벤더의 공개 엔드포인트)과 그 API Key.
# (base URL은 선택. Key는 채널이 yyds일 때 필수이며, 이 저장소는 실제 자격 증명을
#  전혀 포함하지 않습니다)
YYDS_BASE_URL=https://maliapi.215.im
YYDS_API_KEY=
# 직접 배포한 MoeMail 인스턴스 주소와 그 API Key. 둘 다 기본값이 없습니다.
# (채널이 moemail일 때 필수)
MOEMAIL_BASE_URL=
MOEMAIL_API_KEY=
```

위 블록의 모든 변수는 `.env.example`에 한 줄씩 들어 있으며(대개 기본값으로 충분하므로
따로 고칠 일은 드뭅니다), 두 배포 대상 모두 이 값을 읽어 들입니다. 위의 수치형 변수는
모두 양의 정수여야 하며, 그렇지 않으면 게이트웨이가 기동을 거부합니다.

## 두 런타임 간 스케줄링 차이

### 누가 트리거하고 간격은 어디서 오는가

| 배포 대상 | 트리거 방식 | 간격을 결정하는 요소 |
|---------|-----------|--------------------|
| Cloudflare Worker | `wrangler.toml`의 `[triggers]`에 설정한 Cron(기본값 `*/30 * * * *`, 30분마다) | `wrangler.toml`의 cron 표현식을 수정 |
| Node / Docker | 프로세스 내 타이머 | `TEND_INTERVAL_MS`(기본값 `1800000`ms) |

두 설정은 각각 다음과 같은 형태입니다:

```toml
# wrangler.toml -- Worker 형태의 트리거 간격은 여기서만 결정됩니다
[triggers]
crons = ["*/30 * * * *"]
```

```env
# .env -- Node / Docker 형태의 트리거 간격(밀리초)
TEND_INTERVAL_MS=1800000
```

두 런타임 모두 결국 **동일한 보충 함수**를 호출합니다. 차이는 **누가 제때 호출할 책임을
지는가**, 그리고 **트리거 간격이 어디서 오는가**입니다:

| | 트리거 | 간격의 출처 | 바꾸면 |
|----|------|-----------|------|
| Node / Docker | 프로세스 내 자체 재스케줄 타이머 | `TEND_INTERVAL_MS`(환경 변수 > 저장된 설정 > 기본값 `1800000`) | **다음 라운드부터 적용**(현재 라운드는 기존 간격으로 끝까지 진행. 기본값 기준 최대 30분). **재시작 불필요** |
| Cloudflare Worker | 플랫폼의 Cron Trigger | `wrangler.toml`의 `[triggers].crons` | **설정을 바꿔도 반영되지 않음**. `wrangler.toml`을 수정하고 재배포해야 함 |

트리거 간격을 제외한 나머지 보충 설정 항목(`TARGET_KEYS` / `MINT_BATCH` / 채널 자격 증명 등)은
두 런타임에서 실제로 완전히 동일합니다.

### Cloudflare Cron 트리거의 월클록(wall-clock) 상한(파라미터 조정 전 필독)

Worker에 배포하는 경우, 보충은 Cron 트리거에 의해 시작됩니다. 파라미터를 건드리기 전에
이 절을 끝까지 읽어 두세요.

#### 플랫폼이 거는 네 가지 상한

| 제한 항목 | 값 | 설명 |
|---------|----|----|
| 호출 1회의 월클록(wall-clock) | **15분(900초)** | Cron 트리거의 상한이며, 닿으면 플랫폼이 호출을 중단합니다. |
| `ctx.waitUntil()` | **이 상한을 연장하지 않습니다** | 그 유예 메커니즘은 HTTP 요청에만 적용되며, Cron으로 트리거된 호출에는 적용되지 않습니다. |
| CPU 시간 | 30초 | 보충 과정에서의 `await` 네트워크 요청(인증 코드 발송, 폴링 등)은 CPU 시간에 포함되지 않으므로 실제 병목이 되지는 않습니다. |
| 요청 단위 타임아웃 | 15초 | 레지스트라 경로의 **모든** HTTP 요청에 걸리는 고정값이며 설정할 수 없습니다. |

**요청 단위 타임아웃은 아래 두 가지 추정이 성립하기 위한 전제입니다**——이것이 없으면 멈춰
버린 연결 하나만으로도 한 라운드가 무한정 길어질 수 있습니다.

#### 한 라운드 소요 시간의 두 가지 추정

| 추정 | 공식 | 기본값에서의 결과 |
|----|----|-----------------|
| **일반적인 소요 시간** | `MINT_BATCH × CODE_TIMEOUT_MS` + `(MINT_BATCH − 1) × MINT_DELAY_MAX_MS` | 600 + 360 = **960초**로 **이미 900초 월클록 상한을 넘습니다**(아래 "Worker는 월클록이 소진되기 전에 스스로 멈춥니다" 참고) |
| **이론상 최악의 소요 시간**(발급 1회) | `CODE_TIMEOUT_MS + (3 × MAX_DOMAIN_ATTEMPTS + 3) × 15초 + (MAX_DOMAIN_ATTEMPTS − 1) × MINT_DELAY_MAX_MS` | 120 + 90 = **210초**(내장값 1) |

- **일반적인 경우**란 모든 요청이 빠르게 응답하는 상황입니다. `MINT_BATCH × CODE_TIMEOUT_MS` =
  5 × 120초 = 600초에 최대 90초짜리 대기 4번 = 360초가 더해집니다.
- **이 대기 항은 이제 무시할 수 없습니다.** `MINT_DELAY_MAX_MS`가 5초에서 90초로
  바뀌면서 20초에서 360초로 늘었고, 라운드 최악은 960초 > 900초입니다.
  **새로운 결함이 아닙니다** — 아래 라운드 예산이 이것을 위해 있습니다.
- **최악의 경우 요청 수**는 코드 폴링 외에 "시도하는 도메인마다 3회 + 3회(가입·로그인·
  key 생성)"입니다. 도메인 목록 조회는 **라운드 단위**로 옮겨졌습니다(라운드당 1회).
  월클록 안에 두고 싶다면 `MINT_BATCH`를 1~2로 낮추거나
  `CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS`를 줄이세요.
- **여기에는 예전에 "채널 수"라는 계수가 있었습니다.** 두 채널이 주/보조 관계였을 때는
  "인증 코드가 오지 않음"이면 폴백으로 재시도했기 때문에, 같은 보충 슬롯이 두 채널에서
  각각 `CODE_TIMEOUT_MS`만큼 기다려야 했습니다. 둘 중 하나만 고르는 방식이 된 지금은
  두 번째 대기가 없어 이 계수는 통째로 사라졌습니다. 시작 시 뜨는
  `TEND_INTERVAL_MS가 라운드 최악 소요 시간보다 작습니다` 경고도 이
  모델(`MINT_BATCH × CODE_TIMEOUT_MS + (MINT_BATCH − 1) × MINT_DELAY_MAX_MS`)을 사용합니다.

#### Worker는 월클록이 소진되기 전에 스스로 멈춥니다

**이것은 위의 "최악 소요 시간" 행은 커버하지만 "이론상 최악" 행은 커버하지 않습니다.**
발급을 한 번 시작하기 전마다 "남은 월클록으로 이번 한 번을 끝까지 돌릴 수 있는가"를 먼저
계산하고(판정식은 `CODE_TIMEOUT_MS` + 시도 간격), 부족하면 **아예 시작하지
않습니다**. 라운드를 일찍 끝내고 `registrar.round_budget_exhausted` 경고 이벤트를
기록합니다("이번 라운드 월클록 예산으로는 발급을 한 번 더 완주할 수 없어 조기 종료합니다"
라는 내용). 이미 발급된 key는 그대로 저장되고 남은 슬롯은 다음 스케줄로 넘어갑니다.
첫 번째 시도조차 들어가지 않는다면 다른 이벤트 `registrar.round_budget_impossible`
(레벨은 error)이 기록됩니다. 자세한 내용은 다음 소절을 참고하세요.

핵심은 "중간에 잘리는" 것이 아니라 "시작하지 않는" 것입니다. 플랫폼에 중단되면 그 순간
사용 중이던 임시 메일함이 삭제되지 못한 채 남습니다(YYDS는 약 24시간 후 `expiresAt`로,
MoeMail은 1시간 TTL로 만료). 따라서 Worker에서 **`MINT_BATCH`는 라운드당 상한이지
보장값이 아닙니다.** 그 라운드가 다 채워지지 않을 수 있습니다. Node/Docker에는 플랫폼
월클록 상한이 없어 **예약 라운드**에서는 이 메커니즘이 동작하지 않으며 `MINT_BATCH`를
그대로 모두 사용합니다.

> [!IMPORTANT]
> **다만 패널의 「지금 보충」은 예외로, 두 런타임 모두 버튼 몫의 상한을 씁니다**
> (예산 70초·최대 1개). 한 번의 클릭이 얼마나 걸리는지는 버튼의 성질이지 런타임의 성질이
> 아니므로, Node/Docker에서도 수동 보충은 정기 라운드보다 적게 발급합니다. 나머지는 다음
> 예약 라운드가 채웁니다.

> [!WARNING]
> **이 예산은 만능이 아니며 남는 시나리오가 있습니다.** 판정식은
> `CODE_TIMEOUT_MS + (MAX_DOMAIN_ATTEMPTS − 1) × MINT_DELAY_MAX_MS`이며, 15초 요청 단위
> 타임아웃은 **의도적으로 넣지 않았습니다**. 넣으면 단 한 번도 시작하지 못하게 됩니다.
> 예산은 월클록의 87%이며, 남은 약 120초가 그 꼬리를 흡수하는 여유입니다.
>
> **이 문단은 예전에 "403 백오프"를 언급했지만, 그것은 죽은 분기를 가리키는 말이었습니다.**
> 속도 제한에 걸리면 이제 **그 자리에서 라운드 전체를 끝내고 라운드를 넘는 백오프 구간을
> 기록합니다**. "잠깐 기다렸다가 계속 두드린다"는 동작은 더 이상 없습니다(아래
> "업스트림 속도 제한에 걸리면 어떻게 되는가" 참고).

| 어느 층이 느린가 | 예산이 커버하는가 | 결과 |
|----------------|-----------------|----|
| **업스트림이 인증 코드를 못 보내주는 것뿐**(이 절에서 가장 흔한 느린 경우) | **완전히 커버됩니다** | 라운드를 조기 종료하고 남은 슬롯은 다음 스케줄로 |
| **거의 모든 HTTP 요청이 15초를 꽉 채워 멈춘다**(병적인 경우) | 한 번의 시도가 남겨둔 여유를 넘길 수 있습니다 | 그래도 플랫폼에 중단되어 그때의 임시 메일함이 남습니다 |

두 번째 행이 걱정된다면 위의 "이론상 최악" 공식으로 계산해 `MINT_BATCH`를 1~2로 낮추거나
`CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS`를 줄이세요.

#### 두 개의 로그: 상한 초과는 이벤트 이름으로 grep

**`CODE_TIMEOUT_MS`를 너무 크게 잡지 마세요.** `CODE_TIMEOUT_MS`가 라운드 예산
(월클록의 87%)을 넘으면 Worker에서는 **시도를 한 번도 시작할 수 없어** 보충이 매 라운드
아무것도 만들어내지 못합니다. 로그는 두 군데에 남습니다. **이벤트 이름**으로 grep하는 편이
더 확실합니다(아래 "문제 해결" 참고 — 문구는 표현 조정으로 바뀔 수 있고 읽고 있는 언어로
번역되어 있으리라는 보장도 없지만, 이벤트 이름은 바뀌지 않습니다).

아래 두 펜스는 게이트웨이가 **그대로** 출력하는 원문입니다. `msg`는 소스에 간체 중국어로
하드코딩되어 있어 **이 페이지의 언어로 번역되지 않습니다**. 한 건의 로그도 항상 **한 줄**입니다
—— `src/adapters/logger-console.ts`가 줄바꿈을 공백으로 눌러버리기 때문인데, 이어지는 줄에는
`[registrar]` 접두사가 없어 유실되기 때문입니다. 따라서 grep은 이벤트 이름으로 하고 이 페이지의
번역문으로는 하지 마세요.

**① 시작 시**에는 **경고**(`console.warn`)가 남습니다. 이벤트 이름은
`registrar.attempt_exceeds_worker_budget`(`grep 'registrar.attempt_exceeds_worker_budget'`)이며,
대략 다음과 같은 형태입니다:

```text
[registrar] registrar.attempt_exceeds_worker_budget CODE_TIMEOUT_MS 超过 Worker 单轮墙钟预算：Cloudflare Worker 形态下补池会一把 key 都铸不出来（每轮 attempted=0），请调小 CODE_TIMEOUT_MS。Node/Docker 的定时轮没有平台墙钟上限、不受此限制，但面板的「立即补池」在两种运行时上都带同一份轮级预算，Node/Docker 上同样铸不出来。 codeTimeoutMs=... worstAttemptMs=... workerRoundBudgetMs=...
```

이 경고는 **게이트웨이 시작을 막지 않습니다** — "자격 증명이 없으면 시작 시점에 오류가
나서 뜨지 않는다"와는 다릅니다. Node/Docker에는 플랫폼 월클록 상한이 없어 같은 설정도
완전히 정상이므로, 두 런타임 모두 이 경고를 남기지만 실제로 영향을 받는 것은 Worker
뿐입니다.

**② Worker의 보충 라운드마다**(첫 번째 시도조차 시작할 수 없을 때) **오류**
(`console.error`)가 남습니다. 이벤트 이름은 `registrar.round_budget_impossible`
(`grep 'registrar.round_budget_impossible'`)이며, 대략 다음과 같은 형태입니다:

```text
[registrar] registrar.round_budget_impossible 单次铸 key 的最坏耗时已超过本轮墙钟预算，一次尝试都无法开始，补池将持续零产出——这是配置问题不是瞬时状况，请调小 CODE_TIMEOUT_MS worstAttemptMs=... roundBudgetMs=...
```

매 라운드 반복되므로 일시적인 상황이 아니라 지속 상태임을 확인할 수 있습니다.

**`MINT_BATCH`, `CODE_TIMEOUT_MS`, `MAX_DOMAIN_ATTEMPTS`를 늘리기 전에 위 두 공식으로 직접
계산해 보세요.** 상한에 닿으면 해당 Cron 호출은 플랫폼에 의해 중단됩니다. 중단되더라도 이미
발급된 key는 손실되지 않습니다——key는 발급되는 즉시 스토리지에 기록되므로, 중단된 라운드는
그저 미완성으로 끝날 뿐이며 다음 스케줄 주기에서 이어서 보충을 시도합니다.

## 부족분을 계산하는 방식(어떤 key가 `TARGET_KEYS` 자리를 차지하는가)

### 네 가지 key 상태와 자리 차지 여부

부족분 = `TARGET_KEYS` − **제외되지 않은 key의 수**. 판단 기준은 단 하나,
**`evicted`가 거짓이면 자리를 차지합니다.**

| key 상태 | `TARGET_KEYS` 자리를 차지하는가 | 업스트림에 쓸 수 있는가 |
|--------|-------------------------------|-----------------------|
| 신규 / 사용 가능 | 예 | 예 |
| **쿨다운 중**(속도 제한, 연속 실패) | **예** | 아니오 |
| **관리자가 비활성화** | **예** | 아니오 |
| 제외됨(401/403, 자격 증명 만료) | 아니오 | 아니오 |

### 왜 쿨다운 중인 key도 자리를 차지하는가

**"쿨다운도 자리를 차지한다"는 의도적입니다.** 쿨다운은 **스스로 돌아오는** 상태인데,
그것을 부족분으로 보고 새 계정을 발급하면 발급된 계정은 **스스로 사라지지 않습니다**
——한 번의 일시적 장애가 영구적인 비용으로 바뀝니다. 실측(`TARGET_KEYS=3`): 쿨다운을 자리로
세지 않으면 풀 전체가 속도 제한된 한 라운드에서 3개가 더 발급되어 ⇒ 풀이 6이 되고,
쿨다운이 끝나면 부족분이 음수가 되어 회수되지 않으므로 ⇒ **영구히 6에 머무릅니다**.
다음 폭풍에는 9, 그다음에는 12로 선형으로 늘어나며, 그 하나하나가 실제 Agnes 가입 1회와
실제로 소비된 임시 메일함 1개입니다.

**비용을 명시합니다**: 풀 전체가 쿨다운 중일 때 레지스트라는 대체분을 **발급하지 않습니다**.
쿨다운 동안 게이트웨이는 계속 `503`을 반환합니다(최대 `COOLDOWN_PAYMENT_MS` /
`COOLDOWN_STRIKE_MS` 한 번). 즉시 복구하려면 보충에 기대지 말고 관리 패널에서 해당 key에
"쿨다운 해제"를 사용하세요.

## 관리 패널의 "지금 보충"

관리 패널의 그 버튼입니다(`POST /admin/api/registrar/tend`). 버튼은 **한 라운드가 끝날 때까지
기다렸다가** `200`과 함께 그 라운드의 결과(발급 수, 시도 수)를 돌려줍니다 — 길면 2분쯤
걸립니다. 예전처럼 `202`로 먼저 답하고 나머지를 뒤에서 계속 돌리는 방식이 아닙니다. 그
방식에서는 Cloudflare가 응답이 끝난 뒤 약 30초 만에 남은 작업을 취소했고, 취소는 예외를
던지지 않으므로 보충 이력도 이벤트도 남지 않고 잠금까지 그대로 물려 있었습니다 — 패널에서
그 한 바퀴는 "누른 적이 없다"와 구분되지 않았습니다.

연결이 중간에 끊기면 패널은 **"결과를 알 수 없으며 아직 돌고 있을 수 있다"**고 표시합니다.
성공으로도 실패로도 그리지 않습니다. 끝까지 돈 라운드는 "보충 이력" 항목에도 남습니다
(`trigger`가 `manual`로 표시됩니다).

한 번의 클릭에는 **정기 라운드와 다른, 이 버튼 몫의 상한**이 붙습니다: 한 번에 최대 1개
발급, 인증 코드 대기 60초, 도메인 시도 1회, 라운드 예산 70초. 앞의 세 값은 설정값과 비교해
**작은 쪽**을 쓰므로, 더 작게 잡아 둔 설정이 이 상한 때문에 커지는 일은 없습니다. 실제로
눌린 경우에는 응답 본문의 `outcome.capped`가 누르기 전과 뒤의 값을 함께 알려 줍니다.
남은 부족분은 다음 정기 라운드가 채웁니다.

### 네 개의 가드레일

**네 개의 가드레일**이 있으며, 하나라도 만족하지 못하면 시작되지 않습니다:

| 가드레일 | 만족하지 못할 때 | 무엇을 막는가 |
|--------|----------------|-------------|
| 같은 프로세스 / 같은 isolate 내 진행 중 가드 | `409 tend_in_flight` | 정기 라운드와 버튼의 충돌, 한 복제본에서의 동시 두 번 클릭 |
| 스토리지 수준의 짧은 잠금(`registrar_tend_lock`) | `409 locked` | **복제본 간** 중첩(볼륨을 공유하는 여러 컨테이너, Worker의 두 isolate) |
| 수동 보충 사이 최소 10분 간격 | `429 manual_cooldown` | 연타로 임시 메일함 한도를 태우는 것 |
| 하루 최대 **24**회 | `429 write_budget_exhausted` | 연타로 **스토리지 쓰기 쿼터**를 태우는 것(계산식은 [DEPLOY.md](DEPLOY.md)의 "쿼터 계산") |

`429` 본문에는 `remaining`(오늘 남은 횟수), `resetAt`(UTC 자정에 회복), `retryAfterMs`가
들어갑니다. **`200` 본문에도 `remaining`이 들어갑니다** — 버튼이 눌리지 않게 된 뒤에야
알리는 대신, 남은 횟수를 처음부터 정직하게 보여주기 위해서입니다. 레지스트라가 꺼져 있으면
`409 registrar_disabled`를 반환합니다.

표 둘째 줄의 그 잠금은 **경로마다 유효 기간이 다릅니다**: 수동 라운드가 쥐면 180초,
정기 라운드가 쥐면 900초입니다. 플랫폼에 중단되어 잠금이 남더라도 180초는 수동 쿨다운
600초보다 짧으므로, 다음 클릭도 그 사이의 정기 라운드도 그 잠금에 막히지 않습니다.

### 정직한 한정과 잔여 위험

> [!WARNING]
> **정직한 한정 — "동시성 문제는 해결되었다"로 읽지 마세요.** KV는 최종 일관성이며, 이
> 스토리지 잠금은 **최선 노력일 뿐 상호 배제 프리미티브가 아닙니다**. 막을 수 있는 것은
> "이전 라운드가 분명히 아직 돌고 있다"는 가장 흔한 중첩이며, 같은 밀리초에 발생한 두 번의
> 클릭은 여전히 둘 다 잠금을 얻을 수 있습니다. 가드 키와 보충 이력도 read-modify-write이므로
> 동시성 구간에서 갱신이 유실될 수 있습니다 — 상한은 "게이트가 최대 (동시 수 − 1)회를 더
> 통과시키고, 보충 이력이 최대 (동시 수 − 1)행을 놓친다"입니다.

> [!WARNING]
> **잔여 위험**: 수동 보충은 **자기 몫의 라운드 단위 월클록 예산 70초**를 가집니다
> (Worker Cron의 780초와 다른 값입니다). 그 역할은 "완주할 수 없음이 뻔한 시도를 시작하지 않는 것"이며,
> **유출을 없애지 않고 확률만 낮춥니다** — 플랫폼은 예산 구간 안에서도 호출을 중단할 수 있고,
> 그 순간 발급 중이던 임시 메일함은 삭제되지 않습니다. 정기 라운드와 다른 점에 유의하세요:
> **Node/Docker의 정기 라운드에는 이 예산이 없고, 수동 보충에는 있습니다**. 그래서 같은 설정에서도
> 수동 라운드는 정기 라운드보다 적게 발급하며, 남은 자리는 다음 정기 라운드로 넘어갑니다.

### 이 키들은 저절로 사라지지 않습니다

`registrar_tend_lock`, `registrar_manual_guard`, `tend:history`, `registrar:domains`,
`registrar:backoff` 다섯 키는 **모두 TTL이 없습니다**. 이름이 고정 리터럴이고 개수는 항상 1이며,
오래된 값은 언제나 **값 비교**로 판정되므로(만료된 잠금은 아무도 막지 않고, 어제의 카운트는
세지 않으며, 만료된 백오프 구간은 어떤 라운드도 막지 않습니다) 남아 있어도 무해합니다.

**비용을 명시합니다**: 레지스트라를 영구히 끄거나, 배포를 삭제하면서 KV 네임스페이스만 남기면
이 키들은 스스로 사라지지 않습니다. 정리하려면 직접 키를 삭제하세요:

- Worker: `wrangler kv key delete --binding=POOL registrar_manual_guard`(다섯 키 각각 한 번)
- Node / Docker: `DATA_DIR/store.json`을 편집해 해당 다섯 개의 최상위 필드를 삭제

**`registrar:domains`는 "도메인 원장이 잘못 기억했다"고 판단했을 때의 유일한 수동 탈출구
이기도 합니다**: 지우면 등록기가 콜드 스타트로 돌아가 이미 지불한 코드 전송 요청을 다시
지불합니다. 정말로 잘못되었다고 판단했을 때만 하세요.

**`tend:history`는 보통 남겨 두는 편이 좋습니다**: 사후 분석에서 가장 보고 싶은 것이며,
"레지스트라를 끈 지 N일 뒤에 보충 이력이 통째로 사라진다"는 최악의 타이밍입니다 — 운영자는
대개 무언가 문제가 생겼기 **때문에** 레지스트라를 끕니다.

## 발급된 key가 전달 경로에서 쓰이기까지

**최대 `POOL_CACHE_TTL_MS` 한 번(기본 60초)이며, "다음 요청부터"가 아닙니다.**

보충과 전달은 서로 독립적인 두 개의 key 풀 저장소 인스턴스를 씁니다. 보충 쪽은 매 라운드
저장소를 실제로 읽습니다(지금 진짜 사용 가능한 개수를 봐야 하며, 그렇지 않으면 중복 발급으로
메일함 할당량을 헛되이 씁니다). 전달 쪽은 isolate / 프로세스 단위 스냅숏을 들고 있습니다.
각자 자기 캐시를 유지하므로, 보충이 key를 쓴 뒤에도 전달 경로는 **자기 스냅숏**이 만료되어야
그것을 봅니다. Worker에서는 활성 isolate마다 각자의 TTL이 걸립니다.

**풀이 비었을 때 가장 오해하기 쉽습니다**: 로그에는 이미 `[registrar] … minted=1`이 찍혔는데
게이트웨이는 TTL 한 번 동안 계속 `503 pool_empty`를 반환합니다. 보충이 안 된 것이 아니므로
`POOL_CACHE_TTL_MS` 한 번을 기다리세요. 줄이고 싶으면 이 값을 작게 하면 됩니다(비용은
[DEPLOY.md](DEPLOY.md)의 "할당량 계산" 참조).

## key를 순차적으로 발급하고 동시에 발급하지 않는 이유

보충은 한 라운드 내에서 key를 **순차적으로** 발급하며, 시도 사이마다 무작위 대기 시간
을 둡니다. 여러 발급 요청을 동시에 실행하지 않습니다. 이는 성능상의 트레이드오프가
아니라 기능적 제약입니다. 동시 실행은 YYDS Mail의 메일함 생성 속도 제한(짧은 시간 안
에 약 10회를 초과해 생성하면 `403`을 반환)과 Agnes 자체의 등록 위험 관리 정책을 동시
에 건드리게 됩니다. 순차 실행과 무작위 대기는 레지스트라가 계속 작동하기 위한 전제
조건이며, 동시성으로 "최적화"해야 할 대상이 아닙니다.

## 개인정보 보호

등록 과정에서 생성되는 이메일 주소, 계정, 비밀번호는 메모리에만 잠시 존재하며, **사용
이 끝나면 즉시 폐기되고 영구 저장되지 않습니다.** 스토리지에는 오직 발급된 API key
기록만 남습니다. 임시 메일함은 발급 성공 여부와 관계없이 시도가 끝나면 삭제됩니다.

## 문제 해결

### 등록기의 세 가지 상태

등록기는 "켬 / 끔" 두 상태가 아니라 **세 가지 상태**입니다. 세 번째가 가장 오해하기 쉬워서
패널의 네 곳에서 같은 말을 합니다.

- **꺼짐**: `REGISTRAR_ENABLED`가 없거나 패널 스위치가 꺼져 있습니다. 보충 라운드가 한 번도
  돌지 않고 외부 요청도 보내지 않습니다. 패널에는 "꺼짐"으로 나옵니다. 기본 상태이므로 복구할
  것이 없습니다. 쓰려면 설정 페이지에서 켜고 메일함 채널을 최소 하나 구성하세요.
- **사용 중**: 켜져 있고 이 설정을 불러올 수 있습니다. `TEND_INTERVAL_MS`(또는 Worker의 Cron)에
  따라 보충합니다. 패널에는 "사용 중"으로 나오고, 두 채널 카드가 자격 증명 유무와 이번에
  사용 중인 채널인지 여부를 보여줍니다.
- **사용 중 · 이번에는 시작 못 함**: 스위치는 켜져 있지만 이 설정을 불러오지 못했습니다(채널
  미선택, 선택한 채널의 자격 증명 누락 등). 그래서 시작하지 않았습니다.
  **게이트웨이 전달은 전혀 영향을 받지 않고** 보충만 멈춥니다.

세 번째 상태는 패널 네 곳에 나오며 모두 같은 것을 가리킵니다: 설정 페이지 상단 배너(빠진 항목
나열), 등록기 상태 줄, 개요 페이지 설정 요약, 그리고 이벤트 섹션의 매 라운드 `error` 등급
`registrar.blocked`.
**복구 방법**: 배너에 나열된 항목을 설정 페이지에서 채우고 저장하면 됩니다. 컨테이너 재시작도
재배포도 필요 없습니다.

> [!WARNING]
> **이렇게 한 대가**: 장애가 "시끄러운 것"에서 "조용한 것"으로 바뀝니다. 보충이 멈추면 풀은
> 서서히 마르고 결국 몇 시간에서 며칠 뒤 `pool_empty` 형태로 터지는데, 그때의 증상은 진짜 원인에서
> 여러 겹 떨어져 있습니다. 위의 네 가지 신호는 바로 그 때문에 존재합니다 — **직접 보러 가야 합니다**.

### 시작과 로그의 약속

- **활성화했는데 자격 증명이 없으면, 이번에는 등록기가 시작하지 않지만 게이트웨이
  전달은 평소대로 계속됩니다.**
  이 부분은 **바뀌었습니다**. 예전에는 게이트웨이 전체를 페일클로즈시켰지만, 등록기는
  선택적 하위 시스템이며 메일함 key 하나가 없다고 전달과 `/health`, 관리 패널까지 함께
  죽어서는 안 됩니다. 이제 빠진 항목이 패널에 하나씩 나열되고, 매 라운드 `error` 등급
  `registrar.blocked`가 기록됩니다. 세 가지 상태는 아래 "등록기의 세 가지 상태"를 보세요.
- 보충 과정의 로그에는 일관되게 `[registrar]` 접두사가 붙으므로, 이를 기준으로 필터
  링해 볼 수 있습니다. 각 로그 줄의 두 번째 필드는 안정적인 기계 판독용 **이벤트
  이름**(예: `registrar.round_budget_impossible`)입니다. 이벤트 이름으로 grep하는 편이
  사람이 읽는 문구로 grep하는 것보다 확실합니다 — 문구는 표현 조정으로 바뀔 수 있지만,
  이벤트 이름은 이 로그의 유일하게 안정적인 대외 계약이며 바뀌지 않습니다.
### `reasons=`의 실패 원인 읽기

- **한 라운드에서 발급되지 않은 슬롯이 있으면 마무리 로그에 `reasons=`가 붙은 경고가 한
  줄 더 남습니다**(예: `reasons=yyds:register_failed×3 moemail:code_timeout×1`). 먼저 이
  줄로 어느 계층의 장애인지 판단하세요. `code_timeout` = 이 채널이 Agnes의 메일을 받지
  못함(도메인 MX / 전달 규칙); `register_failed` / `login_failed` / `key_failed` = Agnes
  쪽 가입 경로가 바뀜; `provider_error` = 메일함 서비스 자체(자격 증명, 활성 메일함 한도,
  서비스 장애); `provider_missing` = 내부 배선 오류이며 정상적인 설정에서는 나타나지 않습니다
  (자격 증명 누락은 시작 시점에 바로 오류가 나므로 여기까지 오지 않습니다).
- **`reasons=`에 `key_suspicious`가 나오는 경우**: 업스트림이 돌려준 key 내용에 출력 불가
  문자나 공백이 들어 있습니다. **그 라운드는 실제로 발급에 성공했습니다**(Agnes 쪽 계정이
  실제로 생성되었고 임시 메일함도 실제로 소비되었습니다). 그래서 그 key는 **그대로 풀에
  저장됩니다** — 여기서 거부하는 것은 두 번 다시 되찾을 수 없는 자격 증명을 파기하는 일이기
  때문입니다. 다만 선택될 때마다 전달이 실패할 가능성이 높으니 관리 패널에서 비활성화하거나
  삭제하세요. 동시에 `registrar.minted_key_suspicious` error 이벤트가 남습니다(채널과 길이만
  기록하며 **평문은 기록하지 않습니다**).
### 등록기는 어떤 메일 도메인이 되는지 기억합니다

업스트림은 일회용 메일 도메인 중 일부만 받아들이고 나머지는 거부합니다. **이 결론을 이제
저장해 두고 재사용합니다**:

- 정상 상태에서는 **발급 1회 성공당 `/api/verification` 요청이 정확히 1회**입니다. 업스트림
  전체 도메인에서 몇 개를 무작위로 뽑아 하나씩 시도하는 대신, 이미 된다고 아는 도메인을
  고릅니다. `MAX_DOMAIN_ATTEMPTS`의 내장값을 1까지 낮출 수 있는 이유가 바로 이것입니다.
- 패널의 등록기 섹션에 "도메인 원장: 사용 가능 N · 제외 N · 재확인 대기 N · 미확인 N
  (갱신 …)" 한 줄이 표시됩니다.
- **연속 두 라운드** 거부되어야 후보 맨 뒤로 밀립니다(**같은 라운드 안에서 몇 번 거부되든
  한 번으로 셉니다**). 한 라운드만 거부된 도메인은 "재확인 대기"로
  여전히 선택되며 우선순위만 낮아집니다. 한 번 성공하면 무조건 "사용 가능"으로 되돌립니다.

#### 이 판정이 틀릴 수 있는 이유

> [!WARNING]
> **"제외"는 업스트림의 선언이 아니라 우리의 판정입니다.** 업스트림은 같은 `400`으로
> "이 도메인은 차단됨"과 "이 발신 주소가 너무 자주 보냄"을 모두 표현하며, 둘을 가르는 유일한
> 단서는 응답 본문입니다. 우리는 그것을 **낱말 목록**으로 판정하므로, 업스트림이 문구를 한 번
> 바꾸면 틀립니다. 이 오판을 누르는 층은 셋입니다: 판정에는 두 번이 필요하고, 한 라운드에
> 최대 한 건만 학습하며, **정렬은 어떤 도메인도 완전히 배제하지 않습니다**(제외된 것은 맨
> 뒤로 갈 뿐). 다만 이 세 층이 누르는 것은 "좋은 도메인이 제외된다"는 한 방향뿐입니다.
> 반대 방향 — 원장의 "사용 가능"이 낡았고 실제로는 업스트림이 이미 차단한 경우 — 을 누르는
> 것은 다른 규칙입니다: **분류기가 내린 판정은 그대로 기록하고, 결론을 삼키지 않는다**.
> 이 규칙은 예전에 한 안전장치("사용 가능하다고 아는 도메인이 거부되면 속도 제한으로 다시
> 읽는다")에 깨져 있었고, 대가는 느려짐이 아니라 최장 7일간의 **보충 0**이었습니다.
> 이 안전장치는 제거되었습니다.
> 즉 이 맺음말은 **방향별로 나누어** 읽어야 합니다. 세 방향의 대가는 같지 않습니다.
> ① 좋은 도메인이 제외되는 방향 — 확실히 느려질 뿐 **0이 되지는 않습니다**
> (세 겹의 방어에 더해, 정렬은 어떤 도메인도 배제하지 않습니다).
> ② 원장은 "사용 가능"인데 업스트림은 이미 차단한 방향 — "분류기가 내린 판정은 그대로
> 기록한다"는 규칙이 받치고 있으며, 그 규칙은 이미 고쳐졌습니다.
> ③ 분류기가 **진짜 속도 제한**을 "도메인 차단"으로 읽는 경우 — 업스트림의 속도 제한 문구에
> **우리 단어 목록이 하나도 일치하지 않았으므로**("업스트림이 아무 말도 하지 않았다"가
> 아닙니다. 말은 했고 우리가 못 알아들었을 뿐입니다) 위의 두 층 백오프는 한 번도 생기지
> 않고, 그 라운드도 더는 일찍 멈추지 않으며, 한 라운드에 최대 `MINT_BATCH`번의 반드시
> 실패할 인증 코드 요청이 나갑니다. 이 경우를 받아내는 것이 아래 표의 세 번째 행이고,
> 근거는 업스트림의 문구가 아니라 **그 라운드의 형태**(같은 라운드에서 여러 도메인이 한꺼번에
> 차단 판정되거나, **업스트림이 제공하는 도메인이 하나도 빠짐없이 차단 판정되고**, 그
> 라운드에서 key가 하나도 나오지 않음)입니다.

#### 도메인 원장이 잘못 기억했다고 판단되면

패널에는 도메인을 하나씩 나열하는 화면이 없습니다(업스트림의
수백 개를 실으면 몇 초마다 폴링되는 엔드포인트 응답이 한 자릿수 커집니다). 선택지는 셋입니다:
결론이 만료되기를 기다리기(제외 24시간, 사용 가능 7일), 두 번 규칙이 스스로 바로잡기를
기다리기, 저장소 키를 손으로 지우기(아래 "이 키들은 저절로 사라지지 않습니다" 참고).

### 업스트림 속도 제한에 걸리면 어떻게 되는가

업스트림 앞단에 엣지 속도 제한(`429`)이 있고, 업스트림 자체의 가입 속도 제한(`400` +
"요청이 너무 잦습니다" 류의 문구)도 있습니다. **두 처벌 구간 모두 보충 한 라운드보다 길고,
구간 안에서 요청을 한 번 보낼 때마다 구간이 연장됩니다.**

그래서 어느 층에든 걸리면:

- **그 라운드는 그 자리에서 끝납니다** — 도메인을 바꾸지도, 다음 슬롯으로 넘어가지도 않습니다.
- **백오프 구간**을 기록하고 다음 라운드를 시작하기 전에 먼저 확인합니다. **구간 안에서는
  업스트림 요청을 한 번도 보내지 않고 임시 메일함도 하나도 만들지 않습니다.** 보충 기록의
  그 행의 실패 원인은 "백오프 구간 안이라 이 라운드는 한 번도 시작하지 않았습니다"입니다.
- 연달아 걸리면 백오프가 **지수적으로** 길어집니다(상한 4시간). 여기서 "연달아"가 세는 것은
  **key가 하나도 나오지 않은 라운드의 연속 횟수**입니다. 한 라운드에서 하나라도 발급했다면 지수는
  처음부터 다시 세며 — 같은 라운드 끝에서 속도 제한에 걸렸더라도 백오프는 두 배가 아니라
  처음 단계로 돌아갑니다. 그 라운드에서 속도 제한에 한 번도 걸리지 않았다면 그 키 자체를 지웁니다.
- 직전 백오프 구간이 끝난 뒤 4시간 넘게 다시 걸리지 않으면 지수도 마찬가지로 처음부터 셉니다
  (풀이 계속 가득 차 있어서 등록기가 여러 라운드 동안 실제로 돌지 않은 경우 등).

#### 세 번째 단: 우리 단어 목록은 하나도 일치하지 않았는데 그 라운드의 도메인이 무더기로 실패했다

업스트림이 문구를 한 번만
바꿔도 진짜 속도 제한이 한 건씩 "도메인 차단"으로 읽힙니다 — 위의 두 단은 한 번도 발동하지
않고, 그 라운드도 더는 일찍 멈추지 않습니다. 이때 유일하게 남는 근거가 **그 라운드의
형태**이고, 판정은 두 가지이며 어느 하나만 맞아도 성립합니다:

- 같은 라운드에서 두 개 넘는 도메인이 차단 판정된다;
- **또는 업스트림이 제공하는 도메인이 그 라운드에서 하나도 빠짐없이 차단 판정된다**
  (메일박스 도메인을 하나만 설정한 배포는 이 조건으로 받아냅니다 — 그런 배포는 위의
  "두 개 넘는"에 영원히 도달하지 못합니다).

둘 다 **그 라운드에서 key가 하나도 나오지 않았을 것**을 요구합니다. 등록기는 이를 근거로
백오프 구간을 기록합니다(시작 30분, 지수도 상한 4시간도 동일). **다만 그 라운드를 중단하지
않고 어떤 도메인 판정도 삼키지 않습니다** — 그 라운드에서 시도할 도메인은 그대로 시도하고,
나올 key도 그대로 나옵니다.
그 라운드에서 key가 하나라도 나왔다면 이 단은 한 글자도 기록하지 않습니다.

#### 이 단이 켜졌을 때 두 가능성이 모두 남아 있습니다

> [!WARNING]
> **두 가지 가능성이 모두 남아 있으며, 배너가 대신 골라 주지 않습니다**:
> 업스트림이 속도 제한 문구를 바꿔 우리 단어 목록이 놓쳤을 수도 있고, 업스트림이 실제로 그
> 도메인들을 차단 목록에 갈아 넣었을 수도 있습니다. **"업스트림이 속도 제한에 대해 아무 말도
> 하지 않았다"로 읽지 마세요** — 이 단이 존재하는 첫째 상황이 바로 업스트림은 말했는데 우리가
> 알아듣지 못한 상황입니다.

#### 업스트림 원문을 어디서 찾을까: 두 갈래가 얻는 증거가 다릅니다

**"`registrar.domain_blocked`를 보면 된다"를 그대로 믿지 마세요 — 두 갈래 중 한쪽에서는
그 이벤트가 아예 한 건도 발행되지 않습니다. 그 대가를 여기에 정직하게 기록합니다:**

- **같은 라운드에서 여러 도메인이 «차단»으로 판정된 갈래**: 클램프가 걸리는 순간 그 라운드의
  **모든** «차단» 판정이 통째로 폐기됩니다 ⇒ 원장은 `blocked`를 학습하지 못합니다 ⇒
  **그 라운드에는 `registrar.domain_blocked`가 한 건도 발행되지 않습니다**. 이 갈래에서
  손에 넣을 수 있는 업스트림 원문은 `registrar.known_good_domain_rejected` 항목뿐이고,
  그것도 **원장이 이미 «사용 가능»으로 알고 있던 도메인만 다룹니다** — 콜드 스타트이거나
  업스트림이 그 라운드에 처음 나열한 도메인이라면 원문이 하나도 남지 않습니다. 같은 라운드에
  발행되는 `registrar.domain_verdicts_discarded`는 폐기된 판정 건수, 그 라운드의 산출,
  백오프 만료 시각만 담고 **업스트림 원문은 담지 않습니다**.
- **업스트림이 나열한 도메인이 하나도 빠짐없이 «차단»으로 판정된 갈래**(메일 도메인을 하나만
  설정한 배포가 지나가는 쪽입니다): 클램프가 문턱에 닿지 않아 걸리지 않습니다 ⇒ 원장은
  평소대로 결론을 학습하고, 두 번째 타격에서 판정이 확정될 때 `registrar.domain_blocked`가
  업스트림 원문을 실어 발행됩니다.

#### 세 번째 단이 받아낸 뒤 남는 요청량

숫자로 적습니다(내장값, 테스트 대역으로 측정): 지수
상한에 도달한 뒤에는 **8 라운드에 한 번, 한 번에 `MINT_BATCH` = 5건의 인증 코드 요청**입니다.
Cron이 30분에 한 번이므로 48 라운드/일 ÷ 8 × 5 = **하루 약 30건**.
비교용 숫자 둘: **이 단이 받아내기 전에는 매 라운드가 가득 나갔습니다 ⇒ 하루 약 240건**.
그리고 "업스트림 문구가 단어 목록에 들어온" 두 번째 단은 걸리는 즉시 라운드 전체를
멈춥니다(라운드당 1건) ⇒ **하루 약 6건**.
⇒ **30은 6이 아닙니다**: 이 단은 라운드를 중단하지 않기 때문에 두 번째 단보다 비쌉니다 —
그 라운드에서 나올 key는 그대로 나오고, 대가로 그 라운드의 남은 시도도 함께 나갑니다.

#### 백오프 배너: 세 단의 대처는 다릅니다

패널의 등록기 섹션에 백오프 배너가 뜹니다:

| 어느 단인가 | 패널이 하는 말 | 할 수 있는 일 |
|-------------|--------------|-------------|
| 엣지 속도 제한 | "보충 간격이 너무 촘촘함" | `MINT_DELAY_MIN_MS`를 늘리거나 `MINT_BATCH`를 줄이기 |
| 업스트림 자체의 가입 제한 | "응답에 «요청이 너무 많습니다» 같은 문구가 있었음 — 이것은 우리 낱말 목록에 따른 판정이며 업스트림이 내려준 결론이 아님" | 먼저 `MINT_DELAY_MIN_MS`를 늘리고 `MINT_BATCH`를 줄이기. 발신 주소 변경은 가입 한도를 정말 다 썼다고 확인한 뒤에 |
| 그 라운드의 도메인이 무더기로 차단 판정되고 발급이 0 | "우리 단어 목록에 일치 없음. 두 가정이 모두 남아 있음" | 갈래마다 증거가 다릅니다(위 절 참조). `registrar.domain_blocked`가 비어 있을 수 있음 |

> [!IMPORTANT]
> **메일박스 채널을 바꿔도 이 구간은 피할 수 없습니다.** 제한은 당신의 발신 주소와 업스트림
> 사이에 걸려 있으며, 어떤 메일박스 채널을 쓰는지와 무관합니다. 백오프 배너가 보일 때 채널을
> 바꾸는 것은 헛수고입니다.

**빈 풀을 채우는 속도는 눈에 띄게 느려집니다**: 목표 20개 key가 "몇 분"에서 대략 4~5
라운드로 바뀝니다. Cron이 30분에 한 번이면 **약 2~2.5시간**입니다. 이것은 "여유를 다 쓰고도
헛되이 계속 두드림"을 "느리지만 진짜로 key가 나옴"으로 바꾼 직접적인 대가입니다.

### 채널이 실패한 뒤에는 어떻게 되나

**둘 중 하나만 고르는 방식이므로 "다른 쪽으로 바꾸는" 일은 오직 당신만 할 수 있습니다.**
선택한 채널이 실패하면:

- **이번 슬롯은 무효가 되고, 이 라운드의 다음 슬롯은 평소대로 시작합니다**(먼저
  `MINT_DELAY_MIN_MS`~`MINT_DELAY_MAX_MS`의 무작위 대기가 들어갑니다). 도메인 목록 조회
  실패, 자격 증명 무효, 후보 도메인 전부에서 메일함을 못 만듦, 인증 코드가 오지 않음,
  네트워크 흔들림, 도메인이 전부 차단, 가입/로그인/key 생성 실패 —
  이 모두가 같은 구간입니다.
- **예외는 두 가지이며, 둘 다 그 라운드를 즉시 종료합니다**:
  - Agnes 백엔드 전체 장애(`upstream_error`) — 계속 돌아 봐야 장애 중에 실패가 확정된
    요청만 늘리기 때문입니다.
  - **업스트림 속도 제한에 걸린 경우(`rate_limited`)** — 아래
    "업스트림 속도 제한에 걸리면 어떻게 되는가"를 보세요.
- **속도 제한 말고는 라운드를 건너뛰는 백오프도, 지수 재시도도 없습니다.** 일반적인 실패는
  다음 라운드 시각을 바꾸지 않습니다(Node/Docker는 고정된 `TEND_INTERVAL_MS` 타이머,
  Worker는 `wrangler.toml`의 Cron). 라운드 안의 조절은 이미 두 겹입니다(시도 사이의
  무작위 대기, Worker 쪽 라운드 단위 월클록 예산).

#### 대가와, 알아채는 법

> [!WARNING]
> **이것은 기능 후퇴입니다. 분명히 적어 둡니다.** 예전에는 인증 코드를 받지 못하는 채널도
> 한 번은 자동으로 전환되어, 보충이 느려질지언정 key는 계속 나왔습니다. 이제는 같은 실패가
> 그 라운드, 경우에 따라서는 그날 내내 하나도 발급하지 못한다는 뜻이며, 직접 채널을 바꿀
> 때까지 그대로입니다. 장애의 모양이 "보충이 느려짐"에서 "보충이 전혀 안 됨 → 풀이 마름 →
> 몇 시간에서 며칠 뒤 `pool_empty` 503으로 터짐"으로 바뀝니다 — **스스로 회복하던 장애를
> 사람이 손봐야 하는 장애와 맞바꾼 것**입니다. 둘 중 하나만 고르는 방식의 본질적인 대가이며
> 결함이 아닙니다.

**어떻게 알아채나**: 보충 이력의 각 라운드 실패 원인에는 채널 이름이 하나씩 붙어 있고
(`reasons=` 줄), 등록기 섹션의 풀 4개 숫자가 있으며, 채널 요청이 실패했을 때는 **실제로
요청한 주소**가 담긴 이벤트가 남습니다. 발급이 0이면 패널에서 다른 채널의 "연결 테스트"를
눌러 봅니다. 이는 도메인을 나열한 다음 **그쪽 자격 증명을 실제로 검증합니다**(방식은
채널마다 다르며, 임시 메일함을 만들었다가 지우는 채널도 있습니다).
바꾼 뒤에는 다음 보충 라운드의 실패 원인을 보세요. key가 발급되어야 확인됩니다.

### 어떤 채널이 계속 실패할 때

- 특정 채널에서 등록이 계속 실패한다면(예: Agnes가 인증 코드나 CAPTCHA 정책을 강화한
  경우), 이는 코드 수준에서는 우회할 수 없는 업스트림 측 변화입니다. 레지스트라를 비
  활성화하고 대신 key를 수동으로 임포트할 수 있습니다([DEPLOY.md](DEPLOY.md) 참고).
