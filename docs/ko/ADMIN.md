# 관리 패널

관리 패널은 **선택 사항**입니다. `ADMIN_TOKEN`을 설정하지 않으면 `/admin` 트리 자체가
등록되지 않으며, 게이트웨이는 평소대로 전달을 계속합니다. 이 문서가 다루는 것은 화면에
보이는 쪽입니다. 각 보드가 어떤 질문에 답하는지, 화면의 수치가 어떤 기준인지, 어떤 동작이
저장소에 쓰는지를 설명합니다. **변수 자체(기본값·허용 범위·대가)는 저장소 전체에서 단
한 곳, [DEPLOY.md](DEPLOY.md)의 환경 변수 표에만 있습니다.** 여기서는 그쪽을 가리키기만
하고 두 번째 사본을 두지 않습니다.

이 문서가 다루는 범위: 패널에 들어가는 방법, 각 보드를 하나씩 훑고, 마지막으로
패널이 하지 않는 일과 문제 해결입니다.

## 패널에 들어가기

### 패널 주소

패널은 게이트웨이 자신의 도메인 아래에 있습니다. 별도의 포트도, 별도의 서비스도 필요하지
않습니다.

```text
https://<your-gateway>/admin
```

`<your-gateway>`는 본인의 게이트웨이 주소로 바꾸세요. 끝에 슬래시가 붙은 `/admin/`는
`/admin`으로 자동 이동하므로, 손으로 입력하는 두 가지 방식 모두 들어갈 수 있습니다.

### 전제 조건

- **전제 조건은 하나뿐**입니다. 배포할 때 `ADMIN_TOKEN`을 설정하는 것입니다. 최소 24자
  이상이어야 하고, 출력 가능한 ASCII로만 이루어져야 하며, `GATEWAY_TOKEN`과 달라야 합니다.
  세 조건 각각의 이유와 경계, 그리고 규칙에 맞지 않을 때 어떤 이벤트가 기록되는지는
  [DEPLOY.md](DEPLOY.md)의 "관리 패널 관련 변수" 절에 있습니다.
- **설정하지 않았거나 규칙에 맞지 않으면 `/admin`은 `401`이 아니라 `404`를 돌려줍니다.**
  트리가 아예 등록되지 않았으므로 "여기에 관리 화면이 있다"고 밖에 알리지도 않습니다.
  패널을 열 수 없어도 **게이트웨이 전달에는 영향이 없습니다**.

### 토큰의 보관과 철회

- **토큰은 브라우저의 localStorage에 그대로 저장되며**, 패널은 12시간 뒤에 다시 입력하도록
  요구합니다.
- 이 상한이 줄이는 것은 localStorage에 놓인 값의 사용 가능 구간일 뿐 **철회가 아닙니다**.
  철회하는 길은 하나뿐입니다. `ADMIN_TOKEN`을 새 값으로 바꾸고 다시 배포하거나 컨테이너를
  다시 만드는 것입니다. 패널은 TLS 뒤에 두고, 신뢰하는 기기에서만 여세요. 자세한 논증은
  [DEPLOY.md](DEPLOY.md)의 "관리 토큰 유출" 문단에 있습니다.

## 여덟 개 보드 한눈에 보기

| 보드 | 답하는 질문 | 읽기 전용인가 쓰는가 | 필요한 스위치 |
|----|-----------|--------------------|-------------|
| 개요 | 이 배포는 지금 어떤 형태이고, 쓸 수 있는 key가 몇 개 남았는가 | 읽기 전용 | – |
| Key 풀 | 각 key는 지금 어떤 상태이고, 왜 못 쓰는가 | 씀 | – |
| 레지스트라 | 자동 보충이 돌고 있는가, 최근 몇 회에 무엇을 발급했는가 | 씀 | `REGISTRAR_ENABLED` |
| 이벤트 | 최근에 어떤 운영 수준의 일이 있었는가 | 읽기 전용 | – |
| 사용량 | 요청량·성공률·지연이 시간에 따라 어떻게 움직였는가 | 읽기 전용 | `USAGE_STATS_ENABLED`(둘째 층에만) |
| 모델 | 게이트웨이가 대외적으로 인정하는 모델과 그 모달리티·프로토콜 | 읽기 전용 | – |
| 플레이그라운드 | 진짜 요청 한 번으로 특정 프로토콜이 통하는지 확인 | 업스트림 호출 | – |
| 설정 | 런타임 설정의 현재 값과, 환경 변수에 고정된 항목 | 씀 | – |

"씀"은 **그 페이지에서 누른 동작이 저장소에 쓴다**는 뜻이고, "업스트림 호출"은 업스트림으로
실제 요청을 한 번 보낸다는 뜻입니다. ⚠️ **"업스트림 호출"이 "저장소에 쓰지 않는다"는 뜻은
아닙니다.** 플레이그라운드가 보내는 것은 이 게이트웨이 자신의 전달 입구로 가는 진짜 요청이며,
평소의 전달과 똑같은 경로를 지나갑니다 —— 이번에 쓰인 key도 똑같이 기록되고, 저장되는 조건도
전달 경로와 완전히 같으며(마찬가지로 모아서 씁니다), 둘째 층 사용량이 켜져 있으면 한 건을
더 남깁니다.

## 개요

개요가 답하는 질문은 하나입니다. **이 배포는 지금 어떤 형태이고, 풀에 쓸 수 있는 key가
몇 개 남았는가.**

### 풀의 버킷과 런타임 자기 보고

- **풀의 다섯 버킷**: 총계 / 사용 가능 / 쿨다운 중 / 배제됨 / 비활성화됨. 다섯 칸 모두 항상
  표시합니다. 진짜 `0`은 그 자체로 참이기 때문입니다. **읽지 못한 칸은 `—`를 표시하고
  `0`을 지어내지 않습니다** —— 이 둘은 화면에서 같은 모습이어서는 안 됩니다.
- **런타임과 저장소의 자기 보고**: 런타임 이름, 버전, 서버 시각, 저장소 백엔드, 쓰기 가능
  여부, 그리고 Node 형태에만 있는 메모리 / 가동 시간 / PID. 모두 API가 돌려준 데이터만
  사용하며, 패널이 자기가 어느 런타임에서 도는지 넘겨짚지 않습니다. Worker 형태에는 상주
  프로세스가 없으므로 그 세 칸은 "상주 프로세스 없음"으로 표시됩니다. `0`도 공백도 아닙니다.

### 두 줄의 신선도와 첫째 층 사용량

- **두 줄의 신선도**: 풀 스냅숏과 설정은 각각 "몇 초 전에 읽었는지"를 따로 가집니다. 같은
  시간축이 아니므로 나누어 표시합니다. 풀 쪽의 지연은 `POOL_CACHE_TTL_MS`에 엣지 캐시 한
  겹이 더해져 정해지며, 그 상한과 대가는 [DEPLOY.md](DEPLOY.md)의 해당 칸에 적혀 있습니다.
- **첫째 층 누적 사용량**: 요청 수 / 성공 / 실패 / 클라이언트 오류 / 성공률. 풀 전체 key의
  누적 합계이므로 `≈`가 붙습니다. key별 카운터는 동시 요청에서 적게 집계되고(KV에 CAS가
  없음), 저장은 최대 `POOL_TOUCH_INTERVAL_MS` 하나만큼 늦어집니다.

### 설정 요약

- **설정 요약**: 레지스트라 스위치, 주/보조 채널, `TARGET_KEYS`의 현재 실효값. 환경 변수에
  고정된 필드에는 잠금 표시가 붙습니다 —— 그 항목들은 설정 페이지에서 바꿔도 적용되지
  않습니다. 환경 변수가 우선하기 때문입니다.

## Key 풀

### 버킷 배지는 우선순위의 투영

- **버킷 배지는 우선순위를 한 번 투영한 결과**이지 독립된 네 개의 깃발이 아닙니다. 하나의
  key가 여러 조건을 동시에 만족하면 비활성화됨 > 배제됨 > 쿨다운 중 > 사용 가능 순서로
  첫 번째를 취합니다. 그래서 "비활성화되었고 아직 쿨다운 중"인 key의 배지는 "비활성화됨"이
  됩니다. 쿨다운이 사라진 것이 아니라 배지에서 보이지 않을 뿐입니다.

### 보드에서 할 수 있는 동작

#### 단건 동작

- **단건 동작 여덟 가지**: 비활성화, 활성화, 쿨다운 해제, 실패 횟수 초기화, 배제 취소,
  메모 수정, 연결 확인, 삭제.

#### 일괄 동작

- **일괄 동작 세 가지**: 일괄 비활성화, 일괄 쿨다운 해제, 일괄 삭제.

### 가져오기와 상태 초기화

- **한 번에 최대 200개의 key까지 가져옵니다.** 이 수를 넘기면 곧바로 `400`이고, **조용히
  잘라내지 않습니다** —— 잘라내기는 "넣은 줄 알았는데 사실 없었다"를 만듭니다.
- **"이미 있는 key의 상태를 초기화" 체크박스가 실제로 초기화하는 것**: **시스템이 판정한
  실패 상태**입니다. 실패 횟수, 쿨다운 만료 시각, 쿨다운 사유, 배제 표시, 배제 사유.
  다음 네 가지는 **일부러 건드리지 않습니다**: 비활성화 상태(직접 내린 스위치이며, 한 번의
  붙여넣기로 조용히 되돌릴 일이 아닙니다), 추가 시각(내력은 실패 상태가 아닙니다), 사용량
  통계(이력은 실패 상태가 아닙니다), 메모(스스로 보려고 적어 둔 말입니다).

### 삭제의 전제 조건과 단건 연결 확인

- **key를 지우려면 비활성화되었거나 배제된 상태여야 합니다.** 둘 중 하나만 만족하면 되며,
  시스템이 이미 배제한 key를 손으로 다시 비활성화할 필요는 없습니다. 아직 쓰이고 있는 key를
  그대로 지우려 하면 거부됩니다. 일괄 경로에서는 이 제약이 배치 전체의 실패가 아니라
  항목별 사유로 돌아옵니다.
- **단건 연결 확인**은 그 key로 업스트림에 실제로 한 번 요청을 보냅니다. 목록의 "마지막
  사용"과 사용량 카운터는 모아 두었다가 저장하므로, 해상도는 `POOL_TOUCH_INTERVAL_MS`
  간격보다 더 촘촘해지지 않습니다.

### key 하나를 바꾸는 요청과 응답

보드의 단건 동작은 모두 같은 `PATCH /admin/api/keys/{id}`를 지나가며, 한 번의 요청에 여러
개를 함께 실을 수 있습니다 —— 여기서는 활성화와 쿨다운 해제 둘입니다. 헤더에 싣는 것은
**관리 토큰**이지 게이트웨이 토큰이 아닙니다.

```bash
curl -X PATCH http://localhost:8080/admin/api/keys/9f2c \
  -H "x-admin-key: your-admin-token" \
  -H "Content-Type: application/json" \
  -d '{ "disabled": false, "clearCooldown": true }'
```

응답이 알려 주는 것은 이번 쓰기가 통했는지뿐이고, 레코드 전체를 다시 읽어 오지는 않습니다.
바뀐 상태는 목록으로 돌아가 확인하세요.

```json
{ "ok": true }
```

이 요청 본문에 실리는 각 필드의 타입과 의미는 [API.md](API.md)에 있으며, 이 문서는 두 번째
사본을 두지 않습니다.

## 레지스트라

패널의 레지스트라 보드는 **색인이지 설명서가 아닙니다.** 보충 규칙 전부, 채널 고르는 법,
직접 준비해야 하는 자격 증명, 문제가 났을 때 추적하는 법은 모두
[REGISTRAR.md](REGISTRAR.md)에 있으며 이 문서는 두 번째 사본을 두지 않습니다. 보드에서
볼 수 있는 것은 다음과 같습니다.

### 두 메일 채널

- **메일 채널 둘은 대등하며** 기본값이 없습니다. 주 채널은 반드시 명시해야 하고 보조 채널은
  비워 두어도 됩니다. 보드에는 각각의 역할(주 / 보조)과 자격 증명 설정 여부가 표시됩니다.

### 보충 이력과 채널 테스트

- **보충 이력**: 각 회차가 언제 돌았는지, 어느 채널을 탔는지, 타이머가 시작했는지 사람이
  눌렀는지, 얼마나 걸렸는지.
- **채널 테스트는 그 채널의 사용 가능한 도메인 목록만 읽습니다.** 메일박스를 만들지도,
  계정을 등록하지도, 정원을 소비하지도 않습니다.

### 지금 보충의 네 가드레일

- **"지금 보충"에는 네 개의 가드레일**이 있고, 하나라도 만족하지 못하면 시작하지 않습니다.
  같은 복제본 안의 진행 중 가드, 복제본 사이의 저장소 단기 잠금, 수동 보충 사이의 최소
  간격, 그리고 하루 수동 실행 상한입니다. 각각의 오류 코드·산식·잔여 위험은
  [REGISTRAR.md](REGISTRAR.md)의 "지금 보충" 절에 있습니다.
- 레지스트라가 꺼져 있으면(`REGISTRAR_ENABLED`가 `true`가 아니면) 보드는 그대로 보이지만
  상태가 꺼짐으로 표시되고, "지금 보충"은 백엔드에서 거부됩니다.

## 이벤트

### 여기에 실리는 것

- 여기에는 **저빈도 구조화 이벤트**만 실립니다. 설정 읽기 실패, 풀 색인 재구축, 관리 API
  로그인 실패 같은 운영 진단에 더해, 레지스트라의 보충 이벤트와 패널 자신의 쓰기 동작입니다.
  **전달 경로가 key를 자동으로 쿨다운에 넣거나 배제할 때는 지금은 이벤트를 내지 않습니다**
  —— 그 부분은 Key 풀 보드에서 그 key 자신의 상태를 보세요.

### 도구 모음과 보관 창

- **도구 모음**: 수준으로 거르기, 텍스트로 검색, 자동 새로 고침 일시정지, 지우기, 내려받기.
  "지우기"는 화면의 이 목록만 지우며 **서버에 이미 저장된 이벤트는 건드리지 않습니다.**
  다시 보려면 "내려받기"를 누르거나 페이지를 새로 고치세요.
- **이벤트는 시간 단위 창에 담기고, 24개의 창이 유지됩니다** —— 꼬박 하루치이며, 그보다
  오래된 것은 저절로 만료되어 패널에서 더는 찾을 수 없습니다.

### 다섯 개의 경고 바

- 경고 바는 각각 다른 이야기를 하며, **서로 독립된 바여서 동시에 켜질 수 있습니다.**

| 경고 바 | 무엇을 말하는가 | 무엇을 해야 하는가 |
|-------|---------------|------------------|
| 버려짐 | 이 복제본의 이벤트 버퍼가 저장되기 전에 가장 오래된 몇 건을 밀어냈다 | 이벤트가 저장보다 빨리 생긴다. 컨테이너 로그 / Workers Logs에서 그 구간을 찾는다 |
| 예산 | 이 복제본의 오늘치 이벤트 쓰기 예산을 다 썼다 | 위와 같다. 저장되지 못한 것들은 로그에 남아 있다 |
| 잘림 | 이 페이지가 조건에 맞는 이벤트를 전부 보여 주지 못했다 | 필터를 좁히거나, 보려는 기간을 짧게 한다 |
| 커서 앞섬 | 가져오기 위치가 서버 시계보다 앞서 있다. 시계 되돌림이거나 복제본 사이의 시계 편차다 | 패널이 이미 새 위치에서 다시 가져왔다. 이 건은 저절로 가라앉는다 |
| 커서 계약 위반 | API가 돌려준 커서가 숫자도 null도 아니어서 패널이 이전 커서를 유지했다 —— **이후로 새 이벤트가 계속 보이지 않을 수 있다** | 이벤트 저장소를 이 게이트웨이 밖의 무언가가 썼는지 확인한다 |

### 이벤트 한 건의 모습

패널이 key 하나를 비활성화한 뒤, 이벤트 보드와 "내려받기"가 돌려주는 것은 같은 구조화
레코드입니다. 이벤트 이름은 안정적인 기계 판독용 문자열이며, 거르기와 분류는 오직 그것만
보고 `msg`를 해석하지 않습니다.

```json
{
  "ts": 1735689600000,
  "level": "warn",
  "event": "key.disabled",
  "msg": "面板停用了一把 key（它仍然占着 targetKeys 的名额，不会触发补池）",
  "fields": { "id": "9f2c" }
}
```

## 사용량

### 두 개의 층

- **사용량은 두 층이고, 첫째 층은 언제나 있습니다.** 첫째 층은 풀 전체의 누적 수치(개요
  페이지 위쪽 카드가 쓰는 것이 바로 이것)로 스위치가 필요 없습니다. 둘째 층은 일 / 시간 /
  모델 / 프로토콜로 분해한 시계열이며 `USAGE_STATS_ENABLED`가 제어하고 **기본값은 꺼짐**입니다.
- **꺼져 있는 동안 이 페이지는 빈 차트를 그리지 않습니다.** `0`으로 채워진 차트는 "이 기간에
  아무도 쓰지 않았다"로 읽히지만, 사실은 "이 배포는 애초에 기록하지 않는다"입니다. 이 둘이
  같은 모습이어서는 안 됩니다.

### 기간과 보관

- **기간은 네 단계**: `24h`, `3d`, `7d`, `30d`.
- **최대 30일까지 보관하며** 그보다 오래된 데이터는 만료되었습니다. 가장 긴 단계는 구간
  전체의 샤드를 한 번에 읽는데, 그것이 Cloudflare Worker에서 항상 완료되는지를 이 저장소는
  실제 환경에서 측정한 적이 없습니다 —— 실패하면 완전해 보이는 숫자를 내놓는 대신 읽기
  실패로 그대로 표시합니다.

### 왜 근삿값인가

- **여기 수치에는 `≈`가 붙고, 출처 세 가지는 서로 다릅니다**: ① 저장되지 못한 꼬리 ——
  카운터는 먼저 인스턴스 메모리에 쌓였다가 나중에 한꺼번에 기록되며, 이 구간의 길이는
  패널이 직접 알려 줍니다. ② 수명이 짧은 인스턴스 —— 기록 전에 회수되면 그 구간은
  사라집니다. ③ 하루치 샤드에는 2개의 슬롯밖에 없어서, 그보다 많은 복제본이 동시에 쓰면
  같은 슬롯은 나중에 쓴 쪽이 덮어씁니다.
- **읽지 못한 칸은 `—`를 표시하고 `0`으로 두지 않습니다.** "오늘 정말 요청이 0건이었다",
  "둘째 층이 꺼져 있다", "이번 읽기가 실패했다"는 서로 다른 셋이며, 패널이 그것들을 같은
  모습으로 그리는 것은 허용되지 않습니다.

## 모델

### 이 페이지가 답하는 것

- **이 페이지가 답하는 질문은 하나입니다**: 이 게이트웨이가 대외적으로 인정하는 모델은
  무엇이고, 각 모델은 어떤 유형이며, 실제로 어떤 프로토콜에서 쓸 수 있고, 어느
  엔드포인트를 호출해야 하는가.

### 세 가지 유형과 프로토콜 지원

- **유형은 세 가지**: 대화, 이미지, 동영상. 대화 모델은 네 가지 대화 프로토콜에 걸립니다.
  이미지와 동영상 모델은 프로토콜 열이 비어 있습니다 —— 어떤 대화 프로토콜에도 속하지
  않고 각자의 미디어 엔드포인트를 지나갑니다.
- **프로토콜 지원은 칸마다 붙는 배지**이지 "지원" 또는 "미지원"이라는 한마디가 아닙니다.
  이 열은 모델마다 따로 채웁니다. ⚠️ **오늘 카탈로그에는 "한 프로토콜에서는 되고 다른
  프로토콜에서는 안 되는" 모델이 하나도 없습니다**: 대화 모델은 네 가지 모두에서 쓸 수
  있고, 미디어 모델 셋은 이 열이 비어 있습니다. 프로토콜로 거를 수 있으며, 거른 결과가
  하나도 없으면 빈 표를 그리지 않고 "이 프로토콜에서 사용할 수 있는 모델이 없습니다"라고
  그대로 말합니다.

### 엔드포인트 열과 읽기 실패

- **엔드포인트 열이 주는 것은 "클라이언트가 어느 경로를 호출해야 하는가"**이며,
  [API.md](API.md)와 같은 진짜 출처에서 옵니다. 이 문서는 두 번째 사본을 두지 않습니다.
- **카탈로그를 읽지 못하면 이 페이지는 대시를 표시하고**, 같은 화면에 읽기 실패 배너와
  다시 시도 버튼이 함께 뜹니다. ⚠️ **"읽지 못했다"와 "모델이 하나도 없다"는 서로 다른
  일인데, 오늘 그것을 분명히 말해 주는 문구는 대시의 호버 설명에만 있습니다**(`title=`):
  마우스로는 보이지만 터치 화면에서는 나오지 않습니다.
- ⚠️ **대외 계약에 알려진 불일치가 한 군데 있어 그대로 적어 둡니다**: Gemini 쪽 모델 목록
  엔드포인트는 **모든** 모델에 대해 `generateContent`를 선언하며, **그 동영상 모델까지
  포함**합니다. 그러나 동영상의 실제 경로는 "작업 생성 + 폴링"의 두 단계입니다. 이
  페이지는 실제 사용 가능 여부로 채우므로, 둘이 어긋나면 이 페이지를 믿으세요.

## 플레이그라운드

### 두 열쇠는 엄격히 분리

- **두 열쇠는 엄격히 분리되어 있으며, 이것이 이 페이지에서 가장 중요한 점입니다.**
  관리 토큰은 `x-admin-key`로 가서 `/admin/api` 트리만 두드립니다. 플레이그라운드가 쓰는
  것은 **게이트웨이 토큰**(`GATEWAY_TOKEN`)이며, 각 프로토콜이 관례로 쓰는 인증 헤더를
  타고 대외 트리로 갑니다. 둘은 브라우저 안에 따로 저장되고 **로그아웃할 때 함께
  지워집니다** —— 공용 기기나 화면 공유 자리에서는, 지우지 않은 쪽이 그대로 다음 사람에게
  넘어갑니다.
- **게이트웨이 토큰은 직접 한 번 붙여 넣으며 "자동 채우기"는 없습니다**: 패널은 평문을
  읽을 수 없으므로(자격 증명은 쓰기 전용), 설정 페이지에 저장된 마지막 4자와 붙여 넣은
  값을 맞춰 보고 "일치", "불일치", "읽을 수 없어 이번에는 대조 못 함" 중 하나를 알려 줄
  뿐입니다.

### 세 가지 모드

- **모드는 세 가지이고, 각각 설정할 수 있는 것이 다릅니다**:

| 모드 | 호출하는 엔드포인트 | 이 모드에서 설정할 수 있는 것 |
|----|-------------------|-----------------------------|
| 대화 | 네 가지 대화 프로토콜 각각의 대외 경로 | 프로토콜과 모델을 고르고, 스트리밍을 켤 수 있음 |
| 이미지 | 이미지 생성 엔드포인트 하나 | 모델만. 프로토콜 선택도 스트리밍 스위치도 없음 |
| 동영상 | 작업 생성과 결과 조회 두 개 | 모델만. 작업을 만든 뒤 결과를 자동으로 폴링 |

**프로토콜 선택과 스트리밍 스위치는 대화 모드에서만 나타납니다.** 그냥 숨긴 것이
아닙니다: 프로토콜 카탈로그에서 미디어 쪽 두 엔드포인트는 어떤 대화 프로토콜에도 속하지
않으며, 누를 수 없는 버튼을 늘어놓으면 이미지도 프로토콜을 고르거나 스트리밍할 수 있다고
오해하게 만들 뿐입니다.

### 스트리밍과 동영상 모드

- **스트리밍에서는 token 수를 표시하지 않습니다**: 패널은 스트리밍 중 사용량을 읽지
  않으므로 거기에 `0`을 적으면 거짓이 됩니다. 그래서 그 칸에는 숫자를 두지 않습니다.
- **동영상은 두 단계입니다**: 먼저 작업을 만들어 작업 ID를 받고, 그 ID로 결과를 폴링합니다.
  폴링은 **5초마다, 상한은 60회 / 5분**이며 먼저 닿는 쪽이 적용됩니다 —— 오늘은 이 둘이
  정확히 같습니다(60회 × 5초가 딱 5분). 페이지가 숨겨져 있던 동안에는 폴링이 멈춰도
  벽시계는 흐르므로, 그때는 시간 쪽이 먼저 닿습니다.
- ⚠️ **진짜 업스트림이 동영상 한 편을 만드는 데 얼마나 걸리는지 이 저장소는 한 번도 재 본
  적이 없습니다.** 이 두 상한은 "닫는 것을 잊은 탭이 영구 폴링 기계가 되는 일"을 막으려고
  둔 것이지 실제 생성 시간에서 끌어낸 값이 아니며, 이 문서는 둘 사이의 관계에 대해 어떤
  결론도 내리지 않습니다. 상한에 닿으면 패널은 폴링이 상한에 도달해 멈췄다고 분명히 말하고
  작업 ID를 화면에 남깁니다 —— 작업 자체는 아직 돌고 있을 수 있으며, 나중에 그 ID로 직접
  조회할 수 있습니다.

### 보내기는 매번 실제로 업스트림을 호출

- **작업 생성 응답에 쓸 수 있는 작업 ID가 없으면 패널은 추측하지 않습니다**: 정해진 항목만
  ID로 읽고, 어느 것도 쓸 수 없으면 폴링하지 않으며, 응답 원문을 그대로 보여 줍니다.
- **"보내기"를 누를 때마다 실제로 업스트림을 호출합니다**: 그 요청은 평소의 전달과 완전히
  같은 경로를 지나가고, 쓰인 key도 똑같이 기록됩니다(보드 한눈에 보기 아래의 문장 참고).
  동영상은 한 번에 작업 생성 1회에 최대 60회의 폴링이 더해집니다.
- **화면에는 최대 20턴까지 남습니다.** 더 오래된 것은 이 페이지에서 지워지고, 몇 턴을
  지웠는지 패널이 알려 줍니다. "대화 지우기"로 직접 지울 수도 있습니다. 지워지는 것은
  화면의 이 사본뿐이고 서버 쪽은 아무것도 건드리지 않습니다.

## 설정

### 다섯 장의 카드

설정 페이지에는 오늘 다섯 장의 카드가 있습니다.

| 카드 | 무엇을 다루는가 | 알아 둘 점 |
|----|---------------|----------|
| 인증 키 | 게이트웨이 토큰 하나뿐. 관리 토큰은 이 카드에서 읽기 전용으로만 보이며, 패널은 자기 열쇠를 바꾸지 못합니다 | 자격 증명은 쓰기 전용: 입력란을 비우면 그 항목은 그대로 |
| 업스트림 및 쿨다운 | 업스트림 주소, 타임아웃, 쿨다운과 배제 손잡이들 | 그중 둘은 인스턴스를 만들 때 한 번 읽는 항목. 이 절 끝을 보세요 |
| 등록기 | 보충 손잡이 전부와 **각 메일 채널 자신의 자격 증명**(대칭인 하위 카드 두 장), 그리고 "고급" 접힘 영역 | 접힘 영역의 그 항목은 매번의 자동 가입이 어디로 가는지를 바꿉니다 |
| 통합 예제 | 그대로 실행할 수 있는 호출 예제 | 주소는 지금 패널을 연 오리진에서 가져오고, 토큰은 자리표시자입니다 |
| 위험 구역 | 되돌릴 수 없는 버튼 두 개: 설정 초기화와 Key 풀 비우기 | 둘 다 2차 확인을 거치고, 풀 비우기는 현재 풀 크기를 직접 입력해야 합니다 |

### 네 값과 우선순위

- **모든 항목이 네 쪽을 함께 펼칩니다**: 저장소에 무엇이 있는지, 환경 변수에 무엇이 있는지,
  지금 실효인 것은 어느 쪽인지, 그리고 누가 그것을 고정했는지. 우선순위는
  **환경 변수 > 저장소의 값 > 내장 기본값**입니다. 환경 변수에 고정된 항목은 이 페이지에서
  바꿔도 적용되지 않으며, 패널이 배포 쪽의 어느 변수를 바꿔야 하는지 바로 알려 줍니다.

### 자격 증명은 쓰기 전용

- **자격 증명은 쓰기 전용**: 패널은 평문을 받지 못하고, 화면에는 "설정됨 / 설정 안 됨"과
  마지막 4자만 나옵니다. 비워 두면 바꾸지 않음. 정말 지우려면 "지우기"를 눌러야 하며, 그
  단계는 지운 뒤 무슨 일이 생기는지를 먼저 알려 줍니다 —— 환경 변수의 값으로 되돌아가는지,
  다음 재시작에서 못 뜨는지, 지금은 아무것도 달라지지 않는지.

### 저장했을 때의 응답

- **저장한 뒤 패널이 내놓는 것은 "저장했다" 한마디가 아닙니다**: 실효값을 다시 읽고,
  정말로 바뀐 항목을 강조하고, 이번에 어떤 종류의 항목을 건드렸는지에 따라 전파를 나눠
  말합니다. 보통 항목이라면 화면의 문장은 **글자 그대로
  "이 인스턴스에는 이미 반영되었습니다"로 시작**하고, 이어서 다른 복제본 / isolate가
  이번 변경을 보기까지 최대 얼마가 걸리는지를 말합니다 —— 즉 이 인스턴스에는 이미
  적용되었다는 말이지, "아직 어디에도 적용되지 않았다"가 아닙니다.
  이 상한은 설정 캐시와 KV 엣지 캐시 두 겹을 더한 값입니다.
  ⚠️ **두 숫자 모두 환경 변수 표에는 없습니다**: 둘 다 `src/http/config-holder.ts`에
  하드코딩된 상수라 아무도 조정할 수 없습니다. 값은 [DEPLOY.md](DEPLOY.md)에서 설정 페이지의
  저장 응답을 설명하는 **본문**에 적혀 있습니다.

### 예외인 두 항목

- ⚠️ **예외인 항목이 둘 있습니다**: 풀 스냅숏 캐시와 쓰기 병합 간격(`POOL_CACHE_TTL_MS`와
  `POOL_TOUCH_INTERVAL_MS`)은 **인스턴스를 만들 때 한 번만 읽는** 항목입니다 ⇒ 저장해도
  **이 인스턴스조차 아직 적용되지 않았습니다.** 컨테이너를 다시 시작하거나 isolate가
  회수되어야 합니다. 이번 저장이 **이 둘만** 건드렸을 때는 위의 "이미 반영됨 + 상한"
  문장이 **통째로 나오지 않고**, 대신 "저장은 되었지만 이 인스턴스에도 아직 반영되지
  않았다"가 나옵니다. 두 종류를 함께 바꿨을 때는 두 문장이 같이 나옵니다.

### 패널은 자기 열쇠를 바꾸지 못한다

- **패널은 자기 열쇠를 바꾸지 못합니다**: `ADMIN_TOKEN`은 환경 변수에서만 읽습니다.
  교체하려면 배포 쪽 환경 변수를 바꾸고 다시 시작하세요.
- **저장소의 설정을 불러오지 못하면 이 페이지는 진단 화면이 됩니다**: 무엇이 빠졌는지 한
  건씩 늘어놓고, 게다가 **양식은 그대로 편집할 수 있습니다** —— 그것이 유일한 출구입니다.

## 위험 구역

설정 페이지의 마지막 카드입니다. 여기 있는 두 버튼은 모두 되돌릴 수 없고, 취소 경로도
없습니다.

| 버튼 | 건드리는 것 | 건드리지 않는 것 | 2차 확인 |
|----|-----------|----------------|--------|
| 설정 초기화 | 저장소의 설정 항목 하나를 쓰기 한 번으로 통째로 비웁니다(게이트웨이 토큰과 두 메일 채널의 자격 증명 포함) | 키 풀, 키별 사용량, 이벤트 기록, 보충 이력 | 대화 상자가 초기화 뒤에 무엇이 빠지는지 알려 준 다음 확인을 받습니다 |
| Key 풀 비우기 | 풀에 있는 모든 key의 레코드와 그 id 색인 | 설정, 이벤트 기록, 보충 이력 | 확인에 더해 현재 풀 크기를 직접 입력해야 합니다 |

### 초기화는 공장 초기화가 아니다

- **설정 초기화는 공장 초기화가 아닙니다.** 실효값은 "환경 변수 > 저장소 > 내장 값" 세
  층에서 정해지고, 이 버튼이 지우는 것은 가운데 층뿐입니다. 환경 변수로 잠긴 항목은 1비트도
  움직이지 않습니다. 그래서 일부 항목에는 아무 일도 하지 않으며, 화면은 실제로 바뀐 항목만
  강조해서 보여 줍니다.

### 비우기는 사용량 이력까지 가져간다

- **Key 풀 비우기는 사용량 이력까지 함께 가져갑니다.** 키별 요청 수, 성공 수, 마지막 오류는
  그 레코드의 값 안에 있어서, 레코드를 지우는 것은 이력을 지우는 것이며 되찾을 사본이
  없습니다. key 원문 역시 저장소에만 있습니다.

### 화면에서 끝나도 복제본은 아직이다

- **화면에서 끝났다고 모든 복제본이 따라잡은 것은 아닙니다.** 초기화 뒤 다른 복제본이나
  isolate는 설정 캐시와 엣지 캐시가 만료된 뒤에야 그것을 봅니다. 비운 뒤에도 전달 경로는
  풀 스냅숏 TTL과 엣지 캐시를 합한 시간만큼 그 key들을 계속 고를 수 있습니다. 풀 스냅숏 쪽
  상한의 손잡이(`POOL_CACHE_TTL_MS`)는 [DEPLOY.md](DEPLOY.md)의 환경 변수 표에 있습니다.
  ⚠️ **설정 쪽 상한은 그 표에 없습니다** —— `src/http/config-holder.ts`에 하드코딩된 상수
  둘을 더한 값이라 아무도 조정할 수 없고, 값은 같은 문서의 본문에 적혀 있습니다.
  이 문서 안에서는 설정 쪽 상한이 위의 설정 카드 설명에도 나오고, 풀 스냅숏 쪽은 개요
  페이지의 두 신선도 항목에 적혀 있습니다.

### 할당량과 자격 증명

- **각 버튼이 할당량을 얼마나 쓰는지는 [DEPLOY.md](DEPLOY.md)의 할당량 계산에 적혀
  있습니다**: 초기화는 쓰기 한 번, 비우기는 key 하나당 삭제 한 번에 색인 쓰기 한 번을 더한
  값입니다. 풀이 클수록 이 버튼은 비쌉니다.
- **두 버튼 모두 자격 증명을 되돌려 보여 주지 않습니다.** 초기화 응답에는 다시 읽어 온 네
  값, "설정 여부", 그리고 마지막 네 글자 힌트(`hint`, 설정 페이지의 자격 증명 칸에 나오는
  것과 같은 것)가 들어 있습니다 —— **이 페이지의 다른 곳과 글자 그대로 같은 기준입니다:
  마지막 네 글자는 있고, 평문은 한 글자도 없습니다.**

## 패널이 하지 않는 일

### 자기 열쇠를 교체하지 않는다

`ADMIN_TOKEN`은 환경 변수에서만 읽으므로 패널은 그것을 바꿀 수도 없고, "이미 내보낸 세션을
지금 즉시 무효로 만든다"는 철회 경로도 없습니다. 교체란 배포 쪽 변수를 바꾸고 다시
배포하거나 컨테이너를 다시 만드는 일입니다.

### 자격 증명의 평문을 되돌려 보여 주지 않는다

백엔드가 돌려주는 것은 "설정 여부"와 마지막 4자뿐이라, "내 토큰을 채워 줘" 같은 버튼은
만들 수 없습니다 —— 그러려면 백엔드에 평문을 읽어 내는 구멍이 필요하고, 그 구멍이 한 번
열리면 쓰기 전용 원칙은 통째로 사라집니다.

### wrangler secret이나 .env를 대신하지 않는다

이 페이지가 바꾸는 것은 저장소 쪽 설정이고, 환경 변수가 더 우선합니다. 둘이 어긋나면
화면에 잠금 표시가 붙지만, 환경 변수 자체를 바꾸는 일은 배포 쪽에서만 할 수 있습니다.

### 원격 미디어를 대신 가져오지 않는다

플레이그라운드의 결과 주소는 온 그대로 나열되어 언제든 복사할 수 있습니다. **"열기" 링크가
붙는 것은 `http` / `https` 로 시작하는 것뿐**이고, `javascript:` / `blob:` / `file:` 은
업스트림이 정말로 돌려주더라도 붙지 않습니다(따라가면 업스트림 내용이 정하는 최상위 문서가
되기 때문입니다). 삽입되는 것은 `data:` 형식의 이미지뿐이고, 그 경로는 어떤 제삼자에게도
요청을 만들지 않습니다.

## 문제 해결

### 열리지 않고 `404`가 돌아온다

**원인**: 이 배포에 `ADMIN_TOKEN`이 없거나, 설정했지만 규칙에 맞지 않았습니다. 트리가
등록되지 않았으므로 바깥에서는 관리 화면이 있는지조차 알 수 없습니다.

**해결**: 배포 쪽에서 규칙에 맞는 `ADMIN_TOKEN`을 다시 설정하고(세 조건은 이 문서 앞부분에
있습니다), 다시 배포하거나 컨테이너를 다시 만드세요.

### 열리지 않고 `401`이 돌아온다

**원인**: 토큰 자체가 틀렸습니다. 대개는 이미 교체된 값입니다.

**해결**: 지금 쓰이는 `ADMIN_TOKEN`을 다시 입력하세요. ⚠️ **이것을 패널이 로그인 화면으로
되돌리는 동작과 뭉뚱그리지 마세요**: 12시간이라는 구간은 패널이 스스로 판정하며, 그때가
되면 요청이 한 건도 나가지 않으므로 서버 쪽에는 아무 기록도 남지 않습니다. 둘 다 다시
입력하면 됩니다.

### 열리지 않고 `503`이 돌아온다

**원인**: `ADMIN_TOKEN`이 저장소 쪽 게이트웨이 토큰과 같은 값이 되었습니다. 이 규칙은 관리
요청마다 다시 확인되며, 이벤트 보드와 로그에 `admin.token_conflict`가 한 건 남습니다.

**해결**: 저장소 쪽 게이트웨이 토큰을 `ADMIN_TOKEN`과 다른 값으로 바꾸세요. ⚠️ **이 단계로
회복되는 것은 가용성뿐입니다**: 그 관리 토큰은 유출된 것으로 다루어야 하고, 전체 절차는
[DEPLOY.md](DEPLOY.md)에 있으며, 두 단계를 모두 마쳐야 처리가 끝납니다.

### 토큰을 붙여 넣으면 로그인 칸이 문자를 거부한다

**원인**: 패널은 보내기 전에 문자 종류를 먼저 판정하며 출력 가능한 ASCII(`0x20–0x7E`)만
받습니다. `U+00FF`를 넘는 코드 포인트 —— 한자, 이모지, 폭 없는 공백 —— 그리고 NUL / LF / CR
은 브라우저가 애초에 보낼 수 없고, `é` / `£` 는 보낼 수는 있지만 런타임 간 인코딩을 고려해
이 게이트웨이도 받지 않습니다. 이 경로에서는 **요청이 한 건도 나가지 않으므로** 서버 쪽에는
로그인 실패 한 건조차 남지 않습니다.

**해결**: 출력 가능한 ASCII로만 만든 토큰으로 바꿔 다시 붙여 넣으세요. ⚠️ **그런 토큰을 들고
있는 쪽이 배포 쪽이라면 이 문구는 볼 수 없습니다**: 그때는 트리가 아예 등록되지 않으며,
돌아오는 것은 위의 `404` 입니다.

### 화면이 옛날 값 그대로다

**원인**: 설정과 풀 스냅숏은 각자의 캐시 구간을 가지며, 그 바깥에 KV 엣지 캐시가 한 겹 더
있습니다. 풀 스냅숏 쪽 상한과 대가는 [DEPLOY.md](DEPLOY.md)의 환경 변수 표에 있습니다.
설정 쪽 상한은 하드코딩된 상수라 **그 표에는 없고**, 값은 같은 문서의 본문에 적혀 있습니다.
둘 다 여기에 옮겨 적지 않습니다.

**해결**: 두 겹의 캐시가 각각 만료되기를 기다리거나, 컨테이너를 다시 시작하고 isolate가
회수되기를 기다리세요. 개요 페이지의 "몇 초 전에 읽었는지" 두 줄이 바로 이것을 위한
것입니다.

### 오류 문구가 백엔드의 원문이다

**원인**: 패널은 **자기가 아는** 오류 코드에는 자기 언어 문구를 보여 주고, 모르는 코드에는
백엔드의 문장을 그대로 내놓으면서 옆에 "이것은 백엔드의 원문입니다. 이 패널에는 그 오류
코드의 번역문이 아직 없습니다"라고 표시합니다.

**해결**: 그 원문을 단서로 로그와 이벤트 보드를 확인하세요. ⚠️ **이것을 "모든 오류가 내
언어로 나온다"로 읽지 마세요** —— 알아보지 못한 것들은 그렇지 않으며, 패널은 번역문인
척하기보다 그 사실을 표시하는 쪽을 고릅니다.
