# 관리 패널

**언어:** [English](../en/ADMIN.md) | [简体中文](../zh-CN/ADMIN.md) | [繁體中文](../zh-TW/ADMIN.md) | [日本語](../ja/ADMIN.md) | 한국어

관리 패널은 **선택 사항**입니다. `ADMIN_TOKEN`을 설정하지 않으면 `/admin` 트리 자체가
등록되지 않으며, 게이트웨이는 평소대로 전달을 계속합니다. 이 문서가 다루는 것은 화면에
보이는 쪽입니다. 각 보드가 어떤 질문에 답하는지, 화면의 수치가 어떤 기준인지, 어떤 동작이
저장소에 쓰는지를 설명합니다. **변수 자체(기본값·허용 범위·대가)는 저장소 전체에서 단
한 곳, [DEPLOY.md](DEPLOY.md)의 환경 변수 표에만 있습니다.** 여기서는 그쪽을 가리키기만
하고 두 번째 사본을 두지 않습니다.

이 문서가 다루는 범위: 패널에 들어가는 방법과 개요 / Key 풀 / 레지스트라 / 이벤트 /
사용량 보드입니다.

## 패널에 들어가기

- **주소**: `https://<your-gateway>/admin`. `<your-gateway>`는 본인의 게이트웨이 주소로
  바꾸세요. 끝에 슬래시가 붙은 `/admin/`는 `/admin`으로 자동 이동하므로, 손으로 입력하는
  두 가지 방식 모두 들어갈 수 있습니다.
- **전제 조건은 하나뿐**입니다. 배포할 때 `ADMIN_TOKEN`을 설정하는 것입니다. 최소 24자
  이상이어야 하고, 출력 가능한 ASCII로만 이루어져야 하며, `GATEWAY_TOKEN`과 달라야 합니다.
  세 조건 각각의 이유와 경계, 그리고 규칙에 맞지 않을 때 어떤 이벤트가 기록되는지는
  [DEPLOY.md](DEPLOY.md)의 "관리 패널 관련 변수" 절에 있습니다.
- **설정하지 않았거나 규칙에 맞지 않으면 `/admin`은 `401`이 아니라 `404`를 돌려줍니다.**
  트리가 아예 등록되지 않았으므로 "여기에 관리 화면이 있다"고 밖에 알리지도 않습니다.
  패널을 열 수 없어도 **게이트웨이 전달에는 영향이 없습니다**.
- **토큰은 브라우저의 localStorage에 그대로 저장되며**, 패널은 12시간 뒤에 다시 입력하도록
  요구합니다.
- 이 상한이 줄이는 것은 localStorage에 놓인 값의 사용 가능 구간일 뿐 **철회가 아닙니다**.
  철회하는 길은 하나뿐입니다. `ADMIN_TOKEN`을 새 값으로 바꾸고 다시 배포하거나 컨테이너를
  다시 만드는 것입니다. 패널은 TLS 뒤에 두고, 신뢰하는 기기에서만 여세요. 자세한 논증은
  [DEPLOY.md](DEPLOY.md)의 "관리 토큰 유출" 문단에 있습니다.

| 레지스트라 | 자동 보충이 돌고 있는가, 최근 몇 회에 무엇을 발급했는가 | 씀 | `REGISTRAR_ENABLED` |

| 모델 | 게이트웨이가 대외적으로 인정하는 모델과 그 모달리티·프로토콜 | 읽기 전용 | – |
| 플레이그라운드 | 진짜 요청 한 번으로 특정 프로토콜이 통하는지 확인 | 업스트림 호출 | – |
| 설정 | 런타임 설정의 현재 값과, 환경 변수에 고정된 항목 | 씀 | – |

"씀"은 **저장소에 쓴다**는 뜻이고, "업스트림 호출"은 저장소에는 쓰지 않지만 업스트림으로
실제 요청을 한 번 보낸다는 뜻입니다.

## 개요

개요가 답하는 질문은 하나입니다. **이 배포는 지금 어떤 형태이고, 풀에 쓸 수 있는 key가
몇 개 남았는가.**

- **풀의 다섯 버킷**: 총계 / 사용 가능 / 쿨다운 중 / 배제됨 / 비활성화됨. 다섯 칸 모두 항상
  표시합니다. 진짜 `0`은 그 자체로 참이기 때문입니다. **읽지 못한 칸은 `—`를 표시하고
  `0`을 지어내지 않습니다** —— 이 둘은 화면에서 같은 모습이어서는 안 됩니다.
- **런타임과 저장소의 자기 보고**: 런타임 이름, 버전, 서버 시각, 저장소 백엔드, 쓰기 가능
  여부, 그리고 Node 형태에만 있는 메모리 / 가동 시간 / PID. 모두 API가 돌려준 데이터만
  사용하며, 패널이 자기가 어느 런타임에서 도는지 넘겨짚지 않습니다. Worker 형태에는 상주
  프로세스가 없으므로 그 세 칸은 "상주 프로세스 없음"으로 표시됩니다. `0`도 공백도 아닙니다.
- **두 줄의 신선도**: 풀 스냅숏과 설정은 각각 "몇 초 전에 읽었는지"를 따로 가집니다. 같은
  시간축이 아니므로 나누어 표시합니다. 풀 쪽의 지연은 `POOL_CACHE_TTL_MS`에 엣지 캐시 한
  겹이 더해져 정해지며, 그 상한과 대가는 [DEPLOY.md](DEPLOY.md)의 해당 칸에 적혀 있습니다.
- **첫째 층 누적 사용량**: 요청 수 / 성공 / 실패 / 클라이언트 오류 / 성공률. 풀 전체 key의
  누적 합계이므로 `≈`가 붙습니다. key별 카운터는 동시 요청에서 적게 집계되고(KV에 CAS가
  없음), 저장은 최대 `POOL_TOUCH_INTERVAL_MS` 하나만큼 늦어집니다.
- **설정 요약**: 레지스트라 스위치, 주/보조 채널, `TARGET_KEYS`의 현재 실효값. 환경 변수에
  고정된 필드에는 잠금 표시가 붙습니다 —— 그 항목들은 설정 페이지에서 바꿔도 적용되지
  않습니다. 환경 변수가 우선하기 때문입니다.

## Key 풀

- **버킷 배지는 우선순위를 한 번 투영한 결과**이지 독립된 네 개의 깃발이 아닙니다. 하나의
  key가 여러 조건을 동시에 만족하면 비활성화됨 > 배제됨 > 쿨다운 중 > 사용 가능 순서로
  첫 번째를 취합니다. 그래서 "비활성화되었고 아직 쿨다운 중"인 key의 배지는 "비활성화됨"이
  됩니다. 쿨다운이 사라진 것이 아니라 배지에서 보이지 않을 뿐입니다.
- **단건 동작 여덟 가지**: 비활성화, 활성화, 쿨다운 해제, 실패 횟수 초기화, 배제 취소,
  메모 수정, 연결 확인, 삭제.
- **일괄 동작 세 가지**: 일괄 비활성화, 일괄 쿨다운 해제, 일괄 삭제.
- **한 번에 최대 200개의 key까지 가져옵니다.** 이 수를 넘기면 곧바로 `400`이고, **조용히
  잘라내지 않습니다** —— 잘라내기는 "넣은 줄 알았는데 사실 없었다"를 만듭니다.
- **"이미 있는 key의 상태를 초기화" 체크박스가 실제로 초기화하는 것**: **시스템이 판정한
  실패 상태**입니다. 실패 횟수, 쿨다운 만료 시각, 쿨다운 사유, 배제 표시, 배제 사유.
  다음 네 가지는 **일부러 건드리지 않습니다**: 비활성화 상태(직접 내린 스위치이며, 한 번의
  붙여넣기로 조용히 되돌릴 일이 아닙니다), 추가 시각(내력은 실패 상태가 아닙니다), 사용량
  통계(이력은 실패 상태가 아닙니다), 메모(스스로 보려고 적어 둔 말입니다).
- **삭제하려면 먼저 비활성화해야 합니다.** 아직 쓰이고 있는 key를 그대로 지우려 하면
  거부됩니다. 일괄 경로에서는 이 제약이 배치 전체의 실패가 아니라 항목별 사유로 돌아옵니다.
- **단건 연결 확인**은 그 key로 업스트림에 실제로 한 번 요청을 보냅니다. 목록의 "마지막
  사용"과 사용량 카운터는 모아 두었다가 저장하므로, 해상도는 `POOL_TOUCH_INTERVAL_MS`
  간격보다 더 촘촘해지지 않습니다.

## 레지스트라

패널의 레지스트라 보드는 **색인이지 설명서가 아닙니다.** 보충 규칙 전부, 채널 고르는 법,
직접 준비해야 하는 자격 증명, 문제가 났을 때 추적하는 법은 모두
[REGISTRAR.md](REGISTRAR.md)에 있으며 이 문서는 두 번째 사본을 두지 않습니다. 보드에서
볼 수 있는 것은 다음과 같습니다.

- **메일 채널 둘은 대등하며** 기본값이 없습니다. 주 채널은 반드시 명시해야 하고 보조 채널은
  비워 두어도 됩니다. 보드에는 각각의 역할(주 / 보조)과 자격 증명 설정 여부가 표시됩니다.
- **보충 이력**: 각 회차가 언제 돌았는지, 어느 채널을 탔는지, 타이머가 시작했는지 사람이
  눌렀는지, 얼마나 걸렸는지.
- **채널 테스트는 그 채널의 사용 가능한 도메인 목록만 읽습니다.** 메일박스를 만들지도,
  계정을 등록하지도, 정원을 소비하지도 않습니다.
- **"지금 보충"에는 네 개의 가드레일**이 있고, 하나라도 만족하지 못하면 시작하지 않습니다.
  같은 복제본 안의 진행 중 가드, 복제본 사이의 저장소 단기 잠금, 수동 보충 사이의 최소
  간격, 그리고 하루 수동 실행 상한입니다. 각각의 오류 코드·산식·잔여 위험은
  [REGISTRAR.md](REGISTRAR.md)의 "관리 패널의 「지금 보충」" 절에 있습니다.
- 레지스트라가 꺼져 있으면(`REGISTRAR_ENABLED`가 `true`가 아니면) 보드는 그대로 보이지만
  상태가 꺼짐으로 표시되고, "지금 보충"은 백엔드에서 거부됩니다.

## 이벤트

- 여기에는 **저빈도 구조화 이벤트**만 실립니다. 설정 읽기 실패, 풀 색인 재구축, 관리 API
  로그인 실패 같은 운영 진단에 더해, 레지스트라의 보충 이벤트와 패널 자신의 쓰기 동작입니다.
  **전달 경로가 key를 자동으로 쿨다운에 넣거나 배제할 때는 지금은 이벤트를 내지 않습니다**
  —— 그 부분은 Key 풀 보드에서 그 key 자신의 상태를 보세요.
- **도구 모음**: 수준으로 거르기, 텍스트로 검색, 자동 새로 고침 일시정지, 지우기, 내려받기.
  "지우기"는 화면의 이 목록만 지우며 **서버에 이미 저장된 이벤트는 건드리지 않습니다.**
  다시 보려면 "내려받기"를 누르거나 페이지를 새로 고치세요.
- **이벤트는 시간 단위 창에 담기고, 24개의 창이 유지됩니다** —— 꼬박 하루치이며, 그보다
  오래된 것은 저절로 만료되어 패널에서 더는 찾을 수 없습니다.
- 네 가지 경고 바는 각각 다른 이야기를 합니다.

| 경고 바 | 무엇을 말하는가 | 무엇을 해야 하는가 |
|---|---|---|
| 버려짐 | 이 복제본의 이벤트 버퍼가 저장되기 전에 가장 오래된 몇 건을 밀어냈다 | 이벤트가 저장보다 빨리 생긴다. 컨테이너 로그 / Workers Logs에서 그 구간을 찾는다 |
| 예산 | 이 복제본의 오늘치 이벤트 쓰기 예산을 다 썼다 | 위와 같다. 저장되지 못한 것들은 로그에 남아 있다 |
| 잘림 | 이 페이지가 조건에 맞는 이벤트를 전부 보여 주지 못했다 | 필터를 좁히거나, 보려는 기간을 짧게 한다 |
| 커서 | 가져오기 위치가 계약에 어긋나거나 서버 시계보다 앞서 있다 | 패널이 이미 다시 가져왔다. 반복되면 이벤트 저장소를 이 게이트웨이 밖의 무언가가 썼다는 뜻이다 |

## 사용량

- **사용량은 두 층이고, 첫째 층은 언제나 있습니다.** 첫째 층은 풀 전체의 누적 수치(개요
  페이지 위쪽 카드가 쓰는 것이 바로 이것)로 스위치가 필요 없습니다. 둘째 층은 일 / 시간 /
  모델 / 프로토콜로 분해한 시계열이며 `USAGE_STATS_ENABLED`가 제어하고 **기본값은 꺼짐**입니다.
- **꺼져 있는 동안 이 페이지는 빈 차트를 그리지 않습니다.** `0`으로 채워진 차트는 "이 기간에
  아무도 쓰지 않았다"로 읽히지만, 사실은 "이 배포는 애초에 기록하지 않는다"입니다. 이 둘이
  같은 모습이어서는 안 됩니다.
- **기간은 네 단계**: `24h`, `3d`, `7d`, `30d`.
- **최대 30일까지 보관하며** 그보다 오래된 데이터는 만료되었습니다. 가장 긴 단계는 구간
  전체의 샤드를 한 번에 읽는데, 그것이 Cloudflare Worker에서 항상 완료되는지를 이 저장소는
  실제 환경에서 측정한 적이 없습니다 —— 실패하면 완전해 보이는 숫자를 내놓는 대신 읽기
  실패로 그대로 표시합니다.
- **여기 수치에는 `≈`가 붙고, 출처 세 가지는 서로 다릅니다**: ① 저장되지 못한 꼬리 ——
  카운터는 먼저 인스턴스 메모리에 쌓였다가 나중에 한꺼번에 기록되며, 이 구간의 길이는
  패널이 직접 알려 줍니다. ② 수명이 짧은 인스턴스 —— 기록 전에 회수되면 그 구간은
  사라집니다. ③ 하루치 샤드에는 2개의 슬롯밖에 없어서, 그보다 많은 복제본이 동시에 쓰면
  같은 슬롯은 나중에 쓴 쪽이 덮어씁니다.
- **읽지 못한 칸은 `—`를 표시하고 `0`으로 두지 않습니다.** "오늘 정말 요청이 0건이었다",
  "둘째 층이 꺼져 있다", "이번 읽기가 실패했다"는 서로 다른 셋이며, 패널이 그것들을 같은
  모습으로 그리는 것은 허용되지 않습니다.
