# 배포 가이드

**언어:** [English](../en/DEPLOY.md) | [简体中文](../zh-CN/DEPLOY.md) | [繁體中文](../zh-TW/DEPLOY.md) | [日本語](../ja/DEPLOY.md) | 한국어

agnes2api는 동일한 코드베이스와 요청 처리 로직으로 만들어진 두 가지 배포
대상을 제공합니다. 여러분의 인프라에 맞는 쪽을 선택하면 됩니다. 두 방식의
차이는 저장소 백엔드뿐입니다. Worker는 Cloudflare KV 네임스페이스를, Docker는
마운트된 볼륨 위의 JSON 파일을 사용합니다.

## 환경 변수

| 변수 | 필수 여부 | 기본값 | 설명 |
|---|---|---|---|
| `GATEWAY_TOKEN` | **예** | – | 클라이언트가 이 게이트웨이를 호출할 때 반드시 제시해야 하는 토큰. |
| `AGNES_BASE_URL` | 아니오 | `https://apihub.agnes-ai.com/v1` | 업스트림 Agnes API의 base URL. |
| `UPSTREAM_TIMEOUT_MS` | 아니오 | `8000` | **스트리밍** 응답과 비디오 폴링의 첫 바이트 타임아웃. 이 시간(밀리초) 안에 업스트림의 첫 바이트가 도착하지 않으면 호출을 중단. |
| `UPSTREAM_SYNC_TIMEOUT_MS` | 아니오 | `120000` | **동기** 엔드포인트의 전체 타임아웃 예산. "첫 바이트가 업스트림이 결과 전체를 계산한 뒤에야 도착하는" 요청에만 적용됨: 이미지 생성, 비디오 작업 생성, 그리고 모든 **비스트리밍** 대화. 아래 설명 참조. |
| `MAX_STRIKES` | 아니오 | `3` | 연속된 일시적 실패(타임아웃, 네트워크 오류, 업스트림 `5xx`)가 이 임계값에 도달하면 해당 key를 긴 쿨다운에 넣음. |
| `COOLDOWN_RATE_LIMIT_MS` | 아니오 | `60000` | 업스트림이 `429`를 반환한 뒤 해당 key에 적용되는 쿨다운 시간. |
| `COOLDOWN_PAYMENT_MS` | 아니오 | `3600000` | 업스트림이 `402`를 반환한 뒤 해당 key에 적용되는 쿨다운 시간. |
| `COOLDOWN_STRIKE_MS` | 아니오 | `1800000` | key의 일시적 실패가 `MAX_STRIKES`에 도달한 뒤의 쿨다운 시간. 만료되면 자동으로 복구됨. |
| `POOL_CACHE_TTL_MS` | 아니오 | `60000` | 각 isolate/프로세스가 key 풀 스냅숏을 메모리에 유지하는 시간. `0`이면 캐시를 끔. **KV 읽기 횟수는 요청 수와 무관**하며 갱신 주기로만 결정됨. 산식은 아래 "할당량 계산" 참조. 대가: 다른 isolate가 판정한 쿨다운/제외가 이 isolate에 보이기까지 최대 **이 값 + 약 60초**가 걸림(60초는 KV 엣지 캐시의 기본 `cacheTtl`). 기본값 60000일 때 상한은 약 **120초**. 게다가 "늦게 보이는" 것만이 문제가 아님: 오래된 스냅숏 위에서 일어나는 스케줄링 관련 쓰기는 레코드 전체를 덮어써, 다른 isolate가 그 창 안에서 막 기록한 `evicted` / `cooldownUntil`을 **지워버림**——그 판정을 처음부터 다시 해야 함. |
| `POOL_TOUCH_INTERVAL_MS` | 아니오 | `21600000` | key의 "마지막 사용 시각"을 최대 얼마 만에 한 번 저장할지. `0`이면 성공한 요청마다 저장. 표시 전용 필드로 스케줄링은 전혀 읽지 않으며, 요청마다 쓰면 무료 등급의 하루 1,000회 쓰기 할당량을 다 써버려 쿨다운과 제외조차 기록하지 못함. 대가: "마지막 사용"의 정밀도가 이 간격까지 거칠어짐. 같은 간격은 패널의 사용량 카운터(요청 수 / 성공률)에도 적용됨. **스토리지의 `stats`를 손으로 줄이면(예: 0으로 초기화) 패널에 잠깐 그 값이 보였다가 다시 옛 값으로 되돌아갈 수 있음**: 스냅숏은 TTL이 지나면 초기화된 레코드를 읽지만, 실행 중인 인스턴스는 자신이 저장한 기준값을 기억하고 다음 실제 저장 때 그 값을 다시 씀. 늦어도 해당 인스턴스가 회수된 뒤에는 완전히 일치함. P3c에서 repo를 거치는 정식 초기화 경로를 제공할 예정. |
| `PORT` | 아니오 (Node/Docker 전용) | `8080` | Node 런타임의 리스닝 포트. Worker에서는 사용되지 않음. |
| `DATA_DIR` | 아니오 (Node/Docker 전용) | `/app/data` | 파일 저장소가 `store.json`을 쓰는 디렉터리. Worker에서는 사용되지 않음. |

`COOLDOWN_RATE_LIMIT_MS`와 `COOLDOWN_PAYMENT_MS`는 기본적으로
`.env.example`에 나열되어 있지 않지만, 두 배포 대상 모두 환경 변수로 읽어
들이므로 필요에 따라 설정할 수 있습니다. 위의 수치형 변수는 모두 정수여야 하며,
`POOL_CACHE_TTL_MS`와 `POOL_TOUCH_INTERVAL_MS`는 하한이 `0`("끔"을 의미)이고 나머지는
모두 `0`보다 커야 합니다. 그렇지 않으면 게이트웨이가 기동을 거부합니다.

`POOL_CACHE_TTL_MS`와 `POOL_TOUCH_INTERVAL_MS`는 **app을 만들 때 한 번만** 읽습니다.
변경하려면 컨테이너를 재시작하거나 isolate가 회수되기를 기다려야 하며, 다른 설정
항목처럼 요청마다 반영되지는 않습니다.

### 할당량 계산: Worker + 무료 등급 KV로 하루 몇 건을 처리할 수 있나

무료 등급 KV는 하루 100,000회 읽기, 1,000회 쓰기입니다. 게이트웨이의 읽기와 쓰기는 모두
**요청 수에 비례해 늘어나지 않습니다**. 따라서 "요청당 몇 회"가 아니라 "하루에 몇 회"로 셉니다.

- **기본 설정에서는 KV가 더 이상 병목이 아니며**, 상한은 Cloudflare Workers 무료 등급 자체의
  **하루 100,000 요청**이 됩니다. 다만 이 결론에는 **전제가 있으며 무조건적이지 않습니다**:
  KV 읽기 할당량은 대신 "동시에 활성인 isolate 수"를 제약하는데, 이는 트래픽의 지리적 분포에
  따라 달라지는 값이라 직접 지정할 수 없습니다. 활성 isolate 하나가 하루에

      (86400 ÷ POOL_CACHE_TTL_MS 초) × (1 + 풀의 key 수)  +  2880

  회를 읽습니다. 끝의 2880은 설정 홀더가 30초마다 갱신하는 몫이며 같은 할당량을 씁니다.
  기본값에 key 20개면 isolate당 **33,120회**이고, 하루 48~96회의 인덱스 대조를 더하면
  **활성 isolate 3개로 약 99.5%를 소진**합니다. 즉 권장 설정에서 이미 임계점입니다.
  isolate가 더 많을 것으로 예상되면 `POOL_CACHE_TTL_MS`를 키우세요(key 20개에 isolate 5개면
  약 `120000`).
- **캐시를 끄면**(`POOL_CACHE_TTL_MS=0`, 비상 탈출구) 읽기가 요청 수에 비례해 늘어나며
  하한은 대략 `100,000 ÷ (1 + key 수)` ⇒ key 20개일 때 **하루 약 4,700 요청**입니다.
- **쓰기 쪽**: 정상 상태에서 하루 약 `key 수 × 4`회(`lastUsedAt`을 6시간마다 한 번 갱신).
  key 20개면 80회로 쓰기 할당량의 8%이고, 나머지는 쿨다운과 제외 기록에 쓰입니다. 여기에
  각 key가 처음 사용될 때 일회성 쓰기가 한 번 더 발생합니다.
- **이벤트 보드(Task 6)의 쓰기 쪽**: 각 isolate는 하루 최대 `EVENT_WRITES_PER_DAY`(**12**)회까지만
  저장합니다. 초과하면 `budgetExhausted`가 사실대로 보고되며, 조용히 버리거나 재시도하지
  않습니다. **이 게이트는 단일 isolate 내부에서만 작동**하며, 전체적으로 안전한지는
  "동시 isolate 수 × 이 값"이 여전히 할당량 안에 들어오는지에 달려 있습니다——하나의
  isolate는 다른 isolate가 할당량을 얼마나 썼는지 알 방법이 없습니다(CAS도, isolate 간
  조율도 없음). **동시 isolate 8개**로 추정하면(이 절의 다른 곳에서 쓰는 3개보다 더
  보수적인 값입니다: 트래픽이 적은 개인용 게이트웨이라도 Cloudflare 엣지는 전 세계에
  퍼져 있어 실제 동시 isolate 수를 완전히 제어할 수 없기 때문입니다): `12 × 8 = 96`회/일,
  쓰기 할당량의 **9.6%**. 위의 key 풀 쓰기 쪽(하루 80회, 8%)과 합치면 총 약 176회/일
  (**17.6%**)이며, 약 82%의 여유가 남습니다. **이 계산은 리뷰에서 실제 문제를 발견했기
  때문에 존재합니다**: 초기 버전은 시간 단위로 예산을 계산했고 각 isolate가 독립적으로
  시간당 최대 12회까지 세었기 때문에, isolate가 4개만 있어도 쓰기 할당량을 뚫을 수
  있었습니다(`4 × 12 × 24 = 1,152`, 1,000 초과). 수정 방법은 예산 창을 "시간 단위"에서
  "일 단위"로 바꾸고 이 계산을 여기에 적어 두는 것이었습니다. 같은 라운드에서 콜드
  스타트한 isolate의 첫 플러시가 스로틀링을 건너뛰던 허점도 막았습니다——예전에는
  isolate가 콜드 스타트할 때마다 무조건 쓰기가 한 번 발생했지만, 이제는 콜드 스타트 후
  첫 플러시도 다른 모든 플러시와 같은 최소 간격 게이트를 통과합니다.
- **이벤트 보드의 읽기 쪽**: 폴링은 더 이상 인덱스에 의존하지 않으므로 후보 키 수가
  **유계(bounded)**입니다——패널을 처음 열 때(또는 뷰를 지우고 다시 불러올 때, `after` 없이
  API를 직접 호출할 때)는 "콜드 읽기"로, 24개의 시간 윈도우 × 2개의 슬롯 = 48회의 get을
  스캔합니다. 그 이후의 각 폴링은 "웜 읽기"로, 보통 2회의 get만 필요합니다(폴링이 시간
  윈도우 경계를 넘는 순간에만 4회). **배포가 얼마나 오래 실행되었는지, 이벤트가 얼마나
  쌓였는지와는 무관합니다.** 탭 하나를 열어 두고 계속 폴링할 경우 웜 읽기의 상한은 하루
  약 23,000회(읽기 할당량의 약 23%; 실제로는 윈도우 경계를 넘는 폴링이 일부에 불과하므로
  보통 이보다 훨씬 낮습니다). **이는 위의 key 풀 읽기 쪽에 추가로 더해집니다**: 배포가
  이미 풀 읽기 할당량에서 빠듯하다면(위의 "활성 isolate 3개가 이미 약 99.5%를 사용" 시나리오
  참고), 이벤트 보드를 열기 전에 `POOL_CACHE_TTL_MS`를 늘리거나 동시에 여는 패널 탭 수를
  줄이는 것을 고려하세요.
- **`list`와 `delete`는 또 다른 두 개의 할당량이며 각각 하루 1,000회**로, 읽기·쓰기 할당량과는
  별개입니다. 정상 상태의 전달에서는 `list`가 한 번도 발생하지 않습니다 — `pool:index` 인덱스
  키가 바로 그 때문에 존재합니다. 이를 소비하는 곳은 **세 군데**입니다: 하루 48~96회의 인덱스
  대조(독립적으로 스케줄되는 작업); **풀이 비었을 때의 폴백 스캔**(인덱스는 정상인데 살아 있는
  레코드를 하나도 읽지 못할 때, 수동으로 가져온 레코드가 인덱스에 빠져 있는지 확인하려고
  `list`를 한 번 실행합니다); 그리고 **인덱스 유실 시 폴백**(`pool:index` 자체를 읽을 수 없거나
  파싱에 실패했을 때 마찬가지로 `list`를 한 번 실행해 인덱스 재구축을 시도합니다 — 대개 쓰기
  할당량이 소진되어 인덱스를 끝내 만들지 못한 경우입니다). 뒤의 두 가지는 내장된 **10분**
  백오프를 **공유**합니다(환경 변수가 아닌 고정 상수) — 둘 다 같은 `list` 할당량을 쓰므로 각자
  따로 창을 열어봐야 의미가 없습니다 — 따라서 풀이 비어 있거나 인덱스가 깨진 동안에도
  isolate당 하루 최대 144회이며, 인덱스 대조의 48~96회를 더해도 여유가 남습니다.
- **`list` 할당량이 소진되면 성능 저하가 아니라 기능 정지입니다.** 풀이 비어 있고 `list`가
  실패하면 게이트웨이는 `500`을 반환하고 실제 원인을 로그에 남깁니다. **`503 pool_empty`로
  위장하지 않습니다** — 이때 대조 역시 같은 할당량을 쓰고 있어 함께 실패하며, 이 문서가 제시한
  두 가지 자가 치유 경로가 모두 사라진 상태이기 때문입니다. UTC 자정에 할당량이 재설정될
  때까지 복구되지 않습니다.

**위의 읽기 산식에는 "isolate가 TTL보다 오래 산다"는 전제가 있습니다.** 트래픽이 적거나
충분히 많은 Cloudflare 엣지 위치로 분산되면 isolate는 TTL 한 주기가 다 지나기 전에 회수되는
경우가 흔하며, 그때는 각 isolate가 생애 동안 최소 한 번은 풀을 로드하므로 읽기 횟수는
TTL이 아니라 **콜드 스타트 횟수**로 결정됩니다. 상한은 대략 `100000 ÷ (풀 안의 key 수 + 2)`
콜드 스타트/일입니다(`+2`는 인덱스와 설정에 각각 한 번씩). **이 구간에서는 `POOL_CACHE_TTL_MS`를
키워도 읽기가 한 번도 절약되지 않습니다** — 절약되는 것은 "같은 isolate 안에서의 중복 로드"뿐입니다.

같은 이유로 풀이 비었을 때와 인덱스가 유실됐을 때의 `list` 백오프도 **인스턴스별**입니다.
차가운 isolate마다 각자 비용을 치르므로 총량은 isolate 수에 비례해 늘어납니다.

### 관리 패널 관련 변수(P3, 기본값은 비활성화)

| 변수 | 필수 | 기본값 | 설명 |
|---|---|---|---|
| `ADMIN_TOKEN` | 아니오 | 없음(패널 비활성화) | 관리 엔드포인트의 토큰. **`GATEWAY_TOKEN`과 달라야 하며**, 최소 24자 이상이어야 합니다. 또한 **앞뒤에 공백이 있으면 안 됩니다**: HTTP는 헤더 값의 앞뒤 공백을 제거하지만 환경 변수는 그대로 유지하므로, 공백이 붙은 토큰은 어떤 클라이언트도 보낼 수 없습니다. 미설정이거나 규칙에 어긋나면 `/admin` 트리 전체가 등록되지 않으며, 이유는 `admin.token_rejected`로 기록됩니다. |
| `TRUST_PROXY` | 아니오 | 미설정(**어떤** 전달 헤더도 신뢰하지 않음) | 게이트웨이가 실제로 프록시 뒤에 있을 때**만** `1`로 설정하세요. **Cloudflare Worker 형태도 여기에 해당하므로 설정해야 합니다.** 설정하면 로그인 실패 이벤트에 기록되는 클라이언트 IP는 `CF-Connecting-IP`에서 오고, 없을 때만 `X-Forwarded-For`의 첫 구간으로 폴백합니다. |

**설정하지 않으면 관리 패널만 사용할 수 없을 뿐, 게이트웨이 전달은 정상 동작합니다.** 이때
`/admin/...` 요청은 **`401`이 아니라 `404`**를 받습니다. 트리 자체가 등록되지 않으므로 "여기에
관리 화면이 있다"는 사실조차 노출되지 않습니다. 레지스트라가 기본 비활성화인 것과 같은 원칙으로,
`ADMIN_TOKEN`이 없거나 잘못되었다고 해서 게이트웨이 전달이 멈춰서는 안 됩니다.

**24자 하한이 있는 이유.** Worker 형태에는 **분산 로그인 속도 제한이 없습니다.** 이를 구현하려면
KV를 카운트 윈도로 써야 하는데, 그것은 공격자에게 쓰기 할당량을 소진시킬 지렛대를 쥐여 주는 일이며
공격면이 "비밀번호 추측"에서 "키 풀 상태 기록 마비"까지 넓어집니다. 따라서 토큰 엔트로피가 유일한
방어선이고, 이 하한은 권고값이 아닙니다. 하한 미만이면 패널이 활성화되지 않고 컨테이너 로그에
`admin.token_rejected`가 남습니다.

**`GATEWAY_TOKEN`과 달라야 하는 이유.** `GATEWAY_TOKEN`은 **모든 다운스트림 사용자**에게 나눠 주는
중계 토큰입니다. 이를 패널 토큰으로 재사용하면, 중계 토큰을 가진 누구나 키 풀 전체를 읽고,
레지스트라를 끄고, 등록 백엔드를 자기 서버로 바꿀 수 있습니다. 그 이후 생성되는 모든 계정의
메일 주소·비밀번호·인증 코드가 그에게 넘어갑니다.

이 규칙은 **관리 요청마다 다시 검사할 뿐, 시작 시에는 막지 않습니다.** 둘이 같으면 — 예를 들어
`wrangler kv key put`이나 `store.json` 직접 편집으로 `gatewayToken`을 손으로 바꾼 경우 — 관리
엔드포인트는 **`503`을 반환**하고 error 수준으로 `admin.token_conflict`가 기록됩니다(시작 시점에
이미 충돌하고 있다면 시작 로그에도 같은 줄이 남아 원인을 바로 알 수 있습니다).
**게이트웨이 전달은 영향을 받지 않습니다.** 둘 중 하나를 되돌리면 관리 엔드포인트는 스스로
복구됩니다. 저장소의 `gatewayToken`을 되돌린 경우 설정 캐시가 다음에 갱신되는 시점에 적용되며
**재시작이 필요 없습니다**. `ADMIN_TOKEN` 쪽을 바꾸는 경우에는 환경 변수이므로 재배포(Worker)
또는 컨테이너 재생성(Docker)이 필요합니다.

**왜 이 규칙만 시작 시에 막지 않는가.** `gatewayToken`은 운영 중에 바뀔 수 있는데 시작 시점의
판정에는 두 번째 평가 기회가 없습니다. 거기서 `/admin` 트리 전체를 등록하지 않게 하면, 충돌
중에 콜드 스타트한 isolate(그리고 충돌 중에 기동한 Docker 컨테이너)는 **영구히 `404`**가 되어
설정을 되돌려도 낫지 않고 재시작밖에 방법이 없습니다. 반면 충돌 전에 만들어진 것들은 `503`에
그치고 값을 되돌리면 즉시 복구됩니다. 같은 설정, 같은 순간에 두 가지 답이 존재하게 되고, 위의
"재시작이 필요 없습니다"라는 문장이 반쯤 거짓이 됩니다. `ADMIN_TOKEN` 자체에 관한 두 규칙
(앞뒤 공백, 최소 길이)은 입력이 환경 변수뿐이라 운영 중에 바뀌지 않으므로 계속 시작 시에
막으며, 실패 형태도 `404` 그대로입니다.

`ADMIN_TOKEN`은 **환경 변수에서만 읽고 저장소에서는 읽지 않습니다.** 패널이 자기 키를 스스로
교체할 수 없습니다. 교체 방법은 Worker는 `npx wrangler secret put ADMIN_TOKEN` 후 재배포,
Docker는 `.env`를 수정하고 컨테이너를 다시 만드는 것입니다.

**`TRUST_PROXY`는 보안 스위치이므로 기본값이 꺼짐입니다.** 이 값이 결정하는 클라이언트 IP는
`admin.login_failed` 이벤트에 기록되므로, 클라이언트가 보낸 헤더를 무조건 신뢰하면 누구나 무차별 대입
흔적을 임의의 IP에 뒤집어씌울 수 있습니다.

**꺼진 상태에서는 어떤 전달 헤더도 신뢰하지 않으며 이 필드는 일률적으로 `null`로 기록됩니다 —
`CF-Connecting-IP`도 예외가 아닙니다.** 이 헤더는 흔히 "플랫폼이 주입하므로 위조할 수 없다"고
설명되지만, 그 성질은 **요청이 실제로 Cloudflare를 통과할 때만** 성립합니다. Node/Docker를 직접
노출한 구성에서는 이를 덮어쓰는 것이 아무것도 없으므로, 클라이언트가 스스로
`CF-Connecting-IP: 1.2.3.4`를 보내면 그대로 믿게 됩니다 — 그리고 직접 노출은 Docker 배포의 기본
형태입니다.

**켜진 상태에서는 `CF-Connecting-IP`가 우선이고 `X-Forwarded-For`는 폴백일 뿐입니다.** 두 헤더는
위조 가능성이 근본적으로 다릅니다.

- `CF-Connecting-IP`는 Cloudflare 엣지가 기록하며, 클라이언트가 보낸 동일 이름 헤더를 **덮어씁니다** —
  요청이 실제로 Cloudflare를 통과하는 한 위조할 수 없습니다.
- `X-Forwarded-For`는 어떤 중간 장비든 덧붙일 수 있는 체인이고 클라이언트가 가짜를 보낼 수도 있어,
  어디까지 믿을 수 있는지는 전적으로 프록시 구성에 달려 있습니다.

**Worker 형태에서는 `TRUST_PROXY=1`을 설정하세요.** 그곳에서는 Cloudflare가 정의상 앞단에 있으므로
`CF-Connecting-IP`가 권위 있는 값입니다. 이 형태에서 `X-Forwarded-For`를 우선하는 것은 잘못이며,
그 체인에는 클라이언트가 채워 넣은 값이 들어 있을 수 있습니다. 스위치를 설정하지 않으면 이 필드는
그냥 `null`로 기록됩니다.

**범용 리버스 프록시(nginx / Caddy / Traefik) 뒤에서 `TRUST_PROXY=1`을 켤 때는 프록시에서
`CF-Connecting-IP`를 제거하세요.** 그런 구성에서는 이 헤더를 덮어쓰는 것이 아무것도 없는데,
게이트웨이는 "Cloudflare가 앞단에 있다"는 전제로 이를 우선하므로 공격자가 직접 붙인 헤더가
프록시가 방금 쓴 `X-Forwarded-For`를 **이깁니다**. nginx는 한 줄이면 됩니다:

```nginx
proxy_set_header CF-Connecting-IP "";
```

Caddy는 `header_up CF-Connecting-IP ""`, Traefik은 미들웨어의 `customRequestHeaders`를 씁니다.

**두 헤더 모두 먼저 형태 검사를 거칩니다**: 점 표기 IPv4와 IPv6 형태(16진수, 콜론, `::ffff:`
매핑 안의 점)만 이벤트에 들어가고, 그 외에는 일률적으로 `null`로 기록됩니다. 이것은 인증
방어선이 아니며(이 값의 소비 지점은 저장소 전체에서 로그인 실패 이벤트 한 곳뿐입니다),
인증되지 않은 호출자가 감사 필드에 임의의 텍스트를 써 넣지 못하게 하려는 것입니다. 관리
패널의 이벤트 영역이 이 필드로 필터링하고 표시하기 때문입니다.

쓸 수 있는 값이 하나도 없으면 이 필드는 정직하게 `null`로 기록됩니다 — **`"unknown"` 같은 가짜 값은
절대 만들지 않습니다.** 실재하는 출처로 오해되기 때문입니다.

### 레지스트라 관련 변수(선택 사항, 기본값은 비활성화)

원리, 두 메일함 채널을 고르는 방법, Cloudflare Cron의 월클록 상한 등 전체 설명은
[REGISTRAR.md](REGISTRAR.md)를 참고하세요.

| 변수 | 필수 여부 | 기본값 | 설명 |
|---|---|---|---|

| `REGISTRAR_PRIMARY` | 활성화 시 필수 | 없음 | 주 채널, `yyds` 또는 `moemail`. 둘은 대등하며 기본값 없음. |

| `TEND_INTERVAL_MS` | 아니오(Node/Docker 전용) | `1800000` | Node 측 보충 간격. Worker 측은 `wrangler.toml`의 Cron이 대신 결정. |

### 두 가지 타임아웃 예산의 역할

기준은 "업스트림의 첫 바이트가 언제 도착할 수 있는가"이지 엔드포인트의 이름이
아닙니다:

| 예산 | 대상 엔드포인트 | 변수 |
|---|---|---|
| 첫 바이트 | **스트리밍** 대화(`stream: true`), 비디오 폴링 `GET /v1/videos/{id}` | `UPSTREAM_TIMEOUT_MS` |
| 동기 | 이미지 생성, 비디오 작업 생성, **모든 비스트리밍 대화**(네 프로토콜 모두) | `UPSTREAM_SYNC_TIMEOUT_MS` |

비스트리밍 요청은 업스트림이 답변 전체를 생성한 뒤에야 응답 헤더를 보냅니다. 이미지
생성과 완전히 같은 지연 특성이므로, 8초짜리 첫 바이트 예산으로 자르면 정상적인 요청이
대량으로 실패하고 key 풀까지 함께 망가집니다.

`UPSTREAM_SYNC_TIMEOUT_MS`는 **요청 한 건의 총예산**, 즉 클라이언트의 최악 대기 시간이며
"풀 크기 × 예산"이 아닙니다. 게이트웨이는 이 예산에서 key 하나에 최대 절반만 쓰고, 나머지는
다른 key로 재시도하는 데 남겨 둡니다. 그래야 풀에 멈춘 key(연결은 되지만 절대 응답하지
않는)가 있어도 요청 하나를 통째로 잡아먹지 않습니다. 따라서 **단일 호출의 최악 소요 시간의
2배 이상**으로 설정하세요.

동기 예산에서의 타임아웃은 즉시 key를 처벌하지 않습니다. 같은 요청 안에서 바꿔 쓴 다른
key가 실제로 성공했을 때에만 먼저 타임아웃된 key에 책임을 지웁니다(`MAX_STRIKES`에
도달하면 쿨다운). 그 요청에서 모든 key가 타임아웃했다면 하나도 처벌하지 않습니다 ——
예산이 너무 작거나 업스트림 전체가 느릴 가능성이 더 크기 때문입니다.

"제거"와 "쿨다운"은 다릅니다. 위 설정과 무관하게, 업스트림 `401`/`403`은 해당
key를 **영구** 제거합니다 —— 이는 "이 key는 더 이상 유효하지 않음" 상태이며
재시도가 무의미하기 때문입니다. 일시적 실패는 결코 제거로 이어지지 않습니다.
`MAX_STRIKES`에 도달해도 `COOLDOWN_STRIKE_MS` 쿨다운에 들어갈 뿐 스스로 복구되므로,
업스트림의 일시적 장애가 key 풀을 영구히 망가뜨리는 일은 없습니다.

어떤 key도 요청을 처리할 수 없을 때 게이트웨이는 `503`과 함께 판별 가능한
`error.reason`을 반환합니다: `pool_empty`(key 미등록), `all_cooling`(모든 key가
쿨다운 중 — 자동 복구되며 `Retry-After` 헤더가 복구 시점을 알려줌),
`all_evicted`(자격 증명 실효로 모든 key가 영구 제거됨 — **자동 복구되지 않으므로**
key 교체 필요), `upstream_error`(key 자체는 정상이나 업스트림이 매번 실패).

## Cloudflare Worker

### 방법 A —— Deploy to Cloudflare 버튼

루트 [README](../../README.md)에 있는 버튼을 클릭하고 Cloudflare를 인증하면
저장소를 fork/clone하고 배포까지 자동으로 진행됩니다. 이후에도 아래의
**secret**과 **KV 네임스페이스** 단계는 직접 완료해야 합니다 —— 버튼만으로는
이 두 가지가 설정되지 않습니다.

### 방법 B —— 수동 배포

1. 저장소를 클론하고 의존성을 설치합니다.

   ```bash
   git clone https://github.com/xwteam/agnes2api.git
   cd agnes2api
   pnpm install
   ```

2. key 풀을 위한 KV 네임스페이스를 만들고 `wrangler.toml`에 다시 씁니다.

   ```bash
   node scripts/setup-worker.mjs
   ```

   저장소의 `wrangler.toml`에 들어 있는 `id`는 항상 자리표시자입니다
   (공개 저장소에는 실제 배포 정보를 전혀 넣지 않습니다), 그래서 이 단계는
   필수입니다. 이 스크립트는 수동으로 `npx wrangler kv namespace create
   POOL`을 실행하고 반환된 `id`를 `[[kv_namespaces]]` 블록의
   `REPLACE_WITH_YOUR_KV_NAMESPACE_ID` 자리에 붙여넣는 것과 같은 일을
   합니다. **실행 후 이 `wrangler.toml` 변경 사항은 커밋하지 마세요**——
   `check-wrangler-placeholder.mjs` CI 게이트가 실수로 커밋된 실제 id를
   막습니다.

3. 게이트웨이 토큰을 Worker secret으로 설정합니다(`wrangler.toml`에
   절대 커밋하지 마세요).

   ```bash
   npx wrangler secret put GATEWAY_TOKEN
   ```

4. 배포합니다.

   ```bash
   npx wrangler deploy
   ```

### 태그 push 시 자동 배포

`.github/workflows/deploy-worker.yml`은 `v*` 태그가 push될 때마다 Worker를
자동으로 배포합니다. 단, 저장소의 **Settings → Secrets and variables →
Actions**에 `CLOUDFLARE_API_TOKEN`이 설정되어 있어야 합니다. 설정되어 있지
않으면 워크플로가 경고를 출력하고 배포 단계를 건너뛸 뿐, 전체 실행이
실패하지는 않습니다.

`GATEWAY_TOKEN`은 `wrangler.toml`과 같은 디렉터리에 있는 로컬 `.dev.vars`

## Docker

1. 저장소를 클론하고 환경 변수 파일을 준비합니다.

   ```bash
   git clone https://github.com/xwteam/agnes2api.git
   cd agnes2api
   cp .env.example .env
   ```

2. `.env`를 편집해 최소한 `GATEWAY_TOKEN`을 설정합니다. 나머지 변수는 위의
   [환경 변수](#환경-변수) 표를 참고하세요.

3. 컨테이너를 시작합니다.

   ```bash
   docker compose up -d
   ```

   `docker-compose.yml`은 기본적으로 `8080` 포트를 게시하며(`.env`의
   `PORT`로 재정의 가능), `./data`를 컨테이너 내부의 `/app/data`에
   마운트합니다 —— `store.json`(key 풀 및 영속화된 설정)이 여기에
   저장됩니다. 재시작/업그레이드 시에도 이 디렉터리를 반드시 유지하세요.
   임포트된 key 풀의 유일한 사본입니다.

4. 컨테이너가 정상적으로 기동했는지 확인합니다.

   ```bash
   curl http://localhost:8080/health
   ```

   이미지에는 `HEALTHCHECK`가 내장되어 있어 Docker가 이를 기준으로 컨테이너
   상태를 보고합니다. 데이터 디렉터리에 쓸 수 없으면 `/health`는 `status`가
   `degraded`인 `503`을 반환하고 컨테이너는 unhealthy로 표시됩니다. 구체적인 원인은
   컨테이너 로그를 확인하세요.

### 컨테이너가 `./data`의 소유자를 바꿉니다 (먼저 확인하세요)

컨테이너는 **root로 entrypoint에 진입**해 두 가지를 한 뒤 권한을 낮춥니다:

- `DATA_DIR`(기본 `/app/data`)의 소유자가 컨테이너 내 실행 사용자 `app`
  (**uid 100 / gid 101**)과 다를 때에만 그 디렉터리를 재귀적으로 `chown`합니다.
  소유자가 이미 일치하면 아무것도 바꾸지 않습니다.
- 그다음 `su-exec`로 권한을 낮추므로 **메인 프로세스(PID 1)는 root가 아니라 app**으로
  실행됩니다.

런타임에 해야 하는 이유는, 바인드 마운트에서는 호스트 디렉터리의 소유자가 이미지 빌드
시점의 `chown`을 덮어쓰기 때문입니다. 그러면 컨테이너 안의 app이 `store.json`에 쓸 수 없고,
이 실패는 조용합니다(모든 API가 `pool_empty`를 반환).

**부작용**: 바인드 마운트에서 바뀌는 것은 **호스트**의 파일입니다. `docker compose up -d`
이후 여러분의 `./data`와 그 안의 파일 소유자는 본인 uid에서 `100:101`로 바뀌며, 이후
호스트에서 읽고 쓰거나 백업하려면 `sudo`가 필요합니다. 원하지 않는다면 `--user`(또는
compose의 `user:`)로 비 root 실행을 지정하세요. 그러면 entrypoint는 chown을 전혀 하지
않으며, 데이터 디렉터리의 소유자와 쓰기 가능 여부는 직접 준비하게 됩니다.

같은 이유로 이미지에는 **`USER app`이 없습니다**. 기본 사용자는 root입니다
(`docker inspect --format '{{.Config.User}}' <image>`는 빈 값을 출력). 이는 Kubernetes에
영향을 줍니다: `runAsNonRoot: true`를 설정하고 `runAsUser`를 명시하지 않으면 kubelet이
컨테이너 기동을 거부합니다. 그런 배포에서는 `runAsUser: 100`, `runAsGroup: 101`(또는 원하는
uid)을 명시하고 볼륨 소유자를 직접 준비하세요 —— 비 root로 기동하면 entrypoint는
"chown 없이 그대로 실행" 분기를 탑니다.

안전 경계: `DATA_DIR`이 `/`나 최상위 시스템 디렉터리(`/etc`, `/usr` 등)로 설정되면
entrypoint는 그 위에서의 재귀 chown을 거부합니다(경고만 출력하고 기동은 계속). 컨테이너
파일 시스템 전체가 app 쓰기 가능해지는 것을 막기 위함입니다.

## 업스트림 Agnes key 임포트

현재 버전의 게이트웨이는 key를 풀에 추가하기 위한 HTTP 엔드포인트를 제공하지
않습니다. 저장소 백엔드에 직접 기록해야 합니다. 각 항목은 `key:<id>`를
키로 하는 JSON 객체이며, `<id>`는 풀 내에서 고유하기만 하면 어떤 문자열이든
가능합니다(게이트웨이가 스스로 레코드를 생성할 때는 key의 해시값에서
파생하지만, 읽을 때 이 값을 검증하지는 않으므로 수동 임포트 시에는 고유한
식별자면 무엇이든 사용할 수 있습니다).

```json
{
  "id": "1a2b3c4d5e6f7a8b",
  "key": "실제-agnes-api-key",
  "addedAt": 1735689600000,
  "lastUsedAt": null,
  "cooldownUntil": 0,
  "strikes": 0,
  "evicted": false,
  "evictedReason": null
}
```

### Docker

실행 중인 프로세스와의 쓰기 경합을 피하기 위해 먼저 컨테이너를 중지한 뒤,
호스트에서 `./data/store.json`을 편집해 `"key:1a2b3c4d5e6f7a8b"` 키
아래에 위와 같은 레코드를 추가하고, 다시 컨테이너를 시작합니다.

```bash
docker compose stop
# ./data/store.json 편집
docker compose start
```

`./data/store.json`이 아직 없다면, `key:<id>` 형식의 키를 갖는 단일 JSON
객체로 새로 만들면 됩니다.

### Cloudflare Worker

wrangler로 레코드를 `POOL` KV 네임스페이스에 직접 씁니다.

```bash
npx wrangler kv key put --binding=POOL "key:1a2b3c4d5e6f7a8b" \
  '{"id":"1a2b3c4d5e6f7a8b","key":"실제-agnes-api-key","addedAt":1735689600000,"lastUsedAt":null,"cooldownUntil":0,"strikes":0,"evicted":false,"evictedReason":null}' \
  --remote
```

`--remote`를 생략하면 프로덕션이 아니라 `wrangler dev`가 사용하는 로컬
네임스페이스에 기록됩니다.

게이트웨이는 풀의 id 목록을 `pool:index` 키에 보관하여 전달 요청마다 KV `list`를 쓰지 않게
합니다(무료 등급의 `list` 할당량은 하루 1,000회뿐이며 읽기·쓰기와는 별개의 할당량입니다).
**레코드를 손으로 써도 이 색인은 바뀌지 않습니다.** 따라서 새 key가 언제부터 쓰이는지는 그
시점의 풀 상태에 달려 있습니다:

- **풀이 비어 있을 때**: 색인이 "비어 있다"고 하고 실제로도 레코드를 하나도 읽지 못하면,
  게이트웨이는 `list` 스캔으로 한 번 폴백해 수동으로 가져온 레코드를 찾아 색인에 채웁니다.
  이 스캔에는 내장된 10분 백오프가 있으므로(위 "할당량 계산" 참조), 가시성 상한은
  **10분 이내 + `POOL_CACHE_TTL_MS` 한 번**입니다.
- **풀이 비어 있지 않을 때**: 전달 경로는 색인이 아는 레코드만 가져오므로, 색인이 모르는
  레코드는 **완전히 보이지 않습니다**(오류도 전혀 나지 않습니다). 다음 cron 대조가 색인을
  고칠 때까지(기본 30분이며 **트리거 시점에 공식적인 보장이 없습니다**, 아래 참조), 그리고
  그 뒤 최대 `POOL_CACHE_TTL_MS` 한 번을 더 기다려야 합니다.

**수동 가져오기를 즉시 반영하려면 레코드를 쓸 때 id도 함께 `pool:index`에 추가하세요:**

```bash
npx wrangler kv key get --binding=POOL "pool:index" --remote
# ids 배열에 새 id를 추가하고 값 전체를 다시 씁니다(v는 항상 1)
npx wrangler kv key put --binding=POOL "pool:index" \
  '{"v":1,"ids":["기존id","1a2b3c4d5e6f7a8b"]}' --remote
```

색인을 쓰고 나면 각 isolate는 최대 `POOL_CACHE_TTL_MS` 한 번 뒤에 이 key를 쓰기 시작합니다.

레지스트라를 쓰지 않더라도 `wrangler.toml`의 `[triggers]` 블록을 지우지 마십시오.
이 cron은 `pool:index`와 실제 `key:` 레코드를 대조해 고치는 유일한 경로이며,
`REGISTRAR_ENABLED` 값과 무관하게 실행됩니다.

**이 cron의 트리거 시점은 공식적으로 보장되지 않습니다.** Cloudflare는 Cron
Trigger가 `crons` 표현식대로 정확히 발동한다는 신뢰성을 문서화하지 않았습니다
(건너뛰지 않는다는 보장도, 지연 상한도 명시되어 있지 않습니다). 이는 할당량
계산에는 안전한 방향입니다 —— 대사(對帳) 트리거가 줄어들수록 실제 KV 읽기/쓰기
소비량은 예상보다 줄어들 뿐, 늘어나지 않습니다. 다만 **고아 레코드나 유령
색인 항목이 색인으로 회수되기까지 걸리는 시간은 보장되지 않습니다**. 최악의
경우 예상했던 "최대 30분"보다 더 오래 걸릴 수 있습니다. 그 대기 시간 동안
해당 key는 일시적으로 사용할 수 없을 뿐이며, 데이터가 손실되거나 손상되지는
않습니다.

## key 폐기하기

**레코드를 지우고, 그 id를 `pool:index`에서도 빼세요 — 두 단계 모두 해야 합니다.** 레코드만
지워도 오류는 나지 않지만(읽을 수 없는 레코드는 그냥 걸러집니다) id가 색인에 남아, 다음
대조가 잘라낼 때까지 갱신할 때마다 읽기 한 번을 헛되이 씁니다.

```bash
npx wrangler kv key delete --binding=POOL "key:1a2b3c4d5e6f7a8b" --remote
# ids 배열에서 해당 id를 빼고 값 전체를 다시 씁니다
npx wrangler kv key put --binding=POOL "pool:index" '{"v":1,"ids":["남은id"]}' --remote
```

Docker에서는 `./data/store.json`에서 `"key:<id>"` 항목을 지우고 `"pool:index"`의 `ids` 배열을
고치면 됩니다. 먼저 `docker compose stop`을 하는 것을 권합니다.

이미 예전 스냅숏을 읽어 둔 isolate / 프로세스는 최대 `POOL_CACHE_TTL_MS` 한 번 뒤에 이 key를
더는 고르지 않습니다. Worker에서는 여기에 KV 전파 창(약 60초)이 더 붙습니다. 삭제가 모든
colo에 보이기까지 그만큼 걸리기 때문입니다.

**그 창 동안에도 다시 기록되지는 않습니다**: 게이트웨이는 어떤 상태 변경이든 저장하기 전에
레코드가 아직 있는지 먼저 확인하고, 읽히지 않으면 그 쓰기를 버리며 자신의 스냅숏을 즉시
갱신합니다. 유일한 예외가 그 전파 창으로, 확인용 읽기가 KV 엣지 캐시에서 응답되면 그 colo는
레코드가 아직 있다고 판단합니다. Docker(파일 저장소)에는 이 캐시가 없어 그쪽은 정확합니다.
