# 배포 가이드

agnes2api는 동일한 코드베이스와 요청 처리 로직으로 만들어진 두 가지 배포
대상을 제공합니다. 여러분의 인프라에 맞는 쪽을 선택하면 됩니다. 두 방식의
차이는 저장소 백엔드뿐입니다. Worker는 Cloudflare KV 네임스페이스를, Docker는
마운트된 볼륨 위의 JSON 파일을 사용합니다.

## 환경 요구사항

두 형태는 사전 조건이 다릅니다. 선택한 쪽 열만 읽으면 되고, 양쪽을 다 갖출 필요는 없습니다.

| 항목 | Cloudflare Worker | Docker |
|------|-------------------|--------|
| 로컬 런타임 | Node.js 20+(`wrangler`와 빌드를 돌리는 용도) | 필요 없음 |
| 커맨드라인 | `npx wrangler`(`pnpm install`로 설치됨) | Docker Engine 24+ 와 `docker compose` |
| 플랫폼 | Cloudflare 계정 하나, 무료 등급이면 충분 | 컨테이너를 돌릴 수 있는 머신 한 대 |
| 업스트림 | Agnes API key 최소 한 개, 다음 절 참고 | Agnes API key 최소 한 개, 다음 절 참고 |

> [!TIP]
> Docker 쪽은 Docker가 깔린 머신 한 대면 됩니다. `cp .env.example .env` 다음에
> `docker compose up -d` 한 번으로 뜹니다.
> Worker 쪽은 서버가 필요 없지만, 본인 Cloudflare 계정에 KV 네임스페이스를 먼저 만들어야
> 합니다 —— 이 단계는 대체할 방법이 없습니다.

## Agnes 자격 증명 준비

게이트웨이는 key를 만들어내지 않습니다. 여러분이 이미 가진 한 개 또는 여러 개의 Agnes API
key로 요청을 나눠 보낼 뿐입니다. 얻는 경로는 두 가지이고 **둘은 대등**하며, 주/보조를 정해
두지 않았습니다.

### 직접 발급받기

Agnes 플랫폼에서 계정을 만들고 콘솔에서 API key를 하나 발급해 복사해 둡니다.
이 경로는 한 번에 한 개만 주지만, 게이트웨이를 일단 띄우고 네 가지 프로토콜이 통하는지
확인하는 단계에는 그걸로 충분합니다.

### 레지스트라에게 자동 보충 맡기기

이 저장소에는 선택 사항인 레지스트라가 들어 있어 `TARGET_KEYS`를 목표로 풀을 자동으로
보충합니다. **기본값은 꺼짐**입니다(`REGISTRAR_ENABLED`를 설정하지 않으면 꺼진 상태).
동작 원리, 두 메일함 채널 중 무엇을 고를지, Cloudflare Cron의 벽시계 상한은
[REGISTRAR.md](REGISTRAR.md)에 전부 적혀 있습니다.

> [!IMPORTANT]
> 어느 경로든 key는 KV / `store.json`에 **평문**으로 저장됩니다. 데이터 디렉터리와 KV
> 네임스페이스는 자격 증명으로 취급하세요.

## 어떤 형태를 선택할까

두 형태는 같은 코드베이스에서 만들어지며, 네 가지 프로토콜도 관리 패널도 레지스트라도
양쪽에 다 있습니다. 차이는 아래 항목뿐입니다.

| 항목 | Cloudflare Worker | Docker |
|------|-------------------|--------|
| 어디서 도는가 | 본인 Cloudflare 계정, 엣지 | 본인 서버 또는 로컬 머신 |
| 저장소 백엔드 | KV 네임스페이스(`POOL` 바인딩) | 마운트한 볼륨 위의 `store.json` |
| 서버 필요 여부 | 불필요 | 필요 |
| 할당량 제약 | 무료 등급 KV는 하루 100,000회 읽기·1,000회 쓰기 | 본인 머신의 제약만 |
| 정기 보충 | `wrangler.toml`의 Cron | `TEND_INTERVAL_MS` |
| 아주 긴 비스트리밍 요청 | 기댈 수 있는 벽시계 보장이 없음(아래 참고) | 본인이 설정한 예산만 |

**둘 사이에 주·보조는 없습니다**. 서버가 이미 있으면 Docker, 서버를 두고 싶지 않으면 Worker
입니다. 둘 다 돌려도 되지만, **같은 key를 공유하면서 상태를 따로 두지는 마세요** —— 쿨다운과
제외는 저장소에 기록되는데 두 저장소는 서로를 모르고, 같은 key가 두 번 판정됩니다.

## Cloudflare Worker 배포

### 사전 조건

> [!NOTE]
> **이 저장소는 Cloudflare 원클릭 배포 버튼을 제공하지 않습니다.** 여기서는 그 경로가
> 성립하지 않기 때문입니다: 저장소의 `wrangler.toml`에 있는 KV 네임스페이스 id는 항상
> 자리표시자이고(공개 저장소에는 실제 배포 정보를 두지 않습니다. CI에서는
> `scripts/check-wrangler-placeholder.mjs`가 지키고 있습니다), `GATEWAY_TOKEN`은 필수
> 민감 값이라 secret으로만 주입할 수 있습니다 —— 둘 중 하나라도 빠지면 기동되지 않습니다
> (`src/core/config.ts`가 읽지 못하면 곧바로 예외를 던집니다). 원클릭 흐름은 이 두 가지
> 어느 쪽도 대신해 주지 못하므로 아래 단계는 직접 한 번씩 진행해야 합니다. 명령만 보려면
> 같은 디렉터리 [README](README.md)의 `## ⚡ 빠른 배포` 절을 참고하세요. tag를 찍는
> 자동 배포는 뒤에서 다룹니다.

저장소를 클론하고 의존성을 설치합니다.

```bash
git clone https://github.com/xwteam/agnes2api.git
cd agnes2api
pnpm install
```

### 설정

1. key 풀을 위한 KV 네임스페이스를 만들고 `wrangler.toml`에 다시 씁니다.

   ```bash
   node scripts/setup-worker.mjs
   ```

   저장소의 `wrangler.toml`에 들어 있는 `id`는 항상 자리표시자입니다
   (공개 저장소에는 실제 배포 정보를 전혀 넣지 않습니다), 그래서 이 단계는
   필수입니다. 이 스크립트는 수동으로 `npx wrangler kv namespace create
   POOL`을 실행하고 반환된 `id`를 `[[kv_namespaces]]` 블록의
   `REPLACE_WITH_YOUR_KV_NAMESPACE_ID` 자리에 붙여넣는 것과 같은 일을
   합니다. **실행 후 이 `wrangler.toml` 변경 사항은 커밋하지 마세요**——
   `check-wrangler-placeholder.mjs` CI 게이트가 실수로 커밋된 실제 id를
   막습니다.

2. 게이트웨이 토큰을 Worker secret으로 설정합니다(`wrangler.toml`에
   절대 커밋하지 마세요).

   ```bash
   npx wrangler secret put GATEWAY_TOKEN
   ```

#### 로컬 개발

```bash
pnpm dev:worker   # Worker 형태: 패널 자원을 먼저 생성한 뒤 wrangler dev
pnpm dev:node     # Node 형태: 패널 자원을 생성하고 pnpm build 후 dist/entry/node.js 실행
```

⚠️ **둘 다 `node scripts/build-ui.mjs`로 시작하며, 이는 곁다리가 아닙니다**: 패널 자원은
생성물(`src/ui/assets.generated.ts`)입니다. `npx wrangler dev`만으로도 뜨지만 패널은 마지막으로
생성된 내용에 머뭅니다 —— `admin-ui/`를 고쳤는데 아무 변화가 없다면 대개 이것 때문입니다.

`GATEWAY_TOKEN`은 `wrangler.toml`과 같은 디렉터리에 있는 로컬 `.dev.vars`
파일(이미 `.gitignore`에 포함됨)에 작성하세요 —— 비밀 값을 `wrangler.toml`에
직접 쓰지 마세요.

⚠️ 이 파일은 `pnpm test:workers`가 무조건 workerd의 `env`로 읽어 들입니다
(`@cloudflare/vitest-pool-workers`가 wrangler를 호출할 때 `envFiles`를 넘기지 않습니다).
CI에는 이 파일이 없으므로 테스트 전에 `mv .dev.vars .dev.vars.off` 를 실행하세요.
이 파일이 **`env`에 바인딩 이름을 하나 더 들여오는 순간** 저장소의 어서션 한 칸이 즉시
빨간불이 됩니다——판정 기준은 키 이름 집합이므로, 빈 파일이거나 KV 바인딩과 같은 이름인
`POOL`만 적은 경우에는 빨간불이 되지 않습니다.

`GATEWAY_TOKEN`은 이 파일에 씁니다. 형식은 `.env`와 같습니다.

```env
# 필수: 클라이언트가 이 게이트웨이를 호출할 때 제시해야 하는 토큰.
# 로컬 개발에서는 아무 값이나 되지만, 운영에서 쓰는 값을 여기 붙여넣지는 마세요.
GATEWAY_TOKEN=local-dev-token-change-me

# 선택: 관리 패널 토큰. 설정하지 않으면 로컬에서도 패널이 열리지 않습니다.
# GATEWAY_TOKEN과 달라야 하고, 24자 이상이며 출력 가능한 ASCII만 씁니다.
ADMIN_TOKEN=local-dev-admin-token-change-me
```

### 배포

배포합니다.

```bash
npx wrangler deploy
```

#### 태그 push 시 자동 배포

`.github/workflows/deploy-worker.yml`은 `v*` 태그가 push될 때마다 Worker를
자동으로 배포합니다. 단, 저장소의 **Settings → Secrets and variables →
Actions**에 `CLOUDFLARE_API_TOKEN`이 설정되어 있어야 합니다. 설정되어 있지
않으면 워크플로가 경고를 출력하고 배포 단계를 건너뛸 뿐, 전체 실행이
실패하지는 않습니다.

### 검증

배포가 끝나면 wrangler가 `https://{name}.{sub}.workers.dev`를 출력합니다. 그 주소를 base URL로
삼아 헬스 체크를 한 번 돌립니다.

```bash
curl -s https://your-worker.your-subdomain.workers.dev/health
```

`200`이 오고 `status`가 `ok`면 뜬 것입니다. 세 개짜리 전체 검증 명령은 아래에 있습니다.

### 업데이트

```bash
git pull
pnpm install
npx wrangler deploy
```

KV 안의 key 풀과 설정은 **영향을 받지 않습니다**. 배포로 바뀌는 것은 코드이고 바인딩은 여전히
같은 네임스페이스를 가리킵니다. `wrangler.toml`은 로컬에서 수정된 상태이므로
(namespace id를 `setup-worker.mjs`가 써 넣었습니다) `git pull`이 거기서 충돌을 내면 로컬 id를
남기세요.

## Docker 배포

### 사전 조건

저장소를 클론하고 환경 변수 파일을 준비합니다.

```bash
git clone https://github.com/xwteam/agnes2api.git
cd agnes2api
cp .env.example .env
```

### 설정

`.env`를 편집해 최소한 `GATEWAY_TOKEN`을 설정합니다. 나머지 변수는 아래의
[환경 변수](#환경-변수) 표를 참고하세요.

`.env`의 최소 형태는 두 줄입니다. 나머지는 모두 기본값이 있으니 필요할 때 더하면 됩니다.

```env
# 필수: 클라이언트가 이 게이트웨이를 호출할 때 제시해야 하는 토큰. 다운스트림에 나눠 주는 값입니다.
GATEWAY_TOKEN=본인의 긴 랜덤 문자열로 교체

# 선택: Node 런타임의 리스닝 포트. Worker는 이 변수를 쓰지 않습니다.
# docker-compose.yml은 이 값을 호스트 쪽에 공개하는 포트로도 씁니다.
PORT=8080
```

#### 데이터 디렉터리와 소유자: 컨테이너가 `./data`를 바꿉니다 (먼저 확인하세요)

컨테이너는 **root로 entrypoint에 진입**해 두 가지를 한 뒤 권한을 낮춥니다:

- `DATA_DIR`(기본 `/app/data`)의 소유자가 컨테이너 내 실행 사용자 `app`
  (**uid 100 / gid 101**)과 다를 때에만 그 디렉터리를 재귀적으로 `chown`합니다.
  소유자가 이미 일치하면 아무것도 바꾸지 않습니다.
- 그다음 `su-exec`로 권한을 낮추므로 **메인 프로세스(PID 1)는 root가 아니라 app**으로
  실행됩니다.

런타임에 해야 하는 이유는, 바인드 마운트에서는 호스트 디렉터리의 소유자가 이미지 빌드
시점의 `chown`을 덮어쓰기 때문입니다. 그러면 컨테이너 안의 app이 `store.json`에 쓸 수 없고,
이 실패는 조용합니다(모든 API가 `pool_empty`를 반환).

**부작용**: 바인드 마운트에서 바뀌는 것은 **호스트**의 파일입니다. `docker compose up -d`
이후 여러분의 `./data`와 그 안의 파일 소유자는 본인 uid에서 `100:101`로 바뀌며, 이후
호스트에서 읽고 쓰거나 백업하려면 `sudo`가 필요합니다. 원하지 않는다면 `--user`(또는
compose의 `user:`)로 비 root 실행을 지정하세요. 그러면 entrypoint는 chown을 전혀 하지
않으며, 데이터 디렉터리의 소유자와 쓰기 가능 여부는 직접 준비하게 됩니다.

같은 이유로 이미지에는 **`USER app`이 없습니다**. 기본 사용자는 root입니다
(`docker inspect --format '{{.Config.User}}' <image>`는 빈 값을 출력). 이는 Kubernetes에
영향을 줍니다: `runAsNonRoot: true`를 설정하고 `runAsUser`를 명시하지 않으면 kubelet이
컨테이너 기동을 거부합니다. 그런 배포에서는 `runAsUser: 100`, `runAsGroup: 101`(또는 원하는
uid)을 명시하고 볼륨 소유자를 직접 준비하세요 —— 비 root로 기동하면 entrypoint는
"chown 없이 그대로 실행" 분기를 탑니다.

안전 경계: `DATA_DIR`이 `/`나 최상위 시스템 디렉터리(`/etc`, `/usr` 등)로 설정되면
entrypoint는 그 위에서의 재귀 chown을 거부합니다(경고만 출력하고 기동은 계속). 컨테이너
파일 시스템 전체가 app 쓰기 가능해지는 것을 막기 위함입니다.

### 배포

컨테이너를 시작합니다.

```bash
docker compose up -d
```

**첫 이미지가 배포되기 전**(또는 fork 이후)에는 이 명령이 로컬 빌드로 폴백합니다 ——
`docker-compose.yml` 의 `build:` 블록이 그 역할을 합니다.

`docker-compose.yml`은 기본적으로 `8080` 포트를 게시하며(`.env`의
`PORT`로 재정의 가능), `./data`를 컨테이너 내부의 `/app/data`에
마운트합니다 —— `store.json`(key 풀 및 영속화된 설정)이 여기에
저장됩니다. 재시작/업그레이드 시에도 이 디렉터리를 반드시 유지하세요.
임포트된 key 풀의 유일한 사본입니다.

### 검증

컨테이너가 정상적으로 기동했는지 확인합니다.

```bash
curl http://localhost:8080/health
```

이미지에는 `HEALTHCHECK`가 내장되어 있어 Docker가 이를 기준으로 컨테이너
상태를 보고합니다. 데이터 디렉터리에 쓸 수 없으면 `/health`는 `status`가
`degraded`인 `503`을 반환하고 컨테이너는 unhealthy로 표시됩니다. 구체적인 원인은
컨테이너 로그를 확인하세요.

### 업데이트

```bash
docker compose pull
docker compose up -d
```

`./data`는 그대로이고 key 풀과 설정이 거기 있습니다. **업그레이드 전에 그 디렉터리를 백업하세요**
(아래 "백업과 복구" 참고). 임포트한 key 풀의 유일한 사본이며, 두 번째 사본은 없습니다.

## 환경 변수

| 변수 | 필수 여부 | 기본값 | 설명 |

위 표의 모든 변수는 `.env.example`에 한 줄씩 들어 있습니다. `cp .env.example .env` 후
필요한 항목만 고치면 됩니다. 그 파일의 주석은 분량이 제각각이라(대부분 한 줄, 일부는
십수 줄) 값의 범위와 대가는 이 표를 기준으로 하세요. 위의 수치형 변수는 모두 정수여야 하며,
`POOL_CACHE_TTL_MS`와 `POOL_TOUCH_INTERVAL_MS`는 하한이 `0`("끔"을 의미)이고 나머지는
모두 `0`보다 커야 합니다. 그렇지 않으면 게이트웨이가 기동을 거부합니다.

`POOL_CACHE_TTL_MS`와 `POOL_TOUCH_INTERVAL_MS`는 **app을 만들 때 한 번만** 읽습니다.
변경하려면 컨테이너를 재시작하거나 isolate가 회수되기를 기다려야 하며, 다른 설정
항목처럼 요청마다 반영되지는 않습니다.

### `RESET_CONFIG`: 이 비상 탈출구를 언제 쓰나

> 저장된 설정이 망가져 게이트웨이가 기동하지 못할 때 복구용으로 쓰세요. 복구한 뒤에는 이 줄을
> 지워야 하며, 지우지 않으면 패널에서 저장한 설정이 영원히 적용되지 않습니다.

### `POOL_CACHE_TTL_MS`의 대가

> 다른 isolate가 판정한 쿨다운/제외가 이 isolate에 보이기까지 최대 **이 값 + 약 60초**가
> 걸림(60초는 KV 엣지 캐시의 기본 `cacheTtl`). 기본값 60000일 때 상한은 약 **120초**.

게다가 "늦게 보이는" 것만이 문제가 아님: 오래된 스냅숏 위에서 일어나는 스케줄링 관련 쓰기는
레코드 전체를 덮어써, 다른 isolate가 그 창 안에서 막 기록한 `evicted` / `cooldownUntil`을
**지워버림**——그 판정을 처음부터 다시 해야 함.

### `POOL_TOUCH_INTERVAL_MS`의 대가와 "카운터를 지우는 법"

요청마다 쓰면 무료 등급의 하루 1,000회 쓰기 할당량을 다 써버려 쿨다운과 제외조차 기록하지
못함. 대가: "마지막 사용"의 정밀도가 이 간격까지 거칠어짐. 같은 간격은 패널의 사용량
카운터(요청 수 / 성공률)에도 적용됨.

> [!WARNING]
> **스토리지의 `stats`를 손으로 줄이면(예: 0으로 초기화) 패널에 잠깐 그 값이 보였다가 다시 옛
> 값으로 되돌아갈 수 있음**: 스냅숏은 TTL이 지나면 초기화된 레코드를 읽지만, 실행 중인
> 인스턴스는 자신이 저장한 기준값을 기억하고 다음 실제 저장 때 그 값을 다시 씀. 늦어도 해당
> 인스턴스가 회수된 뒤에는 완전히 일치함.

**카운터를 지우려면 repo를 거치는 정식 경로를 쓸 것**: `PATCH /admin/api/keys/:id` 에
`clearStats`. 이는 **이번 요청을 처리한 인스턴스**가 들고 있던 저장 기준값과 아직 저장하지
않은 증분을 함께 버리므로, **이번 초기화 이후에 시작된 요청**이 옛 값을 다시 쓰는 일은 없음.
다만 **초기화 시점에 이미 진행 중이던 요청**은 초기화 전 레코드를 들고 있어, 완료될 때 그 옛
값으로 기준값을 다시 만듦. 동시에 돌고 있는 **다른** 인스턴스(다른 isolate, 또는 같은 볼륨을
쓰는 다른 컨테이너)도 각자 자기 기준값을 갖고 있어 옛 값을 한 번 되돌려 쓸 수 있음.
**오늘은 API만 있고 패널에는 이 버튼이 없음.**

### `USAGE_STATS_ENABLED`: 켜면 무엇을 치르나

"꺼짐"은 무비용입니다: 메모리 누적기를 만들지 않고 저장소 쓰기도 한 번도 일어나지 않습니다.
켜면 인스턴스당 하루 최대 13회 put(쓰기 할당량의 약 10.4%, isolate 8개면 하루 총 104회)이고,
소진하면 그날은 더 쓰지 않으며 다음 UTC 날짜에 회복합니다. 미기록 꼬리는 최대 2시간입니다.
자세한 내용은 아래 "할당량 계산"의 Tier-2 항목을 참고하세요.

### 할당량 계산: Worker + 무료 등급 KV로 하루 몇 건을 처리할 수 있나

무료 등급 KV는 하루 100,000회 읽기, 1,000회 쓰기입니다. 게이트웨이의 읽기와 쓰기는 모두
**요청 수에 비례해 늘어나지 않습니다**. 따라서 "요청당 몇 회"가 아니라 "하루에 몇 회"로 셉니다.

- **기본 설정에서는 KV가 더 이상 병목이 아니며**, 상한은 Cloudflare Workers 무료 등급 자체의
  **하루 100,000 요청**이 됩니다. 다만 이 결론에는 **전제가 있으며 무조건적이지 않습니다**:
  KV 읽기 할당량은 대신 "동시에 활성인 isolate 수"를 제약하는데, 이는 트래픽의 지리적 분포에
  따라 달라지는 값이라 직접 지정할 수 없습니다. 활성 isolate 하나가 하루에

      (86400 ÷ POOL_CACHE_TTL_MS 초) × (1 + 풀의 key 수)  +  2880

  회를 읽습니다. 끝의 2880은 설정 홀더가 30초마다 갱신하는 몫이며 같은 할당량을 씁니다.
  기본값에 key 20개면 isolate당 **33,120회**이고, 하루 48~96회의 인덱스 대조를 더하면
  **활성 isolate 3개로 약 99.4%를 소진**합니다. 즉 권장 설정에서 이미 임계점입니다.
  isolate가 더 많을 것으로 예상되면 `POOL_CACHE_TTL_MS`를 키우세요(key 20개에 isolate 5개면
  약 `120000`).
- **캐시를 끄면**(`POOL_CACHE_TTL_MS=0`, 비상 탈출구) 읽기가 요청 수에 비례해 늘어나며
  하한은 대략 `100,000 ÷ (1 + key 수)` ⇒ key 20개일 때 **하루 약 4,700 요청**입니다.
- **쓰기 쪽**: 정상 상태에서 하루 약 `key 수 × 4`회(`lastUsedAt`을 6시간마다 한 번 갱신).
  key 20개면 80회로 쓰기 할당량의 8%이고, 나머지는 쿨다운과 제외 기록에 쓰입니다. 여기에
  각 key가 처음 사용될 때 일회성 쓰기가 한 번 더 발생합니다.
- **이벤트 보드(Task 6)의 쓰기 쪽**: 각 isolate는 하루 최대 `EVENT_WRITES_PER_DAY`(**12**)회까지만
  저장합니다. 초과하면 `budgetExhausted`가 사실대로 보고되며, 조용히 버리거나 재시도하지
  않습니다. **이 게이트는 단일 isolate 내부에서만 작동**하며, 전체적으로 안전한지는
  "동시 isolate 수 × 이 값"이 여전히 할당량 안에 들어오는지에 달려 있습니다——하나의
  isolate는 다른 isolate가 할당량을 얼마나 썼는지 알 방법이 없습니다(CAS도, isolate 간
  조율도 없음). **동시 isolate 8개**로 추정하면(이 절의 다른 곳에서 쓰는 3개보다 더
  보수적인 값입니다: 트래픽이 적은 개인용 게이트웨이라도 Cloudflare 엣지는 전 세계에
  퍼져 있어 실제 동시 isolate 수를 완전히 제어할 수 없기 때문입니다): `12 × 8 = 96`회/일,
  쓰기 할당량의 **9.6%**. 위의 key 풀 쓰기 쪽(하루 80회, 8%)과 합치면 총 약 176회/일
  (**17.6%**)이며, 약 82%의 여유가 남습니다. **이 계산은 리뷰에서 실제 문제를 발견했기
  때문에 존재합니다**: 초기 버전은 시간 단위로 예산을 계산했고 각 isolate가 독립적으로
  시간당 최대 12회까지 세었기 때문에, isolate가 4개만 있어도 쓰기 할당량을 뚫을 수
  있었습니다(`4 × 12 × 24 = 1,152`, 1,000 초과). 수정 방법은 예산 창을 "시간 단위"에서
  "일 단위"로 바꾸고 이 계산을 여기에 적어 두는 것이었습니다. 같은 라운드에서 콜드
  스타트한 isolate의 첫 플러시가 스로틀링을 건너뛰던 허점도 막았습니다——예전에는
  isolate가 콜드 스타트할 때마다 무조건 쓰기가 한 번 발생했지만, 이제는 콜드 스타트 후
  첫 플러시도 다른 모든 플러시와 같은 최소 간격 게이트를 통과합니다.
- **레지스트라 쓰기 쪽(P3c Task 1에서 추가) —— 이 절 전체는 `registrar.enabled`가 참일
  때만 존재합니다.** 기본 배포(레지스트라는 꺼져 있음)에서 이 절이 추가하는 쓰기는
  **하루 0회**이며, "몇 번 줄어든다"가 아닙니다. 켜져 있으면 보충 한 바퀴마다 세 항목을
  지불하며, **전부 "보충 주기"라는 축 하나에 매달려 있습니다**(Worker는 `wrangler.toml`의
  Cron, 기본값 `*/30 * * * *` = 하루 48바퀴. Node는 `TEND_INTERVAL_MS`):
  - **보충 잠금**: 바퀴당 put 1회 + delete 1회. 이 항목은 이번 변경 이전부터 이미
    존재했지만, 이 계산에 적힌 적이 한 번도 없었습니다.
  - **보충 이벤트 저장**: 바퀴당 최대 put 1회. **쓸지 말지를 정하는 것은 "이번 바퀴의
    이벤트 버퍼가 비었는지"**이지 이벤트 이름이 아닙니다. 건강하고 **설정까지 건강한**
    한 바퀴는 이벤트를 하나도 내지 않으므로 0회입니다.
    ⚠️ **"건강하면 0"에는 전제가 있으며, 반드시 밝혀 둡니다**: `loadConfig`는
    `TEND_INTERVAL_MS`가 `MINT_BATCH × CODE_TIMEOUT_MS × 채널 수`
    (기본값 `5 × 120000 × 1 = 600000`, 즉 10분)보다 작으면 **매 바퀴마다** 설정 경고를
    한 건 냅니다. 그 설정에서는 **아무것도 주조하지 않은 바퀴도 매번 한 번 씁니다**.
  - **보충 이력(`tend:history`)**: 바퀴당 get 1회 + put 1회, **무조건**.
    단일 키, 팬아웃 없음.
  ⚠️ **이 세 항목을 `EVENT_WRITES_PER_DAY`(isolate당 하루 12회)로 이해하지 마세요.**
  그 게이트는 `fetch` 경로용이며 "isolate 하나가 많은 요청을 처리하므로 예산이 오래 사는
  인스턴스에서 반복 소비된다"라는 전제 위에 서 있습니다. 보충 경로에서는 매 바퀴가
  **완전히 새로운 isolate**(Worker의 `scheduled()`)일 가능성이 높고, 평생 한 번만 저장하며
  매번 새 예산을 들고 옵니다 ⇒ **이 축에서 그 게이트는 아무것도 막지 못하고 상한도 되지
  않습니다**. 진짜 상한은 보충 주기 자체입니다: **Cron을 촘촘히 하거나 `TEND_INTERVAL_MS`를
  줄이면 이 세 항목이 그만큼 늘어납니다.**
#### 패널 쓰기 작업의 단가 —— "사람이 클릭할 때만 발생"

- **패널 쓰기 작업의 쓰기 쪽(P3c에서 추가) —— "사람이 클릭할 때만 발생"하므로 위의 정상
  상태 계산에는 들어가지 않습니다.** 빈도 상한을 말할 수 없습니다(상한은 운영자의 손입니다).
  그래서 여기서는 **작업별 단가**를 적습니다. 아래 숫자는 모두 실측값이며 **한 칸씩
  세었습니다**: key 쓰기 작업은 `tests/contract/admin-keys-write.test.ts`, "지금 보충"은
  `tests/contract/manual-tend.test.ts`, 설정 페이지의 두 엔드포인트는
  `tests/contract/admin-config.test.ts`에 있습니다.
  (이 문장은 원래 첫 번째 파일만 지목했지만 "지금 보충" 줄은 그 파일과 아무 관계가 없고
  당시에는 그것을 센 칸이 하나도 없었습니다 —— 전체 브랜치 리뷰 I4. 고치는 방법은 그 칸을
  채우는 것이지 이 문장을 무르게 만드는 것이 아닙니다.)
  - **새 key M개 가져오기**: put `M + 1`회(레코드 M개 + 인덱스 1회), get `M + 1`회, **list 0회**.
    한 번에 최대 200개(넘으면 400, **조용히 잘라내지 않습니다**) ⇒ 한 번 클릭의 상한은
    **put 201회**, 즉 하루 쓰기 할당량의 20%입니다. 여러 번에 나눠도 싸지지 않습니다
    (인덱스 1회는 배치마다 냅니다).
  - **중복 가져오기**(같은 key를 다시 붙여넣고 "기존 key 상태 초기화"를 체크하지 않음):
    **put 0회**. 중복은 기본적으로 건너뛰고 덮어쓰지 않으므로 목록 전체를 다시 붙여넣어도
    싸고 안전합니다.
  - "기존 key 상태 초기화"를 체크한 경우: **이미 풀에 있는** key 하나당 put 1회.
  - **key 하나 수정**(중지 / 재개 / 메모 / 쿨다운 해제 / strikes 초기화 / 제외 해제 /
    사용량 카운터 초기화): get 1회 + put 1회. **위 동작은 모두 단가가 같음**: 같은 handler,
    같은 한 번의 저장을 지나가며, 사용량 카운터 초기화는 추가로 읽거나 쓰는 것이 없음
    (지우는 대상은 메모리에 있는 저장 기준값).
    ⚠️ **괄호 안 마지막 항목은 이 절에서 유일하게 "패널에서 누를 수 없는" 것임**:
    사용량 카운터 초기화는 **오늘 API만 있고 패널에는 이 버튼이 없음**
    (위 `POOL_TOUCH_INTERVAL_MS` 칸과 동일). 이 열거는 그 handler가 이해하는 동작 전부이고
    패널 버튼 목록이 아님. 여기에 적어 둔 이유는 단가가 나머지와 완전히 같기 때문이며,
    다른 경로가 더 비싸다고 오해하지 않게 하기 위해서임.
  - **key 하나 삭제**: get 2회 + put 1회(인덱스) + delete 1회.
  - **N개 일괄 중지 / 일괄 쿨다운 해제**: get N회 + put N회.
  - **N개 일괄 삭제**: get `N + 1`회 + put **1**회(인덱스는 한 번만 씀) + delete N회.
  - **"지금 보충"을 한 번 누름**: 고정 put **3회**(가드 키 + 잠금 획득 + 보충 이력)
    + delete 1회(잠금 해제, 다른 버킷) 및 **실제로 발급된 key 1개당 put 2회**
    (레코드 + 인덱스). 이것은 **하루 상한이 있는 유일한 패널 동작**으로, 하루 최대
    **24**회입니다(네 번째 가드레일, [REGISTRAR.md](REGISTRAR.md) 참고) ⇒ 지속 가능한 값은
    `24 × 3 = 72`회/일이며, 아래 세 번째 행의 320에 더하면 **392회/일(39.2%)**입니다.
    매번 기본값 `MINT_BATCH = 5`를 채워 발급하는 경우의 상한은 `24 × 13 = 312` ⇒
    **632회/일(63.2%)**이지만, 그 행은 임시 메일함 한도와 `TARGET_KEYS`가 먼저 한계에
    부딪히므로 지속되지 않습니다. **이 게이트를 넣는 이유는 "쿼터를 뚫기 때문"이 아니라
    "여유가 없기 때문"입니다**: 10분 쿨다운만 있으면 상한이 `24 × 6 = 144`회/일 = put
    432회이고, 320에 더하면 이미 75%입니다. 게다가 그 320 중 96은
    `12 × 동시 isolate 수`이며 **직접 조정할 수도 없습니다**.
  - **설정을 한 번 저장**(`PUT /admin/api/config`): **put 1회** + get 3~4회
    (쓰기 전에 `readAll` 1회 + 원본 읽기 1회, 쓴 뒤 `readAll`로 1회 되읽기. 바로 이어서 다시
    저장하면 직전의 `invalidate()` 때문에 설정 갱신 미들웨어가 1회 더 읽고, 진단 상태 분기도
    마찬가지로 1회 늘어납니다).
    **검증에 실패한 요청은 put 0회 + get 2~3회** —— 1바이트도 쓰지 않습니다
    (저장 직후에는 마찬가지로 1회 더 읽습니다. 위와 같은 이유입니다).
  - **자격 증명 하나 비우기**(`POST /admin/api/config/secrets/clear`): **put 1회** + get 2회.
    `gatewayToken`을 비우는 분기(비운 뒤에는 이 설정을 불러올 수 없음)는 get 3회입니다.
  - **드라이런 검증**(`POST /admin/api/config/validate`): **put 0회** + get 1회.
  - **설정 초기화**(`/admin/api/config/reset`, 설정 페이지 위험 구역의 첫 번째 버튼):
    **put 1회** + get 2회(쓰기 전에 한 번, 쓴 뒤에 다시 한 번 읽어 옵니다).
    저장소의 설정 항목 하나를 통째로 비우며, **쓰는 곳은 put 버킷이지 delete 버킷이
    아닙니다** — 키를 지우는 대신 빈 값을 쓰는 것은 KV 삭제 툼스톤 계열 문제를 피하기
    위해서입니다.
  - **Key 풀 비우기**(`/admin/api/keys/purge`, 위험 구역의 두 번째 버튼):
    **delete N회(N = 풀 크기) + put 1회**(색인은 딱 한 번만 쓰며, 일괄 삭제와 같은
    판단입니다).
    ⚠️ **무료 등급의 delete 버킷은 하루 1,000회**(읽기·쓰기·list와 각각 별개)이므로
    **N이 1,000에 가까워지면 이 버튼 하나가 그날의 삭제 할당량을 다 써 버립니다**.
    풀이 클수록 비싸집니다. 읽기 쪽은 풀 스냅숏 한 번(isolate 캐시에 맞으면 get 0회)과
    읽어 오기 한 번이며, 빈 풀에서 다시 누르면 delete 0회·put 0회입니다.
  ⚠️⚠️ **위의 "설정을 한 번 저장"과 "자격 증명 하나 비우기"에는 하루 상한이 없습니다.
  빠뜨린 것이 아니라 의도한 것입니다.** 둘 다 관리자 토큰이 필요하고 사람이 직접 클릭할 때만
  발생하며, 어떤 자동 경로도 이를 촉발할 수 없습니다. 여기에 스토리지 가드레일을 붙이는 것
  자체가 read-modify-write(가드 키)를 한 번 더 만드는 일 —— 쓰기 한 번을 아끼려고 먼저 한 번
  더 내는 셈입니다. **침묵 때문에 어떤 예산이 이들을 관리한다고 오해하지 않도록 대가를 명시
  합니다**: 한 번의 튜닝 작업에서 수십 번 저장하는 것은 지극히 정상적인 운영이며, 수십 번의
  put은 하루 쓰기 할당량의 몇 퍼센트입니다. 그리고 "지금 보충"의 하루 24회 게이트는
  **이 두 가지에는 적용되지 않습니다**. 여유를 계획할 때 이 점을 감안하세요.
  ⚠️ 이 항목들은 아래 세 열과 **더하지 않습니다**: 세 열은 "아무도 건드리지 않을 때 하루 몇 번",
  이 절은 "클릭 한 번에 얼마"입니다. 신경 쓸 형태는 하나뿐입니다 ——
  **한 번에 수백 개의 key를 가져오는 것**. 패널에서 가장 비싼 단일 클릭입니다.

#### 쓰기 쪽 합계: `registrar.enabled`를 축으로 세 열

- **쓰기 쪽 합계, `registrar.enabled`를 축으로 세 열**(key 20개, 동시 isolate 8개 기준):

  | 시나리오 | put/일 | 쓰기 할당량 대비 비율 |
  |--------|------|---------------------|
  | **레지스트라 꺼짐(기본값)**, 아무도 조작하지 않음 | **176** | **17.6%** |
  | 레지스트라 켜짐, **매 바퀴가 건강함**, 아무도 조작하지 않음 | **272** | **27.2%** |
  | 레지스트라 켜짐, **매 바퀴가 실패 이벤트를 냄**, 아무도 조작하지 않음 | **320** | **32.0%** |

  ⚠️ **이 세 숫자는 모두 상한이 아니라 "현재 값"입니다.** 하루 96회 항목은
  `12 × 동시 isolate 수`와 같고, 그 수는 트래픽의 지리적 분포에 따라 변하며
  **당신 스스로도 설정할 수 없습니다**. 여유를 계획할 때 이 점을 따르고, 272나 320을
  천장으로 여기지 마세요.
  **`delete` 버킷**은 따로 계산합니다: 보충 잠금이 하루 48회 해제하지만, 그 버킷은 오늘
  거의 비어 있습니다.

  ⚠️ **이 세 항목은 모두 바퀴 단위로 과금되며, "하루 몇 바퀴인가"에는 서로 무관한 축이
  두 개 있습니다. 섞어서 읽지 마세요:**
  - **주기 축**: 보충 주기를 촘촘히 하면 세 항목이 **비례해서 늘어납니다**(위 문장이 그것입니다).
    **Worker 형태에서 조절하는 것은 `wrangler.toml`의 Cron**이고, Node 형태에서는
    `TEND_INTERVAL_MS`입니다. `TEND_INTERVAL_MS`는 **Node 스케줄러만 소비합니다**
    ——Worker에서 이 값을 바꿔도 **한 바퀴도 늘지 않습니다**. 반대로
    `registrar_tend_lock`의 put/delete 쌍은 **두 런타임 모두에 존재합니다**
    (P3c Task 5부터 Node 쪽도 같은 잠금을 잡습니다 — 여러 컨테이너가 하나의 볼륨을
    공유하는 구성에서는 프로세스 내부의 불리언이 무용지물이기 때문입니다).
  - **임계 축**: `TEND_INTERVAL_MS`가 `MINT_BATCH × CODE_TIMEOUT_MS × 채널 수` 아래로
    떨어지면 이벤트 항목이 **"건강한 바퀴 0회"에서 "매 바퀴 1회"로 뜁니다**. 이 도약은
    주기와 무관하며, 위에서 말한 매 바퀴 나오는 설정 경고가 원인입니다.
  **가장 나쁜 것은 두 축이 겹칠 때입니다.** 이 절은 Worker + 무료 등급 KV 이야기이므로,
  **그 형태에서 완전히 합법적인** 예를 듭니다: Cron을 `*/5 * * * *`로 바꾸면 ⇒ 하루 288바퀴,
  게다가 매 바퀴 이벤트가 나옴 ⇒ `80 + 96 + 288 + 288 + 288 = 1,040`회/일로,
  **이미 쓰기 할당량을 넘습니다**.
  위의 세 행은 모두 기본 Cron(30분에 한 바퀴)을 전제로 합니다. **주기와 무관한 상수로 읽지
  마세요.**

#### Tier-2 사용량 통계의 쓰기 측(기본값은 꺼짐)

- **Tier-2 사용량 통계의 쓰기 측(P3d에서 신규, `USAGE_STATS_ENABLED`, **기본값은 꺼짐**)
  —— 이번 단계에서 유일한 새 기록자입니다.**

  **꺼져 있는 동안 이 항목의 쓰기는 항상 0**입니다. 메모리 누적기도 만들지 않고
  `storage.put`도 한 번도 일어나지 않습니다. 이것은 "겸사겸사 아끼는" 수준이 아닙니다.
  위 key 풀의 하루 80회와 **같은** 하루 1,000회 쓰기 버킷을 두고 경쟁하며, 통계가 쓰기
  할당량을 먹어치우면 key 풀의 쿨다운과 제외 기록까지 함께 죽습니다.

  켠 뒤에는: **인스턴스당 하루 최대 13회 put**. 동시 isolate 8개로 추산하면
  `13 × 8` = **104**회/일이고, 쓰기 할당량의 약 10.4%입니다. 네 가지 시나리오의 합계:

  | 시나리오 | put/일 | 쓰기 할당량에서 차지하는 비율 |
  |--------|------|-----------------------------|
  | **Tier-2 꺼짐(기본값)**, 레지스트라도 꺼짐 | **176** | 17.6% |
  | Tier-2 켜짐, 레지스트라는 꺼짐 | **280** | 28.0% |
  | Tier-2 켜짐, 레지스트라도 켜져 있고 매 바퀴가 실패 이벤트를 냄 | **424** | 42.4% |
  | 위 행 + 하루 24회 게이트를 다 쓸 때까지 "지금 보충"을 누름 | **496** | 49.6% |

  ⚠️ **위의 세 열과 마찬가지로 이 표도 상한이 아닙니다.** 올바른 읽는 법은 이렇습니다:
  **이 표에서 하드 게이트가 있는 항목은 두 개**입니다 —— Tier-2의 104(인스턴스당 하루
  13회 put, 아래 ③)와 "지금 보충"의 72(하루 24회, 위의 "'지금 보충'을 한 번 누름" 항목).
  나머지 항목에는 게이트가 없으며, 얼마나 쓰는지는 운영하는 사람의 손에 달려 있습니다.
  마지막 행은 **새 key를 발급하지 않는** 전제(한 번에 put 3회 고정)입니다. 매번 발급하면
  더 비싸지만, 그 열은 임시 메일함 한도에 먼저 부딪혀 지속되지 않습니다 —— 계산식은
  같은 항목에 있습니다.

이 13회의 내역은 다음 여섯 가지이며, 여섯 가지 모두 읽어야 합니다.

① **12회 기록 + 1**. 기록 최소 간격이 **2시간**이라 하루에 들어가는 것은 최대 12회입니다.
   그 `+1`은 여유가 아니라 **UTC 자정을 넘는 기록이 키를 두 개 쓴다**는 사실입니다
   (전날 것 하나, 당일 것 하나). 12로 하면 24시간마다 정확히 한 번 쓰기가 예산에
   거부됩니다 —— 데이터는 사라지지 않지만(그날은 미기록 표시가 남아 다음 바퀴에
   따라옵니다), ②의 "최대 2시간"이라는 약속이 4시간이 됩니다.

② **미기록 꼬리는 최대 2시간이고, 그 두 가지 증상은 하나의 사실이지 둘이 아닙니다**:
   패널의 "오늘" 숫자가 최대 2시간 오래될 수 있다는 것과, **2시간을 채우지 못하는
   인스턴스**(수명이 짧은 Worker isolate, 빠른 Docker 재시작)가 **모아둔 카운트와 함께
   사라진다**는 것입니다. 시간은 인스턴스가 시작된 순간부터 재므로, 10분만 살아 있던
   isolate는 한 글자도 저장하지 못합니다. 이것은 사용량 숫자에 내내 "≈"가 붙는 이유
   중 하나이며 결함이 아닙니다.

③ **인스턴스당 하루 13회 put은 하드 게이트입니다**: 소진하면 그날은 더 쓰지 않고,
   **다음 UTC 날짜에 자동으로 회복**하며, 밀렸던 날들은 회복 후에 기록됩니다
   (메모리의 누적기는 비우지 않습니다) —— **그 인스턴스가 살아 있다는 전제에서만**
   그렇습니다.
   ⚠️ **이 반쪽 문장은 Worker 형태에서는 구조적으로 도달하지 못합니다**: 누적기는 메모리
   안에만 있고, Worker의 isolate는 보통 다음 UTC 날짜까지 살아남지 못합니다(위 ②와 같은
   이야기입니다: 10분만 살았던 isolate는 한 글자도 저장하지 못합니다). 즉 Worker에서
   "회복 후에 기록된다"가 성립하려면 **같은 isolate가 UTC 자정을 넘겨야** 하고, 그것은
   상례가 아니라 예외입니다. 넘기지 못하면 그 며칠치 카운트는 **인스턴스와 함께
   사라집니다 —— 늦게 반영되는 것이 아닙니다**.
   ⚠️⚠️ **Docker 형태에서는 이 게이트 자체가 없으므로** 이 약속은 그쪽에 아예 해당하지
   않습니다: 하루 쓰기 예산이 있는지는 **저장소에 쓰기 할당량이 있는지**로만 정해지며
   (판정 기준은 아래 ④), 파일 저장소에는 없습니다 ⇒ 예산은 비어 있고
   (`budgetPerDay = null`) 소진될 일도, 따라서 "회복"이나 "밀린 몫 기록"도 없습니다.
   **"Docker면 13회 게이트에 부딪혀도 데이터가 사라지지 않는다"로 읽지 마세요 ——
   Docker에는 그 게이트가 없습니다**. 그쪽에서 잃는 것은 위 ②의 꼬리(프로세스가 멈출 때
   아직 기록되지 않은 최대 2시간)입니다.
   ⚠️ 이 게이트는 **단일 인스턴스 내부에서만 유효**합니다 —— isolate가 8개면 13회짜리
   한도가 8개 각각 독립적으로 존재합니다. 위 이벤트 게이트와 완전히 같은 방식이며
   인스턴스 간 조율은 없습니다.

④ **두 런타임의 동작은 완전히 동일하며, 런타임 감지는 하지 않습니다.** 기록 간격의
   **기본값**은 양쪽 모두 같은 값, 같은 코드 경로입니다(요청 마무리에서 **쓰기 완료를
   동기적으로 기다립니다**. 백그라운드 작업이 아닙니다 —— Workers에서는 응답이 돌아간 뒤
   isolate가 멈추면서 백그라운드 작업이 조용히 잘립니다).
   `USAGE_FLUSH_INTERVAL_MS`로 덮어쓸 수 있지만, **판단 기준은 "당신의 저장소에 쓰기
   할당량이 있는가"이지 "어느 런타임에서 도는가"가 아닙니다**:
   · **파일 저장소(Docker)에는 쓰기 할당량이 없음** ⇒ 임의의 양의 정수를 받아들이고,
     **하루 쓰기 예산도 없어집니다**. 상한은 간격 그 자체입니다.
     300000(5분)으로 되돌리는 것은 충분히 합리적입니다.
   · **KV(Workers)에는 쓰기 할당량이 있음** ⇒ 예산은 인스턴스당 하루 13회 그대로이고,
     간격은 `간격 × (13 − 1) >= 하루`를 만족해야 합니다. 어기면 **시작할 때 오류**가 나며
     사용 가능한 최소값(7200000)을 알려줍니다. 조용히 받아들이지 않는 것은 의도적입니다:
     그런 값에서도 쓰기량은 기준 안으로 보이지만 **데이터는 점심때부터 거짓이 됩니다**.
     시작이 안 되는 것보다 알아차리기 어렵습니다.

⑤ **같은 날짜에 대해 남는 것은 최대 2개 인스턴스 분이고, 그것을 넘으면 서로 덮어씁니다.**
   사용량 샤드는 `usage:<UTC 날짜>:<슬롯>`으로 저장되며 **슬롯은 2개뿐**이고, 각 인스턴스는
   자기 샤드 id로 안정적으로 배정됩니다. ⇒ 위에서 isolate 8개로 계산한 하루 104회는
   **쓰기량**이지 "8개분 데이터가 모두 남았다"가 아닙니다. 같은 슬롯에서는 나중에 쓴 쪽이
   이깁니다. **이것도 사용량 숫자에 "≈"가 붙는 이유 중 하나입니다**(다른 하나는 ②의 꼬리).
   쓰기 할당량에는 영향이 없고 숫자의 완전성에만 영향을 줍니다. "≈"가 뜻하는 것이 이것입니다.

⑥ **미디어 세 엔드포인트(이미지 생성, 비디오 생성, 비디오 조회)는 집계에 들어가지 않습니다.**
   네 개의 대화 프로토콜과 **같은 상류 key를 소모**하지만 기록하지 않으므로, 패널의
   "총 요청 수"는 실제 전달량보다 체계적으로 작습니다. 이번 단계의 알려진 경계이지
   결함이 아닙니다. key 소모량은 key 풀 쪽 숫자로 판단하세요.

</details>

#### 읽기 쪽의 세 가지 개별 계정

- **Tier-2 사용량의 읽기 쪽 —— 여기서 소모되는 것은 하루 읽기 할당량이 아니라 "호출 한 번이
  하위 요청을 몇 개까지 낼 수 있는가"입니다.** `/admin/api/usage`의 `30d` 구간은
  **요청 한 번에 `USAGE_DAY_RETAIN × USAGE_SLOTS` = `30 × 2` = 60회의 KV get**을
  발행합니다(`src/core/admin/usage-stats.ts`). 하루 100,000회 읽기 할당량에 견주면 이 60회는
  무시할 수 있습니다. **플랫폼 보장이 없는 쪽은 호출 한 번당 하위 요청 개수입니다**:
  Cloudflare의 Workers limits 문서는 이를 두 줄로 나눕니다 —— "Subrequests per invocation"은
  무료 요금제 **50**, "Subrequests to internal services"는 무료 요금제 **1,000**. 그런데 그
  문서는 internal services가 무엇인지 끝까지 정의하지 않고, KV 바인딩 호출이 어느 줄에
  해당하는지도 밝히지 않습니다. 반면 KV 자체의 limits 문서에는
  "Operations/Worker invocation" **1,000**(무료와 유료가 동일)이라고 따로 적혀 있습니다.
  **두 문서가 서로 어긋나며, 저희도 실제 기기에서 결론을 내지 않았습니다** ⇒ KV 문서로 읽으면
  60회는 6%이고, 50 줄로 읽으면 **60은 초과**입니다. 따라서 `30d` 구간은 Worker에서 Node와
  다르게 동작할 수 있으며, 이 게이트웨이가 보장하는 것은 **정직하게 실패하는 것**뿐입니다:
  읽기 팬아웃이 도중에 실패하면 **`days` 전체가 `null`로 돌아오고**(패널은 `—`로 표시),
  `note`는 `read_failed`가 됩니다. 500을 반환하지도, 이미 읽어 온 샤드를 전체인 양
  내놓지도 않습니다.
  ⚠️ **아래 이벤트 보드의 48회 콜드 리드를 근거로 삼지 마세요** —— 48은 위 두 해석 모두에서
  적법하므로 "60이 괜찮은가"에 대해서는 한마디도 하지 않습니다. 무료 요금제에서 이 구간을
  마음 놓고 쓰려면 먼저 실제 기기에서 측정해야 합니다.
- **Playground의 비디오: 한 작업당 최대 `1 + 60`회의 상류 요청**(생성 1회 + 최대 60회 폴링,
  `VIDEO_POLL_MAX_ATTEMPTS`). ⚠️ **이 61배가 키우는 것은 상류 쪽 할당량과 key 사용 횟수뿐이며,
  KV의 하루 쓰기 할당량은 키우지 않습니다**: `lastUsedAt`과 사용량 카운터는
  `POOL_TOUCH_INTERVAL_MS`(기본 6시간)라는 쓰기 억제 게이트가 지키고 있어 폴링 한 바퀴로는
  기록 간격을 채우지 못합니다. 쿨다운과 제외 두 가지는 여전히 실패 횟수로 셉니다.
  **이 둘을 섞어 읽지 마세요** —— 먼저 소진되는 것은 상류 쪽이지 KV가 아닙니다.

- **이벤트 보드의 읽기 쪽(평가 C4/C4b 수정 후 실제 수치, 이전 초안보다 보수적)**: 폴링은
  더 이상 인덱스에 의존하지 않으므로 후보 키 수가 **엄격히 유계(bounded)**입니다——`after`가
  아무리 오래됐든, 배포가 며칠을 실행됐든, 요청 한 번이 스캔하는 것은 최대 24개의 시간
  윈도우 × 2개의 슬롯 = **48**회의 get입니다(평가 C4 수정 전에는 오래되었거나 악의적인
  `after` 값이 요청 한 번을 약 100만 회의 get까지 밀어붙일 수 있었습니다.
  `tests/contract/quota-panel.test.ts`의 회귀 테스트 참고). `after`가 최근 시간 윈도우
  내에 있으면 "웜 읽기"로, 보통 2회의 get만 필요합니다(폴링이 시간 윈도우 경계를 넘는
  순간에만 4회).
  **"유계"가 "활동 수준과 무관"을 의미하지는 않습니다**——평가 C4b가 지적한 직관에
  반하는 결론은 다음과 같습니다:
  - **새 이벤트가 꾸준히 발생하는 "활성" 배포**: 새 이벤트가 폴링 간격을 계속 최소값인
    15초로 되돌리고, 대부분의 폴링이 웜 읽기에 해당합니다. 매번 4회/폴링이라는 최악의
    경우로 계산하면: `(86400 ÷ 15) × 4 = 23,040`회/일(읽기 할당량의 약 23%; 실제로는
    윈도우 경계를 넘는 폴링이 일부에 불과하므로 보통 이보다 훨씬 낮습니다).
  - **오랫동안 새 이벤트가 없는 "조용한" 배포**(방금 배포되어 아직 진단 이벤트가 한 번도
    발생하지 않은 경우 포함): `after` 커서가 새 값을 받지 못한 채로 멈춰 있다가, 그
    고정된 커서가 24시간 보존 윈도우를 벗어나는 순간부터 **이후의 모든 폴링이 만액인
    48회의 get을 소모합니다**. 동시에 새 내용이 없으므로 지수 백오프가 폴링 간격을
    상한인 60초까지 밀어 올립니다. 정상 상태는 `(86400 ÷ 60) × (48 + 1) = 70,560`회/일
    ⚠️ **이 수치는 「정상 상태의 유휴 포락선」이지 상한이 아닙니다.** 보드를 열어 둔 채
    아무도 건드리지 않는 상태를 가정합니다. 상호작용 경로는 포함되지 않습니다: 레벨
    필터 버튼을 한 번 누를 때마다 만액 콜드 리드가 한 번 발생하고, 이 보드로 돌아오거나
    탭이 다시 보이게 될 때도 즉시 한 바퀴를 돕니다——**오늘은 어느 것도 스로틀링되지 않습니다**.
    (읽기 할당량의 약 **71%**)입니다. 식의 `+1`은 **폴링 한 바퀴가 스스로 유발하는 설정
    읽기**입니다. 설정 갱신 미들웨어는 모든 라우트보다 먼저 실행되고 설정 캐시 TTL은
    30초로 60초인 폴링 간격보다 짧으므로, 한 바퀴마다 정확히 한 번씩 더 읽습니다.
    이는 아래 key 풀 계산의 `86400 ÷ 설정 TTL 초` 항목과 **같은 버킷**을 씁니다(그 항목은
    상한인 2,880회/일이고, 패널만 돌고 있는 isolate가 실제로 쓰는 것은 1,440회).
    두 계산을 합산할 때 **두 번 세지 마세요**.
    **진단 이벤트를 거의 발생시키지 않을 만큼 건강한 배포가
    패널 탭 하나만 열어도 "활성" 배포보다 더 많은 읽기 할당량을 소모한다**는, 직관에
    반하지만 사실인 결론입니다. 할당량 여유를 계획할 때는 더 작은 "활성" 수치가 아니라
    이 더 큰 수치를 기준으로 삼으세요. 특히 위의 key 풀 읽기 쪽과 합산할 때 더욱
    그렇습니다(위의 "활성 isolate 3개가 이미 약 99.4%를 사용" 시나리오 참고).
  - **다운로드 엔드포인트**(`GET /admin/api/events/download`)는 클릭할 때마다 고정
    48회의 get을 소모합니다(`readEvents(null)`은 항상 커서 없이 콜드 읽기를 수행합니다)
    ——이는 수동 클릭 시에만 발생하며 규모상 무시할 수 있는 수준이지만, 정확성을 위해
    여기에 기록해 둡니다.
  두 시나리오의 상한 모두 **배포가 실행된 일수가 늘어나도 계속 커지지 않습니다**——이
  부분은 C4 수정 후에도 여전히 성립합니다.
#### `list`와 `delete` 두 할당량

- **`list`와 `delete`는 또 다른 두 개의 할당량이며 각각 하루 1,000회**로, 읽기·쓰기 할당량과는
  별개입니다. 정상 상태의 전달에서는 `list`가 한 번도 발생하지 않습니다 — `pool:index` 인덱스
  키가 바로 그 때문에 존재합니다. 이를 소비하는 곳은 **네 군데**입니다: 하루 48~96회의 인덱스
  대조(보충 스케줄의 매 라운드 시작마다 한 번씩); **패널의 "지금 보충"**(P3c부터, 그 라운드에서
  실제로 key를 발급했다면 마무리에 한 번 더 대조합니다 ⇒ 하루 최대 24회 추가이며 상한은 그
  가드레일 자체입니다 —— 이 한 군데가 원래 이 목록에서 빠져 있었고, 게다가 이 문장은 대조를
  "독립적으로 스케줄되는 작업"으로 한정했지만 P3c 이후에는 **운영자가 수동으로 촉발하는**
  소비자도 생겼습니다. 전체 브랜치 리뷰 I2); **풀이 비었을 때의 폴백 스캔**(인덱스는 정상인데 살아 있는
  레코드를 하나도 읽지 못할 때, 수동으로 가져온 레코드가 인덱스에 빠져 있는지 확인하려고
  `list`를 한 번 실행합니다); 그리고 **인덱스 유실 시 폴백**(`pool:index` 자체를 읽을 수 없거나
  파싱에 실패했을 때 마찬가지로 `list`를 한 번 실행해 인덱스 재구축을 시도합니다 — 대개 쓰기
  할당량이 소진되어 인덱스를 끝내 만들지 못한 경우입니다). 뒤의 두 가지는 내장된 **10분**
  백오프를 **공유**합니다(환경 변수가 아닌 고정 상수) — 둘 다 같은 `list` 할당량을 쓰므로 각자
  따로 창을 열어봐야 의미가 없습니다 — 따라서 풀이 비어 있거나 인덱스가 깨진 동안에도
  isolate당 하루 최대 144회이며, 인덱스 대조의 48~96회와 패널의 최대 24회를 더해도 여유가
  남습니다.
- **`list` 할당량이 소진되면 성능 저하가 아니라 기능 정지입니다.** 풀이 비어 있고 `list`가
  실패하면 게이트웨이는 `500`을 반환하고 실제 원인을 로그에 남깁니다. **`503 pool_empty`로
  위장하지 않습니다** — 이때 대조 역시 같은 할당량을 쓰고 있어 함께 실패하며, 이 문서가 제시한
  두 가지 자가 치유 경로가 모두 사라진 상태이기 때문입니다. UTC 자정에 할당량이 재설정될
  때까지 복구되지 않습니다.

**위의 읽기 산식에는 "isolate가 TTL보다 오래 산다"는 전제가 있습니다.** 트래픽이 적거나
충분히 많은 Cloudflare 엣지 위치로 분산되면 isolate는 TTL 한 주기가 다 지나기 전에 회수되는
경우가 흔하며, 그때는 각 isolate가 생애 동안 최소 한 번은 풀을 로드하므로 읽기 횟수는
TTL이 아니라 **콜드 스타트 횟수**로 결정됩니다. 상한은 대략 `100000 ÷ (풀 안의 key 수 + 2)`
콜드 스타트/일입니다(`+2`는 인덱스와 설정에 각각 한 번씩). **이 구간에서는 `POOL_CACHE_TTL_MS`를
키워도 읽기가 한 번도 절약되지 않습니다** — 절약되는 것은 "같은 isolate 안에서의 중복 로드"뿐입니다.

같은 이유로 풀이 비었을 때와 인덱스가 유실됐을 때의 `list` 백오프도 **인스턴스별**입니다.
차가운 isolate마다 각자 비용을 치르므로 총량은 isolate 수에 비례해 늘어납니다.

### 관리 패널 관련 변수(P3, 기본값은 비활성화)

| 변수 | 필수 | 기본값 | 설명 |
|----|----|------|----|
| `ADMIN_TOKEN` | 아니오 | 없음(패널 비활성화) | 관리 엔드포인트의 토큰. **`GATEWAY_TOKEN`과 달라야 하며**, 최소 24자 이상이어야 하고, **앞뒤에 공백이 없어야** 하며, **출력 가능한 ASCII(0x20–0x7E)로만** 구성되어야 합니다. 세 규칙 각각의 이유는 아래에 있습니다. 미설정이거나 규칙에 어긋나면 `/admin` 트리 전체가 등록되지 않으며, 이유는 `admin.token_rejected`로 기록됩니다. |
| `TRUST_PROXY` | 아니오 | 미설정(**어떤** 전달 헤더도 신뢰하지 않음) | 게이트웨이가 실제로 프록시 뒤에 있을 때**만** `1`로 설정하세요. **Cloudflare Worker 형태도 여기에 해당하므로 설정해야 합니다.** 로그인 실패 이벤트의 클라이언트 IP를 어디에서 가져올지 결정합니다. 자세한 내용은 아래. |

**설정하지 않으면 관리 패널만 사용할 수 없을 뿐, 게이트웨이 전달은 정상 동작합니다.** 이때
`/admin/...` 요청은 **`401`이 아니라 `404`**를 받습니다. 트리 자체가 등록되지 않으므로 "여기에
관리 화면이 있다"는 사실조차 노출되지 않습니다. 레지스트라가 기본 비활성화인 것과 같은 원칙으로,
`ADMIN_TOKEN`이 없거나 잘못되었다고 해서 게이트웨이 전달이 멈춰서는 안 됩니다.

#### `ADMIN_TOKEN`의 세 가지 하드 룰

**앞뒤에 공백이 있으면 안 됩니다**: HTTP는 헤더 값의 앞뒤 공백을 제거하지만 환경 변수는 그대로
유지하므로, 공백이 붙은 토큰은 어떤 클라이언트도 보낼 수 없습니다.

또한 토큰은 **출력 가능한 ASCII(0x20–0x7E)로만** 구성되어야 합니다. 이 제한에는 성격이 다른 세
가지 이유가 있습니다:

1. U+00FF를 넘는 문자(한자, 이모지, 폭 없는 공백)와 줄바꿈·NUL은 헤더 값을 설정할 때 `fetch`가
   **예외를 던집니다** — 요청 자체가 나가지 않으므로 200을 반환하지만 결코 들어갈 수 없는 패널이
   만들어지고, 서버에는 `admin.login_failed` 한 줄조차 남지 않습니다.
2. **TAB을 제외한** 그 밖의 제어 문자(`0x01–0x08`, `0x0B`, `0x0C`, `0x0E–0x1F`, `0x7F` — 총 29개)는
   브라우저가 보낼 수 있지만 HTTP 파서가 `400`으로 거부합니다.
3. **TAB(`0x09`)**과 `é` / `£` / 줄바꿈 없는 공백 같은 `0x80–0xFF` 바이트는 **실제로 전송되고
   동작합니다** — 이를 거부하는 것은 물리적 제약이 아니라 **저희 쪽의 견고성 절충**이며,
   **둘의 이유는 서로 다릅니다**. TAB은 **눈에 보이지 않는 문자**라 `.env`나 시크릿에 붙여넣어도
   아무도 알아채지 못합니다(앞뒤 공백과 같은 종류의 진단 가능성 문제지만, 그쪽은 물리적이고
   이쪽은 절충입니다). `0x80–0xFF`는 대신 인코딩 문제입니다: 환경 변수는 UTF-8로, 헤더 값은
   Latin-1로 해석되며 그 구간에서 둘이 일치한다는 보장은 명세에 없습니다(Node에서만 검증했고
   Cloudflare Workers 쪽은 미검증입니다). 또한 RFC 9110은 이 구간을 폐기 예정으로 표시했습니다.

ASCII 전용 토큰을 사용하세요. **중간의 공백은 허용됩니다**——`correct horse battery staple` 같은
패스프레이즈는 문제없이 전송되고 도달하며, 24자 하한 아래에서는 무작위 문자열보다 오히려 다루기
쉬운 경우가 많습니다. 앞뒤 공백은 위의 규칙이 담당합니다.

**24자 하한이 있는 이유.** Worker 형태에는 **분산 로그인 속도 제한이 없습니다.** 이를 구현하려면
KV를 카운트 윈도로 써야 하는데, 그것은 공격자에게 쓰기 할당량을 소진시킬 지렛대를 쥐여 주는 일이며
공격면이 "비밀번호 추측"에서 "키 풀 상태 기록 마비"까지 넓어집니다. 따라서 토큰 엔트로피가 유일한
방어선이고, 이 하한은 권고값이 아닙니다. 하한 미만이면 패널이 활성화되지 않고 컨테이너 로그에
`admin.token_rejected`가 남습니다.

**`GATEWAY_TOKEN`과 달라야 하는 이유.** `GATEWAY_TOKEN`은 **모든 다운스트림 사용자**에게 나눠 주는
중계 토큰입니다. 이를 패널 토큰으로 재사용하면, 중계 토큰을 가진 누구나 키 풀 전체를 읽고,
레지스트라를 끄고, 등록 백엔드를 자기 서버로 바꿀 수 있습니다. 그 이후 생성되는 모든 계정의
메일 주소·비밀번호·인증 코드가 그에게 넘어갑니다.

이 규칙은 **관리 요청마다 다시 검사할 뿐, 시작 시에는 막지 않습니다.** 둘이 같으면 — 예를 들어
`wrangler kv key put`이나 `store.json` 직접 편집으로 `gatewayToken`을 손으로 바꾼 경우 — 관리
엔드포인트는 **`503`을 반환**하고 error 수준으로 `admin.token_conflict`가 기록됩니다(시작 시점에
이미 충돌하고 있다면 시작 로그에도 같은 줄이 남아 원인을 바로 알 수 있습니다).
**게이트웨이 전달은 영향을 받지 않습니다.**

**충돌이 일어난 시점부터 `ADMIN_TOKEN`은 유출된 것으로 취급해야 합니다. 복구 방법은 하나뿐,
완전히 새로운 값으로 교체하는 것입니다.** Worker는 `npx wrangler secret put ADMIN_TOKEN`을
실행한 뒤 재배포하고, Docker는 `.env`를 고친 뒤 컨테이너를 다시 만듭니다.
**저장소의 `gatewayToken`만 되돌리고 끝내지 마십시오.** 그렇게 해도 관리 엔드포인트는 바로
복구되지만(설정 캐시가 다음에 갱신되는 시점에 적용되며 **재시작이 필요 없습니다**),
그것이 되찾아 주는 것은 가용성이지 보안이 아닙니다. 충돌하던 동안 관리 토큰과 게이트웨이
토큰은 같은 값이었고, 게이트웨이 토큰은 **모든 다운스트림 사용자**에게 나눠 주는 값입니다 —
이미 가지고 있는 사람(또는 앞으로 받게 될 사람)은 그대로 관리 화면을 열 수 있습니다.
가용성을 먼저 되찾기 위해 `gatewayToken`을 되돌리는 것은 괜찮지만, 그 뒤에 **반드시
`ADMIN_TOKEN`을 교체**해야 합니다. 두 단계를 모두 마쳐야 대응이 끝난 것입니다.

**왜 이 규칙만 시작 시에 막지 않는가.** `gatewayToken`은 운영 중에 바뀔 수 있는데 시작 시점의
판정에는 두 번째 평가 기회가 없습니다. 거기서 `/admin` 트리 전체를 등록하지 않게 하면, 충돌
중에 콜드 스타트한 isolate(그리고 충돌 중에 기동한 Docker 컨테이너)는 **영구히 `404`**가 되어
설정을 되돌려도 낫지 않고 재시작밖에 방법이 없습니다. 반면 충돌 전에 만들어진 것들은 `503`에
그치고 값을 되돌리면 즉시 복구됩니다. 같은 설정, 같은 순간에 두 가지 답이 존재하게 되고, 위의
"재시작이 필요 없습니다"라는 문장이 반쯤 거짓이 됩니다. `ADMIN_TOKEN` 자체에 관한 세 규칙
(앞뒤 공백, 보낼 수 없는 문자, 최소 길이)은 입력이 환경 변수뿐이라 운영 중에 바뀌지 않으므로 계속 시작 시에
막으며, 실패 형태도 `404` 그대로입니다.

`ADMIN_TOKEN`은 **환경 변수에서만 읽고 저장소에서는 읽지 않습니다.** 패널이 자기 키를 스스로
교체할 수 없습니다. 교체 방법은 Worker는 `npx wrangler secret put ADMIN_TOKEN` 후 재배포,
Docker는 `.env`를 수정하고 컨테이너를 다시 만드는 것입니다.

**관리 토큰 유출 = `ADMIN_TOKEN` 유출입니다.** 패널은 이 값을 브라우저의 localStorage에 그대로
저장합니다. 파생 토큰도 없고 제품 안에 폐기 경로도 없습니다. 폐기하는 방법은 하나뿐입니다:
시크릿을 바꾼 뒤 재배포(Worker)하거나 컨테이너를 다시 만드는 것(Docker)입니다.
패널은 12시간 뒤에 토큰을 다시 입력하도록 요구하지만, 그것은 그 localStorage 값이 쓰일 수 있는
기간을 줄일 뿐 **폐기가 아닙니다**. 패널은 TLS 뒤에 두고, 신뢰하는 기기에서만 여세요.

**이 상한이 할 수 없는 일도 분명히 밝힙니다.** 패널의 CSP는 `connect-src 'self'`로 토큰을 외부
도메인으로 `fetch`하는 것을, `form-action 'none'`으로 폼을 통한 유출을 막습니다. 하지만
`location.href = "https://…?k=" + token` 같은 **내비게이션을 통한 유출**은 막지 못합니다
— CSP에는 이를 막을 지시어가 더 이상 없습니다(`navigate-to`는 표준에서 제거되었습니다).
진짜 해법은 서버가 발급하는 **폐기 가능한 파생 토큰**이지만, 그것은 서버가 세션을 저장해야 하고
"`ADMIN_TOKEN`은 환경 변수에서만 읽는다"는 설계 제약과 충돌하므로 이후 릴리스로 미룹니다.

#### `TRUST_PROXY`는 클라이언트 IP를 어디서 가져올지 정한다

설정하면 로그인 실패 이벤트에 기록되는 클라이언트 IP는 `CF-Connecting-IP`에서 오고, 없을 때만
`X-Forwarded-For`의 첫 구간으로 폴백합니다.

**`TRUST_PROXY`는 보안 스위치이므로 기본값이 꺼짐입니다.** 이 값이 결정하는 클라이언트 IP는
`admin.login_failed` 이벤트에 기록되므로, 클라이언트가 보낸 헤더를 무조건 신뢰하면 누구나 무차별 대입
흔적을 임의의 IP에 뒤집어씌울 수 있습니다.

**꺼진 상태에서는 어떤 전달 헤더도 신뢰하지 않으며 이 필드는 일률적으로 `null`로 기록됩니다 —
`CF-Connecting-IP`도 예외가 아닙니다.** 이 헤더는 흔히 "플랫폼이 주입하므로 위조할 수 없다"고
설명되지만, 그 성질은 **요청이 실제로 Cloudflare를 통과할 때만** 성립합니다. Node/Docker를 직접
노출한 구성에서는 이를 덮어쓰는 것이 아무것도 없으므로, 클라이언트가 스스로
`CF-Connecting-IP: 1.2.3.4`를 보내면 그대로 믿게 됩니다 — 그리고 직접 노출은 Docker 배포의 기본
형태입니다.

**켜진 상태에서는 `CF-Connecting-IP`가 우선이고 `X-Forwarded-For`는 폴백일 뿐입니다.** 두 헤더는
위조 가능성이 근본적으로 다릅니다.

- `CF-Connecting-IP`는 Cloudflare 엣지가 기록하며, 클라이언트가 보낸 동일 이름 헤더를 **덮어씁니다** —
  요청이 실제로 Cloudflare를 통과하는 한 위조할 수 없습니다.
- `X-Forwarded-For`는 어떤 중간 장비든 덧붙일 수 있는 체인이고 클라이언트가 가짜를 보낼 수도 있어,
  어디까지 믿을 수 있는지는 전적으로 프록시 구성에 달려 있습니다.

**Worker 형태에서는 `TRUST_PROXY=1`을 설정하세요.** 그곳에서는 Cloudflare가 정의상 앞단에 있으므로
`CF-Connecting-IP`가 권위 있는 값입니다. 이 형태에서 `X-Forwarded-For`를 우선하는 것은 잘못이며,
그 체인에는 클라이언트가 채워 넣은 값이 들어 있을 수 있습니다. 스위치를 설정하지 않으면 이 필드는
그냥 `null`로 기록됩니다.

**범용 리버스 프록시(nginx / Caddy / Traefik) 뒤에서 `TRUST_PROXY=1`을 켤 때는 프록시에서
`CF-Connecting-IP`를 제거하세요.** 그런 구성에서는 이 헤더를 덮어쓰는 것이 아무것도 없는데,
게이트웨이는 "Cloudflare가 앞단에 있다"는 전제로 이를 우선하므로 공격자가 직접 붙인 헤더가
프록시가 방금 쓴 `X-Forwarded-For`를 **이깁니다**. nginx는 한 줄이면 됩니다:

```nginx
proxy_set_header CF-Connecting-IP "";
```

Caddy는 `header_up CF-Connecting-IP ""`, Traefik은 미들웨어의 `customRequestHeaders`를 씁니다.

**두 헤더 모두 먼저 형태 검사를 거칩니다**: 점 표기 IPv4와 IPv6 형태(16진수, 콜론, `::ffff:`
매핑 안의 점)만 이벤트에 들어가고, 그 외에는 일률적으로 `null`로 기록됩니다. 이것은 인증
방어선이 아니며(이 값의 소비 지점은 저장소 전체에서 로그인 실패 이벤트 한 곳뿐입니다),
인증되지 않은 호출자가 감사 필드에 임의의 텍스트를 써 넣지 못하게 하려는 것입니다. 관리
패널의 이벤트 영역이 이 필드로 필터링하고 표시하기 때문입니다.

쓸 수 있는 값이 하나도 없으면 이 필드는 정직하게 `null`로 기록됩니다 — **`"unknown"` 같은 가짜 값은
절대 만들지 않습니다.** 실재하는 출처로 오해되기 때문입니다.

### 설정 페이지에서 바꿀 수 있는 것(P3c)

패널의 **설정** 페이지는 카드 세 장입니다: **인증 키** / **업스트림 및 쿨다운** /
**등록기**(완전히 동등한 두 메일박스 채널 서브카드와 「고급」 접기 영역 포함).
쓰기 대상은 **저장소의 `config` 키**이며 환경 변수가 아닙니다.

**각 항목에는 하나가 아니라 세 개의 값이 표시됩니다.** 「저장값 X · 환경 변수 Y · 실효값 Z」
한 줄이 「내가 저장한 것」 「배포 쪽이 준 것」 「게이트웨이가 실제로 쓰는 것」을 분리해 보여 줍니다.
우선순위는 항상 **환경 변수 > 저장소 > 내장값** 입니다.

**환경 변수로 잠긴 항목은 패널에서 바꿔도 반영되지 않으므로, 패널은 아예 편집을 막습니다.**
해당 입력란은 비활성화되고 어떤 환경 변수인지와 배포 쪽에서 바꿔야 한다는 설명이 붙습니다.
`PUT /admin/api/config` 는 그런 항목에 대해 `400 locked_by_env` 를 돌려주고 **저장소에 아무것도
쓰지 않습니다**: 써 버리면 「저장 성공, 실효값은 그대로」가 되어 운영자는 캐시 탓이라 여기고
두 주기를 헛되이 기다리게 됩니다.

⚠️ **P3c부터 등록기 계열(`REGISTRAR_ENABLED` / `REGISTRAR_PRIMARY` / `REGISTRAR_FALLBACK` /
`TARGET_KEYS` / `MINT_BATCH` / `TEND_INTERVAL_MS` / `CODE_TIMEOUT_MS` / `MINT_DELAY_MIN_MS` /
`MINT_DELAY_MAX_MS` / `MAX_DOMAIN_ATTEMPTS` / `REGISTRAR_TOKEN_NAME` / `AGNES_PLATFORM_URL` /
`YYDS_BASE_URL` / `YYDS_API_KEY` / `MOEMAIL_BASE_URL` / `MOEMAIL_API_KEY`)도 이 잠금 표에
들어갔습니다.** 그 전에는 없었습니다: `docker-compose.yml` 에 `TARGET_KEYS=30` 이 있는데
패널에서 20으로 바꾸면 저장은 성공하지만 실효값은 계속 30이었고, **재시작해도 고쳐지지 않으며**
패널에는 아무 안내도 없었습니다.

**자격 증명은 쓰기 전용입니다.** 게이트웨이 토큰과 두 채널의 API 키는 **평문으로 절대
반환하지 않습니다**. 반환하는 것은 「설정 여부」와 **마지막 4자리**뿐입니다(5자 미만이면 그 4자리도
주지 않습니다 — 그건 전부를 보여 주는 것이니까요). 따라서:

- 입력란은 항상 비어 있고, 플레이스홀더에는 **비워 두면 변경되지 않습니다**라고 표시됩니다;
- 저장할 때 이 칸들이 **없거나 비어 있으면 = 바꾸지 않음**(지우기가 아닙니다). 비움을 지우기로
  구현하면 운영자가 설정 페이지를 한 번 저장하는 것만으로 게이트웨이 토큰이 지워지고, 게다가
  **현재 프로세스는 마지막 정상 스냅숏으로 계속 동작**하므로 다음 재시작 전까지는 이상이 보이지 않습니다;
- 지우기는 확인 대화상자가 붙은 전용 「지우기」 버튼으로만 가능합니다.

⚠️ **패널에서 쓴 자격 증명은 KV / `store.json` 에 평문으로 저장됩니다.** P1의 「키 평문 저장」과
같은 수준입니다. 여기에 입력하는 값이 암호화된 secret이라고 생각하지 마세요.
데이터 디렉터리 / KV 네임스페이스는 자격 증명으로 취급하세요.

⚠️ **환경 변수에도 `GATEWAY_TOKEN` 이 없는 상태에서 게이트웨이 토큰을 지우면**, 현재 프로세스는
계속 동작하지만 **다음 재시작이나 isolate 회수 시 기동에 실패합니다.** 패널이 그 자리에서 붉은
안내로 알려 줍니다. 같은 페이지에서 즉시 새 게이트웨이 토큰을 설정해 복구하세요. **환경 변수가 이 값을 제공하는 경우 지우기는 안전합니다**: 저장소의 사본만 사라지고 실효값은 환경 변수로 폴백하여 그대로입니다. 패널은 이 두 상태에서 서로 다른 문구를 보여 주며, 판단을 사용자에게 떠넘기지 않습니다.

⚠️ **「고급」 접기 영역 안의 가입 백엔드 URL(`AGNES_PLATFORM_URL`)은 평범한 설정 항목이 아닙니다.**
이것은 **모든 자동 가입의 전송 대상**입니다: 다른 서버로 바꾸면 그 서버가 각 가입에 쓰이는
메일 주소·비밀번호·인증 코드를 받게 됩니다. 그래서 접기 영역 안에 두고, 붉은 경고를 붙이고,
메인 「저장」과 함께 가지 않는 전용 확인 버튼을 둡니다.

**저장 후 패널은 「저장되어 적용되었습니다」라고 말하지 않습니다.** 실효값을 **다시 읽어**
실제로 바뀐 항목을 강조하고, **다른 복제본/isolate가 변경을 보기까지 최대 얼마나 걸리는지**를
명시합니다: 설정 홀더의 TTL은 30초, KV 엣지 캐시 기본값은 60초이므로 상한은 약 **90초**입니다.
이 인스턴스는 즉시입니다(저장 시 로컬 캐시를 무효화합니다). 다른 인스턴스는 그렇지 않습니다.
**패널 문구에 「즉시 적용」이라고 써서는 안 됩니다.**

### 두 가지 타임아웃 예산의 역할

기준은 "업스트림의 첫 바이트가 언제 도착할 수 있는가"이지 엔드포인트의 이름이
아닙니다:

| 예산 | 대상 엔드포인트 | 변수 |
|----|---------------|----|
| 첫 바이트 | **스트리밍** 대화(`stream: true`), 비디오 폴링 `GET /v1/videos/{id}` | `UPSTREAM_TIMEOUT_MS` |
| 동기 | 이미지 생성, 비디오 작업 생성, **모든 비스트리밍 대화**(네 프로토콜 모두) | `UPSTREAM_SYNC_TIMEOUT_MS` |

비스트리밍 요청은 업스트림이 답변 전체를 생성한 뒤에야 응답 헤더를 보냅니다. 이미지
생성과 완전히 같은 지연 특성이므로, 8초짜리 첫 바이트 예산으로 자르면 정상적인 요청이
대량으로 실패하고 key 풀까지 함께 망가집니다.

`UPSTREAM_SYNC_TIMEOUT_MS`는 **요청 한 건의 총예산**, 즉 클라이언트의 최악 대기 시간이며
"풀 크기 × 예산"이 아닙니다. 게이트웨이는 이 예산에서 key 하나에 최대 절반만 쓰고, 나머지는
다른 key로 재시도하는 데 남겨 둡니다. 그래야 풀에 멈춘 key(연결은 되지만 절대 응답하지
않는)가 있어도 요청 하나를 통째로 잡아먹지 않습니다. 따라서 **단일 호출의 최악 소요 시간의
2배 이상**으로 설정하세요.

동기 예산에서의 타임아웃은 즉시 key를 처벌하지 않습니다. 같은 요청 안에서 바꿔 쓴 다른
key가 실제로 성공했을 때에만 먼저 타임아웃된 key에 책임을 지웁니다(`MAX_STRIKES`에
도달하면 쿨다운). 그 요청에서 모든 key가 타임아웃했다면 하나도 처벌하지 않습니다 ——
예산이 너무 작거나 업스트림 전체가 느릴 가능성이 더 크기 때문입니다.

"제거"와 "쿨다운"은 다릅니다. 위 설정과 무관하게, 업스트림 `401`/`403`은 해당
key를 **영구** 제거합니다 —— 이는 "이 key는 더 이상 유효하지 않음" 상태이며
재시도가 무의미하기 때문입니다. 일시적 실패는 결코 제거로 이어지지 않습니다.
`MAX_STRIKES`에 도달해도 `COOLDOWN_STRIKE_MS` 쿨다운에 들어갈 뿐 스스로 복구되므로,
업스트림의 일시적 장애가 key 풀을 영구히 망가뜨리는 일은 없습니다.

어떤 key도 요청을 처리할 수 없을 때 게이트웨이는 `503`과 함께 판별 가능한
`error.reason`을 반환합니다: `pool_empty`(key 미등록), `all_cooling`(모든 key가
쿨다운 중 — 자동 복구되며 `Retry-After` 헤더가 복구 시점을 알려줌),
`all_evicted`(자격 증명 실효로 모든 key가 영구 제거됨 — **자동 복구되지 않으므로**
key 교체 필요), `upstream_error`(key 자체는 정상이나 업스트림이 매번 실패).

### 아주 긴 비스트리밍 요청이 도중에 끊길 수 있나 (두 배포 형태가 다를 수 있음)

**결론: Worker 쪽에는 의지할 수 있는 플랫폼 약속이 없습니다. 따라서 이 문서도, 관리
콘솔도 아무것도 약속하지 않습니다.**

Cloudflare Workers의 limits 문서에서 확인된 공식 문구는 두 가지입니다. HTTP로 트리거되는
Worker에는 **실시간(wall-clock) 상한이 없고**("There is no hard limit on duration for
HTTP-triggered Workers"), 개별 아웃바운드 서브요청에도 **시간 제한이 없습니다**
("There is no set time limit on individual subrequests"). 둘 다 「클라이언트가 연결을
유지하는 동안」이라는 조건이 붙습니다.

**이 두 문장이 전부를 덮지는 못합니다.** 항목별로 명시합니다.

- 공식 문서의 **125초 프록시 읽기 시간 초과(오류 524)** 는 「Cloudflare를 리버스 프록시로
  거치는 존 트래픽」 맥락에서만 서술되며, **Worker 자신이 보내는 서브요청에 적용되는지는
  전혀 언급되지 않습니다**. 찾을 수 없으면 「플랫폼 약속 없음」으로 취급하고 추측하지 않습니다.
- 같은 페이지에는 런타임이 주 몇 회 갱신되며, 갱신 시 진행 중인 요청에 **30초**의 유예가
  주어지고 그 뒤에는 종료된다고 적혀 있습니다. 확률은 낮지만 존재합니다.
- `wrangler.toml`의 **15분(900초)** 는 **Cron Trigger(`scheduled()`)** 의 실시간 상한이며
  **`fetch()`의 것이 아닙니다**. 근거로 옮겨 쓰지 마세요.

⇒ **실질적인 영향 두 가지:**
① `UPSTREAM_SYNC_TIMEOUT_MS`(기본 120000) 수준의 비스트리밍 요청은 Worker와 Docker에서
   **동작이 같다고 볼 수 없습니다**. Node/Docker 쪽에는 플랫폼 실시간 상한이 없고,
   직접 설정한 예산만 적용됩니다.
② **관리 콘솔(플레이그라운드) 문구는 「두 형태가 같다」고 말하지 않으며**, 「몇 초까지는
   반드시 끊기지 않는다」는 숫자도 제시하지 않습니다. 긴 요청이 필요하면 실측한 범위로
   `UPSTREAM_SYNC_TIMEOUT_MS`를 조정하거나 스트리밍 엔드포인트(첫 바이트 예산)로
   전환하세요.

## 다중 계정 설정

현재 버전의 게이트웨이는 key를 풀에 추가하기 위한 HTTP 엔드포인트를 제공하지
않습니다. 저장소 백엔드에 직접 기록해야 합니다. 각 항목은 `key:<id>`를
키로 하는 JSON 객체이며, `<id>`는 풀 내에서 고유하기만 하면 어떤 문자열이든
가능합니다(게이트웨이가 스스로 레코드를 생성할 때는 key의 해시값에서
파생하지만, 읽을 때 이 값을 검증하지는 않으므로 수동 임포트 시에는 고유한
식별자면 무엇이든 사용할 수 있습니다).

```json
{
  "id": "1a2b3c4d5e6f7a8b",
  "key": "실제-agnes-api-key",
  "addedAt": 1735689600000,
  "lastUsedAt": null,
  "cooldownUntil": 0,
  "strikes": 0,
  "evicted": false,
  "evictedReason": null
}
```

### Docker로 임포트

실행 중인 프로세스와의 쓰기 경합을 피하기 위해 먼저 컨테이너를 중지한 뒤,
호스트에서 `./data/store.json`을 편집해 `"key:1a2b3c4d5e6f7a8b"` 키
아래에 위와 같은 레코드를 추가하고, 다시 컨테이너를 시작합니다.

```bash
docker compose stop
# ./data/store.json 편집
docker compose start
```

`./data/store.json`이 아직 없다면, `key:<id>` 형식의 키를 갖는 단일 JSON
객체로 새로 만들면 됩니다.

### Cloudflare Worker로 임포트

wrangler로 레코드를 `POOL` KV 네임스페이스에 직접 씁니다.

```bash
npx wrangler kv key put --binding=POOL "key:1a2b3c4d5e6f7a8b" \
  '{"id":"1a2b3c4d5e6f7a8b","key":"실제-agnes-api-key","addedAt":1735689600000,"lastUsedAt":null,"cooldownUntil":0,"strikes":0,"evicted":false,"evictedReason":null}' \
  --remote
```

`--remote`를 생략하면 프로덕션이 아니라 `wrangler dev`가 사용하는 로컬
네임스페이스에 기록됩니다.

### 색인과 반영까지 걸리는 시간

게이트웨이는 풀의 id 목록을 `pool:index` 키에 보관하여 전달 요청마다 KV `list`를 쓰지 않게
합니다(무료 등급의 `list` 할당량은 하루 1,000회뿐이며 읽기·쓰기와는 별개의 할당량입니다).
**레코드를 손으로 써도 이 색인은 바뀌지 않습니다.** 따라서 새 key가 언제부터 쓰이는지는 그
시점의 풀 상태에 달려 있습니다:

- **풀이 비어 있을 때**: 색인이 "비어 있다"고 하고 실제로도 레코드를 하나도 읽지 못하면,
  게이트웨이는 `list` 스캔으로 한 번 폴백해 수동으로 가져온 레코드를 찾아 색인에 채웁니다.
  이 스캔에는 내장된 10분 백오프가 있으므로(위 "할당량 계산" 참조), 가시성 상한은
  **10분 이내 + `POOL_CACHE_TTL_MS` 한 번**입니다.
- **풀이 비어 있지 않을 때**: 전달 경로는 색인이 아는 레코드만 가져오므로, 색인이 모르는
  레코드는 **완전히 보이지 않습니다**(오류도 전혀 나지 않습니다). 다음 cron 대조가 색인을
  고칠 때까지(기본 30분이며 **트리거 시점에 공식적인 보장이 없습니다**, 아래 참조), 그리고
  그 뒤 최대 `POOL_CACHE_TTL_MS` 한 번을 더 기다려야 합니다.

**수동 가져오기를 즉시 반영하려면 레코드를 쓸 때 id도 함께 `pool:index`에 추가하세요:**

```bash
npx wrangler kv key get --binding=POOL "pool:index" --remote
# ids 배열에 새 id를 추가하고 값 전체를 다시 씁니다(v는 항상 1)
npx wrangler kv key put --binding=POOL "pool:index" \
  '{"v":1,"ids":["기존id","1a2b3c4d5e6f7a8b"]}' --remote
```

색인을 쓰고 나면 각 isolate는 최대 `POOL_CACHE_TTL_MS` 한 번 뒤에 이 key를 쓰기 시작합니다.

레지스트라를 쓰지 않더라도 `wrangler.toml`의 `[triggers]` 블록을 지우지 마십시오.
이 cron은 `pool:index`와 실제 `key:` 레코드를 대조해 고치는 유일한 경로이며,
`REGISTRAR_ENABLED` 값과 무관하게 실행됩니다.

**이 cron의 트리거 시점은 공식적으로 보장되지 않습니다.** Cloudflare는 Cron
Trigger가 `crons` 표현식대로 정확히 발동한다는 신뢰성을 문서화하지 않았습니다
(건너뛰지 않는다는 보장도, 지연 상한도 명시되어 있지 않습니다). 이는 할당량
계산에는 안전한 방향입니다 —— 대사(對帳) 트리거가 줄어들수록 실제 KV 읽기/쓰기
소비량은 예상보다 줄어들 뿐, 늘어나지 않습니다. 다만 **고아 레코드나 유령
색인 항목이 색인으로 회수되기까지 걸리는 시간은 보장되지 않습니다**. 최악의
경우 예상했던 "최대 30분"보다 더 오래 걸릴 수 있습니다. 그 대기 시간 동안
해당 key는 일시적으로 사용할 수 없을 뿐이며, 데이터가 손실되거나 손상되지는
않습니다.

### key 폐기하기

**레코드를 지우고, 그 id를 `pool:index`에서도 빼세요 — 두 단계 모두 해야 합니다.** 레코드만
지워도 오류는 나지 않지만(읽을 수 없는 레코드는 그냥 걸러집니다) id가 색인에 남아, 다음
대조가 잘라낼 때까지 갱신할 때마다 읽기 한 번을 헛되이 씁니다.

```bash
npx wrangler kv key delete --binding=POOL "key:1a2b3c4d5e6f7a8b" --remote
# ids 배열에서 해당 id를 빼고 값 전체를 다시 씁니다
npx wrangler kv key put --binding=POOL "pool:index" '{"v":1,"ids":["남은id"]}' --remote
```

Docker에서는 `./data/store.json`에서 `"key:<id>"` 항목을 지우고 `"pool:index"`의 `ids` 배열을
고치면 됩니다. 먼저 `docker compose stop`을 하는 것을 권합니다.

이미 예전 스냅숏을 읽어 둔 isolate / 프로세스는 최대 `POOL_CACHE_TTL_MS` 한 번 뒤에 이 key를
더는 고르지 않습니다. Worker에서는 여기에 KV 전파 창(약 60초)이 더 붙습니다. 삭제가 모든
colo에 보이기까지 그만큼 걸리기 때문입니다.

**그 창 동안에도 다시 기록되지는 않습니다**: 게이트웨이는 어떤 상태 변경이든 저장하기 전에
레코드가 아직 있는지 먼저 확인하고, 읽히지 않으면 그 쓰기를 버리며 자신의 스냅숏을 즉시
갱신합니다. 유일한 예외가 그 전파 창으로, 확인용 읽기가 KV 엣지 캐시에서 응답되면 그 colo는
레코드가 아직 있다고 판단합니다. Docker(파일 저장소)에는 이 캐시가 없어 그쪽은 정확합니다.

## 검증

명령 세 개, 싼 것부터. `$BASE`는 본인 주소(Worker는 `https://{name}.{sub}.workers.dev`,
Docker는 `http://localhost:8080`)로, `$TOKEN`은 본인이 설정한 `GATEWAY_TOKEN`으로 바꾸세요.

### 헬스 체크

```bash
curl -s "$BASE/health"
```

`status`가 `ok`면 저장소를 읽고 쓸 수 있다는 뜻이고, `degraded`면 저장소 쪽에 문제가 있다는
뜻이며 원인은 로그에 있습니다. **이 명령만 토큰이 필요 없어서**, 토큰이 틀렸을 때도 답이
돌아오는 유일한 엔드포인트이기도 합니다.

### 모델 목록

```bash
curl -s "$BASE/v1/models" -H "Authorization: Bearer $TOKEN"
```

이 게이트웨이가 다루는 모델 목록이 돌아옵니다. 이게 통과하면 토큰이 맞은 것이고, `401`이면
틀린 것입니다.

### 실제 대화 한 번

```bash
curl -s "$BASE/v1/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"agnes-2.0-flash","messages":[{"role":"user","content":"ping"}]}'
```

실제로 업스트림까지 가는 건 이 명령입니다. `503`이 오고 `error.reason`이 `pool_empty`면 풀에
아직 key가 없다는 뜻이니, 위 절로 돌아가 하나 임포트하세요.

## 문제 해결

마주치기 쉬운 순서로 여섯 가지. 모두 "증상 → 해결" 형태이고, 해결은 위에서부터 차례로
해 보세요.

### 게이트웨이가 뜨지 않고 로그에 토큰이 없다는 한 줄만 나온다

**증상**: 컨테이너나 Worker가 기동 직후 종료하고, 로그에는 `缺少 GATEWAY_TOKEN，网关无法启动` 한 줄뿐이다.

**해결**:

1. Docker: `.env`에 `GATEWAY_TOKEN=` 줄이 있고 **등호 뒤가 비어 있지 않은지** 확인합니다.
2. Worker: `npx wrangler secret put GATEWAY_TOKEN`을 한 번 실행한 뒤 `npx wrangler deploy`.
3. 저장된 설정이 망가져도 로드에 실패합니다. `RESET_CONFIG=1`로 한 번 기동해 복구하고, **복구한 뒤에는 그 줄을 지우세요**.

### 모든 요청이 503을 주고 이유는 풀이 비었음

**증상**: 어떤 전달 엔드포인트든 `503`을 주고 `error.reason`이 `pool_empty`다.

**해결**:

1. "다중 계정 설정" 절을 따라 key를 최소 한 개 임포트합니다.
2. 이미 임포트했는데도 비어 있음: 손으로 쓴 레코드는 **`pool:index`를 건드리지 않습니다**. 대사(기본 30분)를 기다리거나 id를 직접 색인에 넣으세요.
3. 레지스트라는 켜져 있는데 풀이 늘지 않음: 패널의 이벤트 보드를 보거나 [REGISTRAR.md](REGISTRAR.md)를 따라 두 메일함 채널을 점검하세요.

### 패널이 열리지 않고 `/admin`이 404를 준다

**증상**: 브라우저로 `/admin`을 열면 `404`가 온다. 로그인 화면도 `401`도 아니다.

**해결**:

1. **`ADMIN_TOKEN`을 설정하지 않았을 때**의 정상적인 모습입니다. 트리 자체가 등록되지 않으므로 "여기에 관리 화면이 있다"는 사실조차 새지 않습니다.
2. 설정했는데도 404: 토큰이 규칙에 어긋납니다(24자 미만 / 앞뒤 공백 / 출력 불가 ASCII). 컨테이너 로그에 `admin.token_rejected`가 남습니다.
3. 패널은 열리는데 엔드포인트가 `503`: `ADMIN_TOKEN`이 저장소의 `gatewayToken`과 충돌했습니다. 로그는 `admin.token_conflict`이고, 처리 방법은 위 절에 있습니다.

### 패널에서 저장한 설정이 다른 인스턴스에 한참 반영되지 않는다

**증상**: 패널에서 설정을 저장했고 이 인스턴스는 바로 바뀌었는데, 다른 복제본 / isolate는 여전히 옛 값이다.

**해결**:

1. **정상입니다**. 설정 홀더의 TTL은 30초, KV 엣지 캐시 기본값은 60초 ⇒ 상한은 약 **90초**입니다. 조금 기다렸다 다시 보세요.
2. 2분이 지나도 그대로면: 그 필드가 환경 변수로 잠겨 있지 않은지 확인합니다. 잠긴 필드는 패널에서 흐리게 표시되고 엔드포인트는 `400 locked_by_env`를 줍니다.
3. 바꾼 것이 `POOL_CACHE_TTL_MS` / `POOL_TOUCH_INTERVAL_MS`라면: 이 둘은 **인스턴스를 만들 때 한 번만** 읽으므로 컨테이너 재시작이나 isolate 회수 외에는 방법이 없습니다.

### 비스트리밍 요청이 무더기로 타임아웃되고 key 풀이 붉어진다

**증상**: 이미지 생성, 비디오 작업 생성, 비스트리밍 대화가 무더기로 타임아웃되고 패널에서 key 한 무리가 쿨다운에 들어간다.

**해결**:

1. `UPSTREAM_SYNC_TIMEOUT_MS`를 **단일 호출 최악 소요 시간의 두 배 이상**으로 올립니다. 기본값 `120000`은 느린 모델에는 빡빡합니다.
2. `UPSTREAM_TIMEOUT_MS`(첫 바이트 예산, 기본 `8000`)로 비스트리밍 요청을 묶지 마세요. 그 예산은 스트리밍과 비디오 폴링용입니다.
3. 업스트림 전체가 느려진 게 아닌지 확인합니다. 한 요청 안에서 모든 key가 타임아웃되면 게이트웨이는 **어느 것도 벌하지 않습니다**. 쿨다운은 같은 요청에서 다른 key가 실제로 성공했을 때만 기록됩니다.

### Docker 컨테이너는 떴는데 `/health`가 degraded다

**증상**: `docker compose ps`가 unhealthy를 보이고 `/health`는 `503`, `status`는 `degraded`다.

**해결**:

1. 열에 아홉은 데이터 디렉터리에 쓰지 못하는 경우입니다. 컨테이너 로그의 entrypoint 줄을 읽고 `./data`의 소유자가 `100:101`인지 확인하세요.
2. `--user`나 compose의 `user:`로 비 root를 지정했다면 entrypoint는 chown을 **하지 않습니다**. 소유자와 쓰기 가능 여부는 직접 준비해야 합니다.
3. `DATA_DIR`가 `/`나 최상위 시스템 디렉터리를 가리키면 entrypoint는 재귀 chown을 거부하고 경고만 찍습니다 —— 멀쩡한 디렉터리로 바꾸세요.

## 성능 최적화

먼저 한 가지를 분명히 해 둡니다. **이 게이트웨이 자체는 시간을 거의 쓰지 않습니다.**
비용은 두 곳에 있습니다 —— 업스트림 응답 시간, 그리고 저장소의 읽기/쓰기 할당량.
그래서 이 절에서 만질 값어치가 있는 손잡이는 셋뿐입니다.

```env
# 선택: 각 isolate/프로세스가 key 풀 스냅숏을 유지하는 시간(밀리초). 0이면 캐시를 끔.
# 키우면 KV 읽기를 아낌. 대가는 다른 인스턴스의 판정이 더 늦게 보인다는 점.
POOL_CACHE_TTL_MS=120000

# 선택: "마지막 사용 시각"을 저장하는 최대 간격(밀리초). 0이면 성공 요청마다 저장.
# 표시 전용 필드라서 줄여 봐야 KV 쓰기만 늘고 스케줄링에는 아무 이득이 없음.
POOL_TOUCH_INTERVAL_MS=21600000

# 선택: 동기 엔드포인트(이미지, 비디오 작업, 모든 비스트리밍 대화)의 전체 예산(밀리초).
# 단일 호출 최악 소요 시간의 두 배 이상으로 두지 않으면 정상 요청까지 죽고 key 풀이 상함.
UPSTREAM_SYNC_TIMEOUT_MS=180000
```

효과가 큰 순서로 셋:

1. **Worker + 무료 등급 KV에서 풀이 key 20개를 넘으면 `POOL_CACHE_TTL_MS`부터 키웁니다.**
   기본값 그대로면 "key 20개, 활성 isolate 3개"에서 이미 읽기 할당량의 약 99.4%를 씁니다.
   산식은 위 "할당량 계산"에 있습니다.
2. **패널의 "마지막 사용"을 더 정확히 보겠다고 `POOL_TOUCH_INTERVAL_MS`를 줄이지 마세요.**
   그건 표시 전용 필드인데 쓰기 할당량은 하루 1,000회뿐이고, 쿨다운과 제외 기록이 같은
   할당량을 두고 다툽니다.
3. **긴 요청은 스트리밍 엔드포인트로 옮기세요.** 첫 바이트 예산은 첫 바이트까지만 묶고 그
   뒤의 생성 시간은 세지 않습니다. 비스트리밍 예산은 업스트림이 답을 다 만들 때까지를 품어야
   하고, 두 형태의 플랫폼 쪽 거동이 같다는 보장도 없습니다.

## 모니터링과 유지보수

### 헬스 엔드포인트

`/health`는 토큰이 필요 없는 유일한 엔드포인트이며 두 형태 모두에 있습니다.

```bash
curl -s "$BASE/health"
```

`status`가 `ok`면 저장소를 읽고 쓸 수 있다는 뜻이고, `degraded`면 저장소 쪽에 문제가 있다는
뜻입니다(Docker에서는 대개 데이터 디렉터리에 쓰지 못하는 경우). Docker 형태에서는 이미지에
내장된 `HEALTHCHECK`가 바로 이걸 때리고, `docker compose ps`의 healthy/unhealthy가 거기서
나옵니다.

### 패널의 이벤트 보드

`ADMIN_TOKEN`을 설정하면 패널의 이벤트 보드가 게이트웨이가 스스로 남긴 진단 이벤트를
등급별로 보여 줍니다(로그인 실패, 토큰 충돌, 보충 실패, 예산 소진 등).
**로그를 대신하지는 못합니다**: 보관은 24시간이고 한 번의 폴링이 되짚는 키는 최대 48개입니다.
오래 남겨야 한다면 컨테이너 로그를 어딘가로 보내세요.

### 사용량 통계(기본값은 꺼짐)

일／시간／모델／프로토콜별 시계열은 **기본값이 꺼짐**이고, 그 "꺼짐"은 무비용입니다 ——
누적기를 만들지 않고 저장소 쓰기도 한 번도 일어나지 않습니다. 켜려면:

```env
# 선택: 패널 "사용량" 섹션의 Tier-2 시계열. 판정은 문자 그대로 true이고 1이나 yes는 꺼짐.
# 켜면 인스턴스당 하루 최대 13회 put(쓰기 할당량의 약 10.4%), 미기록 꼬리는 최대 2시간.
USAGE_STATS_ENABLED=true
```

켜기 전에 위 "할당량 계산"의 Tier-2 항목을 읽으세요. key 풀의 쿨다운/제외 기록과 같은 쓰기
할당량을 두고 다툽니다.

## 서비스 업그레이드

각 형태의 업그레이드 명령은 해당 절의 "업데이트"에 있습니다
([Cloudflare Worker](#cloudflare-worker-배포) / [Docker](#docker-배포)).
이 절에서는 그 두 명령 바깥에 있는, 두 형태에 공통인 이야기를 합니다.

### 업그레이드 전에

1. **먼저 저장소를 백업합니다.** key 풀과 설정은 사본이 하나뿐입니다. 아래 "백업과 복구" 참고.
2. **CHANGELOG를 한 번 봅니다.** 파괴적 변경은 거기 적힙니다. 여섯 개 README의 배지가 그곳을
   가리킵니다.
3. **업그레이드에 저장소 초기화는 필요 없습니다.** 저장된 레코드는 하위 호환이며 `pool:index`의
   `v` 필드는 오늘 기준 항상 `1`입니다.

### 업그레이드 후 확인할 것

1. `/health`가 `200`을 주고 `status`가 `ok`일 것.
2. 패널을(돌리고 있다면) 로그인할 수 있고 key 풀의 개수가 업그레이드 전과 같을 것.
3. 위 "검증"의 세 번째 명령을 한 번 돌려 실제로 업스트림까지 닿는지 확인할 것.

롤백: Docker는 이미지 tag를 이전 버전으로 고정하고 `docker compose up -d`를 다시 실행합니다.
Worker는 Cloudflare 대시보드의 Deployments에서 되돌리거나, `git checkout`으로 이전 tag로
돌아가 `npx wrangler deploy`를 다시 실행합니다.

## 백업과 복구

key 풀과 설정은 사본이 하나뿐이고 두 번째는 없습니다. **백업이란 저장소 자체를 뜨는
일입니다.**

### Docker

```bash
docker compose stop
cp -a ./data ./data.bak
docker compose start
```

한 번 멈추는 것은 쓰기 경합을 피하기 위해서입니다. `./data/store.json` 안에 전부 들어 있습니다:
key 레코드, `pool:index`, 그리고 저장소 쪽 설정. 복구는 디렉터리를 되돌려 놓고
`docker compose up -d` 하면 됩니다.

### Cloudflare Worker

```bash
npx wrangler kv key list --binding=POOL --remote
npx wrangler kv key get --binding=POOL "pool:index" --remote
```

`key:<id>`를 하나씩 꺼내 파일로 남기면 됩니다. 복구는 `npx wrangler kv key put`으로 하며,
아래 key 임포트와 같은 방식입니다.

> [!WARNING]
> 백업 파일에는 **평문 key와 평문 자격 증명**이 들어 있습니다(게이트웨이 토큰도, 두 메일함
> 채널의 API Key도 저장소 쪽 설정에 있습니다). 자격 증명으로 취급하세요: 저장소에 넣지 말고,
> 공개 오브젝트 스토리지에도 올리지 마세요.

## 보안 권장사항

- **`GATEWAY_TOKEN`과 `ADMIN_TOKEN`은 서로 다른 두 개여야 합니다.** 앞의 것은 **모든
  다운스트림 사용자**에게 나눠 주는 중계 토큰입니다. 그것을 패널 토큰으로 돌려쓰면 key 풀
  전체, 레지스트라 스위치, 등록 백엔드 주소까지 함께 넘기는 셈입니다.
- **패널은 TLS 뒤에 두고 신뢰하는 머신에서만 여세요.** 패널은 `ADMIN_TOKEN`을 브라우저의
  localStorage에 그대로 보관하며, 파생 토큰도 제품 내 폐기 경로도 없습니다. 12시간 뒤에 다시
  입력하게 하는 것은 창을 줄일 뿐 **폐기가 아닙니다**.
- **`TRUST_PROXY`는 게이트웨이가 정말로 프록시 뒤에 있을 때만 켜세요.** 일반 리버스 프록시
  뒤에서 켤 때는 그 프록시에서 `CF-Connecting-IP`를 떼어내세요. 그러지 않으면 공격자가 직접
  붙인 값이 프록시가 방금 쓴 `X-Forwarded-For`를 눌러 버립니다.
- **데이터 디렉터리, KV 네임스페이스, 백업 파일은 모두 자격 증명으로 취급하세요.** key도
  패널로 써 넣은 자격 증명도 전부 평문으로 저장되며, key 평문 저장과 같은 수위입니다.

최소한의 보안 기준 설정:

```env
# 필수: 클라이언트가 이 게이트웨이를 호출할 때 제시해야 하는 토큰. 다운스트림에 나눠 주는 값입니다.
GATEWAY_TOKEN=본인의 긴 랜덤 문자열로 교체

# 선택: 관리 패널 토큰. 설정하지 않으면 /admin 트리 전체가 등록되지 않아 401이 아니라 404가 옵니다.
# GATEWAY_TOKEN과 달라야 하고, 24자 이상이며 출력 가능한 ASCII만 씁니다.
ADMIN_TOKEN=또 다른 긴 랜덤 문자열로 교체

# 선택: 게이트웨이가 정말로 프록시 뒤에 있을 때만 1로 둡니다. Worker 형태가 여기에 해당합니다.
TRUST_PROXY=1
```
