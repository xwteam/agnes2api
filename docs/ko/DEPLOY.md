# 배포 가이드

agnes2api의 배포 대상은 하나뿐이며, 이 저장소의 코드로 만든 Docker 이미지를 `docker compose`로 돌립니다.

> [!NOTE]
> 상태는 전부 한 곳에만 있습니다 —— 마운트된 볼륨 위의 JSON 파일(`store.json`)입니다.
> 그 디렉터리를 백업해 두면 상태를 전부 백업한 것입니다.

## 환경 요구사항

길이 하나뿐이라 열도 하나입니다.

| 항목 | 요구사항 |
|------|----------|
| 커맨드라인 | Docker Engine 24+ 와 `docker compose` |
| 플랫폼 | 컨테이너를 돌릴 수 있는 머신 한 대 |
| 업스트림 | Agnes API key 최소 한 개, 다음 절 참고 |

> [!TIP]
> 그 밖에 설치할 것은 없습니다 —— 로컬 Node.js도, 빌드 툴체인도 필요 없습니다.
> `cp .env.example .env` 다음에 `docker compose up -d` 한 번으로 뜹니다.
## Agnes 자격 증명 준비

게이트웨이는 key를 만들어내지 않습니다. 여러분이 이미 가진 한 개 또는 여러 개의 Agnes API
key로 요청을 나눠 보낼 뿐입니다. 얻는 경로는 두 가지이고 **둘은 대등**하며, 주/보조를 정해
두지 않았습니다.

### 직접 발급받기

Agnes 플랫폼에서 계정을 만들고 콘솔에서 API key를 하나 발급해 복사해 둡니다.
이 경로는 한 번에 한 개만 주지만, 게이트웨이를 일단 띄우고 네 가지 프로토콜이 통하는지
확인하는 단계에는 그걸로 충분합니다.

### 레지스트라에게 자동 보충 맡기기

이 저장소에는 선택 사항인 레지스트라가 들어 있어 `TARGET_KEYS`를 목표로 풀을 자동으로
보충합니다. **기본값은 꺼짐**입니다(`REGISTRAR_ENABLED`를 설정하지 않으면 꺼진 상태).
동작 원리, 두 메일함 채널 중 무엇을 고를지, 한 라운드가 얼마나 걸릴 수 있는지는
[REGISTRAR.md](REGISTRAR.md)에 전부 적혀 있습니다.

> [!IMPORTANT]
> 어느 경로든 key는 `store.json`에 **평문**으로 저장됩니다.
> 데이터 디렉터리는 자격 증명으로 취급하세요.

## Docker 배포

### 사전 조건

> [!NOTE]
> 같은 디렉터리의 [README](README.md) 「`## ⚡ 빠른 배포`」 절에는 같은 세 명령이 짧은
> 형태로 있습니다. 이 절은 그 긴 형태입니다: 각 명령이 여러분에게 맡기는 판단을 펼쳐
> 씁니다. 첫 번째는 처음 띄우기 전에 반드시 정해 두어야 하는 토큰입니다.

저장소를 클론하고 환경 변수 파일을 준비합니다.

```bash
git clone https://github.com/xwteam/agnes2api.git
cd agnes2api
cp .env.example .env
```

**이미지를 쓰지 않고 소스에서 돌릴 때**: `pnpm dev:node`는 `node scripts/build-ui.mjs`로
시작해 빌드한 뒤 `dist/entry/node.js`를 띄웁니다. 맨손으로 `node dist/entry/node.js`를
띄워도 되지만, 패널은 마지막으로 생성된 그대로 남습니다 —— `admin-ui/`를 고쳤는데 아무
변화가 없다면 대개 이것이 이유입니다.

### 설정

`.env`를 편집해 최소한 `GATEWAY_TOKEN`을 설정합니다. 나머지 변수는 아래의
[환경 변수](#환경-변수) 표를 참고하세요.

`.env`의 최소 형태는 두 줄입니다. 나머지는 모두 기본값이 있으니 필요할 때 더하면 됩니다.

```env
# 필수: 클라이언트가 이 게이트웨이를 호출할 때 제시해야 하는 토큰. 다운스트림에 나눠 주는 값입니다.
GATEWAY_TOKEN=본인의 긴 랜덤 문자열로 교체

# 선택: 컨테이너 안의 리스닝 포트.
# docker-compose.yml은 이 값을 호스트 쪽에 공개하는 포트로도 씁니다.
PORT=8080
```

> [!CAUTION]
> **`DATA_DIR`는 docker-compose.yml의 볼륨 마운트와 묶여 있습니다. Docker 형태에서는 이것만
> 따로 바꾸지 마세요.** 그 줄 `./data:/app/data`는 하드코딩이고 `.env`의 `DATA_DIR`는 그
> 보간에 전혀 관여하지 않습니다. 그 줄을 그대로 두고 `DATA_DIR`만 다른 경로로 바꿔도 아무도
> 막지 않습니다: 컨테이너는 뜨고 `/health`는 `ok`를 주며 패널도 key 풀도 정상이고 등록기도
> 계속 채웁니다 —— 그동안 store.json은 **컨테이너 쓰기 계층**에 떨어집니다. 다음에 "업데이트"
> 대로 한 번 올리면 컨테이너가 재생성되면서 key 풀 전체, 발급된 외부용 API 키, 패널 설정이
> 함께 사라지고, 당신이 계속 백업해 온 `./data`는 처음부터 비어 있습니다.
> 데이터를 호스트의 어디에 둘지 바꾸려면 그 마운트 줄의 **왼쪽 절반**을 바꾸고, 오른쪽 절반을
> 바꾸려면 `DATA_DIR`도 같은 경로로 함께 바꿉니다. 기동할 때 entrypoint가 이것을 검사해서,
> 어떤 마운트 지점에도 얹혀 있지 않으면 컨테이너 로그에 "어떤 마운트 지점에도
> 얹혀 있지 않다"는 경고를 남깁니다 —— 이 연쇄에서 유일한 신호가 그 한 줄이고, `/health`는
> 데이터가 어디에 떨어졌는지 알려 주지 않습니다.

#### 데이터 디렉터리와 소유자: 컨테이너가 `./data`를 바꿉니다 (먼저 확인하세요)

컨테이너는 **root로 entrypoint에 진입**해 두 가지를 한 뒤 권한을 낮춥니다:

- `DATA_DIR`(기본 `/app/data`)의 소유자가 컨테이너 내 실행 사용자 `app`
  (**uid 100 / gid 101**)과 다를 때에만 그 디렉터리를 재귀적으로 `chown`합니다.
  소유자가 이미 일치하면 아무것도 바꾸지 않습니다.
- 그다음 `su-exec`로 권한을 낮추므로 **메인 프로세스(PID 1)는 root가 아니라 app**으로
  실행됩니다.

런타임에 해야 하는 이유는, 바인드 마운트에서는 호스트 디렉터리의 소유자가 이미지 빌드
시점의 `chown`을 덮어쓰기 때문입니다. 그러면 컨테이너 안의 app이 `store.json`에 쓸 수 없고,
이 실패는 조용합니다(모든 API가 `pool_empty`를 반환).

**부작용**: 바인드 마운트에서 바뀌는 것은 **호스트**의 파일입니다. `docker compose up -d`
이후 여러분의 `./data`와 그 안의 파일 소유자는 본인 uid에서 `100:101`로 바뀌며, 이후
호스트에서 읽고 쓰거나 백업하려면 `sudo`가 필요합니다. 원하지 않는다면 `--user`(또는
compose의 `user:`)로 비 root 실행을 지정하세요. 그러면 entrypoint는 chown을 전혀 하지
않으며, 데이터 디렉터리의 소유자와 쓰기 가능 여부는 직접 준비하게 됩니다.

같은 이유로 이미지에는 **`USER app`이 없습니다**. 기본 사용자는 root입니다
(`docker inspect --format '{{.Config.User}}' <image>`는 빈 값을 출력). 이는 Kubernetes에
영향을 줍니다: `runAsNonRoot: true`를 설정하고 `runAsUser`를 명시하지 않으면 kubelet이
컨테이너 기동을 거부합니다. 그런 배포에서는 `runAsUser: 100`, `runAsGroup: 101`(또는 원하는
uid)을 명시하고 볼륨 소유자를 직접 준비하세요 —— 비 root로 기동하면 entrypoint는
"chown 없이 그대로 실행" 분기를 탑니다.

안전 경계: `DATA_DIR`이 `/`나 최상위 시스템 디렉터리(`/etc`, `/usr` 등)로 설정되면
entrypoint는 그 위에서의 재귀 chown을 거부합니다(경고만 출력하고 기동은 계속). 컨테이너
파일 시스템 전체가 app 쓰기 가능해지는 것을 막기 위함입니다.

### 배포

컨테이너를 시작합니다.

```bash
docker compose up -d
```

**첫 이미지가 배포되기 전**(또는 fork 이후)에는 이 명령이 로컬 빌드로 폴백합니다 ——
`docker-compose.yml` 의 `build:` 블록이 그 역할을 합니다.

`docker-compose.yml`은 기본적으로 `8080` 포트를 게시하며(`.env`의
`PORT`로 재정의 가능), `./data`를 컨테이너 내부의 `/app/data`에
마운트합니다 —— `store.json`(key 풀 및 영속화된 설정)이 여기에
저장됩니다. 재시작/업그레이드 시에도 이 디렉터리를 반드시 유지하세요.
임포트된 key 풀의 유일한 사본입니다.

### 검증

컨테이너가 정상적으로 기동했는지 확인합니다.

```bash
curl http://localhost:8080/health
```

이미지에는 `HEALTHCHECK`가 내장되어 있어 Docker가 이를 기준으로 컨테이너
상태를 보고합니다. 데이터 디렉터리에 쓸 수 없으면 `/health`는 `status`가
`degraded`인 `503`을 반환하고 컨테이너는 unhealthy로 표시됩니다. 구체적인 원인은
컨테이너 로그를 확인하세요.

문제 해결에서 반복해서 쓰는 두 줄을 먼저 여기 적어 둡니다. 이 문서에서 이후에 나오는
"컨테이너 로그"는 모두 두 번째 줄을 가리킵니다.

```bash
docker compose ps                     # 떠 있는지, 건강한지
docker compose logs -f --tail=100     # 컨테이너 로그: entrypoint 경고도 admin.token_rejected도 여기
```

### 업데이트

```bash
docker compose pull
docker compose up -d
```

`docker compose pull`이 가져오는 것은 `.env`의 `IMAGE_TAG`가 가리키는 tag입니다(설정하지
않으면 `latest`). 이미지 전체 이름은 `ghcr.io/xwteam/agnes2api`이고, 사용할 수 있는 tag는
[GHCR packages 페이지](https://github.com/xwteam/agnes2api/pkgs/container/agnes2api)에 있습니다.
**업그레이드 = `IMAGE_TAG`를 올릴 버전으로 바꾸고 `docker compose up -d`, 롤백 = 되돌리기.**
tag를 고정해야 비로소 이 `.env`가 "지금 어느 버전이 도는가"에 답할 수 있습니다. `:latest`는
답하지 못합니다.

> [!IMPORTANT]
> **`.env`를 고쳤으면 `docker compose restart`가 아니라 `docker compose up -d`를 실행하세요.**
> 후자는 같은 컨테이너를 다시 시작할 뿐이고, 컨테이너의 환경은 **생성** 시점에 고정되므로
> `.env`를 바꿔도 1바이트도 달라지지 않습니다. `up -d`가 설정 변화를 감지해야 컨테이너를
> 재생성합니다. `ADMIN_TOKEN` 추가와 토큰 교체가 같은 함정이고, 후자가 더 고약합니다:
> 교체했다고 믿는데 옛 토큰이 그대로 살아 있습니다.

`./data`는 그대로이고 key 풀과 설정이 거기 있습니다. **업그레이드 전에 그 디렉터리를 백업하세요**
(아래 "백업과 복구" 참고). 임포트한 key 풀의 유일한 사본이며, 두 번째 사본은 없습니다.

## 환경 변수

| 변수 | 필수 여부 | 기본값 | 설명 |
|----|---------|------|----|
| `GATEWAY_TOKEN` | **예** | – | 클라이언트가 이 게이트웨이를 호출할 때 반드시 제시해야 하는 토큰. |
| `RESET_CONFIG` | 아니오 | – | 비상 탈출구: `1`로 두면 기동 시 저장소의 `config` 키를 **완전히 무시**하고(무시할 뿐 삭제하지는 않음) 환경 변수와 내장 기본값만 사용합니다. 언제 쓰는지, 쓰고 나서 무엇을 해야 하는지는 아래를 보세요. |
| `AGNES_BASE_URL` | 아니오 | `https://apihub.agnes-ai.com/v1` | 업스트림 Agnes API의 base URL. |
| `UPSTREAM_TIMEOUT_MS` | 아니오 | `8000` | **스트리밍** 응답과 비디오 폴링의 첫 바이트 타임아웃. 이 시간(밀리초) 안에 업스트림의 첫 바이트가 도착하지 않으면 호출을 중단. |
| `UPSTREAM_SYNC_TIMEOUT_MS` | 아니오 | `120000` | **동기** 엔드포인트의 전체 타임아웃 예산. "첫 바이트가 업스트림이 결과 전체를 계산한 뒤에야 도착하는" 요청에만 적용됨: 이미지 생성, 비디오 작업 생성, 그리고 모든 **비스트리밍** 대화. 아래 설명 참조. |
| `MAX_STRIKES` | 아니오 | `3` | 연속된 일시적 실패(타임아웃, 네트워크 오류, 업스트림 `5xx`)가 이 임계값에 도달하면 해당 key를 긴 쿨다운에 넣음. |
| `COOLDOWN_RATE_LIMIT_MS` | 아니오 | `60000` | 업스트림이 `429`를 반환한 뒤 해당 key에 적용되는 쿨다운 시간. |
| `COOLDOWN_PAYMENT_MS` | 아니오 | `3600000` | 업스트림이 `402`를 반환한 뒤 해당 key에 적용되는 쿨다운 시간. |
| `COOLDOWN_STRIKE_MS` | 아니오 | `1800000` | key의 일시적 실패가 `MAX_STRIKES`에 도달한 뒤의 쿨다운 시간. 만료되면 자동으로 복구됨. |
| `POOL_CACHE_TTL_MS` | 아니오 | `60000` | 각 프로세스가 key 풀 스냅숏을 메모리에 유지하는 시간. `0`이면 캐시를 끔. **저장소 읽기 횟수는 요청 수와 무관**하며 갱신 주기로만 결정됨. 대가는 아래를 참조. **인스턴스를 만들 때 한 번만** 읽습니다(`src/http/wire.ts`). 변경은 컨테이너를 다시 만든 뒤에 반영되며, **패널에서 바꿔도 즉시 반영되지 않습니다**. |
| `POOL_TOUCH_INTERVAL_MS` | 아니오 | `21600000` | key의 "마지막 사용 시각"을 최대 얼마 만에 한 번 저장할지. `0`이면 성공한 요청마다 저장. 표시 전용 필드로 스케줄링은 전혀 읽지 않으며, 같은 간격은 패널의 사용량 카운터에도 적용됨. 대가와 "카운터를 지우는 법"은 아래. **인스턴스를 만들 때 한 번만** 읽습니다(`src/http/wire.ts`). 변경은 컨테이너를 다시 만든 뒤에 반영되며, **패널에서 바꿔도 즉시 반영되지 않습니다**. |
| `USAGE_STATS_ENABLED` | 아니오 | `false` | 패널 "사용량" 섹션의 Tier-2 시계열(일／시간／모델／프로토콜별). **판정은 문자 그대로 `true`**이며 `1`이나 `yes`는 꺼짐으로 봅니다. **기본값은 꺼짐이고 그 "꺼짐"은 무비용**입니다. 켰을 때 무엇을 치르는지, 그리고 **수명이 짧은 인스턴스에서는 카운트가 늦는 게 아니라 사라진다**는 점은 아래를 보세요. app 빌드 시 한 번 읽으므로 변경은 컨테이너를 다시 만든 뒤에 적용됩니다. |
| `PORT` | 아니오 | `8080` | 컨테이너 안의 리스닝 포트. `docker-compose.yml`이 같은 번호를 호스트에도 공개함. |
| `DATA_DIR` | 아니오 | `/app/data` | 파일 저장소가 `store.json`을 쓰는 디렉터리. **이것만 따로 바꾸지 마세요**: compose 볼륨 마운트와 묶여 있습니다. 위의 "Docker 배포 → 설정" 참고. |
| `APIKEY_CACHE_TTL_MS` | 아니오 | `300000` | 외부용 API 키 표를 각 인스턴스가 캐시하는 시간. `0`이면 끔. 중지한 키가 같은 볼륨을 공유하는 다른 컨테이너에서 언제 실효되는지도 정합니다. 아래 참고. |

### 허용 범위와 "인스턴스 생성 시 한 번만 읽는" 두 가지 예외

위 표의 모든 변수는 `.env.example`에 한 줄씩 들어 있습니다. `cp .env.example .env` 후
필요한 항목만 고치면 됩니다. 그 파일의 주석은 분량이 제각각이라(대부분 한 줄, 일부는
십수 줄) 값의 범위와 대가는 이 표를 기준으로 하세요. 위의 수치형 변수는 모두 정수여야 하며,
`POOL_CACHE_TTL_MS`와 `POOL_TOUCH_INTERVAL_MS`는 하한이 `0`("끔"을 의미)이고 나머지는
모두 `0`보다 커야 합니다. 그렇지 않으면 게이트웨이가 기동을 거부합니다.

`POOL_CACHE_TTL_MS`와 `POOL_TOUCH_INTERVAL_MS`는 **app을 만들 때 한 번만** 읽습니다.
변경하려면 컨테이너를 다시 만들어야 하며, 다른 설정
항목처럼 요청마다 반영되지는 않습니다.

### `RESET_CONFIG`: 이 비상 탈출구를 언제 쓰나

> 실제 용도는 **패널에 저장된 설정을 통째로 우회하는 것**입니다. 환경 변수와 내장 기본값만으로
> 한 번 기동해 알려진 깨끗한 상태로 돌아갑니다. 다 쓰면 이 줄을 지우세요. 지우지 않으면 패널에서
> 저장한 설정이 영원히 적용되지 않습니다.

> [!WARNING]
> **"설정이 망가지면 이걸로 복구한다"고 생각하지 마세요.** 이제 저장된 값 때문에 게이트웨이가
> 기동하지 못하는 일은 거의 없습니다. 숫자가 잘못되면 **기본값으로 폴백**하고(패널에 저하로 표시됩니다),
> 등록기 쪽 문제는 **이번에 등록기만 시작하지 않을** 뿐 게이트웨이 전달은 평소대로입니다.
> 지금도 기동을 막을 수 있는 유일한 조건은 **게이트웨이 토큰이 양쪽 모두 없는 것**이며,
> `RESET_CONFIG=1`은 바로 그 저장된 토큰까지 무시합니다. **그대로 따르면 상황이 더 나빠집니다.**

### `POOL_CACHE_TTL_MS`의 대가

**저장소 읽기 횟수는 요청 수와 무관합니다** —— 스냅숏이 따뜻한 동안 전달 경로는 한 번도 읽지
않으므로, 이 손잡이로 사는 것은 "프로세스마다 `store.json`을 읽는 횟수가 줄어드는 것"이고
치르는 것은 "그 스냅숏이 얼마나 오래돼도 되는가"입니다.

> **이건 여러 프로세스가 볼륨 하나를 공유할 때만 의미가 있습니다**: 로드 밸런서 뒤에 여러
> 컨테이너, 또는 롤링 재시작으로 새 컨테이너와 옛 컨테이너가 함께 도는 경우입니다. 다른
> 프로세스가 판정한 쿨다운/제외는 최대 **이 값**만큼 늦게 보입니다. 기본값 60000이면 상한은
> **60**초입니다. 컨테이너가 하나면 이런 창 자체가 없습니다: 쿨다운을 판정한 쪽이 곧 그
> 스냅숏을 쥐고 있는 프로세스이기 때문입니다.

게다가 "늦게 보이는" 것만이 문제가 아님: 오래된 스냅숏 위에서 일어나는 스케줄링 관련 쓰기는
레코드 전체를 덮어써, 다른 프로세스가 그 창 안에서 막 기록한 `evicted` / `cooldownUntil`을
**지워버림**——그 판정을 처음부터 다시 해야 함.

### `POOL_TOUCH_INTERVAL_MS`의 대가와 "카운터를 지우는 법"

성공한 요청마다 저장한다는 것은, 아무도 스케줄링에 쓰지 않는 타임스탬프 하나 때문에
`store.json`을 매번 통째로 다시 쓴다는 뜻임. 그렇게 하지 않는 대가: "마지막 사용"의 정밀도가
이 간격까지 거칠어짐. 같은 간격은 패널의 사용량 카운터(요청 수 / 성공률)에도 적용됨.

> [!WARNING]
> **스토리지의 `stats`를 손으로 줄이면(예: 0으로 초기화) 패널에 잠깐 그 값이 보였다가 다시 옛
> 값으로 되돌아갈 수 있음**: 스냅숏은 TTL이 지나면 초기화된 레코드를 읽지만, 실행 중인
> 인스턴스는 자신이 저장한 기준값을 기억하고 다음 실제 저장 때 그 값을 다시 씀. 늦어도 해당
> 인스턴스가 회수된 뒤에는 완전히 일치함.

**카운터를 지우려면 repo를 거치는 정식 경로를 쓸 것**: `PATCH /admin/api/keys/:id` 에
`clearStats`. 이는 **이번 요청을 처리한 인스턴스**가 들고 있던 저장 기준값과 아직 저장하지
않은 증분을 함께 버리므로, **이번 초기화 이후에 시작된 요청**이 옛 값을 다시 쓰는 일은 없음.
다만 **초기화 시점에 이미 진행 중이던 요청**은 초기화 전 레코드를 들고 있어, 완료될 때 그 옛
값으로 기준값을 다시 만듦. 같은 볼륨을 쓰는 **다른** 컨테이너도 각자 자기 기준값을 갖고 있어
옛 값을 한 번 되돌려 쓸 수 있음.
**오늘은 API만 있고 패널에는 이 버튼이 없음.**

### `USAGE_STATS_ENABLED`: 켜면 무엇을 치르나

"꺼짐"은 무비용입니다: 메모리 누적기를 만들지 않고 저장소 쓰기도 한 번도 일어나지 않습니다.
켜면 인스턴스마다 한 기록 간격에 `store.json`의 샤드 하나를 다시 씁니다 ——
**기본 2시간 간격이면 하루 최대 13회**이고, 트래픽이 없는 간격에는 한 번도 쓰지 않습니다.
미기록 꼬리는 최대 2시간입니다. 이 스위치는 컨테이너를 다시 만든 뒤에 적용됩니다.

> [!WARNING]
> **"꼬리"는 "늦음"과 다릅니다**: 카운트는 먼저 인스턴스 메모리에 쌓이므로,
> **한 번의 기록 간격을 넘기지 못한 인스턴스는 쌓아둔 카운트를 그대로 가지고 사라집니다**.
> **늦게 반영되는 것이 아닙니다**.
> **컨테이너를 다시 만드는 순간이야말로 이 일이 가장 자주 벌어지는 상황입니다**: 환경 변수
> 하나를 바꾸려고 다시 만들기만 해도 최대 2시간치 카운트가 옛 프로세스와 함께 사라지고,
> 패널에서 그 구간은 "아무도 쓰지 않았다"와 구분되지 않습니다. 신경 쓰인다면
> `USAGE_FLUSH_INTERVAL_MS`를 줄이세요. 그 대가는 다음 절에 적혀 있습니다.

### `USAGE_FLUSH_INTERVAL_MS`: 무엇을 되살 수 있고 무엇은 남는가

"꼬리는 최대 2시간"을 보면 대개 기록 간격부터 줄이려 합니다. 이 형태에서는 그 길이 열려
있습니다: `USAGE_FLUSH_INTERVAL_MS`는 **1 이상의 정수라면 무엇이든** 받으므로 300000(5분)도
충분히 합리적입니다. 치르는 값은 인스턴스마다 한 간격에 샤드를 한 번 더 다시 쓰는 것,
사는 값은 "프로세스가 멈출 때 함께 사라지는 카운트"의 구간이 짧아지는 것입니다.

> [!WARNING]
> **이 값을 잘못 넣으면 첫 요청이 아니라 app 조립 시점에 거부됩니다**
> (`src/http/usage-sink.ts`): 정수가 아니거나 1 미만이면 프로세스가 이유를 찍고 종료합니다.
> **이 검사는 `USAGE_STATS_ENABLED`가 켜져 있는지와 무관하므로**(`src/http/wire.ts`가 무조건
> 계산합니다) 통계를 꺼도 **사라지지 않습니다** —— 값을 고치거나 그 줄을 지우세요.
> 컨테이너가 뜨지 않는다는 증상은 일부러 고른 것입니다: "통계 데이터가 조용히 틀어지는" 것보다
> 훨씬 알아채기 쉽기 때문입니다.

<details>
<summary><b>펼쳐 보기: "꼬리는 최대 2시간"이 약속하는 것과 하지 않는 것(네 가지)</b></summary>

① **꼬리는 "늦음"이 아니고, 두 증상은 사실 하나입니다**: 패널의 "오늘" 수치는 기록 간격
   하나만큼 오래됐을 수 있고, **다음 기록 전에 멈춘 인스턴스는 쌓아둔 카운트를 함께
   가져갑니다**. 시계는 인스턴스가 시작한 순간부터 도므로, 10분 돌고 다시 만들어진 컨테이너는
   한 건도 저장하지 못합니다. 사용량 숫자에 "≈"가 붙는 이유 중 하나이며 결함이 아닙니다.

② **이 형태에는 "하루 쓰기 예산"이라는 게이트가 없습니다.** 코드에는 그 게이트가
   있지만(`budgetPerDay`), 파일 저장소에는 지켜야 할 쓰기 할당량이 없어 게이트웨이는 그 자리를
   비워 둡니다: "소진"이 일어나지 않으니 "회복"도 "밀린 기록"도 없습니다. **"Docker에서는
   카운트를 잃지 않는다"로 읽지 마세요** —— 잃는 것은 ①의 꼬리입니다.

③ **같은 날짜에 대해 최대 2개 인스턴스분만 남고 그 이상은 서로 덮어씁니다.** 사용량 샤드는
   `usage:<UTC 날짜>:<슬롯>`으로 저장되고 **슬롯은 2개뿐**이며, 각 인스턴스는 자기 샤드 id로
   안정적으로 한쪽에 배정됩니다. 컨테이너 3개 이상이 볼륨 하나를 공유하면 같은 슬롯 안에서는
   나중에 쓴 쪽이 이깁니다. **"≈"가 붙는 또 하나의 이유**이고, 영향을 받는 것은 숫자의
   완전성뿐이며 전달에는 전혀 영향이 없습니다.

④ **세 개의 미디어 엔드포인트(이미지 생성, 비디오 작업 생성, 비디오 폴링)는 세지 않습니다.**
   네 가지 대화 프로토콜과 **같은** 업스트림 key를 쓰면서도 아무것도 기록하지 않으므로 ⇒
   패널의 "총 요청 수"는 실제 전달량보다 구조적으로 작게 나옵니다. 알려진 경계이지 결함이
   아닙니다. key 소비량은 key 풀 쪽에서 판단하세요.

</details>

### 저장소의 각 키를 맞춰 두는 대가

파일 저장소에는 읽기·쓰기·`list`·delete 어느 것에도 할당량이 없습니다 —— 한 번 다시 쓰는
대가는 자기 디스크에 한 번 쓰는 것뿐입니다. 그래도 알아 둘 값어치가 있는 것은 **한 번의
변경이 다른 쪽에 보이기까지 얼마나 걸리는가**입니다. 이 성질은 두 키에게는 보안 속성이고,
나머지에게는 장애를 볼 때의 함정입니다.

#### key 풀과 그 인덱스

게이트웨이는 풀 안의 id를 나열한 `pool:index`를 두어 전달 경로가 전수 탐색을 하지 않아도 되게
합니다. **두 개의 자가 치유 경로만은 전수 탐색을 피할 수 없고**, 둘 다 같은 내장 **10분**
백오프를 공유합니다(환경 변수가 아니라 고정 상수입니다):

- **빈 풀 재탐색** —— 인덱스는 읽히는데 살아 있는 레코드가 한 건도 읽히지 않을 때, 게이트웨이가
  한 번 훑어 "손으로 써 넣었지만 인덱스에 없는" 레코드를 찾아냅니다.
- **인덱스 결손 대비** —— `pool:index` 자체가 읽히지 않거나 깨졌을 때, 게이트웨이가 마찬가지로
  한 번 훑어 인덱스 재구성을 시도합니다.

풀이 비어 있고 **게다가** 그 탐색도 실패하면 게이트웨이는 `500`을 돌려주고 진짜 이유는 로그에
남깁니다. **`503 pool_empty`로 위장하지 않습니다** —— 그 시점에는 이 문서가 설명한 두 자가 치유
경로가 모두 끊겨 있으므로, "풀이 비었다"고 말하는 것은 사람을 엉뚱한 곳으로 보내는 일이기
때문입니다.

#### 외부용 API 키: 실효는 즉시가 아닙니다

패널이 발급한 키를 검증하려면 표 하나를 읽습니다. 각 인스턴스는 그것을
`APIKEY_CACHE_TTL_MS`(기본 5분) 동안 캐시합니다.

- **모든 클라이언트가 `GATEWAY_TOKEN`을 쓰는 배포는 이 표를 한 번도 읽지 않습니다.** 그 0은
  스위치가 아니라 **구조적**입니다: 마스터 토큰은 인증 1단계에서 비교가 끝나고, 그 경로에는
  이 표를 읽는 호출 지점 자체가 없습니다. 자격 증명을 전혀 싣지 않은 요청도 마찬가지로 0회라,
  스캐너가 지렛대로 삼을 수 없습니다.
- **발급 / 이름 변경 / 중지 / 삭제 / 비우기는 각각 표 전체를 한 번씩 다시 씁니다**. 그것도
  사람이 클릭할 때만입니다. 표에 키가 몇 개 있든 횟수는 달라지지 않습니다.

> [!IMPORTANT]
> **중지와 삭제는 즉시가 아닙니다. 이건 보안과 관련되므로 "곧 적용된다"로 읽지 마세요.**
> 그 요청을 처리한 인스턴스는 즉시 반영하지만, 같은 볼륨을 공유하는 다른 컨테이너는 최대
> `APIKEY_CACHE_TTL_MS` ⇒ 기본 약 **5분**이 걸립니다. 빠르게 하는 방법은 그 값을 줄이는 것뿐이고,
> 대가는 인스턴스마다 한 간격에 표를 한 번 더 읽는 것뿐입니다.

#### 패널에서 한 번 클릭하면 무엇이 쓰이나

전부 계량되지는 않지만, 클릭하기 전에 알아 둘 만한 형태가 둘 있습니다:

- **새 key를 M개 가져오면** 레코드 M개와 인덱스 한 번을 씁니다. **한 번에 최대 200개** ——
  넘으면 곧바로 `400`이고 **조용히 잘라내지 않습니다**. 큰 가져오기를 나눠도 싸지지 않습니다.
  인덱스는 배치마다 다시 쓰기 때문입니다.
- **같은 key를 다시 가져와도**("기존 key 상태 초기화"를 켜지 않았다면) **아무것도 쓰지
  않습니다**: 중복은 기본적으로 건너뛰고 덮어쓰지 않으므로 목록을 통째로 다시 붙여넣어도
  안전합니다.
- **N개 일괄 삭제**는 인덱스를 **한 번만** 다시 씁니다(N번이 아닙니다). **key 풀 비우기**도
  같은 규칙입니다.
- **key 하나 수정**(중지 / 사용 / 메모 / 쿨다운 해제 / strikes 초기화 / 제외 해제 /
  사용량 카운터 초기화)는 **무엇을 바꾸든 읽기 한 번, 쓰기 한 번**입니다: 모두 같은
  핸들러의 같은 한 번의 저장을 지나고, 사용량 카운터 초기화는 여분의 읽기도 쓰기도 하지
  않습니다(지우는 것은 메모리 안의 저장 기준값입니다).

  > [!IMPORTANT]
  > **괄호 안 마지막 항목이 여기서 유일하게 "패널에서 누를 수 없는" 것입니다**: 사용량
  > 카운터 초기화는 **오늘은 API만 있고 패널에 이 버튼이 없습니다**(위
  > `POOL_TOUCH_INTERVAL_MS` 행과 같습니다). 이 열거는 핸들러가 아는 모든 동작이지 패널
  > 버튼 목록이 아닙니다. 다른 경로가 더 비싸다고 오해하지 않도록 적어 둡니다.
- **"지금 보충"은 패널에서 유일하게 하루 상한이 있는 동작**입니다 —— 하루 최대 **24**회(네 번째
  가드레일, [REGISTRAR.md](REGISTRAR.md) 참고). 이 게이트가 지키는 것은 임시 메일함 쿼터와
  업스트림 플랫폼이지 저장소 예산이 아닙니다.
- **설정 저장**은 `config` 한 건을 다시 쓰고, **검증에 실패한 저장은 1바이트도 쓰지 않습니다**.
- **위험 구역의 두 버튼**: 설정 초기화(`/admin/api/config/reset`)는 같은 한 건을 다시 쓰고,
  key 풀 비우기(`/admin/api/keys/purge`)는 모든 레코드를 지우고 인덱스를 **한 번만** 다시 씁니다.

같은 이유로 읽기 팬아웃도 둘 알아 둘 값어치가 있습니다:

- **패널 「사용량」의 `30d` 단**은 한 요청에서 `30 × 2`개의 샤드
  (`USAGE_DAY_RETAIN × USAGE_SLOTS`)를 읽습니다. **이 팬아웃을 이 저장소는 실제 환경에서
  측정한 적이 없습니다.** 그래서 여기서 약속하는 것은 **정직하게 실패한다**는 것뿐입니다:
  도중에 실패하면 `days` 계열 전체가 `null`로 돌아오고 `note`는 `read_failed`가 됩니다
  —— 읽은 몇 조각을 완전한 그림인 것처럼 넘기지 않습니다.
- **플레이그라운드의 비디오 한 작업은 업스트림 요청 최대 `1 + 60`회**(생성 1회 + 최대
  `VIDEO_POLL_MAX_ATTEMPTS`회 폴링)입니다. 이것이 곱하는 것은 **업스트림** 쿼터와 key의
  사용 카운트이지, 자기 디스크 위의 무엇이 아닙니다.

### 관리 패널 관련 변수(기본값은 비활성화)

| 변수 | 필수 | 기본값 | 설명 |
|----|----|------|----|
| `ADMIN_TOKEN` | 아니오 | 없음(패널 비활성화) | 관리 엔드포인트의 토큰. **`GATEWAY_TOKEN`과 달라야 하며**, 최소 24자 이상이어야 하고, **앞뒤에 공백이 없어야** 하며, **출력 가능한 ASCII(0x20–0x7E)로만** 구성되어야 합니다. 문자 집합·길이 하한·게이트웨이 토큰과 달라야 한다는 세 규칙의 이유와, 규칙 위반의 종류에 따라 무엇이 일어나는지는 아래에 있습니다. |
| `TRUST_PROXY` | 아니오 | 미설정(**어떤** 전달 헤더도 신뢰하지 않음) | 게이트웨이가 실제로 프록시(CDN, 또는 컨테이너 앞단의 nginx / Caddy / Traefik) 뒤에 있을 때**만** `1`로 설정하세요. 로그인 실패 이벤트의 클라이언트 IP를 어디에서 가져올지 결정합니다. 자세한 내용은 아래. |

**설정하지 않으면 관리 패널만 사용할 수 없을 뿐, 게이트웨이 전달은 정상 동작합니다.** 이때
`/admin/...` 요청은 **`401`이 아니라 `404`**를 받습니다. 트리 자체가 등록되지 않으므로 "여기에
관리 화면이 있다"는 사실조차 노출되지 않습니다. 레지스트라가 기본 비활성화인 것과 같은 원칙으로,
`ADMIN_TOKEN`이 없거나 잘못되었다고 해서 게이트웨이 전달이 멈춰서는 안 됩니다.

두 줄 모두 다른 설정과 같은 `.env`에 씁니다:

```env
# 선택: 관리 패널 토큰. 설정하지 않으면 /admin 트리 자체가 등록되지 않습니다.
# GATEWAY_TOKEN과 달라야 하고, 24자 이상, 출력 가능한 ASCII만.
ADMIN_TOKEN=다른-긴-무작위-문자열로-바꾸세요

# 선택: 클라이언트 주소를 바꿔 쓰는 프록시 뒤에 컨테이너가 있을 때만 1로.
# 직접 노출된 배포에서는 설정하지 마세요.
TRUST_PROXY=1
```

#### `ADMIN_TOKEN`의 세 가지 하드 룰

**"규칙 위반"은 결과가 전혀 다른 두 가지입니다. 한 문장으로 묶지 마세요.** 미설정이거나
토큰 자체가 규칙에 어긋나면(앞뒤 공백 / 출력 불가 ASCII / 24자 미만) `/admin` 트리 전체가
등록되지 않고 로그에는 `admin.token_rejected`가 남습니다. 규칙에는 맞지만 실효
`GATEWAY_TOKEN`과 같으면 트리는 **정상 등록**되어 패널 자체는 열리고, 관리 엔드포인트만
매번 `503`을 돌려주며 로그에는 `admin.token_conflict`가 남습니다(이 규칙은 기동 시가 아니라
관리 요청마다 다시 판정합니다).

**앞뒤에 공백이 있으면 안 됩니다**: HTTP는 헤더 값의 앞뒤 공백을 제거하지만 환경 변수는 그대로
유지하므로, 공백이 붙은 토큰은 어떤 클라이언트도 보낼 수 없습니다.

##### 왜 출력 가능한 ASCII만 허용하는가

또한 토큰은 **출력 가능한 ASCII(0x20–0x7E)로만** 구성되어야 합니다. 이 제한에는 성격이 다른 세
가지 이유가 있습니다:

1. U+00FF를 넘는 문자(한자, 이모지, 폭 없는 공백)와 줄바꿈·NUL은 헤더 값을 설정할 때 `fetch`가
   **예외를 던집니다** — 요청 자체가 나가지 않으므로 200을 반환하지만 결코 들어갈 수 없는 패널이
   만들어지고, 서버에는 `admin.login_failed` 한 줄조차 남지 않습니다.
2. **TAB을 제외한** 그 밖의 제어 문자(`0x01–0x08`, `0x0B`, `0x0C`, `0x0E–0x1F`, `0x7F` — 총 29개)는
   브라우저가 보낼 수 있지만 HTTP 파서가 `400`으로 거부합니다.
3. **TAB(`0x09`)**과 `é` / `£` / 줄바꿈 없는 공백 같은 `0x80–0xFF` 바이트는 **실제로 전송되고
   동작합니다** — 이를 거부하는 것은 물리적 제약이 아니라 **저희 쪽의 견고성 절충**이며,
   **둘의 이유는 서로 다릅니다**. TAB은 **눈에 보이지 않는 문자**라 `.env`나 시크릿에 붙여넣어도
   아무도 알아채지 못합니다(앞뒤 공백과 같은 종류의 진단 가능성 문제지만, 그쪽은 물리적이고
   이쪽은 절충입니다). `0x80–0xFF`는 대신 인코딩 문제입니다: 환경 변수는 UTF-8로, 헤더 값은
   Latin-1로 해석되며 그 구간에서 둘이 일치한다는 보장은 명세에 없습니다.
   또한 RFC 9110은 이 구간을 폐기 예정으로 표시했습니다.

ASCII 전용 토큰을 사용하세요. **중간의 공백은 허용됩니다**——`correct horse battery staple` 같은
패스프레이즈는 문제없이 전송되고 도달하며, 24자 하한 아래에서는 무작위 문자열보다 오히려 다루기
쉬운 경우가 많습니다. 앞뒤 공백은 위의 규칙이 담당합니다.

##### 24자 하한이 있는 이유

**24자 하한이 있는 이유.** 이 게이트웨이에는 **로그인 속도 제한이 전혀 없습니다** —— IP 단위도,
토큰 단위도, 인스턴스 단위도 없습니다. 이를 구현하려면
저장소에 카운트 윈도를 만들어야 하는데, 그것은 인증되지 않은 호출자에게 쓰기를 일으킬 지렛대를 쥐여 주는 일이며
공격면이 "비밀번호 추측"에서 "키 풀 상태 기록 마비"까지 넓어집니다. 따라서 토큰 엔트로피가 유일한
방어선이고, 이 하한은 권고값이 아닙니다. 하한 미만이면 패널이 활성화되지 않고 컨테이너 로그에
`admin.token_rejected`가 남습니다.

##### `GATEWAY_TOKEN`과 달라야 하는 이유

**`GATEWAY_TOKEN`과 달라야 하는 이유.** `GATEWAY_TOKEN`은 **모든 다운스트림 사용자**에게 나눠 주는
중계 토큰입니다. 이를 패널 토큰으로 재사용하면, 중계 토큰을 가진 누구나 키 풀 전체를 읽고,
레지스트라를 끄고, 등록 백엔드를 자기 서버로 바꿀 수 있습니다. 그 이후 생성되는 모든 계정의
메일 주소·비밀번호·인증 코드가 그에게 넘어갑니다.

##### 충돌은 어떻게 드러나고 어떻게 처리하는가

이 규칙은 **관리 요청마다 다시 검사할 뿐, 시작 시에는 막지 않습니다.** 둘이 같으면 — 예를 들어
`store.json` 직접 편집으로 `gatewayToken`을 손으로 바꾼 경우 — 관리
엔드포인트는 **`503`을 반환**하고 error 수준으로 `admin.token_conflict`가 기록됩니다(시작 시점에
이미 충돌하고 있다면 시작 로그에도 같은 줄이 남아 원인을 바로 알 수 있습니다).
**게이트웨이 전달은 영향을 받지 않습니다.**

**충돌이 일어난 시점부터 `ADMIN_TOKEN`은 유출된 것으로 취급해야 합니다. 복구 방법은 하나뿐,
완전히 새로운 값으로 교체하는 것입니다.** `.env`를 고친 뒤 `docker compose up -d`로
컨테이너를 새 값과 함께 다시 만드세요.
**저장소의 `gatewayToken`만 되돌리고 끝내지 마십시오.** 그렇게 해도 관리 엔드포인트는 바로
복구되지만(설정 캐시가 다음에 갱신되는 시점에 적용되며 **재시작이 필요 없습니다**),
그것이 되찾아 주는 것은 가용성이지 보안이 아닙니다. 충돌하던 동안 관리 토큰과 게이트웨이
토큰은 같은 값이었고, 게이트웨이 토큰은 **모든 다운스트림 사용자**에게 나눠 주는 값입니다 —
이미 가지고 있는 사람(또는 앞으로 받게 될 사람)은 그대로 관리 화면을 열 수 있습니다.
가용성을 먼저 되찾기 위해 `gatewayToken`을 되돌리는 것은 괜찮지만, 그 뒤에 **반드시
`ADMIN_TOKEN`을 교체**해야 합니다. 두 단계를 모두 마쳐야 대응이 끝난 것입니다.

##### 왜 이 항목만 시작 시점에 막지 않는가

**왜 이 규칙만 시작 시에 막지 않는가.** `gatewayToken`은 운영 중에 바뀔 수 있는데 시작 시점의
판정에는 두 번째 평가 기회가 없습니다. 거기서 `/admin` 트리 전체를 등록하지 않게 하면, 충돌
중에 기동한 컨테이너는 모두 **영구히 `404`**가 되어
설정을 되돌려도 낫지 않고 한 번 더 재시작하는 수밖에 없습니다. 반면 충돌 전에 기동한 것은 `503`에
그치고 값을 되돌리면 즉시 복구됩니다. 같은 설정, 같은 순간에 두 가지 답이 존재하게 되고, 위의
"재시작이 필요 없습니다"라는 문장이 반쯤 거짓이 됩니다. `ADMIN_TOKEN` 자체에 관한 세 규칙
(앞뒤 공백, 보낼 수 없는 문자, 최소 길이)은 입력이 환경 변수뿐이라 운영 중에 바뀌지 않으므로 계속 시작 시에
막으며, 실패 형태도 `404` 그대로입니다.

##### 교체 방법과 유출 시 대처

`ADMIN_TOKEN`은 **환경 변수에서만 읽고 저장소에서는 읽지 않습니다.** 패널이 자기 키를 스스로
교체할 수 없습니다. 교체 방법은 `.env`를 수정한 뒤 `docker compose up -d`입니다 ——
컨테이너의 환경은 생성 시점에 고정되므로 `docker compose restart`로는 안 됩니다.

**관리 토큰 유출 = `ADMIN_TOKEN` 유출입니다.** 패널은 이 값을 브라우저의 localStorage에 그대로
저장합니다. 파생 토큰도 없고 제품 안에 폐기 경로도 없습니다. 폐기하는 방법은 하나뿐입니다:
`.env`의 값을 바꾼 뒤 컨테이너를 다시 만드는 것입니다.
패널은 12시간 뒤에 토큰을 다시 입력하도록 요구하지만, 그것은 그 localStorage 값이 쓰일 수 있는
기간을 줄일 뿐 **폐기가 아닙니다**. 패널은 TLS 뒤에 두고, 신뢰하는 기기에서만 여세요.

**이 상한이 할 수 없는 일도 분명히 밝힙니다.** 패널의 CSP는 `connect-src 'self'`로 토큰을 외부
도메인으로 `fetch`하는 것을, `form-action 'none'`으로 폼을 통한 유출을 막습니다. 하지만
`location.href = "https://…?k=" + token` 같은 **내비게이션을 통한 유출**은 막지 못합니다
— CSP에는 이를 막을 지시어가 더 이상 없습니다(`navigate-to`는 표준에서 제거되었습니다).
진짜 해법은 서버가 발급하는 **폐기 가능한 파생 토큰**이지만, 그것은 서버가 세션을 저장해야 하고
"`ADMIN_TOKEN`은 환경 변수에서만 읽는다"는 설계 제약과 충돌하므로 이후 릴리스로 미룹니다.

#### `TRUST_PROXY`는 클라이언트 IP를 어디서 가져올지 정한다

설정하면 로그인 실패 이벤트에 기록되는 클라이언트 IP는 `CF-Connecting-IP`에서 오고, 없을 때만
`X-Forwarded-For`의 첫 구간으로 폴백합니다.

**`TRUST_PROXY`는 보안 스위치이므로 기본값이 꺼짐입니다.** 이 값이 결정하는 클라이언트 IP는
`admin.login_failed` 이벤트에 기록되므로, 클라이언트가 보낸 헤더를 무조건 신뢰하면 누구나 무차별 대입
흔적을 임의의 IP에 뒤집어씌울 수 있습니다.

**꺼진 상태에서는 어떤 전달 헤더도 신뢰하지 않으며 이 필드는 일률적으로 `null`로 기록됩니다 —
`CF-Connecting-IP`도 예외가 아닙니다.** 이 헤더는 흔히 "플랫폼이 주입하므로 위조할 수 없다"고
설명되지만, 그 성질은 **요청이 실제로 Cloudflare를 통과할 때만** 성립합니다. Node/Docker를 직접
노출한 구성에서는 이를 덮어쓰는 것이 아무것도 없으므로, 클라이언트가 스스로
`CF-Connecting-IP: 1.2.3.4`를 보내면 그대로 믿게 됩니다 — 그리고 직접 노출은 Docker 배포의 기본
형태입니다.

**켜진 상태에서는 `CF-Connecting-IP`가 우선이고 `X-Forwarded-For`는 폴백일 뿐입니다.** 두 헤더는
위조 가능성이 근본적으로 다릅니다.

- `CF-Connecting-IP`는 Cloudflare 엣지가 기록하며, 클라이언트가 보낸 동일 이름 헤더를 **덮어씁니다** —
  요청이 실제로 Cloudflare를 통과하는 한 위조할 수 없습니다.
- `X-Forwarded-For`는 어떤 중간 장비든 덧붙일 수 있는 체인이고 클라이언트가 가짜를 보낼 수도 있어,
  어디까지 믿을 수 있는지는 전적으로 프록시 구성에 달려 있습니다.

##### 두 가지 토폴로지별 설정 방법

**오리진 앞단에 Cloudflare가 있다면 `TRUST_PROXY=1`을 설정하세요.** Cloudflare는 요청마다
`CF-Connecting-IP`를 다시 쓰므로 그것이 권위 있는 값입니다. 이 형태에서 `X-Forwarded-For`를
우선하는 것은 잘못이며, 그 체인에는 클라이언트가 채워 넣은 값이 들어 있을 수 있습니다. 스위치를
설정하지 않으면 이 필드는 그냥 `null`로 기록됩니다. **오리진에 직접 닿을 수 없게 된 뒤에
켜세요** —— 그렇지 않으면 CDN을 우회한 클라이언트가 헤더를 스스로 붙여 옵니다.

**범용 리버스 프록시(nginx / Caddy / Traefik) 뒤에서 `TRUST_PROXY=1`을 켤 때는 프록시에서
`CF-Connecting-IP`를 제거하세요.** 그런 구성에서는 이 헤더를 덮어쓰는 것이 아무것도 없는데,
게이트웨이는 "Cloudflare가 앞단에 있다"는 전제로 이를 우선하므로 공격자가 직접 붙인 헤더가
프록시가 방금 쓴 `X-Forwarded-For`를 **이깁니다**. nginx는 한 줄이면 됩니다:

```nginx
proxy_set_header CF-Connecting-IP "";
```

Caddy는 `header_up CF-Connecting-IP ""`, Traefik은 미들웨어의 `customRequestHeaders`를 씁니다.

##### 형태 검사, 얻지 못하면 정직하게 `null`

**두 헤더 모두 먼저 형태 검사를 거칩니다**: 점 표기 IPv4와 IPv6 형태(16진수, 콜론, `::ffff:`
매핑 안의 점)만 이벤트에 들어가고, 그 외에는 일률적으로 `null`로 기록됩니다. 이것은 인증
방어선이 아니며(이 값의 소비 지점은 저장소 전체에서 로그인 실패 이벤트 한 곳뿐입니다),
인증되지 않은 호출자가 감사 필드에 임의의 텍스트를 써 넣지 못하게 하려는 것입니다. 관리
패널의 이벤트 영역이 이 필드로 필터링하고 표시하기 때문입니다.

쓸 수 있는 값이 하나도 없으면 이 필드는 정직하게 `null`로 기록됩니다 — **`"unknown"` 같은 가짜 값은
절대 만들지 않습니다.** 실재하는 출처로 오해되기 때문입니다.

### 설정 페이지에서 바꿀 수 있는 것

이 항목들은 카드 세 장에 나뉩니다: **인증 키**와 **업스트림 및 쿨다운**은 **설정**
페이지에, **등록기**(완전히 동등한 두 메일박스 채널 서브카드와 「고급」 접기 영역 포함)는
**레지스트라** 보드의 「설정」 탭에 있습니다.
세 장 모두 쓰기 대상은 **저장소의 `config` 키**이며 환경 변수가 아닙니다.

**각 항목에는 하나가 아니라 세 개의 값이 표시됩니다.** 「저장값 X · 환경 변수 Y · 실효값 Z」
한 줄이 「내가 저장한 것」 「배포 쪽이 준 것」 「게이트웨이가 실제로 쓰는 것」을 분리해 보여 줍니다.
우선순위는 항상 **환경 변수 > 저장소 > 내장값** 입니다.

#### 환경 변수로 잠긴 항목은 아예 수정할 수 없습니다

**환경 변수로 잠긴 항목은 패널에서 바꿔도 반영되지 않으므로, 패널은 아예 편집을 막습니다.**
해당 입력란은 비활성화되고 어떤 환경 변수인지와 배포 쪽에서 바꿔야 한다는 설명이 붙습니다.
`PUT /admin/api/config` 는 그런 항목에 대해 `400 locked_by_env` 를 돌려주고 **저장소에 아무것도
쓰지 않습니다**: 써 버리면 「저장 성공, 실효값은 그대로」가 되어 운영자는 캐시 탓이라 여기고
두 주기를 헛되이 기다리게 됩니다.

> [!IMPORTANT]
> **등록기 계열(`REGISTRAR_ENABLED` / `REGISTRAR_CHANNEL`(호환 별칭 포함) /
> `TARGET_KEYS` / `MINT_BATCH` / `TEND_INTERVAL_MS` / `CODE_TIMEOUT_MS` / `MINT_DELAY_MIN_MS` /
> `MINT_DELAY_MAX_MS` / `MAX_DOMAIN_ATTEMPTS` / `REGISTRAR_TOKEN_NAME` / `AGNES_PLATFORM_URL` /
> `YYDS_BASE_URL` / `YYDS_API_KEY` / `MOEMAIL_BASE_URL` / `MOEMAIL_API_KEY`)도 이 잠금 표에
> 들어갔습니다.** 그 전에는 없었습니다: `docker-compose.yml` 에 `TARGET_KEYS=30` 이 있는데
> 패널에서 20으로 바꾸면 저장은 성공하지만 실효값은 계속 30이었고, **재시작해도 고쳐지지 않으며**
> 패널에는 아무 안내도 없었습니다.

#### 자격 증명은 쓰기 전용

**자격 증명은 쓰기 전용입니다.** 게이트웨이 토큰과 두 채널의 API 키는 **평문으로 절대
반환하지 않습니다**. 반환하는 것은 「설정 여부」와 **마지막 4자리**뿐입니다(5자 미만이면 그 4자리도
주지 않습니다 — 그건 전부를 보여 주는 것이니까요). 따라서:

- 입력란은 항상 비어 있고, 플레이스홀더에는 **비워 두면 변경되지 않습니다**라고 표시됩니다;
- 저장할 때 이 칸들이 **없거나 비어 있으면 = 바꾸지 않음**(지우기가 아닙니다). 비움을 지우기로
  구현하면 운영자가 설정 페이지를 한 번 저장하는 것만으로 게이트웨이 토큰이 지워지고, 게다가
  **현재 프로세스는 마지막 정상 스냅숏으로 계속 동작**하므로 다음 재시작 전까지는 이상이 보이지 않습니다;
- 지우기는 확인 대화상자가 붙은 전용 「지우기」 버튼으로만 가능합니다.

##### 패널에서 쓴 자격 증명은 어떻게 저장되는가

> [!WARNING]
> **패널에서 쓴 자격 증명은 `store.json` 에 평문으로 저장됩니다.** 「키 평문 저장」과
> 같은 수준입니다. 여기에 입력하는 값이 암호화된 secret이라고 생각하지 마세요.
> 데이터 디렉터리는 자격 증명으로 취급하세요.

> [!WARNING]
> **환경 변수에도 `GATEWAY_TOKEN` 이 없는 상태에서 게이트웨이 토큰을 지우면**, 현재 프로세스는
> 계속 동작하지만 **다음 재시작 때 기동에 실패합니다.** 패널이 그 자리에서 붉은
> 안내로 알려 줍니다. 같은 페이지에서 즉시 새 게이트웨이 토큰을 설정해 복구하세요. **환경 변수가 이 값을 제공하는 경우 지우기는 안전합니다**: 저장소의 사본만 사라지고 실효값은 환경 변수로 폴백하여 그대로입니다. 패널은 이 두 상태에서 서로 다른 문구를 보여 주며, 판단을 사용자에게 떠넘기지 않습니다.

#### "고급" 영역의 등록 백엔드 주소

> [!WARNING]
> **「고급」 접기 영역 안의 가입 백엔드 URL(`AGNES_PLATFORM_URL`)은 평범한 설정 항목이 아닙니다.**
> 이것은 **모든 자동 가입의 전송 대상**입니다: 다른 서버로 바꾸면 그 서버가 각 가입에 쓰이는
> 메일 주소·비밀번호·인증 코드를 받게 됩니다. 그래서 접기 영역 안에 두고, 붉은 경고를 붙이고,
> 메인 「저장」과 함께 가지 않는 전용 확인 버튼을 둡니다.

#### 저장 응답과 전파에 걸리는 시간

**저장 후 패널은 「저장되어 적용되었습니다」라고 말하지 않습니다.** 실효값을 **다시 읽어**
실제로 바뀐 항목을 강조하고, **다른 복제본이 변경을 보기까지 최대 얼마나 걸리는지**를
명시합니다: 설정 홀더는 최소 **30**초에 한 번만 갱신하므로 그것이 상한입니다.
이 인스턴스는 즉시입니다(저장 시 로컬 캐시를 무효화합니다). 다른 인스턴스는 그렇지 않습니다.
**패널 문구에 「즉시 적용」이라고 써서는 안 됩니다.**

### 레지스트라 관련 변수(선택 사항, 기본값은 비활성화)

레지스트라는 선택적인 자동 키 풀 보충 구성 요소로, 기본값은 비활성화이며 게이트웨이의
핵심 전달 기능에는 영향을 주지 않습니다. 아래는 변수 빠른 참조용 표일 뿐이며, 동작
원리, 두 메일함 채널을 고르는 방법, Cloudflare Cron의 월클록 상한 등 전체 설명은
[REGISTRAR.md](REGISTRAR.md)를 참고하세요.

| 변수 | 필수 여부 | 기본값 | 설명 |
|----|---------|------|----|
| `REGISTRAR_ENABLED` | 아니오 | `false` | 마스터 스위치. `true`여야 레지스트라가 활성화됨. |
| `REGISTRAR_CHANNEL` | 활성화 시 필수 | 없음 | 레지스트라가 사용할 채널, `yyds` 또는 `moemail`. 둘 중 하나만 고르며 기본값 없음. |
| `TARGET_KEYS` | 아니오 | `20` | 목표로 하는 사용 가능 key 수. |
| `MINT_BATCH` | 아니오 | `5` | 한 라운드에서 발급할 key의 최대 개수. |
| `TEND_INTERVAL_MS` | 아니오 | `1800000` | 보충 라운드를 도는 간격. 같은 타이머가 `pool:index` 대조도 하므로 레지스트라가 꺼져 있어도 계속 돕니다. |
| `CODE_TIMEOUT_MS` | 아니오 | `120000` | 인증 코드를 기다리는 타임아웃. |
| `MINT_DELAY_MIN_MS` / `MINT_DELAY_MAX_MS` | 아니오 | `60000` / `90000` | 발급 시도 사이의 무작위 대기 시간. 하한은 실측값이며(이보다 짧으면 업스트림 앞단 속도 제한이 끼어듭니다), 상한은 지터 여유일 뿐입니다. |
| `MAX_DOMAIN_ATTEMPTS` | 아니오 | `1` | 한 번의 발급 시도에서 시도할 도메인의 최대 개수. 등록기가 도메인 판정을 기억해 재사용하므로 정상 상태에서는 1이면 충분합니다. **키우면 라운드마다 소모하는 속도 제한 여유가 그만큼 늘어납니다**. |
| `REGISTRAR_TOKEN_NAME` | 아니오 | `auto` | 발급된 key가 Agnes 대시보드에 표시되는 이름. |
| `AGNES_PLATFORM_URL` | 아니오 | `https://platform-backend.agnes-ai.com` | 등록에 사용하는 Agnes 플랫폼 백엔드. |
| `YYDS_BASE_URL` / `YYDS_API_KEY` | 아니오 / 채널이 yyds일 때 필수 | `https://maliapi.215.im` / 공백 | YYDS Mail 채널 자격 증명. |
| `MOEMAIL_BASE_URL` / `MOEMAIL_API_KEY` | 채널이 moemail일 때 필수 | 공백 / 공백 | MoeMail 채널 자격 증명(자체 호스팅, 기본 주소 없음). |

> [!NOTE]
> **폐기된 옛 이름 두 개는 의도적으로 위 표에 넣지 않았습니다.**
> `REGISTRAR_PRIMARY`는 `REGISTRAR_CHANNEL`의 **호환 별칭**입니다(우선순위가 낮고, 사용
> 중이면 패널 상단에 알림이 뜨며 해당 항목이 비활성화되는 것은 동일합니다).
> `REGISTRAR_FALLBACK`은 **더 이상 경로 선택에 관여하지 않으며**, 패널에서 "이 채널은
> 폐기되었다"고 이름을 짚어 주기 위해 한 번만 읽힙니다. 두 옛 이름 모두 업그레이드 중인
> 배포를 멈추게 하지 않지만, `.env.example`에는 더 이상 선언하지 않습니다 —— 새 배포는
> 새 이름을 쓰세요.

#### 이 15개 변수에 잘못된 값을 썼을 때

> [!WARNING]
> **이 15개 변수에 잘못된 값을 써도 더 이상 컨테이너가 뜨지 못하는 일은 없습니다.**
> 숫자형(`TARGET_KEYS=abc`, `MINT_BATCH=0` 등)은 **위 표의 기본값으로 폴백**하고,
> 패널에 저하를 한 번 보고하며 이벤트 섹션에 `config.invalid`를 한 건 남깁니다.
> 채널·자격 증명 쪽 실수(채널 이름 오타, 등록기를 켜고도 채널 미선택, 선택한 채널의
> API 키 누락)는 **이번에 등록기만 시작하지 않을** 뿐, 게이트웨이 전달은 평소대로입니다.
>
> **이것은 능력 저하입니다. 분명히 적습니다**: 예전에는 배포 오타로 컨테이너가 죽어 바로 알았지만,
> 이제는 조용히 계속 돌기 때문에 패널 배너나 이벤트 섹션을 직접 보러 가야 합니다.
> 절차는 아래 문제 해결의 "등록기는 켜져 있는데 key를 발급하지 않는다" 항목을 보세요.

### 두 가지 타임아웃 예산의 역할

기준은 "업스트림의 첫 바이트가 언제 도착할 수 있는가"이지 엔드포인트의 이름이
아닙니다:

| 예산 | 대상 엔드포인트 | 변수 |
|----|---------------|----|
| 첫 바이트 | **스트리밍** 대화(`stream: true`), 비디오 폴링 `GET /v1/videos/{id}` | `UPSTREAM_TIMEOUT_MS` |
| 동기 | 이미지 생성, 비디오 작업 생성, **모든 비스트리밍 대화**(네 프로토콜 모두) | `UPSTREAM_SYNC_TIMEOUT_MS` |

비스트리밍 요청은 업스트림이 답변 전체를 생성한 뒤에야 응답 헤더를 보냅니다. 이미지
생성과 완전히 같은 지연 특성이므로, 8초짜리 첫 바이트 예산으로 자르면 정상적인 요청이
대량으로 실패하고 key 풀까지 함께 망가집니다.

`UPSTREAM_SYNC_TIMEOUT_MS`는 **요청 한 건의 총예산**, 즉 클라이언트의 최악 대기 시간이며
"풀 크기 × 예산"이 아닙니다. 게이트웨이는 이 예산에서 key 하나에 최대 절반만 쓰고, 나머지는
다른 key로 재시도하는 데 남겨 둡니다. 그래야 풀에 멈춘 key(연결은 되지만 절대 응답하지
않는)가 있어도 요청 하나를 통째로 잡아먹지 않습니다. 따라서 **단일 호출의 최악 소요 시간의
2배 이상**으로 설정하세요.

동기 예산에서의 타임아웃은 즉시 key를 처벌하지 않습니다. 같은 요청 안에서 바꿔 쓴 다른
key가 실제로 성공했을 때에만 먼저 타임아웃된 key에 책임을 지웁니다(`MAX_STRIKES`에
도달하면 쿨다운). 그 요청에서 모든 key가 타임아웃했다면 하나도 처벌하지 않습니다 ——
예산이 너무 작거나 업스트림 전체가 느릴 가능성이 더 크기 때문입니다.

"제거"와 "쿨다운"은 다릅니다. 위 설정과 무관하게, 업스트림 `401`/`403`은 해당
key를 **영구** 제거합니다 —— 이는 "이 key는 더 이상 유효하지 않음" 상태이며
재시도가 무의미하기 때문입니다. 일시적 실패는 결코 제거로 이어지지 않습니다.
`MAX_STRIKES`에 도달해도 `COOLDOWN_STRIKE_MS` 쿨다운에 들어갈 뿐 스스로 복구되므로,
업스트림의 일시적 장애가 key 풀을 영구히 망가뜨리는 일은 없습니다.

어떤 key도 요청을 처리할 수 없을 때 게이트웨이는 `503`과 함께 판별 가능한
`error.reason`을 반환합니다: `pool_empty`(key 미등록), `all_cooling`(모든 key가
쿨다운 중 — 자동 복구되며 `Retry-After` 헤더가 복구 시점을 알려줌),
`all_evicted`(자격 증명 실효로 모든 key가 영구 제거됨 — **자동 복구되지 않으므로**
key 교체 필요), `upstream_error`(key 자체는 정상이나 업스트림이 매번 실패).

### 아주 긴 비스트리밍 요청이 도중에 끊길 수 있나 (앞단에 있는 것이 결정합니다)

**결론: 게이트웨이 자체는 `UPSTREAM_SYNC_TIMEOUT_MS` 말고는 어떤 실시간 상한도 두지 않으므로,
정상적인 긴 요청을 도중에 끊을 수 있는 것은 그 앞단에 있는 것뿐입니다.**

컨테이너 안에서 도는 Node 프로세스에는 **플랫폼 시간 상한이 전혀 없습니다**: 비스트리밍
요청을 묶는 것은 직접 설정한 예산뿐이고 그 밖에는 아무것도 없습니다. 이 문서가 하는 약속은
그것뿐이고, 관리 콘솔도 그보다 큰 약속은 하지 않습니다.

**앞단에 있는 것은 직접 확인해야 합니다.** 항목별로 명시합니다.

- 리버스 프록시에는 자체 읽기 시간 초과가 있고 기본값은 대체로 짧습니다: nginx의
  `proxy_read_timeout`은 60초, Caddy 자체는 무제한이지만 그 업스트림은 아닐 수 있습니다.
  올리려면 `UPSTREAM_SYNC_TIMEOUT_MS`와 같은 축에서 올리세요. 그렇지 않으면 먼저 끊는 쪽은
  프록시입니다.
- 오리진 앞에 CDN을 두면 한 층이 더 붙습니다: Cloudflare가 문서화한 **프록시 읽기 시간 초과는
  100초(오류 524)** 이고, 게이트웨이의 어떤 설정으로도 늘릴 수 없습니다.
- 로드 밸런서의 유휴 시간 초과도 마찬가지이며, 클라이언트 쪽에서 본 증상은 동일합니다:
  연결이 그냥 끝나고, 들여다볼 `error.reason`도 없습니다.

⇒ **실질적인 영향 두 가지:**
① `UPSTREAM_SYNC_TIMEOUT_MS`(기본 120000)를 **앞단 체인에서 가장 빡빡한 시간 초과보다 작게**
   설정하세요. 그렇지 않으면 게이트웨이라면 끝냈을 요청이 남의 손에 끊기고, 그 이유는 로그에
   남지 않습니다.
② **정말 긴 요청이 필요하면 스트리밍 엔드포인트를 쓰세요.** 첫 바이트 예산은 첫 바이트만
   묶고 그 뒤 생성 시간은 세지 않습니다. 게다가 계속 바이트를 내보내는 스트림은 체인 어디에서
   봐도 유휴로 보이지 않습니다.

## 다중 계정 설정

key를 임포트하는 일반적인 경로는 관리 패널, 또는 `POST /admin/api/keys` 직접
호출입니다(한 번에 최대 200개. [API.md](API.md)와 [ADMIN.md](ADMIN.md) 참고).
아래의 **저장소 백엔드에 직접 기록하는** 방법은 두 가지 상황 전용입니다.
`ADMIN_TOKEN`을 아직 설정하지 않았거나(패널 트리 자체가 등록되지 않습니다),
패널을 쓸 수 없을 때의 비상 복구입니다.
이 방법은 **`pool:index`를 갱신하지 않습니다**. 새 레코드가 바로 보인다는
보장이 없으며, 그 대가는 아래 "색인과 반영까지 걸리는 시간"에 있습니다.
각 항목은 `key:<id>`를
키로 하는 JSON 객체이며, `<id>`는 풀 내에서 고유하기만 하면 어떤 문자열이든
가능합니다(게이트웨이가 스스로 레코드를 생성할 때는 key의 해시값에서
파생하지만, 읽을 때 이 값을 검증하지는 않으므로 수동 임포트 시에는 고유한
식별자면 무엇이든 사용할 수 있습니다).

```json
{
  "id": "1a2b3c4d5e6f7a8b",
  "key": "실제-agnes-api-key",
  "addedAt": 1735689600000,
  "lastUsedAt": null,
  "cooldownUntil": 0,
  "strikes": 0,
  "evicted": false,
  "evictedReason": null
}
```

### Docker로 임포트

실행 중인 프로세스와의 쓰기 경합을 피하기 위해 먼저 컨테이너를 중지한 뒤,
호스트에서 `./data/store.json`을 편집해 `"key:1a2b3c4d5e6f7a8b"` 키
아래에 위와 같은 레코드를 추가하고, 다시 컨테이너를 시작합니다.

```bash
docker compose stop
# ./data/store.json 편집
docker compose start
```

`./data/store.json`이 아직 없다면, `key:<id>` 형식의 키를 갖는 단일 JSON
객체로 새로 만들면 됩니다.

### 색인과 반영까지 걸리는 시간

게이트웨이는 풀의 id 목록을 `pool:index` 키에 보관하여 전달 요청마다 전수 탐색을 하지 않게
합니다. **레코드를 손으로 써도 이 색인은 바뀌지 않습니다.** 따라서 새 key가 언제부터
쓰이는지는 그 시점의 풀 상태에 달려 있습니다:

- **풀이 비어 있을 때**: 색인이 "비어 있다"고 하고 실제로도 레코드를 하나도 읽지 못하면,
  게이트웨이는 스캔으로 한 번 폴백해 수동으로 가져온 레코드를 찾아 색인에 채웁니다.
  이 스캔에는 내장된 10분 백오프가 있으므로(위 "key 풀과 그 인덱스" 참조), 가시성 상한은
  **10분 이내 + `POOL_CACHE_TTL_MS` 한 번**입니다.
- **풀이 비어 있지 않을 때**: 전달 경로는 색인이 아는 레코드만 가져오므로, 색인이 모르는
  레코드는 **완전히 보이지 않습니다**(오류도 전혀 나지 않습니다). 다음 대조가 색인을
  고칠 때까지(`TEND_INTERVAL_MS`, 기본 30분), 그리고
  그 뒤 최대 `POOL_CACHE_TTL_MS` 한 번을 더 기다려야 합니다.

**수동 가져오기를 즉시 반영하려면 같은 편집 안에서 id도 함께 `pool:index`에 추가하세요:**

```json
{"v":1,"ids":["기존id","1a2b3c4d5e6f7a8b"]}
```

색인을 쓰고 나면 풀은 최대 `POOL_CACHE_TTL_MS` 한 번 뒤에 이 key를 쓰기 시작합니다.

**대조는 레지스트라가 켜져 있는지와 무관하게 돕니다**. 같은 `TEND_INTERVAL_MS` 타이머입니다:
이것이 `pool:index`와 실제 `key:` 레코드를 대조해 고치는 유일한 경로이므로, 고아 레코드나
유령 색인 항목은 한 간격 안에 회수됩니다. 이 간격을 터무니없이 크게 잡으면 그 대기도 그만큼
길어집니다. 대기 시간 동안 해당 key는 일시적으로 사용할 수 없을 뿐이며, 손실되거나 손상되지는
않습니다.

### key 폐기하기

**레코드를 지우고, 그 id를 `pool:index`에서도 빼세요 — 두 단계 모두 해야 합니다.** 레코드만
지워도 오류는 나지 않지만(읽을 수 없는 레코드는 그냥 걸러집니다) id가 색인에 남아, 다음
대조가 잘라낼 때까지 갱신할 때마다 읽기 한 번을 헛되이 씁니다.

`./data/store.json`에서 `"key:<id>"` 항목을 지우고 `"pool:index"`의 `ids` 배열을 고치면
됩니다. 돌고 있는 프로세스가 편집을 덮어쓰지 않도록 먼저 `docker compose stop`을 하세요:

```json
{"v":1,"ids":["남은id"]}
```

이미 예전 스냅숏을 읽어 둔 프로세스는 최대 `POOL_CACHE_TTL_MS` 한 번 뒤에 이 key를
더는 고르지 않습니다.

**그 창 동안에도 다시 기록되지는 않습니다**: 게이트웨이는 어떤 상태 변경이든 저장하기 전에
레코드가 아직 있는지 먼저 확인하고, 읽히지 않으면 그 쓰기를 버리며 자신의 스냅숏을 즉시
갱신합니다. 파일 저장소에서는 이 확인용 읽기가 파일 자체에 닿고 중간에 캐시가 없으므로,
이 보장은 정확합니다.

## 검증

명령 세 개, 싼 것부터. `$BASE`는 본인 주소(`PORT`를 바꾸지 않고 앞에 도메인도 두지
않았다면 `http://localhost:8080`)로, `$TOKEN`은 본인이 설정한 `GATEWAY_TOKEN`으로 바꾸세요.

### 헬스 체크

```bash
curl -s "$BASE/health"
```

`status`가 `ok`면 저장소를 읽고 쓸 수 있다는 뜻이고, `degraded`면 저장소 쪽에 문제가 있다는
뜻이며 원인은 로그에 있습니다. **이 명령만 토큰이 필요 없어서**, 토큰이 틀렸을 때도 답이
돌아오는 유일한 엔드포인트이기도 합니다.

### 모델 목록

```bash
curl -s "$BASE/v1/models" -H "Authorization: Bearer $TOKEN"
```

이 게이트웨이가 다루는 모델 목록이 돌아옵니다. 이게 통과하면 토큰이 맞은 것이고, `401`이면
틀린 것입니다.

### 실제 대화 한 번

```bash
curl -s "$BASE/v1/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"agnes-2.0-flash","messages":[{"role":"user","content":"ping"}]}'
```

실제로 업스트림까지 가는 건 이 명령입니다. `503`이 오고 `error.reason`이 `pool_empty`면 풀에
아직 key가 없다는 뜻이니, 위 절로 돌아가 하나 임포트하세요.

## 문제 해결

마주치기 쉬운 순서로 일곱 가지. 모두 "증상 → 해결" 형태이고, 해결은 위에서부터 차례로
해 보세요.

### 게이트웨이가 뜨지 않고 로그에 토큰이 없다는 한 줄만 나온다

**증상**: 컨테이너가 **기동 직후 종료**하고, `docker compose ps`에는 restarting 또는 exited로
보이며, 로그에는 `缺少 GATEWAY_TOKEN，网关无法启动` 한 줄뿐입니다. **어중간한 상태는 여기
없습니다**: 게이트웨이는 모든 요청에 `503`을 주는 대신 아예 조립을 거부하므로, 누가 엔드포인트를
찔러 보지 않아도 `docker compose ps`에서 보입니다.

**해결**:

1. `.env`에 `GATEWAY_TOKEN=` 줄이 있고 **등호 뒤가 비어 있지 않은지** 확인합니다.
2. 고친 뒤 `docker compose up -d`를 실행합니다. **`docker compose restart`는 안 됩니다** ——
   컨테이너의 환경은 생성 시점에 고정되므로 restart로는 아무것도 다시 읽지 않습니다.

> [!WARNING]
> **이 증상에 `RESET_CONFIG=1`을 쓰지 마세요.** 그 의미는 "**저장된 `config` 키를 완전히 무시한다**"이며,
> 게이트웨이 토큰이 바로 거기에 있다면(패널에서 저장한 그것) 하나뿐인 토큰까지 함께 사라집니다.
> 이 장애는 위 두 단계로만 고칠 수 있습니다.

### 모든 요청이 503을 주고 이유는 풀이 비었음

**증상**: 어떤 전달 엔드포인트든 `503`을 주고 `error.reason`이 `pool_empty`다.

**해결**:

1. 관리 패널의 key 풀 화면에서, 또는 `POST /admin/api/keys`([API.md](API.md) 참고)로 key를 최소 한 개 임포트합니다. `ADMIN_TOKEN`을 설정하지 않았다면 "다중 계정 설정" 절을 따라 저장소에 직접 기록합니다.
2. 이미 임포트했는데도 비어 있음: 손으로 쓴 레코드는 **`pool:index`를 건드리지 않습니다**. 대사(`TEND_INTERVAL_MS`, 기본 30분)를 기다리거나 id를 직접 색인에 넣으세요.
3. 레지스트라는 켜져 있는데 풀이 늘지 않음: 패널의 이벤트 보드를 보거나 [REGISTRAR.md](REGISTRAR.md)를 따라 두 메일함 채널을 점검하세요.

### 등록기는 켜져 있는데 key를 발급하지 않는다(패널은 사용 중이라는데 풀이 늘지 않음)

**증상**: 등록기 스위치는 켜져 있는데 보충 라운드가 한 번도 돌지 않습니다. 풀의 key는 줄기만 하고
결국 위의 "모든 요청이 503을 주고 이유는 풀이 비었음" 형태로 터집니다 — 그때는 진짜 원인에서
이미 여러 겹 떨어져 있습니다.

이것은 **조용한 기능 결손**입니다. 등록기는 선택적 하위 시스템이라 설정을 불러오지 못해도
**게이트웨이 전달은 평소대로** 동작하고 보충만 멈춥니다. 아무것도 죽지 않으므로 직접 보러 가야 합니다.

**어디를 보나**(네 곳이 모두 같은 것을 가리킵니다):

1. 관리 패널 **설정** 페이지 상단 배너: "등록기는 켜져 있지만 이 설정을 불러오지 못해 이번에는 시작하지 않았습니다. 전달에는 영향이 없습니다"
   와 함께 빠진 항목이 하나씩 나열됩니다.
2. **등록기** 섹션의 상태 줄이 "사용 중"이 아니라 "사용 중 · 이번에는 시작 못 함"으로 나옵니다.
3. **개요** 페이지 설정 요약의 등록기 줄도 동일하게 표시됩니다.
4. 이벤트 섹션에 매 라운드 `error` 등급 `registrar.blocked`가 남고 빠진 항목이 나열됩니다.

**해결**: 배너에 나열된 항목을 설정 페이지에서 채우세요(선택한 메일박스 채널에 API 키가 없거나,
아예 채널을 고르지 않은 경우가 가장 흔합니다).
**저장하면 복구되며, 컨테이너 재시작도 재배포도 필요 없습니다.**

### 패널이 열리지 않고 `/admin`이 404를 준다

**증상**: 브라우저로 `/admin`을 열면 `404`가 온다. 로그인 화면도 `401`도 아니다.

**해결**:

1. **`ADMIN_TOKEN`을 설정하지 않았을 때**의 정상적인 모습입니다. 트리 자체가 등록되지 않으므로 "여기에 관리 화면이 있다"는 사실조차 새지 않습니다.
2. 설정했는데도 404라면 **먼저 컨테이너가 정말 재생성됐는지 확인하세요**: Docker 형태에서는 `.env`를 고친 뒤 `docker compose up -d`가 필요하고, `docker compose restart`는 다시 읽지 않습니다. 이 단계를 건너뛰면 아래 3번이 엉뚱한 방향으로 이끕니다.
3. 재생성했는데도 404: 토큰이 규칙에 어긋납니다(24자 미만 / 앞뒤 공백 / 출력 불가 ASCII). 컨테이너 로그에 `admin.token_rejected`가 남습니다.
4. 패널은 열리는데 엔드포인트가 `503`: `ADMIN_TOKEN`이 저장소의 `gatewayToken`과 충돌했습니다. 로그는 `admin.token_conflict`이고, 처리 방법은 위 절에 있습니다.

### 패널에서 저장한 설정이 다른 인스턴스에 한참 반영되지 않는다

**증상**: 패널에서 설정을 저장했고 이 인스턴스는 바로 바뀌었는데, 같은 볼륨을 공유하는 다른 컨테이너는 여전히 옛 값이다.

**해결**:

1. **정상입니다**. 설정 홀더는 최소 **30**초에 한 번만 갱신하므로 그것이 상한입니다. 조금 기다렸다 다시 보세요.
2. 2분이 지나도 그대로면: 그 필드가 환경 변수로 잠겨 있지 않은지 확인합니다. 잠긴 필드는 패널에서 흐리게 표시되고 엔드포인트는 `400 locked_by_env`를 줍니다.
3. 바꾼 것이 `POOL_CACHE_TTL_MS` / `POOL_TOUCH_INTERVAL_MS`라면: 이 둘은 **인스턴스를 만들 때 한 번만** 읽으므로 컨테이너를 다시 만드는 수밖에 없습니다.

### 비스트리밍 요청이 무더기로 타임아웃되고 key 풀이 붉어진다

**증상**: 이미지 생성, 비디오 작업 생성, 비스트리밍 대화가 무더기로 타임아웃되고 패널에서 key 한 무리가 쿨다운에 들어간다.

**해결**:

1. `UPSTREAM_SYNC_TIMEOUT_MS`를 **단일 호출 최악 소요 시간의 두 배 이상**으로 올립니다. 기본값 `120000`은 느린 모델에는 빡빡합니다.
2. `UPSTREAM_TIMEOUT_MS`(첫 바이트 예산, 기본 `8000`)로 비스트리밍 요청을 묶지 마세요. 그 예산은 스트리밍과 비디오 폴링용입니다.
3. 업스트림 전체가 느려진 게 아닌지 확인합니다. 한 요청 안에서 모든 key가 타임아웃되면 게이트웨이는 **어느 것도 벌하지 않습니다**. 쿨다운은 같은 요청에서 다른 key가 실제로 성공했을 때만 기록됩니다.

### Docker 컨테이너는 떴는데 `/health`가 degraded다

**증상**: `docker compose ps`가 unhealthy를 보이고 `/health`는 `503`, `status`는 `degraded`다.

**해결**:

1. 열에 아홉은 데이터 디렉터리에 쓰지 못하는 경우입니다. 컨테이너 로그의 entrypoint 줄을 읽고 `./data`의 소유자가 `100:101`인지 확인하세요.
2. `--user`나 compose의 `user:`로 비 root를 지정했다면 entrypoint는 chown을 **하지 않습니다**. 소유자와 쓰기 가능 여부는 직접 준비해야 합니다.
3. `DATA_DIR`가 `/`나 최상위 시스템 디렉터리를 가리키면 entrypoint는 재귀 chown을 거부하고 경고만 찍습니다 —— 멀쩡한 디렉터리로 바꾸세요.
4. **소유자를 세 번 확인해도 맞는데 여전히 degraded**: 대개 `store.json`을 파싱하지 못하는 경우입니다. 위 세 항목은 모두 권한 이야기지만 이것은 아닙니다 —— 저장 계층이 올바른 JSON을 읽지 못하면 읽고 쓸 때마다 예외가 나고, 기동 프로브가 "쓰기 가능"을 false로 기록해 `/health`도 똑같이 `503` degraded를 줍니다. 컨테이너를 멈추고 `python3 -m json.tool ./data/store.json`으로 검증하세요: 위 "다중 계정 설정"이 가르치는 손편집이 가장 흔한 파손 경로입니다(쉼표 하나면 충분합니다). 깨졌으면 백업에서 복구하세요. 진짜 원인은 컨테이너 로그 첫 줄에 그대로 나옵니다.

## 성능 최적화

먼저 한 가지를 분명히 해 둡니다. **이 게이트웨이 자체는 시간을 거의 쓰지 않습니다.**
비용은 두 곳에 있습니다 —— 업스트림 응답 시간, 그리고 저장소의 읽기/쓰기 할당량.
그래서 이 절에서 만질 값어치가 있는 손잡이는 셋뿐입니다.

```env
# 선택: 각 프로세스가 key 풀 스냅숏을 유지하는 시간(밀리초). 0이면 캐시를 끔.
# 키우면 파일 읽기를 아낌. 대가는 다른 컨테이너가 쓴 상태가 더 늦게 보인다는 점.
POOL_CACHE_TTL_MS=120000

# 선택: "마지막 사용 시각"을 저장하는 최대 간격(밀리초). 0이면 성공 요청마다 저장.
# 표시 전용 필드라서 줄여 봐야 쓰기 횟수만 늘고 스케줄링에는 아무 이득이 없음.
POOL_TOUCH_INTERVAL_MS=21600000

# 선택: 동기 엔드포인트(이미지, 비디오 작업, 모든 비스트리밍 대화)의 전체 예산(밀리초).
# 단일 호출 최악 소요 시간의 두 배 이상으로 두지 않으면 정상 요청까지 죽고 key 풀이 상함.
UPSTREAM_SYNC_TIMEOUT_MS=180000
```

효과가 큰 순서로 셋:

1. **볼륨 하나를 여러 컨테이너가 공유하는 게 아니라면 `POOL_CACHE_TTL_MS`는 건드리지 마세요.**
   컨테이너가 하나면 그 스냅숏이 곧 권위라서 키워도 얻는 게 없고, `store.json`을 손으로 고친
   것을 알아채는 시점만 늦어집니다. 실제로 복제본을 돌리고 같은 key가 두 번 판정되는 것을
   본 뒤에 키우세요.
   산식은 위 "할당량 계산"에 있습니다.
2. **패널의 "마지막 사용"을 더 정확히 보겠다고 `POOL_TOUCH_INTERVAL_MS`를 줄이지 마세요.**
   그건 표시 전용 필드인데 쓰기 할당량은 하루 1,000회뿐이고, 쿨다운과 제외 기록이 같은
   할당량을 두고 다툽니다.
3. **긴 요청은 스트리밍 엔드포인트로 옮기세요.** 첫 바이트 예산은 첫 바이트까지만 묶고 그
   뒤의 생성 시간은 세지 않습니다. 비스트리밍 예산은 업스트림이 답을 다 만들 때까지를 품어야
   하고, 두 형태의 플랫폼 쪽 거동이 같다는 보장도 없습니다.

## 모니터링과 유지보수

### 헬스 엔드포인트

`/health`는 토큰이 필요 없는 유일한 엔드포인트이며 두 형태 모두에 있습니다.

```bash
curl -s "$BASE/health"
```

`status`가 `ok`면 저장소를 읽고 쓸 수 있다는 뜻이고, `degraded`면 저장소 쪽에 문제가 있다는
뜻입니다(Docker에서는 대개 데이터 디렉터리에 쓰지 못하는 경우). Docker 형태에서는 이미지에
내장된 `HEALTHCHECK`가 바로 이걸 때리고, `docker compose ps`의 healthy/unhealthy가 거기서
나옵니다.

### 패널의 이벤트 보드

`ADMIN_TOKEN`을 설정하면 패널의 이벤트 보드가 게이트웨이가 스스로 남긴 진단 이벤트를
등급별로 보여 줍니다(로그인 실패, 토큰 충돌, 보충 실패, 예산 소진 등).
**로그를 대신하지는 못합니다**: 보관은 24시간이고 한 번의 폴링이 되짚는 키는 최대 48개입니다.
오래 남겨야 한다면 컨테이너 로그를 어딘가로 보내세요.

### 사용량 통계(기본값은 꺼짐)

일／시간／모델／프로토콜별 시계열은 **기본값이 꺼짐**이고, 그 "꺼짐"은 무비용입니다 ——
누적기를 만들지 않고 저장소 쓰기도 한 번도 일어나지 않습니다. 켜려면:

```env
# 선택: 패널 "사용량" 섹션의 Tier-2 시계열. 판정은 문자 그대로 true이고 1이나 yes는 꺼짐.
# 켜면 인스턴스마다 한 기록 간격에 샤드 하나를 다시 씀. 미기록 꼬리는 최대 2시간.
# 기록 간격을 넘기지 못한 인스턴스는 그 카운트를 그대로 가지고 사라진다(늦게 반영되는 것이 아니다).
USAGE_STATS_ENABLED=true
```

**켜기 전에 위의 경고 두 개를 읽으세요.** 잃는 것은 프로세스가 멈추는 순간까지 아직 들고
있던 카운트이고, 환경 변수 하나를 바꾸려고 컨테이너를 다시 만들기만 해도 그 일이 벌어집니다.
이 형태에서는 `USAGE_FLUSH_INTERVAL_MS`를 원하는 만큼 줄일 수 있습니다 —— 이 절충은 여러분의
것이지 밖에서 강제된 제한이 아닙니다.

## 서비스 업그레이드

업그레이드 명령 두 개는 [Docker 배포](#docker-배포)의 "업데이트"에 있습니다.
이 절에서는 그 두 명령 바깥의 이야기를 합니다.

### 업그레이드 전에

1. **먼저 저장소를 백업합니다.** key 풀과 설정은 사본이 하나뿐입니다. 아래 "백업과 복구" 참고.
2. **기준선을 적어 둡니다: 지금의 `version`과 key 풀 개수.** 앞의 것은
   `curl -s "$BASE/health"`가 돌려주는 그 필드이고, 뒤의 것은 패널 개요 페이지에 있습니다.
   기준선이 없으면 아래 세 가지 확인으로는 "올라갔다"와 "아예 안 올라갔다"를 가릴 수 없습니다.
3. **CHANGELOG를 한 번 봅니다.** 파괴적 변경은 거기 적힙니다. 여섯 개 README의 배지가 그곳을
   가리킵니다.
4. **업그레이드에 저장소 초기화는 필요 없습니다.** 저장된 레코드는 하위 호환이며 `pool:index`의
   `v` 필드는 오늘 기준 항상 `1`입니다.

### 업그레이드 후 확인할 것

1. `/health`가 `200`, `status`가 `ok`이고 **`version`이 이번에 올린 버전 번호와 같을 것**.
   세 가지 중 이 뒷부분만이 "올라갔다"와 "아예 안 올라갔다"를 가릅니다: `version`은 컴파일
   시점 상수로 이미지에 구워지고, 나머지 둘은 옛 버전에서도 한 글자 틀리지 않고 통과합니다.
   이미지가 배포되지 않았을 때(Release는 나갔는데 빌드가 취소된 사고, 이 저장소가 실제로 겪음)
   `docker compose pull`은 조용히 성공하는 빈 동작입니다.
2. 패널을(돌리고 있다면) 로그인할 수 있고 key 풀의 개수가 업그레이드 전과 같을 것. 개요
   페이지 런타임 칸에도 버전 번호가 있어 1번과 서로 뒷받침합니다.
3. 위 "검증"의 세 번째 명령을 한 번 돌려 실제로 업스트림까지 닿는지 확인할 것.

롤백: Docker는 `.env`의 `IMAGE_TAG`를 이전 버전으로 되돌리고 `docker compose up -d`를 다시
실행합니다(이미지 전체 이름과 tag 목록 위치는 위 "Docker 배포 → 업데이트").
**그 tag가 registry에 정말 있는지 먼저 확인하세요**: 받아오지 못하면 compose는 실패하지 않고
**지금의 작업 트리**로 그 버전 번호를 단 이미지를 빌드합니다. 롤백은 "성공"하고 장애는 그대로
남습니다.

## 백업과 복구

key 풀과 설정은 사본이 하나뿐이고 두 번째는 없습니다. **백업이란 저장소 자체를 뜨는
일입니다.**

### 뜨는 법

```bash
docker compose stop
cp -a ./data ./data.bak
docker compose start
```

한 번 멈추는 것은 쓰기 경합을 피하기 위해서입니다. 복구는 디렉터리를 되돌려 놓고
`docker compose up -d` 하면 됩니다.

### 안에 무엇이 들어 있나, 그리고 골라 베끼는 것이 왜 함정인가

`./data/store.json` 안에 전부 들어 있습니다 —— key 레코드와 `pool:index`뿐 아니라
`apikeys`(발급된 외부용 API 키 표), `config`(패널이 저장한 설정),
`registrar:domains`와 `registrar:backoff`(등록기의 도메인 가용성·백오프 장부),
`tend:history`(보충 이력), 그리고 이벤트 링까지.

> [!CAUTION]
> **그 파일에서 `key:<id>`와 `pool:index`만 골라내면 네 갈래의 키를 빠뜨리고, 그 누락은 복구
> 현장에서 전혀 보이지 않습니다.** 그렇게 골라 복구하면: 업스트림 key 풀은 돌아오고 `/health`는 `ok`를
> 주고 직접 `GATEWAY_TOKEN`으로 찔러 봐도 통합니다 —— 그런데 다운스트림 사용자 손에 있는
> 서브키는 전부 `401`입니다. 빠지는 것은 이 네 갈래: `apikeys`(발급된 외부용 API 키 표.
> 복구하지 않는 것은 모든 서브키를 한 번에 폐기하는 것과 같고, 평문은 발급 그 한 번만
> 보여 주므로 되찾을 수 없어 전부 재발급해야 합니다), `config`(패널이 저장한 설정. 게이트웨이
> 토큰과 두 메일함 채널의 자격 증명 포함), `registrar:domains`와 `registrar:backoff`(잃으면
> 등록기가 "사용 중 · 이번에는 기동하지 못함"이 됩니다), `tend:history`(보충 이력).
> **위의 `cp -a ./data`에는 이 문제가 전혀 없습니다** —— 그래서 그것이 권장 레시피입니다.

> [!WARNING]
> 백업 파일에는 **평문 key와 평문 자격 증명**이 들어 있습니다(게이트웨이 토큰도, 두 메일함
> 채널의 API Key도 저장소 쪽 설정에 있습니다). 자격 증명으로 취급하세요: 저장소에 넣지 말고,
> 공개 오브젝트 스토리지에도 올리지 마세요.

## 보안 권장사항

- **`GATEWAY_TOKEN`과 `ADMIN_TOKEN`은 서로 다른 두 개여야 합니다.** 앞의 것은 **모든
  다운스트림 사용자**에게 나눠 주는 중계 토큰입니다. 그것을 패널 토큰으로 돌려쓰면 key 풀
  전체, 레지스트라 스위치, 등록 백엔드 주소까지 함께 넘기는 셈입니다.
- **패널은 TLS 뒤에 두고 신뢰하는 머신에서만 여세요.** 패널은 `ADMIN_TOKEN`을 브라우저의
  localStorage에 그대로 보관하며, 파생 토큰도 제품 내 폐기 경로도 없습니다. 12시간 뒤에 다시
  입력하게 하는 것은 창을 줄일 뿐 **폐기가 아닙니다**.
- **`TRUST_PROXY`는 게이트웨이가 정말로 프록시 뒤에 있을 때만 켜세요.** 일반 리버스 프록시
  뒤에서 켤 때는 그 프록시에서 `CF-Connecting-IP`를 떼어내세요. 그러지 않으면 공격자가 직접
  붙인 값이 프록시가 방금 쓴 `X-Forwarded-For`를 눌러 버립니다.
- **데이터 디렉터리와 백업 파일은 모두 자격 증명으로 취급하세요.** key도
  패널로 써 넣은 자격 증명도 전부 평문으로 저장되며, key 평문 저장과 같은 수위입니다.
### 외부용 API 키는 업스트림 key 풀과 정반대입니다

- **외부용 API 키의 평문은 딱 한 번만 나타납니다.** 발급한 그 요청의 응답에만 들어 있고 이후
  어떤 인터페이스로도 가져올 수 없습니다 — 게이트웨이는 SHA-256 다이제스트만 저장합니다.
  잃어버리면 복구할 수 없으니 삭제하고 다시 발급하세요. **업스트림 key 풀과는 정반대**입니다
  (그쪽은 실제로 써야 하므로 평문으로 저장해야 합니다).
- **`GATEWAY_TOKEN`을 나눠 주지 말고 다운스트림마다 서브키를 하나씩 주세요.** 서브키는 개별로
  중지·만료 설정·폐기를 할 수 있지만, 마스터 토큰은 한 번 나눠 주면 교체해서 모두를 동시에
  끊는 것 말고는 취소할 방법이 없습니다.

최소한의 보안 기준 설정:

```env
# 필수: 클라이언트가 이 게이트웨이를 호출할 때 제시해야 하는 토큰. 다운스트림에 나눠 주는 값입니다.
GATEWAY_TOKEN=본인의 긴 랜덤 문자열로 교체

# 선택: 관리 패널 토큰. 설정하지 않으면 /admin 트리 전체가 등록되지 않아 401이 아니라 404가 옵니다.
# GATEWAY_TOKEN과 달라야 하고, 24자 이상이며 출력 가능한 ASCII만 씁니다.
ADMIN_TOKEN=또 다른 긴 랜덤 문자열로 교체

# 선택: 클라이언트 주소를 바꿔 쓰는 프록시나 CDN 뒤에 컨테이너가 있을 때만 1로.
# 직접 노출된 배포에서는 설정하지 마세요.
TRUST_PROXY=1
```
