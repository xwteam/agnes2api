# 部署指南

**语言：** [English](../en/DEPLOY.md) | 简体中文 | [繁體中文](../zh-TW/DEPLOY.md) | [日本語](../ja/DEPLOY.md) | [한국어](../ko/DEPLOY.md)

agnes2api 提供两种部署形态，构建自同一套代码与请求处理逻辑，按你的基础设施二选一即可。
两者仅在存储后端上有区别：Worker 用 Cloudflare KV 命名空间，Docker 用挂载卷上的 JSON
文件。

## 环境变量

| 变量 | 是否必填 | 默认值 | 说明 |
|---|---|---|---|
| `GATEWAY_TOKEN` | **是** | – | 客户端调用本网关时必须携带的令牌。 |
| `RESET_CONFIG` | 否 | – | 逃生口：置 `1` 时启动**完全忽略**存储里的 `config` 键（只忽略，不删除），只用环境变量与内置默认值。存储里的配置被写坏到网关起不来时用它救回来；救回之后记得去掉这一行，否则面板里保存的配置永远不会生效。 |
| `AGNES_BASE_URL` | 否 | `https://apihub.agnes-ai.com/v1` | 上游 Agnes API 的基址。 |
| `UPSTREAM_TIMEOUT_MS` | 否 | `8000` | **流式**响应与视频轮询的首字节超时：超过这个毫秒数未收到上游首字节则中止本次调用。 |
| `UPSTREAM_SYNC_TIMEOUT_MS` | 否 | `120000` | **同步**端点的整体超时预算，只作用于「首字节要等上游把整个结果算完才到达」的请求：图片生成、视频建任务，以及所有**非流式**对话。见下文说明。 |
| `MAX_STRIKES` | 否 | `3` | 连续瞬时故障（超时、网络错误、上游 `5xx`）累计到该阈值后，该 key 进入长冷却。 |
| `COOLDOWN_RATE_LIMIT_MS` | 否 | `60000` | 上游返回 `429` 后，对应 key 的冷却时长。 |
| `COOLDOWN_PAYMENT_MS` | 否 | `3600000` | 上游返回 `402` 后，对应 key 的冷却时长。 |
| `COOLDOWN_STRIKE_MS` | 否 | `1800000` | key 的瞬时故障累计到 `MAX_STRIKES` 后的冷却时长，到期自动恢复。 |
| `POOL_CACHE_TTL_MS` | 否 | `60000` | 每个 isolate/进程在内存里缓存一份 key 池快照，本值是它的存活时长；`0` = 关闭缓存。**KV 读取次数与请求数无关**，只取决于刷新频率，算法见下文「配额账」。代价：别的 isolate 判定的冷却/剔除，本 isolate 最多晚**本值 + 约 60 秒**才看到（后者是 KV 边缘缓存的默认 `cacheTtl`）；默认 60000 时上界约 **120 秒**。而且不只是「看得晚」：陈旧快照上的任意一次调度写会把整条记录覆写回去，**抹掉**别的 isolate 在这个窗口里刚写下的 `evicted` / `cooldownUntil`，那次判定要重新发生一遍。 |
| `POOL_TOUCH_INTERVAL_MS` | 否 | `21600000` | key 的「最后使用时间」最多多久落盘一次；`0` = 每次成功请求都落盘。它是纯展示字段、不参与调度，为它每请求写一次 KV 会把免费档 1,000 次/天的写配额吃光，连冷却与剔除都写不进去。代价：面板「最后使用」的精度最粗到这个间隔。同一个间隔也管着面板上的用量计数（请求数 / 成功率）。**手工改小存储里的 `stats`（例如清零）之后，面板可能先显示为已清零、随后又被顶回旧值**：快照过一个 TTL 会读到清零后的值，而还在运行的实例记着自己的落盘基线，下一次真落盘又会按基线写回去，最迟到这个实例被回收之后才真正一致；P3c 会提供一条经过 repo 的正式重置路径。 |
| `USAGE_STATS_ENABLED` | 否 | `false` | 面板「用量」板块的 Tier-2 时间序列（按天／小时／模型／协议）。**判据是逐字的 `true`**，写 `1` / `yes` 都算关。**默认关，而且「关」是零成本的**：不建任何内存累加器、一次存储写都没有。打开之后每个实例每天最多 13 次 put（约占写配额 10.4%，8 个 isolate 时合计 104 次/天），耗尽当天不再写、下一个 UTC 日恢复；未落盘的尾巴最长 2 小时。详见下文「配额账」里 Tier-2 那一段。建 app 时读一次，改了要重启容器 / 等 isolate 回收才生效。 |
| `PORT` | 否（仅 Node/Docker） | `8080` | Node 运行时的监听端口，Worker 不使用该变量。 |
| `DATA_DIR` | 否（仅 Node/Docker） | `/app/data` | 文件存储写入 `store.json` 的目录，Worker 不使用该变量。 |

上表里的每个变量在 `.env.example` 里都有一行示例，`cp .env.example .env` 之后按需改即可；
那份文件的注释详略不一（多数变量只有一行，个别写满十几行），完整的取值范围与代价以本表
为准。以上数值型变量都必须是整数；除
`POOL_CACHE_TTL_MS` 与 `POOL_TOUCH_INTERVAL_MS` 的下界是 `0`（`0` 表示「关闭」）之外，
其余都必须大于 `0`，否则网关拒绝启动。

`POOL_CACHE_TTL_MS` 与 `POOL_TOUCH_INTERVAL_MS` 是**建 app 时读一次**的，改了要重启容器 /
等 isolate 回收才生效，不像其余配置项那样逐次生效。

### 配额账：Worker + 免费档 KV 能撑多少请求

免费档 KV 每天 100,000 次读、1,000 次写。网关的读写次数都**不随请求数增长**，所以这笔账
不是「每请求几次」，而是「每天固定几次」：

- **默认配置下 KV 不再是瓶颈**，上限变成 Cloudflare Worker 免费档自身的 **100,000 次请求/天**。
  但这条结论**有前提，不是无条件的**：KV 的读配额转而约束「同时活跃的 isolate 数」，而那
  是随流量地理分布变化的量，你无法直接设定。每个活跃 isolate 每天消耗

      (86400 ÷ POOL_CACHE_TTL_MS 秒数) × (1 + 池中 key 数)  +  2880

  次读，末项 2880 是配置持有者每 30 秒一次的刷新，吃同一个桶。默认值 + 20 把 key 时
  是每 isolate **33,120 次**，加上每天 48~96 次索引对账，**3 个活跃 isolate 就用掉约 99.4%**。
  也就是默认值在推荐配置处已经临界；预期 isolate 更多就要把 `POOL_CACHE_TTL_MS` 调大
  （20 把 key、5 个 isolate 需要约 `120000`）。
- **关掉缓存**（`POOL_CACHE_TTL_MS=0`，逃生口）时读随请求数线性增长，保底约
  `100,000 ÷ (1 + key 数)` ⇒ 20 把 key 时约 **4,700 次请求/天**。
- **写侧**：稳态每天约 `key 数 × 4` 次（`lastUsedAt` 每 6 小时触达一次），20 把 key 时 80 次，
  占写配额 8%，其余留给冷却与剔除的记账。每把 key **首次**被用到时另有一次性的一次写。
- **事件板块（Task 6）的写侧**：每个 isolate 每天最多落盘 `EVENT_WRITES_PER_DAY`（**12**）
  次，超过之后 `budgetExhausted` 如实报告，不吞、不重试。**这条闸只在单个 isolate
  内部生效**，全局是否安全取决于「并发 isolate 数 × 这个值」是否仍在预算内——单个
  isolate 无法知道别的 isolate 用了多少预算（没有 CAS、没有跨 isolate 协调）。以
  **8 个并发 isolate**估算（比本节其余处用的 3 个更保守：这类个人自用网关即便流量
  不大，Cloudflare 边缘节点遍布全球，实际并发 isolate 数不完全由你控制）：
  `12 × 8 = 96` 次/天，占写配额 **9.6%**。加上上面 key 池写侧的 80 次/天（8%），
  合计约 176 次/天（**17.6%**），仍留有约 82% 的余量。**这份账是评审要求主动给出
  的**：早期版本按小时算预算、每 isolate 独立计数到 12/小时，4 个 isolate 就能把
  写配额打穿（`4 × 12 × 24 = 1,152`，超过 1,000），修法是把预算窗口从「每小时」
  改成「每天」并把这份账写进这里；同一轮还堵掉了冷启动首刷不受节流的口子——原来
  每次 isolate 冷启动会送一次零门槛写，现在冷启动首刷与其余任何一次落盘走同一套
  最小间隔闸。
- **注册机的写侧（P3c Task 1 新增）——这一整段只在 `registrar.enabled` 为真时存在。**
  默认部署（注册机是关着的）下，本节新增的写是 **0 次/天**，不是"少几次"。
  开着时每一轮补池付三笔，**全部挂在补池频率这一根轴上**（Worker 是 `wrangler.toml`
  里的 Cron，默认 `*/30 * * * *` = 每天 48 轮；Node 是 `TEND_INTERVAL_MS`）：
    - **补池锁**：每轮一次 put + 一次 delete。这一项在本次之前就已经存在，
      只是从来没有被记进这份账。
    - **补池事件落库**：每轮最多一次 put。**决定写不写的是「这一轮的事件缓冲空不空」**
      ——不是「事件叫什么名字」。健康且**配置也健康**的一轮一条事件都不产出，
      于是是 0。⚠️ **「健康时是 0」有一个前提，必须说清楚**：`loadConfig` 有一条
      **逐轮都会打**的配置警告——`TEND_INTERVAL_MS` 小于
      `MINT_BATCH × CODE_TIMEOUT_MS × 通道数`（默认 `5 × 120000 × 1 = 600000`，
      即 10 分钟）时，**每一轮都会写一次**，哪怕那一轮什么都没铸。
    - **补池历史（`tend:history`）**：每轮一次 get + 一次 put，**无条件**。
      单键、无扇出。
  ⚠️ **不要拿 `EVENT_WRITES_PER_DAY`（每 isolate 每天 12 次）去理解这三笔。**
  那条闸是给 `fetch` 路径设的，前提是"一个 isolate 服务很多请求、预算在长寿实例上
  被反复消费"。补池这条路上每一轮很可能是一个**全新的 isolate**（Worker 的
  `scheduled()`），一生只落一次盘、每次都带着一份全新的预算 ⇒ **那条闸在这根轴上
  既拦不住什么、也不构成任何上界**。真正的上界是补池频率本身：**调密 Cron 或调小
  `TEND_INTERVAL_MS` 会等量放大这三笔**。
- **面板写操作的写侧（P3c 新增）——「人点一下才发生」，不进上面那些稳态账。**
  它没有频率上界可言（上界是运维的手），所以这里给的是**每次操作的单价**，
  下面每个数字都是一次实测读数，**逐格数出来的**：Key 写操作在
  `tests/contract/admin-keys-write.test.ts`、「立即补池」在
  `tests/contract/manual-tend.test.ts`、设置页那两条在 `tests/contract/admin-config.test.ts`。
  （这句原来只点名了第一个文件，而「立即补池」那一行与它毫无关系、当时也没有任何一格
  数过它 —— 全分支评审 I4。修法是把那一格补上，不是把这句话改软。）
    - **导入 M 把新 key**：`M + 1` 次 put（M 条记录 + 1 次索引）、`M + 1` 次 get、**0 次 list**。
      一次最多 200 把（超了直接 400，**不静默截断**）⇒ 单次点击的上界是 **201 次 put**，
      也就是两成日写配额。分几次导入不会更便宜（索引那一次每批都要付）。
    - **重复导入**（同一把 key 再粘一遍，且不勾「重置已存在 key 的状态」）：**0 次 put**。
      重复项默认跳过、不覆盖，所以重新粘一遍整份清单是廉价且安全的。
    - 勾了「重置已存在 key 的状态」之后：每把**已经在池子里**的 key 各 1 次 put。
    - **改一把 key**（停用 / 启用 / 备注 / 清冷却 / 清 strikes / 解除剔除）：1 次 get + 1 次 put。
    - **删一把 key**：2 次 get + 1 次 put（索引）+ 1 次 delete。
    - **批量停用 / 批量清冷却 N 把**：N 次 get + N 次 put。
    - **批量删除 N 把**：`N + 1` 次 get + **1** 次 put（索引只写一次）+ N 次 delete。
    - **点一次「立即补池」**：固定 **3 次 put**（护栏键 + 抢锁 + 补池历史）+ 1 次 delete
      （释放锁，走另一个桶），外加**每铸出一把 key 再 2 次 put**（记录 + 索引）。
      它是**唯一带每日上限的面板动作**：每天最多 **24** 次（第四条护栏，见
      [REGISTRAR.md](REGISTRAR.md)）⇒ 可持续 `24 × 3 = 72` 次 put/天，叠上下面第三栏的
      320 ⇒ **392 次/天（39.2%）**；每次都铸满默认的 `MINT_BATCH = 5` 时上界
      `24 × 13 = 312` ⇒ **632 次/天（63.2%）**，而那一栏靠临时邮箱名额与 `TARGET_KEYS`
      先撞死，不可持续。**加这道闸的理由不是"会打穿"，是"没有余量"**：只靠 10 分钟冷却
      的话上界是 `24 × 6 = 144` 次/天 = 432 次 put，叠上 320 就占到 75%，
      而那 320 里的 96 等于 `12 × 并发 isolate 数`，**连你自己都调不了**。
    - **保存一次设置**（`PUT /admin/api/config`）：**1 次 put** + 3~4 次 get
      （写之前一次 `readAll` + 一次原始读，写完回读一次 `readAll`；紧接着再保存一次时，
      上一次的 `invalidate()` 会让配置刷新中间件多读一次，诊断态那一支同样多一次）。
      **校验没过的那一次是 0 次 put + 2~3 次 get** —— 一个字节都不写
      （紧跟在一次保存之后同样多读一次，与上面那条同一个原因）。
    - **清空一把凭据**（`POST /admin/api/config/secrets/clear`）：**1 次 put** + 2 次 get；
      清掉 `gatewayToken`（清完这份配置就装载不起来）那一支是 3 次 get。
    - **干跑校验**（`POST /admin/api/config/validate`）：**0 次 put** + 1 次 get。
  ⚠️⚠️ **上面「保存一次设置」与「清空一把凭据」这两条没有每日上限，这是刻意的，不是漏了。**
  它们要管理员口令、而且只有人手动点一下才会发生，不是任何自动路径触发得了的；
  给它们上一把存储护栏本身又要新增一次读改写（护栏键），等于为了省一次写先多付一次写。
  **代价明写，别靠沉默让人以为它们被某个预算管着**：一次调参会话按几十次保存算是完全
  正常的运维行为，几十次 put 就是几个百分点的日写配额；而「立即补池」那条每天 24 次的闸
  **管不到这两条**。规划余量时按这一点来。
  ⚠️ 这几笔与下面那三栏**不相加**：三栏说的是「没有人操作时每天固定几次」，
  这一段说的是「你每点一下花多少」。真正值得留意的只有一个形态：**一次导入几百把 key**
  ——它是面板上单次点击最贵的动作。

- **写侧合计，按 `registrar.enabled` 分三栏**（20 把 key、8 个并发 isolate 的口径）：

  | 场景 | put/天 | 占写配额的比例 |
  |---|---|---|
  | **注册机关着（默认）**，无人操作 | **176** | **17.6%** |
  | 注册机开着、**每轮都健康**，无人操作 | **272** | **27.2%** |
  | 注册机开着、**每轮都有失败事件**，无人操作 | **320** | **32.0%** |

  ⚠️ **这三个数都不是上界，是"当前取值"**：其中 96 次/天那一项等于
  `12 × 并发 isolate 数`，而并发 isolate 数随流量的地理分布变化、**连你自己都调不了**。
  规划余量时请按这一点来，别把 272 或 320 当成天花板。
  **`delete` 桶**另计：补池锁每天释放 48 次，那个桶今天几乎闲置。

  ⚠️ **这三笔是按轮计费的，而"每天几轮"有两根互不相干的轴，别把它们混着读：**
    - **频率轴**：调密补池频率 ⇒ 三笔**等量放大**（就是上面那句）。
      **Worker 形态看的是 `wrangler.toml` 的 Cron**，Node 形态看的是
      `TEND_INTERVAL_MS`——`TEND_INTERVAL_MS` **只被 Node 的调度器消费**，
      在 Worker 上调它**一轮都不会多**；而 `registrar_tend_lock` 那对
      put/delete **两种运行时都有**（P3c Task 5 起 Node 侧也接上了同一把锁——
      多副本共卷部署下进程内的那个布尔形同虚设）。
    - **阈值轴**：`TEND_INTERVAL_MS` 跌破 `MINT_BATCH × CODE_TIMEOUT_MS × 通道数`
      时，**事件那一笔从「健康轮 0 次」跳成「每轮 1 次」**——这一跳与频率无关，
      是上面那条逐轮配置警告造成的。
  **两轴叠加才是最坏**。本节讲的是 Worker + 免费档 KV，所以举一个**这个形态下
  完全合法**的配置：Cron 改成 `*/5 * * * *` ⇒ 每天 288 轮，且每轮都有事件产出 ⇒
  `80 + 96 + 288 + 288 + 288 = 1,040` 次/天，**已经打穿写配额**。
  上面三栏都是按默认的 Cron（每 30 分钟一轮）算的，**别把它们当成与频率无关的常数**。

- **Tier-2 用量统计的写侧（P3d 新增，`USAGE_STATS_ENABLED` **默认关**）——它是本期唯一的新写者。**

  **关着时这一段的写量恒为 0**：不建任何内存累加器、一次 `storage.put` 都没有。
  这不是"顺手省一点"：它与上面 key 池那 80 次/天抢的是**同一个**每天 1,000 次的写桶，
  统计吃掉写配额会连带打死 key 池的冷却与剔除记账。

  打开之后：**每个实例每天最多 13 次 put**，按 8 个并发 isolate 估算是
  `13 × 8` = **104** 次/天，约占写配额的 10.4%。四种场景的合计：

  | 场景 | put/天 | 占写配额的比例 |
  |---|---|---|
  | **Tier-2 关（默认）**，注册机关着 | **176** | 17.6% |
  | Tier-2 开，注册机关着 | **280** | 28.0% |
  | Tier-2 开，注册机开着且每轮都有失败事件 | **424** | 42.4% |
  | 上一行 + 每 10 分钟点一次「立即补池」 | **856** | 85.6% |

  ⚠️ **最坏那一行没有余量，而且这张表和上面那三栏一样不是上界。** 正确的读法是：
  **Tier-2 那 104 是这张表里唯一一项有硬闸的**（下面第 ③ 条），其余各项都没有。

  这 13 次是这么来的，四条都要读：

  ① **12 次落盘 + 1**。落盘最小间隔是 **2 小时**，一整天最多 12 次；那个 `+1` 不是余量，
     是**跨 UTC 零点那一次落盘要写两个键**（前一天一个、当天一个）。
     取 12 的话每 24 小时恰好有一次写被预算拒绝——数据不丢（那天的待落盘标记不清，
     下一轮补上），但下面第 ② 条那句「最长 2 小时」会变成 4 小时。

  ② **未落盘的尾巴最长 2 小时，它的两种表现是同一件事，不是两条**：
     面板上「今天」的数字最多旧 2 小时；**存活不足 2 小时的实例**
     （Worker 的短命 isolate、Docker 的快速重启）攒的计数**随实例一起消失**。
     计时从实例启动那一刻开始，所以一个只活了 10 分钟的 isolate 一个字都存不下。
     这是用量数字全程标注「≈」的原因之一，不是缺陷。

  ③ **每个实例每天 13 次 put 是一道硬闸**：耗尽之后当天不再写，**下一个 UTC 日自动恢复**，
     而且欠下的那几天会在恢复之后补上（内存里的累加器不清）。
     ⚠️ 这道闸**只在单个实例内部生效**——8 个 isolate 就是 8 份各自独立的 13 次，
     与上面事件板块那道闸完全同源，没有跨实例协调。

  ④ **两种运行时的行为完全相同，不做运行时嗅探。** 落盘间隔的**默认值**两边同一个、
     同一条代码路径（请求收尾**同步等待写完**，不是后台任务——后台任务在 Worker 上会被
     响应返回后的 isolate 停摆静默截断）。
     `USAGE_FLUSH_INTERVAL_MS` 可以覆盖它，**判据是「你的存储有没有写配额」，
     不是「跑在哪个运行时上」**：
     · **文件存储（Docker）没有写配额** ⇒ 任意正整数放行，**而且不再有每天的写预算**，
       上界就是间隔本身。调回 300000（5 分钟）完全合理。
     · **KV（Worker）有写配额** ⇒ 预算恒为每实例每天 13 次，而间隔必须满足
       `间隔 × (13 − 1) >= 一天`，破了**启动就报错**并告诉你最小可用值（7200000）。
       不默默接受是有意的：那种值下写量仍然合格，**而数据从中午起就是假的**，
       比起不来更难发现。

  ⑤ **同一天最多只有 2 个实例的数据进得来，超出的会互相覆盖。** 用量分片按
     `usage:<UTC 日>:<槽位>` 存，**槽位只有 2 个**，实例按自己的分片 id 稳定地散进去。
     ⇒ 上面按 8 个 isolate 算的那 104 次/天是**写量**，不是「8 份数据都留下了」——
     同槽位是后写覆盖先写。**这也是用量数字全程标注「≈」的原因之一**（另一条是 ② 的尾巴）。
     它不影响写配额，只影响数字的完整度；`≈` 的含义就是这个。

  ⑥ **媒体那三条端点（图片生成、视频建任务、视频查询）不进用量统计。** 它们与四条
     对话协议**烧同一批上游 key**，但不记账 ⇒ 面板上的「总请求数」系统性地小于真实转发量。
     这是本期的已知边界，不是缺陷；判断 key 消耗要看 key 池那一侧的计数。

- **事件板块的读侧（评审 C4/C4b 修复后的真实账目，比早期草稿更保守）**：面板轮询
  不依赖索引，候选键数**有硬上界**——不论 `after` 有多陈旧、部署已经跑了多少天，
  单次请求最多回看 24 个时间窗 × 2 个槽位 = **48** 次 get（评审 C4 修复前，一个
  陈旧或敌意的 `after` 能把单次请求打到接近 100 万次 get，见
  `tests/contract/quota-panel.test.ts` 的回归用例）；`after` 落在最近的时间窗内时
  是"暖读"，通常只需要 2 次 get（跨过时间窗边界的那一刻是 4 次）。
  **但"上界有限"不等于"开销与活跃度无关"**——评审 C4b 点出一个反直觉的结论：
    - **持续有新事件的"活跃"部署**：新事件不断把轮询间隔顶回最短的 15 秒，多数
      命中暖读。全按最坏 4 次/轮估算：`(86400 ÷ 15) × 4 = 23,040` 次/天（约读配额
      的 23%，实际因为只有少数轮询恰好跨越窗口边界，通常远低于这个数）。
    - **长期没有新事件的"安静"部署**（含刚部署完、尚未触发过任何诊断事件）：
      `after` 游标永远等不到新值，冻结的游标一旦掉出 24 小时保留窗口，**之后每一次
      轮询都是满额的 48 次 get**；同时因为没有新内容，指数退避把轮询间隔顶到上限的
      60 秒。稳态是 `(86400 ÷ 60) × (48 + 1) = 70,560` 次/天（约读配额的 **71%**）——
      ⚠️ **这个数是「稳态空闲界」，不是上界。** 它假设面板就那么开着、没有人动它；
      交互路径不在这个数里：每点一次「级别」筛选按钮就是一次满额冷读，而
      切回本板块、标签页重新变可见同样会立刻拉一轮，**这几条今天都没有节流**。
      式子里那个 `+1` 是**每一轮轮询自己顺带触发的那次配置读**：配置刷新中间件挂在
      所有路由之前，配置缓存的 TTL 是 30 秒，短于 60 秒的轮询间隔，所以每轮恰好多读一次。
      它吃的是下文 key 池那笔账里 `86400 ÷ 配置 TTL 秒数` 那一项的**同一个桶**
      （那一项写的是上界 2,880 次/天；只有面板在跑的 isolate 实际只用掉 1,440 次），
      两笔账合并时**别把它算两遍**。
      **一个健康到几乎不产生诊断事件的部署，单开一个面板标签页反而比"活跃"部署
      吃掉更多读配额**，规划余量时请按这个更高的数字来，尤其是与上面 key 池读侧的
      账合并考虑时（见上文「3 个活跃 isolate 就用掉约 99.4%」那个场景）。
    - **下载端点**（`GET /admin/api/events/download`）每次点击固定 48 次 get
      （`readEvents(null)` 永远走冷读，不带游标）——只在人手动点击时发生，量级
      可忽略，这里只是如实记一笔。
  两种场景的上界都**不会随部署运行的天数继续增长**，这一点在 C4 修复后依然成立。
- **`list` 与 `delete` 是另外两个桶，各 1,000 次/天**，与读、写那两个桶互不相通。稳态转发
  一次 `list` 都不用——`pool:index` 索引键正是为此存在的。会消耗它的一共**四处**：每天
  48~96 次索引对账（补池调度每一轮开头各一次）；**面板上的「立即补池」**（P3c 起，那一轮
  真的铸出了 key 时收尾会再对账一次 ⇒ 每天最多再 24 次，上界就是那条护栏本身——
  这一处原来漏在这份清单外，而且这句话原来把对账限定成「独立的定时任务」，
  P3c 之后它有了一个**运维手动触发**的消费者，全分支评审 I2）；
  **池子为空时的兜底扫描**（索引合法却一条活记录都
  读不到时，网关 `list` 一次，确认是不是有手工导入的记录没进索引）；以及**索引缺失回落**
  （`pool:index` 本身读不出来或结构损坏时，网关同样 `list` 一次并尝试重建索引，多半是写桶
  被打穿导致索引一直建不起来）。后两者**共用同一个**内置的 **10 分钟**退避窗口（固定常量，
  不是环境变量）——它们通向同一个 `list` 桶，各自开一扇窗等于没开——因此空池或索引损坏期间
  每个 isolate 每天最多 144 次，叠上索引对账的 48~96 次与面板最多 24 次仍有余量。
- **`list` 桶被打穿的后果是失能而不是降级。** 池子为空且 `list` 失败时，网关返回 `500` 并把
  真实原因写进日志，**不会**伪装成 `503 pool_empty`——因为此时对账用的是同一个桶、同样在失败，
  本文档给出的两条自愈路径都已经不可用，只能等 UTC 跨天配额重置。

**上面的读取公式有一个前提：「isolate 活得比 TTL 长」。** 流量很低、或者分散到很多
Cloudflare 边缘节点时，isolate 常常活不满一个 TTL 就被回收，那时每个 isolate 一生至少
要装载一次池子，读取次数由**冷启动次数**而不是 TTL 决定，上界约
`100000 ÷ (池中 key 数 + 2)` 次冷启动/天（分母里的 `+2` 是索引与配置各一次）。**这个区间
里调大 `POOL_CACHE_TTL_MS` 一次读都省不掉**——它只能省「同一个 isolate 内的重复装载」。

同理，空池态与索引缺失态的 `list` 退避也是**每实例**的：冷 isolate 各付一次，总量随
isolate 数线性增长。

### 管理面板相关变量（P3，默认关闭）

| 变量 | 是否必填 | 默认值 | 说明 |
|---|---|---|---|
| `ADMIN_TOKEN` | 否 | 无（面板不启用） | 管理接口的口令。**必须与 `GATEWAY_TOKEN` 不同**，且至少 24 位。另外**首尾不得有空白**：HTTP 请求头的值在传输层会被去掉首尾空白，而环境变量不会，带空白的口令任何客户端都送不出来。口令还必须只由**可打印 ASCII（0x20–0x7E）**组成，这条限制有三段不同性质的理由：① 汉字 / emoji / 零宽空格这类码点大于 U+00FF 的字符，以及换行与 NUL，浏览器在设置请求头时**直接抛错**——请求压根发不出去，留着它只会装出一棵 200 但永远进不去的面板，而且服务端连一条 `admin.login_failed` 都不会有；② **除 TAB 外**的其余控制字符（`0x01–0x08`、`0x0B`、`0x0C`、`0x0E–0x1F`、`0x7F`，共 29 个）浏览器送得出去，但会被 HTTP 解析器判成 `400`；③ **TAB（`0x09`）**与 `é` / `£` / 不间断空格这类 `0x80–0xFF` 的字符**其实送得出去也能用**，拦它们是本网关的**稳健性取舍**而不是物理限制；**两者的理由并不相同**：TAB 是**不可见字符**，粘进 `.env` 或 secret 里没人看得见（与首尾空白同类的可诊断性问题，只是那条是物理、这条是取舍）；`0x80–0xFF` 则是编码口径问题——环境变量按 UTF-8 解、HTTP 头值按 Latin-1 解，两边在这一段并不由规范保证一致（我们也只在 Node 上验过，Cloudflare Workers 侧未验），而 RFC 9110 已把这段标为弃用。请用纯 ASCII 口令。**中间带空格是允许的**——`correct horse battery staple` 这类 passphrase 送得出去也送得到，而且在 24 位下限之下它往往比随机串更好记、更不容易抄错；首尾空白由上面那条规则管着。未设置或不合规时整棵 `/admin` 树都不注册，具体原因记在 `admin.token_rejected` 事件里。 |
| `TRUST_PROXY` | 否 | 未设置（**任何**转发头都不信） | 只有在网关确实位于代理之后时才设成 `1`——**Cloudflare Worker 形态也属于这种情况，应当设上**。设了之后，登录失败事件里的客户端 IP 取自 `CF-Connecting-IP`，缺席时才退到 `X-Forwarded-For` 的首段。 |

**没配就是面板整个不可用，而网关照常转发。** 此时访问 `/admin/...` 得到的是 **`404` 而不是
`401`**：整棵树压根没注册，因此不会泄漏「这里有个后台」。这与注册机默认关闭是同一条规矩——
`ADMIN_TOKEN` 缺失或配错，绝不能让网关转发停摆。

**为什么有 24 位的下限。** Worker 形态**没有分布式登录限速**。要做它就得拿 KV 当计数窗口，
那等于给攻击者一根消耗写配额的杠杆，把攻击面从「猜口令」扩大到「打死 key 池的状态回写」。
因此口令熵是这里唯一的防线，下限不是建议值。低于下限时面板不会启用，容器日志里会有一条
`admin.token_rejected`。

**为什么必须与 `GATEWAY_TOKEN` 不同。** `GATEWAY_TOKEN` 是你发给**每一个下游用户**的中转
口令。复用它当面板口令，等于任何拿到中转口令的人都能读走你的整池 key、关掉注册机、把注册
后端指向他自己的服务器——从此每一次注册的邮箱、密码、验证码都会被他收走。

这条规则**只在每一个管理请求上复查，不在启动时拦**。若两者相同——例如用
`wrangler kv key put` 或直接编辑 `store.json` 手工把 `gatewayToken` 写成了管理口令——管理
接口会**返回 `503`**，同时打一条 error 级的 `admin.token_conflict`（启动时就撞上冲突的话，
启动日志里也会有同样一条，方便你立刻看到原因）。**网关转发不受影响。**

**冲突一旦成立，`ADMIN_TOKEN` 必须按已泄漏处置——恢复方式只有一条：把它轮换成一把全新的口令。**
Worker 执行 `npx wrangler secret put ADMIN_TOKEN` 后重新部署；Docker 改 `.env` 后重建容器。
**别只把存储里的 `gatewayToken` 改回去。** 那确实能让管理接口立刻恢复（配置缓存下一次刷新之后生效，
不需要重启），但它救的是可用性、不是安全性：冲突期间这把管理口令与中转口令是同一个值，
而中转口令是发给**每一个下游用户**的——只要它曾经被发出去过（或者接下来会被发出去），
拿着它的人就能直接开你的后台。可用性可以靠改 `gatewayToken` 先恢复，
但那之后**仍然要轮换 `ADMIN_TOKEN`**，两步都做完才算处置完。

**为什么这一条刻意不在启动时拦。** `gatewayToken` 运行中会变，而启动时的判定没有第二次求值的
机会：一旦在那里把整棵 `/admin` 树反注册掉，冲突期间冷启动的 isolate（以及冲突期间启动的整个
Docker 容器）就会**永久 404**，把配置改回去也救不了，必须重启——而冲突之前建好的那些只是 `503`
且改回去立刻恢复。同一份配置、同一时刻两种结果，上面那句「不需要重启」就成了半句假话。
相比之下 `ADMIN_TOKEN` 自身的三条规则（首尾空白 / 含发不出去的字符 / 长度不足）只取决于环境变量，运行中不会变，
所以它们仍然在启动时拦，失效形态是 `404`。

`ADMIN_TOKEN` **只从环境变量读、不从存储读**：面板不能自助轮换自己的钥匙。轮换方式：Worker
执行 `npx wrangler secret put ADMIN_TOKEN` 后重新部署；Docker 改 `.env` 后重建容器。

**管理口令泄漏 = `ADMIN_TOKEN` 泄漏。** 面板把它原样存在浏览器的 localStorage 里，没有派生令牌，
也没有产品内的撤销路径。撤销方式只有一条：改 secret 后重新部署（Worker）/ 重建容器（Docker）。
面板会在 12 小时后要求重新输入口令，但那只缩短这份 localStorage 值的可用窗口，**不等于撤销**。
请把面板放在 TLS 之后，并且只在你信任的机器上打开它。

**这个上限做不到什么，也一并说清楚。** 面板的 CSP 用 `connect-src 'self'` 挡住了把口令 `fetch`
到外部域名，用 `form-action 'none'` 挡住了表单外传；但它挡不住
`location.href = "https://…?k=" + token` 这种**导航式外传**——CSP 规范里已经没有可用的指令拦它
（`navigate-to` 已被移除）。真正的解法是服务端签发**可撤销的派生令牌**，那要求服务端存储会话，
与「`ADMIN_TOKEN` 只从环境变量读、不从存储读」这条设计约束冲突，因此留给后续版本。

**`TRUST_PROXY` 是安全开关，所以默认关闭。** 它决定的客户端 IP 会写进 `admin.login_failed`
事件，无脑信任一个由客户端提供的头，等于允许任何人把爆破痕迹嫁祸给任意 IP。

**关闭时任何转发头都不信，该字段一律记 `null`——`CF-Connecting-IP` 也不例外。** 这个头常被说成
「平台注入、伪造不了」，但那个性质**只在请求真的经过 Cloudflare 时**成立；Node/Docker 直连暴露时
没有任何东西会覆盖它，客户端自己发一个 `CF-Connecting-IP: 1.2.3.4` 就会被采信——而直连正是 Docker
部署的默认形态。

**打开时 `CF-Connecting-IP` 优先，`X-Forwarded-For` 只作兜底。** 两个头的可伪造性根本不同：

- `CF-Connecting-IP` 由 Cloudflare 边缘写入，并且会**覆盖**客户端传来的同名头——只要请求真的经过
  Cloudflare，它就伪造不了。
- `X-Forwarded-For` 是任何中间件都能追加的链，客户端可以自己发一个假的，可信与否完全取决于你的
  代理链长什么样。

**Worker 形态请设 `TRUST_PROXY=1`。** 那里 Cloudflare 定义上就在前面，`CF-Connecting-IP` 是权威值；
在这种形态下优先 `X-Forwarded-For` 是错的——那条链里可能装着客户端自己塞的东西。不设这个开关的话，
该字段就只是记成 `null`。

**通用反代（nginx / Caddy / Traefik）后面打开 `TRUST_PROXY=1` 时，请在反代上把
`CF-Connecting-IP` 剥掉。** 那种拓扑里没有任何东西会覆盖这个头，而网关按「Cloudflare 在前面」
优先采信它，于是攻击者自带一个就会**压过**反代刚写好的 `X-Forwarded-For`。nginx 加一行即可：

```nginx
proxy_set_header CF-Connecting-IP "";
```

Caddy 用 `header_up CF-Connecting-IP ""`，Traefik 用中间件的 `customRequestHeaders`。

**两个头都会先过一遍形态校验**：只有 IPv4 点分十进制与 IPv6 形态（十六进制、冒号，以及
`::ffff:` 映射里的点）能进事件，其余一律记 `null`。这条不是鉴权防线（这个值全仓只有登录失败
事件一个消费点），它防的是「未鉴权的调用方往审计字段里塞任意文本」——管理面板的事件板块
要按这个字段做筛选与展示。

什么都拿不到时该字段如实记 `null`，**绝不伪造一个 `"unknown"`**——那会被当成一个真实来源。

### 设置页能改什么（P3c）

面板的**设置**页对应三张卡：**认证密钥** / **上游与冷却** / **注册机**（含两条完全平级的
邮箱通道子卡与一个「高级」折叠区）。它写的是**存储里那个 `config` 键**，而不是环境变量。

**每个字段显示三个值，不是一个。** 一行「存储 X · 环境变量 Y · 生效 Z」把
「你保存的是什么」「部署那一侧给了什么」「网关实际在用什么」分开写。
优先级恒为 **环境变量 > 存储 > 内置取值**。

**被环境变量锁定的字段，面板改了不会生效——所以面板直接不让改。**
那一格的输入框置灰，旁边写着是哪个环境变量、以及要改就得改部署那一侧。
`PUT /admin/api/config` 对这类字段一律返回 `400 locked_by_env`，**不写存储**：
写下去的后果是「保存成功、生效值纹丝不动」，运维会以为是缓存没刷，白等两轮。

⚠️ **P3c 起注册机那一族（`REGISTRAR_ENABLED` / `REGISTRAR_PRIMARY` / `REGISTRAR_FALLBACK` /
`TARGET_KEYS` / `MINT_BATCH` / `TEND_INTERVAL_MS` / `CODE_TIMEOUT_MS` / `MINT_DELAY_MIN_MS` /
`MINT_DELAY_MAX_MS` / `MAX_DOMAIN_ATTEMPTS` / `REGISTRAR_TOKEN_NAME` / `AGNES_PLATFORM_URL` /
`YYDS_BASE_URL` / `YYDS_API_KEY` / `MOEMAIL_BASE_URL` / `MOEMAIL_API_KEY`）也进了这张锁定表。**
在此之前它们不在表里：`docker-compose.yml` 里写了 `TARGET_KEYS=30`、面板上改成 20，
保存成功而生效值永远是 30，**重启也不会好**，面板上还没有任何提示。

**凭据只写不读。** 网关口令与两条通道的 API Key 在接口里**永远不返回明文**，只返回
「配没配」与**末 4 位**（不足 5 位时连末 4 位都不给——给了就是给全）。因此：

- 输入框永远是空的，占位符写着**留空则不修改**；
- 保存时这几格**缺席或留空 = 不改**（不是清空）。若把留空实现成清空，运维保存一次设置页
  就会抹掉网关口令，而**当前进程靠上一份快照还能继续跑**，直到下一次重启才整个停摆；
- 清空只能走那颗单独的「清空」按钮（带二次确认）。

⚠️ **面板写进去的凭据以明文落在 KV / `store.json` 里**，与 P1 的「key 明文存盘」同一水位。
别以为这里输的是加密过的 secret。数据目录 / KV namespace 请按凭据处置。

⚠️ **清掉网关口令而环境变量里也没有 `GATEWAY_TOKEN` 时**：当前进程还能跑，
但**下一次重启 / isolate 回收会起不来**。面板会当场用一条红色提示说破这件事，
恢复方式是立刻在同一页写一把新的网关口令。**而环境变量里有这一项时清空是安全的**：清掉的只是存储里那一份，生效值回落到环境变量，纹丝不动——面板会按这两种状态说两句不同的话，不会让你自己猜。

⚠️ **「高级」折叠区里那个注册后端地址（`AGNES_PLATFORM_URL`）不是普通配置项。**
它是**每一次自动注册的去向**：换成别的服务器，那台服务器就会收到本网关注册时用的
邮箱、密码与验证码。所以它折在高级区里、带红色警告、有自己的二次确认按钮，
不跟主表单那颗「保存」一起走。

**保存之后面板不弹「已保存并生效」**，而是**回读**一遍生效值，把真的变了的字段高亮，
并写明**别的副本 / isolate 最长多久才看得到**：配置持有者的 TTL 是 30 秒，
KV 边缘缓存默认 60 秒 ⇒ 上界约 **90 秒**。本实例是立刻生效的（保存那一步会作废本地缓存），
别的实例不是。**面板文案不许写「立即生效」。**

### 两档超时分别管什么

判据是「上游的第一个字节什么时候才可能到达」，不是端点的名字：

| 档位 | 适用端点 | 用哪个变量 |
|---|---|---|
| 首字节档 | **流式**对话（`stream: true`）、视频轮询 `GET /v1/videos/{id}` | `UPSTREAM_TIMEOUT_MS` |
| 同步档 | 图片生成、视频建任务、**所有非流式对话**（四种协议均如此） | `UPSTREAM_SYNC_TIMEOUT_MS` |

非流式请求要等上游把整段回答生成完才发响应头，和图片生成是同一种延迟语义，用 8 秒的
首字节档去卡它只会让正常请求大量失败并连累 key 池。

`UPSTREAM_SYNC_TIMEOUT_MS` 是**一次请求的总预算**，也就是客户端的最坏等待时间——不是
「池大小 × 预算」。网关在这个预算里最多为单把 key 花掉一半，剩下的用来换一把 key 再试，
这样池里有一把 key 挂起（连得上但永不响应）时不会白白吃掉这次请求。因此把它设成
**单次调用最坏耗时的两倍以上**。

同步档超时不会立刻惩罚 key：只有当同一次请求里换的另一把 key 真的成功了，网关才把超时
算到先超时的那把 key 头上（累计到 `MAX_STRIKES` 进冷却）；如果本次请求里每一把都超时，
则一把都不惩罚——那更可能是预算配小了或上游整体变慢。

「剔除」与「冷却」是两回事。无论以上参数如何设置，上游 `401`/`403` 都会**永久**剔除该
key——这两种状态被视为「这个 key 已失效」，重试没有意义。瞬时故障则永远不会导致剔除：
累计到 `MAX_STRIKES` 只是进入 `COOLDOWN_STRIKE_MS` 的冷却，到期自动恢复，因此上游抽风
不会永久损毁你的 key 池。

当没有任何 key 能服务本次请求时，网关返回 `503`，并在 `error.reason` 里给出可判别的原因：
`pool_empty`（尚未导入 key）、`all_cooling`（全部 key 冷却中，会自动恢复，响应头 `Retry-After`
给出恢复时刻）、`all_evicted`（全部 key 因凭据失效被永久剔除，**不会**自愈，请更换 key）、
`upstream_error`（key 本身可用，但上游每次尝试都失败）。

### 超长的非流式请求会不会被平台从中间砍断（两种形态可能不同）

**结论：Worker 那一侧没有可以依赖的平台承诺，所以本文不做承诺，面板也不做承诺。**

已核实的官方口径（Cloudflare Workers 的 limits 页）有两条：HTTP 触发的 Worker
**没有**墙钟时长上限（"There is no hard limit on duration for HTTP-triggered Workers"），
单条出站子请求也**没有**时间上限（"There is no set time limit on individual subrequests"），
两条都以「客户端还连着」为条件。

**但这两条覆盖不到全部**，逐条写明：

- 官方文档里那条 **125 秒回源读超时（错误码 524）** 只写在「经 Cloudflare 反向代理的
  站点流量」语境下，**从没说过它适不适用于 Worker 自己发出的子请求**——查不到就按
  「没有平台承诺」处理，不臆测。
- 同一页还写着运行时每周会更新几次，更新时在飞的请求有 **30 秒**宽限期，超过就被中止。
  这是低概率事件，但它是**存在的**。
- `wrangler.toml` 里那个 **15 分钟（900 秒）**是 **Cron Trigger（`scheduled()`）**的墙钟上限，
  **不是 `fetch()` 的**，别把它搬过来当依据。

⇒ **实际影响两条**：
① `UPSTREAM_SYNC_TIMEOUT_MS`（默认 120000）级别的非流式请求，在 Worker 与 Docker
   两种形态下**表现不一定相同**；Node/Docker 那一侧没有平台墙钟，只受你自己配的预算约束。
② **面板（调试台）的文案不承诺「两种形态一样」**，也不给出任何「多久之内一定不会被中断」
   的数字。真要跑长请求，把 `UPSTREAM_SYNC_TIMEOUT_MS` 调到你实测能过的范围，
   或者改用流式端点（首字节档）。

### 方式一：Deploy to Cloudflare 按钮

点击根目录 [README](../../README.md) 中的按钮，授权 Cloudflare 后会自动 fork/clone 本

### 方式二：手动部署

1. 克隆仓库并安装依赖：

   ```bash
   git clone https://github.com/xwteam/agnes2api.git
   cd agnes2api
   pnpm install
   ```

2. 为 key 池创建一个 KV 命名空间并写回 `wrangler.toml`：

   ```bash
   node scripts/setup-worker.mjs
   ```

   仓库里 `wrangler.toml` 的 `id` 永远是占位符（公开仓不放任何真实部署细节），
   这一步必不可少。脚本内部做的事等价于手动执行 `npx wrangler kv namespace
   create POOL` 后把返回的 `id` 填进 `[[kv_namespaces]]` 段替换掉
   `REPLACE_WITH_YOUR_KV_NAMESPACE_ID`。**跑完不要提交这次对 `wrangler.toml`
   的改动**——`check-wrangler-placeholder.mjs` 那道 CI 门禁会拦下误提交的真实 id。

3. 把网关令牌设置为 Worker secret（绝不要提交进 `wrangler.toml`）：

   ```bash
   npx wrangler secret put GATEWAY_TOKEN
   ```

4. 部署：

   ```bash
   npx wrangler deploy
   ```

### 本地开发

```bash
npx wrangler dev
```

把 `GATEWAY_TOKEN` 写进 `wrangler.toml` 同目录下的本地 `.dev.vars` 文件（已加入

⚠️ 这个文件会被 `pnpm test:workers` 无条件读进 workerd 的 `env`

## Docker

1. 克隆仓库并准备环境变量文件：

   ```bash
   git clone https://github.com/xwteam/agnes2api.git
   cd agnes2api
   cp .env.example .env
   ```

2. 编辑 `.env`，至少设置 `GATEWAY_TOKEN`。其余变量见上文的
   [环境变量](#环境变量) 表。

3. 启动容器：

   ```bash
   docker compose up -d
   ```

   `docker-compose.yml` 默认发布 `8080` 端口（可通过 `.env` 里的 `PORT` 覆盖），并把
   `./data` 挂载到容器内的 `/app/data`——`store.json`（key 池与任何持久化配置）就存在
   这里。重启/升级时务必保留这个目录，它是已导入 key 池的唯一副本。

4. 确认容器健康：

   ```bash
   curl http://localhost:8080/health
   ```

   镜像内置了 `HEALTHCHECK`，Docker 会据此上报容器健康状态。数据目录不可写时 `/health`
   返回 `503` 且 `status` 为 `degraded`，容器会被标成 unhealthy，具体原因见容器日志。

### 容器会改写 `./data` 的属主（请先知悉）

容器**以 root 进入 entrypoint**，做两件事后再降权：

- 若 `DATA_DIR`（默认 `/app/data`）的属主与容器内运行用户 `app`（**uid 100 / gid 101**）
  不一致，就递归 `chown` 该目录；属主已经一致时不做任何改写。
- 随后用 `su-exec` 降权，**主进程（PID 1）以 app 运行，不是 root**。

必须在运行期做这件事的原因是：绑定挂载时宿主目录的属主会盖过镜像里构建期的 `chown`，
容器内的 app 因此写不进 `store.json`，而这种失败是静默的（所有 API 返回 `pool_empty`）。

**副作用**：绑定挂载改的是**宿主**上的文件——`docker compose up -d` 之后，你的 `./data`
及其中的文件属主会从你自己的 uid 变成 `100:101`，之后在宿主上读写或备份它需要 `sudo`。
不希望发生这件事的话，用 `--user`（或 compose 的 `user:`）指定非 root 运行：此时
entrypoint 完全不 chown，数据目录的属主与可写性由你自己准备。

出于同样的原因，镜像**没有** `USER app`，默认用户是 root
（`docker inspect --format '{{.Config.User}}' <image>` 输出为空）。这对 Kubernetes 有影响：
配了 `runAsNonRoot: true` 却没显式给 `runAsUser` 时，kubelet 会拒绝启动该容器。这类部署请
显式写 `runAsUser: 100`、`runAsGroup: 101`（或任何你自己的 uid），并自行准备卷的属主——
非 root 启动时 entrypoint 走的是「不 chown、直接执行」的分支。

安全边界：`DATA_DIR` 被设成 `/` 或某个顶层系统目录（`/etc`、`/usr` 等）时，entrypoint
拒绝在其上递归 chown（只打印警告，不影响启动），避免把整个容器文件系统改成 app 可写。

## 导入 Agnes 上游 key

当前版本的网关没有提供导入 key 的 HTTP 接口，需要直接写入存储后端。每条记录是一个
键为 `key:<id>` 的 JSON 对象，`<id>` 可以是池内唯一的任意字符串（网关自己创建记录时
会用 key 的哈希值派生一个，但读取时不校验这个值，所以手动导入时用任意唯一标识即可）：

```json
{
  "id": "1a2b3c4d5e6f7a8b",
  "key": "你的真实-agnes-api-key",
  "addedAt": 1735689600000,
  "lastUsedAt": null,
  "cooldownUntil": 0,
  "strikes": 0,
  "evicted": false,
  "evictedReason": null
}
```

### Docker

先停止容器，避免与正在运行的进程产生写入竞争；在宿主机上编辑 `./data/store.json`，
在键 `"key:1a2b3c4d5e6f7a8b"` 下加入如上记录，然后再启动容器：

```bash
docker compose stop
# 编辑 ./data/store.json
docker compose start
```

如果 `./data/store.json` 还不存在，直接新建一个 JSON 对象文件，键为若干个
`key:<id>` 字符串即可。

### Cloudflare Worker

用 wrangler 直接把记录写进 `POOL` KV 命名空间：

```bash
npx wrangler kv key put --binding=POOL "key:1a2b3c4d5e6f7a8b" \
  '{"id":"1a2b3c4d5e6f7a8b","key":"你的真实-agnes-api-key","addedAt":1735689600000,"lastUsedAt":null,"cooldownUntil":0,"strikes":0,"evicted":false,"evictedReason":null}' \
  --remote
```

不加 `--remote` 则写入 `wrangler dev` 使用的本地命名空间，而不是生产环境。

网关用一个 `pool:index` 键保存池内的 id 列表，这样每次转发都不必消耗 KV 的 `list` 操作
（免费档的 `list` 配额只有每天 1,000 次，是独立于读、写之外的另一个桶）。**手工写记录不会
动这个索引**，所以新 key 多久能被用上，取决于池子当时的状态：

- **池子为空时**：索引说池子是空的、记录也确实一条都读不到，网关会回落一次 `list` 扫描把
  手工导入的记录发现并补进索引。这条扫描有内置的 10 分钟退避（见上文「配额账」），因此
  可见上界是 **≤10 分钟 + 一个 `POOL_CACHE_TTL_MS`**。
- **池子非空时**：转发路径只按索引取记录，索引不知道的记录**完全隐身**，而且没有任何报错。
  它要等下一次 Cron 对账把索引修好（默认 30 分钟，且**触发时机没有官方保证**，见下），
  之后再等最多一个 `POOL_CACHE_TTL_MS`。

**想让手工导入立刻生效，就在写记录的同时把 id 补进 `pool:index`：**

```bash
npx wrangler kv key get --binding=POOL "pool:index" --remote
# 把新 id 追加进 ids 数组再整个写回（v 固定为 1）
npx wrangler kv key put --binding=POOL "pool:index" \
  '{"v":1,"ids":["已有的id","1a2b3c4d5e6f7a8b"]}' --remote
```

索引写完之后，各 isolate 最多再等一个 `POOL_CACHE_TTL_MS` 就会用上这把 key。

**即使你完全不用注册机，也不要删掉 `wrangler.toml` 里的 `[triggers]`**：那个 cron 是
`pool:index` 与实际 `key:` 记录之间唯一的对账修复路径，且与 `REGISTRAR_ENABLED` 无关。

**这个 cron 的触发时机没有官方保证。** Cloudflare 没有文档化 Cron Trigger 按
`crons` 表达式触发的可靠性承诺（不保证不跳过、不保证延迟上界）。这对配额账
是安全的——对账触发得越少，实际消耗的 KV 读写只会比预估更少，不会更多；但
**孤儿记录 / 幽灵索引项被捡回索引的时间没有保证**，极端情况下可能比预期的
「最长 30 分钟」更晚。这段等待期间该 key 只是暂时用不上，不会造成数据损坏。

## 吊销一把 key

**删记录、再把 id 从 `pool:index` 里摘掉，两步都要做。** 只删记录不会出错（读不到的记录会被
直接过滤掉），但索引里那个 id 还在，每次刷新都白付一次读，要等下一次对账才会被剪掉。

```bash
npx wrangler kv key delete --binding=POOL "key:1a2b3c4d5e6f7a8b" --remote
# 把该 id 从 ids 数组里去掉再整个写回
npx wrangler kv key put --binding=POOL "pool:index" '{"v":1,"ids":["剩下的id"]}' --remote
```

Docker 形态就是在 `./data/store.json` 里删掉 `"key:<id>"` 那个键，并把 `"pool:index"` 的
`ids` 数组改好，建议先 `docker compose stop`。

已经装载了旧快照的 isolate / 进程最多再等一个 `POOL_CACHE_TTL_MS` 才会停止选中这把 key；
Worker 上还要再加一个 KV 的传播窗口（约 60 秒），因为删除要这么久才对所有 colo 可见。

**这段窗口里它也不会被写回来**：网关在落盘任何状态变更之前都会先确认记录还在，读不到就
丢弃这次写并立刻刷新自己的快照。唯一的例外同样是那个传播窗口——确认用的那次读若被 KV
的边缘缓存挡下，本 colo 会以为记录还在。Docker（文件存储）没有这层缓存，那里是精确的。
