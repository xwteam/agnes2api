# 部署指南

agnes2api 只有一种部署形态：用本仓的代码构建出的 Docker 镜像，跑在 `docker compose` 上。

> [!NOTE]
> 全部状态只落在一个地方——挂载卷上的一份 JSON 文件（`store.json`）。把那个目录备份下来，
> 就等于把全部状态备份下来了。

## 环境要求

只有一条路，所以只有一列。

| 项 | 要求 |
|----|------|
| 命令行 | Docker Engine 24+ 与 `docker compose` |
| 平台 | 一台能跑容器的机器 |
| 上游 | 至少一把 Agnes API key，见下一节 |

> [!TIP]
> 除此之外什么都不用装——不需要本机 Node.js，也不需要构建工具链：`cp .env.example .env`
> 之后一条 `docker compose up -d` 就能起来。
## 获取 Agnes 凭据

网关自己不产生 key，它只是把请求分发到你手上那一把或几把 Agnes API key 上。
拿到 key 有两条路，**两条平级**，不预设主备。

### 手动获取

去 Agnes 平台注册账号，在后台新建一把 API key，复制出来备用。
这条路一次只给你一把，适合先把网关跑通、确认四种协议都通了再说。

### 让注册机自动补池

本仓自带一套可选的注册机，能按 `TARGET_KEYS` 把池子自动补到目标数量。
它**默认关闭**（`REGISTRAR_ENABLED` 不设就是关），工作原理、两条邮箱通道怎么选、
一轮补池最长要跑多久，完整说明见 [REGISTRAR.md](REGISTRAR.md)。

> [!IMPORTANT]
> 无论走哪条路，key 都以**明文**落在 `store.json` 里。数据目录请按凭据处置。

## Docker 部署

### 前置条件

> [!NOTE]
> 同目录 [README](README.md) 的 `## ⚡ 快速部署` 一节给的是同样三条命令的短版。
> 本节是长版：它把每一条命令留给你自己决定的那些事写开，第一件就是首次启动前必须
> 设好的那把令牌。

克隆仓库并准备环境变量文件：

```bash
git clone https://github.com/xwteam/agnes2api.git
cd agnes2api
cp .env.example .env
```

**不用镜像、直接从源码跑**：`pnpm dev:node` 以 `node scripts/build-ui.mjs` 开头，
然后构建并跑起 `dist/entry/node.js`。裸跑 `node dist/entry/node.js` 也起得来，
但面板会停在上一次生成的那一份——改了 `admin-ui/` 却看不到变化，多半就是这个原因。

### 配置

编辑 `.env`，至少设置 `GATEWAY_TOKEN`。其余变量见下文的
[环境变量](#环境变量) 表。

`.env` 的最小可用形态就两行；其余变量都有默认值，需要时再加：

```env
# 必填：客户端调用本网关时必须携带的令牌。发给下游用户的就是它。
GATEWAY_TOKEN=换成你自己的长随机串

# 可选：容器内的监听端口。
# docker-compose.yml 会把它同时用作宿主侧发布的端口。
PORT=8080
```

> [!CAUTION]
> **`DATA_DIR` 与 docker-compose.yml 的卷挂载绑死，Docker 形态下别单独改它。**
> 那一行 `./data:/app/data` 是写死的，`.env` 里的 `DATA_DIR` 完全不参与它的插值。
> 把 `DATA_DIR` 改成别的路径而不动那一行，什么都不会拦你：容器起得来、`/health` 回
> `ok`、面板与 key 池一切正常、注册机照常补池，而 store.json 落进**容器可写层**——
> 下一次照「更新」升级一次，容器一重建，整池 key、已签发的对外 API 密钥、面板配置
> 一起消失，而你一直在备份的 `./data` 从头到尾是空的。
> 要换数据落在宿主哪儿，改那行挂载的**左半边**；真要改右半边，就把 `DATA_DIR` 改成
> 同一个路径，两边一起改。容器启动时 entrypoint 会检查这件事：它没落在任何
> 挂载点上时，容器日志里有一条「没有落在任何挂载点上」的警告——那是这条链上唯一的
> 信号，`/health` 不报数据落在哪儿。

#### 数据目录与属主：容器会改写 `./data`（请先知悉）

容器**以 root 进入 entrypoint**，做两件事后再降权：

- 若 `DATA_DIR`（默认 `/app/data`）的属主与容器内运行用户 `app`（**uid 100 / gid 101**）
  不一致，就递归 `chown` 该目录；属主已经一致时不做任何改写。
- 随后用 `su-exec` 降权，**主进程（PID 1）以 app 运行，不是 root**。

必须在运行期做这件事的原因是：绑定挂载时宿主目录的属主会盖过镜像里构建期的 `chown`，
容器内的 app 因此写不进 `store.json`，而这种失败是静默的（所有 API 返回 `pool_empty`）。

**副作用**：绑定挂载改的是**宿主**上的文件——`docker compose up -d` 之后，你的 `./data`
及其中的文件属主会从你自己的 uid 变成 `100:101`，之后在宿主上读写或备份它需要 `sudo`。
不希望发生这件事的话，用 `--user`（或 compose 的 `user:`）指定非 root 运行：此时
entrypoint 完全不 chown，数据目录的属主与可写性由你自己准备。

出于同样的原因，镜像**没有** `USER app`，默认用户是 root
（`docker inspect --format '{{.Config.User}}' <image>` 输出为空）。这对 Kubernetes 有影响：
配了 `runAsNonRoot: true` 却没显式给 `runAsUser` 时，kubelet 会拒绝启动该容器。这类部署请
显式写 `runAsUser: 100`、`runAsGroup: 101`（或任何你自己的 uid），并自行准备卷的属主——
非 root 启动时 entrypoint 走的是「不 chown、直接执行」的分支。

安全边界：`DATA_DIR` 被设成 `/` 或某个顶层系统目录（`/etc`、`/usr` 等）时，entrypoint
拒绝在其上递归 chown（只打印警告，不影响启动），避免把整个容器文件系统改成 app 可写。

### 部署

启动容器：

```bash
docker compose up -d
```

**首个镜像发布之前**（或 fork 之后），这条命令会回落到本地构建——
`docker-compose.yml` 里那段 `build:` 就是干这个的。

`docker-compose.yml` 默认发布 `8080` 端口（可通过 `.env` 里的 `PORT` 覆盖），并把
`./data` 挂载到容器内的 `/app/data`——`store.json`（key 池与任何持久化配置）就存在
这里。重启/升级时务必保留这个目录，它是已导入 key 池的唯一副本。

### 验证

确认容器健康：

```bash
curl http://localhost:8080/health
```

镜像内置了 `HEALTHCHECK`，Docker 会据此上报容器健康状态。数据目录不可写时 `/health`
返回 `503` 且 `status` 为 `degraded`，容器会被标成 unhealthy，具体原因见容器日志。

下面两条是排障时反复要用的，先在这儿给全——本文后面凡是说「见容器日志」，指的都是
第二条：

```bash
docker compose ps                     # 容器在不在、健康不健康
docker compose logs -f --tail=100     # 容器日志：entrypoint 的警告、admin.token_rejected 都在这里
```

### 更新

```bash
docker compose pull
docker compose up -d
```

`docker compose pull` 拉的是 `.env` 里 `IMAGE_TAG` 指定的那个 tag（不设就是 `latest`）。
镜像全名是 `ghcr.io/xwteam/agnes2api`，有哪些 tag 见
[GHCR 的 packages 页](https://github.com/xwteam/agnes2api/pkgs/container/agnes2api)。
**升级 = 把 `IMAGE_TAG` 改成要升的版本号再 `docker compose up -d`；回滚 = 改回上一版。**
钉住版本号之后，这份 `.env` 才答得出「现在跑的是哪一版」，`:latest` 答不出。

> [!IMPORTANT]
> **改完 `.env` 要跑 `docker compose up -d`，不是 `docker compose restart`。**
> 后者只是重启同一个容器，而容器的环境是**创建**时固化的，改了 `.env` 一个字节都不会
> 变；`up -d` 检测到配置变化才会重建容器。补 `ADMIN_TOKEN` 与轮换口令踩的是同一个坑，
> 后者更隐蔽：你以为轮换完了，旧口令其实还在生效。

`./data` 不动，key 池与配置都在那儿。**升级前先备份那个目录**（见下文「备份和恢复」）：
它是已导入 key 池的唯一副本，没有第二份。

## 环境变量

| 变量 | 是否必填 | 默认值 | 说明 |
|----|--------|------|----|
| `GATEWAY_TOKEN` | **是** | – | 客户端调用本网关时必须携带的令牌。 |
| `RESET_CONFIG` | 否 | – | 逃生口：置 `1` 时启动**完全忽略**存储里的 `config` 键（只忽略，不删除），只用环境变量与内置默认值。什么时候用、用完要做什么，见下文。 |
| `AGNES_BASE_URL` | 否 | `https://apihub.agnes-ai.com/v1` | 上游 Agnes API 的基址。 |
| `UPSTREAM_TIMEOUT_MS` | 否 | `8000` | **流式**响应与视频轮询的首字节超时：超过这个毫秒数未收到上游首字节则中止本次调用。 |
| `UPSTREAM_SYNC_TIMEOUT_MS` | 否 | `120000` | **同步**端点的整体超时预算，只作用于「首字节要等上游把整个结果算完才到达」的请求：图片生成、视频建任务，以及所有**非流式**对话。见下文说明。 |
| `MAX_STRIKES` | 否 | `3` | 连续瞬时故障（超时、网络错误、上游 `5xx`）累计到该阈值后，该 key 进入长冷却。 |
| `COOLDOWN_RATE_LIMIT_MS` | 否 | `60000` | 上游返回 `429` 后，对应 key 的冷却时长。 |
| `COOLDOWN_PAYMENT_MS` | 否 | `3600000` | 上游返回 `402` 后，对应 key 的冷却时长。 |
| `COOLDOWN_STRIKE_MS` | 否 | `1800000` | key 的瞬时故障累计到 `MAX_STRIKES` 后的冷却时长，到期自动恢复。 |
| `POOL_CACHE_TTL_MS` | 否 | `60000` | 每个进程在内存里缓存一份 key 池快照，本值是它的存活时长；`0` = 关闭缓存。**存储读取次数与请求数无关**，只取决于刷新频率。代价见下文。 **建实例时读一次**（`src/http/wire.ts`）：改了要重建容器才生效，**面板改它不会立刻生效**。 |
| `POOL_TOUCH_INTERVAL_MS` | 否 | `21600000` | key 的「最后使用时间」最多多久落盘一次；`0` = 每次成功请求都落盘。它是纯展示字段、不参与调度，同一个间隔也管着面板上的用量计数。代价与「怎么清计数」见下文。 **建实例时读一次**（`src/http/wire.ts`）：改了要重建容器才生效，**面板改它不会立刻生效**。 |
| `USAGE_STATS_ENABLED` | 否 | `false` | 面板「用量」板块的 Tier-2 时间序列（按天／小时／模型／协议）。**判据是逐字的 `true`**，写 `1` / `yes` 都算关。**默认关，而且「关」是零成本的**。打开之后的开销、**短命实例上计数会丢而不是迟到**见下文。建 app 时读一次，改了要重建容器才生效。 |
| `PORT` | 否 | `8080` | 容器内的监听端口；`docker-compose.yml` 会把同一个数发布到宿主上。 |
| `DATA_DIR` | 否 | `/app/data` | 文件存储写入 `store.json` 的目录。**别单独改它**：它与 compose 的卷挂载绑死，见上文「Docker 部署 → 配置」。 |
| `APIKEY_CACHE_TTL_MS` | 否 | `300000` | 对外 API 密钥表在每个实例里的缓存时长；`0` = 关缓存。它同时决定停用一把密钥多久才在共用同一个卷的别的容器上失效，见下文。**建实例时读一次。** |

### 取值范围与两个「建实例时读一次」的例外

上表里的每个变量在 `.env.example` 里都有一行示例，`cp .env.example .env` 之后按需改即可；
那份文件的注释详略不一（多数变量只有一行，个别写满十几行），完整的取值范围与代价以本表
为准。以上数值型变量都必须是整数；除
`POOL_CACHE_TTL_MS` 与 `POOL_TOUCH_INTERVAL_MS` 的下界是 `0`（`0` 表示「关闭」）之外，
其余都必须大于 `0`，否则网关拒绝启动。

`POOL_CACHE_TTL_MS` 与 `POOL_TOUCH_INTERVAL_MS` 是**建 app 时读一次**的，改了要重建容器
才生效，不像其余配置项那样逐次生效。

### `RESET_CONFIG`：什么时候用这个逃生口

> 它真正的用途是**把面板存的那份配置整份旁路掉**：只用环境变量与内置默认值起一次，
> 好让你回到一个已知干净的状态。用完记得去掉这一行，否则面板里保存的配置永远不会生效。

> [!WARNING]
> **别把它当成「配置写坏了就用它救」。** 存储里的值今天几乎写不坏到让网关起不来：
> 数值非法会**回落到默认值**（面板上会报降级），注册机那一族的问题只让**注册机本次不启动**、
> 网关照常转发。真正还能让网关起不来的只剩一条——**网关口令两边都没有**——
> 而 `RESET_CONFIG=1` 恰恰会把存储里那把口令也一起忽略，**照做只会让情况更糟**。

### `POOL_CACHE_TTL_MS` 的代价

**存储读取次数与请求数无关**——快照热着的时候转发路径一次都不读，所以这颗旋钮买到的是
「每个进程少读几次 `store.json`」，付出的是「那份快照允许多陈旧」。

> **这件事只在多个进程共用一个卷时才有意义**：负载均衡后面挂几个容器，或者滚动重启时
> 新旧容器同时在跑。别的进程判定的冷却/剔除，本进程最多晚**本值**才看到；默认 60000 时
> 上界是 **60** 秒。单容器部署没有这个窗口：判冷却的就是握着快照的那个进程。

而且不只是「看得晚」：陈旧快照上的任意一次调度写会把整条记录覆写回去，**抹掉**别的
进程在这个窗口里刚写下的 `evicted` / `cooldownUntil`，那次判定要重新发生一遍。

### `POOL_TOUCH_INTERVAL_MS` 的代价与「怎么清计数」

为它每次成功请求都落一次盘，等于为一个没人拿去调度的时间戳整份重写一遍 `store.json`。
不这么做的代价是：面板「最后使用」的精度最粗到这个间隔。同一个间隔也管着面板上的用量
计数（请求数 / 成功率）。

> [!WARNING]
> **手工改小存储里的 `stats`（例如清零）之后，面板可能先显示为已清零、随后又被顶回旧值**：
> 快照过一个 TTL 会读到清零后的值，而还在运行的实例记着自己的落盘基线，下一次真落盘又会
> 按基线写回去，最迟到这个实例被回收之后才真正一致。

**要清计数就走经过 repo 的那条正式路径**：`PATCH /admin/api/keys/:id` 带 `clearStats`，
它把**处理这次请求的那个实例**攒着的落盘基线与未落盘增量一并作废，**于是在这次重置之后
才开始的请求不会把旧值顶回去**；但**重置那一刻已经在飞的请求**手上那份记录取自重置之前，
它收尾时会拿那份旧值重建基线，同时跑在同一个卷上的**别的**容器也各有各的基线，
仍可能把旧值顶回来一次。**它今天只有 API，面板上没有这颗按钮。**

### `USAGE_STATS_ENABLED`：打开之后要付什么

「关」是零成本的：不建任何内存累加器、一次存储写都没有。打开之后每个实例每个落盘间隔
重写一次 `store.json` 里的一个分片——**默认两小时的间隔下每天最多 13 次**，没有流量的
那个间隔一次都不写。未落盘的尾巴最长 2 小时。这个开关要重建容器之后才生效。

> [!WARNING]
> **「尾巴」不等于「迟到」**：计数先攒在实例的内存里，实例活不到一个落盘间隔时，
> **那些计数随实例一起消失，不是延迟到账**。
> **重建容器正是这件事最常发生的场景**：为改一个环境变量重建一次容器，最多两小时的计数
> 就跟着旧进程走了，面板上那一段时间看起来与「没人用过」一模一样。
> 在意这段的话就调小 `USAGE_FLUSH_INTERVAL_MS`，下一节写着它的代价。

### `USAGE_FLUSH_INTERVAL_MS`：能买回什么，买不回什么

看到「尾巴最长 2 小时」，第一反应是把落盘间隔调小——这条路在本形态下是通的：
`USAGE_FLUSH_INTERVAL_MS` **接受任何正整数**，写 300000（5 分钟）完全合理。
付出的是每个实例每个间隔多写一次分片，买到的是「进程停掉时会随它消失的那段计数」变短。

> [!WARNING]
> **这个值写错是在装配 app 时就拒绝，不是等到第一个请求**（`src/http/usage-sink.ts`）：
> 不是整数、或者小于 1，进程会打印原因并退出。**这道校验与 `USAGE_STATS_ENABLED`
> 开没开无关**（`src/http/wire.ts` 无条件解析它），所以把统计关掉**并不能让它消失**——
> 要么把值改对，要么把这一行删掉。容器起不来是刻意选的症状：它比「统计数据悄悄变歪」
> 好发现得多。

<details>
<summary><b>点击展开：「尾巴最长 2 小时」承诺了什么、没承诺什么（四点）</b></summary>

① **尾巴不等于「迟到」，而且它的两个症状是同一件事**：面板上的「今天」最多可能差一个
   落盘间隔；而**任何一个在下次落盘之前就停掉的实例，会把它累计的那些计数一起带走**。
   计时是从实例启动那一刻开始的，所以一个只活了十分钟就被重建的容器，一个数都没存下。
   这是用量数字全程带「≈」的原因之一，不是缺陷。

② **本形态下没有「每天写预算」这道闸。** 代码里那道闸还在（`budgetPerDay`），但文件
   存储没有写配额要保护，于是网关把它留空：不会有「用尽」，也就谈不上「恢复」与「补写」。
   **别把这句读成「Docker 上不会丢数」**——会丢的是第 ① 点那条尾巴。

③ **同一天最多只留得下 2 个实例的数据，多出来的互相覆盖。** 用量分片按
   `usage:<UTC 日>:<槽>` 存，**只有 2 个槽**，每个实例按自己的分片 id 稳定散列到其中一个。
   所以三个以上容器共用一个卷时，同一个槽里是后写覆盖先写。**这是用量数字带「≈」的另一个
   原因**；它影响的是数字全不全，从不影响网关转发。

④ **三条媒体端点（图片生成、视频建任务、视频轮询）不计数。** 它们烧的是与四条对话协议
   **同一批**上游 key，却什么都不记 ⇒ 面板上的「总请求数」系统性地低于真实转发量。
   这是一条已知边界、不是缺陷；要判断 key 的消耗，看 key 池那一侧。

</details>

### 存储里每一把键的同步代价

文件存储没有读、写、`list`、delete 任何配额——一次重写的代价就是你自己磁盘上的一次写。
真正值得知道的是**一处改动多久才会被别人看见**：这件事对其中两把键是安全属性，对其余
几把是排障时的坑。

#### key 池与它的索引

网关维护一把 `pool:index`，里面列着池子里全部 id，好让转发路径永远不必扫全库。
**有两条自愈路径绕不开一次全量扫描**，它们共用同一个内置的 **10 分钟**退避
（写死的常量，不是环境变量）：

- **空池重扫**——索引解析得开，却一条活记录都读不出来，于是网关扫一次，把「手写进去
  但没进索引」的记录找回来；
- **索引缺失兜底**——`pool:index` 本身读不出来或解析不开，于是网关同样扫一次，尝试重建索引。

池子是空的**并且**那次扫描也失败时，网关回 `500`，真实原因写进日志；它**不会**把这种
失败伪装成 `503 pool_empty`，因为此刻本文档描述的两条自愈路径都已经断了，说一句
「池子是空的」只会把人引去看错的地方。

#### 对外 API 密钥：吊销不是立刻生效

校验一把面板签发的密钥要读一张表，每个实例把它缓存 `APIKEY_CACHE_TTL_MS`（默认 5 分钟）。

- **全部客户端都用 `GATEWAY_TOKEN` 的部署，一次都不读这张表。** 那个零是**结构性**的、
  不是开关：主口令在鉴权的第一段就比完了，那条路径上根本没有读这张表的调用点。
  完全不带凭据的请求同样一次都不读——扫描器撬不动它。
- **签发 / 改名 / 停用 / 删除 / 清空各自整表重写一次**，而且只在人点一下时发生。
  表里有多少把密钥不影响这个次数。

> [!IMPORTANT]
> **停用与删除不是立刻生效的。这一条与安全有关，别把它读成「很快就会生效」。**
> 处理这次请求的那个实例立刻生效；共用同一个卷的别的容器最长还要
> `APIKEY_CACHE_TTL_MS` 才停用 ⇒ 默认约 **5 分钟**。想更快只有调小它，代价只是每个实例
> 每个间隔多读一次表。

#### 面板里点一下会写什么

这些都不计量，但有两种形状值得在点之前知道：

- **导入 M 把新 key** 会写 M 条记录加一次索引，**一次最多 200 把**——超了直接 `400`，
  **不静默截断**。把一次大导入拆成几批不会更便宜，因为索引每批都要重写一次。
- **重复导入同一批 key**（不勾「重置已存在 key 的状态」）**什么都不写**：重复项默认跳过、
  不覆盖，所以重新粘一遍整份清单是安全的。
- **批量删除 N 把** 只重写**一次**索引，不是 N 次；**清空 key 池**同理。
- **改一把 key**（停用 / 启用 / 备注 / 清冷却 / 清 strikes / 解除剔除 / 重置用量计数）
  **无论改的是哪一项，都是一读一写**：它们走同一个 handler、同一次落盘，重置用量计数
  不额外读写任何东西（它清的是内存里那份落盘基线）。

  > [!IMPORTANT]
  > **括号里最后那一项是这里唯一一个「面板上点不到」的**：重置用量计数**今天只有 API，
  > 面板上没有这颗按钮**（同上面 `POOL_TOUCH_INTERVAL_MS` 那一格）。这份枚举列的是那个
  > handler 认得的全部动作，不是面板上按钮的清单；它写在这里，是免得有人以为换条路更贵。
- **「立即补池」是唯一带每日上限的面板动作**——每天最多 **24** 次（第四条护栏，见
  [REGISTRAR.md](REGISTRAR.md)）。这道闸护的是你的临时邮箱名额与上游平台，不是存储预算。
- **保存设置**重写 `config` 那一条，而**校验没过的保存一个字节都不写**。
- **危险区那两颗按钮**：重置配置（`/admin/api/config/reset`）重写的是同一条；清空 key 池
  （`/admin/api/keys/purge`）删掉每一条记录，索引只重写**一次**。

有两笔读扇出出于同样的理由值得知道：

- **面板「用量」板块的 `30d` 那一档**一次请求读 `30 × 2` 个分片
  （`USAGE_DAY_RETAIN × USAGE_SLOTS`）。**这段扇出本仓没有在真机上了结过它**，所以这里唯一
  承诺的是它**如实失败**：中途失败时整条 `days` 序列回 `null`、`note` 是 `read_failed`
  ——它绝不会把已经读到的那几片冒充成完整画面。
- **调试台跑一次视频任务最多 `1 + 60` 次上游请求**（1 次建任务 + 最多
  `VIDEO_POLL_MAX_ATTEMPTS` 拍轮询）。它放大的是**上游**配额与 key 的使用计数，
  与你自己磁盘上的任何东西无关。

### 管理面板相关变量（默认关闭）

| 变量 | 是否必填 | 默认值 | 说明 |
|----|--------|------|----|
| `ADMIN_TOKEN` | 否 | 无（面板不启用） | 管理接口的口令。**必须与 `GATEWAY_TOKEN` 不同**，且至少 24 位；**首尾不得有空白**，且只能由**可打印 ASCII（0x20–0x7E）**组成。字符集、长度下限、与网关口令不同这三条的理由，以及两种不合规各自的后果，见下文。 |
| `TRUST_PROXY` | 否 | 未设置（**任何**转发头都不信） | 只有在网关确实位于代理之后（CDN，或容器前面的 nginx / Caddy / Traefik）时才设成 `1`。它决定登录失败事件里的客户端 IP 从哪里取，见下文。 |

**没配就是面板整个不可用，而网关照常转发。** 此时访问 `/admin/...` 得到的是 **`404` 而不是
`401`**：整棵树压根没注册，因此不会泄漏「这里有个后台」。这与注册机默认关闭是同一条规矩——
`ADMIN_TOKEN` 缺失或配错，绝不能让网关转发停摆。

两行都写进与其余配置同一份 `.env`：

```env
# 可选：管理面板口令。不设 = 整棵 /admin 树不注册。
# 必须与 GATEWAY_TOKEN 不同，且至少 24 位、纯可打印 ASCII。
ADMIN_TOKEN=换成你自己的另一串长随机字符串

# 可选：容器确实位于会改写客户端地址的代理之后时才设成 1。
# 直接暴露的部署不要设它。
TRUST_PROXY=1
```

#### `ADMIN_TOKEN` 的三条硬规则

**「不合规」有两种，后果完全不同，别混成一句：** 未设置、或它自身不合规（首尾空白 / 含非可
打印 ASCII / 短于 24 位）时整棵 `/admin` 树都不注册，日志里是 `admin.token_rejected`；配得
合规、却与生效的 `GATEWAY_TOKEN` 相同时，树**照常注册**、面板本体打得开，只有管理接口每次
返回 `503`，日志里是 `admin.token_conflict`（这条只在每个管理请求上复查，不在启动时拦）。

**首尾不得有空白**：HTTP 请求头的值在传输层会被去掉首尾空白，而环境变量不会，带空白的
口令任何客户端都送不出来。

##### 为什么只许可打印 ASCII

口令还必须只由**可打印 ASCII（0x20–0x7E）**组成，这条限制有三段不同性质的理由：

1. 汉字 / emoji / 零宽空格这类码点大于 U+00FF 的字符，以及换行与 NUL，浏览器在设置请求头时
   **直接抛错**——请求压根发不出去，留着它只会装出一棵 200 但永远进不去的面板，而且服务端
   连一条 `admin.login_failed` 都不会有。
2. **除 TAB 外**的其余控制字符（`0x01–0x08`、`0x0B`、`0x0C`、`0x0E–0x1F`、`0x7F`，共 29 个）
   浏览器送得出去，但会被 HTTP 解析器判成 `400`。
3. **TAB（`0x09`）**与 `é` / `£` / 不间断空格这类 `0x80–0xFF` 的字符**其实送得出去也能用**，
   拦它们是本网关的**稳健性取舍**而不是物理限制；**两者的理由并不相同**：TAB 是**不可见
   字符**，粘进 `.env` 或 secret 里没人看得见（与首尾空白同类的可诊断性问题，只是那条是物理、
   这条是取舍）；`0x80–0xFF` 则是编码口径问题——环境变量按 UTF-8 解、HTTP 头值按 Latin-1 解，
   两边在这一段并不由规范保证一致，
   而 RFC 9110 已把这段标为弃用。

请用纯 ASCII 口令。**中间带空格是允许的**——`correct horse battery staple` 这类 passphrase
送得出去也送得到，而且在 24 位下限之下它往往比随机串更好记、更不容易抄错；首尾空白由上面
那条规则管着。

##### 为什么有 24 位的下限

**为什么有 24 位的下限。** 本网关**没有任何登录限速**——不按 IP、不按口令、也不按实例。
要做它就得在存储里开一个计数窗口，那等于给一个未鉴权的调用方一根「让网关按需写盘」的杠杆，
把攻击面从「猜口令」扩大到「让它循环重写 `store.json`」。因此口令熵是这里唯一的防线，
下限不是建议值。低于下限时面板不会启用，容器日志里会有一条 `admin.token_rejected`。

##### 为什么必须与 `GATEWAY_TOKEN` 不同

**为什么必须与 `GATEWAY_TOKEN` 不同。** `GATEWAY_TOKEN` 是你发给**每一个下游用户**的中转
口令。复用它当面板口令，等于任何拿到中转口令的人都能读走你的整池 key、关掉注册机、把注册
后端指向他自己的服务器——从此每一次注册的邮箱、密码、验证码都会被他收走。

##### 冲突怎么被发现、怎么处置

这条规则**只在每一个管理请求上复查，不在启动时拦**。若两者相同——例如直接编辑
`store.json` 手工把 `gatewayToken` 写成了管理口令——管理
接口会**返回 `503`**，同时打一条 error 级的 `admin.token_conflict`（启动时就撞上冲突的话，
启动日志里也会有同样一条，方便你立刻看到原因）。**网关转发不受影响。**

**冲突一旦成立，`ADMIN_TOKEN` 必须按已泄漏处置——恢复方式只有一条：把它轮换成一把全新的口令。**
改 `.env` 之后跑一次 `docker compose up -d`，让容器带着新值重建。
**别只把存储里的 `gatewayToken` 改回去。** 那确实能让管理接口立刻恢复（配置缓存下一次刷新之后生效，
不需要重启），但它救的是可用性、不是安全性：冲突期间这把管理口令与中转口令是同一个值，
而中转口令是发给**每一个下游用户**的——只要它曾经被发出去过（或者接下来会被发出去），
拿着它的人就能直接开你的后台。可用性可以靠改 `gatewayToken` 先恢复，
但那之后**仍然要轮换 `ADMIN_TOKEN`**，两步都做完才算处置完。

##### 为什么这一条刻意不在启动时拦

**为什么这一条刻意不在启动时拦。** `gatewayToken` 运行中会变，而启动时的判定没有第二次求值的
机会：一旦在那里把整棵 `/admin` 树反注册掉，冲突期间启动的每一个容器都会**永久 404**，
把配置改回去也救不了，必须再重启一次——而冲突之前起来的那个只是 `503`，改回去立刻恢复。
同一份配置、同一时刻两种结果，上面那句「不需要重启」就成了半句假话。
相比之下 `ADMIN_TOKEN` 自身的三条规则（首尾空白 / 含发不出去的字符 / 长度不足）只取决于环境变量，运行中不会变，
所以它们仍然在启动时拦，失效形态是 `404`。

##### 怎么轮换，泄漏了怎么处置

`ADMIN_TOKEN` **只从环境变量读、不从存储读**：面板不能自助轮换自己的钥匙。轮换方式：改
`.env` 之后跑 `docker compose up -d`——`docker compose restart` 不行，因为容器的环境在创建
那一刻就冻住了。

**管理口令泄漏 = `ADMIN_TOKEN` 泄漏。** 面板把它原样存在浏览器的 localStorage 里，没有派生令牌，
也没有产品内的撤销路径。撤销方式只有一条：改 `.env` 里的值之后重建容器。
面板会在 12 小时后要求重新输入口令，但那只缩短这份 localStorage 值的可用窗口，**不等于撤销**。
请把面板放在 TLS 之后，并且只在你信任的机器上打开它。

**这个上限做不到什么，也一并说清楚。** 面板的 CSP 用 `connect-src 'self'` 挡住了把口令 `fetch`
到外部域名，用 `form-action 'none'` 挡住了表单外传；但它挡不住
`location.href = "https://…?k=" + token` 这种**导航式外传**——CSP 规范里已经没有可用的指令拦它
（`navigate-to` 已被移除）。真正的解法是服务端签发**可撤销的派生令牌**，那要求服务端存储会话，
与「`ADMIN_TOKEN` 只从环境变量读、不从存储读」这条设计约束冲突，因此留给后续版本。

#### `TRUST_PROXY` 决定客户端 IP 从哪里取

设了之后，登录失败事件里的客户端 IP 取自 `CF-Connecting-IP`，缺席时才退到
`X-Forwarded-For` 的首段。

**`TRUST_PROXY` 是安全开关，所以默认关闭。** 它决定的客户端 IP 会写进 `admin.login_failed`
事件，无脑信任一个由客户端提供的头，等于允许任何人把爆破痕迹嫁祸给任意 IP。

**关闭时任何转发头都不信，该字段一律记 `null`——`CF-Connecting-IP` 也不例外。** 这个头常被说成
「平台注入、伪造不了」，但那个性质**只在请求真的经过 Cloudflare 时**成立；Node/Docker 直连暴露时
没有任何东西会覆盖它，客户端自己发一个 `CF-Connecting-IP: 1.2.3.4` 就会被采信——而直连正是 Docker
部署的默认形态。

**打开时 `CF-Connecting-IP` 优先，`X-Forwarded-For` 只作兜底。** 两个头的可伪造性根本不同：

- `CF-Connecting-IP` 由 Cloudflare 边缘写入，并且会**覆盖**客户端传来的同名头——只要请求真的经过
  Cloudflare，它就伪造不了。
- `X-Forwarded-For` 是任何中间件都能追加的链，客户端可以自己发一个假的，可信与否完全取决于你的
  代理链长什么样。

##### 两种拓扑各自怎么配

**源站前面挂着 Cloudflare 时请设 `TRUST_PROXY=1`。** Cloudflare 会在每个请求上重写
`CF-Connecting-IP`，它因此是权威值；这种形态下优先 `X-Forwarded-For` 是错的——那条链里可能
装着客户端自己塞的东西。不设这个开关的话，该字段就只是记成 `null`。**等源站真的不能被直连
之后再打开它**，否则绕过 CDN 的客户端会自己带一个头进来。

**通用反代（nginx / Caddy / Traefik）后面打开 `TRUST_PROXY=1` 时，请在反代上把
`CF-Connecting-IP` 剥掉。** 那种拓扑里没有任何东西会覆盖这个头，而网关按「Cloudflare 在前面」
优先采信它，于是攻击者自带一个就会**压过**反代刚写好的 `X-Forwarded-For`。nginx 加一行即可：

```nginx
proxy_set_header CF-Connecting-IP "";
```

Caddy 用 `header_up CF-Connecting-IP ""`，Traefik 用中间件的 `customRequestHeaders`。

##### 形态校验，拿不到就如实记 `null`

**两个头都会先过一遍形态校验**：只有 IPv4 点分十进制与 IPv6 形态（十六进制、冒号，以及
`::ffff:` 映射里的点）能进事件，其余一律记 `null`。这条不是鉴权防线（这个值全仓只有登录失败
事件一个消费点），它防的是「未鉴权的调用方往审计字段里塞任意文本」——管理面板的事件板块
要按这个字段做筛选与展示。

什么都拿不到时该字段如实记 `null`，**绝不伪造一个 `"unknown"`**——那会被当成一个真实来源。

### 设置页能改什么

这几个字段在面板上分三张卡：**认证密钥**与**上游与冷却**在**设置**页上，**注册机**那张
（含两条完全平级的邮箱通道子卡与一个「高级」折叠区）在**注册机**板块的「设置」分页里。
三张卡写的都是**存储里那个 `config` 键**，而不是环境变量。

**每个字段显示三个值，不是一个。** 一行「存储 X · 环境变量 Y · 生效 Z」把
「你保存的是什么」「部署那一侧给了什么」「网关实际在用什么」分开写。
优先级恒为 **环境变量 > 存储 > 内置取值**。

#### 被环境变量锁定的字段，面板直接不让改

**被环境变量锁定的字段，面板改了不会生效——所以面板直接不让改。**
那一格的输入框置灰，旁边写着是哪个环境变量、以及要改就得改部署那一侧。
`PUT /admin/api/config` 对这类字段一律返回 `400 locked_by_env`，**不写存储**：
写下去的后果是「保存成功、生效值纹丝不动」，运维会以为是缓存没刷，白等两轮。

> [!IMPORTANT]
> **注册机那一族（`REGISTRAR_ENABLED` / `REGISTRAR_CHANNEL`（连同它的兼容别名）/
> `TARGET_KEYS` / `MINT_BATCH` / `TEND_INTERVAL_MS` / `CODE_TIMEOUT_MS` / `MINT_DELAY_MIN_MS` /
> `MINT_DELAY_MAX_MS` / `MAX_DOMAIN_ATTEMPTS` / `REGISTRAR_TOKEN_NAME` / `AGNES_PLATFORM_URL` /
> `YYDS_BASE_URL` / `YYDS_API_KEY` / `MOEMAIL_BASE_URL` / `MOEMAIL_API_KEY`）也进了这张锁定表。**
> 在此之前它们不在表里：`docker-compose.yml` 里写了 `TARGET_KEYS=30`、面板上改成 20，
> 保存成功而生效值永远是 30，**重启也不会好**，面板上还没有任何提示。

#### 凭据只写不读

**凭据只写不读。** 网关口令与两条通道的 API Key 在接口里**永远不返回明文**，只返回
「配没配」与**末 4 位**（不足 5 位时连末 4 位都不给——给了就是给全）。因此：

- 输入框永远是空的，占位符写着**留空则不修改**；
- 保存时这几格**缺席或留空 = 不改**（不是清空）。若把留空实现成清空，运维保存一次设置页
  就会抹掉网关口令，而**当前进程靠上一份快照还能继续跑**，直到下一次重启才整个停摆；
- 清空只能走那颗单独的「清空」按钮（带二次确认）。

##### 面板写进去的凭据怎么落盘

> [!WARNING]
> **面板写进去的凭据以明文落在 `store.json` 里**，与「key 明文存盘」同一水位。
> 别以为这里输的是加密过的 secret。数据目录请按凭据处置。

> [!WARNING]
> **清掉网关口令而环境变量里也没有 `GATEWAY_TOKEN` 时**：当前进程还能跑，
> 但**下一次重启会起不来**。面板会当场用一条红色提示说破这件事，
> 恢复方式是立刻在同一页写一把新的网关口令。**而环境变量里有这一项时清空是安全的**：清掉的只是存储里那一份，生效值回落到环境变量，纹丝不动——面板会按这两种状态说两句不同的话，不会让你自己猜。

#### 「高级」区里的那个注册后端地址

> [!WARNING]
> **「高级」折叠区里那个注册后端地址（`AGNES_PLATFORM_URL`）不是普通配置项。**
> 它是**每一次自动注册的去向**：换成别的服务器，那台服务器就会收到本网关注册时用的
> 邮箱、密码与验证码。所以它折在高级区里、带红色警告、有自己的二次确认按钮，
> 不跟主表单那颗「保存」一起走。

#### 保存回执与传播时延

**保存之后面板不弹「已保存并生效」**，而是**回读**一遍生效值，把真的变了的字段高亮，
并写明**别的副本最长多久才看得到**：配置持有者最多每 **30** 秒刷新一次，那就是上界。
本实例是立刻生效的（保存那一步会作废本地缓存），共用同一个卷的别的容器不是。
**面板文案不许写「立即生效」。**

| `YYDS_BASE_URL` / `YYDS_API_KEY` | 否 / 通道为 yyds 时必填 | `https://maliapi.215.im` / 空 | YYDS Mail 通道凭据。 |
| `MOEMAIL_BASE_URL` / `MOEMAIL_API_KEY` | 通道为 moemail 时必填 | 空 / 空 | MoeMail 通道凭据（自建服务，无默认地址）。 |

> 现在它安静地跑着，得自己去看面板横幅或者事件板块。
> 走一遍的入口是下面「常见问题」里的「注册机开着却不铸 key」那一条。

### 两档超时分别管什么

判据是「上游的第一个字节什么时候才可能到达」，不是端点的名字：

| 档位 | 适用端点 | 用哪个变量 |
|----|--------|----------|
| 首字节档 | **流式**对话（`stream: true`）、视频轮询 `GET /v1/videos/{id}` | `UPSTREAM_TIMEOUT_MS` |
| 同步档 | 图片生成、视频建任务、**所有非流式对话**（四种协议均如此） | `UPSTREAM_SYNC_TIMEOUT_MS` |

非流式请求要等上游把整段回答生成完才发响应头，和图片生成是同一种延迟语义，用 8 秒的
首字节档去卡它只会让正常请求大量失败并连累 key 池。

`UPSTREAM_SYNC_TIMEOUT_MS` 是**一次请求的总预算**，也就是客户端的最坏等待时间——不是
「池大小 × 预算」。网关在这个预算里最多为单把 key 花掉一半，剩下的用来换一把 key 再试，
这样池里有一把 key 挂起（连得上但永不响应）时不会白白吃掉这次请求。因此把它设成
**单次调用最坏耗时的两倍以上**。

同步档超时不会立刻惩罚 key：只有当同一次请求里换的另一把 key 真的成功了，网关才把超时
算到先超时的那把 key 头上（累计到 `MAX_STRIKES` 进冷却）；如果本次请求里每一把都超时，
则一把都不惩罚——那更可能是预算配小了或上游整体变慢。

「剔除」与「冷却」是两回事。无论以上参数如何设置，上游 `401`/`403` 都会**永久**剔除该
key——这两种状态被视为「这个 key 已失效」，重试没有意义。瞬时故障则永远不会导致剔除：
累计到 `MAX_STRIKES` 只是进入 `COOLDOWN_STRIKE_MS` 的冷却，到期自动恢复，因此上游抽风
不会永久损毁你的 key 池。

当没有任何 key 能服务本次请求时，网关返回 `503`，并在 `error.reason` 里给出可判别的原因：
`pool_empty`（尚未导入 key）、`all_cooling`（全部 key 冷却中，会自动恢复，响应头 `Retry-After`
给出恢复时刻）、`all_evicted`（全部 key 因凭据失效被永久剔除，**不会**自愈，请更换 key）、
`upstream_error`（key 本身可用，但上游每次尝试都失败）。

### 超长的非流式请求会不会被从中间砍断（取决于挡在前面的那一层）

**结论：网关自己除了 `UPSTREAM_SYNC_TIMEOUT_MS` 之外不设任何墙钟，所以能把一个健康的长
请求砍断的，只可能是挡在它前面的东西。**

容器里跑的这个 Node 进程**没有任何平台时长上限**：一次非流式请求只受你配的预算约束，
再没有别的。这就是本文做出的全部承诺，面板也不做更大的承诺。

**挡在你前面的那一层要你自己去查**，逐条写明：

- 反向代理有自己的读超时，而且默认值都不长：nginx 的 `proxy_read_timeout` 是 60 秒，
  Caddy 自己不限但它的上游未必。要调就与 `UPSTREAM_SYNC_TIMEOUT_MS` 一起调，否则先砍
  的是代理。
- 源站前面再挂 CDN 会多一层：Cloudflare 文档化的**回源读超时是 100 秒（错误码 524）**，
  网关任何配置都延长不了它。
- 负载均衡器的空闲超时同理，而且从客户端那一侧看症状一模一样：连接就这么断了，
  连一个 `error.reason` 都没有。

⇒ **实际影响两条**：
① 把 `UPSTREAM_SYNC_TIMEOUT_MS`（默认 120000）设在**你前面那条链里最紧的那个超时之下**，
   否则本来网关能跑完的请求会被别人砍断，而那个原因永远进不了日志。
② **真要跑长请求就用流式端点。** 首字节档只管首字节，之后生成花多久都不计；而且一条持续
   出字节的流，在整条链上看起来都不像「空闲」。

## 多账号配置

导入 key 的常规路径是管理面板，或者直接调 `POST /admin/api/keys`（一次最多 200 把，
见 [API.md](API.md) 与 [ADMIN.md](ADMIN.md)）。下面这套**直接写存储后端**的做法只用于
两种场景：还没配 `ADMIN_TOKEN`（面板整棵树都不注册），或者面板不可用时的应急恢复。
它**不会更新 `pool:index`**，因此新记录未必立刻可见，代价见下面的「索引与可见时延」。
每条记录是一个
键为 `key:<id>` 的 JSON 对象，`<id>` 可以是池内唯一的任意字符串（网关自己创建记录时
会用 key 的哈希值派生一个，但读取时不校验这个值，所以手动导入时用任意唯一标识即可）：

```json
{
  "id": "1a2b3c4d5e6f7a8b",
  "key": "你的真实-agnes-api-key",
  "addedAt": 1735689600000,
  "lastUsedAt": null,
  "cooldownUntil": 0,
  "strikes": 0,
  "evicted": false,
  "evictedReason": null
}
```

### 导入到 Docker

先停止容器，避免与正在运行的进程产生写入竞争；在宿主机上编辑 `./data/store.json`，
在键 `"key:1a2b3c4d5e6f7a8b"` 下加入如上记录，然后再启动容器：

```bash
docker compose stop
# 编辑 ./data/store.json
docker compose start
```

如果 `./data/store.json` 还不存在，直接新建一个 JSON 对象文件，键为若干个
`key:<id>` 字符串即可。

### 索引与可见时延

网关用一个 `pool:index` 键保存池内的 id 列表，这样每次转发都不必扫全库。**手工写记录不会
动这个索引**，所以新 key 多久能被用上，取决于池子当时的状态：

- **池子为空时**：索引说池子是空的、记录也确实一条都读不到，网关会回落一次扫描把手工导入
  的记录发现并补进索引。这条扫描有内置的 10 分钟退避（见上文「key 池与它的索引」），因此
  可见上界是 **≤10 分钟 + 一个 `POOL_CACHE_TTL_MS`**。
- **池子非空时**：转发路径只按索引取记录，索引不知道的记录**完全隐身**，而且没有任何报错。
  它要等下一次对账把索引修好（`TEND_INTERVAL_MS`，默认 30 分钟），之后再等最多一个
  `POOL_CACHE_TTL_MS`。

**想让手工导入立刻生效，就在同一次编辑里把 id 补进 `pool:index`：**

```json
{"v":1,"ids":["已有的id","1a2b3c4d5e6f7a8b"]}
```

索引写完之后，池子最多再等一个 `POOL_CACHE_TTL_MS` 就会用上这把 key。

**对账与注册机开没开无关**，走的是同一个 `TEND_INTERVAL_MS` 定时器：它是 `pool:index` 与
实际 `key:` 记录之间唯一的修复路径，所以孤儿记录或幽灵索引项会在一个间隔之内被收回。
把这个间隔设成一个离谱的大值，这段等待就等量变长；等待期间该 key 只是暂时用不上，
不会丢失也不会损坏。

### 吊销一把 key

**删记录、再把 id 从 `pool:index` 里摘掉，两步都要做。** 只删记录不会出错（读不到的记录会被
直接过滤掉），但索引里那个 id 还在，每次刷新都白付一次读，要等下一次对账才会被剪掉。

在 `./data/store.json` 里删掉 `"key:<id>"` 那个键，并把 `"pool:index"` 的 `ids` 数组改好；
先 `docker compose stop`，免得还在跑的进程把你的编辑覆盖掉：

```json
{"v":1,"ids":["剩下的id"]}
```

已经装载了旧快照的进程最多再等一个 `POOL_CACHE_TTL_MS` 才会停止选中这把 key。

**这段窗口里它也不会被写回来**：网关在落盘任何状态变更之前都会先确认记录还在，读不到就
丢弃这次写并立刻刷新自己的快照。文件存储的这次确认读直接读文件、中间没有任何缓存，
所以这条保证是精确的。

## 验证部署

三条命令，从最便宜的一条开始。把 `$BASE` 换成你自己的地址（没改 `PORT`、前面也没挂域名
的话就是 `http://localhost:8080`），`$TOKEN` 换成你设的 `GATEWAY_TOKEN`。

### 健康检查

```bash
curl -s "$BASE/health"
```

`status` 为 `ok` 表示存储可读可写；`degraded` 表示存储那一侧有问题，具体原因见日志。
**这一条不需要令牌**，所以它也是唯一一条在令牌配错时仍然回得来的端点。

### 模型列表

```bash
curl -s "$BASE/v1/models" -H "Authorization: Bearer $TOKEN"
```

回来的是本网关支持的模型清单。这一条能过，说明令牌对上了；回 `401` 就是令牌不对。

### 一次真实对话

```bash
curl -s "$BASE/v1/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"agnes-2.0-flash","messages":[{"role":"user","content":"ping"}]}'
```

这一条才真的打到上游。回 `503` 且 `error.reason` 是 `pool_empty`，说明池子里还没有 key，
回上面那一节导入一把。

## 常见问题

七条按会遇到的先后排。每条都是「症状 → 解决方案」，解决方案按顺序做。

### 网关起不来，日志里只有一行缺少令牌

**症状**：容器**一启动就退出**，`docker compose ps` 上是 restarting 或 exited，日志里只有
`缺少 GATEWAY_TOKEN，网关无法启动` 这一行。**这里没有「半死不活」这一档**：网关宁可拒绝装配，
也不会每个请求回 `503`，所以不用谁去打端点，`docker compose ps` 上就看得见。

**解决方案**：

1. 确认 `.env` 里有 `GATEWAY_TOKEN=`，而且**等号后面不是空的**。
2. 改完跑 `docker compose up -d`，**别用 `docker compose restart`**——容器的环境在创建那一刻
   就冻住了，restart 什么都不会重读。

> [!WARNING]
> **不要用 `RESET_CONFIG=1` 来救这一条。** 它的语义是**完全忽略存储里的 `config` 键**
> ——如果你的网关口令正是存在那里的（面板保存的那把），忽略它只会让唯一的一把口令也一起消失。
> 这条故障只有上面两步能修。

### 所有请求都回 503，理由是池子空的

**症状**：任何一条转发端点都回 `503`，`error.reason` 是 `pool_empty`。

**解决方案**：

1. 在管理面板的 key 池页导入至少一把 key，或者调 `POST /admin/api/keys`（见 [API.md](API.md)）；没配 `ADMIN_TOKEN` 时按「多账号配置」那一节直接写存储后端。
2. 已经导入了却仍然是空的：手工写记录**不会动 `pool:index`**，等一次对账（`TEND_INTERVAL_MS`，默认 30 分钟）或者手动把 id 补进索引。
3. 注册机开着但池子不涨：去看面板的事件板块，或按 [REGISTRAR.md](REGISTRAR.md) 排查两条邮箱通道。

### 注册机开着却不铸 key（面板说已启用，池子却一直不涨）

**症状**：注册机的开关是开着的，但补池一轮都没跑：池子里的 key 只减不增，
最终以上面那条「所有请求都回 503，理由是池子空的」的形式炸出来——而那时离真正的原因已经隔了好几层。

这是一次**安静的功能缺失**：注册机是可选子系统，它的配置装不起来时**网关照常转发**，
只是不再补池。没有任何东西会崩，所以你得主动去看。

**怎么看**（四处指的是同一件事）：

1. 管理面板的**设置**页顶部有一条横幅：「注册机开着，但这份配置装不起来，本次没有启动它；转发不受影响」，
   下面逐条列出缺哪几格。
2. **注册机**板块的运行状态那一行写的是「已启用 · 本次没跑起来」，不是「已启用」。
3. **概览**页的配置摘要里，「注册机」那一行同样写「已启用 · 本次没跑起来」。
4. 事件板块里每一轮都有一条 `error` 级的 `registrar.blocked`，字段里列出缺的那几格。

**解决方案**：按横幅列出的那几格去设置页补齐（最常见的是选中那条邮箱通道缺 API Key，
或者压根没选通道），**保存即可恢复，不需要重启容器、也不需要重新部署**。

### 面板打不开，`/admin` 回 404

**症状**：浏览器打开 `/admin` 得到 `404`，不是登录页，也不是 `401`。

**解决方案**：

1. 这就是**没配 `ADMIN_TOKEN`** 时的正常形态：整棵树压根没注册，所以不会泄漏「这里有个后台」。
2. 配了仍然 404，**先确认容器真的重建过**：Docker 形态下改完 `.env` 要跑 `docker compose up -d`，`docker compose restart` 不会重读它。这一步没做的话，下面第 3 条会把你引向一个错误的方向。
3. 重建过仍然 404：口令不合规（少于 24 位 / 首尾有空白 / 含非可打印 ASCII），容器日志里会有一条 `admin.token_rejected`。
4. 面板能开但接口回 `503`：`ADMIN_TOKEN` 与存储里的 `gatewayToken` 撞了，日志里是 `admin.token_conflict`，按上文那一段处置。

### 改了面板里的设置，别的实例半天不生效

**症状**：在面板里保存了配置，本实例立刻变了，共用同一个卷的另一个容器还是旧值。

**解决方案**：

1. 这是**正常的**：配置持有者最多每 **30** 秒刷新一次，那就是上界。等一等再看。
2. 超过两分钟仍然不变：确认那个字段没有被环境变量锁住——被锁的字段面板会置灰，接口回 `400 locked_by_env`。
3. 改的是 `POOL_CACHE_TTL_MS` / `POOL_TOUCH_INTERVAL_MS` 这两个旋钮：它们**建实例时读一次**，只能重建容器。

### 非流式请求大量超时，key 池跟着变红

**症状**：图片生成、视频建任务或非流式对话成片超时，面板上一批 key 进了冷却。

**解决方案**：

1. 把 `UPSTREAM_SYNC_TIMEOUT_MS` 调到**单次调用最坏耗时的两倍以上**：默认 `120000` 对慢模型偏紧。
2. 别拿 `UPSTREAM_TIMEOUT_MS`（首字节档，默认 `8000`）去卡非流式请求——那一档是给流式与视频轮询的。
3. 确认不是上游整体变慢：同一次请求里每一把 key 都超时时，网关**一把都不惩罚**，冷却只会在换的另一把真的成功之后才记。

### Docker 容器起来了，但 `/health` 是 degraded

**症状**：`docker compose ps` 显示 unhealthy，`/health` 回 `503`，`status` 是 `degraded`。

**解决方案**：

1. 九成是数据目录写不进去。看容器日志里 entrypoint 那几行，确认 `./data` 的属主是不是 `100:101`。
2. 用 `--user` 或 compose 的 `user:` 指定了非 root 运行时，entrypoint **不会** chown，属主与可写性得你自己准备。
3. `DATA_DIR` 被设成 `/` 或某个顶层系统目录时 entrypoint 拒绝递归 chown，只打警告——换一个正常的目录。
4. **属主查了三遍都对，却还是 degraded**：多半是 `store.json` 解析不了。前三条全是权限，这一条不是——存储层读不出合法 JSON 时每次读写都抛，启动探测因此把「可写」记成 false，`/health` 同样回 `503` degraded。停容器后 `python3 -m json.tool ./data/store.json` 验一下：上文「多账号配置」教的手工编辑正是最常见的写坏方式（多一个逗号就够），坏了就从备份恢复。真因原文在容器日志的第一行。

## 性能优化

先认清一件事：**这个网关自己几乎不花时间**，开销在两处——上游的响应时间，以及存储的读写配额。
所以这一节只有三个旋钮值得动。

```env
# 可选：每个进程缓存 key 池快照的存活时长，单位毫秒；0 = 关闭缓存。
# 调大 = 省文件读；代价是别的容器写下的状态更晚才可见。
POOL_CACHE_TTL_MS=120000

# 可选：「最后使用时间」最多多久落盘一次，单位毫秒；0 = 每次成功请求都落盘。
# 它是纯展示字段，调小只会等量放大写盘次数，换不来任何调度上的好处。
POOL_TOUCH_INTERVAL_MS=21600000

# 可选：同步端点（图片、视频建任务、所有非流式对话）的整体超时预算，单位毫秒。
# 设成单次调用最坏耗时的两倍以上，否则正常请求会被误杀并连累 key 池。
UPSTREAM_SYNC_TIMEOUT_MS=180000
```

三条经验，按收益排：

1. **除非有多个容器共用一个卷，否则别动 `POOL_CACHE_TTL_MS`。** 单容器时那份快照就是权威，
   调大它买不到任何东西，只会让「手工改了 `store.json`」这件事更晚被发现。真跑起副本、
   并且看到同一把 key 被判两遍的时候，再调大它。
2. **别为了让面板上的「最后使用」准一点去调小 `POOL_TOUCH_INTERVAL_MS`。**
   那是纯展示字段，`0` 的意思是「每次成功请求都整份重写一遍存储」，而你买到的那个精度
   没有任何调度逻辑会去读。
3. **长请求改用流式端点。** 首字节档的超时只卡第一个字节，后面生成多久都不再计时；
   非流式那一档要等上游把整段答案算完，而挡在你前面的代理可能比你的预算先动手。

## 监控和维护

### 健康端点

`/health` 是唯一不需要令牌的端点：

```bash
curl -s "$BASE/health"
```

`status` 为 `ok` = 存储可读可写；`degraded` = 存储那一侧有问题，多半是数据目录写不进去。
镜像内置的 `HEALTHCHECK` 就是打这条，`docker compose ps` 里的 healthy/unhealthy 由它来。

### 面板的事件板块

配了 `ADMIN_TOKEN` 之后，面板的事件板块会按级别列出网关自己记下来的诊断事件
（登录失败、口令冲突、补池失败、预算耗尽……）。它**不是日志的替代品**：只保留 24 小时，
而且单次轮询最多回看 48 个键。要长期留存就去接容器日志。

### 用量统计（默认关）

按天／小时／模型／协议的时间序列**默认关**，而且「关」是零成本的——不建累加器、一次存储写都没有。
要打开：

```env
# 可选：面板「用量」板块的 Tier-2 时间序列。判据是逐字的 true，写 1 / yes 都算关。
# 打开之后每个实例每个落盘间隔重写一次分片；未落盘的尾巴最长 2 小时。
# 那条尾巴会直接变成丢数：进程在这段窗口里停掉，计数就随它消失，不是延迟到账。
USAGE_STATS_ENABLED=true
```

**打开之前先读一遍上面那两条警示。** 会丢的正是进程停掉那一刻还攥在手里的那些计数，
而为改一个环境变量重建一次容器就足以触发它。本形态下 `USAGE_FLUSH_INTERVAL_MS` 想调多小
就调多小——这笔取舍归你，不是外面强加的限制。

## 升级服务

两条升级命令写在 [Docker 部署](#docker-部署) 的「更新」里。这一节讲的是那两条命令之外的事。

### 升级前

1. **先备份存储。** key 池与配置只有一份，见下文「备份和恢复」。
2. **记下基线：当前的 `version` 与 key 池条数。** 前者就是 `curl -s "$BASE/health"` 回的那个字段，后者在面板概览页。没有基线，下面那三条确认就分不清「升上去了」和「压根没升」。
3. **看一眼 CHANGELOG。** 破坏性变更会写在那里；本仓的版本号在六份 README 的徽章上。
4. **升级不需要清空存储。** 存储里的记录是向后兼容的，`pool:index` 的 `v` 字段今天恒为 `1`。

### 升级之后确认什么

1. `/health` 回 `200`、`status` 为 `ok`，**并且 `version` 等于你这次升的版本号**。三条里只有这半句分得开「升上去了」和「压根没升」：`version` 是编译期常量、烧在镜像里，而另外两条在旧版本上一字不差地全绿。镜像没发出去时（构建被取消而 Release 已经发了，本仓真出过一次）`docker compose pull` 是一次静默成功的空操作。
2. 面板（如果开着）能登录，key 池的条数与升级前一致；概览页运行时那一格也写着版本号，与上一条互为佐证。
3. 跑一次上文「验证部署」里的第三条，确认真的能打到上游。

回滚：Docker 把 `.env` 里的 `IMAGE_TAG` 改回上一版再 `docker compose up -d`（镜像全名与
tag 列在哪儿，见上文「Docker 部署 → 更新」）。
**先确认那个 tag 在 registry 上真的存在**：拉不到时 compose 不会当场失败，而是拿你**当前
工作树**本地构建一个顶着那个版本号的镜像，于是回滚「成功」而故障照旧。

## 备份和恢复

key 池与配置只有一份，没有第二副本。**备份就是备份存储本身。**

### 怎么备份

```bash
docker compose stop
cp -a ./data ./data.bak
docker compose start
```

停一下再拷是为了避开写入竞争。恢复就是把目录拷回去再 `docker compose up -d`。

### 里面有什么，以及为什么挑着抄是个坑

`./data/store.json` 里就是全部——不只是 key 记录与 `pool:index`，还有
`apikeys`（已签发的对外 API 密钥表）、`config`（面板保存的那份配置）、
`registrar:domains` 与 `registrar:backoff`（注册机的域名可用性与退避账）、
`tend:history`（补池历史），以及事件环。

> [!CAUTION]
> **只从那份文件里挑 `key:<id>` 与 `pool:index` 抄出来，会漏掉四族键，而漏掉它们在恢复
> 现场一点都看不出来。** 照那种挑法恢复之后：上游 key 池回来了、`/health` 回 `ok`、
> 你自己拿 `GATEWAY_TOKEN` 一测也通——而每一个下游用户手上的子密钥全部 `401`。
> 漏的是这四族：`apikeys`（不恢复它等于把所有子密钥一次吊销，而明文只在签发那一次给过、
> 找不回来，只能全部重发一遍）、`config`（面板保存的配置，含网关口令与两条邮箱通道的
> 凭据）、`registrar:domains` 与 `registrar:backoff`（丢了之后注册机变成
> 「已启用 · 本次没跑起来」）、`tend:history`（补池历史）。
> **上面那条 `cp -a ./data` 完全没有这个问题**——这正是它被选成推荐做法的理由。

> [!WARNING]
> 备份文件里是**明文 key 与明文凭据**（网关口令、两条邮箱通道的 API Key 都在存储侧的配置里）。
> 请按凭据处置：别放进仓库、别放进公开的对象存储。

## 安全建议

- **`GATEWAY_TOKEN` 与 `ADMIN_TOKEN` 必须是两把不同的口令。** 前者是发给**每一个下游用户**的中转口令，
  拿它当面板口令等于把整池 key、注册机开关、注册后端地址一起交出去。
- **面板放在 TLS 之后，只在你信任的机器上打开。** 面板把 `ADMIN_TOKEN` 原样存在浏览器的 localStorage 里，
  没有派生令牌、也没有产品内的撤销路径；12 小时后要求重新输入只缩短窗口，**不等于撤销**。
- **`TRUST_PROXY` 只在网关真的位于代理之后时才打开。** 通用反代后面打开它时，请在反代上把
  `CF-Connecting-IP` 剥掉，否则攻击者自带一个就能压过反代刚写好的 `X-Forwarded-For`。
- **数据目录与备份文件一律按凭据处置。** key 与面板写进去的凭据都是明文落盘的，
  与 key 明文存盘是同一水位。
### 对外 API 密钥与上游 key 池方向相反

- **对外 API 密钥的明文只出现一次。** 面板签发时那一次响应里带着它，此后任何接口都拿不到
  ——网关只存它的 SHA-256 摘要。丢了找不回来，只能删掉重发；**这与上游 key 池是相反的两件事**
  （那一族必须明文落盘，因为要拿去用）。
- **给不同的下游各发一把子密钥，别把 `GATEWAY_TOKEN` 分出去。** 前者可以逐把停用、设到期、
  随时吊销，而后者一旦分出去，唯一的撤销方式是轮换它、让所有下游同时失效。

一份最小的安全基线配置：

```env
# 必填：客户端调用本网关时必须携带的令牌。发给下游用户的就是它。
GATEWAY_TOKEN=换成你自己的长随机串

# 可选：管理面板口令。不设 = 整棵 /admin 树不注册，访问得到 404 而不是 401。
# 必须与 GATEWAY_TOKEN 不同，且至少 24 位、纯可打印 ASCII。
ADMIN_TOKEN=换成另一把长随机串

# 可选：容器确实位于会改写客户端地址的代理或 CDN 之后时才设成 1。
# 直接暴露的部署不要设它。
TRUST_PROXY=1
```
