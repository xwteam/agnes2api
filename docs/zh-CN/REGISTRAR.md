# 注册机（自动补池）

本文讲注册机：它做什么、两条邮箱通道怎么选、有哪些配置项，以及跑起来之后怎么看日志与排障。

> **默认关闭。** `REGISTRAR_ENABLED` 默认为 `false`，装上本项目不会自动开始注册任何账号；
> 只有显式把它设为 `true` 才会启用注册机。

## 它是什么

注册机是一个可选组件：当 key 池中的可用 key 数低于 `TARGET_KEYS` 时，它会自动注册新的
Agnes 账号、登录、铸出一把 API key 写入池子。注册过程需要接收 Agnes 发来的邮箱验证码，
因此依赖下文的邮箱通道之一。

> [!WARNING]
> **合规提示**
>
> 批量注册与 Agnes 服务条款之间存在张力。是否启用注册机、以何种频率使用，须由部署者自行
> 判断并承担相应责任——本项目不替使用者做这个决定。

## 两条邮箱通道：如何选择

注册机支持两条邮箱通道，用来接收验证码：

### 两条通道的对照

| | YYDS Mail | MoeMail |
|----|---------|-------|
| 性质 | 第三方临时邮箱服务 | 可自行部署的临时邮箱服务 |
| API 基址 | 有默认值（`YYDS_BASE_URL`，指向其公开 API 端点） | 无默认值（`MOEMAIL_BASE_URL`），需填你自己部署实例的地址 |
| 获取凭据 | 向该服务申请 API Key（`YYDS_API_KEY`） | 在自己部署的实例中生成 API Key（`MOEMAIL_API_KEY`） |
| 地址怎么填 | 填服务的根地址，不带 `/v1` 这类接口路径前缀 | 填实例的根地址，同样不带接口路径前缀 |

地址那一行值得单说：网关自己对外的 `AGNES_BASE_URL` 是**带** `/v1` 的，这两个不是一回事，
顺手照抄是最常见的一种填错。填成 `…/v1` 时，注册机会拼出 `…/v1/v1/domains`，上游返回 404。
这类失败现在会把它**实际请求的那个地址**写进事件里（地址里的用户名/口令、查询串与片段会被
换成占位标记），所以看一眼事件就能认出这个坑。

### 选哪条通道

> [!IMPORTANT]
> **两条通道二选一。没有主备，也没有自动降级。**
> 两条通道完全平级，本项目不预设任何一条，也不推荐任何一条。

`REGISTRAR_CHANNEL` 没有默认值，启用注册机时必须显式指定为 `yyds` 或 `moemail`。
选中的那条负责收验证码；另一条**填了也不会被用到**，但可以先配好，随时切过来。

> [!WARNING]
> **选中的这条通道失败时，注册机不会自动改用另一条。** 它收不到验证码（域名 MX 记录
> 失效、邮件转发规则被删——API 全部返回 2xx、只是信永远不到），就是「这条通道现在产不出
> key」，而这一轮乃至这一天都会零产出，直到你自己去面板换一条。具体行为见下面
> 「一条通道失败之后会发生什么」。

#### 旧名字怎么办

> 这一格从前叫 `REGISTRAR_PRIMARY`，旁边还有一个 `REGISTRAR_FALLBACK`。
> 旧的主通道名**长期保留为兼容别名**（优先级低于新名字，用到它时面板顶部会有一条提示）；
> 旧的备通道变量**不再参与选路**，但仍会被读一次，只为在面板上点名告诉你「这条通道被丢掉了」。
> 两个旧名字都不会让升级中的部署停跑。

### 怎么挑这一条通道

判断依据：注册机靠"换域名"绕开 Agnes 对一次性邮箱域名的屏蔽，可用域名越多，注册机就越
耐用。查一下你在两边各自拥有多少可用域名，域名多的那一条更耐用——这与是哪家
服务无关，只取决于你自己的账号或自建实例的配置。

## 零内置凭据，请自行准备

本仓库不包含任何真实密钥、账号或私有域名。启用注册机前，你需要自行准备：

### 两条通道各要准备什么

- **使用 YYDS Mail**：向该服务申请一个 API Key，写入 `YYDS_API_KEY`（`YYDS_BASE_URL`
  已有默认值，一般无需更改）。
- **使用 MoeMail**：自行部署一个 MoeMail 实例，把它的访问地址填入 `MOEMAIL_BASE_URL`、
  在实例中生成的 API Key 填入 `MOEMAIL_API_KEY`（两项都没有默认值，必须显式提供）。

### 至少要准备到什么程度

至少准备好 `REGISTRAR_CHANNEL` 指向的那一条通道。另一条通道的凭据可以先填好、也可以留空：
它不影响注册机跑不跑得起来，填好之后面板上那条通道的「已配置」与「测试连接」都能用，
方便你在切换之前先比一比。

## 配置项

```env
# ── 开关与通道 ────────────────────────────────────────────────────
# 总开关。为 true 才会启用注册机。（可选，默认 false）
REGISTRAR_ENABLED=false
# 注册机用哪一条通道，yyds 或 moemail；两条通道二选一，无默认值。（启用注册机时必填）
# 旧名字 REGISTRAR_PRIMARY 长期保留为兼容别名；旧的备通道变量已不再参与选路。
REGISTRAR_CHANNEL=

# ── 补池节奏 ──────────────────────────────────────────────────────
# 目标可用 key 数，低于它才会触发补池。（可选，默认 20）
TARGET_KEYS=20
# 单轮最多铸几把 key。（可选，默认 5）
MINT_BATCH=5
# 多久跑一轮补池（毫秒）。同一个定时器也负责 pool:index 对账，注册机关着也照跑。
# （可选，默认 1800000＝30 分钟，仅 Node/Docker 读取）
TEND_INTERVAL_MS=1800000
# 单次铸 key 等待验证码的超时（毫秒）。（可选，默认 120000＝120 秒）
CODE_TIMEOUT_MS=120000
# 单轮内每次铸 key 之间随机间隔的下限 / 上限（毫秒）。（可选，默认 60000 / 90000）
# 下限是实测出来的：同一个出口在 60 秒以上的间隔下能连着发码成功，而无间隔连发时
# 第三次就会被上游前置的限流挡下，惩罚窗口按十几分钟计。上限只是抖动余量，不是实测值。
MINT_DELAY_MIN_MS=60000
MINT_DELAY_MAX_MS=90000
# 单次铸 key 最多尝试几个临时邮箱域名。（可选，默认 1）
# 注册机会记住「上游认不认这个域名」并复用，稳态下一次成功铸号只打一次发码请求。
# 调大它会等量放大每轮的限流预算消耗（实测预算约每个窗口 4~6 次）。
MAX_DOMAIN_ATTEMPTS=1
# 铸出的 Agnes API key 在 Agnes 后台显示的名称。（可选，默认 auto）
REGISTRAR_TOKEN_NAME=auto

# ── 上游与通道凭据 ────────────────────────────────────────────────
# 注册、登录、铸 key 使用的 Agnes 平台后端地址（厂商公开端点）。（可选）
AGNES_PLATFORM_URL=https://platform-backend.agnes-ai.com
# YYDS Mail 的 API 基址（厂商公开端点）与它的 API Key。
# （基址可选；Key 在通道为 yyds 时必填，本仓不提供任何真实凭据）
YYDS_BASE_URL=https://maliapi.215.im
YYDS_API_KEY=
# 你自己部署的 MoeMail 实例地址与它的 API Key，两项都没有默认值。
# （通道为 moemail 时必填）
MOEMAIL_BASE_URL=
MOEMAIL_API_KEY=
```

上面这段里的每个变量在 `.env.example` 里都有一行示例（默认值通常够用，不必逐项改），两种
部署形态都会读取。以上数值型变量都必须是正整数，否则网关拒绝启动。

## 调度：谁触发一轮，一轮能跑多久

### 谁负责触发、间隔从哪里来

| 谁在跑 | 触发方式 | 由谁决定间隔 |
|--------|--------|------------|
| 定时轮 | 进程内自重排定时器 | `TEND_INTERVAL_MS`（默认 `1800000` 毫秒） |
| 面板的「立即补池」 | 人点一下 | 不走调度；四条护栏见下文 |

那一处配置长这样：

```env
# .env —— 多久跑一轮补池（毫秒）
TEND_INTERVAL_MS=1800000
```

改了之后**下一轮生效**：在途的那一轮先按旧间隔走完，默认最长 30 分钟。**不需要重启**——
这个值每轮重新解析一次，顺序是环境变量 > 存储 > 默认值。

同一个定时器还负责把 `pool:index` 与实际的 `key:` 记录对账，而那一半**与注册机开没开
无关**——见 [DEPLOY.md](DEPLOY.md) 的「索引与可见时延」。

### 补池锁的有效期，以及一轮为什么必须装得进去（务必读完再调参数）

定时轮跑起来时会握一把存储锁（`registrar_tend_lock`），有效期 **15 分钟（900 秒）**，
而除此之外没有任何东西限制这一轮能跑多久。动下面这些数之前请务必读完本节。

#### 一轮真正受哪些限制

| 限制 | 取值 | 说明 |
|----|----|----|
| 补池锁有效期 | **15 分钟（900 秒）** | 这是我们自己的取舍，不是平台规定。它必须**明显短于** `TEND_INTERVAL_MS`（进程被硬杀时锁只能自然过期，代价上界是「最多跳过一轮」），同时**盖得住一轮真实最坏耗时**。 |
| 轮级预算 | **780 秒（有效期的 87%）** | 余下约 120 秒留给预算刻意不计的那些单请求尾巴。 |
| 单请求超时 | 15 秒 | 注册机链路上**每一个** HTTP 请求都带着它，写死值、不可配。 |
| 定时轮的墙钟 | **不设** | 没有任何东西会把它从中间砍断；上面那份预算今天只做启动期交叉校验，这一轮真正的上界是你的耐心。 |

**单请求超时正是让下面两笔估算有意义的前提**：没有它，一个挂住的连接就能把一轮无限拉长。

#### 一轮补池的两笔耗时估算

| 估算 | 公式 | 默认值代入 |
|----|----|----------|
| **常态耗时** | `MINT_BATCH × CODE_TIMEOUT_MS` ＋ `(MINT_BATCH − 1) × MINT_DELAY_MAX_MS` | 600 ＋ 360 = **960 秒**，**已经超过 900 秒的锁有效期**（见下） |
| **理论最坏**（单次铸 key） | `CODE_TIMEOUT_MS ＋ (3 × MAX_DOMAIN_ATTEMPTS ＋ 3) × 15 秒 ＋ (MAX_DOMAIN_ATTEMPTS − 1) × MINT_DELAY_MAX_MS` | 上限取 1 时 120 ＋ 90 = **210 秒** |

- **常态**指每个请求都很快返回、第一个域名就没被屏蔽，于是耗时由等验证码与名额之间的
  间隔主导：`MINT_BATCH × CODE_TIMEOUT_MS` = 5 × 120 秒 = 600 秒，加上 4 段最多 90 秒的
  间隔 = 360 秒。
- **那个间隔项从前可以忽略，现在不能了。** `MINT_DELAY_MAX_MS` 从 5 秒改成 90 秒之后，
  它从 20 秒涨到 360 秒，最坏一轮因此是 960 秒 > 900 秒。**这么长的一轮会跑过自己那把锁**：
  锁一过期，下一次触发、或者共用同一个卷的另一个容器就会在它还活着的时候并发开跑，
  两边同时撞邮箱建号限流与上游注册风控。这笔估算对得上你的配置时，请调小 `MINT_BATCH`
  或 `CODE_TIMEOUT_MS`。
- **最坏情况下的请求数**由此而来：除轮询验证码外，一次铸 key 要发「每尝试一个域名 3 次
  （建信箱、发码、删信箱）＋ 另外 3 次（注册、登录、建 key）」；列域名已经提到**轮级**
  （每轮一次，不再是每个名额一次）。想让极端情况也留在锁的有效期之内，把 `MINT_BATCH`
  设成 1~2，或者调小 `CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS`。
- **这里从前还有一个「通道数」因子。** 两条通道曾经是主备关系，「收不到验证码」会降级到
  另一条，同一个名额把 `CODE_TIMEOUT_MS` 等两遍。改成二选一之后没有第二次等待，这个因子
  整个消失了。启动期那条「`TEND_INTERVAL_MS` 小于单轮最坏耗时」的警告用的正是这个模型：
  `MINT_BATCH × CODE_TIMEOUT_MS ＋ (MINT_BATCH − 1) × MINT_DELAY_MAX_MS`。

#### 定时轮没有东西会砍断它 —— 那份预算属于「立即补池」

**定时轮既没有墙钟上限，也不带轮级预算**：它一直跑到跑完为止，唯一可能出问题的就是上面
那件事——跑过自己那把锁。因此 `MINT_BATCH` 在这条路上是**足额生效**的。

**面板那颗「立即补池」才是带预算的那一轮，而且紧得多——70 秒，对比定时轮那份 780 秒。**
开始一次铸 key 之前它先看剩下的预算够不够跑完一次完整尝试（`CODE_TIMEOUT_MS` 加上尝试
之间的间隔）。不够就**根本不开始**：这一轮提前收尾，已经铸出来的 key 全部留着，剩下的
名额留给下一轮。「不开始」正是关键，与「跑到一半被砍断」相对：被砍断的调用不会去删那个
正在用的临时邮箱（YYDS 靠 `expiresAt` 约 24 小时后过期，MoeMail 是 1 小时 TTL）。

> [!IMPORTANT]
> **那份预算属于这颗按钮，不属于某种运行时。** 点一次最多铸 **1 把** key、等验证码最多
> **60 秒**、只试 **1 个**域名；剩下的留给下一次定时轮。正是这三格压顶让这条路上的
> `worstAttemptMs` 恒为常数，于是调大 `CODE_TIMEOUT_MS` 或 `MAX_DOMAIN_ATTEMPTS`
> 也不会把这颗按钮变成诚实空转。

> [!WARNING]
> **这份预算不是万能保证——残余场景仍然存在。** 判据算的是
> `CODE_TIMEOUT_MS ＋ (MAX_DOMAIN_ATTEMPTS − 1) × MINT_DELAY_MAX_MS`，它**刻意不计**那些
> 15 秒的单请求超时：计进去的话没有任何一次尝试敢开始。定时轮那份预算与锁有效期之间留的
> 约 120 秒，就是给这些尾巴的。
>
> **这一段从前写的是「或者 403 退避」，那指向的是一条已经不存在的分支。** 撞上限流现在
> **当场结束整轮并记下跨轮退避窗口**，不再有「等一下继续硬打」这回事（见下文「撞上上游
> 限流之后会发生什么」）。

| 慢在哪儿 | 预算能不能兜住 | 后果 |
|--------|--------------|----|
| **上游不发验证码**（常见的慢） | **完全兜得住** | 手动那一轮提前收尾；定时轮只是跑得更久 |
| **几乎每个 HTTP 请求都挂满 15 秒**（病态） | 单次尝试可能超出预留余量 | 定时轮可能跑过自己那把锁，见上面的并发风险 |

第二行让你不放心的话，请按上面的「理论最坏」公式核算，把 `MINT_BATCH` 设成 1~2，
或者调小 `CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS`。

#### 超限时的两条日志：按事件名 grep

**别把 `CODE_TIMEOUT_MS` 调得太大。** 一旦单次尝试的最坏耗时超过轮级预算（锁有效期的
87%），定时轮就可能跑过自己那把锁。有两条日志，按**事件名** grep（见下文「排障」；
比 grep 正文可靠——正文措辞会随版本变，而且不会翻成你正在读的这种语言）：

下面两个围栏里是网关**逐字打印**的内容：`msg` 在源码里是写死的简体中文，**不会翻译成本页
语言**；而且一条日志恒为**单行**——`src/adapters/logger-console.ts` 刻意把换行压成空格，
因为续行没有 `[registrar]` 前缀会被丢掉。所以请按事件名 grep，别按本页的正文 grep。

**① 启动时**打一条**警告**（`console.warn`），事件名
`registrar.attempt_exceeds_worker_budget`（`grep 'registrar.attempt_exceeds_worker_budget'`），
大致长这样：

```text
[registrar] registrar.attempt_exceeds_worker_budget CODE_TIMEOUT_MS 大到一次尝试就可能跑过补池锁的有效期（15 分钟）：锁在这一轮还没跑完时就过期，下一次触发或另一个共卷副本会并发开跑，同时撞邮箱建号限流与上游注册风控。请调小 CODE_TIMEOUT_MS。（面板的「立即补池」不受影响：那一轮把等码超时压到 60 秒。） codeTimeoutMs=... worstAttemptMs=... roundBudgetMs=...
```

**事件名里那个 `worker` 是一处刻意留着的残留**：它正是这五份文档逐字交给运维去 grep 的
那个串，改名必须源码与五份文档同一次改完。它**不会**阻止网关启动——不同于「缺凭据在启动
时就拦」——因为这是一份起得来、只是有并发风险的配置，运维看到警告就能自己把值调回去。

**② 点一次「立即补池」**而连第一次尝试都装不进那 70 秒预算时，再打一条**错误**
（`console.error`），事件名 `registrar.round_budget_impossible`
（`grep 'registrar.round_budget_impossible'`），大致长这样：

```text
[registrar] registrar.round_budget_impossible 单次铸 key 的最坏耗时已超过本轮墙钟预算，一次尝试都无法开始，补池将持续零产出——这是配置问题不是瞬时状况，请调小 CODE_TIMEOUT_MS worstAttemptMs=... roundBudgetMs=...
```

它每点一次就打一次，据此可以判断这是常态而不是偶发。

**调大 `MINT_BATCH` / `CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS` 之前，请按上面两条公式
核算。** 无论一轮因为什么原因被打断，都不会丢失已经铸好的 key——每铸出一把就立刻落盘，
被打断的那一轮只是不完整，下一次定时轮会接着补。

## 补池怎么算缺口（什么样的 key 占着 `TARGET_KEYS` 名额）

### 四种 key 状态各占不占名额

缺口 = `TARGET_KEYS` − **没有被剔除的 key 数**。判据只有一条：**`evicted` 为假就占名额。**

| key 的状态 | 占 `TARGET_KEYS` 名额吗 | 能不能拿去打上游 |
|----------|-----------------------|----------------|
| 全新 / 可用 | 是 | 能 |
| **冷却中**（被限流、连续失败） | **是** | 不能 |
| **被管理员停用** | **是** | 不能 |
| 已剔除（401/403，凭据失效） | 否 | 不能 |

### 为什么冷却中的 key 也占名额

**「冷却中也占名额」是刻意的**：冷却是**会自己回来**的状态，拿它当缺口去铸新号，
铸出来的账号却**不会**自己走——一次瞬时故障换来一份永久成本。实测（`TARGET_KEYS=3`）：
按「冷却不占名额」算的话，整池被限流冷却一轮就会补出 3 把新的 ⇒ 池子变 6；
冷却到期后缺口转负、不再回收 ⇒ **永久停在 6**；下一次风暴 9，再下一次 12，线性增长，
而每一把都是一次真实的 Agnes 建号 + 一个真实花掉的临时邮箱。

**代价，明写**：整池都在冷却时注册机**不会**去铸替补，网关在冷却窗口内会持续返回
`503`（最长一个 `COOLDOWN_PAYMENT_MS` / `COOLDOWN_STRIKE_MS`）。要立刻恢复，请在面板上
对这些 key 用「清冷却」，而不是指望补池。

## 面板的「立即补池」

管理面板上那颗按钮（`POST /admin/api/registrar/tend`）。**它会等这一轮真的跑完再返回
`200`**（最长约两分钟），响应体里的 `outcome` 就是这一轮的结局；补池历史那一栏里
`trigger` 会标成 `manual`。

`outcome` 分三种，**别把它们读成同一种「失败」**，处置完全不同：`done` 是跑完了，带着
这一轮的 `minted` / `attempted` / `failures`；`skipped` 是一次上游请求都没发出去（注册机
在点击之后被关掉、或这份配置装不起来了）；`crashed` 是整轮抛错中断，上游那边**可能已经
建出临时邮箱**，归因去事件板块看。

> [!NOTE]
> **成功从 `202` 改成 `200` 是破坏性变更**（`started: true` 保留给旧面板，另加
> `done: true`）。从前它一收到点击就回 `202`，整轮丢给 `ctx.waitUntil` 在响应之后跑；
> 而后台任务可能被从中间掐掉，**掐掉不抛异常** ⇒ 补池历史不写、
> 事件不发、锁也不放，面板上那一轮与「压根没点过」逐字节不可区分，而泄漏的那把锁
> 连定时轮也一起挡掉。处置是**换载体**：端点自己 `await` 完这一轮再返回真实结果，
> 于是这一轮的墙钟上界变成「浏览器 / 前面那层反代愿意等多久」，它也因此需要一份
> 自己的预算。

### 四条护栏

它有**四条护栏**，任何一条不满足都不会启动：

| 护栏 | 不满足时 | 挡什么 |
|----|--------|------|
| 同进程内的在途守卫 | `409 tend_in_flight` | 定时轮与按钮撞车、同一副本上的两个并发点击 |
| 存储级短锁（`registrar_tend_lock`） | `409 locked` | **跨副本**重叠（多个容器共用一个卷） |
| 两次手动补池至少隔 10 分钟 | `429 manual_cooldown` | 连点烧临时邮箱名额 |
| 每天最多 **24** 次 | `429 write_budget_exhausted` | 连点烧临时邮箱名额与上游的注册风控预算 |

`429` 的响应体里带 `remaining`（今天还剩几次）、`resetAt`（UTC 零点恢复）与 `retryAfterMs`；
**`200` 的响应体里同样带 `remaining`**，面板据此如实显示还剩几次，不必等到点不动了才说。
注册机没打开时返回 `409 registrar_disabled`。前置拒绝的这几个状态码一个都没变。

**那把短锁的 TTL 按路径分岔**：定时轮 15 分钟（＝上文那份锁有效期），手动轮
**3 分钟**。手动轮的进程被硬杀时锁只能等自然过期，取 15 分钟就意味着一次点击必然挡掉
至少一轮定时补池（线上真发生过两次）；3 分钟短于两次手动之间那 10 分钟冷却，所以一把
泄漏的锁活不到下一次可点。

### 诚实限定与残余风险

> [!WARNING]
> **诚实限定，别读成「并发已解决」**：那把存储锁是对一份 JSON 文件的「读—改—写」，
> 因此是**尽力而为、不是互斥原语**。它挡的是「上一轮明明还在跑」这种最常见的重叠；同一毫秒发起的两次点击仍然
> 可能双双抢到。护栏键与补池历史同样是「读—改—写」，并发窗口里会丢更新——后果的上界是
> 「闸门最多多放行（并发数 − 1）次、补池历史最多缺（并发数 − 1）行」。

> [!WARNING]
> **残余风险**：手动补池带的是**自己那一族上限**——轮级预算 70 秒、一轮最多铸 1 把、
> 等验证码最多 60 秒、只试 1 个域名，与定时轮那份 780 秒各算各的。
> 后三格一律取 `Math.min` 压顶而不是赋值：设置里调得更小的值不会被抬回来；真被压小时，
> 响应体的 `outcome.capped` 会如实报出压前压后的两组数（走响应体不走事件——做成事件就是
> 每点一次多一次存储写，会打破「健康的一轮零写」那条配额性质）。
> 它的作用仍是「不启动一次明知跑不完的尝试」，**不消灭泄漏，只把概率压下来**——进程仍可能
> 在预算窗口之内被硬杀，此刻正在铸的那个临时邮箱就不会被删掉。
> 注意这条与定时轮不同：**Node/Docker 的定时轮不带这个预算，而手动补池带**，
> 所以同一份配置下手动那一轮铸得比定时轮少，剩下的名额留给下一次定时轮。

### 这几把键不会自己消失

`registrar_tend_lock`、`registrar_manual_guard`、`tend:history`、`registrar:domains`、
`registrar:backoff` 五把键**都不带 TTL**。它们的名字是固定字面量、数量恒为 1，陈旧值一律靠
**值比较**判定（过期的锁不拦任何人、昨天的计数不算数、过期的退避窗口不拦任何一轮），
所以留着无害。

**代价明写**：永久关掉注册机、或者删掉部署但保留数据目录时，它们不会自己消失。
要清理请先停容器，编辑 `DATA_DIR/store.json`，删掉这五个顶层字段。

**`registrar:domains` 也是「认定域名台账记错了」时唯一的手动出口**：删掉它等于让注册机
回到冷启动，把已经花过的发码请求重新花一遍——只在真的判断它记错了的时候才这么做。

**`tend:history` 通常应当留着**：它是事故复盘时最想看的东西，而「关掉注册机 N 天后补池
历史整个消失」恰恰是最坏的时机——运维往往正是**因为**出事才关的注册机。

## 铸出来的 key 多久能被转发路径用上

**最多一个 `POOL_CACHE_TTL_MS`（默认 60 秒），不是「下一个请求」。**

补池与转发用的是两个相互独立的 key 池仓储实例：补池那个每轮都真读一遍存储（它必须看到
当前真实的可用数，否则会重复补池、白烧邮箱配额），转发那个持有一份进程级的
快照。两者各自维护自己的缓存，所以补池写完 key 之后，转发路径要等**自己那份快照**过期
才会看到；共用同一个卷的每个容器各有各的 TTL。

**这条在池子被打空时最容易被误读**：日志已经打了 `[registrar] … minted=1`，而网关还会
继续返回 `503 pool_empty` 长达一个 TTL。那不是补池没生效，等一个 `POOL_CACHE_TTL_MS`
即可；想缩短就把它调小，代价是每个进程每个间隔多读一次文件。

## 为什么顺序铸 key、不并发

补池在单轮内**顺序**铸 key，每次之间插入随机间隔，而不是并发发起多个铸 key 请求。这不
是性能取舍，而是功能性约束：并发会同时撞上 YYDS Mail 的建号限流（短时间内建立邮箱超过
约 10 次会返回 `403`）和 Agnes 自身的注册风控。顺序执行加随机间隔是让注册机能持续工作
的必要条件，不建议通过并发来"优化"它。

## 隐私说明

注册过程中产生的邮箱地址、账号密码只在内存中短暂存在，**用完即弃、不会被持久化**；存
储里只会出现铸出的 API key 记录。铸 key 结束后（无论成功还是失败）都会去删那个临时邮箱。**删除是尽力而为，不是保证**：删不掉时（上游 4xx/5xx、网络中断、或轮次被平台从中间砍断）它会留到上游自己回收 —— 两条通道各自的 TTL 见上面通道对照表那一节。系统不会假装它已经删干净：`cleaned:false` 会如实报出来。

## 排障

### 注册机的三态

注册机不是「开 / 关」两态，是**三态**。第三态最容易被误读，面板上四处都写着它。

- **已关闭**：`REGISTRAR_ENABLED` 没开，或面板上的开关是关的。补池一次都不跑、一次外部请求都不发。
  面板上写「已关闭」。这是默认状态，不用恢复；要用它就去设置页打开，并配好至少一条邮箱通道。
- **已启用**：开着，而且这份配置装得起来，按 `TEND_INTERVAL_MS` 定时器补池。
  面板上写「已启用」，两张通道卡各自说清有没有凭据、是不是本次选中的那条。
- **已启用 · 本次没跑起来**：开关是开的，但这份配置装不起来（没选通道、选中那条通道缺凭据
  ……），所以本次没有启动它。**网关转发完全不受影响**，只是不再补池。

第三态在面板上有四处提示，指的是同一件事：设置页顶部的横幅（逐条列出缺哪几格）、
注册机板块的状态行、概览页的配置摘要、以及事件板块里每一轮一条 `error` 级的 `registrar.blocked`。
**恢复方式**：按横幅列出的那几格在设置页补齐，保存即可，不需要重启容器、也不需要重新部署。

> [!WARNING]
> **这样做的代价**：故障从「响亮」变成了「安静」。补池停摆之后池子会慢慢耗干，最终以
> `pool_empty` 的形式在几小时到几天后炸出来，那时的症状离真正的原因隔着好几层。
> 上面那四处提示就是为此存在的——**你得去看**。

### 启动与日志的约定

- **启用后若缺凭据，注册机本次不启动，但网关照常转发。**
  这一条**改过**：从前是「启动即报错」（fail-closed 到整个网关），而注册机是可选子系统，
  它缺一把邮箱 key 不该让转发、`/health` 与管理面板一起死。现在缺的那几格会逐条列在面板上，
  并且每一轮记一条 `error` 级的 `registrar.blocked`。三种状态各自长什么样，见下面「注册机的三态」。
- 补池过程中的日志统一带 `[registrar]` 前缀，可据此过滤查看注册机相关的运行状态。每条
  日志的第二个字段是稳定的机器可读**事件名**（如 `registrar.round_budget_impossible`），
  按事件名 `grep` 比按中文文案 `grep` 更可靠：文案是给人看的，可能因为措辞调整而变化；
  事件名是这套日志唯一对外稳定的契约，不会变。
### 读懂 `reasons=` 里的失败原因

- **一轮里有名额没铸出来时，收尾会多打一条带 `reasons=` 的告警**，形如
  `reasons=yyds:register_failed×3 moemail:code_timeout×1`。先看这一行判断故障在哪一层：
  `code_timeout` = 这条通道收不到 Agnes 的信（域名 MX / 邮件转发规则）；
  `register_failed` / `login_failed` / `key_failed` = Agnes 侧的注册链路变了；
  `provider_error` = 邮箱服务本身（凭据、活跃邮箱配额、服务不可用）；
  `provider_missing` = 内部接线错误，正常配置下不会出现（缺凭据是启动即报错，走不到这里）。
- **`reasons=` 里出现 `key_suspicious`**：上游发回来的 key 材料含不可打印字符或空白。
  **这一轮确实铸出来了**（Agnes 侧账号已经真的建出来、一个临时邮箱已经花掉），所以它
  **照常存进了池子**——在这里拒收等于销毁一份再也找不回来的凭据。但它多半每次被选中都
  会让转发失败，请在面板上停用或删除它。同时会有一条 `registrar.minted_key_suspicious`
  的 error 事件（只记通道与长度，**不记明文**）。
### 注册机会记住哪些邮箱域名能用

上游只接受一部分一次性邮箱域名，剩下的会被拒。**这个结论现在会落盘复用**：

- 稳态下**一次成功铸号只打一次 `/api/verification`**——挑一个已知能用的域名，不再从
  上游全部域名里随机取若干个逐个试。这正是 `MAX_DOMAIN_ATTEMPTS` 的内置取值能降到 1 的原因。
- 面板的注册机板块有一行「域名台账：可用 N · 判死 N · 待复查 N · 未探过 N（更新于 …）」。
- 结论要**连着两轮**被拒才会被排到候选末尾（**同一轮里被拒几次都只算一次**）；只挨过一轮的
  算「待复查」，仍然会被选中，
  只是优先级低。一次成功会无条件把它覆盖回「可用」。

#### 这个判定为什么可能错

> [!WARNING]
> **「判死」是我们的判定，不是上游的声明。** 上游用同一个 `400` 同时表达「这个域名被
> 屏蔽了」与「你这个出口发得太频繁了」，唯一的区分线索是响应正文，而我们靠一张**词表**
> 去认它——上游改一次措辞就会认错。压着这个误判的有三层：判死要两跳、一轮最多学一条、
> 以及**排序永远不会把任何域名彻底排除**（判死的只是排在最后）。
> 但这三层压的全是「好域名被判死」这一个方向。反方向——台账里那条「可用」已经过时、
> 域名其实早被上游拉黑——靠的是另一条规矩：**分类器判出什么就记什么，一条结论都不许吞掉**。
> 这条规矩曾被一道保险破坏过（「已知能用的域名被拒就改判成限流」），后果不是变慢而是
> **补池归零**，最长 7 天；那道保险已经拆掉。
> 也就是说，这句收口的话得**按方向拆开**，三个方向的后果并不一样：
> ① 好域名被判死这个方向——确实只是变慢、**不会归零**（三层护栏 + 排序永不排除任何域名）；
> ② 台账说「可用」而上游其实早已拉黑——靠「判出什么就记什么」，那条规矩已经修好；
> ③ 分类器把**真限流**读成「域名被屏蔽」——上游那句限流的话**我们的词表一个都没认出来**
>（注意不是「上游没说」：它说了，是我们没认出来），所以上面那两层退避一次都不会产生，
> 本轮也不再提前停手，一轮最多打 `MINT_BATCH` 次注定失败的发码请求。接住这一档的是下面
> 那张表的第三行：判据是**这一轮的形状**（同一轮里好几个域名一起被判屏蔽，**或者上游列
> 出来的域名一个不落全被判屏蔽**，而这一轮一把 key 都没铸出来），不是上游的字眼。

#### 认定域名台账记错了怎么办

面板上没有「逐个域名列出来」的视图（上游几百个域名会把一个每几秒
被轮询一次的接口响应撑大一个量级）。可选的处置有三种：等结论过期（判死的 24 小时、可用的
7 天）、等两跳规则自己纠正、或者手工删掉那把存储键（见下面「这几把键不会自己消失」）。

### 撞上上游限流之后会发生什么

上游前面有一层边缘限流（`429`），上游自己还有一层注册限流（`400` + 一句「请求过于频繁」
之类的话）。**两层的惩罚窗口都比一轮补池长，而且窗口里每打一次请求就把窗口续一次。**

所以撞上任意一层之后：

- **这一轮当场结束**，不换域名、不继续下一个名额；
- 记下一个**退避窗口**，下一轮开跑前先看它——**窗口内一次上游请求都不发、一个临时邮箱都
  不建**。补池历史里这一行的失败归因是「还在退避窗口里，这一轮一次都没开始」；
- 连着撞会**指数**拉长退避（封顶 4 小时）。这里的「连着」数的是**连着几轮一把 key 都没出**：
  一轮里只要铸出过 key，指数就从头数起——那一轮末尾又撞上限流的话，退避回到起步那一档
  而不是接着翻倍；那一轮一次限流都没撞到的话，那把键直接清掉。
- 上一段退避过完之后，隔了 4 小时以上都没再撞上，指数同样从头数（比如池子一直是满的、
  注册机好几轮都没真正跑过的那种）。

#### 第三档：我们的词表一个字都没命中，但这一轮的域名成片挂了

上游改一次限流文案，真限流就会被逐条读成「域名被屏蔽」
——上面两档一次都不会触发，而本轮也不再提前停手。这时唯一还站得住的证据是**这一轮的形状**，
它有两条判据，命中任意一条就算：

- 同一轮里有两个以上的域名被判屏蔽；
- **或者上游列出来的域名这一轮一个不落全被判屏蔽**（只配了一个邮箱域名的部署就靠这一条 ——
  它永远凑不满上面那两个）。

两条都要求**这一轮一把 key 都没铸出来**。注册机据此记一个退避窗口（起步 30 分钟，同样指数、
同样封顶 4 小时），**但它不中止这一轮、也不吞掉任何域名结论**——这一轮该轮着试的域名照试、
该出的 key 照出。只要这一轮铸出过 key，这一档就一个字都不记。

#### 这一档亮起来时，两种可能都还开着

> [!WARNING]
> **这一档亮起来的时候，两种可能都还开着，横幅不会替你选**：上游换了限流的措辞、而我们的
> 词表没认出来；或者上游真的把这些域名成批换进了黑名单。**别把它读成「上游没说过限流」**
> —— 这一档要治的头号场景恰恰是上游说了、只是我们没认出来。

#### 上游原话去哪里翻：两支拿得到的证据不一样

**别照着「去看 `registrar.domain_blocked`」一条路走到黑 —— 它在其中一支上根本发不出来。
代价如实记在这里：**

- **同一轮里好几个域名一起被判屏蔽**那一支：钳位一生效，本轮**全部**「被屏蔽」判定被整体
  作废 ⇒ 台账学不到 `blocked` ⇒ `registrar.domain_blocked` **这一轮一条都不会发**。
  这一支能拿到的上游原话只有 `registrar.known_good_domain_rejected` 那几条，而它**只覆盖
  台账里已知能用的那些域名** —— 冷启动、或者上游这一轮新列出来的域名，一句原话都没有。
  同一轮发出的 `registrar.domain_verdicts_discarded` 只带被作废的条数、本轮产出与退避截止
  时刻，**不带上游原话**。
- **上游列出来的域名一个不落全被判屏蔽**那一支（只配一个邮箱域名的部署走的就是它）：钳位
  凑不满、不生效 ⇒ 台账照常学得到结论，第二跳判死时 `registrar.domain_blocked` 带着上游
  原话发出来。

#### 第三档接住之后还剩多少请求量

数写在这里（内置值、测试替身量出来的）：走到指数封顶之后是
**每 8 轮打一次、每次 `MINT_BATCH` = 5 个发码请求**，每 30 分钟一轮
⇒ 48 轮/天 ÷ 8 × 5 = **约 30 次/天**。
两个对照数：**接上这一档之前是每一轮都打满 ⇒ 约 240 次/天**；而「上游的措辞落进了词表」的
第二档是撞上就整轮停手（一轮 1 次）⇒ **约 6 次/天**。
⇒ **30 不是 6**：这一档比第二档贵，因为它不中止本轮 —— 本轮该出的 key 照出，代价是本轮
剩下的名额照打。

#### 退避横幅：三档的处置不一样

面板的注册机板块会显示一条退避横幅：

| 是哪一档 | 面板怎么说 | 你能做什么 |
|------------|----------|----------|
| 边缘限流 | 「补池打得太密」 | 调大 `MINT_DELAY_MIN_MS`，或调小 `MINT_BATCH` |
| 上游自己的注册限流 | 「上游回话里带着『请求过于频繁』这类字眼，这是我们按词表下的判定，不是上游给的结论」 | 先调大 `MINT_DELAY_MIN_MS`、调小 `MINT_BATCH`；确认这个出口的注册额度真到顶了，再谈换出口 |
| 这一轮的域名成片被判屏蔽（好几个一起，或者列出来的全都被判屏蔽）、且这一轮零产出 | 「上游的回话里没有一句我们认得出的限流的话，这是我们按这个形状下的判定；上游换了限流措辞、或者真的成批换了黑名单，两种可能都还开着」 | 两支拿得到的证据不一样，见上一节；别默认 `registrar.domain_blocked` 里一定有 |

> [!IMPORTANT]
> **换一条邮箱通道逃不掉这一档。** 限流发生在「你的出口地址 → 上游」这条边上，与你用
> 哪条邮箱通道无关。看到退避横幅时去切通道是白费力气。

**空池填满会明显变慢**：目标 20 把 key 从「几分钟」变成大约 4~5 轮。每 30 分钟一轮
⇒ **约 2~2.5 小时**。这是把「打光额度还在白打」换成「慢但真的出 key」的直接代价。

### 一条通道失败之后会发生什么

**两条通道是二选一，所以「换一条」这件事只有你能做。** 选中的那条通道失败时：

- **本次名额作废，本轮的下一个名额照常开始**（先睡 `MINT_DELAY_MIN_MS`~`MINT_DELAY_MAX_MS`
  的随机间隔）。列域名失败、凭据无效、所有候选域名都建不出邮箱、收不到验证码、
  网络抖动、域名被全部屏蔽、注册 / 登录 / 建 key 失败——这几种全都是这一档。
- **有两种例外，都会立刻结束这一轮**：
  - Agnes 后端整体故障（`upstream_error`）——继续跑只会在故障期间制造更多注定失败的请求；
  - **撞上上游限流（`rate_limited`）**——见下面「撞上上游限流之后会发生什么」。
- **除限流之外没有跨轮退避，也没有指数补偿。** 一般失败不改变下一轮的时间：Node/Docker
  是固定的 `TEND_INTERVAL_MS` 定时器，它按自己的节奏走。轮内的节流来自尝试之间的随机
  间隔，「立即补池」那条路上还多一份它自己的轮级预算。

#### 代价，以及怎么发现它

> [!WARNING]
> **这是一次能力下降，明写在这里。** 从前一条通道收不到验证码还有一次自动换通道的机会，
> 补池会变慢但仍然出 key；现在同一条通道收不到验证码 = 这一轮乃至这一天一把都铸不出来，
> 直到你自己去面板换一条通道。故障形态从「补池变慢」变成「补池零产出、池子慢慢耗干、
> 几小时到几天后以 `pool_empty` 503 炸出来」——**把一个自愈的故障换成了一个要人管的故障**。
> 这是「二选一」的固有代价，不是缺陷。

**怎么发现它**：补池历史里每一轮的失败归因逐条带着通道名（`reasons=` 那一行）、注册机板块
的池子四格数字、以及通道请求失败时那条带**实际请求地址**的事件。看到零产出就去面板上点一下
另一条通道的「测试连接」：它会列一次域名，再**真的验一次那边的凭据**（怎么验由通道自己
决定；有的通道靠「建一个临时邮箱再删掉」来验，那一下会占一个活跃邮箱名额）。
切过去之后看下一轮补池历史的失败归因，铸出 key 才算数。

### 某条通道持续失败怎么办

- 若某条通道持续注册失败（例如 Agnes 收紧了验证码或人机验证策略），这是代码层面无法
  规避的上游变化，可以关闭注册机、改为手动导入 key（见 [DEPLOY.md](DEPLOY.md)）。
