# 註冊機（自動補池）

本文講註冊機：它做什麼、兩條信箱通道怎麼選、有哪些設定項目，以及跑起來之後怎麼看日誌與疑難排解。

> **預設關閉。** `REGISTRAR_ENABLED` 預設為 `false`，裝上本專案不會自動開始註冊任何帳號；
> 只有明確把它設為 `true` 才會啟用註冊機。

## 這是什麼

註冊機是一個可選元件：當 key 池中的可用 key 數低於 `TARGET_KEYS` 時，它會自動註冊新的
Agnes 帳號、登入、鑄出一把 API key 寫入池子。註冊過程需要接收 Agnes 寄來的信箱驗證碼，
因此依賴下文的信箱通道之一。

> [!WARNING]
> **合規提示**
>
> 大量註冊與 Agnes 服務條款之間存在張力。是否啟用註冊機、以何種頻率使用，須由部署者自行
> 判斷並承擔相應責任——本專案不替使用者做這個決定。

## 兩條信箱通道：如何選擇

註冊機支援兩條信箱通道，用來接收驗證碼：

### 兩條通道的對照

| | YYDS Mail | MoeMail |
|----|---------|-------|
| 性質 | 第三方臨時信箱服務 | 可自行部署的臨時信箱服務 |
| API 基底位址 | 有預設值（`YYDS_BASE_URL`，指向其公開 API 端點） | 無預設值（`MOEMAIL_BASE_URL`），需填入你自己部署實例的位址 |
| 取得憑證 | 向該服務申請 API Key（`YYDS_API_KEY`） | 在自己部署的實例中產生 API Key（`MOEMAIL_API_KEY`） |
| 位址怎麼填 | 填服務的根位址，不帶 `/v1` 這類介面路徑前綴 | 填實例的根位址，同樣不帶介面路徑前綴 |

位址那一行值得單獨說：閘道自己對外的 `AGNES_BASE_URL` 是**帶** `/v1` 的，這兩個不是一回事，
順手照抄是最常見的一種填錯。填成 `…/v1` 時，註冊機會拼出 `…/v1/v1/domains`，上游回傳 404。
這類失敗現在會把它**實際請求的那個位址**寫進事件裡（位址裡的使用者名稱／密碼、查詢字串與
片段會被換成佔位標記），所以看一眼事件就能認出這個坑。

### 選哪條通道

> [!IMPORTANT]
> **兩條通道二選一。沒有主備，也沒有自動降級。**
> 兩條通道完全平等，本專案不預設任何一條，也不推薦任何一條。

`REGISTRAR_CHANNEL` 沒有預設值，啟用註冊機時必須明確指定為 `yyds` 或 `moemail`。
選中的那條負責收驗證碼；另一條**填了也不會被用到**，但可以先配好，隨時切過來。

> [!WARNING]
> **選中的這條通道失敗時，註冊機不會自動改用另一條。** 它收不到驗證碼（網域 MX 記錄
> 失效、郵件轉發規則被刪——API 全部回傳 2xx、只是信永遠不到），就是「這條通道現在產不出
> key」，而這一輪乃至這一天都會零產出，直到你自己去面板換一條。具體行為見下面
> 「一條通道失敗之後會發生什麼」。

#### 舊名字怎麼辦

> 這一格從前叫 `REGISTRAR_PRIMARY`，旁邊還有一個 `REGISTRAR_FALLBACK`。
> 舊的主通道名**長期保留為相容別名**（優先級低於新名字，用到它時面板頂部會有一條提示）；
> 舊的備用通道變數**不再參與選路**，但仍會被讀一次，只為在面板上點名告訴你「這條通道被丟掉了」。
> 兩個舊名字都不會讓升級中的部署停跑。

### 怎麼挑這一條通道

判斷依據：註冊機靠「換網域」繞開 Agnes 對一次性信箱網域的封鎖，可用網域越多，註冊機就
越耐用。查一下你在兩邊各自擁有多少可用網域，網域較多的那一條更耐用——這與是
哪家服務無關，只取決於你自己的帳號或自建實例的配置。

## 零內建憑證，請自行準備

本儲存庫不包含任何真實金鑰、帳號或私有網域。啟用註冊機前，你需要自行準備：

### 兩條通道各要準備什麼

- **使用 YYDS Mail**：向該服務申請一個 API Key，填入 `YYDS_API_KEY`（`YYDS_BASE_URL`
  已有預設值，通常無需更改）。
- **使用 MoeMail**：自行部署一個 MoeMail 實例，把它的存取位址填入 `MOEMAIL_BASE_URL`、
  在實例中產生的 API Key 填入 `MOEMAIL_API_KEY`（兩項都沒有預設值，必須明確提供）。

### 至少要準備到什麼程度

至少準備好 `REGISTRAR_CHANNEL` 所指向的那一條通道。另一條通道的憑證可以先填好、也可以留空：
它不影響註冊機跑不跑得起來，填好之後面板上那條通道的「已配置」與「測試連線」都能用，
方便你在切換之前先比一比。

## 設定項目

```env
# ── 開關與通道 ────────────────────────────────────────────────────
# 總開關。為 true 才會啟用註冊機。（選填，預設 false）
REGISTRAR_ENABLED=false
# 註冊機用哪一條通道，yyds 或 moemail；兩條通道二選一，無預設值。（啟用註冊機時必填）
# 舊名字 REGISTRAR_PRIMARY 長期保留為相容別名；舊的備用通道變數已不再參與選路。
REGISTRAR_CHANNEL=

# ── 補池節奏 ──────────────────────────────────────────────────────
# 目標可用 key 數，低於它才會觸發補池。（選填，預設 20）
TARGET_KEYS=20
# 單輪最多鑄幾把 key。（選填，預設 5）
MINT_BATCH=5
# Node 側補池排程間隔（毫秒）；Worker 側由 wrangler.toml 的 Cron 決定，見下文。
# （選填，預設 1800000＝30 分鐘，僅 Node/Docker 讀取）
TEND_INTERVAL_MS=1800000
# 單次鑄 key 等待驗證碼的逾時（毫秒）。（選填，預設 120000＝120 秒）
CODE_TIMEOUT_MS=120000
# 單輪內每次鑄 key 之間隨機間隔的下限 / 上限（毫秒）。（選填，預設 60000 / 90000）
# 下限是實測出來的：同一個出口在 60 秒以上的間隔下能連著發碼成功，而無間隔連發時
# 第三次就會被上游前置的限流擋下，懲罰視窗按十幾分鐘計。上限只是抖動餘量，不是實測值。
MINT_DELAY_MIN_MS=60000
MINT_DELAY_MAX_MS=90000
# 單次鑄 key 最多嘗試幾個臨時信箱網域。（選填，預設 1）
# 註冊機會記住「上游認不認這個網域」並複用，穩態下一次成功鑄號只打一次發碼請求。
# 調大它會等量放大每輪的限流預算消耗（實測預算約每個視窗 4~6 次）。
MAX_DOMAIN_ATTEMPTS=1
# 鑄出的 Agnes API key 在 Agnes 後台顯示的名稱。（選填，預設 auto）
REGISTRAR_TOKEN_NAME=auto

# ── 上游與通道憑證 ────────────────────────────────────────────────
# 註冊、登入、鑄 key 使用的 Agnes 平台後端位址（廠商公開端點）。（選填）
AGNES_PLATFORM_URL=https://platform-backend.agnes-ai.com
# YYDS Mail 的 API 基底位址（廠商公開端點）與它的 API Key。
# （基底位址選填；Key 在通道為 yyds 時必填，本儲存庫不提供任何真實憑證）
YYDS_BASE_URL=https://maliapi.215.im
YYDS_API_KEY=
# 你自己部署的 MoeMail 實例位址與它的 API Key，兩項都沒有預設值。
# （通道為 moemail 時必填）
MOEMAIL_BASE_URL=
MOEMAIL_API_KEY=
```

上面這段中的每個變數在 `.env.example` 中都有一行範例（預設值通常已足夠，不必逐項修改），
兩種部署形態都會讀取。以上數值型變數皆須為正整數，否則閘道拒絕啟動。

## 兩種執行時的排程差異

### 由誰觸發、間隔從哪裡來

| 部署形態 | 觸發方式 | 由誰決定間隔 |
|--------|--------|------------|
| Cloudflare Worker | `wrangler.toml` 的 `[triggers]` Cron（預設 `*/30 * * * *`，即每 30 分鐘一次） | 修改 `wrangler.toml` 中的 cron 表達式 |
| Node / Docker | 行程內計時器 | `TEND_INTERVAL_MS`（預設 `1800000` 毫秒） |

兩處設定各自長這樣：

```toml
# wrangler.toml —— Worker 形態的觸發間隔只由這裡決定
[triggers]
crons = ["*/30 * * * *"]
```

```env
# .env —— Node / Docker 形態的觸發間隔（毫秒）
TEND_INTERVAL_MS=1800000
```

兩種執行時最終都會呼叫**同一個補池函式**，差異在於**由誰負責準時觸發**，以及**觸發
間隔從哪裡來**：

| | 觸發者 | 間隔來自 | 改了之後 |
|----|------|--------|--------|
| Node / Docker | 行程內自重排計時器 | `TEND_INTERVAL_MS`（環境變數 > 儲存 > 預設 `1800000`） | **下一輪生效**（要等目前這一輪的舊間隔走完，預設最長 30 分鐘）。**不需要重啟** |
| Cloudflare Worker | 平台的 Cron Trigger | `wrangler.toml` 的 `[triggers].crons` | **改設定不生效**，必須改 `wrangler.toml` 並重新部署 |

除觸發間隔之外的補池設定項（`TARGET_KEYS` / `MINT_BATCH` / 通道憑證……）兩種執行時確實
完全相同。

### Cloudflare Cron 觸發器的牆鐘上限（務必讀完再調整參數）

若使用 Worker 部署，補池由 Cron Trigger 觸發，請務必讀完本節再動參數。

#### 平台給的四條硬上限

| 限制項 | 值 | 說明 |
|------|----|----|
| 單次呼叫的牆鐘（wall-clock） | **15 分鐘（900 秒）** | Cron Trigger 的硬上限，頂到就被平台中止。 |
| `ctx.waitUntil()` | **不會延長此上限** | 該寬限機制只對 HTTP 請求生效，對 Cron 觸發的呼叫不適用。 |
| CPU 時間 | 30 秒 | 補池過程中的 `await` 網路請求（寄驗證碼、輪詢驗證碼等）不計入 CPU 時間，所以 CPU 上限並非實際瓶頸。 |
| 單請求逾時 | 15 秒 | 註冊機鏈路上的**每個** HTTP 請求都有，固定值，不可設定。 |

**單請求逾時是下面兩個估算成立的前提**：沒有它，一個掛起的連線就能讓單輪無限拖長。

#### 單輪耗時的兩個估算

| 估算 | 算式 | 預設值下的結果 |
|----|----|--------------|
| **常態耗時** | `MINT_BATCH × CODE_TIMEOUT_MS` ＋ `(MINT_BATCH − 1) × MINT_DELAY_MAX_MS` | 600 ＋ 360 = **960 秒**，**已經超過 900 秒的牆鐘上限**（見下面「Worker 會在牆鐘耗盡前主動收手」） |
| **理論最差耗時**（單次鑄 key） | `CODE_TIMEOUT_MS + (3 × MAX_DOMAIN_ATTEMPTS + 3) × 15 秒 + (MAX_DOMAIN_ATTEMPTS − 1) × MINT_DELAY_MAX_MS` | 120 ＋ 90 = **210 秒**（預設 `MAX_DOMAIN_ATTEMPTS=1`）；調大它會同時抬高這兩項 |

- **常態**指每個請求都很快返回、第一個網域就沒被封鎖，耗時由等待驗證碼與名額之間的
  間隔共同主導：`MINT_BATCH × CODE_TIMEOUT_MS` = 5 × 120 秒 = 600 秒，再加上 4 段
  最長 90 秒的間隔 = 360 秒。
- **間隔那一項從前可以忽略，現在不行了**：`MINT_DELAY_MAX_MS` 從 5 秒改成 90 秒
  之後，它從 20 秒漲到 360 秒，整輪最差 960 秒 > 900 秒。**這不是新缺陷**，下面那個輪級
  預算正是為它準備的：Worker 上最差跑得完 4 個名額，第 5 個留給下一輪。
- **理論最差**裡的請求數是這麼來的：單次鑄 key 除了輪詢驗證碼，還要打「每嘗試一個網域
  3 次（建信箱、寄驗證碼、刪信箱）＋3 次（註冊、登入、建 key）」；列網域已經提到**輪級**
  （一輪 1 次，不再是每個名額 1 次）。若希望連極端情況也留在牆鐘內，把 `MINT_BATCH`
  調到 1～2，或調小 `CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS`。
- **這裡從前還有一個「通道數」因子**：兩條通道曾經是主備，「收不到驗證碼」會降級重試，
  同一個補池名額最差要在兩條通道上各等滿一次 `CODE_TIMEOUT_MS`。兩條通道改成二選一之後
  沒有第二次等待了，那個因子整個消失。啟動時那條 `TEND_INTERVAL_MS 小於單輪最差耗時`
  的告警用的就是這個模型：`MINT_BATCH × CODE_TIMEOUT_MS + (MINT_BATCH − 1) × MINT_DELAY_MAX_MS`。

#### Worker 會在牆鐘耗盡前主動收手

**這一項覆蓋上面「最差耗時」那一行，不覆蓋「理論最差」那一行。** 每次準備開始一次鑄 key
之前，註冊機都會先算「剩餘牆鐘夠不夠完整跑完這一次」，判據是 `CODE_TIMEOUT_MS`
再加上嘗試間隔；不夠就**根本不開始**，提前結束本輪、記一條
`registrar.round_budget_exhausted` 警告（形如「本輪牆鐘預算不足以再完整跑完一次鑄 key，
提前收尾」），已經鑄好的 key 照常入池，剩餘名額留給下個排程週期。若連第一次嘗試都裝不下，
走的是另一個事件 `registrar.round_budget_impossible`，層級為錯誤，見下一小節。

關鍵在於「不開始」而不是「跑到一半被砍」：被平台從中間中止時，那次正在用的臨時信箱來不及
刪除就會殘留（YYDS 約 24 小時後隨 `expiresAt` 過期，MoeMail 按 1 小時 TTL 過期）。因此
**`MINT_BATCH` 在 Worker 上是「單輪上限」而不是「保證值」**：單輪可能鑄不滿。Node/Docker
沒有平台牆鐘上限，**定時輪**不啟用這個機制，`MINT_BATCH` 會照常跑滿。

> [!IMPORTANT]
> **但面板的「立即補池」是例外，兩種執行時都帶同一份輪級預算**：一次點擊最多跑多久是
> 這顆按鈕自己的性質，不是執行時的性質，所以 Node/Docker 上手動補池同樣可能少鑄幾把，
> 下一次定時輪會接著補。

> [!WARNING]
> **這個預算不是萬能的，殘餘場景仍然存在。** 判據算的是
> `CODE_TIMEOUT_MS + (MAX_DOMAIN_ATTEMPTS − 1) × MINT_DELAY_MAX_MS`，**沒有**把單請求
> 逾時（每個 15 秒）算進去——把它也算進去就會變成一次嘗試都不敢開始。預算取牆鐘的
> 87%，留下的那約 120 秒餘量就是給這些尾巴的：
>
> **這段從前寫的是「與 403 退避」——那是一條死分支。** 撞上限流現在是
> **當場結束整輪 + 記一個跨輪退避視窗**（見下面「撞上上游限流之後會發生什麼」）。

| 慢在哪一層 | 預算兜不兜得住 | 後果 |
|----------|--------------|----|
| **上游只是收不到驗證碼**（本節最常見的那種慢） | **已被完全兜住** | 本輪提前收尾，剩餘名額留給下個排程週期 |
| **幾乎每個 HTTP 請求都掛滿 15 秒**（病態情形） | 單次嘗試可能超出預留餘量 | 仍被平台中止，那次的臨時信箱會殘留 |

擔心第二行那種情形，就按上面「理論最差」的公式把 `MINT_BATCH` 調到 1~2，或調小
`CODE_TIMEOUT_MS` / `MAX_DOMAIN_ATTEMPTS`。

#### 兩條日誌：超限時按事件名 grep

**`CODE_TIMEOUT_MS` 別調得過大。** `CODE_TIMEOUT_MS` 一旦超過單輪預算（牆鐘的
87%），Worker 形態下**一次嘗試都無法開始**，補池會持續零產出。有兩條日誌，按**事件名**
grep（見下面「疑難排解」一節——比按中文文案 grep 更可靠，措辭怎麼調整都不會失配）：

下面兩段圍欄是閘道**逐字**印出的原文：`msg` 在原始碼裡是硬編碼的簡體中文，**不隨本頁語言翻譯**；
整條日誌也**只有一行**——`src/adapters/logger-console.ts` 刻意把換行清成空格，因為被撕開的後續行
拿不到 `[registrar]` 前綴就等於遺失。所以請按事件名 grep，別按本頁的譯文 grep。

**① 啟動時**印出一條**警告**（`console.warn`），事件名
`registrar.attempt_exceeds_worker_budget`（`grep 'registrar.attempt_exceeds_worker_budget'`），
形如：

```text
[registrar] registrar.attempt_exceeds_worker_budget CODE_TIMEOUT_MS 超过 Worker 单轮墙钟预算：Cloudflare Worker 形态下补池会一把 key 都铸不出来（每轮 attempted=0），请调小 CODE_TIMEOUT_MS。Node/Docker 的定时轮没有平台墙钟上限、不受此限制，但面板的「立即补池」在两种运行时上都带同一份轮级预算，Node/Docker 上同样铸不出来。 codeTimeoutMs=... worstAttemptMs=... workerRoundBudgetMs=...
```

它**不會阻止閘道啟動**——這一點與「缺憑證啟動即報錯」不同：Node/Docker 沒有平台牆鐘上限，
同一份設定在那邊完全合法，所以兩種形態都會印這條警告，但只有 Worker 真正受影響。

**② Worker 每一輪補池**（連第一次嘗試都開始不了時）再印一條**錯誤**（`console.error`），
事件名 `registrar.round_budget_impossible`（`grep 'registrar.round_budget_impossible'`），
形如：

```text
[registrar] registrar.round_budget_impossible 单次铸 key 的最坏耗时已超过本轮墙钟预算，一次尝试都无法开始，补池将持续零产出——这是配置问题不是瞬时状况，请调小 CODE_TIMEOUT_MS worstAttemptMs=... roundBudgetMs=...
```

每輪都會出現，可據此確認這是持續狀態而非偶發。

**在調大 `MINT_BATCH`、`CODE_TIMEOUT_MS` 或 `MAX_DOMAIN_ATTEMPTS` 之前，請自行依上述兩個
公式核算。** 頂到上限時，本次 Cron 呼叫會被平台中止；即使被中止也不會遺失已經鑄好的
key——每鑄出一把就立即寫入儲存，只是當輪次的補池不完整，下一個排程週期會繼續嘗試補齊。

## 補池怎麼算缺口（什麼樣的 key 佔著 `TARGET_KEYS` 名額）

### 四種 key 狀態各佔不佔名額

缺口 = `TARGET_KEYS` − **沒有被剔除的 key 數**。判準只有一條：**`evicted` 為假就佔名額。**

| key 的狀態 | 佔 `TARGET_KEYS` 名額嗎 | 能不能拿去打上游 |
|----------|-----------------------|----------------|
| 全新 / 可用 | 是 | 能 |
| **冷卻中**（被限流、連續失敗） | **是** | 不能 |
| **被管理員停用** | **是** | 不能 |
| 已剔除（401/403，憑證失效） | 否 | 不能 |

### 為什麼冷卻中的 key 也佔名額

**「冷卻中也佔名額」是刻意的**：冷卻是**會自己回來**的狀態，拿它當缺口去鑄新號，
鑄出來的帳號卻**不會**自己走——一次瞬時故障換來一份永久成本。實測（`TARGET_KEYS=3`）：
按「冷卻不佔名額」算的話，整池被限流冷卻一輪就會補出 3 把新的 ⇒ 池子變 6；
冷卻到期後缺口轉負、不再回收 ⇒ **永久停在 6**；下一次風暴 9，再下一次 12，線性成長，
而每一把都是一次真實的 Agnes 建號 + 一個真實花掉的臨時信箱。

**代價，明寫**：整池都在冷卻時註冊機**不會**去鑄替補，閘道在冷卻視窗內會持續回傳
`503`（最長一個 `COOLDOWN_PAYMENT_MS` / `COOLDOWN_STRIKE_MS`）。要立刻恢復，請在面板上
對這些 key 用「清冷卻」，而不是指望補池。

## 面板的「立即補池」

管理面板上那顆按鈕（`POST /admin/api/registrar/tend`）。回傳 `202` 表示**已經開始**，
補池在回應之後繼續跑；結果去看「補池歷史」那一欄，`trigger` 會標成 `manual`。

### 四條護欄

它有**四條護欄**，任何一條不滿足都不會啟動：

| 護欄 | 不滿足時 | 擋什麼 |
|----|--------|------|
| 同行程 / 同 isolate 的在途守衛 | `409 tend_in_flight` | 定時輪與按鈕撞車、同一副本上的兩個並行點擊 |
| 儲存層短鎖（`registrar_tend_lock`） | `409 locked` | **跨副本**重疊（多容器共用磁碟區、Worker 的兩個 isolate） |
| 兩次手動補池至少隔 10 分鐘 | `429 manual_cooldown` | 連點燒臨時信箱名額 |
| 每天最多 **24** 次 | `429 write_budget_exhausted` | 連點燒**儲存寫配額**（算式見 [DEPLOY.md](DEPLOY.md) 的「配額帳」） |

`429` 的回應內容帶 `remaining`（今天還剩幾次）、`resetAt`（UTC 零點恢復）與 `retryAfterMs`；
**`202` 的回應內容同樣帶 `remaining`**，面板據此如實顯示還剩幾次，不必等到點不動了才說。
註冊機沒打開時回傳 `409 registrar_disabled`。

### 誠實限定與殘餘風險

> [!WARNING]
> **誠實限定，別讀成「並行已解決」**：KV 是最終一致的，那把儲存鎖是**盡力而為、不是
> 互斥原語**。它擋的是「上一輪明明還在跑」這種最常見的重疊；同一毫秒發起的兩次點擊仍然
> 可能雙雙搶到。護欄鍵與補池歷史同樣是「讀—改—寫」，並行視窗裡會丟更新——後果的上界是
> 「閘門最多多放行（並行數 − 1）次、補池歷史最多缺（並行數 − 1）行」。

> [!WARNING]
> **殘餘風險**：手動補池與 Worker 的 Cron 用**同一個輪級牆鐘預算（780 秒）**，
> 它的作用是「不啟動一次明知跑不完的嘗試」，**不消滅洩漏，只把機率壓下來**——平台仍可能
> 在預算視窗之內中止呼叫，此刻正在鑄的那個臨時信箱就不會被刪掉。
> 注意這條與定時輪不同：**Node/Docker 的定時輪不帶這個預算，而手動補池帶**，
> 所以同一份設定下手動那一輪可能比定時輪少鑄幾把，剩下的名額留給下一次定時輪。

### 這幾把鍵不會自己消失

`registrar_tend_lock`、`registrar_manual_guard`、`tend:history`、`registrar:domains`、
`registrar:backoff` 五把鍵**都不帶 TTL**。它們的名字是固定字面量、數量恆為 1，陳舊值一律靠
**值比較**判定（過期的鎖不擋任何人、昨天的計數不算數、過期的退避視窗不擋任何一輪），
所以留著無害。

**代價明寫**：永久關掉註冊機、或者刪掉部署但保留 KV 命名空間時，它們不會自己消失。
要清理請手動刪鍵：

- Worker：`wrangler kv key delete --binding=POOL registrar_manual_guard`（五把各一次）
- Node / Docker：編輯 `DATA_DIR/store.json`，刪掉這五個頂層欄位

**`registrar:domains` 也是「認定網域台帳記錯了」時唯一的手動出口**：刪掉它等於讓註冊機
回到冷啟動，把已經花過的發碼請求重新花一遍——只在真的判斷它記錯了的時候才這麼做。

**`tend:history` 通常應當留著**：它是事故複盤時最想看的東西，而「關掉註冊機 N 天後補池
歷史整個消失」恰恰是最壞的時機——維運往往正是**因為**出事才關的註冊機。

## 鑄出來的 key 多久能被轉發路徑用上

**最多一個 `POOL_CACHE_TTL_MS`（預設 60 秒），不是「下一個請求」。**

補池與轉發用的是兩個相互獨立的 key 池儲存實例：補池那個每輪都真讀一遍儲存（它必須看到
當前真實的可用數，否則會重複補池、白燒信箱配額），轉發那個持有一份 isolate／行程級的
快照。兩者各自維護自己的快取，所以補池寫完 key 之後，轉發路徑要等**自己那份快照**過期
才會看到。Worker 上還要按每個活躍 isolate 各自的 TTL 計算。

**這條在池子被打空時最容易被誤讀**：日誌已經打了 `[registrar] … minted=1`，而閘道還會
繼續回傳 `503 pool_empty` 長達一個 TTL。那不是補池沒生效，等一個 `POOL_CACHE_TTL_MS`
即可；想縮短就把它調小（代價見 [DEPLOY.md](DEPLOY.md) 的「配額帳」）。

## 為什麼依序鑄 key、不並行

補池在單輪內**依序**鑄 key，每次之間插入隨機間隔，而不是並行發出多個鑄 key 請求。這不
是效能取捨，而是功能性限制：並行會同時撞上 YYDS Mail 的建號限流（短時間內建立信箱超過
約 10 次會回傳 `403`）與 Agnes 自身的註冊風控。依序執行加隨機間隔是讓註冊機能持續運作
的必要條件，不建議透過並行來「最佳化」它。

## 隱私說明

註冊過程中產生的信箱位址、帳號密碼只在記憶體中短暫存在，**用完即棄、不會被持久化**；
儲存中只會出現鑄出的 API key 記錄。鑄 key 結束後（無論成功或失敗）臨時信箱都會被刪除。

## 疑難排解

### 註冊機的三態

註冊機不是「開 / 關」兩態，是**三態**。第三態最容易被誤讀，面板上四處都寫著它。

- **已關閉**：`REGISTRAR_ENABLED` 沒開，或面板上的開關是關的。補池一次都不跑、一次外部請求都不發。
  面板上寫「已關閉」。這是預設狀態，不用恢復；要用它就去設定頁打開，並配好至少一條信箱通道。
- **已啟用**：開著，而且這份設定裝得起來，依 `TEND_INTERVAL_MS`（或 Worker 的 Cron）補池。
  面板上寫「已啟用」，兩張通道卡各自說清有沒有憑證、是不是本次選中的那條。
- **已啟用 · 本次沒跑起來**：開關是開的，但這份設定裝不起來（沒選通道、選中那條通道缺憑證
  ……），所以本次沒有啟動它。**閘道轉發完全不受影響**，只是不再補池。

第三態在面板上有四處提示，指的是同一件事：設定頁頂部的橫幅（逐條列出缺哪幾格）、
註冊機板塊的狀態行、總覽頁的設定摘要、以及事件板塊裡每一輪一條 `error` 級的 `registrar.blocked`。
**恢復方式**：按橫幅列出的那幾格在設定頁補齊，儲存即可，不需要重啟容器、也不需要重新部署。

> [!WARNING]
> **這樣做的代價**：故障從「響亮」變成了「安靜」。補池停擺之後池子會慢慢耗乾，最終以
> `pool_empty` 的形式在幾小時到幾天後炸出來，那時的症狀離真正的原因隔著好幾層。
> 上面那四處提示就是為此存在的——**你得去看**。

### 啟動與日誌的約定

- **啟用後若缺憑證，註冊機本次不啟動，但閘道照常轉發。**
  這一條**改過**：從前是「啟動即報錯」（fail-closed 到整個閘道），而註冊機是選用子系統，
  它缺一把信箱 key 不該讓轉發、`/health` 與管理面板一起死。現在缺的那幾格會逐條列在面板上，
  並且每一輪記一條 `error` 級的 `registrar.blocked`。三種狀態各自長什麼樣，見下面「註冊機的三態」。
- 補池過程中的日誌一律帶 `[registrar]` 前綴，可據此過濾查看註冊機相關的執行狀態。每條
  日誌的第二個欄位是穩定的機器可讀**事件名**（如 `registrar.round_budget_impossible`），
  按事件名 `grep` 比按中文文案 `grep` 更可靠：文案是給人看的，可能因措辭調整而變化；
  事件名是這套日誌唯一對外穩定的契約，不會變。
### 讀懂 `reasons=` 裡的失敗原因

- **一輪裡有名額沒鑄出來時，收尾會多打一條帶 `reasons=` 的告警**，形如
  `reasons=yyds:register_failed×3 moemail:code_timeout×1`。先看這一行判斷故障在哪一層：
  `code_timeout` = 這條通道收不到 Agnes 的信（網域 MX／郵件轉發規則）；
  `register_failed` / `login_failed` / `key_failed` = Agnes 側的註冊鏈路變了；
  `provider_error` = 信箱服務本身（憑證、活躍信箱配額、服務不可用）；
  `provider_missing` = 內部接線錯誤，正常設定下不會出現（缺憑證是啟動即報錯，走不到這裡）。
- **`reasons=` 裡出現 `key_suspicious`**：上游發回來的 key 材料含不可列印字元或空白。
  **這一輪確實鑄出來了**（Agnes 側帳號已經真的建出來、一個臨時信箱已經花掉），所以它
  **照常存進了池子**——在這裡拒收等於銷毀一份再也找不回來的憑證。但它多半每次被選中都
  會讓轉發失敗，請在面板上停用或刪除它。同時會有一條 `registrar.minted_key_suspicious`
  的 error 事件（只記通道與長度，**不記明文**）。
### 註冊機會記住哪些信箱網域能用

上游只接受一部分一次性信箱網域，其餘會被拒。**這個結論現在會落盤複用**：

- 穩態下**一次成功鑄號只打一次 `/api/verification`**——挑一個已知能用的網域，不再從
  上游全部網域裡隨機取若干個逐個試。這正是 `MAX_DOMAIN_ATTEMPTS` 的內建取值能降到 1 的原因。
- 面板的註冊機板塊有一行「網域台帳：可用 N · 判死 N · 待複查 N · 未探過 N（更新於 …）」。
- 結論要**連著兩輪**被拒才會被排到候選末尾（**同一輪裡被拒幾次都只算一次**）；只挨過一輪的
  算「待複查」，仍然會被選中，
  只是優先級低。一次成功會無條件把它覆蓋回「可用」。

#### 這個判定為什麼可能錯

> [!WARNING]
> **「判死」是我們的判定，不是上游的聲明。** 上游用同一個 `400` 同時表達「這個網域被
> 封鎖了」與「你這個出口發得太頻繁了」，唯一的區分線索是回應正文，而我們靠一張**詞表**
> 去認它——上游改一次措辭就會認錯。壓著這個誤判的有三層：判死要兩跳、一輪最多學一條、
> 以及**排序永遠不會把任何網域徹底排除**（判死的只是排在最後）。
> 但這三層壓的全是「好網域被判死」這一個方向。反方向——台帳裡那條「可用」已經過時、
> 網域其實早被上游封鎖——靠的是另一條規矩：**分類器判出什麼就記什麼，一條結論都不許吞掉**。
> 這條規矩曾被一道保險破壞過（「已知能用的網域被拒就改判成限流」），後果不是變慢而是
> **補池歸零**，最長 7 天；那道保險已經拆掉。
> 也就是說，這句收口的話得**按方向拆開**，三個方向的後果並不一樣：
> ① 好網域被判死這個方向——確實只是變慢、**不會歸零**（三層護欄 + 排序永不排除任何網域）；
> ② 台帳說「可用」而上游其實早已封鎖——靠「判出什麼就記什麼」，那條規矩已經修好；
> ③ 分類器把**真限流**讀成「網域被封鎖」——上游那句限流的話**我們的詞表一個都沒認出來**
>（注意不是「上游沒說」：它說了，是我們沒認出來），所以上面那兩層退避一次都不會產生，
> 本輪也不再提前停手，一輪最多打 `MINT_BATCH` 次註定失敗的發碼請求。接住這一檔的是下面
> 那張表的第三行：判據是**這一輪的形狀**（同一輪裡好幾個網域一起被判封鎖，**或者上游列
> 出來的網域一個不落全被判封鎖**，而這一輪一把 key 都沒鑄出來），不是上游的字眼。

#### 認定網域台帳記錯了怎麼辦

面板上沒有「逐個網域列出來」的檢視（上游幾百個網域會把一個每幾秒
被輪詢一次的介面回應撐大一個量級）。可選的處置有三種：等結論過期（判死的 24 小時、可用的
7 天）、等兩跳規則自己糾正、或者手工刪掉那把儲存鍵（見下面「這幾把鍵不會自己消失」）。

### 撞上上游限流之後會發生什麼

上游前面有一層邊緣限流（`429`），上游自己還有一層註冊限流（`400` + 一句「請求過於頻繁」
之類的話）。**兩層的懲罰視窗都比一輪補池長，而且視窗裡每打一次請求就把視窗續一次。**

所以撞上任一層之後：

- **這一輪當場結束**，不換網域、不繼續下一個名額；
- 記下一個**退避視窗**，下一輪開跑前先看它——**視窗內一次上游請求都不發、一個臨時信箱都
  不建**。補池歷史裡這一行的失敗歸因是「還在退避視窗裡，這一輪一次都沒開始」；
- 連著撞會**指數**拉長退避（封頂 4 小時）。這裡的「連著」數的是**連著幾輪一把 key 都沒出**：
  一輪裡只要鑄出過 key，指數就從頭數起——那一輪末尾又撞上限流的話，退避回到起步那一檔
  而不是接著翻倍；那一輪一次限流都沒撞到的話，那把鍵直接清掉。
- 上一段退避過完之後，隔了 4 小時以上都沒再撞上，指數同樣從頭數（比如池子一直是滿的、
  註冊機好幾輪都沒真正跑過的那種）。

#### 第三檔：我們的詞表一個字都沒命中，但這一輪的網域成片掛了

上游改一次限流文案，真限流就會被逐條讀成「網域被封鎖」
——上面兩檔一次都不會觸發，而本輪也不再提前停手。這時唯一還站得住的證據是**這一輪的形狀**，
它有兩條判據，命中任一條就算：

- 同一輪裡有兩個以上的網域被判封鎖；
- **或者上游列出來的網域這一輪一個不落全被判封鎖**（只設了一個信箱網域的部署就靠這一條 ——
  它永遠湊不滿上面那兩個）。

兩條都要求**這一輪一把 key 都沒鑄出來**。註冊機據此記一個退避視窗（起步 30 分鐘，同樣指數、
同樣封頂 4 小時），**但它不中止這一輪、也不吞掉任何網域結論**——這一輪該輪著試的網域照試、
該出的 key 照出。只要這一輪鑄出過 key，這一檔就一個字都不記。

#### 這一檔亮起來時，兩種可能都還開著

> [!WARNING]
> **這一檔亮起來的時候，兩種可能都還開著，橫幅不會替你選**：上游換了限流的措辭、而我們的
> 詞表沒認出來；或者上游真的把這些網域成批換進了黑名單。**別把它讀成「上游沒說過限流」**
> —— 這一檔要治的頭號場景恰恰是上游說了、只是我們沒認出來。

#### 上游原話去哪裡翻：兩支拿得到的證據不一樣

**別照著「去看 `registrar.domain_blocked`」一條路走到黑 —— 它在其中一支上根本發不出來。
代價如實記在這裡：**

- **同一輪裡好幾個網域一起被判屏蔽**那一支：鉗位一生效，本輪**全部**「被屏蔽」判定被整體
  作廢 ⇒ 台帳學不到 `blocked` ⇒ `registrar.domain_blocked` **這一輪一條都不會發**。
  這一支能拿到的上游原話只有 `registrar.known_good_domain_rejected` 那幾條，而它**只涵蓋
  台帳裡已知能用的那些網域** —— 冷啟動、或者上游這一輪新列出來的網域，一句原話都沒有。
  同一輪發出的 `registrar.domain_verdicts_discarded` 只帶被作廢的條數、本輪產出與退避截止
  時刻，**不帶上游原話**。
- **上游列出來的網域一個不落全被判屏蔽**那一支（只配一個信箱網域的部署走的就是它）：鉗位
  湊不滿、不生效 ⇒ 台帳照常學得到結論，第二跳判死時 `registrar.domain_blocked` 帶著上游
  原話發出來。

#### 第三檔接住之後還剩多少請求量

數寫在這裡（內建值、測試替身量出來的）：走到指數封頂之後是
**每 8 輪打一次、每次 `MINT_BATCH` = 5 個發碼請求**，Cron 每 30 分鐘一輪
⇒ 48 輪/天 ÷ 8 × 5 = **約 30 次/天**。
兩個對照數：**接上這一檔之前是每一輪都打滿 ⇒ 約 240 次/天**；而「上游的措辭落進了詞表」的
第二檔是撞上就整輪停手（一輪 1 次）⇒ **約 6 次/天**。
⇒ **30 不是 6**：這一檔比第二檔貴，因為它不中止本輪 —— 本輪該出的 key 照出，代價是本輪
剩下的名額照打。

#### 退避橫幅：三檔的處置不一樣

面板的註冊機板塊會顯示一條退避橫幅：

| 是哪一檔 | 面板怎麼說 | 你能做什麼 |
|------------|----------|----------|
| 邊緣限流 | 「補池打得太密」 | 調大 `MINT_DELAY_MIN_MS`，或調小 `MINT_BATCH` |
| 上游自己的註冊限流 | 「上游回話裡帶著『請求過於頻繁』這類字眼，這是我們按詞表下的判定，不是上游給的結論」 | 先調大 `MINT_DELAY_MIN_MS`、調小 `MINT_BATCH`；確認這個出口的註冊額度真到頂了，再談換出口 |
| 這一輪的網域成片被判封鎖（好幾個一起，或者列出來的全都被判封鎖）、且這一輪零產出 | 「上游的回話裡沒有一句我們認得出的限流的話，這是我們按這個形狀下的判定；上游換了限流措辭、或者真的成批換了黑名單，兩種可能都還開著」 | 兩支拿得到的證據不一樣，見上一節；別預設 `registrar.domain_blocked` 裡一定有 |

> [!IMPORTANT]
> **換一條信箱通道逃不掉這一檔。** 限流發生在「你的出口位址 → 上游」這條邊上，與你用
> 哪條信箱通道無關。看到退避橫幅時去切通道是白費力氣。

**空池填滿會明顯變慢**：目標 20 把 key 從「幾分鐘」變成大約 4～5 輪。Cron 每 30 分鐘一輪
⇒ **約 2～2.5 小時**。這是把「打光額度還在白打」換成「慢但真的出 key」的直接代價。

### 一條通道失敗之後會發生什麼

**兩條通道是二選一，所以「換一條」這件事只有你能做。** 選中的那條通道失敗時：

- **本次名額作廢，本輪的下一個名額照常開始**（先睡 `MINT_DELAY_MIN_MS`~`MINT_DELAY_MAX_MS`
  的隨機間隔）。列網域失敗、憑證無效、所有候選網域都建不出信箱、收不到驗證碼、
  網路抖動、網域被全部封鎖、註冊 / 登入 / 建 key 失敗——這幾種全都是這一檔。
- **有兩種例外，都會立刻結束這一輪**：
  - Agnes 後端整體故障（`upstream_error`）——繼續跑只會在故障期間製造更多注定失敗的請求；
  - **撞上上游限流（`rate_limited`）**——見下面「撞上上游限流之後會發生什麼」。
- **除限流之外沒有跨輪退避，也沒有指數補償。** 一般失敗不改變下一輪的時間：Node/Docker
  是固定的 `TEND_INTERVAL_MS` 計時器，Worker 是 `wrangler.toml` 裡的 Cron。輪內的節流已經
  有兩層（嘗試之間的隨機間隔、Worker 側的輪級牆鐘預算）。

#### 代價，以及怎麼發現它

> [!WARNING]
> **這是一次能力下降，明寫在這裡。** 從前一條通道收不到驗證碼還有一次自動換通道的機會，
> 補池會變慢但仍然出 key；現在同一條通道收不到驗證碼 = 這一輪乃至這一天一把都鑄不出來，
> 直到你自己去面板換一條通道。故障形態從「補池變慢」變成「補池零產出、池子慢慢耗乾、
> 幾小時到幾天後以 `pool_empty` 503 炸出來」——**把一個自癒的故障換成了一個要人管的故障**。
> 這是「二選一」的固有代價，不是缺陷。

**怎麼發現它**：補池歷史裡每一輪的失敗歸因逐條帶著通道名（`reasons=` 那一行）、註冊機板塊
的池子四格數字、以及通道請求失敗時那條帶**實際請求位址**的事件。看到零產出就去面板上點一下
另一條通道的「測試連線」，通了就把通道切過去。

### 某條通道持續失敗怎麼辦

- 若某條通道持續註冊失敗（例如 Agnes 收緊了驗證碼或人機驗證策略），這是程式碼層面無法
  規避的上游變化，可以關閉註冊機、改為手動匯入 key（見 [DEPLOY.md](DEPLOY.md)）。
