# 部署指南

agnes2api 只有一種部署形態：用本倉庫的程式碼建構出的 Docker 映像，跑在 `docker compose` 上。

> [!NOTE]
> 全部狀態只落在一個地方——掛載卷上的一份 JSON 檔案（`store.json`）。把那個目錄備份下來，
> 就等於把全部狀態備份下來了。

## 系統要求

只有一條路，所以只有一欄。

| 項 | 要求 |
|----|------|
| 命令列 | Docker Engine 24+ 與 `docker compose` |
| 平台 | 一台能跑容器的機器 |
| 上游 | 至少一把 Agnes API key，見下一節 |

> [!TIP]
> 除此之外什麼都不用裝——不需要本機 Node.js，也不需要建置工具鏈：`cp .env.example .env`
> 之後一條 `docker compose up -d` 就能起來。
## 取得 Agnes 憑證

閘道自己不產生 key，它只是把請求分發到你手上那一把或幾把 Agnes API key 上。
拿到 key 有兩條路，**兩條平級**，不預設主備。

### 手動取得

去 Agnes 平台註冊帳號，在後台新建一把 API key，複製出來備用。
這條路一次只給你一把，適合先把閘道跑通、確認四種協定都通了再說。

### 讓註冊機自動補池

本倉庫自帶一套可選的註冊機，能依 `TARGET_KEYS` 把池子自動補到目標數量。
它**預設關閉**（`REGISTRAR_ENABLED` 不設就是關），工作原理、兩條信箱通道怎麼選、
一輪補池最長要跑多久，完整說明見 [REGISTRAR.md](REGISTRAR.md)。

> [!IMPORTANT]
> 無論走哪條路，key 都以**明文**落在 `store.json` 裡。資料目錄請按憑證處置。

## Docker 部署

### 前置條件

> [!NOTE]
> 同目錄 [README](README.md) 的 `## ⚡ 快速部署` 一節給的是同樣三條指令的短版。
> 本節是長版：它把每一條指令留給你自己決定的那些事寫開，第一件就是首次啟動前必須
> 設好的那把權杖。

克隆倉庫並準備環境變數檔：

```bash
git clone https://github.com/xwteam/agnes2api.git
cd agnes2api
cp .env.example .env
```

**不用映像、直接從原始碼跑**：`pnpm dev:node` 以 `node scripts/build-ui.mjs` 開頭，
然後建置並跑起 `dist/entry/node.js`。裸跑 `node dist/entry/node.js` 也起得來，
但面板會停在上一次產生的那一份——改了 `admin-ui/` 卻看不到變化，多半就是這個原因。

### 設定

編輯 `.env`，至少設定 `GATEWAY_TOKEN`。其餘變數見下方
[環境變數](#環境變數) 表。

`.env` 的最小可用形態就兩行；其餘變數都有預設值，需要時再加：

```env
# 必填：用戶端呼叫本閘道時必須攜帶的權杖。發給下游使用者的就是它。
GATEWAY_TOKEN=換成你自己的長隨機串

# 選填：容器內的監聽埠。
# docker-compose.yml 會把它同時用作宿主側發布的埠。
PORT=8080
```

> [!CAUTION]
> **`DATA_DIR` 與 docker-compose.yml 的卷掛載綁死，Docker 形態下別單獨改它。**
> 那一行 `./data:/app/data` 是寫死的，`.env` 裡的 `DATA_DIR` 完全不參與它的插值。
> 把 `DATA_DIR` 改成別的路徑而不動那一行，什麼都不會攔你：容器起得來、`/health` 回
> `ok`、面板與 key 池一切正常、註冊機照常補池，而 store.json 落進**容器可寫層**——
> 下一次照「更新」升級一次，容器一重建，整池 key、已簽發的對外 API 密鑰、面板設定
> 一起消失，而你一直在備份的 `./data` 從頭到尾是空的。
> 要換資料落在宿主哪兒，改那行掛載的**左半邊**；真要改右半邊，就把 `DATA_DIR` 改成
> 同一個路徑，兩邊一起改。容器啟動時 entrypoint 會檢查這件事：它沒落在任何
> 掛載點上時，容器日誌裡有一條「沒有落在任何掛載點上」的警告——那是這條鏈上唯一的
> 訊號，`/health` 不報資料落在哪兒。

#### 資料目錄與擁有者：容器會改寫 `./data`（請先知悉）

容器**以 root 進入 entrypoint**，做兩件事後再降權：

- 若 `DATA_DIR`（預設 `/app/data`）的擁有者與容器內執行使用者 `app`（**uid 100 / gid 101**）
  不一致，就遞迴 `chown` 該目錄；擁有者已經一致時不做任何改寫。
- 隨後用 `su-exec` 降權，**主行程（PID 1）以 app 執行，不是 root**。

必須在執行期做這件事的原因是：綁定掛載時宿主目錄的擁有者會蓋過映像檔建置期的 `chown`，
容器內的 app 因此寫不進 `store.json`，而這種失敗是靜默的（所有 API 回傳 `pool_empty`）。

**副作用**：綁定掛載改的是**宿主**上的檔案——`docker compose up -d` 之後，你的 `./data`
及其中的檔案擁有者會從你自己的 uid 變成 `100:101`，之後在宿主上讀寫或備份它需要 `sudo`。
不希望發生這件事的話，用 `--user`（或 compose 的 `user:`）指定非 root 執行：此時
entrypoint 完全不 chown，資料目錄的擁有者與可寫性由你自己準備。

基於同樣的原因，映像檔**沒有** `USER app`，預設使用者是 root
（`docker inspect --format '{{.Config.User}}' <image>` 輸出為空）。這對 Kubernetes 有影響：
設了 `runAsNonRoot: true` 卻沒明確給 `runAsUser` 時，kubelet 會拒絕啟動該容器。這類部署請
明確寫 `runAsUser: 100`、`runAsGroup: 101`（或任何你自己的 uid），並自行準備磁碟區的
擁有者——非 root 啟動時 entrypoint 走的是「不 chown、直接執行」的分支。

安全邊界：`DATA_DIR` 被設成 `/` 或某個頂層系統目錄（`/etc`、`/usr` 等）時，entrypoint
拒絕在其上遞迴 chown（只印出警告，不影響啟動），避免把整個容器檔案系統改成 app 可寫。

### 部署

啟動容器：

```bash
docker compose up -d
```

**首個映像發布之前**（或 fork 之後），這條命令會回落到本機建置——
`docker-compose.yml` 裡那段 `build:` 就是做這件事的。

`docker-compose.yml` 預設發布 `8080` 埠（可透過 `.env` 內的 `PORT` 覆寫），並將
`./data` 掛載到容器內的 `/app/data`——`store.json`（key 池與任何持久化設定）就存
放在這裡。重啟／升級時務必保留這個目錄，它是已匯入 key 池的唯一副本。

### 驗證

確認容器健康：

```bash
curl http://localhost:8080/health
```

映像檔內建 `HEALTHCHECK`，Docker 會依此回報容器健康狀態。資料目錄不可寫時 `/health`
回傳 `503` 且 `status` 為 `degraded`，容器會被標成 unhealthy，具體原因見容器日誌。

下面兩條是查問題時反覆要用的，先在這兒給全——本文後面凡是說「見容器日誌」，指的都是
第二條：

```bash
docker compose ps                     # 容器在不在、健康不健康
docker compose logs -f --tail=100     # 容器日誌：entrypoint 的警告、admin.token_rejected 都在這裡
```

### 更新

```bash
docker compose pull
docker compose up -d
```

`docker compose pull` 拉的是 `.env` 裡 `IMAGE_TAG` 指定的那個 tag（不設就是 `latest`）。
映像全名是 `ghcr.io/xwteam/agnes2api`，有哪些 tag 見
[GHCR 的 packages 頁](https://github.com/xwteam/agnes2api/pkgs/container/agnes2api)。
**升級 = 把 `IMAGE_TAG` 改成要升的版本號再 `docker compose up -d`；回滾 = 改回上一版。**
釘住版本號之後，這份 `.env` 才答得出「現在跑的是哪一版」，`:latest` 答不出。

> [!IMPORTANT]
> **改完 `.env` 要跑 `docker compose up -d`，不是 `docker compose restart`。**
> 後者只是重啟同一個容器，而容器的環境是**建立**時固化的，改了 `.env` 一個位元組都不會
> 變；`up -d` 偵測到設定變化才會重建容器。補 `ADMIN_TOKEN` 與輪換口令踩的是同一個坑，
> 後者更隱蔽：你以為輪換完了，舊口令其實還在生效。

`./data` 不動，key 池與設定都在那兒。**升級前先備份那個目錄**（見下文「備份與還原」）：
它是已匯入 key 池的唯一副本，沒有第二份。

## 環境變數

| 變數 | 是否必填 | 預設值 | 說明 |
|----|--------|------|----|
| `GATEWAY_TOKEN` | **是** | – | 客戶端呼叫本閘道時必須攜帶的權杖。 |
| `RESET_CONFIG` | 否 | – | 逃生口：設為 `1` 時啟動**完全忽略**儲存裡的 `config` 鍵（只忽略，不刪除），只用環境變數與內建預設值。什麼時候用、用完要做什麼，見下文。 |
| `AGNES_BASE_URL` | 否 | `https://apihub.agnes-ai.com/v1` | 上游 Agnes API 的基底位址。 |
| `UPSTREAM_TIMEOUT_MS` | 否 | `8000` | **串流**回應與影片輪詢的首位元組逾時：超過此毫秒數未收到上游首位元組則中止本次呼叫。 |
| `UPSTREAM_SYNC_TIMEOUT_MS` | 否 | `120000` | **同步**端點的整體逾時預算，只作用於「首位元組要等上游把整個結果算完才到達」的請求：圖片生成、影片建任務，以及所有**非串流**對話。見下文說明。 |
| `MAX_STRIKES` | 否 | `3` | 連續瞬時故障（逾時、網路錯誤、上游 `5xx`）累積到此閾值後，該 key 進入長冷卻。 |
| `COOLDOWN_RATE_LIMIT_MS` | 否 | `60000` | 上游回傳 `429` 後，對應 key 的冷卻時長。 |
| `COOLDOWN_PAYMENT_MS` | 否 | `3600000` | 上游回傳 `402` 後，對應 key 的冷卻時長。 |
| `COOLDOWN_STRIKE_MS` | 否 | `1800000` | key 的瞬時故障累積到 `MAX_STRIKES` 後的冷卻時長，到期自動恢復。 |
| `POOL_CACHE_TTL_MS` | 否 | `60000` | 每個行程在記憶體裡快取一份 key 池快照，本值是它的存活時長；`0` = 關閉快取。**儲存讀取次數與請求數無關**，只取決於重新整理頻率。代價見下文。 **建立實例時讀一次**（`src/http/wire.ts`）：改了要重建容器才生效，**面板改它不會立刻生效**。 |
| `POOL_TOUCH_INTERVAL_MS` | 否 | `21600000` | key 的「最後使用時間」最多多久寫入一次；`0` = 每次成功請求都寫入。它是純展示欄位、不參與排程，同一個間隔也管著面板上的用量計數。代價與「怎麼清計數」見下文。 **建立實例時讀一次**（`src/http/wire.ts`）：改了要重建容器才生效，**面板改它不會立刻生效**。 |
| `USAGE_STATS_ENABLED` | 否 | `false` | 面板「用量」板塊的 Tier-2 時間序列（按天／小時／模型／協定）。**判據是逐字的 `true`**，寫 `1` / `yes` 都算關。**預設關，而且「關」是零成本的**。打開之後的開銷、**短命實例上計數會丟而不是遲到**見下文。建 app 時讀一次，改了要重建容器才生效。 |
| `PORT` | 否 | `8080` | 容器內的監聽埠；`docker-compose.yml` 會把同一個數發布到主機上。 |
| `DATA_DIR` | 否 | `/app/data` | 檔案儲存寫入 `store.json` 的目錄。**別單獨改它**：它與 compose 的卷掛載綁死，見上文「Docker 部署 → 設定」。 |
| `APIKEY_CACHE_TTL_MS` | 否 | `300000` | 對外 API 密鑰表在每個實例裡的快取時長；`0` = 關快取。它同時決定停用一把密鑰多久才在共用同一個卷的別的容器上失效，見下文。**建立實例時讀一次。** |

### 取值範圍與兩個「建立實例時讀一次」的例外

上表中的每個變數在 `.env.example` 中都有一行範例，`cp .env.example .env` 之後依需求修改即可；
那份檔案的註解詳略不一（多數變數只有一行，個別寫滿十幾行），完整的取值範圍與代價以本表
為準。以上數值型變數都必須是整數；除
`POOL_CACHE_TTL_MS` 與 `POOL_TOUCH_INTERVAL_MS` 的下界是 `0`（`0` 表示「關閉」）之外，
其餘都必須大於 `0`，否則閘道拒絕啟動。

`POOL_CACHE_TTL_MS` 與 `POOL_TOUCH_INTERVAL_MS` 是**建立 app 時讀取一次**的，改了要重建
容器才生效，不像其餘設定項那樣逐次生效。

### `RESET_CONFIG`：什麼時候用這個逃生口

> 它真正的用途是**把面板存的那份設定整份旁路掉**：只用環境變數與內建預設值起一次，
> 好讓你回到一個已知乾淨的狀態。用完記得移除這一行，否則面板裡儲存的設定永遠不會生效。

> [!WARNING]
> **別把它當成「設定寫壞了就用它救」。** 儲存裡的值今天幾乎寫不壞到讓閘道起不來：
> 數值非法會**回落到預設值**（面板上會報降級），註冊機那一族的問題只讓**註冊機本次不啟動**、
> 閘道照常轉發。真正還能讓閘道起不來的只剩一條——**閘道權杖兩邊都沒有**——
> 而 `RESET_CONFIG=1` 恰恰會把儲存裡那把權杖也一起忽略，**照做只會讓情況更糟**。

### `POOL_CACHE_TTL_MS` 的代價

**儲存讀取次數與請求數無關**——快照熱著的時候轉發路徑一次都不讀，所以這顆旋鈕買到的是
「每個行程少讀幾次 `store.json`」，付出的是「那份快照允許多陳舊」。

> **這件事只在多個行程共用一個卷時才有意義**：負載平衡後面掛幾個容器，或者滾動重啟時
> 新舊容器同時在跑。其他行程判定的冷卻／剔除，本行程最多晚**本值**才看到；預設 60000 時
> 上界是 **60** 秒。單容器部署沒有這個視窗：判冷卻的就是握著快照的那個行程。

而且不只是「看得晚」：陳舊快照上的任意一次排程寫入會把整條記錄覆寫回去，**抹掉**其他
行程在這個視窗裡剛寫下的 `evicted` / `cooldownUntil`，那次判定要重新發生一遍。

### `POOL_TOUCH_INTERVAL_MS` 的代價與「怎麼清計數」

為它每次成功請求都寫一次盤，等於為一個沒人拿去排程的時間戳整份重寫一遍 `store.json`。
不這麼做的代價是：面板「最後使用」的精度最粗到這個間隔。同一個間隔也管著面板上的用量
計數（請求數 / 成功率）。

> [!WARNING]
> **手工改小儲存裡的 `stats`（例如歸零）之後，面板可能先顯示為已歸零、隨後又被頂回舊值**：
> 快照過一個 TTL 會讀到歸零後的值，而還在執行的實例記著自己的寫入基線，下一次真正寫入又會
> 按基線寫回去，最遲到這個實例被回收之後才真正一致。

**要清計數就走經過 repo 的那條正式路徑**：`PATCH /admin/api/keys/:id` 帶 `clearStats`，
它把**處理這次請求的那個實例**攢著的寫入基線與尚未寫入的增量一併作廢，**於是在這次重設之後
才開始的請求不會把舊值頂回去**；但**重設那一刻已經在飛的請求**手上那份記錄取自重設之前，
它收尾時會拿那份舊值重建基線，同時跑在同一個卷上的**別的**容器也各有各的基線，
仍可能把舊值頂回來一次。**它今天只有 API，面板上沒有這顆按鈕。**

### `USAGE_STATS_ENABLED`：打開之後要付什麼

「關」是零成本的：不建任何記憶體累加器、一次儲存寫都沒有。打開之後每個實例每個落盤間隔
重寫一次 `store.json` 裡的一個分片——**預設兩小時的間隔下每天最多 13 次**，沒有流量的
那個間隔一次都不寫。未落盤的尾巴最長 2 小時。這個開關要重建容器之後才生效。

> [!WARNING]
> **「尾巴」不等於「遲到」**：計數先攢在實例的記憶體裡，實例活不到一個落盤間隔時，
> **那些計數隨實例一起消失，不是延遲入帳**。
> **重建容器正是這件事最常發生的場景**：為改一個環境變數重建一次容器，最多兩小時的計數
> 就跟著舊行程走了，面板上那一段時間看起來與「沒人用過」一模一樣。
> 在意這段的話就調小 `USAGE_FLUSH_INTERVAL_MS`，下一節寫著它的代價。

### `USAGE_FLUSH_INTERVAL_MS`：能買回什麼，買不回什麼

看到「尾巴最長 2 小時」，第一反應是把落盤間隔調小——這條路在本形態下是通的：
`USAGE_FLUSH_INTERVAL_MS` **接受任何正整數**，寫 300000（5 分鐘）完全合理。
付出的是每個實例每個間隔多寫一次分片，買到的是「行程停掉時會隨它消失的那段計數」變短。

> [!WARNING]
> **這個值寫錯是在裝配 app 時就拒絕，不是等到第一個請求**（`src/http/usage-sink.ts`）：
> 不是整數、或者小於 1，行程會印出原因並退出。**這道校驗與 `USAGE_STATS_ENABLED`
> 開沒開無關**（`src/http/wire.ts` 無條件解析它），所以把統計關掉**並不能讓它消失**——
> 要嘛把值改對，要嘛把這一行刪掉。容器起不來是刻意選的症狀：它比「統計資料悄悄變歪」
> 好發現得多。

<summary><b>點擊展開：「尾巴最長 2 小時」承諾了什麼、沒承諾什麼（四點）</b></summary>

① **尾巴不等於「遲到」，而且它的兩個症狀是同一件事**：面板上的「今天」最多可能差一個
   落盤間隔；而**任何一個在下次落盤之前就停掉的實例，會把它累計的那些計數一起帶走**。
   計時是從實例啟動那一刻開始的，所以一個只活了十分鐘就被重建的容器，一個數都沒存下。
   這是用量數字全程帶「≈」的原因之一，不是缺陷。

② **本形態下沒有「每天寫預算」這道閘。** 程式碼裡那道閘還在（`budgetPerDay`），但檔案
   儲存沒有寫入配額要保護，於是閘道把它留空：不會有「用盡」，也就談不上「恢復」與「補寫」。
   **別把這句讀成「Docker 上不會丟資料」**——會丟的是第 ① 點那條尾巴。

③ **同一天最多只留得下 2 個實例的資料，多出來的互相覆蓋。** 用量分片按
   `usage:<UTC 日>:<槽>` 存，**只有 2 個槽**，每個實例按自己的分片 id 穩定雜湊到其中一個。
   所以三個以上容器共用一個卷時，同一個槽裡是後寫覆蓋先寫。**這是用量數字帶「≈」的另一個
   原因**；它影響的是數字全不全，從不影響閘道轉發。

④ **三條媒體端點（圖片生成、影片建任務、影片輪詢）不計數。** 它們燒的是與四條對話協定
   **同一批**上游 key，卻什麼都不記 ⇒ 面板上的「總請求數」系統性地低於真實轉發量。
   這是一條已知邊界、不是缺陷；要判斷 key 的消耗，看 key 池那一側。

### 儲存裡每一把鍵的同步代價

檔案儲存沒有讀取、寫入、`list`、delete 任何配額——一次重寫的代價就是你自己磁碟上的一次寫。
真正值得知道的是**一處改動多久才會被別人看見**：這件事對其中兩把鍵是安全屬性，對其餘
幾把是疑難排解時的坑。

#### key 池與它的索引

閘道維護一把 `pool:index`，裡面列著池子裡全部 id，好讓轉發路徑永遠不必掃全庫。
**有兩條自癒路徑繞不開一次全量掃描**，它們共用同一個內建的 **10 分鐘**退避
（寫死的常數，不是環境變數）：

- **空池重掃**——索引解析得開，卻一條活記錄都讀不出來，於是閘道掃一次，把「手寫進去
  但沒進索引」的記錄找回來；
- **索引缺失兜底**——`pool:index` 本身讀不出來或解析不開，於是閘道同樣掃一次，嘗試重建索引。

池子是空的**並且**那次掃描也失敗時，閘道回 `500`，真實原因寫進日誌；它**不會**把這種
失敗偽裝成 `503 pool_empty`，因為此刻本文件描述的兩條自癒路徑都已經斷了，說一句
「池子是空的」只會把人引去看錯的地方。

#### 對外 API 密鑰：吊銷不是立刻生效

校驗一把面板簽發的密鑰要讀一張表，每個實例把它快取 `APIKEY_CACHE_TTL_MS`（預設 5 分鐘）。

- **全部客戶端都用 `GATEWAY_TOKEN` 的部署，一次都不讀這張表。** 那個零是**結構性**的、
  不是開關：主權杖在鑑權的第一段就比完了，那條路徑上根本沒有讀這張表的呼叫點。
  完全不帶憑證的請求同樣一次都不讀——掃描器撬不動它。
- **簽發 / 改名 / 停用 / 刪除 / 清空各自整表重寫一次**，而且只在人點一下時發生。
  表裡有多少把密鑰不影響這個次數。

> [!IMPORTANT]
> **停用與刪除不是立刻生效的。這一條與安全有關，別把它讀成「很快就會生效」。**
> 處理這次請求的那個實例立刻生效；共用同一個卷的別的容器最長還要
> `APIKEY_CACHE_TTL_MS` 才停用 ⇒ 預設約 **5 分鐘**。想更快只有調小它，代價只是每個實例
> 每個間隔多讀一次表。

#### 面板裡點一下會寫什麼

這些都不計量，但有兩種形狀值得在點之前知道：

- **匯入 M 把新 key** 會寫 M 條記錄加一次索引，**一次最多 200 把**——超了直接 `400`，
  **不靜默截斷**。把一次大匯入拆成幾批不會更便宜，因為索引每批都要重寫一次。
- **重複匯入同一批 key**（不勾「重設已存在 key 的狀態」）**什麼都不寫**：重複項預設跳過、
  不覆蓋，所以重新貼一遍整份清單是安全的。
- **批次刪除 N 把** 只重寫**一次**索引，不是 N 次；**清空 key 池**同理。
- **改一把 key**（停用 / 啟用 / 備註 / 清冷卻 / 清 strikes / 解除剔除 / 重設用量計數）
  **無論改的是哪一項，都是一讀一寫**：它們走同一個 handler、同一次落盤，重設用量計數
  不額外讀寫任何東西（它清的是記憶體裡那份落盤基線）。

  > [!IMPORTANT]
  > **括號裡最後那一項是這裡唯一一個「面板上點不到」的**：重設用量計數**今天只有 API，
  > 面板上沒有這顆按鈕**（同上面 `POOL_TOUCH_INTERVAL_MS` 那一格）。這份枚舉列的是那個
  > handler 認得的全部動作，不是面板上按鈕的清單；它寫在這裡，是免得有人以為換條路更貴。
- **「立即補池」是唯一帶每日上限的面板動作**——每天最多 **24** 次（第四條護欄，見
  [REGISTRAR.md](REGISTRAR.md)）。這道閘護的是你的臨時信箱名額與上游平台，不是儲存預算。
- **儲存設定**重寫 `config` 那一條，而**校驗沒過的儲存一個位元組都不寫**。
- **危險區那兩顆按鈕**：重設設定（`/admin/api/config/reset`）重寫的是同一條；清空 key 池
  （`/admin/api/keys/purge`）刪掉每一條記錄，索引只重寫**一次**。

有兩筆讀取扇出基於同樣的理由值得知道：

- **面板「用量」板塊的 `30d` 那一檔**一次請求讀 `30 × 2` 個分片
  （`USAGE_DAY_RETAIN × USAGE_SLOTS`）。**這段扇出本倉沒有在真機上了結過它**，所以這裡唯一
  承諾的是它**如實失敗**：中途失敗時整條 `days` 序列回 `null`、`note` 是 `read_failed`
  ——它絕不會把已經讀到的那幾片冒充成完整畫面。
- **偵錯台跑一次影片任務最多 `1 + 60` 次上游請求**（1 次建任務 + 最多
  `VIDEO_POLL_MAX_ATTEMPTS` 拍輪詢）。它放大的是**上游**配額與 key 的使用計數，
  與你自己磁碟上的任何東西無關。

### 管理面板相關變數（預設關閉）

| 變數 | 是否必填 | 預設值 | 說明 |
|----|--------|------|----|
| `ADMIN_TOKEN` | 否 | 無（面板不啟用） | 管理介面的口令。**必須與 `GATEWAY_TOKEN` 不同**，且至少 24 位；**首尾不得有空白**，且只能由**可列印 ASCII（0x20–0x7E）**組成。字元集、長度下限、與閘道口令不同這三條的理由，以及兩種不合規各自的後果，見下文。 |
| `TRUST_PROXY` | 否 | 未設定（**任何**轉發標頭都不信） | 只有在閘道確實位於代理之後（CDN，或容器前面的 nginx / Caddy / Traefik）時才設成 `1`。它決定登入失敗事件裡的用戶端 IP 從哪裡取，見下文。 |

**沒設定就是面板整個不可用，而閘道照常轉發。** 此時存取 `/admin/...` 得到的是 **`404` 而不是
`401`**：整棵樹根本沒註冊，因此不會洩漏「這裡有個後台」。這與註冊機預設關閉是同一條規矩——
`ADMIN_TOKEN` 缺失或設錯，絕不能讓閘道轉發停擺。

兩行都寫進與其餘設定同一份 `.env`：

```env
# 選填：管理面板口令。不設 = 整棵 /admin 樹不註冊。
# 必須與 GATEWAY_TOKEN 不同，且至少 24 位、純可列印 ASCII。
ADMIN_TOKEN=換成你自己的另一串長隨機字串

# 選填：容器確實位於會改寫用戶端位址的代理之後時才設成 1。
# 直接暴露的部署不要設它。
TRUST_PROXY=1
```

#### `ADMIN_TOKEN` 的三條硬規則

**「不合規」有兩種，後果完全不同，別混成一句：** 未設定、或它自身不合規（首尾空白 / 含非可
列印 ASCII / 短於 24 位）時整棵 `/admin` 樹都不註冊，日誌裡是 `admin.token_rejected`；設定得
合規、卻與生效的 `GATEWAY_TOKEN` 相同時，樹**照常註冊**、面板本體打得開，只有管理介面每次
回傳 `503`，日誌裡是 `admin.token_conflict`（這條只在每個管理請求上複查，不在啟動時攔）。

**首尾不得有空白**：HTTP 請求標頭的值在傳輸層會被去掉首尾空白，而環境變數不會，帶空白的
口令任何用戶端都送不出來。

##### 為什麼只允許可列印 ASCII

口令還必須只由**可列印 ASCII（0x20–0x7E）**組成，這條限制有三段不同性質的理由：

1. 漢字 / emoji / 零寬空格這類碼點大於 U+00FF 的字元，以及換行與 NUL，瀏覽器在設定請求標頭時
   **直接拋錯**——請求壓根送不出去，留著它只會裝出一棵 200 但永遠進不去的面板，而且服務端
   連一條 `admin.login_failed` 都不會有。
2. **除 TAB 外**的其餘控制字元（`0x01–0x08`、`0x0B`、`0x0C`、`0x0E–0x1F`、`0x7F`，共 29 個）
   瀏覽器送得出去，但會被 HTTP 解析器判成 `400`。
3. **TAB（`0x09`）**與 `é` / `£` / 不間斷空格這類 `0x80–0xFF` 的字元**其實送得出去也能用**，
   攔它們是本網關的**穩健性取捨**而不是物理限制；**兩者的理由並不相同**：TAB 是**不可見
   字元**，貼進 `.env` 或 secret 裡沒人看得見（與首尾空白同類的可診斷性問題，只是那條是物理、
   這條是取捨）；`0x80–0xFF` 則是編碼口徑問題——環境變數按 UTF-8 解、HTTP 標頭值按 Latin-1 解，
   兩邊在這一段並不由規範保證一致，
   而 RFC 9110 已把這段標為棄用。

請用純 ASCII 口令。**中間帶空格是允許的**——`correct horse battery staple` 這類 passphrase
送得出去也送得到，而且在 24 位下限之下它往往比隨機串更好記、更不容易抄錯；首尾空白由上面
那條規則管著。

##### 為什麼有 24 位的下限

**為什麼有 24 位的下限。** 本閘道**沒有任何登入限速**——不按 IP、不按權杖、也不按實例。要做它就得在儲存裡開一個計數視窗，
那等於給攻擊者一根消耗寫入配額的槓桿，把攻擊面從「猜口令」擴大到「打死 key 池的狀態回寫」。
因此口令熵是這裡唯一的防線，下限不是建議值。低於下限時面板不會啟用，容器日誌裡會有一條
`admin.token_rejected`。

##### 為什麼必須與 `GATEWAY_TOKEN` 不同

**為什麼必須與 `GATEWAY_TOKEN` 不同。** `GATEWAY_TOKEN` 是你發給**每一個下游使用者**的中轉
口令。複用它當面板口令，等於任何拿到中轉口令的人都能讀走你的整池 key、關掉註冊機、把註冊
後端指向他自己的伺服器——從此每一次註冊的信箱、密碼、驗證碼都會被他收走。

##### 衝突怎麼被發現、怎麼處置

這條規則**只在每一個管理請求上複查，不在啟動時攔**。若兩者相同——例如用
直接編輯 `store.json` 手工把 `gatewayToken` 寫成了管理口令——管理
介面會**回傳 `503`**，同時打一條 error 級的 `admin.token_conflict`（啟動時就撞上衝突的話，
啟動日誌裡也會有同樣一條，方便你立刻看到原因）。**閘道轉發不受影響。**

**衝突一旦成立，`ADMIN_TOKEN` 必須按已洩漏處置——恢復方式只有一條：把它輪換成一把全新的口令。**
改 `.env` 之後跑一次 `docker compose up -d`，讓容器帶著新值重建。
**別只把儲存裡的 `gatewayToken` 改回去。** 那確實能讓管理介面立刻恢復（設定快取下一次重新整理之後生效，
不需要重啟），但它救的是可用性、不是安全性：衝突期間這把管理口令與中轉口令是同一個值，
而中轉口令是發給**每一個下游使用者**的——只要它曾經被發出去過（或者接下來會被發出去），
拿著它的人就能直接開你的後台。可用性可以靠改 `gatewayToken` 先恢復，
但那之後**仍然要輪換 `ADMIN_TOKEN`**，兩步都做完才算處置完。

##### 為什麼這一條刻意不在啟動時攔

**為什麼這一條刻意不在啟動時攔。** `gatewayToken` 執行中會變，而啟動時的判定沒有第二次求值的
機會：一旦在那裡把整棵 `/admin` 樹反註冊掉，衝突期間啟動的整個
Docker 容器）就會**永久 404**，把設定改回去也救不了，必須重啟——而衝突之前建好的那些只是 `503`
且改回去立刻恢復。同一份設定、同一時刻兩種結果，上面那句「不需要重啟」就成了半句假話。
相比之下 `ADMIN_TOKEN` 自身的三條規則（首尾空白 / 含送不出去的字元 / 長度不足）只取決於環境變數，執行中不會變，
所以它們仍然在啟動時攔，失效形態是 `404`。

##### 怎麼輪換，外洩了怎麼處置

`ADMIN_TOKEN` **只從環境變數讀、不從儲存讀**：面板不能自助輪換自己的鑰匙。輪換方式：改
`.env` 之後跑 `docker compose up -d`——`docker compose restart` 不行，因為容器的環境在建立
那一刻就凍住了。

**管理口令外洩 = `ADMIN_TOKEN` 外洩。** 面板把它原樣存在瀏覽器的 localStorage 裡，沒有衍生權杖，
也沒有產品內的撤銷路徑。撤銷方式只有一條：改 `.env` 裡的值之後重建容器。
面板會在 12 小時後要求重新輸入口令，但那只縮短這份 localStorage 值的可用視窗，**不等於撤銷**。
請把面板放在 TLS 之後，並且只在你信任的機器上打開它。

**這個上限做不到什麼，也一併說清楚。** 面板的 CSP 用 `connect-src 'self'` 擋住了把口令 `fetch`
到外部網域，用 `form-action 'none'` 擋住了表單外傳；但它擋不住
`location.href = "https://…?k=" + token` 這種**導覽式外傳**——CSP 規範裡已經沒有可用的指令攔它
（`navigate-to` 已被移除）。真正的解法是服務端簽發**可撤銷的衍生權杖**，那要求服務端儲存工作階段，
與「`ADMIN_TOKEN` 只從環境變數讀、不從儲存讀」這條設計約束衝突，因此留給後續版本。

#### `TRUST_PROXY` 決定用戶端 IP 從哪裡取

設了之後，登入失敗事件裡的用戶端 IP 取自 `CF-Connecting-IP`，缺席時才退到
`X-Forwarded-For` 的首段。

**`TRUST_PROXY` 是安全開關，所以預設關閉。** 它決定的用戶端 IP 會寫進 `admin.login_failed`
事件，無腦信任一個由用戶端提供的標頭，等於允許任何人把爆破痕跡嫁禍給任意 IP。

**關閉時任何轉發標頭都不信，該欄位一律記 `null`——`CF-Connecting-IP` 也不例外。** 這個標頭常被說成
「平台注入、偽造不了」，但那個性質**只在請求真的經過 Cloudflare 時**成立；容器直連暴露時
沒有任何東西會覆蓋它，用戶端自己發一個 `CF-Connecting-IP: 1.2.3.4` 就會被採信——而直連正是 Docker
部署的預設形態。

**打開時 `CF-Connecting-IP` 優先，`X-Forwarded-For` 只作備援。** 兩個標頭的可偽造性根本不同：

- `CF-Connecting-IP` 由 Cloudflare 邊緣寫入，並且會**覆蓋**用戶端傳來的同名標頭——只要請求真的經過
  Cloudflare，它就偽造不了。
- `X-Forwarded-For` 是任何中介都能追加的鏈，用戶端可以自己發一個假的，可信與否完全取決於你的
  代理鏈長什麼樣。

##### 兩種拓撲各自怎麼配

**源站前面掛著 Cloudflare 時請設 `TRUST_PROXY=1`。** Cloudflare 會在每個請求上重寫
`CF-Connecting-IP`，它因此是權威值；這種形態下優先 `X-Forwarded-For` 是錯的——那條鏈裡可能
裝著用戶端自己塞的東西。不設這個開關的話，該欄位就只是記成 `null`。**等源站真的不能被直連
之後再打開它**，否則繞過 CDN 的用戶端會自己帶一個標頭進來。

**通用反向代理（nginx / Caddy / Traefik）後面打開 `TRUST_PROXY=1` 時，請在反向代理上把
`CF-Connecting-IP` 剝掉。** 那種拓撲裡沒有任何東西會覆蓋這個標頭，而閘道按「Cloudflare 在前面」
優先採信它，於是攻擊者自帶一個就會**壓過**反向代理剛寫好的 `X-Forwarded-For`。nginx 加一行即可：

```nginx
proxy_set_header CF-Connecting-IP "";
```

Caddy 用 `header_up CF-Connecting-IP ""`，Traefik 用中介軟體的 `customRequestHeaders`。

##### 形態檢查，拿不到就如實記 `null`

**兩個標頭都會先過一遍形態檢查**：只有 IPv4 點分十進位與 IPv6 形態（十六進位、冒號，以及
`::ffff:` 映射裡的點）能進事件，其餘一律記 `null`。這條不是鑑權防線（這個值全倉只有登入失敗
事件一個消費點），它防的是「未鑑權的呼叫方往稽核欄位裡塞任意文字」——管理面板的事件區塊
要按這個欄位做篩選與顯示。

什麼都拿不到時該欄位如實記 `null`，**絕不偽造一個 `"unknown"`**——那會被當成一個真實來源。

### 設定頁能改什麼

這幾個欄位在面板上分三張卡：**認證密鑰**與**上游與冷卻**在**設定**頁上，**註冊機**那張
（含兩條完全平級的郵箱通道子卡與一個「進階」摺疊區）在**註冊機**板塊的「設定」分頁裡。
三張卡寫的都是**儲存裡那個 `config` 鍵**，而不是環境變數。

**每個欄位顯示三個值，不是一個。** 一行「儲存 X · 環境變數 Y · 生效 Z」把
「你儲存的是什麼」「部署那一側給了什麼」「網關實際在用什麼」分開寫。
優先級恆為 **環境變數 > 儲存 > 內建取值**。

#### 被環境變數鎖定的欄位，面板直接不讓改

**被環境變數鎖定的欄位，面板改了不會生效——所以面板直接不讓改。**
那一格的輸入框置灰，旁邊寫著是哪個環境變數、以及要改就得改部署那一側。
`PUT /admin/api/config` 對這類欄位一律回傳 `400 locked_by_env`，**不寫儲存**：
寫下去的後果是「儲存成功、生效值紋絲不動」，維運會以為是快取沒刷，白等兩輪。

> [!IMPORTANT]
> **註冊機那一族（`REGISTRAR_ENABLED` / `REGISTRAR_CHANNEL`（連同它的相容別名）/
> `TARGET_KEYS` / `MINT_BATCH` / `TEND_INTERVAL_MS` / `CODE_TIMEOUT_MS` / `MINT_DELAY_MIN_MS` /
> `MINT_DELAY_MAX_MS` / `MAX_DOMAIN_ATTEMPTS` / `REGISTRAR_TOKEN_NAME` / `AGNES_PLATFORM_URL` /
> `YYDS_BASE_URL` / `YYDS_API_KEY` / `MOEMAIL_BASE_URL` / `MOEMAIL_API_KEY`）也進了這張鎖定表。**
> 在此之前它們不在表裡：`docker-compose.yml` 裡寫了 `TARGET_KEYS=30`、面板上改成 20，
> 儲存成功而生效值永遠是 30，**重啟也不會好**，面板上還沒有任何提示。

#### 憑據只寫不讀

**憑據只寫不讀。** 網關口令與兩條通道的 API Key 在介面裡**永遠不回傳明文**，只回傳
「配沒配」與**末 4 位**（不足 5 位時連末 4 位都不給——給了就是給全）。因此：

- 輸入框永遠是空的，佔位符寫著**留空則不修改**；
- 儲存時這幾格**缺席或留空 = 不改**（不是清空）。若把留空實作成清空，維運儲存一次設定頁
  就會抹掉網關口令，而**當前行程靠上一份快照還能繼續跑**，直到下一次重啟才整個停擺；
- 清空只能走那顆單獨的「清空」按鈕（帶二次確認）。

##### 面板寫進去的憑據怎麼落盤

> [!WARNING]
> **面板寫進去的憑據以明文落在 `store.json` 裡**，與「key 明文存檔」同一水位。
> 別以為這裡輸的是加密過的 secret。資料目錄請按憑據處置。

> [!WARNING]
> **清掉網關口令而環境變數裡也沒有 `GATEWAY_TOKEN` 時**：當前行程還能跑，
> 但**下一次重啟會起不來**。面板會當場用一條紅色提示說破這件事，
> 恢復方式是立刻在同一頁寫一把新的網關口令。**而環境變數裡有這一項時清空是安全的**：清掉的只是儲存裡那一份，生效值回落到環境變數，紋絲不動——面板會按這兩種狀態說兩句不同的話，不會讓你自己猜。

#### 「進階」區裡的那個註冊後端位址

> [!WARNING]
> **「進階」摺疊區裡那個註冊後端位址（`AGNES_PLATFORM_URL`）不是普通設定項。**
> 它是**每一次自動註冊的去向**：換成別的伺服器，那台伺服器就會收到本網關註冊時用的
> 信箱、密碼與驗證碼。所以它摺在進階區裡、帶紅色警告、有自己的二次確認按鈕，
> 不跟主表單那顆「儲存」一起走。

#### 儲存回執與傳播延遲

**儲存之後面板不彈「已儲存並生效」**，而是**回讀**一遍生效值，把真的變了的欄位標示出來，
並寫明**別的副本最長多久才看得到**：設定持有者最多每 **30** 秒重新整理一次，那就是上界。
本實例是立刻生效的（儲存那一步會作廢本地快取），共用同一個卷的別的容器不是。
**面板文案不許寫「立即生效」。**

### 註冊機相關變數（可選，預設關閉）

註冊機是一套可選的自動補池元件，預設關閉，不影響閘道的核心轉發功能。以下僅列變數
速查，運作原理、兩條信箱通道如何選擇、一輪補池最長要跑多久等完整說明見
[REGISTRAR.md](REGISTRAR.md)。

| 變數 | 是否必填 | 預設值 | 說明 |
|----|--------|------|----|
| `REGISTRAR_ENABLED` | 否 | `false` | 總開關，須為 `true` 才會啟用註冊機。 |
| `REGISTRAR_CHANNEL` | 啟用時必填 | 無 | 註冊機用哪一條通道，`yyds` 或 `moemail`；兩條通道二選一，無預設值。 |
| `TARGET_KEYS` | 否 | `20` | 目標可用 key 數。 |

| `TEND_INTERVAL_MS` | 否 | `1800000` | 多久跑一輪補池。同一個計時器也負責 `pool:index` 對帳，所以註冊機關著時它照樣在跑。 |
| `CODE_TIMEOUT_MS` | 否 | `120000` | 輪詢驗證碼的逾時。 |
| `MINT_DELAY_MIN_MS` / `MINT_DELAY_MAX_MS` | 否 | `60000` / `90000` | 每次鑄 key 之間的隨機間隔。下限是實測出來的（間隔小於它時上游前置的限流會切進來）；上限只是抖動餘量。 |

| `MOEMAIL_BASE_URL` / `MOEMAIL_API_KEY` | 通道為 moemail 時必填 | 空 / 空 | MoeMail 通道憑證（自建服務，無預設位址）。 |

> [!NOTE]
> **兩個已棄用的舊名字，刻意不進上表。** `REGISTRAR_PRIMARY` 是 `REGISTRAR_CHANNEL` 的
> **相容別名**（優先級更低，用到它時面板頂部有一條提示，那一格照樣置灰）；
> `REGISTRAR_FALLBACK` **不再參與選路**，只被讀一次，用來在面板上點名告訴你

> 裡已經不再宣告它們——新部署直接用新名字。

> [!WARNING]
> **這 15 個變數寫錯值不會再讓容器起不來。**
> 數值類（`TARGET_KEYS=abc`、`MINT_BATCH=0` 這一族）**回落到上表的預設值**，
> 在面板上報一次降級、並記一條 `config.invalid` 事件；通道與憑證類
>（通道名拼錯、註冊機開著卻沒選通道、選中那條通道缺 API Key）
> 只讓**註冊機**本次不啟動，閘道照常轉發。
>
> **這是一次能力下降，明說**：從前一個部署筆誤會讓容器崩掉，所以你立刻就知道；
> 現在它安靜地跑著，得自己去看面板橫幅或者事件板塊。
> 走一遍的入口是下面「常見問題排除」裡的「註冊機開著卻不鑄 key」那一條。

### 兩檔逾時各自管什麼

判準是「上游的第一個位元組什麼時候才可能到達」，不是端點的名字：

| 檔位 | 適用端點 | 用哪個變數 |
|----|--------|----------|
| 首位元組檔 | **串流**對話（`stream: true`）、影片輪詢 `GET /v1/videos/{id}` | `UPSTREAM_TIMEOUT_MS` |
| 同步檔 | 圖片生成、影片建任務、**所有非串流對話**（四種協定皆是） | `UPSTREAM_SYNC_TIMEOUT_MS` |

非串流請求要等上游把整段回答生成完才發回應標頭，和圖片生成是同一種延遲語意，用 8 秒的
首位元組檔去卡它只會讓正常請求大量失敗並連累 key 池。

`UPSTREAM_SYNC_TIMEOUT_MS` 是**一次請求的總預算**，也就是用戶端的最壞等待時間——不是
「池大小 × 預算」。閘道在這個預算裡最多為單一 key 花掉一半，剩下的用來換一把 key 再試，
這樣池裡有一把 key 掛起（連得上但永不回應）時不會白白吃掉這次請求。因此請把它設成
**單次呼叫最壞耗時的兩倍以上**。

同步檔逾時不會立刻懲罰 key：只有當同一次請求裡換的另一把 key 真的成功了，閘道才把逾時
算到先逾時的那把 key 頭上（累積到 `MAX_STRIKES` 進冷卻）；如果本次請求裡每一把都逾時，
則一把都不懲罰——那更可能是預算設太小或上游整體變慢。

「剔除」與「冷卻」是兩回事。不論上述參數如何設定，上游 `401`/`403` 都會**永久**剔除該
key——這兩種狀態被視為「這把 key 已失效」，重試沒有意義。瞬時故障則永遠不會導致剔除：
累積到 `MAX_STRIKES` 只是進入 `COOLDOWN_STRIKE_MS` 的冷卻，到期自動恢復，因此上游抽風
不會永久損毀你的 key 池。

當沒有任何 key 能服務本次請求時，閘道回傳 `503`，並在 `error.reason` 中給出可判別的原因：
`pool_empty`（尚未匯入 key）、`all_cooling`（全部 key 冷卻中，會自動恢復，回應標頭
`Retry-After` 給出恢復時刻）、`all_evicted`（全部 key 因憑證失效被永久剔除，**不會**自癒，
請更換 key）、`upstream_error`（key 本身可用，但上游每次嘗試都失敗）。

### 超長的非串流請求會不會被從中間砍斷（取決於擋在前面的那一層）

**結論：閘道自己除了 `UPSTREAM_SYNC_TIMEOUT_MS` 之外不設任何牆鐘，所以能把一個健康的長
請求砍斷的，只可能是擋在它前面的東西。**

容器裡跑的這個 Node 行程**沒有任何平台時長上限**：一次非串流請求只受你配的預算約束，
再沒有別的。這就是本文做出的全部承諾，面板也不做更大的承諾。

**擋在你前面的那一層要你自己去查**，逐條寫明：

- 反向代理有自己的讀取逾時，而且預設值都不長：nginx 的 `proxy_read_timeout` 是 60 秒，
  Caddy 自己不限但它的上游未必。要調就與 `UPSTREAM_SYNC_TIMEOUT_MS` 一起調，否則先砍
  的是代理。
- 源站前面再掛 CDN 會多一層：Cloudflare 文件化的**回源讀取逾時是 100 秒（錯誤碼 524）**，
  閘道任何設定都延長不了它。
- 負載平衡器的閒置逾時同理，而且從用戶端那一側看症狀一模一樣：連線就這麼斷了，
  連一個 `error.reason` 都沒有。

⇒ **實際影響兩條**：
① 把 `UPSTREAM_SYNC_TIMEOUT_MS`（預設 120000）設在**你前面那條鏈裡最緊的那個逾時之下**，
   否則本來閘道能跑完的請求會被別人砍斷，而那個原因永遠進不了日誌。
② **真要跑長請求就用串流端點。** 首位元組檔只管首位元組，之後生成花多久都不計；而且一條
   持續出位元組的串流，在整條鏈上看起來都不像「閒置」。

## 多帳號設定

匯入 key 的常規路徑是管理面板，或者直接呼叫 `POST /admin/api/keys`（一次最多 200 把，
見 [API.md](API.md) 與 [ADMIN.md](ADMIN.md)）。下面這套**直接寫儲存後端**的做法只用於
兩種場景：還沒設 `ADMIN_TOKEN`（面板整棵樹都不註冊），或者面板不可用時的應急復原。
它**不會更新 `pool:index`**，因此新記錄未必立刻可見，代價見下面的「索引與可見延遲」。
每筆記錄是一個
鍵為 `key:<id>` 的 JSON 物件，`<id>` 可以是池內唯一的任意字串（閘道自己建立記錄時
會用 key 的雜湊值推導一個，但讀取時不會校驗這個值，所以手動匯入時用任意唯一識別碼
即可）：

```json
{
  "id": "1a2b3c4d5e6f7a8b",
  "key": "你的真實-agnes-api-key",
  "addedAt": 1735689600000,
  "lastUsedAt": null,
  "cooldownUntil": 0,
  "strikes": 0,
  "evicted": false,
  "evictedReason": null
}
```

### 匯入到 Docker

先停止容器，避免與正在執行的程序產生寫入競爭；在主機上編輯 `./data/store.json`，
在鍵 `"key:1a2b3c4d5e6f7a8b"` 下加入如上記錄，然後再啟動容器：

```bash
docker compose stop
# 編輯 ./data/store.json
docker compose start
```

若 `./data/store.json` 尚不存在，直接新建一個 JSON 物件檔案，鍵為若干個
`key:<id>` 字串即可。

### 索引與可見延遲

閘道用一個 `pool:index` 鍵保存池內的 id 清單，這樣每次轉發都不必掃全庫。**手動寫記錄不會
動這個索引**，所以新 key 多久能被用上，取決於池子當時的狀態：

- **池子為空時**：索引說池子是空的、記錄也確實一條都讀不到，閘道會回落一次掃描把手動匯入
  的記錄發現並補進索引。這條掃描有內建的 10 分鐘退避（見上文「key 池與它的索引」），因此
  可見上界是 **≤10 分鐘 + 一個 `POOL_CACHE_TTL_MS`**。
- **池子非空時**：轉發路徑只按索引取記錄，索引不知道的記錄**完全隱身**，而且沒有任何報錯。
  它要等下一次對帳把索引修好（`TEND_INTERVAL_MS`，預設 30 分鐘），之後再等最多一個
  `POOL_CACHE_TTL_MS`。

**想讓手動匯入立刻生效，就在同一次編輯裡把 id 補進 `pool:index`：**

```json
{"v":1,"ids":["已有的id","1a2b3c4d5e6f7a8b"]}
```

索引寫完之後，池子最多再等一個 `POOL_CACHE_TTL_MS` 就會用上這把 key。

**對帳與註冊機開沒開無關**，走的是同一個 `TEND_INTERVAL_MS` 計時器：它是 `pool:index` 與
實際 `key:` 記錄之間唯一的修復路徑，所以孤兒記錄或幽靈索引項會在一個間隔之內被收回。
把這個間隔設成一個離譜的大值，這段等待就等量變長；等待期間該 key 只是暫時用不上，
不會遺失也不會損壞。

### 吊銷一把 key

**刪記錄、再把 id 從 `pool:index` 裡摘掉，兩步都要做。** 只刪記錄不會出錯（讀不到的記錄會被
直接過濾掉），但索引裡那個 id 還在，每次重新整理都白付一次讀，要等下一次對帳才會被剪掉。

在 `./data/store.json` 裡刪掉 `"key:<id>"` 那個鍵，並把 `"pool:index"` 的 `ids` 陣列改好；
先 `docker compose stop`，免得還在跑的行程把你的編輯覆蓋掉：

```json
{"v":1,"ids":["剩下的id"]}
```

已經裝載了舊快照的行程最多再等一個 `POOL_CACHE_TTL_MS` 才會停止選中這把 key。

**這段視窗裡它也不會被寫回來**：閘道在落盤任何狀態變更之前都會先確認記錄還在，讀不到就
丟棄這次寫並立刻重新整理自己的快照。檔案儲存的這次確認讀直接讀檔案、中間沒有任何快取，
所以這條保證是精確的。

## 驗證

三條命令，從最便宜的一條開始。把 `$BASE` 換成你自己的位址（沒改 `PORT`、前面也沒掛網域
的話就是 `http://localhost:8080`），`$TOKEN` 換成你設的 `GATEWAY_TOKEN`。

### 健康檢查

```bash
curl -s "$BASE/health"
```

`status` 為 `ok` 表示儲存可讀可寫；`degraded` 表示儲存那一側有問題，具體原因見日誌。
**這一條不需要權杖**，所以它也是唯一一條在權杖設錯時仍然回得來的端點。

### 模型清單

```bash
curl -s "$BASE/v1/models" -H "Authorization: Bearer $TOKEN"
```

回來的是本閘道支援的模型清單。這一條能過，說明權杖對上了；回 `401` 就是權杖不對。

### 一次真實對話

```bash
curl -s "$BASE/v1/chat/completions" \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"model":"agnes-2.0-flash","messages":[{"role":"user","content":"ping"}]}'
```

這一條才真的打到上游。回 `503` 且 `error.reason` 是 `pool_empty`，說明池子裡還沒有 key，
回上面那一節匯入一把。

## 常見問題排除

七條按會遇到的先後排。每條都是「症狀 → 解決方案」，解決方案按順序做。

### 閘道起不來，日誌裡只有一行缺少權杖

**症狀**：容器**一啟動就退出**，`docker compose ps` 上是 restarting 或 exited，日誌裡只有
`缺少 GATEWAY_TOKEN，網關無法啟動` 這一行。**這裡沒有「半死不活」這一檔**：閘道寧可拒絕裝配，
也不會每個請求回 `503`，所以不用誰去打端點，`docker compose ps` 上就看得見。

**解決方案**：

1. 確認 `.env` 裡有 `GATEWAY_TOKEN=`，而且**等號後面不是空的**。
2. 改完跑 `docker compose up -d`，**別用 `docker compose restart`**——容器的環境在建立那一刻
   就凍住了，restart 什麼都不會重讀。

> [!WARNING]
> **不要用 `RESET_CONFIG=1` 來救這一條。** 它的語義是**完全忽略儲存裡的 `config` 鍵**
> ——如果你的閘道權杖正是存在那裡的（面板儲存的那把），忽略它只會讓唯一的一把權杖也一起消失。
> 這條故障只有上面兩步能修。

### 所有請求都回 503，理由是池子空的

**症狀**：任何一條轉發端點都回 `503`，`error.reason` 是 `pool_empty`。

**解決方案**：

1. 在管理面板的 key 池頁匯入至少一把 key，或者呼叫 `POST /admin/api/keys`（見 [API.md](API.md)）；沒設 `ADMIN_TOKEN` 時按「多帳號設定」那一節直接寫儲存後端。
2. 已經匯入了卻仍然是空的：手工寫記錄**不會動 `pool:index`**，等一次對帳（`TEND_INTERVAL_MS`，預設 30 分鐘）或者手動把 id 補進索引。
3. 註冊機開著但池子不漲：去看面板的事件板塊，或按 [REGISTRAR.md](REGISTRAR.md) 排查兩條信箱通道。

### 註冊機開著卻不鑄 key（面板說已啟用，池子卻一直不漲）

**症狀**：註冊機的開關是開著的，但補池一輪都沒跑：池子裡的 key 只減不增，
最終以上面那條「所有請求都回 503，理由是池子空的」的形式炸出來——而那時離真正的原因已經隔了好幾層。

這是一次**安靜的功能缺失**：註冊機是選用子系統，它的設定裝不起來時**閘道照常轉發**，
只是不再補池。沒有任何東西會崩，所以你得主動去看。

**怎麼看**（四處指的是同一件事）：

1. 管理面板的**設定**頁頂部有一條橫幅：「註冊機開著，但這份設定裝不起來，本次沒有啟動它；轉發不受影響」，
   下面逐條列出缺哪幾格。
2. **註冊機**板塊的執行狀態那一行寫的是「已啟用 · 本次沒跑起來」，不是「已啟用」。
3. **總覽**頁的設定摘要裡，「註冊機」那一行同樣寫「已啟用 · 本次沒跑起來」。
4. 事件板塊裡每一輪都有一條 `error` 級的 `registrar.blocked`，欄位裡列出缺的那幾格。

**解決方案**：按橫幅列出的那幾格去設定頁補齊（最常見的是選中那條郵箱通道缺 API Key，
或者壓根沒選通道），**儲存即可恢復，不需要重啟容器、也不需要重新部署**。

### 面板打不開，`/admin` 回 404

**症狀**：瀏覽器打開 `/admin` 得到 `404`，不是登入頁，也不是 `401`。

**解決方案**：

1. 這就是**沒設定 `ADMIN_TOKEN`** 時的正常形態：整棵樹根本沒註冊，所以不會洩漏「這裡有個後台」。
2. 設定了仍然 404，**先確認容器真的重建過**：Docker 形態下改完 `.env` 要跑 `docker compose up -d`，`docker compose restart` 不會重讀它。這一步沒做的話，下面第 3 條會把你引向一個錯誤的方向。
3. 重建過仍然 404：口令不合規（少於 24 位 / 首尾有空白 / 含非可列印 ASCII），容器日誌裡會有一條 `admin.token_rejected`。
4. 面板能開但介面回 `503`：`ADMIN_TOKEN` 與儲存裡的 `gatewayToken` 撞了，日誌裡是 `admin.token_conflict`，按上文那一段處置。

### 改了面板裡的設定，別的實例半天不生效

**症狀**：在面板裡儲存了設定，本實例立刻變了，共用同一個卷的另一個容器還是舊值。

**解決方案**：

1. 這是**正常的**：設定持有者最多每 **30** 秒重新整理一次，那就是上界。等一等再看。
2. 超過兩分鐘仍然不變：確認那個欄位沒有被環境變數鎖住——被鎖的欄位面板會置灰，介面回 `400 locked_by_env`。
3. 改的是 `POOL_CACHE_TTL_MS` / `POOL_TOUCH_INTERVAL_MS` 這兩個旋鈕：它們**建立實例時讀一次**，只能重建容器。

### 非串流請求大量逾時，key 池跟著變紅

**症狀**：圖片生成、影片建任務或非串流對話成片逾時，面板上一批 key 進了冷卻。

**解決方案**：

1. 把 `UPSTREAM_SYNC_TIMEOUT_MS` 調到**單次呼叫最壞耗時的兩倍以上**：預設 `120000` 對慢模型偏緊。
2. 別拿 `UPSTREAM_TIMEOUT_MS`（首位元組檔，預設 `8000`）去卡非串流請求——那一檔是給串流與影片輪詢的。
3. 確認不是上游整體變慢：同一次請求裡每一把 key 都逾時時，閘道**一把都不懲罰**，冷卻只會在換的另一把真的成功之後才記。

### Docker 容器起來了，但 `/health` 是 degraded

**症狀**：`docker compose ps` 顯示 unhealthy，`/health` 回 `503`，`status` 是 `degraded`。

**解決方案**：

1. 九成是資料目錄寫不進去。看容器日誌裡 entrypoint 那幾行，確認 `./data` 的擁有者是不是 `100:101`。
2. 用 `--user` 或 compose 的 `user:` 指定了非 root 執行時，entrypoint **不會** chown，擁有者與可寫性得你自己準備。
3. `DATA_DIR` 被設成 `/` 或某個頂層系統目錄時 entrypoint 拒絕遞迴 chown，只印警告——換一個正常的目錄。
4. **擁有者查了三遍都對，卻還是 degraded**：多半是 `store.json` 解析不了。前三條全是權限，這一條不是——儲存層讀不出合法 JSON 時每次讀寫都拋，啟動探測因此把「可寫」記成 false，`/health` 同樣回 `503` degraded。停容器後 `python3 -m json.tool ./data/store.json` 驗一下：上文「多帳號設定」教的手工編輯正是最常見的寫壞方式（多一個逗號就夠），壞了就從備份還原。真因原文在容器日誌的第一行。

## 效能優化

先認清一件事：**這個閘道自己幾乎不花時間**，開銷在兩處——上游的回應時間，以及儲存的讀寫配額。
所以這一節只有三個旋鈕值得動。

```env
# 選填：每個行程快取 key 池快照的存活時長，單位毫秒；0 = 關閉快取。
# 調大 = 省檔案讀取；代價是其他容器寫下的狀態更晚才可見。
POOL_CACHE_TTL_MS=120000

# 選填：「最後使用時間」最多多久寫入一次，單位毫秒；0 = 每次成功請求都寫入。
# 它是純展示欄位，調小只會等量放大寫入次數，換不來任何排程上的好處。
POOL_TOUCH_INTERVAL_MS=21600000

# 選填：同步端點（圖片、影片建任務、所有非串流對話）的整體逾時預算，單位毫秒。
# 設成單次呼叫最壞耗時的兩倍以上，否則正常請求會被誤殺並連累 key 池。
UPSTREAM_SYNC_TIMEOUT_MS=180000
```

三條經驗，按收益排：

1. **除非有多個容器共用一個卷，否則別動 `POOL_CACHE_TTL_MS`。** 單容器時那份快照就是權威，
   調大它買不到任何東西，只會讓「手工改了 `store.json`」這件事更晚被發現。真跑起副本、
   而且看到同一把 key 被判兩遍的時候，再調大它。
2. **別為了讓面板上的「最後使用」準一點去調小 `POOL_TOUCH_INTERVAL_MS`。**
   那是純展示欄位，`0` 的意思是「每次成功請求都整份重寫一遍儲存」，而你買到的那個精度
   沒有任何排程邏輯會去讀。
3. **長請求改用串流端點。** 首位元組檔的逾時只卡第一個位元組，後面生成多久都不再計時；
   非串流那一檔要等上游把整段答案算完，而擋在你前面的代理可能比你的預算先動手。

## 監控與維護

### 健康端點

`/health` 是唯一不需要權杖的端點，兩種形態都有：

```bash
curl -s "$BASE/health"
```

`status` 為 `ok` = 儲存可讀可寫；`degraded` = 儲存那一側有問題（Docker 上多半是資料目錄寫不進去）。
Docker 形態下映像內建的 `HEALTHCHECK` 就是打這條，`docker compose ps` 裡的 healthy/unhealthy 由它來。

### 面板的事件板塊

設定了 `ADMIN_TOKEN` 之後，面板的事件板塊會按級別列出閘道自己記下來的診斷事件
（登入失敗、口令衝突、補池失敗、預算耗盡……）。它**不是日誌的替代品**：只保留 24 小時，
而且單次輪詢最多回看 48 個鍵。要長期留存就去接容器日誌。

### 用量統計（預設關）

按天／小時／模型／協定的時間序列**預設關**，而且「關」是零成本的——不建累加器、一次儲存寫都沒有。
要打開：

```env
# 選填：面板「用量」板塊的 Tier-2 時間序列。判據是逐字的 true，寫 1 / yes 都算關。
# 打開之後每個實例每個落盤間隔重寫一次分片；未落盤的尾巴最長 2 小時。
# 那條尾巴會直接變成丟數：行程在這段視窗裡停掉，計數就隨它消失，不是延遲入帳。
USAGE_STATS_ENABLED=true
```

**打開之前先讀一遍上面那兩條警示。** 會丟的正是行程停掉那一刻還攥在手裡的那些計數，
而為改一個環境變數重建一次容器就足以觸發它。本形態下 `USAGE_FLUSH_INTERVAL_MS` 想調多小
就調多小——這筆取捨歸你，不是外面強加的限制。

## 升級服務

兩條升級命令寫在 [Docker 部署](#docker-部署) 的「更新」裡。這一節講的是那兩條命令之外的事。

### 升級前

1. **先備份儲存。** key 池與設定只有一份，見下文「備份與還原」。
2. **記下基線：目前的 `version` 與 key 池筆數。** 前者就是 `curl -s "$BASE/health"` 回的那個欄位，後者在面板概覽頁。沒有基線，下面那三條確認就分不清「升上去了」和「根本沒升」。
3. **看一眼 CHANGELOG。** 破壞性變更會寫在那裡；本倉庫的版本號在六份 README 的徽章上。
4. **升級不需要清空儲存。** 儲存裡的記錄是向後相容的，`pool:index` 的 `v` 欄位今天恆為 `1`。

### 升級之後確認什麼

1. `/health` 回 `200`、`status` 為 `ok`，**並且 `version` 等於你這次升的版本號**。三條裡只有這半句分得開「升上去了」和「根本沒升」：`version` 是編譯期常數、燒在映像裡，而另外兩條在舊版本上一字不差地全綠。映像沒發出去時（建置被取消而 Release 已經發了，本倉庫真出過一次）`docker compose pull` 是一次靜默成功的空操作。
2. 面板（如果開著）能登入，key 池的筆數與升級前一致；概覽頁執行時那一格也寫著版本號，與上一條互為佐證。
3. 跑一次上文「驗證」裡的第三條，確認真的能打到上游。

回滾：Docker 把 `.env` 裡的 `IMAGE_TAG` 改回上一版再 `docker compose up -d`（映像全名與
tag 列在哪兒，見上文「Docker 部署 → 更新」）。
**先確認那個 tag 在 registry 上真的存在**：拉不到時 compose 不會當場失敗，而是拿你**目前
工作樹**本機建置一個頂著那個版本號的映像，於是回滾「成功」而故障照舊。

## 備份與還原

key 池與設定只有一份，沒有第二副本。**備份就是備份儲存本身。**

### 怎麼備份

```bash
docker compose stop
cp -a ./data ./data.bak
docker compose start
```

停一下再拷是為了避開寫入競爭。還原就是把目錄拷回去再 `docker compose up -d`。

### 裡面有什麼，以及為什麼挑著抄是個坑

`./data/store.json` 裡就是全部——不只是 key 記錄與 `pool:index`，還有
`apikeys`（已簽發的對外 API 密鑰表）、`config`（面板儲存的那份設定）、
`registrar:domains` 與 `registrar:backoff`（註冊機的網域可用性與退避帳）、
`tend:history`（補池歷史），以及事件環。

> [!CAUTION]
> **只從那份檔案裡挑 `key:<id>` 與 `pool:index` 抄出來，會漏掉四族鍵，而漏掉它們在還原現場一點都看不出來。**
> 照那種清單還原之後：上游 key 池回來了、`/health` 回 `ok`、你自己拿 `GATEWAY_TOKEN`
> 一測也通——而每一個下游使用者手上的子密鑰全部 `401`。漏的是這四族：
> `apikeys`（已簽發的對外 API 密鑰表，不還原它等於把所有子密鑰一次吊銷，而明文只在
> 簽發那一次給過、找不回來，只能全部重發一遍）、`config`（面板儲存的設定，含閘道口令
> 與兩條信箱通道的憑證）、`registrar:domains` 與 `registrar:backoff`（丟了之後註冊機變成
> 「已啟用 · 本次沒跑起來」）、`tend:history`（補池歷史）。

> [!WARNING]
> 備份檔案裡是**明文 key 與明文憑證**（閘道口令、兩條信箱通道的 API Key 都在儲存側的設定裡）。
> 請按憑證處置：別放進倉庫、別放進公開的物件儲存。

## 安全建議

- **`GATEWAY_TOKEN` 與 `ADMIN_TOKEN` 必須是兩把不同的口令。** 前者是發給**每一個下游使用者**的中轉口令，
  拿它當面板口令等於把整池 key、註冊機開關、註冊後端位址一起交出去。
- **面板放在 TLS 之後，只在你信任的機器上打開。** 面板把 `ADMIN_TOKEN` 原樣存在瀏覽器的 localStorage 裡，
  沒有衍生權杖、也沒有產品內的撤銷路徑；12 小時後要求重新輸入只縮短視窗，**不等於撤銷**。
- **`TRUST_PROXY` 只在閘道真的位於代理之後時才打開。** 通用反代後面打開它時，請在反代上把
  `CF-Connecting-IP` 剝掉，否則攻擊者自帶一個就能壓過反代剛寫好的 `X-Forwarded-For`。
- **資料目錄與備份檔案一律按憑證處置。** key 與面板寫進去的憑證都是明文落盤的，
  與 key 明文存檔是同一水位。
### 對外 API 密鑰與上游 key 池方向相反

- **對外 API 密鑰的明文只出現一次。** 面板簽發時那一次回應裡帶著它，此後任何介面都拿不到
  ——閘道只存它的 SHA-256 摘要。丟了找不回來，只能刪掉重發；**這與上游 key 池是相反的兩件事**
  （那一族必須明文落盤，因為要拿去用）。
- **給不同的下游各發一把子密鑰，別把 `GATEWAY_TOKEN` 分出去。** 前者可以逐把停用、設到期、
  隨時吊銷，而後者一旦分出去，唯一的撤銷方式是輪換它、讓所有下游同時失效。

一份最小的安全基線設定：

```env
# 必填：用戶端呼叫本閘道時必須攜帶的權杖。發給下游使用者的就是它。
GATEWAY_TOKEN=換成你自己的長隨機串

# 選填：管理面板口令。不設 = 整棵 /admin 樹不註冊，存取得到 404 而不是 401。
# 必須與 GATEWAY_TOKEN 不同，且至少 24 位、純可列印 ASCII。
ADMIN_TOKEN=換成另一把長隨機串

# 選填：容器確實位於會改寫用戶端位址的代理或 CDN 之後時才設成 1。
# 直接暴露的部署不要設它。
TRUST_PROXY=1
```
